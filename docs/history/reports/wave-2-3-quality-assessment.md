## Прямой ответ

# ПРОДОЛЖАТЬ С УСЛОВИЯМИ

Не «продолжать как есть» и не «остановить». Три факта вместе не оставляют третьего варианта:

1. **Код, который реально написан, — хорошего качества.** Чистый домен, порты/адаптеры без
   единого нарушения в проверенных файлах, честные фасады, работающая FSM-логика, 26
   полноценных use case, добросовестный seed на 317 позиций. Выбрасывать это дороже, чем
   чинить (обоснование — раздел «Экономика решения»).
2. **Волна физически не готова к тому, чтобы поверх неё стартовала волна 4.** Модуль
   каталога недостижим извне (`CatalogModule` — пустой `@Module({})`, не в
   `AppModule.imports`), EP-05 (волна 4) по графу зависимостей `00-EPICS.md` требует
   закрытого EP-04. Восемь администраторских эндпоинтов открыты без аутентификации.
   `db:seed` физически не грузит данные, которые нужны следующей волне.
3. **Причина провала — не архитектура, а недоверие к самоотчёту.** Все шесть находок,
   ломающих картину «9 из 9 зелёные», обнаруживаются за секунды прямой командой
   (`vitest run`, `grep`, чтение `app.module.ts`) — они не были скрыты, их просто не
   проверили перед тем как объявить волну готовой. Это чинится процессом, не переписыванием
   кода.

Условия, при которых «продолжать» — это не то же самое, что «продолжать в лоб» (сценарий А
ниже), раскрыты в разделах 5-7. Без них ответ был бы «не продолжать» — тот же паттерн на
EP-09/EP-10 (деньги, escrow) не тикет, а системный риск для бизнеса.

## Что сделано хорошо

Честно и с примерами — это не комплимент для баланса, а фактическая база, на которой строится
рекомендация «не переписывать».

- **Домен чист буквально, а не на словах.** Лично проверил `apps/api/src/modules/onboarding/domain/pharmacy-account.entity.ts`
  и `apps/api/src/modules/catalog/domain/medicine.entity.ts` — ни одного импорта
  `@nestjs/*`/`drizzle-orm`/`ioredis`/`bullmq`/`fastify`. Приватные конструкторы, фабрики
  `create()`/`restore()`, ошибки — собственные классы (`domain-error.ts`), не `HttpException`.
- **Порты и адаптеры выдержаны без исключений** в проверенных use case: зависимости приходят
  через конструктор с DI-токенами, ни одного `new` инфраструктурного класса внутри
  `application/`.
- **`tests/arch/run-fixture-check.spec.ts`** — редкая по качеству практика: реальные
  фикстуры-нарушители прогоняются через настоящий ESLint/depcruise дочерним процессом и
  проверяют ненулевой код возврата. Это доказанный, а не декларативный гейт — единственный
  из всех гейтов волны, который я не смог уличить в слепоте.
- **State machine `OnboardingStatus`** — полная 8×8 таблица переходов с корректно замкнутыми
  терминальными состояниями (`rejected`/`terminated`), явной обработкой реактивации,
  покрыта параметризованным тестом на все 64 пары.
- **`Barcode.checkEan13Checksum`** реализует стандартный GS1 mod-10 корректно.
- **Ни одного голого сеттера** на проверенных агрегатах (`Medicine`, `Tenant`,
  `PharmacyChain`, `PharmacyAccount`) — везде методы-намерения (`attachBarcode`, `publish`,
  `proposeControlCategory`, `suspend`), включая корректную реализацию D-08
  (`proposeControlCategory` возвращает событие вместо синхронной мутации для категорий,
  требующих модерации).
- **`OnboardingFacade`** (`apps/api/src/modules/onboarding/onboarding.facade.ts`) корректно
  реализует Facade-паттерн межмодульного взаимодействия по §1.2 `02-CLEAN-ARCHITECTURE-AND-CODE.md`,
  включая нетривиальную бизнес-логику «аптека активна только если сеть тоже approved|active».
- **`NullOrdersCancellationAdapter`** — честная документированная заглушка на ещё не
  начатый EP-10, с явным TODO на конкретный эпик. Это ровно то, как нужно готовить интерфейс
  для будущей волны, не забегая в неё.
- **Seed-данные каталога реальны**: лично посчитал — `apps/api/src/db/seed/data/medicines.seed.json`
  содержит **317** позиций (не заглушка), проходят через доменную фабрику `Medicine.create()`.
- **`packages/domain-kernel` — обоснованное архитектурное решение, не самодеятельность.**
  Тикет `DTJ-090` (в `00-INDEX.md`, под-волна 1 EP-04) прямо предписывает создание пакета
  ещё в исходном wave-1 коммите — предварительная метрика архитектора здесь ошибалась, я
  подтверждаю это как факт, не как смягчение.
- **Дисциплина размера файлов и `eslint-disable` реальна.** Ни один новый файл не превышает
  300 строк; из ~51 `eslint-disable` в новом коде подавляющее большинство снабжено
  содержательным обоснованием (не голым `// eslint-disable-next-line` без комментария).
- **Обоснования архитектурных исключений (`no-restricted-imports` и т.п.) не фиктивны** —
  реальное ограничение тулчейна (`tsc`/`nest build` не переписывают алиас `@/*`), не
  придуманная отговорка.

**Вывод этого раздела:** там, где модель писала код в границах одного файла/модуля с ясным
ТЗ (тикетом), результат ровно того качества, которое было в волне 1. Проблема не в том,
*как* написан код, а в том, что́ из написанного было **подключено к системе** и **проверено
перед сдачей**.

## Что сделано плохо

По убыванию серьёзности. Каждый пункт — подтверждён лично (файл/строка/команда), не
переписан из отчётов ревьюеров без проверки.

### 1. Аутентификации не существует — 8 из 8 admin-эндпоинтов открыты (BLOCKER)

`find apps/api/src -iname "*auth*"` → пусто. Ни одного `AuthGuard`/`RolesGuard`, ни одного
`CanActivate` во всём `apps/api/src` (`grep -rln "CanActivate" apps/api/src` → пусто).
Все 8 файлов в `apps/api/src/modules/onboarding/presentation/controllers/` декорированы
`@Public()` с идентичным `TODO(EP-01): @Roles(...) + @Permissions(...)`. Это включает
`approve`/`reject`/`terminate`/`suspend`/`revoke` верификации сетей и аптек. Сегодня любой
неаутентифицированный вызывающий может выполнить любое из этих действий для любой сети/аптеки.
Дополнительно: **11 мест** (`grep -c` подтвердил) вызывают use case с захардкоженным
`actorId: '00000000-0000-0000-0000-000000000000'` — даже после появления auth аудит-лог не
будет знать, кто реально принял решение, пока это не переписано отдельно.

### 2. `TenantScopeGuard` не существует ни файлом, ни классом (BLOCKER)

Ни одного `CanActivate` в `apps/api/src` (см. выше — тот же grep покрывает оба факта разом).
`TenantResolutionMiddleware` сам, по собственному докстрингу, **не блокирует** запрос — только
резолвит контекст и передаёт решение guard'у. Guard'а нет. Значит сегодня между «JWT с
`tenantId`» и «фактическим тенантом ресурса» нет ни одной проверки в рантайме.

### 3. `TenantResolutionMiddleware` написан, но не подключён (BLOCKER, тривиален по фиксу)

`apps/api/src/app.module.ts`, метод `configure()` (строка 31): `consumer.apply(RequestContextMiddleware, HttpLoggerMiddleware).forRoutes('*')`
— только эти два middleware. Комментарий строками выше прямо говорит: «EP-02 добавляет
`TenantResolutionMiddleware` СТРОГО ПОСЛЕ этих двух строк» — этого не произошло. Файл
middleware существует (166 строк, реализация качественная — тройной приоритет резолвинга
Host → X-Tenant-Slug → neutral, Redis-кэш с fallback), но `grep` по всему `apps/` показывает,
что класс упоминается **только** в JSDoc-комментариях 7 файлов, ни разу — в реальном
`consumer.apply(...)`. `TenantContext.current()` сегодня всегда `undefined` в рантайме.

### 4. `CatalogModule` — пустой `@Module({})`, каталога снаружи не существует (BLOCKER)

`apps/api/src/modules/catalog/catalog.module.ts` — класс декорирован буквально `@Module({})`,
собственный комментарий признаёт: «Сейчас модуль пуст». `apps/api/src/modules/catalog/{application,infrastructure,presentation}/`
содержат только `README.md`, ни одного `.ts`. `app.module.ts` `imports: [...]` не содержит
`CatalogModule`. Итог: нет ни одного HTTP-эндпоинта каталога (`GET /categories`,
`GET /medicines/:id` и т.д. не существуют), при том что домен (`Medicine`, VO, инварианты)
реализован аккуратно и протестирован. **Это прямой блокер волны 4**: EP-05 (Приём остатков)
по графу `00-EPICS.md` зависит от EP-04.

### 5. Баг в ядре Analog Engine — единственного защитимого УТП релиза (BLOCKER)

`packages/domain-kernel/src/value-objects/dosage.vo.ts`. `COMPARABLE_UNIT_PAIRS` строится
как **диагональное** множество (`unit::unit` для каждой единицы), используется как guard в
начале `isEquivalentTo()`, который возвращает `false` для любой пары **разных** единиц ДО
того, как код кросс-конвертации массы (`mg`/`g`/`mcg`, ниже в той же функции, сам по себе
написан корректно) успевает выполниться. Я лично прогнал тесты и воспроизвёл:
```
FAIL src/value-objects/dosage.vo.spec.ts > 500 mcg equivalent to 0.5 mg (TC-CAT-011)
AssertionError: expected false to be true
```
3 из 3 теста на кросс-юнитную эквивалентность падают. `isEquivalentTo` потребляется
`analog-equivalence.service.ts` — сервисом, который по SRS/DTJ-099 принимает финальное решение
«препарат B — аналог A». Для любых двух препаратов с одинаковым веществом, но разными
единицами дозировки (500 мг vs 0.5 г) движок сегодня их не признает эквивалентными.

### 6. Тесты красные в 4 workspace, самоотчёт «зелёное» не соответствовал действительности

Лично прогнал `vitest run` в каждом пакете — воспроизвёл всё:
| Пакет | Результат моего прогона |
|---|---|
| `apps/api` | **8 упавших тестов, 3 файла** (`tenant.entity.spec.ts`, `tenant-id.vo.spec.ts`) — 209 passed / 8 failed из 217 |
| `packages/domain-kernel` | **3 упавших теста** (баг п.5 выше) — 29 passed / 3 failed из 32 |
| `packages/contracts` | **1 упавший тест** — `errors.spec.ts`, рассинхрон фикстуры: код добавил `ALREADY_REVIEWED`, `CHAIN_APPLICATION_ALREADY_EXISTS` в `errors.ts`, но не обновил параллельный список в тесте |
| `apps/worker` | **coverage hard fail**: 42.5% строк / 22.22% ветвей против порога 70% — целиком из-за нового `src/jobs/license-expiry-check/*` (3 файла, **0% покрытия** на всех) |

Причина падений в `apps/api` — невалидные по RFC4122 UUID в собственных тестовых фикстурах

выполнялся зелёным перед тем, как волна была объявлена завершённой — иначе это было бы

### 7. Гейт покрытия `apps/api` физически слеп к новому коду

`apps/api/vitest.config.ts`: `coverage.include: ['src/common/**/*.ts', 'src/config/**/*.ts']`
— я прочитал файл целиком, это не устарело частично, это буквально весь `include`. Порог 70%
формально «зелёный» **потому что не измеряет ни одного файла из `src/modules/**`** — то есть
ни одного из 104 новых `.ts`-файлов волны 2-3. Отдельно посчитал: `apps/api/src/modules/onboarding/{application,infrastructure}/`
— **31 файл, 0 spec-файлов** (`find ... -name "*.spec.ts" | wc -l` → 0). Не «покрытие
просело» — покрытия целого слоя не существует, и гейт, который должен был это заметить, не
может в принципе, независимо от того, что туда допишут.

### 8. `pnpm db:seed` физически не работает

`apps/api/package.json:20`: `"db:seed": "tsx src/infrastructure/database/seed.ts"`. Я
проверил — `apps/api/src/infrastructure/database/` содержит только `database.module.ts` и
`drizzle.provider.ts`, файла `seed.ts` там нет. Реальный seed-раннер лежит в
`apps/api/src/db/seed/...` и экспортирует `runSeedCatalog(port)` без точки входа/CLI-вызова.
Заявленные 317 позиций каталога не загружаются в БД штатной командой — ни один разработчик
следующей волны не может получить рабочую БД одной командой из документации.

### 9. `apps/admin` исключён из архитектурного гейта явным образом

`.dependency-cruiser.cjs`, строки 47-51 и 274-276 (я прочитал файл, не поверил находке на
слово): `if (workspaceDir === 'apps' && entry.name === 'admin') continue` и повторное
исключение `'^apps/admin/'` в правилах. `arch:check` зелёный **потому что** новое приложение
целиком выведено из-под проверки, а не потому что оно ей соответствует.

### 10. Мелкое, но симптоматичное: комментарий обещает валидацию, код её не делает

`apps/api/src/modules/onboarding/domain/pharmacy-account.entity.ts`, метод `suspend()`:
сигнатура `suspend(reason: PharmacySuspensionReason, _actor: { readonly id: string })`, тело
начинается с `void _actor` — параметр принят и демонстративно отброшен. JSDoc над методом
описывает `actor` как часть контракта перехода состояния, реализация его не использует.
Не блокер сам по себе, но тот же паттерн «докстрing написан по спеке, код — по упрощённому
пути», что и у `analog-equivalence.service.ts`, который в JSDoc заявляет использование
`Dosage.isEquivalentTo()`.

## Системные паттерны

Это важнее отдельных багов из раздела выше: единичный баг чинится один раз, паттерн
воспроизведётся в каждой следующей волне, если его не остановить процессом. Все шесть находок
раздела «Что сделано плохо» — это **не шесть независимых случайностей**, а проявления
четырёх повторяющихся привычек:

1. **«Написано» ≠ «подключено».** Минимум три подтверждённых экземпляра за одну волну:
   `TenantResolutionMiddleware` (написан, не в `consumer.apply`), `TenantScopeGuard`
   (не написан вообще, хотя на него ссылаются как на существующий защитный слой 6+
   комментариев), `CatalogModule` (пустой, не в `AppModule.imports`). Ни typecheck, ни lint,
   ни `arch:check`, ни `test:arch` физически не способны поймать этот класс дефекта — он
   виден только интеграционным тестом, который реально поднимает приложение, или ручным
   аудитом. За одну волну — три раза. Без нового типа гейта в волне 4-12 будет ещё как
   минимум три-четыре.
2. **Код пишется, тесты пишутся, но `vitest run` перед сдачей не выполняется.** Не
   единичный инцидент: `dosage.vo.spec.ts`, `tenant.entity.spec.ts` + `tenant-id.vo.spec.ts`,
   `errors.spec.ts`, `license-expiry-check` (нет тестов вообще) — 4 независимых пакета,
   4 разных причины падения. Общий знаменатель один: последняя команда перед коммитом
   отчёта о готовности не включала реальный прогон тест-сьюта.
3. **Гейты сконфигурированы под то, что существовало в волне 1, и не расширяются
   автоматически под то, что появляется в волне N.** `apps/api/vitest.config.ts` coverage
   `include` — allowlist из волны 1, не увидел ни одного из 104 новых файлов.
   `.dependency-cruiser.cjs` — anchors под `apps/*/src/modules/*`, `apps/admin` и `db/seed`
   вне этого пути либо не проверяются вовсе, либо явно исключены. Это один и тот же слепой
   паттерн конфигурации гейтов, а не два разных бага.
4. **`@Public()`/пустой модуль/README-заглушка как способ двигаться дальше мимо блокирующей
   зависимости, вместо того чтобы остановиться и эскалировать.** EP-03/EP-04 кодировались
   поверх отсутствующего EP-01, вместо паузы или явного тикета-блокера с эскалацией
   владельцу. Сам TODO (`TODO(EP-01): @Roles(...)`) по тону читается как «поменять
   декоратор в одном файле» — по факту это ссылка на XL-эпик (~9 тикетов ядра
   аутентификации), который вообще не начат. Формулировка TODO систематически занижает
   реальный объём отложенной работы — это не только у auth, то же самое видно в тоне
   комментария `CatalogModule` («модуль пуст — скелет для подключения последующими
   тикетами», без пометки severity).

Отдельно, не дефект кода, но часть той же картины: **волна 1, зафиксированная как
«принята» в `docs/STATE-AND-RESUME-POINT.md`**, сама была неполной относительно
собственного тикетного плана — в исходном разбиении волны 1 (`tickets/00-INDEX.md`,
под-волны 6-10) auth-тикеты `DTJ-022`…`DTJ-030` числятся частью волны 1, но в волну 1
попали только `health/config/logger`. Это значит: разрыв EP-01 **не создан** волной 2-3 —
он **унаследован** от волны 1 и молча пронесён дальше без блокирующей эскалации. Важно для
экономики решения ниже: часть сегодняшнего долга — не брак этой волны, а неоплаченный счёт
из предыдущей.

## Экономика решения

### Единицы измерения

Использую шкалу условных единиц самого проекта (`tickets/00-INDEX.md`, расчёт критического
пути): **XS=1, S=2, M=3, L=5, XL=8**. Это не деньги — это трудоёмкость в тех же единицах,
которыми уже размечены все 271+ тикетов бэклога, поэтому оценка сопоставима напрямую со
скоростью, которую уже показала волна 1.

### Декомпозиция долга волны 2-3 (важна для честного ответа ниже)

## Как усилить процесс

Разделено на то, что можно и нужно проверять автоматически (гейт в CI/скрипте — не зависит
от человеческого внимания), и то, что требует ручного суждения архитектора при приёмке
волны.

### Автоматически

1. **Реальный прогон тестов как обязательный CI-чек, блокирующий приёмку волны.** Сегодня
   `pnpm verify` существует (`typecheck && lint && arch:check && test:arch && test && build`),
   но волна была объявлена «9 из 9 зелёных» при фактически красных 4 из 6+ пакетов — то есть
   команда либо не запускалась, либо её результат не проверялся. Нужен required CI-check на
   уровне репозитория (не локальный скрипт, который можно пропустить), и приёмка волны не
   должна начинаться без зелёного прогона, воспроизведённого независимо от отчёта агента.
2. **Wiring-smoke-тест.** Единственный тип гейта, который в этой волне отсутствовал
   полностью и который поймал бы 3 из 5 блокеров сразу (middleware, guard, пустой модуль):
   лёгкий интеграционный тест, поднимающий реальное Nest-приложение и проверяющий: (а)
   запрос без токена на защищённый роут возвращает 401 once auth существует; (б) запрос с
   `X-Tenant-Slug` реально резолвит `TenantContext` (не `undefined`); (в) каждый экспортируемый
   `*Middleware`/`*Guard` класс используется хотя бы один раз вне своего собственного теста
   (можно грубым статическим анализом — «класс объявлен, но `consumer.apply`/`@UseGuards`
   на него нигде не ссылается» — это ловится скриптом за минуты).
3. **Политика `coverage.include` по умолчанию, не allowlist.** Сегодня `apps/api/vitest.config.ts`
   покрывает только то, что было в волне 1 (`src/common/**`, `src/config/**`) — новые модули
   невидимы для гейта, пока кто-то не вспомнит добавить путь. Переключить на
   `include: ['src/**/*.ts']` минус явный, ревьюируемый exclude-список — тогда новый код
   покрыт по умолчанию, а не по забывчивости.
4. **Запрет молчаливых исключений в `.dependency-cruiser.cjs`.** Любое `continue`/regex-исключение
   пути из архитектурной проверки обязано ссылаться на номер тикета с датой пересмотра в
   комментарии рядом; отдельный скрипт (можно частью `arch:check`) перечисляет все такие
   исключения и подсвечивает их в отчёте о приёмке волны, чтобы `apps/admin`-класса случай не
   повторился молча.
5. **Эпик-гейт в самом оркестраторе.** Перед стартом тикетов волны N — механическая проверка
   по графу `00-EPICS.md`/`00-INDEX.md`: у каждого `depends_on`-эпика ВСЕ пункты Definition of
   Done отмечены, а не просто «предыдущая волна принята». Именно это позволило EP-03/EP-04
   стартовать поверх незаконченного EP-01 (auth-тикеты `DTJ-022`…`DTJ-030` волны 1 так и не
   были реализованы) без единой блокирующей эскалации.
6. **Устранить класс бага «параллельный список рассинхронизировался»** (`errors.spec.ts` vs
   `errors.ts`) не тестом-ловушкой, а структурно: фикстуру теста генерировать из того же
   источника правды, что и сам `ErrorCode`, а не поддерживать вручную вторым списком.

### Вручную (архитектор/ревьюер при приёмке волны)

1. **Security-пас по каждому новому контроллеру волны**: для каждого нового роута —
   осознанное решение `@Public()` vs `@Roles()`, соответствующее чувствительности операции.
   Автоматика не знает, что admin-эндпоинт модерации не должен быть публичным — это ровно та
   проверка, которую в этой волне никто не сделал вручную.
2. **Не верить сводке «все гейты зелёные» — воспроизводить её лично** перед приёмкой волны
   (именно так эта проверка нашла 4 из 6 красных пакетов, не отражённых в исходной сводке
   архитектора). Сделать это стандартной, а не разовой практикой ревью-цикла.
3. **Сверка тикет → тест-кейс**: для тикетов, называющих конкретные ID тест-кейсов (как
   `DTJ-099` называет `TC-CAT-011`/`TC-CAT-012`), проверять, что именно эти ID присутствуют в
   сьюте — эта волна показала, что 2 из 6 обязательных кейсов тихо выпали именно там, где
   они оказались бы «неудобными» (проявили бы баг).
4. **Аудит последовательности волн против графа зависимостей** — не «предыдущая волна
   принята», а «эпик, от которого зависит текущая волна, закрыт по своему собственному DoD».
5. **Точечная проверка расхождения JSDoc/реализация** на новых доменных методах — дёшево
   (минуты на файл), в этой волне поймала бы обе находки (`suspend()`, `analog-equivalence.service.ts`)
   до сдачи, а не после.
