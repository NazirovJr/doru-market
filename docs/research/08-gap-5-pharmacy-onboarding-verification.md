# Исследование 08 (Пробел 5): Онбординг аптек/сетей и верификация лицензии

> Статус: **research draft v1.0**. Область: end-to-end пайплайн подключения новой аптеки/аптечной сети к
> DoruTJ — от заявки в разделе «Для аптек/поставщиков» (REQ-MARKET-7) до появления в поиске покупателя,
> включая ручную верификацию лицензии (следствие из 02: публичного реестра фармлицензий РТ не существует),
> машину состояний, эффект приостановки на инвентарь/заказы и мониторинг истечения лицензии.
> Метод: анализ существующих research-документов (00, 01, 02, 03, 04), устава проекта, и внешних
> прецедентов онбординга продавцов/аптек на маркетплейсах (Ozon, Wildberries, Instacart, DoorDash,
> Stripe Connect) как эталонной практики KYB/лицензионной верификации. Всё непроверенное по
> таджикскому первоисточнику помечено **ASSUMPTION**/**UNVERIFIED**.

## 0. Контекст и связь с другими документами

- **REQ-MARKET-7** (01, §6): раздел «Для аптек/поставщиков» обязателен в `apps/admin` с MVP —
  но полей заявки, роли-верификатора и статусной модели нигде не определено. Этот документ закрывает пробел.
- **REQ-REG-17** (02, §8): карточка каждой аптеки/сети обязана показывать юр. адрес, телефон, номер и
  срок действия лицензии, наименование выдавшего органа — эти же поля являются входом онбординга,
  описанного здесь.
- **02, §1** уже установил: лицензию выдаёт **Служба государственного надзора здравоохранения и
  социальной защиты населения РТ** совместно с МЗиСЗН; держателем лицензии юридически может быть только
  аптека/сеть, не платформа-агрегатор ([Закон РТ №39 от 06.08.2001, ст.5, ст.30](https://ncz.tj/content/%D0%B7%D0%B0%D0%BA%D0%BE%D0%BD-%D1%80%D0%B5%D1%81%D0%BF%D1%83%D0%B1%D0%BB%D0%B8%D0%BA%D0%B8-%D1%82%D0%B0%D0%B4%D0%B6%D0%B8%D0%BA%D0%B8%D1%81%D1%82%D0%B0%D0%BD-%D0%BE-%D0%BB%D0%B5%D0%BA%D0%B0%D1%80%D1%81%D1%82%D0%B2%D0%B5%D0%BD%D0%BD%D1%8B%D1%85-%D1%81%D1%80%D0%B5%D0%B4%D1%81%D1%82%D0%B2%D0%B0%D1%85-%D0%B8-%D1%84%D0%B0%D1%80%D0%BC%D0%B0%D1%86%D0%B5%D0%B2%D1%82%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%BE%D0%B9-%D0%B4%D0%B5%D1%8F%D1%82%D0%B5%D0%BB%D1%8C%D0%BD%D0%BE%D1%81%D1%82%D0%B8)).
- **02** не нашёл публичного машиночитаемого реестра фармлицензий РТ → верификация лицензии **не может**
  быть автоматизирована через внешний API на старте; это research-подтверждённая вводная, а не
  инженерное допущение.
- **04, §1, REQ-SYNC-18**: для сетей на «1С:Управление аптечной сети» интеграционная точка 1С — **одна на
  сеть**, а не на аптеку. Это прямо влияет на модель онбординга (см. §5): технически заведение сети как
  единой сущности с несколькими точками — уже архитектурное решение в другой области, онбординг должен
  ему соответствовать, а не противоречить.
- **03**: `payoutAccountRef`/`tin` аптеки уже фигурирует в контракте эскроу-провайдера — банковские
  реквизиты/мерчант-ID должны собираться на этапе онбординга, а не изобретаться заказом.
- **Чартер, §5**: «Схема БД… реализуется 1:1; расширения допускаются» — все поля/статусы ниже вводятся
  как **расширения** существующих таблиц `pharmacy_chains`/`pharmacies` из `tz.log`, без переименования
  уже заданных колонок.
- **Роли по чартеру** фиксированы: `customer, pharmacist, courier, pharmacy_admin, super_admin` — новой
  роли «комплаенс-офицер» в БД не вводится (см. §3 и «Открытые вопросы», п.6).

рабочих дней**, не мгновенно.

## 2. Два уровня онбординга: сеть (юрлицо) и аптека (точка/лицензия)

Отвечая на прямой вопрос задания — онбординг **двухуровневый**, а не «либо/либо»:

1. **Уровень сети (`pharmacy_chains`) — один раз на юридическое лицо.** KYB-данные, банковские
   реквизиты/мерчант-привязка, White-Label флаг. Это административно-договорной уровень, не завязанный
   на конкретный физический адрес.
2. **Уровень аптеки (`pharmacies`) — на каждую точку отдельно.** Фармлицензия физически привязана к
   конкретному помещению/адресу (аналогия с российской моделью лицензирования аптечных организаций,
   где лицензия и Положение о лицензировании фармацевтической деятельности регламентируют требования
   именно к помещению — [письмо Росздравнадзора №02и-362/26](https://www.consultant.ru/document/cons_doc_LAW_532737/96c60c11ee5b73882df84a7de3c4fb18f1a01961/); прямого таджикского
   подтверждения такой привязки не найдено — см. «Открытые вопросы», п.2). Поэтому каждая новая точка
   сети проходит **свою** проверку лицензии, даже если сеть уже одобрена.

**Одиночная аптека без сети** заводится по идентичному пайплайну: создаётся `pharmacy_chains`-запись
«из одной точки» (`name` = имя аптеки, `is_whitelabel_active = false`), поверх неё — одна `pharmacies`-
запись. В UI администратора для соло-аптек шаг «данные сети» и шаг «данные точки» показываются как один
объединённый экран (визуально не различаются), но в БД это остаётся тем же двухуровневым представлением
— один код онбординга на все случаи, без спецкейса.

Это согласуется с REQ-SYNC-18 (04): 1С-эндпоинт/API-ключ сети живёт на уровне `pharmacy_chains`, а
маппинг на конкретные точки — по коду точки в батче; онбординг не создаёт для этого отдельной сущности.

### 3.3 Аудит-лог решений

```sql
CREATE TABLE onboarding_review_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_type VARCHAR(20) NOT NULL,      -- 'chain' | 'pharmacy'
    entity_id UUID NOT NULL,
    action VARCHAR(30) NOT NULL,           -- 'submitted','approved','rejected','changes_requested',
                                            -- 'suspended','reactivated','terminated'
    actor_user_id UUID REFERENCES users(id), -- NULL для системных/cron-действий (авто-suspend по сроку)
    reason TEXT,
    checklist_snapshot JSONB,               -- см. §4 — снимок чек-листа на момент решения
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Append-only, без UPDATE/DELETE — единственный источник правды «кто и почему одобрил/отклонил/приостановил».

## 4. Кто и как верифицирует

**Кто**: `super_admin` — единственная роль с правом решения по заявке. Новая роль в БД не вводится
(роли зафиксированы чартером); при росте объёма заявок за пределами MVP управление нагрузкой — вопрос
операционного штата (несколько людей с ролью `super_admin`), а не новой RBAC-сущности — см. «Открытые
вопросы», п.6.

**Почему вручную, а не автоматически**: 02 не нашёл публичного машиночитаемого реестра фармлицензий РТ.
Единый государственный реестр юридических лиц и ИП РТ существует как институт (ведётся по принципу
«единого окна», [Закон РТ №508](https://base.spinform.ru/show_doc.fwx/show_doc.fwx?rgn=28086)), но
публичный онлайн-поиск по нему для сторонних систем **не подтверждён** — доступны только коммерческие
посреднические выписки для иностранных заявителей ([пример: egrul.ru/ino_reestry/tadzhikistan](https://www.egrul.ru/ino_reestry/tadzhikistan)), что не
является пригодным API-интеграционным каналом. Таким образом ИНН/юрлицо тоже проверяется вручную на
момент MVP — **UNVERIFIED**, требуется прямой запрос в Налоговый комитет РТ о наличии программного
доступа к реестру (см. «Открытые вопросы», п.1).

**Чек-лист верификации** (хранится как `checklist_snapshot` в `onboarding_review_log` при решении):

Для сети:
1. `registration_certificate_scan_url` — номер/дата свидетельства читаемы, не просрочен документ.
2. `legal_entity_name` и `director_full_name` совпадают с данными на скане.
3. `tin_inn` совпадает с указанным в свидетельстве.
4. `contact_phone` прошёл OTP-подтверждение (переиспользуется существующая OTP-инфраструктура из Auth-модуля `tz.log`) — противодействие заявкам с чужим/фиктивным номером.

Для аптеки:
1. `license_scan_url` — номер лицензии на скане совпадает с `license_number`.
2. `license_expiry_date` ≥ дата подачи + 30 дней (иначе — `changes_requested`: «обновите лицензию перед подачей»).
3. `license_issuing_authority` соответствует ожидаемому органу (см. таблицу выше).
4. Адрес на лицензии (если виден на скане) совпадает с `address_text`.
5. Совпадение `chain.legal_entity_name` ↔ юрлицо-держатель на лицензии (если сеть).

Совпадение проверяется человеком визуально по сканам — это открытая, а не скрытая ручная операция;
чек-лист не превращается в OCR/ML-пайплайн на MVP (в отличие от Модуля 2 `tz.log`, где OCR распознаёт
рецепты — здесь у нас нет датасета/точности для доверия автоматике на регуляторно-значимом решении).

## 5. Машина состояний

### 5.1 Уровень сети — `chain_onboarding_status`

```sql
CREATE TYPE chain_onboarding_status AS ENUM (
    'draft',              -- заявка создаётся, не отправлена
    'pending_review',     -- отправлена, ждёт super_admin
    'changes_requested',  -- super_admin запросил доп. документы/правки
    'approved',           -- KYB одобрен; ждёт первую активную аптеку под собой
    'active',             -- есть ≥1 активная pharmacies-запись; сеть видна как продавец
    'rejected',           -- отклонено при первичном рассмотрении
    'suspended',          -- приостановлена целиком (юр. нарушение уровня сети/фрод)
    'terminated'          -- расторжение (закрытие юрлица, окончание договора)
);
```

Переход `approved → active` **автоматический** (без второго ручного шага): срабатывает, когда первая
`pharmacies`-запись под этой сетью получает `status = 'active'`. Это устраняет дублирующий ручной гейт —
KYB уже проверен, а решение по конкретной точке — самостоятельная проверка лицензии (§5.2).

### 5.2 Уровень аптеки — `pharmacy_onboarding_status`

```sql
CREATE TYPE pharmacy_onboarding_status AS ENUM (
    'draft',
    'pending_review',
    'changes_requested',
    'approved',            -- лицензия проверена; ждёт первой синхронизации остатков (см. edge case §8)
    'active',              -- видна в поиске, принимает заказы
    'rejected',
    'suspended',
    'terminated'
);

CREATE TYPE pharmacy_suspension_reason AS ENUM (
    'license_expired',       -- авто, см. §7
    'license_revoked',       -- регулятор отозвал лицензию (ручной сигнал support/super_admin)
    'policy_violation',      -- нарушение правил площадки (см. «Открытые вопросы», п.4)
    'fraud_or_safety',       -- подделка/просрочка партии, поддельные документы — самая жёсткая категория
    'requested_by_pharmacy', -- самостоятельная временная пауза (отпуск, ремонт, ...)
    'chain_suspended'        -- унаследовано от приостановки родительской сети (см. §6)
);
```

Дочерняя `pharmacies`-запись НЕ может быть `active`, если родительская `pharmacy_chains.status` не
`approved`/`active` — гвард на уровне сервиса (аналог tenant-guard из чартера §3.4, тот же слой проверки).

### 5.3 Диаграмма переходов (обе сущности используют одну форму)

```
draft ──submit──> pending_review ──request changes──> changes_requested ──resubmit──> pending_review
                        │                                                                    │
                        ├──approve──> approved ──(chain: auto | pharmacy: first sync ok)──> active
                        │                                                                    │
                        └──reject───> rejected                                    ┌───────────┘
                                                                                   │
                                            ┌──────────────────────────────────────┤
                                            ▼                                      ▼
                                     suspend (license_expired /            terminate (закрытие,
                                     license_revoked / policy_violation /   расторжение)
                                     fraud_or_safety / requested_by_pharmacy /
                                     chain_suspended)
                                            │
                                     reactivate (повторная проверка,
                                     НЕ автоматически) ──> pending_review
```

`rejected` и `terminated` — терминальные состояния для конкретной заявки/точки; повторный вход — новая
заявка (`draft`), не реюз старой записи (сохраняет чистоту аудит-лога).

## 6. Эффект приостановки (`suspended`) на инвентарь и заказы

Это центральный незакрытый вопрос задания — фиксируем конкретное, тестируемое правило:

| Аспект | Поведение при `suspended` |
|---|---|
| **Видимость в поиске/каталоге** | Немедленно скрыта. Поисковый провайдер (`PostgresSearchProvider`/`ElasticSearchProvider`, 03.4 чартера) обязан фильтровать `pharmacies.status = 'active'` на уровне запроса, не полагаясь на переиндексацию по расписанию. |
| **Новые заказы (checkout)** | Блокируются на API: попытка создать заказ на `pharmacy_id` со `status != 'active'` возвращает `409 { error: { code: 'PHARMACY_SUSPENDED' } }`. Клиент не хардкодит эту логику (правило переносимости клиентов, чартер §3.6) — сервер отвечает единым кодом ошибки. |
| **Заказы в `pending_payment`** (деньги ещё не списаны/захолдированы) на момент приостановки | Автоматически переводятся в `cancelled` с причиной `pharmacy_suspended`; уведомление покупателю. Обязательство ещё не возникло — ждать нечего. |
| **Заказы в `paid_escrow` / `processing` / `picked_up`** на момент приостановки | **Продолжают выполняться штатно** (эскроу уже держит деньги, курьер/фармацевт уже задействованы — см. CUJ-3/CUJ-4 чартера). Это дефолт для «мягких» причин (`license_expired`, `requested_by_pharmacy`, `policy_violation`). |
| **Исключение — `fraud_or_safety` / `license_revoked`** | `super_admin` может **вручную** форс-отменить все незавершённые заказы (`pending_payment`, `paid_escrow`, `processing`) с полным возвратом через `PaymentProvider.refund` — отдельное явное действие, не побочный эффект простого перевода в `suspended`. Обоснование: некоторые причины (отозванная лицензия, фальсификат) делают продолжение физической выдачи товара недопустимым независимо от уже принятого заказа. |
| **`pharmacy_inventory`** | Не удаляется и не блокируется для записи — 1С/ручная синхронизация (Модуль 4 `tz.log`, 04) продолжает приниматься и обновлять остатки в фоне, чтобы при снятии приостановки данные не были «протухшими». Строки инвентаря просто исключены из выдачи поиска через тот же join-фильтр по `pharmacies.status`. |
| **Терминал фармацевта (`apps/pharmacy`)** | Продолжает показывать уже принятые заказы для завершения сборки (кроме форс-отменённых), но не получает уведомлений о новых. |
| **Реактивация** | Не автоматическая. `pharmacy_admin` подгружает актуальный документ (например, новую лицензию) → запись переходит в `pending_review` → `super_admin` повторяет чек-лист §4 → `active`. |

Правило «мягкая причина не трогает уже принятые заказы» напрямую воспроизводит паттерн DoorDash
(Temporary Deactivation блокирует только новые заказы) — работоспособный, проверяемый прецедент, а не
изобретение с нуля.

Если `pharmacy_chains.status` становится `suspended`, все дочерние `pharmacies` **визуально** скрываются
(эффективная видимость = `chain.status = 'active' AND pharmacy.status = 'active'`), но их собственный
`pharmacy.status`/`suspension_reason` не перезаписывается автоматически в `chain_suspended` — это read-time
вычисление в сервисе каталога, а не write-time каскад, чтобы не терять состояние точки при снятии
приостановки сети.

## 7. Мониторинг истечения лицензии (проактивная часть задания)

Фоновая задача (BullMQ repeatable job в `apps/worker`, тот же паттерн, что и escrow-таймауты из 03):

```
ежедневно 06:00 (после ночной 1С-синхронизации 03:00, чартер §3.1):
  SELECT id, license_expiry_date FROM pharmacies WHERE status = 'active'
    AND license_expiry_date <= now() + interval '30 days'

  ЕСЛИ license_expiry_date <= now() + 30d И license_expiry_warning_sent_at IS NULL (или прошло >7д с последнего)
    → уведомление pharmacy_admin (SmsProvider/email) + запись в notifications: «лицензия истекает через N дней»
    → повтор на T-14d, T-3d (эскалация тона сообщения)

  ЕСЛИ license_expiry_date <= now() (уже истекла) И status = 'active'
    → авто-переход status = 'suspended', suspension_reason = 'license_expired', suspended_at = now()
    → onboarding_review_log: action='suspended', actor_user_id=NULL (системное действие), reason='license_expiry_date reached'
    → уведомление pharmacy_admin И super_admin
```

Это закрывает явно поставленный в задании кейс «истёкшая лицензия обнаружена после запуска»: обнаружение
не полагается на то, что кто-то вручную просматривает список аптек — это ежедневный автоматический скан
по уже собранному на онбординге полю `license_expiry_date`.

## 8. Ключевые edge cases

1. **Одиночная аптека vs сеть** — см. §2; технически всегда создаётся пара `pharmacy_chains` (1 запись) +
   `pharmacies` (≥1 запись), UI прячет это разделение для соло-аптек.
2. **White-Label заявки** (Sifat/Oson/Madad Pharm) — помечаются `is_whitelabel_requested = true` уже на
   входе; такие заявки маршрутизируются в отдельную очередь ревью (обычно sales-assisted, контракт
   подписывается офлайн до подачи формы), но проходят **ту же** машину состояний — не отдельный процесс,
   чтобы не плодить два параллельных пайплайна и не терять аудит.
3. **Первая точка новой сети** — `pharmacy_chains` не может стать `active`, пока под ней нет ни одной
   `pharmacies.status = 'active'`. Заявка на сеть без единой аптеки «зависает» в `approved` бессрочно —
   это осознанное поведение (сеть без точек не может ничего продавать), а не дефект.
4. **Первая синхронизация остатков после `approved → active`**: аптека, только что прошедшая проверку
   лицензии, может не иметь ни одной позиции в `pharmacy_inventory` до первого батча 1С/ручного ввода
   (04, §1). Рекомендация: `pharmacy.status` переходит в `active` по факту одобрения лицензии (не ждёт
   инвентарь) — пустой каталог у активной аптеки не ошибка, а естественное начальное состояние,
   аналогично «магазин открылся, полки заполняются».
5. **Смена адреса существующей аптеки** — трактуется как повод для повторной проверки лицензии
   (`active → pending_review`, не тихий `UPDATE address_text`), так как лицензия физически привязана к
   помещению (аналогия РФ — см. §2); прямое подтверждение для РТ не найдено (открытый вопрос, п.2).
6. **Повторная заявка после `rejected`** — новая запись (`draft`), не реюз старой; `tin_inn` UNIQUE уже
   не даёт создать вторую `pharmacy_chains`-запись с тем же ИНН, поэтому повторная заявка того же юрлица
   обязана переиспользовать существующую (отклонённую) запись, переводя её обратно в `draft`/
   `pending_review`, а не создавать дубликат — важное уточнение к constraint'у, иначе заявитель получит
   голую 500-ошибку от UNIQUE-нарушения БД вместо понятного UX.
7. **Заведомо поддельный документ на входе** — при обнаружении фальсификации on top of `rejected`
   рекомендуется отдельный флаг/блок-лист по `tin_inn` (не специфицирован здесь в деталях — см. «Открытые
   вопросы», п.8), чтобы не позволить мгновенно пересоздать заявку с теми же данными.
8. **Приостановка на время, когда уже назначен курьер** (`processing`/`picked_up`) — см. таблицу §6:
   штатно продолжается, кроме `fraud_or_safety`/`license_revoked` с ручной форс-отменой.

## 9. Целевой SLA ревью

- **Целевой SLA**: решение (`approved`/`rejected`/`changes_requested`) в течение **2 рабочих дней** с
  момента `submitted_at` для полного пакета документов — ориентир на верхнюю границу индустриального
  бенчмарка (Instacart ~2 дня, Ozon/Wildberries 3–5 дней) с поправкой на то, что у DoruTJ ожидается
  на порядок меньший поток заявок, чем у этих платформ, на старте (**ASSUMPTION**: обоснованный ориентир,
  не измеренная величина — нет собственных исторических данных по объёму заявок).
- Часы «на паузе» (`changes_requested`) не засчитываются в SLA — таймер останавливается до `resubmit`.
- SLA — продуктовая метрика для мониторинга (admin-дашборд: «заявки старше 2 дней»), не жёсткий deadline
  с автоматическим одобрением по истечении (в отличие от Stripe Connect, где по истечении срока
  блокируются выплаты/приём — здесь по истечении срока ничего не меняется автоматически, кроме
  внутреннего алерта команде поддержки).

## Требования, вытекающие из исследования

1. **REQ-ONBOARD-1**: Онбординг ДОЛЖЕН быть двухуровневым: `pharmacy_chains` (юрлицо, KYB, банковские/
   мерчант-реквизиты — один раз) и `pharmacies` (точка, фармлицензия — на каждый адрес отдельно, включая
   каждую новую точку уже одобренной сети).
2. **REQ-ONBOARD-2**: Одиночная аптека без сети ДОЛЖНА заводиться той же парой сущностей (`pharmacy_chains`
   «из одной точки» + одна `pharmacies`-запись) — без отдельной ветки кода/схемы для соло-аптек.
3. **REQ-ONBOARD-3**: Форма заявки на уровне сети ДОЛЖНА собирать как минимум: `legal_entity_name`,
   `tin_inn`, `legal_address`, `registration_certificate_number` + скан, `director_full_name`,
   `contact_phone` (с OTP-подтверждением), `bank_name`+`bank_account_number`, опционально
   `payout_merchant_ref` по каждому `PaymentProvider`, и обязательно — если `is_whitelabel_requested=true`.
4. **REQ-ONBOARD-4**: Форма заявки на уровне аптеки ДОЛЖНА собирать как минимум: `address_text`,
   `landmark_tj`, координаты, `phone`, `license_number`, `license_issuing_authority`,
   `license_issue_date`, `license_expiry_date`, `license_scan_url`, `pharmacist_in_charge_name`.
5. **REQ-ONBOARD-5**: Решение по заявке (сеть и аптека) ДОЛЖНО приниматься исключительно пользователем с
   ролью `super_admin`; никакая новая роль в `user_role` под верификацию не вводится.
6. **REQ-ONBOARD-6**: Проверка ИНН/лицензии на MVP ДОЛЖНА быть ручной (визуальная сверка сканов
   ревьюером) — автоматическая интеграция с госреестром НЕ закладывается в архитектуру как обязательная
   зависимость запуска, поскольку публичный машиночитаемый источник не подтверждён (02).
7. **REQ-ONBOARD-7**: Каждое решение по заявке (approve/reject/changes_requested/suspend/reactivate/
   terminate) ДОЛЖНО писаться в append-only `onboarding_review_log` с `actor_user_id` (или `NULL` для
   системных авто-действий), `reason` и снимком чек-листа.
8. **REQ-ONBOARD-8**: `pharmacy_chains.status` и `pharmacies.status` ДОЛЖНЫ реализовывать enum'ы
   `chain_onboarding_status`/`pharmacy_onboarding_status` со значениями `draft, pending_review,
   changes_requested, approved, active, rejected, suspended, terminated`.
9. **REQ-ONBOARD-9**: Переход `pharmacy_chains.status: approved → active` ДОЛЖЕН происходить автоматически
   при появлении первой дочерней `pharmacies.status = 'active'`, без отдельного ручного шага ревью сети.
10. **REQ-ONBOARD-10**: `pharmacies.status` НЕ ДОЛЖЕН допускать значение `active`, если родительская
    `pharmacy_chains.status` не в `{'approved','active'}` — проверка на уровне сервиса при каждом
    переходе, а не только при создании.
11. **REQ-ONBOARD-11**: Поиск/каталог (`PostgresSearchProvider`/`ElasticSearchProvider`) ДОЛЖЕН исключать
    из выдачи любую `pharmacies` со `status != 'active'` ИЛИ с родительской сетью не в
    `{'approved','active'}`, вычисляемо на момент запроса, а не только на момент индексации.
12. **REQ-ONBOARD-12**: Создание заказа (checkout) на `pharmacy_id` со `status != 'active'` ДОЛЖНО
    отклоняться API с кодом ошибки `PHARMACY_SUSPENDED` (единый формат ошибок чартера §5).
13. **REQ-ONBOARD-13**: При переходе аптеки в `suspended` все её заказы в статусе `pending_payment`
    ДОЛЖНЫ автоматически переводиться в `cancelled` с причиной `pharmacy_suspended`; заказы в
    `paid_escrow`/`processing`/`picked_up` ДОЛЖНЫ продолжать штатное исполнение, ЕСЛИ причина
    приостановки не `fraud_or_safety`/`license_revoked`.
14. **REQ-ONBOARD-14**: Для причин `fraud_or_safety`/`license_revoked` `super_admin` ДОЛЖЕН иметь
    отдельное явное действие «форс-отменить незавершённые заказы аптеки» с полным возвратом через
    `PaymentProvider.refund`, отделённое от простого перевода в `suspended`.
15. **REQ-ONBOARD-15**: Приём и обработка 1С/ручных обновлений `pharmacy_inventory` (Модуль 4 `tz.log`)
    ДОЛЖНЫ продолжаться для аптек в статусе `suspended` — только видимость в поиске блокируется, не
    приём синхронизации.
16. **REQ-ONBOARD-16**: Фоновая задача ДОЛЖНА ежедневно сканировать `pharmacies.status = 'active'` с
    `license_expiry_date` в пределах 30/14/3 дней и слать эскалирующиеся уведомления `pharmacy_admin`;
    по достижении `license_expiry_date` ДОЛЖЕН выполняться автоматический переход в `suspended` с
    `suspension_reason = 'license_expired'`, без участия человека в самом переходе.
17. **REQ-ONBOARD-17**: Реактивация из `suspended` в `active` НЕ ДОЛЖНА быть автоматической ни для одной
    причины приостановки — всегда через `pending_review` и повторный чек-лист `super_admin`.
18. **REQ-ONBOARD-18**: Целевой SLA первичного решения по полной заявке — 2 рабочих дня с момента
    `submitted_at`; время в статусе `changes_requested` НЕ ДОЛЖНО засчитываться в этот SLA.
19. **REQ-ONBOARD-19**: Повторная подача заявки тем же `tin_inn` после `rejected` ДОЛЖНА переиспользовать
    существующую запись (перевод `rejected → draft/pending_review`), а не создавать вторую строку —
    во избежание падения на UNIQUE-constraint с необработанной 500-ошибкой.
20. **REQ-ONBOARD-20**: Смена `address_text` у уже `active` аптеки ДОЛЖНА переводить её обратно в
    `pending_review` (повторная проверка лицензии на новый адрес), а не применяться как обычное
    редактирование поля.

## Открытые вопросы

1. Существует ли у Налогового комитета РТ или оператора Единого государственного реестра юридических лиц
   и ИП программный (API/выгрузка) доступ для сверки `tin_inn`/названия юрлица, помимо ручной сверки по
   скану и платных посреднических выписок для иностранных заявителей? Требуется официальный запрос —
   без ответа проверка ИНН остаётся полностью ручной бессрочно, а не только на MVP.
2. Привязана ли фармлицензия в РТ юридически к конкретному адресу помещения (как в модели РФ), или
   лицензия выдаётся на юрлицо в целом с правом открытия точек по факту уведомления? От ответа зависит,
   действительно ли смена адреса (REQ-ONBOARD-20) обязана запускать повторную проверку, или это
   избыточная строгость.
3. Какой конкретно государственный орган и по какой процедуре формально подтверждает `license_revoked`
   (отзыв лицензии) — приходит ли такой сигнал DoruTJ проактивно (маловероятно) или полагаться нужно
   только на самостоятельный мониторинг support/новостей? Без ответа `license_revoked` остаётся
   инициируемым исключительно вручную сигналом службы поддержки, без внешнего триггера.
4. Что именно входит в `policy_violation` (нарушение правил площадки) — нужен отдельный документ
   «Условия для аптек/сетей» (Terms for Pharmacies), которого пока не существует; без него причина
   приостановки декларативна, но не операционализирована.
5. Каков срок и политика хранения данных отклонённых (`rejected`)/расторгнутых (`terminated`) заявок —
   пересекается с общими требованиями по защите персональных данных (упомянуты, но не детализированы
   в 02) и не специфицировано в этом документе.
6. Насколько реалистична нагрузка на ограниченное число `super_admin`-пользователей при росте до
   заявленных в `tz.log` 500+ аптек — нужна оценка операционного штата поддержки/комплаенс, отдельная от
   RBAC-модели (роль не меняется, но число людей с этой ролью — открытый организационный вопрос).
7. Действительно ли `pharmacist_in_charge_cert_number` добавляет ценность на входе (риск дублирования
   уже выполненной регулятором проверки при выдаче лицензии) или это поле стоит убрать из формы заявки
