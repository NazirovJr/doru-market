## 1. На чём реально работают аптеки Таджикистана и СНГ

### 1.1 Линейка 1С для аптек

- **«1С:Розница 8. Аптека»** — целевая конфигурация для одиночной аптеки/аптечного пункта: партионный учёт медикаментов, контроль контрафакта и сроков годности, контроль наценок на ЖНВЛП, отчёты по регулируемым ценам. Поддерживает выгрузку номенклатуры, фото, цен, остатков и статусов заказов на сайты, а также обратную загрузку заказов/оплат/данных покупателей с сайта. Из коробки поддерживается обмен с CMS (1С‑Битрикс, InSales, HostCMS и др.) и с любыми площадками, поддерживающими **CommerceML** ([solutions.1c.ru/catalog/drugstore](https://solutions.1c.ru/catalog/drugstore), [.../features](https://solutions.1c.ru/catalog/drugstore/features)).
- **«1С:Управление аптечной сетью»** — конфигурация для сетей: back‑office (управляющая компания) ↔ front‑office (точки). Раздача ассортимента, розничных цен, ожидаемых поставок из центра вниз; сбор товародвижения, продаж и остатков с точек вверх. Обмен **периодический**, рассчитан на автономную работу удалённой аптеки при потере связи; поддерживается тонкий/веб‑клиент ([solutions.1c.ru/catalog/pharmacy-chain/features](https://solutions.1c.ru/catalog/pharmacy-chain/features)). **Важно для DoruTJ**: если сеть уже ведёт остатки в этой конфигурации, интеграционная точка — одна (центральный узел сети), а не по каждой аптеке отдельно; `pharmacy_chains.one_c_endpoint`/аналог должен допускать связывание на уровне сети, а не только точки.
- **Устаревшие версии** — в регионах СНГ до сих пор встречаются файловые базы **1С:Предприятие 7.7** (DBF/CDX формат хранения, включая конфигурации типа «1С:Рарус‑Аптека»); обмен из них обычно делается внешними выгрузками в DBF/XML/TXT, а не через сервисы ([center-comptech.ru](https://center-comptech.ru/st_opisanie_sostav_ib_1cv7.html), [infostart.ru/1c/tools/102785](https://infostart.ru/1c/tools/102785/)).
- 1С официально локализована и продаётся в Таджикистане («1С:Бухгалтерия 8 для Таджикистана», «1С:Управление торговлей 8 для Таджикистана»), франчайзи есть в Душанбе ([v8.1c.ru/all-partners/tadzhikistan](https://v8.1c.ru/all-partners/tadzhikistan/), [1c.tj](https://1c.tj/)). Это подтверждает, что интеграционный шлюз под «1С» — реалистичное ожидание минимум для части сетей (Sifat Pharma, Oson и т.п.), а не гипотетический сценарий.
- ASSUMPTION: доля аптек Таджикистана, реально ведущих товарный учёт в 1С (а не в Excel/тетради), неизвестна — прямых данных не найдено. Для 500+ целевых аптек проекта следует закладывать смешанный парк: современный 1С:Розница 8 (сетевые аптеки), устаревший 1С 7.7/DBF (часть региональных сетей), полностью ручной учёт (одиночные аптечные пункты).

### 1.2 Механизмы обмена, которые реально существуют в экосистеме 1С

|---|---|---|
| **HTTP‑сервисы (REST)** | Собственный прикладной HTTP-интерфейс, который разработчик 1С пишет внутри конфигурации; принимает/отдаёт JSON или XML по HTTP ([its.1c.ru/db/content/intgr83/src/24.html](https://its.1c.ru/db/content/intgr83/src/24.html), [.../29/hdoc](https://its.1c.ru/db/intgr83/content/29/hdoc)) | Это ровно то, что описано в `tz.log` как `POST /api/v1/inventory/batch-update` — но **со стороны 1С это должен написать интегратор аптеки** (внешняя обработка/расширение), готового «из коробки» эндпоинта под контракт DoruTJ не существует ни у кого |
| **OData (стандартный REST-интерфейс)** | Автоматически публикуемый интерфейс ко всем объектам конфигурации, начиная с платформы 8.3.5 (сентябрь 2015). Протокол OData v3.0, ответы Atom/XML или JSON. Публикуется через диалог «Публикация на веб-сервере» без написания кода ([its.1c.ru/db/intgr83/content/47/hdoc](https://its.1c.ru/db/intgr83/content/47/hdoc), [habr.com/.../865798](https://habr.com/ru/companies/modusbi/articles/865798/)) | Даёт «бесплатный» push/pull доступ к справочникам и регистрам без программирования на стороне 1С. Реалистичный fallback для аптек с современной 1С и штатным ИТ-специалистом: DoruTJ может **тянуть** (pull) остатки через OData вместо ожидания push от аптеки |
| **CommerceML 2.x** | Отраслевой XML-стандарт обмена каталогом/остатками/заказами между 1С и сайтами; файлы `import.xml` (номенклатура) + `offers.xml` (цены/остатки/характеристики). Работает **батчами по расписанию, не в реальном времени** ([v8.1c.ru/.../commerceml-2](https://v8.1c.ru/tekhnologii/obmen-dannymi-i-integratsiya/standarty-i-formaty/standarty-commerceml/commerceml-2/), [docs.cs-cart.ru](https://docs.cs-cart.ru/4.11.x/user_guide/addons/commerceml/moy_sklad/index.html)) | Штатный формат для «1С:Розница 8. Аптека»; DоruTJ должен уметь **принимать** CommerceML 2.05 как альтернативный входной формат для аптек, которые уже настроили выгрузку на свой старый сайт и просто продублируют её на DoruTJ |
| **Регламентные задания** | Встроенный планировщик 1С запускает обмен автоматически по расписанию (чекбокс «Использовать регламентное задание»); без него обмен только вручную ([helpf.pro/faq8/view/715](https://helpf.pro/faq8/view/715.html), [42clouds.com](https://42clouds.com/ru-ru/manuals/nastroyka-obmena-dannymi-s-internet-magazinom-v-1s-unf/)) | Означает, что тайминг отправки батча со стороны аптеки **не управляется DoruTJ** — только промежутком в настройках регламентного задания на стороне клиента. DoruTJ не может «попросить» 1С прислать данные прямо сейчас, если аптека не открыла HTTP-сервис для pull |
| **Файловый обмен (CSV/DBF/XML)** | Для старых/неавтоматизированных конфигураций — экспорт в файл, ручная или FTP-передача | Обязательный fallback-канал (см. §5) |

### 1.3 Как это делают реальные фарм-агрегаторы (первичные источники)

- **Ютека (Uteka)** публикует открытый DevBook для партнёров: обмен через **FTP** файлами `pharmacies.<csv|json|xml>`, `products.<...>`, `/stocks/stocks_<pharmacy>.<...>`, кодировка UTF-8. Поля остатков: `productId`, `pharmacyId`, `price`, `quantity`, `partNumber` (серия), `expirationDate` (`ДД.ММ.ГГГГ`). Идентификация товара — **свой `productId`**, а не производителя, с сопоставлением через штрихкод/ЕГК/РЛС/код Катрен. **Обновления полностью перезаписывают файл целиком — дельт нет.** Частота: справочники аптек/товаров — раз в 3 часа, остатки — раз в 15 минут. Авторизация — Basic/Bearer‑токен/JSON-токен. REST-версия API отвечает кодами 200/400/403/500 с телом `{"error": "..."}` ([docs-dev.uteka.ru/developers/ftp_rest](https://docs-dev.uteka.ru/developers/ftp_rest/)).
- **Аптека.ру**: изначально работали только через файловый обмен, затем разработали API, покрывающее сущности «Аптеки/Товары/Цены/Остатки/Заказы» и статусы по каждой из них; часть партнёров по-прежнему готовит фиды в JSON/YAML и кладёт на FTP/SFTP ([farmbazis.ru/integracija-s-apteka-ru](https://farmbazis.ru/integracija-s-apteka-ru/), [standart-n.ru/.../apteka-ru](https://www.standart-n.ru/news/apteka-ru-nastroyka-raboty-cherez-api)).

**Вывод для архитектуры**: у обоих референсных агрегаторов реальная частота обновления остатков — **15 минут**, а не заявленные в `tz.log` 3 минуты, и оба используют **полную перезапись**, а не дельту, как основной режим. Дельта в 3 минуты из `tz.log` — не отраслевая норма, а завышенное требование клиента; далее в документе она сохранена как целевой SLA, но с пометкой, что для аптек без активной 1С-интеграции (файл/веб-кабинет) реалистичный интервал — 15–60 минут (см. REQ-SYNC-16).

## 2. Идентификация товара: штрихкод vs SKU vs GUID

### 2.1 Три параллельных идентификатора в батче

Контракт `tz.log` уже содержит три поля на одну позицию: `barcode`, `internal_sku`, `trade_name`. Ни один из них не гарантированно надёжен в одиночку:

- **`barcode` (EAN-13/GTIN)** — глобально уникален, только если это настоящий GS1 GTIN производителя. GS1 существует и в Таджикистане (страновой префикс **488**, [gs1.org/locations/tajikistan](https://www.gs1.org/locations/tajikistan)), но:
  - штрихкоды с префиксом **«2»** (2NPPPPPPMMMMZ) зарезервированы GS1 под **внутреннее использование конкретного продавца** (весовой товар, PLU) и **не уникальны глобально** — их нельзя матчить как GTIN между разными аптеками ([rarus.ru/forum/forum7/topic10737](https://rarus.ru/forum/forum7/topic10737/), [forum.infostart.ru/forum2/topic167927](https://forum.infostart.ru/forum2/topic167927/)). Если DoruTJ увидит одинаковый barcode "20XXXXX..." у двух аптек — это **не один и тот же товар**.
  - 75–80% ассортимента — импорт (Индия, РФ, Китай, ЕС; `tz.log` ч.I §1), поэтому фактические GTIN-префиксы в базе DoruTJ будут преимущественно **не** 488-Tajikistan (Индия 890, Россия 460–469, Китай 690–699 и т.д.) — валидировать штрихкод по «национальному» префиксу бессмысленно, только по контрольной цифре EAN-13 и длине.
- **`internal_sku`** — уникален только в рамках одной 1С-базы одной аптеки/сети; **не может** быть глобальным ключом в `medicines`, только частью составного ключа `(pharmacy_id, internal_sku)` на стороне `pharmacy_inventory`.
- **`trade_name`** — свободный текст («Каптоприл 25мг №20»), нужен только как fallback для нечёткого сопоставления и для товара без штрихкода.

### 2.2 Товар без штрихкода — обязательный сценарий, не исключение

Товары без штрихкода — это норма, а не край: рецептурные препараты россыпью, весовые/фасуемые товары (БАД на развес, травы), товары с внутренним PLU аптеки, свежепоступившие позиции, которым ещё не присвоили код. Правило матчинга:

1. Если `barcode` присутствует, валиден по контрольной сумме EAN-13 **и не начинается с 2** (внутренний диапазон) → поиск точного совпадения в `medicines.barcode`.
2. Если совпадения нет **или** штрихкода нет/он внутренний → сопоставление по нормализованной паре `(trade_name, dosage_strength/форма)` через триграммное сходство (`pg_trgm`, тот же движок, что и в поиске по каталогу — решение архитектора, см. `00-PROJECT-CHARTER.md` §3.1, отклонение №1) с порогом схожести (например similarity ≥ 0.6) + проверка `dosage_form`/`dosage_strength` как доп. фильтр (иначе «Каптоприл 25мг №20» и «Каптоприл 50мг №20» ложно смэтчатся).
3. Если однозначного совпадения нет (несколько кандидатов выше порога или ни одного) → позиция уходит в очередь **«требует модерации»** (см. §4.4), **не создаётся** автоматически новая карточка `medicines` силами аптеки (иначе один и тот же МНН расплодится дублями по орфографии каждой сети).
4. Штрихкод, начинающийся с «2» (внутренний диапазон GS1) или короче/длиннее 13 цифр без валидной контрольной суммы, **всегда** трактуется как `internal_sku`-эквивалент конкретной аптеки, никогда — как ключ на `medicines.barcode`.

### 2.3 Дедупликация на стороне `pharmacy_inventory`

`pharmacy_inventory` в `00-PROJECT-CHARTER.md` уже имеет `UNIQUE (pharmacy_id, medicine_id)` — это верно для остатков, но создаёт проблему: **что делать, если у аптеки два разных внутренних SKU (например, разные партии/поставщики) match-ятся на один `medicine_id`?** Решение: агрегировать `stock_quantity` суммой по всем `internal_sku`, матчащимся на один `medicine_id`, а `price_tjs`/`expiry_date`/`batch_number` брать от партии с наименьшим сроком годности (FEFO — First-Expired-First-Out), чтобы покупатель не получил товар с ближайшим истечением срока в первую очередь по ошибке цены от другой партии.

## 3. Контракт синхронизации: расширение `POST /api/v1/inventory/batch-update`

Базовый пример из `tz.log` (ч. II, Модуль 4) сохраняется как ядро контракта; ниже — обязательные расширения, без которых он не переживёт первую же ошибку сети или повторную отправку.

### 3.1 Обязательные поля запроса

```json
{
  "pharmacy_guid": "a4d8c72e-...",
  "batch_id": "b4d1e001-51b2-4e2a-9b7a-8e0b5b8b6b40",
  "sync_type": "delta",
  "sync_timestamp": "2026-08-27T09:00:00Z",
  "source_system": { "product": "1C:Roznica.Apteka", "version": "2.3.14" },
  "items": [
    {
      "barcode": "4601964000125",
      "internal_sku": "SKU-00921",
      "trade_name": "Каптоприл 25мг №20",
      "dosage_form": "таблетки",
      "dosage_strength": "25 мг",
      "price_tjs": 14.50,
      "stock_quantity": 42,
      "batch_number": "L-220145",
      "expiry_date": "2028-06-30",
      "op": "upsert"
    }
  ]
}
```

Добавлено относительно `tz.log`:
- **`batch_id`** — UUID, генерируемый отправителем (1С/скрипт), обязателен для идемпотентности (см. §3.3).
- **`sync_type`**: `"delta"` | `"full"` — обязателен, чтобы worker понимал, нужно ли по завершении обработки **обнулять** позиции аптеки, отсутствующие в батче (актуально только для `full`).
- **`op`** на уровне строки: `"upsert"` (по умолчанию) | `"delete"` — явное удаление позиции (товар выведен из ассортимента), а не «нулевой остаток» (0 остатков ≠ «товара больше не существует», для истории заказов и аналитики это разные события).
- **`source_system`** — для диагностики (какая 1С-конфигурация/версия прислала батч), не критично, но резко ускоряет саппорт при разборе инцидентов.

### 3.2 Дельта vs полная синхронизация

- **`full`** (ночная, `03:00` по `tz.log`) — снапшот **всего** ассортимента аптеки. По завершении обработки батча (все страницы приняты, см. пагинацию ниже) worker обнуляет (`stock_quantity = 0`, не удаляет строку — чтобы сохранить историю цены) все позиции `pharmacy_inventory` этой аптеки, которых не было в присланном снапшоте. Это защищает от рассинхронизации, если аптека вручную удалила позицию в 1С, не прислав `op: "delete"`.
- **`delta`** (каждые 3 минуты, целевой SLA по `tz.log`) — только изменившиеся с последней успешной синхронизации позиции. Требование к 1С-стороне: конфигурация должна уметь отслеживать факт изменения (регистр изменений/`ПланыОбмена` в терминологии 1С) — это штатный механизм платформы, не требует доработки прикладного решения.
- **Пагинация полной синхронизации обязательна**: при среднем ассортименте в несколько тысяч SKU (см. §4) один HTTP-запрос с полным снапшотом — плохая идея (таймауты, память). Контракт должен поддерживать разбиение одного `full`-снапшота на страницы: `"page": 1, "page_count": 6` в теле запроса, с одним общим `batch_id` на все страницы и явным маркером последней страницы (`"is_last_page": true`), чтобы worker знал, когда можно применять шаг «обнулить отсутствующее».

### 3.3 Идемпотентность и повторные отправки

Задача 500+ независимых клиентов (1С регламентные задания, скрипты Excel-загрузки, ручные web-формы), которые будут ретраить при таймауте/обрыве связи — классический **at-least-once delivery** сценарий, для которого отраслевой стандарт — идемпотентный ключ + атомарная claim-запись ([hookdeck.com/webhooks/guides/implement-webhook-idempotency](https://hookdeck.com/webhooks/guides/implement-webhook-idempotency)):

- `batch_id` — идемпотентный ключ уровня батча. Повторный `POST` с тем же `batch_id` (в т.ч. другой page того же батча) должен возвращать **тот же** ранее вычисленный результат (200 + отчёт), а не обрабатываться повторно — `INSERT ... ON CONFLICT (batch_id) DO NOTHING` в таблице `sync_batches`, с последующей отдачей сохранённого отчёта.
- Хранить `batch_id` в течение **не менее 48 часов** (дольше максимального разумного окна ретраев клиента) — TTL-очистка через cron/BullMQ repeatable job.
- Для строк внутри батча (`internal_sku` + `pharmacy_id`) upsert должен быть идемпотентен по построению (`ON CONFLICT (pharmacy_id, medicine_id) DO UPDATE`), т.к. даже без дублирования батча одна и та же позиция может встретиться дважды в одном файле (человеческая ошибка выгрузки).
- **Устаревшие батчи**: если `sync_timestamp` присланного батча старше, чем `last_synced_at` уже применённой записи по конкретной позиции — эта конкретная строка **пропускается** (не откатывает более свежие данные), но остальные строки батча обрабатываются нормально. Актуально при гонке из-за ретраев вне порядка.

### 3.4 Обработка ошибок и отчёт для аптеки

Батч не должен быть «всё или ничего»: одна битая строка (невалидная дата, отрицательная цена) не должна ронять весь батч на 3000 позиций — это тот же принцип, что использует Google Merchant Center для товарных фидов (per-item статус вместо блокировки всего фида) ([support.google.com/merchants/answer/12153802](https://support.google.com/merchants/answer/12153802)). Ответ API:

```json
{
  "batch_id": "b4d1e001-...",
  "status": "partial_success",
  "accepted": 2998,
  "rejected": 2,
  "matched_by_barcode": 2450,
  "matched_by_fuzzy_name": 540,
  "pending_review": 8,
  "errors": [
    { "row_index": 1204, "internal_sku": "SKU-991", "code": "INVALID_EXPIRY_DATE", "message": "expiry_date уже в прошлом" },
    { "row_index": 1877, "internal_sku": "SKU-772", "code": "NEGATIVE_PRICE", "message": "price_tjs < 0" }
  ]
}
```

- Коды ошибок — из общего enum `packages/contracts` (единый формат `{ error: { code, message, details } }` по инженерным стандартам, `00-PROJECT-CHARTER.md` §5).
- `pending_review` — позиции, ушедшие в очередь ручной модерации фаззи-матчинга (§2.2, п.3), а не в ошибку — аптека должна видеть, что товар «принят, но не виден в поиске, пока модератор не подтвердит соответствие».
- Отчёт должен быть доступен аптеке не только в HTTP-ответе (для автоматических интеграций), но и **в веб-кабинете аптеки** (`apps/admin`, роль `pharmacy_admin`) как история синхронизаций — критично для сценария §5, где отправитель — не 1С, а человек, загружающий Excel вручную и не видящий «сырой» HTTP-ответ.

### 3.5 Аутентификация

`tz.log` уже фиксирует `X-Pharmacy-API-Key` + mTLS. Референсный агрегатор (Ютека) поддерживает не mTLS, а более простой набор — Basic Auth / Bearer-токен / JSON-токен в теле ([docs-dev.uteka.ru/developers/ftp_rest](https://docs-dev.uteka.ru/developers/ftp_rest/)). Для DoruTJ mTLS на 500+ разнородных клиентов (часть которых — 1С у не самого сильного местного ИТ-подрядчика) — операционно тяжело (генерация/ротация клиентских сертификатов для каждой аптеки). Рекомендация: **API-ключ (`X-Pharmacy-API-Key`, argon2-хеш в БД по инженерным стандартам) как основной механизм, mTLS — опциональный usilenный режим** для крупных сетей White-Label, включаемый по требованию (см. Открытые вопросы).

## 4. Оценка объёмов и нагрузки

### 4.1 SKU на аптеку

- Крупные городские сети РФ (Москва, МО, Ростов, Краснодар, СПб) держат **17.5–19.7 тыс. SKU** на аптеку — но это зрелые рынки-миллионники с полными складами ([pharmprom.ru](https://pharmprom.ru/assortiment-lekarstv-na-roznichnom-rynke-v-raznyx-regionax-rossii-sushhestvenno-razlichaetsya/)). Это **верхняя граница**, не показатель для Таджикистана.
- ASSUMPTION (нет прямых данных по РТ): для среднего аптечного пункта Таджикистана реалистичный диапазон — **1 500–4 000 SKU** физически на полке одновременно; премиум-сети (Sifat Pharma, 20+ точек) — до 5 000–6 000. Обоснование: план `tz.log` (ч. IV) закладывает базовый каталог платформы в **8 000+ препаратов** на весь нацио­нальный рынок — это верхний предел уникальных МНН/торговых наименований во всей стране, а не ассортимент одной точки; DoD-каталог MVP (`00-PROJECT-CHARTER.md` §2, п.5) требует лишь **≥300 медикаментов** для сидов.
- Это прямо влияет на размер `full`-снапшота (см. §3.2, пагинация обязательна уже при ~2000+ строк на JSON-запрос).

### 4.2 Частота изменения остатков

- Розничная продажа в аптеке — это событие «минус 1–2 упаковки» на каждую продажу; при потоке ~50–150 чеков/день на точку (обычная городская аптека) кол-во **изменившихся строк** остатков за 3 минуты в среднем — единицы, редко больше 10–20 (кроме моментов приёмки поставки, когда за одну операцию обновляются 50–300 позиций разом).
- Референс (Ютека) считает 15-минутный интервал остатков достаточным для маркетплейса такого рода ([docs-dev.uteka.ru](https://docs-dev.uteka.ru/developers/ftp_rest/)) — это подтверждает, что 3-минутный SLA из `tz.log` — искусственно жёсткий, но не невозможный при батчинге через очередь (BullMQ), а не синхронной записи в БД на каждый запрос.

### 4.3 Пиковая нагрузка при 500+ аптеках

Расчёт (без внешнего источника, инженерная оценка для этого проекта):

- **Установившийся режим (delta)**: 500 аптек / 180 сек = **≈2.8 HTTP-запроса/сек** в среднем на приём батчей; при ~20 изменившихся строк на батч это **≈56 item-events/сек** — на 2–3 порядка меньше заявленных в `tz.log` «5000 событий/сек» (это явно завышенная цифра клиента, безопасно приземлить ожидания).
- **«Громовое стадо» (thundering herd)**: регламентные задания 1С у разных аптек с высокой вероятностью настроены на круглые интервалы (например, каждые 3 минуты от начала часа) — если много аптек синхронизировано по системным часам, всплеск запросов может прийти **одновременно** на границе минуты. Требование: воркер должен принимать запрос быстро (просто положить в очередь BullMQ и вернуть 202/200), тяжёлая обработка (matching, upsert) — асинхронно из очереди, не в HTTP-потоке.
- **Ночная полная синхронизация в 03:00**: если все 500 аптек по `tz.log` синхронизируются **одновременно** в 03:00 с ~3000 SKU каждая — это **≈1.5 млн строк** в пределах нескольких минут. Буквальная реализация «все в 03:00» — антипаттерн. Требование: назначать каждой аптеке **свой сдвиг** (`sync_slot`, например `pharmacy_guid` hash mod N минут) внутри окна 02:00–05:00, чтобы распределить нагрузку равномерно, либо переходить на **pull**-модель (worker сам обходит аптеки со включённым OData/HTTP-сервисом по расписанию), а не полагаться на то, что все клиенты стартуют по своим часам синхронно.

### 4.4 Матчинг и модерация как узкое место

Фаззи-матчинг по имени (§2.2) — самая дорогая по CPU операция в пайплайне (триграммное сравнение против каталога). При полном ночном сбросе 500 аптек × N позиций без штрихкода это может создать заметную нагрузку на Postgres. Рекомендация: фаззи-матчинг выполнять **асинхронно в worker**, с кэшированием уже подтверждённых соответствий `(pharmacy_id, internal_sku) → medicine_id` в отдельной таблице-словаре (`pharmacy_sku_mapping`), чтобы повторные батчи (99% строк — те же самые SKU, что вчера) вообще не проходили фаззи-поиск повторно, а сразу брали закреплённое соответствие.

## 5. Аптеки БЕЗ автоматизации

Существенная часть из 2 800 лицензированных аптек РТ (`tz.log` ч.I) не имеет 1С вообще — это нужно поддержать как равноправный, а не «второсортный», канал.

### 5.1 Ручной ввод через веб-кабинет

- Роль `pharmacy_admin`/сотрудник аптеки в `apps/admin` получает форму: поиск позиции по МНН/названию из каталога `medicines` → ввод `price_tjs`, `stock_quantity`, `expiry_date`, `batch_number` → сохранение вызывает **тот же** внутренний сервис, что и `batch-update` (один upsert), просто с `source_system.product = "manual_web"` и батчем из одной строки. Это гарантирует, что бизнес-правила (FEFO, идемпотентность, валидация даты) не дублируются отдельной веткой кода для ручного ввода.
- Обязательное отличие UX от 1С-канала: для полностью ручных аптек `last_synced_at` не обновляется автоматически по таймеру, поэтому нужен **явный признак «протухания» остатка** (например, бейдж «Обновлено 3 дня назад» в карточке товара для покупателя и/или автоматическое понижение приоритета/скрытие позиции в выдаче поиска, если `last_synced_at` старше configurable порога — например 48–72 часов), иначе покупатель увидит несуществующий товар «в наличии».

### 5.2 Импорт из Excel/CSV

- Шаблон для скачивания (аналог практики маркетплейсов Wildberries/Ozon, где продавцы без ERP массово загружают остатки Excel-шаблоном через личный кабинет — это стандартный отраслевой паттерн для marketplace-онбординга продавцов без ERP, не специфичный именно для фармы) — колонки: `barcode` (опционально), `trade_name`, `dosage_form`, `dosage_strength`, `price_tjs`, `stock_quantity`, `expiry_date`, `batch_number`.
- Парсинг → та же нормализация и фаззи-матчинг, что в §2.2, → тот же отчёт `partial_success` с построчными ошибками (§3.4), отображаемый как таблица в UI (подсветка строк с ошибкой/на модерации), а не как «сырой» JSON.
- Формат дат — главный источник ошибок при Excel-импорте (регион/локаль Excel меняет `DD.MM.YYYY` на `MM/DD/YYYY`); парсер обязан **не угадывать** формат по эвристике, а требовать фиксированный формат в шаблоне и жёстко валидировать (`day > 12` → однозначно `DD.MM.YYYY`, иначе — явная ошибка `AMBIGUOUS_DATE_FORMAT`, а не тихая порча даты).

## Требования, вытекающие из исследования

1. **REQ-SYNC-1**: Контракт `POST /api/v1/inventory/batch-update` ДОЛЖЕН принимать обязательное поле `batch_id` (UUID, генерируется отправителем); повторный запрос с тем же `batch_id` ДОЛЖЕН возвращать сохранённый результат первой обработки без повторного применения изменений.
2. **REQ-SYNC-2**: Каждая строка item ДОЛЖНА поддерживать поле `op` со значениями `upsert` (по умолчанию) и `delete`; `delete` ДОЛЖЕН отличаться от `stock_quantity: 0` в модели данных (например, отдельный статус позиции в `pharmacy_inventory`, не удаление строки).
3. **REQ-SYNC-3**: Запрос ДОЛЖЕН содержать `sync_type: "delta" | "full"`. При `sync_type: "full"` после успешного приёма всех страниц батча worker ДОЛЖЕН обнулить остатки по всем позициям аптеки, отсутствующим в снапшоте, но НЕ удалять сами строки `pharmacy_inventory`.
4. **REQ-SYNC-4**: Полная синхронизация (`full`) ДОЛЖНА поддерживать постраничную отправку (`page`, `page_count`, `is_last_page`) под общим `batch_id`; ни один эндпоинт синхронизации не ДОЛЖЕН требовать от клиента передачи более 1000 позиций за один HTTP-запрос.
5. **REQ-SYNC-5**: Идентификация товара ДОЛЖНА проверять `barcode` на: (а) длину и контрольную цифру EAN-13, (б) непринадлежность к диапазону внутренних кодов GS1 (префикс `2`) — штрихкоды с префиксом `2` ДОЛЖНЫ обрабатываться как эквивалент `internal_sku`, а не как ключ поиска по `medicines.barcode`.
6. **REQ-SYNC-6**: При отсутствии валидного глобального `barcode` матчинг товара ДОЛЖЕН выполняться по нормализованному `trade_name` + `dosage_form` + `dosage_strength` через триграммное сходство (`pg_trgm`) с настраиваемым порогом; при нескольких кандидатах выше порога или отсутствии кандидатов позиция ДОЛЖНА получать статус `pending_review`, а не создавать новую запись `medicines` автоматически.
7. **REQ-SYNC-7**: ДОЛЖНА существовать таблица-кэш `pharmacy_sku_mapping (pharmacy_id, internal_sku) → medicine_id`, заполняемая при первом успешном матчинге (в т.ч. после ручной модерации `pending_review`) и используемая для всех последующих батчей той же пары `(pharmacy_id, internal_sku)`, чтобы избежать повторного фаззи-поиска.
8. **REQ-SYNC-8**: Если несколько `internal_sku` одной аптеки матчатся на один `medicine_id` (несколько партий), `pharmacy_inventory.stock_quantity` ДОЛЖЕН быть суммой остатков всех партий, а отображаемые `price_tjs`/`expiry_date`/`batch_number` ДОЛЖНЫ браться от партии с ближайшим сроком годности (FEFO).
9. **REQ-SYNC-9**: Ответ на batch-update ДОЛЖЕН иметь статус `partial_success` при частичных ошибках, содержать счётчики (`accepted`, `rejected`, `pending_review`, `matched_by_barcode`, `matched_by_fuzzy_name`) и построчный список ошибок с `row_index`, `internal_sku`, кодом ошибки из общего enum `packages/contracts` и человекочитаемым сообщением. Ни одна валидная строка батча НЕ ДОЛЖНА быть отклонена из-за ошибки в другой строке того же батча.
10. **REQ-SYNC-10**: История и отчёты по синхронизациям (включая ручной Excel-импорт и ручной ввод через веб-форму) ДОЛЖНЫ быть доступны в `apps/admin` для роли `pharmacy_admin`/сотрудника аптеки как читаемый UI, а не только как HTTP-ответ API.
11. **REQ-SYNC-11**: Строка батча со `sync_timestamp`/временем обработки старше, чем `last_synced_at` уже применённой записи для той же позиции, ДОЛЖНА быть пропущена (не откатывать более свежие данные) без отклонения остального батча.
12. **REQ-SYNC-12**: Приём HTTP-запроса на batch-update ДОЛЖЕН быть немедленным (постановка в очередь BullMQ + быстрый ACK), тяжёлая обработка (matching, upsert, обнуление при `full`) ДОЛЖНА выполняться асинхронно в `apps/worker`, вне HTTP-потока запроса.
13. **REQ-SYNC-13**: Расписание полной ночной синхронизации ДОЛЖНО распределять аптеки по временным слотам внутри окна (например, детерминированный сдвиг по hash от `pharmacy_guid`), а не рассчитывать на одновременный старт всех 500+ аптек в 03:00:00.
14. **REQ-SYNC-14**: Аутентификация входящих batch-update запросов ДОЛЖНА поддерживать `X-Pharmacy-API-Key` (argon2-хеш в БД) как базовый обязательный механизм; mTLS — опциональный дополнительный слой для крупных White-Label сетей, а не обязательное требование для всех 500+ аптек.
15. **REQ-SYNC-15**: Импорт остатков через Excel/CSV в веб-кабинете ДОЛЖЕН использовать фиксированный формат даты в шаблоне колонки `expiry_date` и явно возвращать ошибку `AMBIGUOUS_DATE_FORMAT`/`INVALID_DATE`, а не эвристически угадывать локаль дат.
16. **REQ-SYNC-16**: Для аптек с полностью ручным вводом остатков (без 1С/файлового обмена) карточка товара в поиске ДОЛЖНА нести признак давности (`last_synced_at`) и понижать приоритет/скрывать позицию в выдаче при превышении настраиваемого порога давности (по умолчанию — 72 часа).
17. **REQ-SYNC-17**: Шлюз синхронизации ДОЛЖЕН уметь принимать альтернативный входной формат **CommerceML 2.05** (`import.xml` + `offers.xml`) как второй поддерживаемый канал ingestion наравне с JSON REST-контрактом, конвертируя его во внутреннюю модель `batch-update` перед матчингом.
18. **REQ-SYNC-18**: Для сетей, ведущих учёт в «1С:Управление аптечной сетью», конфигурация интеграции ДОЛЖНА допускать привязку одного `one_c_endpoint`/API-ключа к целой сети (`pharmacy_chains`) с последующим маппингом позиций на конкретные `pharmacies` по коду точки внутри батча, а не требовать по одному ключу на каждую физическую аптеку сети.

## Открытые вопросы

1. Реальная доля аптек Таджикистана, использующих 1С (в любой версии) против Excel/бумаги/полного отсутствия учёта — не найдена ни в открытых источниках, ни в `tz.log`. От этого прямо зависит приоритет разработки: гейтвей 1С vs веб-форма ручного ввода. Нужны данные от заказчика/полевое интервью с 3–5 реальными аптеками-пилотами.
2. Есть ли у Sifat Pharma/Oson Pharm/Madad Pharm (целевые White-Label клиенты) уже развёрнутая 1С:Управление аптечной сетью или частные учётные системы — определяет, что предлагать: готовый HTTP-сервис-адаптер под их текущую 1С или полностью ручной онбординг.
3. Актуальная стоимость и процедура получения GTIN/членства в GS1 Tajikistan для локальных таджикских производителей/дистрибьюторов — не найдено (страница gs1.org/locations/tajikistan подтверждает существование, но не публикует прайс/процесс). Не критично для MVP (штрихкоды приходят от аптек как есть), но важно для будущей проверки подлинности штрихкода.
4. Нужна ли поддержка обязательной маркировки (аналог DataMatrix/ФГИС МДЛП в РФ) для лекарств в Таджикистане — прямых подтверждений действующей системы маркировки в РТ не найдено; закон «О лекарственных средствах и фармацевтической деятельности» РТ описывает госрегистрацию и реестр, но не подтверждён факт цифровой маркировки уровня DataMatrix. Требует юридической проверки, т.к. если появится — потребуется отдельное поле `datamatrix_code` независимо от `barcode`.
5. Согласовать с заказчиком реальный целевой SLA дельта-синхронизации: 3 минуты из `tz.log` избыточны против отраслевой практики (15 минут у Ютеки/Аптека.ру) — понижение SLA до 5–15 минут снизит инфраструктурные риски без заметной потери UX для конечного покупателя.
6. Нужен ли для крупных сетей pull-режим (DoruTJ сам обращается к OData/HTTP-сервису аптеки по расписанию) в дополнение к push-контракту `batch-update` — зависит от того, готовы ли ИТ-подрядчики аптек открывать входящий доступ к своей 1С-базе (обычно не готовы) против готовности настроить исходящий регламентный обмен (обычно да).
