## Модель угроз (STRIDE)

### Активы и их защищаемые свойства

| Актив | Где живёт | Критичное свойство |
|---|---|---|
| **Деньги** (эскроу, комиссия, payout аптеке/курьеру) | `escrow_ledger`, `payout_schedule`, `platform_fee`, `payment_operations`, `courier_earnings`, `courier_payouts`, `platform_billing_invoices` | Целостность (двойная запись сходится), неотрекаемость источника изменения (только через вебхук/`super_admin` override) |
| **Медданные** (фото рецепта, распознанный текст, голосовой ввод) | `prescriptions.image_url` (MinIO), `raw_model_output_ref`, `voice_input_requests` | Конфиденциальность (узкий круг ролей), целостность цепочки решений (`composite_confidence` не подделываема клиентом) |
| **Персональные данные** (телефон, адрес, ФИО, геолокация) | `users`, `user_addresses`, `orders.delivery_*` | Конфиденциальность, минимизация в логах |
| **Ключи доступа аптек (1С)** | `pharmacy_api_keys` | Конфиденциальность секрета, целостность подписи запроса |
| **Токены сессий** (JWT access, refresh, OTP) | `refresh_tokens`, `otp_codes`, in-memory JWT | Конфиденциальность, невозможность повторного использования (replay) |

### Реестр угроз STRIDE

> Столбец «Рубеж» — где физически стоит защита (какой слой/файл/guard), со ссылкой на уже принятое
> решение в модульных SRS, либо на НОВОЕ требование этого документа (`SRS-NFR-*`), если рубеж ранее
> не был явно специфицирован как угроза (хотя механизм местами уже существовал под другим углом).

**SRS-NFR-001** [R1] **Spoofing — подделка вебхука оплаты.** Атакующий отправляет `POST
/api/v1/payments/webhook` с поддельным телом, утверждающим `payment_confirmed` для чужого/своего
неоплаченного заказа, без знания HMAC-секрета банка. *Митигация*: `SRS-PAY-020` — HMAC-проверка
`BankWebhookVerifierPort.verify(rawBody, headers)` ДО десериализации; несовпадение →
`401 INVALID_WEBHOOK_SIGNATURE`, тело не парсится. Категорический запрет (`SRS-PAY-018`): НИ ОДИН
путь, кроме `HandlePaymentWebhookUseCase`, не может вызвать `EscrowLedger.recordHold()`. *Рубеж*:
`infrastructure/adapters/*-webhook-verifier.adapter.ts`, до `application`.

**SRS-NFR-002** [R1] **Spoofing — подделка 1С-запроса (`X-Pharmacy-API-Key`).** Атакующий, узнавший
`key_prefix` (публично видим), пытается подобрать `secret` или подделать `X-Pharmacy-Signature`.
*Митигация*: `argon2.verify` секрета (не по значению, не timing-небезопасно — argon2 сам защищён от
timing-атак по конструкции), HMAC-подпись тела с `crypto.timingSafeEqual` (`SRS-API-033` шаг 9) —
подбор секрета неосуществим без брутфорса 256-битного пространства. *Рубеж*: `PharmacyApiKeyGuard`.

**SRS-NFR-003** [R1] **Spoofing — подделка Telegram `initData`.** Атакующий модифицирует поле `user`
после легитимной выдачи `initData` (например, подставляет чужой `user.id`), не пересчитывая `hash`.
*Митигация*: constant-time сравнение HMAC (`SRS-API-031` шаг 6) — любое изменение полей ломает хеш.
*Рубеж*: `TelegramAuthProvider`.

**SRS-NFR-004** [R1] **Tampering — Replay вебхука/1С-запроса.** Перехваченный легитимный запрос
повторно отправляется атакующим (не банком) с той же подписью, чтобы вызвать повторное
бизнес-действие (например, повторный `capture`/повторную обработку батча остатков как «более
свежего»). *Митигация*: (1) идемпотентность по `bankEventId`/`batch_id` (`SRS-PAY-022`,
`SRS-DOM-168`) — повтор ДАЖЕ С валидной подписью не выполняет бизнес-логику дважды; (2) для 1С —
дополнительно nonce-анти-replay (`SRS-API-033` шаг 6, `PHARMACY_REQUEST_REPLAYED`) и окно timestamp
±5 минут (`PHARMACY_TIMESTAMP_OUT_OF_WINDOW`) — перехваченный запрос старше 5 минут отклоняется ещё
ДО проверки идемпотентности. *Рубеж*: `PharmacyApiKeyGuard` (транспорт) + `payment_operations`/
`inventory_sync_batches` UNIQUE (бизнес-слой) — оборонительная многослойность, ни один рубеж не
полагается на срабатывание другого.

**SRS-NFR-005** [R1] **Tampering — Кросс-тенантный доступ (IDOR через смену Host/slug).**
Пользователь тенанта A подменяет `Host`/`X-Tenant-Slug` на тенант B, пытаясь получить доступ к чужим
данным тем же JWT. *Митигация*: `TenantResolutionGuard` сравнивает `token.tenantId` с резолвленным
`tenantId` запроса ДО контроллера (`SRS-API-045`, `403 CROSS_TENANT_ACCESS_DENIED`); ВТОРОЙ, независимый
рубеж — каждый `TenantScopedRepository`-метод обязан принимать `tenantId` первым параметром
(`SRS-API-043`, `SRS-TEN-011`) — компрометация guard'а НЕ давала бы утечки, т.к. запрос к БД всё равно
идёт с `WHERE tenant_id=`. *Обязательный тест*: `TC-API-030`, `TC-NFR-005` (ниже).

**SRS-NFR-006** [R1] **Tampering — CSS/HTML-инъекция через White-Label брендинг.** `pharmacy_admin`
своей сети, имеющий легитимное право `tenancy:manage-branding`, вписывает
`background:url(javascript:...)` или `</style><script>` в `brand_palette` (JSONB, рендерится как
инлайн CSS-переменные в `<head>` каждого клиента тенанта) — легитимный канал конфигурации становится
вектором XSS против ВСЕХ посетителей White-Label домена. *Митигация*: `SRS-TEN-014` — строгий
allowlist-паттерн на запись (`^#[0-9a-fA-F]{6}$` для цветов, `^\d{1,2}px$` для радиуса, closed enum
для шрифта) — невалидное значение `400 VALIDATION_ERROR` до сохранения, произвольная строка
физически не проходит Zod-схему. *Рубеж*: `BrandPaletteSchema` (`packages/contracts`), применяется на
`PUT /api/v1/admin/tenants/:id/branding`.

**SRS-NFR-007** [R1] **Repudiation — отрицание ручного финансового вмешательства.**
`super_admin`/`support_agent` выполняет `AdminPaymentOverrideUseCase`/`resolveAdjustment`/
`admin_return_override`, затем отрицает факт действия. *Митигация*: append-only `audit_log`
(`SRS-ADM-062..066`) — каждое действие несёт `actor_user_id`, `reason` (NOT NULL для этих категорий),
`before`/`after`, `requestId`; `REVOKE UPDATE, DELETE ON audit_log FROM app_role` на уровне СУБД
(`SRS-ADM-064`) — компрометация приложения не даёт стереть след. *Рубеж*: миграция `0014_platform.sql`
+ `AuditLogRepository` без методов мутации.

**SRS-NFR-008** [R1] **Information Disclosure — утечка фото рецепта.** (а) Прямой доступ к MinIO
presigned URL после истечения предполагаемого использования; (б) IDOR — подбор `prescriptionId` в
`GET /prescriptions/:id/image` ролью без права. *Митигация*: (1) бакет `STORAGE_BUCKET_PRESCRIPTIONS`
— `private`, presigned URL живёт `PRESCRIPTION_IMAGE_URL_TTL_SECONDS=300` и выпускается заново на
каждый запрос (`SRS-RX-009`) — нет долгоживущей прямой ссылки для шаринга; (2)
`PrescriptionAccessPolicy.canViewImage()` — только владелец/назначенный фармацевт/`super_admin` с
обязательным `audit_log` (`SRS-RX-011/012`, `SRS-DOM-155`); (3) шифрование at rest (`SRS-RX-010`).
*Обязательный тест*: `TC-API-045`, `TC-NFR-008`.

**SRS-NFR-009** [R1] **Information Disclosure — IDOR на заказах и рецептах внутри своего тенанта.**
`customer` A подставляет чужой `orderId`/`prescriptionId` того же тенанта (не межтенантный кейс —
внутритенантный перебор). *Митигация*: политика владения в `application`
(`OrderPolicy`/`PrescriptionAccessPolicy`) проверяет `resource.customerId === actor.userId` НЕЗАВИСИМО
от тенантного guard'а (тот проверяет только «тот ли тенант», не «тот ли владелец»); несовпадение
владельца → `404 NOT_FOUND` (не `403` — та же логика скрытия существования чужого ресурса, что
`SRS-API-046`, применённая внутри тенанта, а не только между тенантами). *Рубеж*: `application/policies/*`.

**SRS-NFR-010** [R1] **Information Disclosure — утечка PII/секретов в структурных логах.**
Разработчик по неосторожности логирует объект целиком (`req.body`), в котором есть `phone`/`code`/
`Authorization`. *Митигация*: `pino` `redact`-конфигурация на уровне HTTP-интерцептора
(`SRS-API-068/069`) — allow-list вместо blacklist для `/prescriptions/*`/`/voice-input/*`
(`SRS-RX-014`, `PiiRedactionInterceptor`), общий glob-паттерн `*.password`/`*.secret`/`*.token`/
`*.hash` для остальных эндпоинтов. *Обязательный тест*: `TC-API-044`, `TC-NFR-010` (проверка КОНКРЕТНО
редакции, не «код не падает»).

**SRS-NFR-011** [R1] **Elevation of Privilege — брутфорс OTP входа.** Атакующий подбирает 6-значный
код входа (`otp_codes.purpose='login'`). *Митигация* — трёхуровневая: (1) лимит запроса кода на номер
(`OTP_REQUEST_COOLDOWN_SECONDS=60`, `OTP_REQUEST_MAX_PER_10MIN=3`, `OTP_REQUEST_MAX_PER_DAY=10`,
`SRS-API-019`) — не даёт атакующему получить много кодов подряд на чужой номер; (2) лимит попыток
верификации по `otpRequestId` (`OTP_VERIFY_MAX_ATTEMPTS=5`, `SRS-API-022`) — 6-я попытка `423
OTP_LOCKED` НЕЗАВИСИМО от правильности кода; (3) TTL 300 секунд (`SRS-DOM-080`) — окно атаки короткое.
Математика: 5 попыток × (окно 300с / cooldown частично исчерпан) на 10^6 пространства кода — вероятность
успешного подбора за жизнь одного OTP пренебрежимо мала (5/1 000 000). *Рубеж*: `AuthController` +
Redis-счётчики по `phone`/`otpRequestId`.

**SRS-NFR-012** [R1] **Elevation of Privilege — перебор OTP вручения (4 цифры, более узкое
пространство).** 4-значный `delivery_handover` OTP (10 000 комбинаций) физически слабее 6-значного —
курьер стоит у двери и может пробовать угадать код клиента без его участия (сценарий отличается от
брутфорса входа: атакующий физически СОСЕДСТВУЕТ с легитимным получателем, а не удалённый бот).
*Митигация*: `maxAttempts=5` ЖЁСТКО в самой VO `OtpCode` (`SRS-DOM-080/082`, не только rate-limit
эндпоинта, в отличие от login-OTP) — 5/10000 = 0.05% вероятность угадать за весь лимит попыток; TTL
900 секунд (15 минут) не расширяет окно атаки (ограничено количеством попыток, не временем — атакующий
не может «подождать и повторить», исчерпание попыток перманентно блокирует код до перегенерации
фармацевтом/поддержкой). *Рубеж*: `OtpCode.verify()` домен, вызывается `markDelivered()`.

**SRS-NFR-013** [R1] **Elevation of Privilege — role/permission bypass через прямой вызов API в обход
UI.** Роль `pharmacy_admin` пытается вызвать `disputes:resolve-refund-partial` напрямую (в UI кнопки
нет, но эндпоинт существует). *Митигация*: `@Roles(...)` НА УРОВНЕ ГВАРДА, не только сокрытие в UI
(`SRS-API-039`) — маршрут физически недоступен ролям вне списка декоратора, `403 INSUFFICIENT_ROLE`
до входа в контроллер. Дополнительно — `application`-политика владения (`SRS-DOM-061`,
`REQ-DISPUTE-10`) для случаев, где грубой роли недостаточно (self-dealing). *Обязательный тест*:
`TC-API-029`.

**SRS-NFR-014** [R1] **Tampering — SQL-инъекция.** *Митигация*: Drizzle ORM — параметризованные
запросы по умолчанию для ВСЕХ операций через query builder; сырой SQL (`sql\`...\``, используется в
composite-поиске §3.3 `20-module-catalog-search.md`, `COPY`-загрузка `22-module-inventory-sync-1c.md`
SRS-INV-053) — ТОЛЬКО через параметризованные плейсхолдеры Drizzle (`sql\`... ${param} ...\`` с
автоматическим экранированием драйвером `pg`), конкатенация пользовательского ввода в SQL-строку —
блокирующее замечание код-ревью (`02` §7 п.2 «бизнес-логика вне слоя» распространяется на
security-паттерны — конкатенация строки есть нарушение чистоты границы `infrastructure`, ловится
ревьюером как антипаттерн, не автоматическим линтером в MVP). *Обязательный тест*: `TC-NFR-014` —
security-тест-сьют (`tests/security/sql-injection.spec.ts`) прогоняет OWASP-паттерны (`' OR '1'='1`,
`'; DROP TABLE--`) через каждый текстовый query-параметр публичных эндпоинтов (`search`, `filter[...]`)
и проверяет: (а) `400`/`0 результатов`, НЕ `500`; (б) отсутствие изменения количества строк в
контрольных таблицах после теста.

**SRS-NFR-015** [R1] **Tampering — XSS (Cross-Site Scripting).** Векторы: (1) пользовательский ввод,
отражённый в HTML без экранирования (React экранирует по умолчанию через JSX — `dangerouslySetInnerHTML`
запрещён вне явно вычитанных мест, см. ниже); (2) White-Label брендинг (`SRS-NFR-006`, отдельная
митигация); (3) `doctor_name`/`raw_name` из OCR-ответа, отображаемые фармацевту при верификации.
*Митигация*: (а) React JSX экранирует текстовые узлы по умолчанию — `dangerouslySetInnerHTML`
запрещён линтер-правилом `react/no-danger` (ДОПОЛНЕНИЕ к ESLint-конфигу `02` §6.2, единственное
согласованное исключение — рендер Markdown-описаний медикаментов через санитайзер `dompurify` с
allowlist тегов `p,b,i,ul,li,br`); (б) `Content-Security-Policy: default-src 'self'`
(`SRS-API-064`) — блокирует инлайн-скрипты и внешние источники даже при обходе экранирования; (в)
OCR-текст рендерится ТОЛЬКО как текстовый узел React (никогда не через `innerHTML`), т.к. это внешние,
не доверенные данные независимо от происхождения (тот же принцип, что «данные, а не команды» из
общей safety-политики системы). *Обязательный тест*: `TC-NFR-015`.

**SRS-NFR-016** [R1] **Tampering — CSRF (Cross-Site Request Forgery).** *Митигация*: контракт —
Bearer JWT в заголовке `Authorization`, НЕ cookie-сессия (`Charter §3.6 п.3`, `SRS-API`) — классический
CSRF требует, чтобы браузер АВТОМАТИЧЕСКИ приложил учётные данные (cookie) к кросс-доменному запросу;
т.к. токен передаётся явным заголовком, который куда-либо не подставляется браузером сам, CSRF в
классическом виде НЕ применим к мутирующим эндпоинтам `/api/v1/*`. Единственное место, где куки
теоретически участвуют, — нет: `refresh_tokens` тоже передаётся в теле JSON (`SRS-API-026`), не
куки. CORS allowlist (`SRS-API-065`) — дополнительный рубеж (не основной): даже если бы токен как-то
кэшировался браузером, кросс-доменный `fetch` с чужого origin не получил бы читаемый ответ. *Рубеж*:
архитектурное решение контракта, задокументированное здесь явно как причина ОТСУТСТВИЯ отдельного
CSRF-токена (частый вопрос ревьюера безопасности — ответ: «not applicable by design», не «забыли»).

**SRS-NFR-017** [R1] **Tampering/DoS — SSRF (Server-Side Request Forgery).** Векторы: (1) OCR/STT
провайдеры получают ссылку на файл вместо самого файла — если бы контракт принимал произвольный URL
для загрузки, атакующий мог бы заставить сервер обратиться к `http://169.254.169.254/`
(метаданные облака) или внутренним сервисам; (2) Nominatim-геокодинг (`REQ-GEO-2`) — если бы адрес
пользователя передавался как URL напрямую. *Митигация*: (а) `PrescriptionOcrProvider.recognize()`
принимает `imageBuffer: Buffer` (`SRS-RX-015`), НЕ URL — файл загружается клиентом на сервер
(`multipart/form-data`, `SRS-API-066`), сервер сам кладёт его в MinIO и передаёт байты (или
внутреннюю presigned ссылку на СОБСТВЕННЫЙ MinIO) внешнему провайдеру — атакующий не может подставить
произвольный хост в исходящий запрос сервера; (б) Nominatim вызывается ТОЛЬКО с текстовым query
(геокодинг «текст → координаты»), не принимает и не проксирует произвольный URL от клиента
(`REQ-GEO-2`: Nominatim — вспомогательная подсказка, финальные координаты — пин пользователя, не
результат геокодинга сервером по клиентскому вводу произвольного адреса-URL); (в) любой БУДУЩИЙ
эндпоинт, принимающий URL для server-side fetch (например, `brand_logo_url` при возможной будущей
фиче «загрузить лого по ссылке» — ОТСУТСТВУЕТ в R1, загрузка исключительно файлом через
`multipart/form-data` в MinIO), обязан проходить allowlist-проверку хоста ПЕРЕД любым сетевым
вызовом — зафиксировано здесь как архитектурное ограничение на будущее, а не только текущий код.
**Дополнение к схеме БД не требуется** — угроза закрывается отсутствием соответствующей
функциональности, а не отдельным контролем.

**SRS-NFR-018** [R1] **DoS — дорогие эндпоинты (поиск, автодополнение, OCR, checkout).**
*Митигация по эндпоинту*:

| Эндпоинт | Стоимость запроса | Защита |
|---|---|---|
| `GET /medicines/search` | Composite SQL (GIN trgm + GiST) | `RATE_LIMIT_ANON_PER_MIN=100` (`SRS-CAT-057`) + Redis-кэш результатов 30с с anti-stampede lock (`SRS-CAT-060`) — конкурентные промахи одного ключа НЕ порождают N параллельных тяжёлых запросов |
| `POST /prescriptions` (загрузка + OCR) | Внешний вызов Gemini (медленный, платный) | `RATE_LIMIT_PRESCRIPTION_UPLOAD_PER_DAY` (per-`customerId`, `23-module-prescriptions-ai.md` §11.5) + `multipart` лимит 10 МБ (`SRS-API-066`) + предобработка изображения (deskew/resize) ДО отправки внешнему провайдеру снижает стоимость каждого вызова |
| `POST /api/v1/orders` (checkout) | Пишущая транзакция + резерв остатка | `RATE_LIMIT_USER_PER_MIN=300` (общий) + обязательный `Idempotency-Key` (`SRS-API-009`) не даёт задвоить работу повторными кликами |
| `POST /api/v1/inventory/batch-update` | До 1000 строк, тяжёлая обработка | `RATE_LIMIT_1C_BATCH_PER_MIN=20` на `pharmacyId` + немедленный ACK, тяжёлая логика — асинхронно в BullMQ (`SRS-INV-052`), HTTP-воркер не блокируется |
| `POST /voice-input` (STT) | Внешний вызов Whisper, аудио до `VOICE_INPUT_MAX_SIZE_MB` | Тот же паттерн, что OCR — per-user суточный лимит + лимит размера/длительности файла (`VOICE_INPUT_MAX_DURATION_SEC`) |

**SRS-NFR-019** [R1] [ДОПОЛНЕНИЕ, глобальный рубеж] Помимо per-route лимитов выше, `apps/api` несёт
ГЛОБАЛЬНЫЙ IP-based лимит на уровне Nginx (§«DevOps» ниже, `limit_req_zone`) — второй, независимый от
`@fastify/rate-limit`, рубеж (defense in depth: даже при обходе/ошибке в конфигурации Fastify-лимитера
Nginx продолжает резать аномальный трафик до того, как он дойдёт до Node-процесса).

**SRS-NFR-020** [R1] **Злоупотребление загрузкой файлов.** Векторы: (1) загрузка не-изображения под
видом `image/jpeg` (MIME-спуфинг); (2) zip-бомба/декомпрессионная бомба через некорректно
интерпретируемый файл; (3) исполняемый код, замаскированный под изображение, для эксплуатации
уязвимости в библиотеке обработки изображений. *Митигация*: (а) проверка `mimeType` НЕ по
клиентскому заголовку, а по magic bytes файла (`file-type`-подобная библиотека, серверная сторона,
`infrastructure/adapters/image-preprocessing.adapter.ts`) — несовпадение заявленного и фактического
типа → `415 UNSUPPORTED_MEDIA_TYPE`; (б) жёсткий лимит размера файла ДО начала обработки
(`multipart` `10 MB`, `SRS-API-066`) — потоковая проверка `Content-Length`, файл, превышающий лимит,
не буферизуется в память целиком; (в) предобработка изображения (`SRS-RX-002`/§3.2
`23-module-prescriptions-ai.md`) выполняется библиотекой с ограничением по выходному разрешению
(предотвращает decompression bomb — результирующий буфер ограничен, даже если исходный файл
декларирует огромные размеры); (г) файл НИКОГДА не выполняется/не интерпретируется как код — только
байты, передаваемые в OCR/STT провайдер и в object storage.

**SRS-NFR-021** [R1] **Elevation of Privilege — эскалация через `super_admin`-override без
подотчётности.** Компрометированный или недобросовестный `super_admin`-аккаунт злоупотребляет
`AdminPaymentOverrideUseCase`/`resolveAdjustment` для вывода денег в свою пользу. *Митигация*: (1)
каждый вызов ОБЯЗАН нести непустой `reason` (доменная валидация, `SRS-DOM-035`/`SRS-DOM-060`); (2)
алерт дежурному на КАЖДЫЙ вызов `AdminPaymentOverrideUseCase` (`SRS-PAY-018` — «не тихая операция,
несмотря на легитимность»); (3) append-only `audit_log` неудаляем даже для самого `super_admin`
(`SRS-ADM-064` — `REVOKE` действует на роль БД `app_role`, под которой работает ВЕСЬ прикладной код,
включая запросы от лица `super_admin`); (4) организационный контроль (вне кода) — минимум 2 разных
человека имеют роль `super_admin` с доступом к продовой БД, компенсирующий контроль — вне периметра
этого документа, фиксируется как ОРГАНИЗАЦИОННОЕ требование в чек-листе готовности к продакшену.

### Детерминированность

**SRS-NFR-030** [R1] [`02` §2.6, Charter «работает без единого внешнего API-ключа»] Все автоматические
тесты (unit/integration/E2E) детерминированы:

1. **Время** — порт `ClockPort` (`10-domain-model.md` §2.6) в тестах — `FixedClockAdapter`
   (`infrastructure/testing/fixed-clock.adapter.ts`), возвращающий заданную дату/время
   (`2026-08-27T09:00:00.000Z` — ASSUMPTION стандартная точка отсчёта тестового набора, документируется
   в `tests/fixtures/README.md`). Тесты SLA/таймаутов (`pickup_sla`, `OTP.ttlSeconds`) продвигают
   часы явным вызовом `clock.advance(minutes)`, НЕ реальным `sleep()`.
2. **ID** — порт `IdGenerator` — `SequentialTestIdGenerator` в unit-тестах (предсказуемые
   `00000000-0000-0000-0000-000000000001`, `...002`, ...) для читаемых ассертов; в
   integration/E2E — реальный `Uuidv7IdGenerator` (проверяет реальный путь генерации, не подменяет
   инфраструктуру целиком).
3. **Случайность** (OTP-коды) — `OtpGeneratorPort` в тестах — `FixedOtpGeneratorAdapter`, возвращающий
   заранее известный код (например, всегда `483920` для login, `1234` для handover) — E2E-тест
   вводит именно это значение, не читает случайное.
4. **Внешние провайдеры** — ВСЕГДА Mock-адаптеры в автоматических тестах (`PAYMENT_DRIVER=mock`,
   `OCR_DRIVER=mock`, `SMS_DRIVER=mock`, `STT_DRIVER=mock`, `SEARCH_DRIVER=postgres`,
   `PUSH_DRIVER=mock`) — ни один CI-прогон не делает реальный сетевой вызов к Alif/Gemini/Whisper/SMS-
   агрегатору (Charter «полностью работоспособен без внешних ключей» распространяется и на CI, не
   только на прод-дев-режим).
5. **Сеть между тест-контейнерами** — `docker-compose.test.yml` (§«DevOps») — фиксированные версии
   образов (те же, что prod, `01-TECH-BASELINE.md`), без `:latest`.

**SRS-NFR-044** [R1] Матрица деградации — что ПРОДОЛЖАЕТ работать при недоступности каждого внешнего
провайдера (Charter §7 «падение внешнего провайдера не роняет систему»):

| Провайдер недоступен | Что деградирует | Что ПРОДОЛЖАЕТ работать |
|---|---|---|
| Банк (Alif/DC, R3) | Оплата картой/QR недоступна (CB `open`) | Поиск, каталог, аналоги, `cash_courier`-заказы, кабинет аптеки, курьерский модуль, админка — полностью |
| Gemini (OCR, R2) | Загрузка рецепта не автоматизируется — статус остаётся `uploaded`/ручная очередь | Всё остальное, включая заказ БЕЗ Rx-позиций |
| Whisper (STT, R2) | Голосовой ввод недоступен | Текстовый поиск — основной канал, не деградирует |
| S3/MinIO | Загрузка НОВЫХ фото рецептов невозможна (`503`); УЖЕ загруженные — недоступны для просмотра | Заказы без рецептов, весь остальной функционал; каталог (изображения медикаментов кэшируются CDN-слоем Nginx отдельно от рецептов — публичные ассеты в ДРУГОМ бакете, не одноточечный отказ) |

### Dockerfile-стратегия (multi-stage)

**SRS-NFR-049** [R1] `infra/docker/Dockerfile.api` — multi-stage, ОБЩИЙ для `api`/`worker`/`migrate`
(разные `target`, единый базовый слой зависимостей — не дублирует `pnpm install` в трёх образах):

```dockerfile
# syntax=docker/dockerfile:1
FROM node:22.12-slim AS base
RUN corepack enable && corepack prepare pnpm@11 --activate
WORKDIR /app

FROM base AS deps
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY apps/api/package.json apps/api/
COPY apps/worker/package.json apps/worker/
COPY packages ./packages
RUN pnpm install --frozen-lockfile --filter=api... --filter=worker...

FROM deps AS build
COPY . .
RUN pnpm turbo run build --filter=api --filter=worker

# ---- Стадия для одноразовых миграций/seed (используется init-контейнерами compose) ----
FROM base AS migrator
COPY --from=build /app/apps/api/dist ./apps/api/dist
COPY --from=build /app/apps/api/drizzle ./apps/api/drizzle
COPY --from=deps /app/node_modules ./node_modules
ENTRYPOINT ["node", "apps/api/dist/scripts/migrate-entrypoint.js"]

# ---- Продовый рантайм API — БЕЗ dev-зависимостей, БЕЗ исходников TS ----
FROM node:22.12-slim AS runtime
RUN corepack enable && corepack prepare pnpm@11 --activate
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/apps/api/dist ./dist
COPY --from=build /app/node_modules ./node_modules   # только prod-зависимости (pnpm install --prod в отдельном пере-инсталле, ASSUMPTION оптимизации: pnpm deploy --filter=api --prod ./out)
USER node   # непривилегированный пользователь, не root
EXPOSE 3000
CMD ["node", "dist/main.js"]

FROM runtime AS runtime-worker
CMD ["node", "dist/worker-main.js"]
```

Обоснования: (1) `node:22.12-slim`, не `alpine` — `argon2`/нативные аддоны исторически проблемны на
musl libc, `slim` (debian-based) снижает риск несовместимости нативных биндингов без похода в полный
`node:22.12` образ; (2) отдельный `migrator`-таргет не тащит в продовый рантайм-образ `drizzle-kit`/
CLI-инструменты миграций — уменьшает поверхность атаки продового контейнера; (3) `USER node` —
непривилегированный процесс даже при компрометации приложения не имеет root внутри контейнера.

### nginx.conf

**SRS-NFR-051** [R1] Полная структура (`infra/docker/nginx/nginx.conf` + `conf.d/*.conf`):

```nginx
# --- глобальный контекст http {} ---
limit_req_zone $binary_remote_addr zone=anon_global:10m rate=100r/m;   # SRS-API-012 зеркалируется на границе
limit_req_zone $binary_remote_addr zone=auth_otp:10m rate=10r/m;       # доп. рубеж вокруг /auth/otp/*, defense-in-depth
map $http_upgrade $connection_upgrade { default upgrade; '' close; }   # для WS-проксирования

server {
    listen 443 ssl http2;
    server_name dorutj.com www.dorutj.com;   # neutral — статический список из ENV CORS_STATIC_ORIGINS-подобного набора
    ssl_certificate     /etc/nginx/certs/live/dorutj.com/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/live/dorutj.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    location /api/v1/realtime {
        proxy_pass http://api_upstream;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 90s;     # дольше WS_HEARTBEAT_INTERVAL_MS (25с) с запасом на джиттер
        proxy_set_header Host $host;
    }

    location /api/ {
        limit_req zone=anon_global burst=20 nodelay;
        proxy_pass http://api_upstream;
        proxy_set_header Host $host;              # используется TenantResolutionMiddleware (SRS-API-041)
        proxy_set_header X-Real-IP $remote_addr;   # для rate-limit по IP на стороне Fastify
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/v1/auth/otp/ {
        limit_req zone=auth_otp burst=5 nodelay;
        proxy_pass http://api_upstream;
        proxy_set_header Host $host;
    }

    location / { proxy_pass http://web_upstream; }
}

# --- Динамическая маршрутизация тенантов ---
# White-Label custom_domain НЕ перечисляется статично в nginx.conf (SRS-API-065: список живёт в БД,
# редактируется без деплоя) — вместо этого ОДИН catch-all server-блок с server_name-регэкспом
# `~^(?<tenant_host>.+)$` направляет ЛЮБОЙ Host на тот же upstream `apps/api`; резолвинг тенанта
# происходит ВНУТРИ приложения (TenantResolutionMiddleware), не на уровне Nginx. Nginx отвечает
# только за терминацию TLS и грубый rate-limit/маршрут API vs статика — НЕ за бизнес-логику
# определения тенанта (единственное исключение — сертификат: см. certbot ниже).
server {
    listen 443 ssl http2 default_server;
    server_name _;
    ssl_certificate     /etc/nginx/certs/live/default/fullchain.pem;  # wildcard/SAN или per-domain, выпускается certbot по мере привязки custom_domain
    location /api/ { proxy_pass http://api_upstream; proxy_set_header Host $host; }
    location / { proxy_pass http://web_upstream; }
}

server {
    listen 80;
    server_name _;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }   # certbot HTTP-01 challenge
    location / { return 301 https://$host$request_uri; }
}
```

**SRS-NFR-052** [R1] Обоснование: (1) `limit_req` на Nginx — ПЕРВЫЙ, грубый рубеж (по IP, до входа в
Node) — не заменяет, а дополняет `@fastify/rate-limit` (который считает точнее — по `userId`/`phone`/
`pharmacyId`, недоступным Nginx без парсинга JWT); (2) маршрутизация тенантов НЕ на уровне Nginx —
осознанное решение: держать бизнес-логику (какой тенант, какой бренд) в ОДНОМ месте (`apps/api`), а
не размазывать между Nginx-конфигом и приложением — новый White-Label домен добавляется ЧЕРЕЗ АДМИНКУ
(`SRS-TEN` «за 48 часов»), а не редактированием `nginx.conf`+редеплоем, что противоречило бы Charter
§3.4 «без деплоя»; (3) TLS-сертификат для НОВОГО `custom_domain` — единственное, что реально требует
Nginx-уровня действия (certbot должен узнать о новом домене) — автоматизируется скриптом,
подписывающимся на `TenantDomainAttachedEvent` (уже существующее событие, `SRS-TEN-005`) и вызывающим
`certbot certonly --webroot -d <newdomain>` + `nginx -s reload`.

### Миграции при деплое

**SRS-NFR-055** [R1] [`SRS-DB-032`] Порядок применения при `docker compose up -d`: `migrate`-контейнер
(`depends_on: postgres.condition: service_healthy`) выполняется ДО старта `api`/`worker`
(`depends_on: migrate.condition: service_completed_successfully`) — приложение НИКОГДА не стартует
против БД со старой схемой. В Kubernetes-подобном/managed-деплое (вне scope Docker Compose, но
принцип идентичен) — `migrate` реализуется как `Job`/`initContainer`, блокирующий готовность пода
приложения.

**SRS-NFR-056** [R1] Zero-downtime миграции — политика для ИЗМЕНЯЮЩИХ существующую таблицу миграций
(не `CREATE TABLE` новой сущности): (1) добавление колонки — ВСЕГДА `NULL`-совместимо или с
`DEFAULT` (не блокирующий `ALTER TABLE ... ADD COLUMN ... NOT NULL` без дефолта на большой таблице —
`escrow_ledger`/`audit_log` растут быстро); (2) переименование колонки — ЗАПРЕЩЕНО напрямую (старое
приложение, ещё не передеплоенное при rolling-обновлении, обращается к старому имени) — вместо этого
`expand-contract`: добавить новую колонку → задеплоить код, пишущий в ОБЕ → миграция бэкфилла →
задеплоить код, читающий только новую → следующим релизом удалить старую; (3) `ALTER TYPE ... ADD
VALUE` (новое значение enum) — безопасно добавлять «на лету» (не блокирует), но требует одобрения
архитектора в PR (`SRS-DB-035`, необратимо).

### Стратегия релизов

**SRS-NFR-061** [R1] Ветвление: `main` — защищённая, деплоится в prod ТОЛЬКО по тегу `vX.Y.Z`
(semver); `develop`-подобной долгоживущей ветки НЕТ (Trunk-based, короткоживущие feature-ветки,
Conventional Commits — Charter §5). Тег создаётся вручную после зелёного `main` + ручного QA-сайнофф
(Charter §4 «финальная ручная приёмка архитектором»).

**SRS-NFR-062** [R1] Деплой — rolling (не blue-green в R1 — оправдано только при реальном
multi-region/высоком SLA, ASSUMPTION для масштаба MVP): (1) `docker compose pull` новых образов на
хосте; (2) `migrate`-контейнер применяет миграции (`SRS-NFR-055`); (3) `docker compose up -d
--no-deps api worker` — пересоздаёт ТОЛЬКО стейтлес-сервисы, БД/Redis/MinIO не трогаются; (4) health
check (`SRS-NFR-037`) должен пройти на новом контейнере ДО того, как старый останавливается — при
`replicas: 2` для `api` (`SRS-NFR-047`) обновление — по одному инстансу за раз (несколько секунд
простоя одного из двух, не всего сервиса).

**SRS-NFR-063** [R1] Откат: предыдущий образ (тег предыдущего релиза) остаётся в registry — откат =
`docker compose up -d --no-deps api worker` со старым тегом в `.env`/compose-override. Откат МИГРАЦИИ
БД — ТОЛЬКО если у нового релиза есть `down`-файл (`SRS-DB-034`) — форвард-миграции без обратного
файла делают откат СХЕМЫ невозможным (осознанно, `02` §6 политика: только `ALTER`-миграции обязаны
иметь `down`, чистые `CREATE` — тривиальны и генерируются автоматически) — в общем случае откат
релиза с новыми `CREATE TABLE` безопасен (старый код просто не знает о новых таблицах), откат релиза с
изменением СУЩЕСТВУЮЩЕЙ таблицы без совместимого `down` требует ручного вмешательства DBA (задача
чек-листа готовности к продакшену — ниже).

**SRS-NFR-064** [R1] Feature flags (для фич, готовых кодом, но не готовых бизнес-процессом/данными —
не путать с Provider Pattern ENV-драйверами, которые про инфраструктуру, не про фичи): ENV-булевы
флаги вида `FEATURE_PRESCRIPTION_OCR_ENABLED`, `FEATURE_VOICE_INPUT_ENABLED` (уже упомянуты
`04-SCOPE-DECISION-PIVOT.md` предусловие R2-4: «включается фиче-флагом») — читаются на старте
процесса, НЕ горячая перезагрузка на лету (перезапуск процесса при смене флага — приемлемо, флаги не
меняются часто, в отличие от `tenant_settings`, которые правятся из админки без деплоя).

## Дополнения к схеме БД

> Ниже — ТОЛЬКО добавление, отсутствующее в `11-database-schema.md`, но уже ОБЯЗАТЕЛЬНОЕ по
> `12-api-conventions-auth-tenancy.md` (`SRS-API-009/010`, генерический `Idempotency-Key` для
> человеческих мутирующих запросов). Таблица `payment_operations` (вебхук-специфичная
> идемпотентность) и `inventory_sync_batches`/`batch_id` (1С-специфичная) УЖЕ есть в схеме — это
> ДРУГОЙ, более общий механизм для остальных перечисленных в `SRS-API-009` эндпоинтов
> (checkout, загрузка рецепта, возврат, резолюция спора, фиксация наличных, ротация ключа).

**1. Новая таблица `idempotency_keys`**:

```sql
-- =====================================================================================
-- [ДОПОЛНЕНИЕ SRS-NFR] idempotency_keys — генерическая идемпотентность мутирующих HTTP-запросов
-- =====================================================================================
CREATE TABLE idempotency_keys (
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    endpoint VARCHAR(150) NOT NULL,           -- 'POST /api/v1/orders', канонический метод+путь без ID
    idempotency_key UUID NOT NULL,            -- клиентский UUID v4, заголовок Idempotency-Key
    request_hash CHAR(64) NOT NULL,           -- sha256(rawBody), для обнаружения конфликта (SRS-API-010)
    status idempotency_key_status NOT NULL DEFAULT 'processing',
    response_status SMALLINT,                 -- заполняется по завершении
    response_body JSONB,                      -- заполняется по завершении
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    completed_at TIMESTAMPTZ,
    PRIMARY KEY (user_id, endpoint, idempotency_key)
);
COMMENT ON TABLE idempotency_keys IS
    'SRS-API-009/010: обязательный Idempotency-Key для checkout/загрузки рецепта/возврата/резолюции '
    'спора/фиксации наличных/ротации API-ключа. INSERT со status=processing ДО начала use case '
    '(конфликт PK при конкурентном дубле -> 409 IDEMPOTENCY_KEY_CONFLICT немедленно, SRS-API-010); '
    'UPDATE status=completed + response_* в ТОЙ ЖЕ транзакции, что и бизнес-эффект use case. '
    'Hard-delete по TTL (SRS-DB-004 категория "операционная/очередная", НЕ юридический аудит) — '
    'фоновая job, IDEMPOTENCY_KEY_TTL_HOURS=24 (SRS-API-076).';

CREATE TYPE idempotency_key_status AS ENUM ('processing', 'completed');
```

Обоснование: `SRS-API-010` описывает поведенческий контракт (`{ user_id, endpoint, key, request_hash,
status, response_status, response_body, created_at }`) и `UNIQUE(user_id, endpoint, key)`, но эта
таблица физически отсутствует среди 45 таблиц `11-database-schema.md` — без нее контракт
`Idempotency-Key` для checkout/рецептов/возвратов/споров/наличных/ротации ключей (`SRS-API-009`)
нереализуем. `PRIMARY KEY (user_id, endpoint, idempotency_key)` РЕАЛИЗУЕТ требуемый
`UNIQUE(user_id, endpoint, key)` буквально (составной PK эквивалентен UNIQUE-констрейнту с бонусом
индекса поиска по этим трём полям — самый частый паттерн доступа: «дай мне сохранённый ответ для этого
пользователя+эндпоинта+ключа»).

**2. Дополнение `pnpm audit`-подобной проверки в `02-CLEAN-ARCHITECTURE-AND-CODE.md` §6 конфиг**: не
требует изменений схемы БД — фиксируется здесь ссылкой, что `pnpm verify` (§«Стратегия
тестирования») расширяется шагами `test:contracts`/`test:security`/`env:check` СВЕРХ уже
перечисленных в `02` §6.4 (`typecheck && lint && arch:check && test && build`) — уточнение состава
команды, не новая сущность БД.

## Пограничные случаи и ошибки

**SRS-NFR-066** [R1] **Гонка: два CI-джоба одновременно применяют миграции к одной тестовой БД**
(параллельные PR-прогоны против общего staging, если инфраструктура CI переиспользует один инстанс
Postgres вместо эфемерного). *Решение*: КАЖДЫЙ CI-прогон (`integration-tests`, `e2e`) поднимает
СОБСТВЕННЫЙ эфемерный Postgres-контейнер (`docker-compose.test.yml`/GitHub Actions `services:`),
никогда не переиспользует общий staging для тестов — параллельные PR физически изолированы друг от
друга.

**SRS-NFR-067** [R1] **Idempotency-Key переиспользован между ДВУМЯ разными эндпоинтами одним и тем
же клиентским UUID** (клиентский баг — генератор UUID переиспользует значение). *Решение*:
`PRIMARY KEY (user_id, endpoint, idempotency_key)` включает `endpoint` — коллизия НЕ возникает,
т.к. разные эндпоинты — разные строки таблицы даже при одинаковом `idempotency_key`.

**SRS-NFR-068** [R1] **Circuit breaker флапает** (провайдер то восстанавливается, то падает снова
сразу после `half-open`-пробы — типично при частичной деградации, не полном отказе). *Решение*:
`half-open` пропускает РОВНО ОДИН пробный запрос за `COOLDOWN_MS` — успех переводит в `closed` СРАЗУ
(не требует N подряд успехов для простоты MVP-реализации, ASSUMPTION — усложнение до «N успехов
подряд» и экспоненциально растущего cooldown при повторных флапах — Should, не Must, кандидат на
пост-MVP усиление, если метрика `circuit_breaker_state` покажет реальное флапанье в проде).

**SRS-NFR-069** [R1] **Резервная копия БД восстановлена, но `STORAGE_ENCRYPTION_KEY`/
`BACKUP_ENCRYPTION_KEY` для этого периода утерян** (ротация ключа произошла, старый ключ не
сохранён). *Решение*: политика ротации (`SRS-NFR-024`) ОБЯЗАНА держать старые ключи в
секрет-хранилище НЕОГРАНИЧЕННО долго (не только текущий активный) — ротация добавляет НОВЫЙ ключ,
никогда не удаляет старый немедленно; фоновая job re-encryption (§«Секреты», `SRS-NFR-024`)
переписывает данные под новый ключ ПОСТЕПЕННО, до полного завершения re-encryption оба ключа обязаны
существовать одновременно.

**SRS-NFR-070** [R1] **Nginx `limit_req` отклоняет легитимный всплеск трафика от одного корпоративного
NAT-адреса** (много реальных пользователей за одним IP — типично для офисной сети аптечной сети,
где несколько `pharmacy_admin` работают из одного здания). *Решение*: Nginx-лимит (`SRS-NFR-051`) —
НАМЕРЕННО грубее и выше, чем `RATE_LIMIT_ANON_PER_MIN` (100/мин на IP на Nginx-уровне рассчитан как
защитный потолок от ботов, не как точный бизнес-лимит — точный лимит по `userId` считает
`@fastify/rate-limit` уже ВНУТРИ приложения после аутентификации) — легитимный NAT-трафик
аутентифицированных пользователей лимитируется ПРАВИЛЬНО по `userId` (`RATE_LIMIT_USER_PER_MIN=300`
на каждого), а не по общему IP; Nginx-рубеж существует для АНОНИМНОГО/подозрительного трафика
(до аутентификации), где по определению нет лучшего ключа, чем IP.

**SRS-NFR-071** [R1] **k6-нагрузочный тест проходит локально на машине разработчика, но не проходит в
CI** (разное железо — иной p95). *Решение*: нагрузочные тесты (§«Стратегия тестирования») НЕ
запускаются как блокирующий шаг обычного PR-pipeline (`SRS-NFR-059` — только еженедельный scheduled
job на выделенном раннере со стабильной конфигурацией) — так избегается флапающий CI из-за шумного
соседства ресурсов на shared-раннерах; результат публикуется как артефакт/дашборд, деградация p95
рассматривается ЧЕЛОВЕКОМ (не автоматический red/green PR-gate), кроме прогона НЕПОСРЕДСТВЕННО перед
релизным тегом (`release-tag-only` job), где k6 — обязательный ручной шаг чек-листа готовности
(`SRS-NFR-065`), а не автоматический gate самого workflow.

**SRS-NFR-072** [R1] **On-premise (R3) инсталляция теряет связь с интернетом на срок дольше 24 часов**
(проверка `LICENSE_KEY` — раз в 24ч, `SRS-TEN-033`). *Уточнение*: проверка лицензии — ЛОКАЛЬНАЯ
(публичный ключ зашит в образ, JWT содержит `expiresAt` — НЕ требует сетевого вызова к внешнему
DoruTJ-серверу для валидации, только для ПЕРВОНАЧАЛЬНОЙ выдачи лицензии). Потеря интернет-связи НЕ
влияет на проверку лицензии (она offline по конструкции) — `OFFLINE_MODE=true` уже предполагает
работу без внешней сети как штатный режим on-premise (`SRS-TEN-033` п.3), это не пограничный случай,
а нормальная эксплуатация; единственное, что деградирует при потере интернета в on-premise, —
Telegram-канал уведомлений (публичный Bot API), что уже задокументировано как явное коммерческое
ограничение.
