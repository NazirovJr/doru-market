## Статус

Дизайн **принят и является ОБЯЗАТЕЛЬНОЙ визуальной ссылкой** для реализации `packages/ui` и экранов
`apps/web`/`apps/admin`. Порядок разрешения конфликтов:

- **30-ux (`SRS-UX-*`, `TC-UX-*`) выигрывает** там, где расходится с дизайном — в письменном документе
  зафиксированы требования с ID и тестовые сценарии, дизайн их не переопределяет.
- **Дизайн определяет визуальное исполнение** там, где 30-ux не даёт конкретного значения (точные HEX,
  фактическая раскладка, конкретные тени/радиусы отдельных состояний, конкретные пиксельные размеры
  элементов внутри экрана).

Явные расхождения, найденные при построчном сравнении (30-ux — источник истины, дизайн — как
нарисовано; список исчерпывающий, дальше по документу не повторяется):

| № | Где | 30-ux требует | Дизайн показывает | Разрешение |
|---|---|---|---|---|
| 1 | Порог блокировки OTP при входе (`/login`) | **5** неверных попыток → `423 OTP_LOCKED` (CUJ-2' шаг 2, `SRS-DELIV-023` — тот же порог для курьера) | Блокировка после **3** попыток (`loginLocked: attempts>=3`, `.dc.html:1330`) | **Разрешено [D-26], функциональное — в пользу спеки.** Реализовать **5** попыток, параметром (не константой) — в решении обозначен как `OTP_MAX_ATTEMPTS`, дефолт 5; дизайн приводится в соответствие при вёрстке |

| 7 | Радиусы — единая формула из `--brand-radius` (`SRS-UX-017`: sm=0.5×, md=1×, lg=1.5×, full=999px) | Дизайн использует несогласованный набор пиксельных радиусов (8/10/12/14/16px) не по формуле (см. §«Извлечённые токены») | **Разрешено [D-26], визуальное — в пользу дизайна, кодифицировано токеном.** Конечный набор зафиксирован **8/12/16/999(pill)**, формула токенов пересчитана (`sm`=1×, `md`=1.5×, `lg`=2×) так, чтобы совпадать с этими значениями; 10px и 14px удалены как случайные — шесть радиусов вразнобой означали отсутствие системы, а не гибкость |

## Извлечённые токены

Источник в файле: константы `COLOR_TOKENS`/`LOCKED_TOKENS`/`TYPE_SCALE` и `spacingScale`
(`.dc.html:1090–1105, 1106–1113, 1590`), плюс сама разметка артборда 0 «Дизайн-система»
(`.dc.html:254–498`).

**Важно:** во всём HTML цвета — это **буквальные HEX-литералы** в инлайн-`style`, не CSS-переменные
(это статический демо-канвас, не рабочее приложение). При переносе в `packages/ui` каждое такое
значение обязано стать `var(--brand-*)`/`var(--space-*)`/`var(--radius-*)`, а не быть скопировано как
хардкод — см. §«Реализационные заметки».

### Расширенные (не задокументированные явно в 30-ux) семантические оттенки

Дизайн фактически использует не один HEX на семантику, а связку «фон / рамка / иконка / тёмный
текст» — это разумная практика (нужен более тёмный оттенок для текста ради контраста AA/AAA на
светлом фоне), но 30-ux её не описывает как отдельные токены. Рекомендуется завести производные токены
(`--brand-success-bg`, `--brand-success-border`, `--brand-success-text` и т.д.) вместо повторного
хардкода — для `warning` это уже сделано решением `[D-26]` (см. ниже):

| Семантика | Фон | Рамка | Иконка/акцент | Тёмный текст |
|---|---|---|---|---|
| Success | `#f0fdf4` | `#bbf7d0` | `#16a34a` / `#4ade80` (на тёмном фоне тоста) | `#166534` / `#15803d` |
| Danger | `#fef2f2` | `#fecaca` | `#dc2626` | `#991b1b` / `#7f1d1d` |
| Warning | `#fffbeb` | `#fde68a` | `#b45309` = **`--brand-warning-fg`** [D-26] | `#92400e` = **`--brand-warning-strong`** [D-26] |

### Отступы (8px-сетка)

`spacingScale: [4,8,12,16,20,24,32,40]` (`.dc.html:1590`) — **полностью совпадает** с 30-ux §2.3
(`--space-1`…`--space-8`). Токены `--space-10`(40px) — совпадает; `--space-12`(48px)/`--space-16`(64px)
из 30-ux в демо не показаны (не значит расхождение, просто не понадобились в демонстрационных
карточках).

### Радиусы и тени

- Базовое значение `--brand-radius: 8px` заявлено (`.dc.html:293`), совпадает с 30-ux.
- Формула 30-ux **[обновлено D-26]**: `--radius-sm`=8px (`1×`), `--radius-md`=12px (`1.5×`),
  `--radius-lg`=16px (`2×`), `--radius-full`=999px — было `0.5×/1×/1.5×` (4/8/12px).
- Фактические радиусы в разметке: кнопки/поля — 8px и 10px вперемешку (напр. кнопка «Продолжить»
  курьера 10px `.dc.html:93`, кнопка «Оформить заказ» 8px `.dc.html:839`); карточки — 12px
  (`.dc.html:679, 753, 817`); модальное окно артборда 0 — 14px (`.dc.html:445`); OTP-ячейки/аватары/чипы —
  999px (полностью круглые/пилюли) — это совпадает с `--radius-full`.
  **Разрешено [D-26], расхождение №7 в §«Статус»:** итоговый набор зафиксирован как **8/12/16/999**
  (в пользу дизайна) — формула токенов пересчитана так, чтобы совпасть с этим набором; 10px и 14px
  из демо-канваса в токенизированную систему НЕ переносятся, компонент при реализации округляется до
  ближайшего значения из набора.
- Тени: карточка «Модальное окно» в артборде 0 использует `box-shadow:0 8px 24px rgba(15,23,42,.08)`
  (`.dc.html:445`) — **разрешено [D-26], в пользу дизайна:** `--shadow-modal` теперь тоже alpha
  `0.08` (было `0.16` — визуально тяжело для светлой темы). Тост/уведомление (`.dc.html:773`)
  использует `0 8px 20px rgba(15,23,42,.25)` — третье, ещё более контрастное значение, вне охвата
  D-26 (не токенизировано отдельно, остаётся ориентиром компонента `Toast`, не переопределяет
  `--shadow-modal`). Крупные тени телефона/браузерного окна (`rgba(0,0,0,.25)`/`rgba(0,0,0,.35)`,
  `.dc.html:60,121,198`) — это оформление демо-«рамки устройства» на канвасе, не токен приложения,
  игнорировать при реализации.

## Реализационные заметки

1. **Токены — не хардкод.** Каждый HEX/px в разметке дизайна должен стать CSS-переменной:
   `--brand-primary/-primary-hover/-secondary/-accent/-bg/-surface/-text/-text-muted/-border` (значения
   бренда — из `GET /api/v1/tenant/branding`, не из константы `COLOR_TOKENS` дизайн-файла — та
   константа лишь иллюстрирует ОДИН пример бренда для показа канваса); `--brand-success/-danger/-warning`
   — фиксированные (не редактируются тенантом, `SRS-TEN-014`); отступы — `--space-*`; радиусы —
   `--radius-sm/md/lg/full` по формуле от `--brand-radius`, не произвольные px из дизайна (см.
   расхождение №7). Тени — `--shadow-sm/-modal/-focus-ring`, единые для всех тенантов (не брендируются,
   `SRS-UX-018`).
2. **Строки — только из `packages/i18n`.** Ни один текст, увиденный в дизайне (плейсхолдеры, тексты
   ошибок/пустых состояний, категории, дисклеймер об аналогах, подписи кнопок), не переносится как
   литерал в код компонента. Для типовых ситуаций (пусто/офлайн/ошибка) — обязаны использоваться
   существующие ключи `ux.*` из 30-ux §5, а не новые/дизайновые формулировки — конкретные расхождения
   в формулировках см. таблицу ниже. Для специфичных для экрана текстов (название категории, подписи
   таймлайна заказа, тексты ролей курьера/фармацевта) — заводить новые ключи в том же словаре, не
   хардкодить по-русски «для скорости», даже временно.

   | Ситуация | Текст в дизайне (RU) | Канонический ключ/текст 30-ux §5 | Разница |
   |---|---|---|---|
   | Поиск ничего не нашёл | «По запросу «X» ничего не найдено» / «Проверьте написание или попробуйте название действующего вещества» | `ux.empty.search_no_results`: «Ничего не найдено. Проверьте написание или увеличьте радиус поиска.» | Разная рекомендация («попробовать МНН» vs «увеличить радиус») |
   | Корзина пуста | «Корзина пуста» / «Найдите нужное лекарство по низкой цене» | `ux.empty.cart`: «Корзина пуста. Найдите лекарство дешевле рядом с вами.» | Близко, не дословно |
   | Заказов нет | «Здесь появятся ваши заказы» | `ux.empty.orders`: «У вас пока нет заказов.» | Разная тональность |
   | Офлайн (поиск) | «Нет соединения» / «Проверьте интернет и повторите попытку» | `ux.error.network_offline`: «Нет подключения к интернету. Показаны последние сохранённые данные.» | Разный акцент (retry vs «показан кэш») |
   | Гео отклонена | «Геолокация выключена — аптеки показаны по городу» | `ux.error.geolocation_denied`: «Без доступа к местоположению покажем аптеки по всему городу.» | Близко |
   | OTP заблокирован | «Слишком много попыток» / «Повторите попытку через 5 минут» | `ux.error.otp_locked`: «Слишком много неверных попыток. Запросите новый код через SMS/Telegram.» | Другой сценарий восстановления (см. расхождение №2) |

   Использовать канонический текст 30-ux §5 как есть; дизайн — референс тона/длины, не итоговая копия.
3. **Компоненты, требующие увеличения тап-зоны при переносе:** кнопка «назад» (40×40→48×48+),
   кнопка звонка курьера (44×44→48×48+), чекбокс позиции в сборке (32×32→56×56 — это кабинет аптеки,
   критичное действие, порог 56px), OTP-ячейки логина (44px ширина→48px+), все чипы/пилюли фильтров и
   сортировки (≈32-34px высоты→48px+ реальной области нажатия при сохранении визуальной компактности
   через padding/hit-slop, не через раздувание видимого чипа).
4. **Длинные таджикские/русские строки.** Дизайн демонстрирует переключение языка только для 3 строк
   главного экрана (плейсхолдер поиска, баннер экономии, названия категорий — константа `STRINGS`,
   `.dc.html:1121-1125). Ни один другой экран не показан на `tj`/`en`. Элементы, которые ДОЛЖНЫ пережить
   заметно более длинные таджикские строки (кириллица `tj` заметно многословнее `ru` для многих фраз) и
   не имеют в дизайне заложенного запаса:
   - однострочные заголовки экранов (`Корзина`, `Заказ`, `Карта аптек`) — сейчас `font-weight:700` без
     `text-overflow`/переноса;
   - кнопки с фиксированной шириной по контенту (`Оформить заказ`, «Перейти к оформлению») — должны
     принимать перенос текста без обрезания и без прыжка высоты кнопки (соответствие `SRS-UX-020` —
     переход `loading` не должен «прыгать»);
   - плашка баннера экономии на главном экране (одна строка на 360px ширины экрана — таджикский вариант
     «Корбарон дар як ҳафта 128 400 сомонӣ сарфа карданд» заметно длиннее русского аналога, нужен явный
     перенос на 2 строки, дизайн такого случая не проверял);
   - чипы категорий (`Простуда и грипп` → «Зукому шамолхӯрӣ» короче, но `ЖКТ и пищеварение` → «Меъдаю
     рӯдаҳо» — разная длина требует `white-space:nowrap` + горизонтальный скролл, что дизайн уже
     заложил (`overflow-x:auto`, `.dc.html:551`) — это ЕДИНСТВЕННОЕ место, где перенос длины явно
     предусмотрен);
   - спецбуквы `Ғ ғ Ӣ ӣ Қ қ Ӯ ӯ Ҳ ҳ Ҷ ҷ` — дизайн использует шрифт Inter (Google Fonts) без явной
     проверки покрытия этих глифов; обязательна проверка по `SRS-UX-015`/`SRS-UX-029` до утверждения
     финального шрифта allowlist (Inter обычно покрывает таджикскую кириллицу, но это нужно
     верифицировать, не предполагать).
5. **`LanguageSwitcher` должен быть на каждом экране**, не только на главном (в дизайне он нарисован
   только в шапке Home, `.dc.html:513-517`) — 30-ux `SRS-UX-027` требует доступности переключателя языка
   без авторизации на ВСЕХ экранах/приложениях.
6. **Демо-харнесс (верхняя панель ролей/офлайн/устарело) не переносится как есть** — это инструмент
   показа артбордов Claude Design, а не UI продукта. Реальный гейтинг ролей — через маршруты и RBAC
   (`12-api-conventions-auth-tenancy.md`), не через кнопку-переключатель на общей шапке.
7. **`MapView` в дизайне — заглушка (`iframe` на `map-view.html`)**, реальный `MapLibre GL JS`
   (`packages/ui` `MapView`) при реализации нужно проектировать по требованиям 30-ux/модуля каталога
   (пины/кластеризация/bbox), дизайн даёт только размеры контейнера и точки входа (150-190px превью,
   полноэкранный режим).
8. **Telegram Mini App слой (`--tg-theme-*`, `MainButton`/`BackButton`) в дизайне не показан вообще** —
   реализуется по 30-ux §9 без визуального прецедента в этом канвасе.

## Пробелы дизайна

Экраны и состояния из 30-ux, которых в дизайне НЕТ — реализовывать строго по письменной спецификации,
дизайн для них не даёт визуального ориентира:

### `apps/web` — покупатель
- `/orders` — список ВСЕХ заказов с историей и кнопкой «Повторить заказ» (дизайн показывает только
  ОДИН текущий заказ или пустое состояние, списка прошлых заказов нет).
- `/orders/:id/partial-fulfillment` — отдельный экран подтверждения изменённого состава клиентом
  (таймер до авто-подтверждения, кнопки «Согласен»/«Отменить весь заказ»); в дизайне есть только
  СТОРОНА фармацевта («ждём подтверждения клиента»), самого клиентского экрана нет.
- `/prescriptions/new`, `/prescriptions/:id` — вся ветка загрузки/верификации рецепта (CUJ-5,
  `[R1·флаг]`).
- `/voice-search` — голосовой ввод (CUJ-8, `[R1·флаг]`).
- `/profile` — личный кабинет (телефон, язык, сохранённые адреса, сессии устройств, настройки
  уведомлений).
- `/pharmacy-application` — публичная форма заявки аптеки/сети на онбординг.

### Веб-модуль курьера
- `/courier/shift` — старт/финиш смены, сводка наличных.
- `/courier/offers` — полноэкранная карточка оффера с обратным отсчётом ДО принятия (дизайн начинает
  сразу с уже принятой доставки).
- `/courier/pool` — список пула доступных назначений.
- `/courier/issue/:id` — «Сообщить о проблеме» (причины/фото/заметка).
- `/courier/earnings` — заработок и история выплат.

### Кабинет аптеки / `apps/admin`
- `/admin/order-queue` — сама очередь (секции «Новые»/«В сборке») перед открытием конкретного заказа.
- Практически весь `super_admin`-раздел: тенанты, фиче-флаги, очередь онбординга сетей/аптек
  (`pharmacy-chains`), истекающие лицензии, модерация каталога (`catalog-match-queue`), каталог
  медикаментов, пользователи, кросс-тенантные заказы, весь блок финансов (ledger, расписание выплат,
  расхождения, ставки комиссии, B2B-инвойсы), глобальные настройки платформы, воронка онбординга,
  обращения поддержки, аудит-лог, шаблоны уведомлений.
- Раздел `pharmacy_admin`: свои точки/расписание работы, обзор заказов сети, остатки и цены
  (точечное/массовое редактирование, Excel-импорт с прогресс-баром именно для батчей), история
  синхронизаций 1С, сотрудники, API-ключи 1С, отчёты (продажи/выплаты/здоровье данных остатков),
  форма брендинга (`/admin/branding`).

### Общие сквозные состояния
- Экран/модалка `ErrorState` для непредвиденной ошибки сервера (`ux.error.generic_500`).
- Circuit-breaker сообщение при 3 подряд `502/503`/таймаутах (`SRS-UX-026`).
- `CASH_AMOUNT_MISMATCH` — визуальное состояние несовпадения суммы у курьера.
- `OTP_EXPIRED` отдельно от «неверный код»/«заблокировано» (дизайн смешивает только 2 из 3 состояний
  OTP-ошибок).
- Полноценная демонстрация экрана на `tj`/`en` для чего-либо, кроме 3 строк главного экрана (см.
  §«Реализационные заметки» п.4).
- Слой Telegram Mini App (тема, `MainButton`/`BackButton`) — целиком.
- Компоненты `packages/ui`, не изображённые дизайном ни в каком виде: `RadioGroup` (кроме варианта
  оплаты, где радио-кружок статичен без явных состояний выбора/фокуса), `Switch`, `Textarea`,
  `CursorTable`/`CursorList`, `FileDropzone`, `AudioAlertPlayer`, специфичный для Excel-импорта
  `ProgressBar` (агрегирующий N батчей — показан только обобщённый пример прогресс-бара).
