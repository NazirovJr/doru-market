**SRS-UX-001** [Pivot §2.2, Charter §3.6] **[R1]** Архитектурные основания UX-слоя — дизайн-система
(токены, включая `--brand-*`), состояния компонентов, i18n-инфраструктура, паттерн «тонкий клиент,
ноль бизнес-логики» — закладываются **ЦЕЛИКОМ в R1**, даже для экранов, которые в R1 не入 обязательный
E2E-список (загрузка рецепта, голос) или недоступны реальному пользователю (оплата банком). Ретрофит
дизайн-системы дороже, чем спроектировать её сразу под все три релиза — тот же принцип, что и для
мультитенантности/ledger в бэкенде.

## 1. Дизайн-принципы

> Аудитория (`research/06-ux-jtbd-and-benchmarks.md` §6.1, §7): пожилые пациенты, слабое зрение,
> низкая цифровая грамотность, дешёвые Android-устройства (Android Go, ≤2 ГБ RAM), нестабильный
> 2G/3G/слабый 4G вне Душанбе (§7.2 research), таджикская кириллица без системной раскладки на
> большинстве устройств (§8.2 research).

**SRS-UX-002** [REQ-UX-8, research §7.1] **[R1]** **Крупные тап-зоны.** Минимум **48×48 CSS px** для
ЛЮБОГО интерактивного элемента Customer Web/PWA/TWA (кнопка, пункт списка, чекбокс, иконка-кнопка) —
это ПРАКТИЧЕСКИЙ стандарт (Material 48dp/Apple HIG 44pt), не юридический минимум WCAG 2.5.8 (24px),
который недостаточен для целевой аудитории. Для веб-кабинета аптеки (R1-9, критичные действия сборки
— «Передано курьеру», подтверждение скана) — минимум **56×56px** (та же логика, что и `SRS-PHT-063`
для Flutter-терминала R2, работа в условиях спешки/возможных перчаток за прилавком). Расстояние между
соседними тап-зонами — не менее **8px** (защита от случайного нажатия соседнего элемента).

**SRS-UX-003** [research §6.1, §7.1] **[R1]** **Крупный, высококонтрастный текст.** Базовый размер
текста — **16px минимум** для служебных подписей, **18px** для основного читаемого контента (название
медикамента, цена, статус заказа) — крупнее типичного веб-дефолта 14–16px (research: «пожилые
пользователи лучше воспринимают текстовые подсказки... упрощение критично», «нужны крупный текст,
жирный высококонтрастный текст»). Контраст текста — не ниже **4.5:1** (WCAG AA, Charter §5), для
критичных цифр (цена, экономия, SLA-таймер, OTP-код) — целевой контраст **7:1** (AAA) как внутренняя
планка качества дизайн-системы, не юридическое требование.

**SRS-UX-004** [research §6.1, §7.2] **[R1]** **Простота важнее полноты.** Один основной CTA на
экран (не 3–4 равнозначные кнопки). Второстепенные действия — под меню «Ещё» или ниже линии сгиба.
Ни один пользовательский путь CUJ-1..4' не требует более **4 экранов** от намерения («хочу дешевле»)
до результата («в корзине/заказано») — считается по клику, не включая экраны ввода OTP/адреса при
первом использовании (единоразовая настройка профиля не входит в счётчик «основного пути»).

**SRS-UX-005** [Charter §5 i18n, research §7/§8] **[R1]** **Отсутствие жаргона.** Технические термины
(`МНН`, `эскроу`, `OTP`) не используются в пользовательских текстах напрямую — заменяются понятными
формулировками: `МНН` → «действующее вещество» (RU) / «моддаи фаъол» (TJ); `эскроу` не упоминается
пользователю ВООБЩЕ (внутренний механизм ledger, D-02 — пользователь видит только «Деньги под защитой
до получения заказа»); `OTP` → «код подтверждения» / «рамзи тасдиқ». Список канонических пользовательских
формулировок — словарь `packages/i18n` ключ-группа `ux.plain_language.*`, курируется вместе с текстами
экранов (не изобретается разработчиком на лету).

**SRS-UX-006** [research §7.4, REQ-UX-15] **[R1]** **Ничего не «зависает» без обратной связи.**
Каждое действие пользователя получает видимый отклик **≤150мс**: нажатие кнопки → мгновенное
визуальное состояние `active`/`loading` (§2.5), сеть недоступна → баннер, а не бесконечный спиннер.
Действия, требующие сети (оплата, отправка заказа, скан), явно помечены как недоступные в офлайне —
не позволяют нажать и «ничего не произойдёт».

**SRS-UX-007** [research §7.3, §6.2] **[R1]** **Двойной канал для критичных событий.** Любое событие,
требующее немедленной физической реакции человека (новый заказ на терминале аптеки, несовпадение
партии/срока годности при сканировании) — звук И визуальный сигнал одновременно, ни один канал не
единственный (REQ-UX-9, детали §A.8/§B.4 `24-module-pharmacy-terminal.md`, применимо и к R1-веб-версии
кабинета: вкладка воспроизводит звук через `<audio>`-элемент + мигающий/полноэкранный визуальный
баннер, разблокируется явным жестом «Начать смену», SRS-PHT-050 переносится на веб один в один по
намерению, отличается только техническая реализация аудиоканала — `AudioContext` вместо Android
`AudioAttributes`).

**SRS-UX-008** [research §7.7, D-02] **[R1]** **Невозможность подделать доверие.** Интерфейс НЕ
содержит НИ ОДНОГО поля/экрана, где пользователь может вручную прикрепить скриншот оплаты или ввести
номер транзакции как способ подтверждения платежа (REQ-UX-17) — единственный путь смены статуса на
`paid_escrow` для non-cash — подписанный серверный webhook (R3). Для `cash_courier` (R1) — единственный
путь — ввод наличных курьером на экране `record-cash` (§4, CUJ-2') с автоматическим расчётом сдачи,
не ручной текст.

**SRS-UX-009** [research §7.2, Charter §7] **[R1]** **Работает на медленной сети и слабом устройстве.**
Бюджет первого экрана ≤250KB gzip (Charter §7, §8 этого документа), деградация вместо падения при
потере сети (§5), debounce автокомплита 150–300мс (REQ-UX-12). Ни один сценарий CUJ-1..4' не
блокируется полностью при временной недоступности сети — деградирует до read-only последнего
известного состояния (§5).

**SRS-UX-010** [D-01, `26-module-tenancy-whitelabel.md` §5] **[R1]** **Нейтральность к бренду.**
Ни один экран, компонент или строка кода не содержит хардкода имени бренда/домена/цвета/логотипа —
только `i18n`-ключ `brand.name`, CSS-переменные `--brand-*` (§2.1) и `tenant.settings.brandLogoUrl`
(`GET /api/v1/tenant/branding`, `SRS-API-059`). Нарушение — блокирующее замечание ревью (`SRS-TEN-017`).

**[D-26]** Токены `--brand-warning-fg`/`--brand-warning-strong` вводятся явно, потому что компоненты
`packages/ui` фактически используют производные оттенки `#b45309`/`#92400e` вместо самого
`--brand-warning` (нужен более тёмный тон для контраста текста на светлой подложке) — без отдельного
токена эти оттенки хардкодятся и при White-Label перекраске (`PATCH /tenant-settings`) расходятся с
базовым `--brand-warning`, теряя связь с брендированной семантикой.

**SRS-UX-012** [`SRS-TEN-014`] **[R1]** Семантические токены (`--brand-success/-danger/-warning`) —
**не переопределяются** тенантом мимо фиксированного смысла: зелёный/красный/жёлтый остаются узнаваемы
независимо от палитры сети (White-Label сеть может выбрать свой `--brand-primary`, но не превратить
«ошибку» в зелёный цвет) — allowlist-валидация (`SRS-TEN-014`) применяется на уровне значений HEX, а
семантическая роль токена фиксирована дизайн-системой, не редактируется через `PATCH /tenant-settings`.

**SRS-UX-013** [Приложение TWA, `research 07 §1.3`] **[R2]** Внутри Telegram Mini App поверх
`--brand-*` накладывается второй слой `--tg-theme-*` (`bg_color`, `button_color`, `header_bg_color`,
`accent_text_color`, ...) через `themeParams.bindCssVars()` — порядок каскада: `--brand-*` (базовый
слой тенанта) → `--tg-theme-*` переопределяет ТОЛЬКО те токены, для которых Telegram отдаёт значение
(`--brand-primary` мапится на `--tg-theme-button-color`, `--brand-bg` на `--tg-theme-bg-color` и т.д.,
таблица маппинга — §9.2). Не-TWA режим (обычный PWA/Telegram не запущен) — `--tg-theme-*` не
применяется вовсе, используется чистый `--brand-*`.

| `--font-size-3xl` | 36px | Hero-цифра «Сэкономлено N сомони» на дашборде/после заказа |

**[D-26]** Шкала расширена значениями 22 (`--font-size-h2`) и 28 (`--font-size-h1`) — принятый дизайн
использует H1 28/36/700 и H2 22/30/700, которых не было в исходной шкале; отсутствие этих ступеней —
недосмотр спеки, а не ошибка дизайна, поэтому спека приводится в соответствие с дизайном, а не наоборот.

**SRS-UX-015** [`--brand-font-family`, `SRS-TEN-014`] **[R1]** Шрифтовой стек White-Label ограничен

включать таджикскую кириллицу (глифы `Ғ ғ Ӣ ӣ Қ қ Ӯ ӯ Ҳ ҳ Ҷ ҷ`, §6.3) — проверка покрытия глифов

### 2.4 Радиусы и тени

**SRS-UX-017** [`--brand-radius`, `SRS-TEN-014`] **[R1]** Радиусы — производные от единственного
брендового токена `--brand-radius` (allowlist-формат `^\d{1,2}px$`, `SRS-TEN-014`), НЕ отдельные
per-компонент бренд-токены (упрощает allowlist-валидацию до одного значения):

| Токен | Формула | Значение при дефолте (`--brand-radius: 8px`) | Назначение |
|---|---|---|---|
| `--radius-sm` | `var(--brand-radius)` [D-26] | 8px | Чекбоксы, чипы фильтров, мелкие бейджи |
| `--radius-md` | `calc(var(--brand-radius) * 1.5)` [D-26] | 12px | Кнопки, поля ввода, карточки |
| `--radius-lg` | `calc(var(--brand-radius) * 2)` [D-26] | 16px | Модальные окна, bottom sheet |
| `--radius-full` | `999px` | 999px | Аватары, круглые иконки-кнопки, OTP-ячейки — ВСЕГДА круглые независимо от `--brand-radius` (сеть с `--brand-radius: 0px` — «квадратный» корпоративный стиль — не превращает круглый аватар в квадрат) |

**[D-26]** Конечный набор радиусов зафиксирован как **8 / 12 / 16 / 999 (pill)** — формула изменена
(`sm`=1×, `md`=1.5×, `lg`=2×, было 0.5×/1×/1.5×) так, чтобы токены совпадали с этими значениями при
дефолтном `--brand-radius: 8px`. Значения 10px и 14px, встречавшиеся в компонентах дизайна, из системы
удалены — шесть вразнобой используемых радиусов (8/10/12/14/16/999) означали отсутствие системы, а не
гибкость.

**SRS-UX-018** [ASSUMPTION, не входит в White-Label кастомизацию — фиксировано дизайн-системой] **[R1]**
Тени — семантические, НЕ брендируемые (плоский дизайн предпочтителен для дешёвых GPU/экономии
перерисовки на слабых Android-устройствах, §8):

| Токен | Значение | Применение |
|---|---|---|
| `--shadow-sm` | `0 1px 2px rgba(15,23,42,0.06)` | Приподнятые карточки в списке (минимально, по умолчанию карточки — плоские с `--brand-border`) |
| `--shadow-modal` | `0 8px 24px rgba(15,23,42,0.08)` [D-26, было alpha 0.16] | Модальные окна, bottom sheet, dropdown |
| `--focus-ring` | `0 0 0 3px color-mix(in srgb, var(--brand-primary) 40%, transparent)` | Видимый фокус клавиатуры (§7), офсет 2px от элемента |

**[D-26]** `--shadow-modal` — alpha снижена до `0.08` (было `0.16`): исходное значение визуально
тяжело для светлой темы, `0.08` — то, что фактически показывает принятый дизайн.

**[D-26]** `--focus-ring` подтверждён как производный от `--brand-primary` (не фиксированный
`--brand-accent`, как было в части экранов дизайна) — это единственный визуальный пункт, где
побеждает спека, а не дизайн: фиксированный акцентный цвет кольца фокуса ломает White-Label
(у сети с синим `--brand-primary` кольцо фокуса осталось бы голубым независимо от бренда) и рискует
потерять контраст ≥3:1 с фоном/бордюром конкретной сети — это вопрос доступности (WCAG 2.4.7), а не
вкуса, поэтому переопределять его дизайном нельзя.

**SRS-UX-028** [REQ-UX-19, `users.preferred_locale`/`tenants.default_locale` — уже в схеме,
`11-database-schema.md` строки 583/608, новые поля НЕ требуются] **[R1]** Приоритет резолвинга
языка интерфейса при загрузке:

1. Явный выбор в текущей сессии (`LanguageSwitcher`, немедленно применяется, сохраняется в
   `localStorage` ключ `dorutj.locale` для гостя).
2. Given пользователь авторизован — `users.preferred_locale` (сохраняется на сервере при явном
   переключении авторизованным пользователем — `PATCH /api/v1/profile { preferredLocale }`, персистентно
   между устройствами/сессиями, `REQ-UX-19` «сохраняет выбор между сессиями... профиль»).
3. Given гость без сохранённого выбора — `localStorage.dorutj.locale`, если ранее выбирался.
4. Given ничего не найдено — `tenants.default_locale` резолвленного тенанта (`SRS-DOM-042`, `tj` для
   `neutral`).
5. `Accept-Language` заголовка браузера — НЕ используется как источник (Charter/D-01: дефолт всегда
   `tj`, не auto-detect по системному языку устройства — большинство дешёвых Android в РТ настроены на
   `ru` системно независимо от родного языка пользователя, auto-detect дал бы неверный дефолт чаще, чем
   помогал бы, `research §8`).

**SRS-UX-031** [`SRS-API-008`, D-19] **[R1]** Форматирование чисел/дат/валюты — через `Intl.NumberFormat`/

отдельного `tg-TJ`-стандарта форматирования не существует в большинстве JS-движков; фоллбэк —

| Время | `ЧЧ:ММ`, 24-часовой формат (не 12-часовой AM/PM — не принят в РТ) | `14:32` | `14:32` |

## 7. Доступность WCAG 2.1 AA

**SRS-UX-034** [Charter §5, `02-CLEAN-ARCHITECTURE-AND-CODE.md`] **[R1]** Чек-лист по типу
компонента — обязателен на code review КАЖДОГО PR, затрагивающего `packages/ui` или `features/*/ui`:

| Тип компонента | Проверки |
|---|---|
| **Кнопка/интерактивный элемент** | Тап-зона ≥48×48px (§1 SRS-UX-002); видимый `focus` (§2.5); доступное имя (`aria-label`, если только иконка, не «icon-button-1»); состояние `disabled` имеет `aria-disabled` + не убирается из DOM/tab-order без причины |
| **Форма (Input/Select/Checkbox)** | `<label>` связан через `for`/`aria-labelledby` (не placeholder как единственная подсказка — placeholder исчезает при вводе, что критично при отвлечении); ошибка связана `aria-describedby` + `aria-invalid="true"`; обязательные поля помечены текстом «обязательно», не только звёздочкой (звёздочка нечитаема screen reader без доп. атрибута) |
| **Изображение (фото товара, лого, документ)** | `alt`-текст осмысленный (название препарата, не «image.jpg»); декоративные иконки — `aria-hidden="true"`; изображение рецепта (медданные) — `alt` НЕ описывает содержимое (приватность), только «Фото рецепта» |
| **Цвет/контраст** | Текст ≥4.5:1 (AA), крупный текст (≥24px/≥19px bold) ≥3:1; статус НЕ передаётся только цветом (§2.5 — иконка/текст дублируют бейджи/предупреждения); проверка через `packages/ui` Storybook + автоматический axe-core прогон в CI |
| **Клавиатурная навигация** | Весь функционал доступен без мыши/тача — Tab-порядок логичен (соответствует визуальному порядку), `Escape` закрывает модалки/bottom sheet, `Enter`/`Space` активируют кнопки, ловушка фокуса (`focus trap`) внутри открытого модального окна |
| **Screen reader / ARIA** | Живые регионы (`aria-live="polite"`) для асинхронных обновлений (новый заказ в очереди, SLA-таймер, статус загрузки) — БЕЗ избыточного шума (не каждую секунду тика таймера, только значимые пороги: 5 мин/1 мин/просрочено); `role="alert"` (`aria-live="assertive"`) — только для критичных прерывающих событий (OTP заблокирован, заказ отменён) |
| **Таблицы (admin, отчёты)** | `<th scope="col/row">`, заголовки не теряются при горизонтальном скролле (`overflow-x: auto` на обёртке, не на всей странице) |
| **Карта (`MapView`)** | Список аптек ДУБЛИРУЕТСЯ текстовым списком под/рядом с картой (bottom sheet) — карта НЕ единственный способ увидеть результаты (недоступна для screen reader пользователей содержательно) |
| **Аудио-оповещения (терминал аптеки)** | Звук ВСЕГДА сопровождается визуальным дублем (§1 SRS-UX-007) — глухой/слабослышащий персонал не остаётся без сигнала |
| **Анимация/движение** | Уважает `prefers-reduced-motion: reduce` — декоративные переходы отключаются, функциональные (переход состояния кнопки) сокращаются до мгновенной смены без transition |
| **Увеличение текста браузером** | Layout не ломается при `200%` zoom текста (относительные `rem`-единицы, §2.2 — НЕ `px`, кроме токенов теней/радиусов, которые не текстовые) |

**SRS-UX-035** [Charter §5] **[R1]** Автоматическая проверка — `axe-core` интегрирован в
Playwright E2E-прогон (`tests/e2e`) — КАЖДЫЙ сценарий CUJ-1..8 дополнительно прогоняет
`axe.run()` на финальном состоянии экрана, нарушений уровня `critical`/`serious` — ноль (падение

**SRS-UX-037** [`02-CLEAN-ARCHITECTURE-AND-CODE.md` §5, React Router v7] **[R1]** Стратегия разбиения

### 9.3 Кнопки MainButton/BackButton — правила использования

**SRS-UX-045** [`research 07` §1.1/1.3, ASSUMPTION конкретного маппинга экранов — вывод из общей
практики SDK, не процитирован дословно в research] **[R1]** Таблица обязательных `MainButton` по
экрану (текст — параметризованный i18n-ключ, синхронизирован с состоянием формы):

| Экран | Текст `MainButton` | Активна, когда |
|---|---|---|
| `/medicines/:id` | «В корзину — {{price}} сомони» | Есть хотя бы одно предложение с `stockQuantity > 0` |
| `/cart` | «Оформить заказ» | Корзина не пуста, нет неразрешённых `insufficient_stock`-предупреждений |
| `/checkout` | «Подтвердить заказ» | Адрес выбран, способ оплаты выбран |
| `/prescriptions/new` | «Отправить на проверку» | Файл загружен, согласие дано |
| `/prescriptions/:id` (позиция `needs_clarification`) | «Подтвердить выбор» | Вариант выбран |

**SRS-UX-046** [Charter §5 C18 «функция без сюрпризов»] **[R1]** `MainButton`/`BackButton` — тонкая
презентационная обвязка (`app`-слой, `02` §5): компонент экрана НЕ содержит логики решения «когда
активна кнопка» внутри обработчика SDK-события — та же `model/`-логика чистых функций, что и для
обычной кнопки (§2.5), просто prop `disabled`/`loading` прокидывается в `useMainButton()`-хук вместо
рендера `<Button>`. При выходе из TWA-режима (обычный веб) ТОТ ЖЕ компонент рендерит обычную нижнюю
`Button` — двойной путь рендера по признаку среды, не дублирование бизнес-логики.

### 9.4 Ограничения

**SRS-UX-047** [`research 07` §1.5, §1.6] **[R1]** Явные ограничения, зафиксированные для команды:

1. Нет фонового выполнения — геолокация курьера/офлайн-очередь работают ТОЛЬКО пока Mini App активен
   на переднем плане (в TWA-режиме курьерский флоу — R2, но ограничение относится и к любому
   гипотетическому будущему использованию TWA курьером).
2. Rate limit исходящих сообщений бота — `30 msg/sec` глобально, `1 msg/sec` на `chat_id`
   (`SRS-TEN-028` уже применяет `rateLimiterKey` per-tenant) — не блокирует UX Mini App напрямую,
   влияет на скорость доставки уведомлений о статусе заказа при пиковой нагрузке.
3. `initData` не кэшируется клиентом самостоятельно — считывается заново из
   `window.Telegram.WebApp.initData` при КАЖДОМ запуске/возврате фокуса приложения (`SRS-API-072`) —
   компонент авторизации TWA-режима не хранит `initData` в `localStorage`/Zustand дольше одного акта
   обмена на JWT.
4. Telegram — ОДИН из каналов входа, НЕ единственный (`research §1.6`: неподтверждённый, но
   исторически возможный риск региональной блокировки мессенджеров) — обычный PWA-режим `apps/web`
   (домен вне Telegram) обязан работать полностью независимо, включая OTP-логин, как основной
   постоянно доступный канал.
5. Официальные лимиты Telegram `CloudStorage` не проверены исследованием (`research §1.5` п.5) —
   `CloudStorage` НЕ используется как хранилище состояния в R1 (обычный `localStorage`/сервер —
   единственные источники состояния, никакой зависимости от непроверенного лимита).

### 9.5 Deep-link в TWA из бота

**SRS-UX-048** [REQ-DISPUTE-20, `research/08-gap-2` §3] **[R1]** Уведомление о `delivered` в боте
несёт inline-кнопку «Сообщить о проблеме», ведущую **deep-link в TWA** на экран создания обращения
(`/support/new?orderId=`) — НЕ собирает свободный текст прямо в чате бота (Charter §3.6.1: бизнес-
логика и валидация — только через REST/JSON контракт, не через парсинг текста Telegram-сообщений).
Аналогично «Повторить заказ» (`REQ-UX-18`) из истории заказов в боте — deep-link `t.me/<bot>?start=
reorder_<orderId>` открывает TWA на `/orders/:id` с предзаполненным намерением повтора, сам заказ
создаётся ТОЛЬКО через обычный `/checkout`-флоу внутри TWA, не из параметра `/start` напрямую.

## Пограничные случаи и ошибки

**SRS-UX-050** [Гонка: двойной клик на CTA] **[R1]** Given пользователь нажимает `Button`/`MainButton`
дважды подряд (двойной тап, частый на touch-экранах при неуверенности «сработало ли»), When второй
клик приходит ДО завершения первого запроса, Then кнопка переходит в `loading`/`disabled` СИНХРОННО
с первым кликом (не дожидаясь ответа сервера) — второй клик физически не порождает второй HTTP-запрос
на уровне UI (defense in depth поверх серверной идемпотентности `SRS-API-010` — UI не полагается
ТОЛЬКО на `Idempotency-Key`, чтобы не тратить лишний round-trip на заведомо дублирующийся запрос).

**SRS-UX-051** [Гонка: WS-событие приходит раньше REST-ответа на то же действие] **[R1]** Given
пользователь нажимает «Оформить заказ», REST-запрос ещё не вернул ответ, When WS-событие
`order.paid` для ЭТОГО ЖЕ заказа приходит раньше (теоретически возможно при быстрой обработке
сервером и медленном возврате HTTP-ответа клиенту), Then UI игнорирует WS-событие для заказа,
которого ЕЩЁ НЕТ в локальном состоянии (`orderId` неизвестен клиенту до получения REST-ответа) — не
пытается отрендерить карточку заказа по WS raньше, чем получит полный DTO из REST-ответа (WS —
дельта поверх известного состояния, не первичный источник создания сущности на клиенте, `SRS-API-053`).

**SRS-UX-052** [Кнопка «Назад» браузера/TWA во время checkout] **[R1]** Given пользователь на `/checkout`
нажимает системную «Назад» (браузер) ПОСЛЕ отправки `POST /orders`, но ДО получения ответа, When
навигация уводит с экрана, Then запрос ПРОДОЛЖАЕТ выполняться на сервере (не отменяется — заказ не
должен зависеть от того, остался ли пользователь на странице), а результат синхронизируется при
следующем открытии `/orders` (REST — источник истины, не важно, увидел ли пользователь экран успеха
непосредственно) — UI НЕ показывает «заказ не оформлен» только на основании ухода со страницы.

**SRS-UX-053** [Таймер SLA/OTP рассинхронизирован с часами устройства] **[R1]** [`SRS-PHT-030`]
Given часы клиентского устройства расходятся с сервером (частый случай на дешёвых Android без
автосинхронизации времени), When `CountdownTimer` отображает `slaDeadlineAt`/`otpExpiresAt`, Then
таймер вычисляется от РАЗНИЦЫ, полученной при последнем ответе сервера (`serverTime - clientTime`
дельта, зафиксированная в момент получения ответа, не абсолютное сравнение `Date.now()` клиента с
абсолютным `deadlineAt`) — обновляется при каждом свежем REST/WS-ответе, не накапливает дрейф между
синхронизациями дольше нескольких минут.

**SRS-UX-054** [Переключение локали посреди незавершённой формы] **[R1]** Given пользователь
заполняет многошаговую форму (`/checkout`, `/pharmacy-application`) И переключает язык интерфейса,
Then введённые пользователем данные (адрес, телефон, файлы) СОХРАНЯЮТСЯ — переключение локали меняет
ТОЛЬКО текст меток/подсказок/валидационных сообщений (i18n-словарь), не сбрасывает состояние формы
(`model/`-состояние формы и `i18n`-словарь — независимые слои, `02` §5).

**SRS-UX-055** [Отказ микрофона/камеры на входе в TWA] **[R1]** Given браузерный/TWA-контекст
запрещает доступ к микрофону (`/voice-search`) или камере (загрузка фото рецепта через
`<input type="file" capture>`) на уровне ОС/разрешений устройства, When пользователь открывает
экран, Then UI показывает `ux.error.mic_permission_denied`/аналог для камеры С инструкцией «Как
разрешить» (deep-link в настройки приложения там, где платформа это поддерживает) — НЕ бесконечный
запрос разрешения по кругу; альтернативный путь (текстовый поиск / загрузка из галереи вместо камеры)
остаётся доступным.

**SRS-UX-056** [Список результатов поиска устарел, пока пользователь листал] **[R1]** Given
пользователь открыл `/search`, кэш результатов (§11 модуля 20, TTL 30с) истёк, пока он прокручивал
список (долгое чтение карточек), When он нажимает «Показать ещё» (курсорная пагинация), Then клиент
запрашивает СЛЕДУЮЩУЮ страницу с ТЕМ ЖЕ `cursor`, полученным на предыдущем ответе (не пересчитывает
первую страницу заново) — возможное расхождение цены между уже отрендеренными карточками первой
страницы и вновь загруженными второй — ожидаемое поведение (`SRS-CAT-072`), не ошибка пагинации.
