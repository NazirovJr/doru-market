# DoruTJ — Чистая архитектура и Clean Code (обязательный стандарт)

> Владелец: Architect. Статус: **BASELINE v1.0, ОБЯЗАТЕЛЕН**.
> Нарушение любого правила из §1–§4 = блокирующее замечание code review.
> Правила проверяются автоматически (§6). «Я забыл» не является аргументом — CI не пропустит.

---

## 1. Слои и Правило Зависимостей (Dependency Rule)

Каждый модуль backend (`apps/api/src/modules/<context>`) имеет ровно четыре слоя:

```
modules/<context>/
├── domain/           ← ЯДРО. Сущности, value objects, доменные сервисы, доменные ошибки,
│                       инварианты, state machine. НОЛЬ импортов фреймворка.
├── application/      ← Use cases (по одному классу на сценарий), порты (интерфейсы),
│                       оркестрация транзакций. Зависит ТОЛЬКО от domain.
├── infrastructure/   ← Адаптеры: Drizzle-репозитории, HTTP-клиенты, BullMQ-продюсеры,
│                       провайдеры (Alif/Gemini/S3). Реализуют порты из application.
└── presentation/     ← Controllers, WS-gateways, guards, pipes, mappers DTO↔domain.
                        Зависит ТОЛЬКО от application.
```

**Стрелки зависимостей направлены строго внутрь:**

```
presentation ──▶ application ──▶ domain ◀── infrastructure
                                    ▲
                      (infrastructure реализует порты application,
                       но application НИКОГДА не импортирует infrastructure)
```

### 1.1 Что запрещено категорически

| Запрет | Почему |
|---|---|
| `domain/**` импортирует `@nestjs/*`, `drizzle-orm`, `zod`, `pg`, `ioredis`, `bullmq`, `fastify` | Ядро обязано быть тестируемым без инфраструктуры и переносимым |
| `application/**` импортирует что-либо из `infrastructure/**` | Разворот зависимостей ломается, юзкейсы становятся непроверяемыми |
| `presentation/**` импортирует `domain/**` напрямую в обход `application/**` | Контроллер начинает знать доменные инварианты |
| Любой модуль импортирует `../<другой-модуль>/domain|application|infrastructure` | Нарушение границ контекста |
| Drizzle-схема (`db/schema`) импортируется в `domain/**` или `application/**` | Утечка модели БД в бизнес-логику |
| Сущность БД возвращается наружу из контроллера | Утечка внутренней модели в публичный контракт |

### 1.2 Межмодульное взаимодействие

Единственный разрешённый способ — через **публичный фасад** модуля:

```
modules/<context>/index.ts   ← экспортирует ТОЛЬКО: публичный сервисный интерфейс,
                               публичные типы, доменные события. Больше ничего.
```

Всё остальное внутри модуля — приватно. Импорт `modules/orders/domain/order.entity` из
`modules/payments` = блокирующее нарушение. Правильно: `import { OrdersFacade } from '@/modules/orders'`.

Для слабой связности предпочитать **доменные события** (`OrderPaidEvent`) вместо прямых вызовов
там, где это не синхронная транзакция.

### 1.3 Порты и адаптеры (Provider Pattern из устава — частный случай)

- Порт объявляется в `application/ports/*.port.ts` как `interface` + DI-токен (`Symbol`).
- Реализация — в `infrastructure/adapters/*.adapter.ts`.
- Связывание — только в `<context>.module.ts` через `{ provide: TOKEN, useClass: ... }`.
- Use case получает порт через конструктор. **Никаких `new` инфраструктурных классов внутри use case.**

## 2. Правила слоя Domain

1. Сущность защищает свои инварианты сама. Публичных сеттеров нет — есть методы-намерения:
   `order.markPaid(txId)`, а не `order.status = 'paid_escrow'`.
2. Невалидное состояние невозможно сконструировать: приватный конструктор + фабрика
   `Order.create(...)` / `Order.restore(...)`, возвращающая ошибку при нарушении инварианта.
3. **Value Objects обязательны** для: `Money` (целые дирамы + валюта), `PhoneNumber` (формат РТ),
   `GeoPoint`, `Barcode` (EAN-13 с контрольной цифрой), `Dosage`, `OtpCode`, `TenantId`.
   Примитивы (`string`, `number`) в сигнатурах домена — запах (primitive obsession).
4. Переходы статусов заказа — **явная state machine** в домене: таблица разрешённых переходов,
   попытка недопустимого перехода бросает доменную ошибку. Никаких `if (status === ...)` россыпью.
5. Доменные ошибки — свои классы (`InsufficientStockError`), не `HttpException`.
   Маппинг доменная ошибка → HTTP-код происходит в `presentation`.
6. Домен **чист**: без `Date.now()`, `Math.random()`, `process.env`, обращений к сети/диску.
   Время и идентификаторы приходят через порты `Clock` и `IdGenerator` — иначе тесты недетерминированы.

## 3. Правила слоя Application

1. **Один use case = один класс = один публичный метод `execute()`.** Имя — глагол в императиве:
   `PlaceOrderUseCase`, `CaptureEscrowUseCase`, `SyncInventoryBatchUseCase`.
2. Use case не знает про HTTP: ни `Request`, ни `Response`, ни заголовков, ни статус-кодов.
   На вход — простой Command/Query-объект, на выход — простой результат.
3. Границы транзакции задаются в use case (`unitOfWork.run(...)`), а не в репозитории.
4. Авторизация «может ли этот пользователь это сделать» — политика в application
   (`OrderPolicy.canCancel(user, order)`). В guard'ах — только аутентификация и грубая проверка роли.
5. Никаких «god service» на 800 строк. `OrdersService`, делающий всё, — запрещён.

## 4. Clean Code — измеримые правила

Правила подобраны так, чтобы их можно было проверить линтером или глазами за 5 секунд.

| # | Правило | Порог / проверка |
|---|---|---|
| C1 | Длина функции | ≤ 40 строк (`max-lines-per-function`) |
| C2 | Длина файла | ≤ 300 строк (`max-lines`), кроме сгенерированных и словарей i18n |
| C3 | Цикломатическая сложность | ≤ 10 (`complexity`) |
| C4 | Глубина вложенности | ≤ 3 (`max-depth`); глубже — guard clause или выделение функции |
| C5 | Количество параметров | ≤ 3 (`max-params`); больше — объект-параметр с именованными полями |
| C6 | Магические числа и строки | Запрещены (`no-magic-numbers`); только именованные константы/enum |
| C7 | `any`, `as any`, `@ts-ignore` | Запрещены (`@typescript-eslint/no-explicit-any`); `@ts-expect-error` — только с описанием |
| C8 | Мёртвый и закомментированный код | Запрещён. Удаляем — история в git |
| C9 | `console.*` в продуктовом коде | Запрещён (`no-console`) — только pino-логгер |
| C10 | Именование | `PascalCase` — классы/типы; `camelCase` — функции/переменные; `SCREAMING_SNAKE` — константы; булевы — `is/has/can/should`; функции — глагол |
| C11 | Комментарии | Объясняют **«почему»**, а не «что». Комментарий, пересказывающий код, удаляется. Нетривиальное решение без «почему» = замечание |
| C12 | Обработка ошибок | Запрещены пустой `catch {}` и `catch (e) { throw e }`. Ошибка либо обрабатывается, либо обогащается контекстом, либо не перехватывается |
| C13 | Мутации | Входные параметры не мутируются. Массивы/объекты — `readonly` в сигнатурах, копирование при изменении |
| C14 | Асинхронность | Никаких плавающих промисов (`no-floating-promises`), никакого `await` в цикле там, где нужен `Promise.all` |
| C15 | DRY vs преждевременная абстракция | Дублирование устраняется на **третьем** повторе. Абстракция «на будущее» без второго потребителя — замечание |
| C16 | Импорты | Только алиасы (`@/modules/...`), запрещены `../../../`. Циклические импорты запрещены |
| C17 | Один экспорт на файл | Один класс/компонент верхнего уровня на файл; имя файла = имя сущности в `kebab-case` |
| C18 | Функции без сюрпризов | Функция делает то, что обещает имя. Скрытые побочные эффекты (запись в БД внутри `getX`) = дефект |

## 5. Frontend — чистая архитектура клиента

Структура каждого React-приложения (feature-oriented, зависимости строго вниз):

```
src/
├── app/          ← точка входа, провайдеры, роутер, глобальные стили
├── pages/        ← экраны: композиция features, ноль бизнес-логики
├── features/     ← законченные сценарии (search, cart, checkout, prescription-upload)
│   └── <feature>/
│       ├── api/        ← вызовы через shared/api + TanStack Query хуки
│       ├── model/      ← состояние, селекторы, ЧИСТЫЕ функции бизнес-правил экрана
│       └── ui/         ← компоненты, только рендер
├── entities/     ← переиспользуемые доменные представления (MedicineCard, PharmacyPin, OrderStatusBadge)
└── shared/       ← api-клиент, ui-kit, hooks, lib, конфиг, i18n
```

**Правило зависимостей фронта:** `app → pages → features → entities → shared`. Обратные и
горизонтальные импорты (`feature-a` → `feature-b`) запрещены; общее выносится в `entities`/`shared`.

Дополнительно:
- **Компонент не содержит бизнес-логики.** Вычисления, форматирование, ветвления правил — в
  `model/` (чистые функции, покрытые unit-тестами) или в кастомных хуках.
- `fetch`/`axios` внутри компонента запрещён — только через слой `api` + TanStack Query.
- Компонент ≤ 150 строк. Больше — декомпозиция.
- Ноль хардкодных строк — всё через `useT()` из `packages/i18n`.
- Ноль хардкодных цветов — только токены дизайн-системы (CSS-переменные), иначе White-Label
  перекраска ломается.
- Состояние сервера — TanStack Query. Состояние UI — `useState`/Zustand. Не смешивать.

## 6. Автоматическое принуждение (без него правила — пустой звук)

В корне монорепозитория настраивается и включается в CI:

1. **`dependency-cruiser`** — граф зависимостей с запрещающими правилами из §1.1, §1.2 и §5.
   Конфиг `.dependency-cruiser.cjs`, команда `pnpm arch:check`. Падение = красный CI.
2. **ESLint** — правила C1–C18 включены как `error` (не `warn`), плюс:
   `import/no-cycle`, `import/no-relative-parent-imports`, `@typescript-eslint/no-floating-promises`,
   `@typescript-eslint/explicit-module-boundary-types`.
3. **`tsc --noEmit`** со `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`,
   `noUnusedLocals`, `noUnusedParameters`.
4. **Порог покрытия тестами**: `domain/` и `application/` — ≥ 90 %, остальное — ≥ 70 %.
   Ниже порога — падение CI.
5. **Husky + lint-staged** на pre-commit: `eslint --fix`, `prettier --write`, `tsc --noEmit`.
6. Единая команда приёмки: **`pnpm verify`** = `typecheck && lint && arch:check && test && build`.

> **Правило для агентов-разработчиков:** тикет считается сданным только после локально зелёного
> `pnpm verify`. Сдача с красным `verify` = автоматический возврат в разработку.

### 6.1 Статус принуждения: ПРОВЕРЕНО НА ЖИВЫХ НАРУШЕНИЯХ

Конфигурация не просто написана — архитектор внёс намеренные нарушения и убедился, что каждое
из них блокируется. Результат проверки (27.08.2026):

| Нарушение | Кто поймал | Сообщение |
|---|---|---|
| `domain/` импортирует `drizzle-orm` | ESLint `no-restricted-imports` | «Слой domain обязан быть чистым…» |
| `Date.now()` в `domain/` | ESLint `no-restricted-globals` + `no-restricted-properties` | «В domain время берётся через порт Clock (§2.6)» |
| Магическое число `7919` | ESLint `@typescript-eslint/no-magic-numbers` | «No magic number: 7919» |
| `application/` импортирует `infrastructure/` | ESLint `no-restricted-imports` | «application зависит только от domain и собственных портов…» |
| Глубокий импорт `orders/domain` → `payments/domain` в обход фасада | dependency-cruiser `no-cross-module-deep-import` | «Межмодульное взаимодействие — ТОЛЬКО через публичный фасад…» |
| `application/` → `infrastructure/` (граф) | dependency-cruiser `application-does-not-know-infrastructure` | — |

Дополнительный эффект `projectService: true`: **файл, не включённый ни в один `tsconfig.json`,
падает с ошибкой парсинга**. Это бесплатный guard от «кода-сироты» вне сборки.

> **Обязательный тикет:** создать `tests/arch/` — набор фикстур-нарушителей и тест, который
> проверяет, что `arch:check` и `lint` их отвергают. Guard, который перестал ловить, молчит об этом:
> ловушку нужно проверять ловушкой.

## 7. Как это проверяет ревью

Ревьюер обязан по каждому изменению явно ответить:

1. Не нарушено ли Правило Зависимостей (§1)? Показать импорт-нарушитель или подтвердить чистоту.
2. Есть ли бизнес-логика вне `domain`/`application` (в контроллере, репозитории, компоненте)?
3. Инварианты защищены сущностью или растеклись по сервисам?
4. Есть ли примитивы там, где обязан быть Value Object (§2.3)?
5. Нарушены ли пороги C1–C5, есть ли `any`, магические числа, мёртвый код?
6. Тестируется ли логика без БД и сети (значит, зависимости развёрнуты правильно)?
7. Не появилась ли абстракция без второго потребителя (§C15)?

Замечание по §1 или §2 = **блокирующее**, тикет возвращается разработчику независимо от того,
работает ли функциональность.
