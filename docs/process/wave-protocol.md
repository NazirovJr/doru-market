# Протокол волны

Как координатор запускает, принимает и сливает волну тикетов. Роли — [coordinator.md](coordinator.md), правила исполнителя —
[`AGENTS.md`](../../AGENTS.md), шаблон брифа — [executor-brief-template.md](executor-brief-template.md), окружение интеграционных
тестов — [integration-tests.md](../guides/integration-tests.md). Скрипты — [`scripts/coordinator/`](../../scripts/coordinator/).

Волны запускаются только по слову владельца. Слить в `development` — по слову владельца; `git push` — только по слову владельца.
Текущее состояние — [`docs/status/state.md`](../status/state.md); координатор обновляет его после каждого слияния.

## 1. Подбор тикетов

1. Взять из [`tickets/`](../../tickets/README.md) тикеты, у которых закрыты `depends_on` и **непересекающиеся `files_owned`**
   внутри волны. Пересечение = дефект планирования: развести зависимостью или объединить тикеты (решение D-27).
2. Общие файлы-агрегаторы (barrel: `index.ts`, `*.module.ts`, `package.json`, `ci.yml`, `docker-compose*.yml`) правятся только
   добавлением строк, но при слиянии именно они дают конфликты — см. §6.
3. Параллельно — не больше 6 исполнителей (память машины). Все исполнители — субагенты на модели `sonnet`, указанной явно
   ([coordinator.md §2](coordinator.md)).
4. Тикет с миграцией получает от координатора **номер миграции и `when`** в `_journal.json`; без назначенного номера
   исполнитель останавливается и возвращает блокер.

## 2. База и изоляция

- **Базовый SHA** = текущий `development`; координатор называет его в брифе (`git checkout -b <ветка> <SHA>`, проверка
  `git log --oneline -1`). Дифф считается от него: `git diff <SHA>...HEAD`.
- Один агент — своя ветка `feat/dtj-NNN-<slug>` и свой worktree. Ветки агентов в `development` не мёржатся ими самими.
- Docker-контейнеры (`docker compose up/create`) из worktree агентов не создаются: контейнер запоминает bind-mount путей
  worktree и перестаёт стартовать, когда worktree удалён. Контейнеры Postgres и Redis поднимает координатор из основной копии.
- Перед git-командами в служебных worktree — `git rev-parse --show-toplevel`: у worktree без `.git` команды уходят в основную копию.

## 3. Ресурсы на агента

Координатор назначает каждому агенту в брифе, чтобы параллельные прогоны не мешали друг другу:

| Ресурс | Правило |
|---|---|
| Порт своего API для живой проверки | свободный порт из диапазона 31NN (по номеру тикета), не порты dev и стенда |
| Порт vite | свой, вне портов dev (5173–5175) и стенда (5373–5375) |
| Redis | тестовый Redis на **6380**, у каждого агента **свой номер БД** (`/0`, `/1`, …); порт 6379 занимает Redis другого проекта — туда никогда |
| Тестовая БД | общая `dorutj_test`; тикет с миграцией — своя `dorutj_test_<тикет>` (см. [integration-tests.md](../guides/integration-tests.md)) |
| Номер миграции | назначает координатор (§1.4) |

Dev-окружение владельца (БД `dorutj`, порты dev) и E2E-стенд (БД `dorutj_e2e`) агенты не останавливают и не занимают.

## 4. Замок на тяжёлые команды

Полный typecheck/vitest, `depcruise`, `test:arch`, миграции, интеграционные и e2e спеки, полная проверка идут через замок —
[`scripts/coordinator/heavy-run.ps1`](../../scripts/coordinator/heavy-run.ps1):

```powershell
pwsh -NoProfile -File scripts/coordinator/heavy-run.ps1 -Cmd "<команда>"
```

Код выхода 99 — замок занят, повторить. Каталог замка (`heavy.lock`) лежит вне репозитория (`DORUTJ_LOCK_ROOT`), общий для
всех worktree; удалять его вручную нельзя (скрипт сам снимает замок мёртвого владельца). Дольше 10 минут — запуск в фоне.
Без замка допустимы только: tsc фронтовых пакетов и contracts, `eslint` по своим файлам, точечные unit-спеки, vitest фронтов.

Полная проверка вместо `pnpm verify` (turbo в strict env-mode срезает `REDIS_URL`), одна команда через замок:

```powershell
$env:NODE_OPTIONS='--max-old-space-size=8192'; $env:REDIS_URL='<redis-url на 6380>'
pnpm typecheck; pnpm lint; pnpm arch:check; pnpm test:arch
pnpm exec turbo run test --env-mode=loose --concurrency=1
pnpm build
```

(после каждой команды — проверка `$LASTEXITCODE`). Кучу `NODE_OPTIONS` требует ESLint на всём репозитории. В отчётах это
называется «verify (test с --env-mode=loose)». `@dorutj/security` при грязной общей БД даёт известный красный
(`otp-bruteforce`): его исключают `--filter=!@dorutj/security` с пометкой в отчёте; если тикет трогает auth — прогон
отдельно на свежей БД.

## 5. Приёмка

Приёмка — **повторный прогон гейтов координатором**, а не чтение отчёта ([coordinator.md §3](coordinator.md)):

1. Ветка агента: полная проверка (§4) на её коммите; подавления линтера, `any`, `ts-ignore`, TODO без тикета, число
   строк комментариев (лимит задаёт бриф).
2. Выборочно 10–15 критериев приёмки — по файлу и функции; подключение к рантайму: модуль в `AppModule`, маршрут отвечает.
3. Для API-тикетов — живой старт собранного артефакта: [`smoke-api.ps1`](../../scripts/coordinator/smoke-api.ps1)
   (зелёные гейты не доказывают, что `dist/main.js` стартует).
4. Вердикт: принято / принято частично (долг фиксируется) / возврат. Возврат — тому же агенту через SendMessage.

## 6. Проверочная ветка волны

Принятые ветки собираются в **проверочную ветку** от базового SHA (`wave<N>-verify`) в отдельном worktree координатора.
Сначала сливается всё, потом идёт полная проверка — не по одной ветке в `development`.

- Конфликты «обе стороны добавили» в barrel-файлах — [`union-merge.py`](../../scripts/coordinator/union-merge.py); результат
  всегда проверять `typecheck`. Для интерфейсов, портов и моков в спеках скрипт не годится — только ручная конкатенация
  (скрипт, удаляющий «дубли» строк, однажды съел закрывающие скобки).
- Типовые точки конфликта: `*.module.ts`, `contracts/*/index.ts`, словари i18n, `role-routes.ts` админки, точки входа
  фронтов (`main.tsx`), фейки фасадов в спеках соседних тикетов, `docker-compose*.yml`, `ci.yml`.
- После слияния — полная проверка и **интеграционный прогон с эталоном** (§7).

## 7. Интеграционный набор и сравнение по именам тестов

Интеграционный набор `apps/api` частично красный до волны (известные классы окружения — см.
[integration-tests.md](../guides/integration-tests.md)), поэтому смотрят не на число падений, а на **новые падения**:

1. [`itest.ps1 -Tag <тег>`](../../scripts/coordinator/itest.ps1) через замок: пересоздаёт `dorutj_test`, мигрирует ролью
   мигратора, гоняет весь набор и пишет `itest-<тег>.json`.
2. `node scripts/coordinator/cmp.js <тег> <эталон> [<эталон>…]` печатает падения, которых нет ни в одном эталоне.
   Эталон — прогон предыдущей базы. Регрессия = падение по имени теста, которого нет в эталонах.
3. Каждое новое падение разбирают: регресс тикета (возврат), известный класс окружения (в отчёт) или побочный эффект
   слияния (правка проверочной ветки).

## 8. Слияние в development

По слову владельца, порядок:

1. `git pull origin development` в основной копии; слияние проверочной ветки в `development`.
2. Миграции на dev-БД `dorutj` и БД стенда `dorutj_e2e` — по порядку номеров, ролью мигратора.
3. `pnpm install`, `pnpm build`, перезапуск dev-окружения и E2E-стенда
   ([`e2e-stack.ps1`](../../scripts/coordinator/e2e-stack.ps1)).
4. Обновить [`docs/status/state.md`](../status/state.md). Worktree и ветки агентов удаляются только после слияния.
5. `git push` — только по прямому слову владельца.

## 9. Возобновление после остановки

Остановка (лимит модели, перезагрузка, слово владельца) не теряет работу: незакоммиченное лежит в worktree агента.
Возобновление: `git status` в worktree агента, затем SendMessage агенту «продолжай с места остановки, git status first».
После перезагрузки — проверить, что контейнеры Postgres и Redis подняты из основной копии, а не из удалённого worktree;
dev и стенд поднять заново. Состояние волны (кто принят, что в проверочной ветке) координатор держит в
[`docs/status/state.md`](../status/state.md) и в своих локальных заметках вне репозитория.
