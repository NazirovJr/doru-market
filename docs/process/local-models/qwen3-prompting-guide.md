# Инструкция по промптингу qwen3 (и других внешних моделей) для тикетов DoruTJ

> Живой документ. Обновлять после каждого раунда с новыми находками — не переписывать с нуля.
> Источники находок: (1) провал партии из 13 тикетов, отданных одним махом без ветки/изоляции
> и без реальной проверки (2026-09-19); (2) детальный ревью DTJ-306 после этого провала —
> тикет прошёл первичную проверку лучше, но всё равно содержал реальные баги при заметно более
> точном промпте.

## Главный вывод

Качество вывода модели напрямую зависит от того, **сколько конкретных фактов о реальном
состоянии кода ей дано заранее**, а не от того, насколько подробно описан сам тикет. Модель
охотно генерирует правдоподобный, но несуществующий код (импорты, методы, пакеты), если не
имеет прямого способа проверить, что что-то уже существует. Чем более open-ended инструкция
(«скопируй стиль», «посмотри похожий файл») — тем выше риск, что модель проигнорирует её и
подставит типовой шаблон из общего обучения вместо реального кода этого репозитория.

## Часть 1 — что пошло не так в партии из 13 тикетов (полный провал)

Раздали 13 тикетов без веток/worktree, без указания проверить существующий стек, с общей
инструкцией «следуй пунктам ticket.md». Результат: **517 реальных ошибок компиляции**
(api 462 + admin 29 + worker 26), **82 нарушения архитектуры**, ~1400 ошибок lint (часть —
каскад от нерезолвящихся импортов). Ни один из 13 тикетов не был готов к мержу.

### Паттерн 1 — модель подставляет «типичный» стек вместо реального
- `apps/admin` использовал `@mui/material`, `date-fns` — в проекте их нет (только `packages/ui`
  + CSS-переменные).
- Импорты `@/shared/ui/button`, `@/shared/lib/utils`, `@/i18n` — алиасы из чужого
  (shadcn/Next.js-подобного) шаблона, в этом репозитории таких путей никогда не было.
- `apps/worker`-тесты писались на **Jest** (`jest.fn()`, `jest.Mocked`) — весь проект на
  **Vitest**.
- `apps/worker` импортировал `@/modules/payments/application/ports/...` — пути из **другого**
  TS-проекта (`apps/api`). `apps/worker` и `apps/api` — раздельные процессы с раздельными
  деревьями исходников, так импортировать нельзя.
- Контроллер импортировал `express`/`@nestjs/swagger` — проект на **Fastify**, Swagger не
  установлен.
- Импорт несуществующих npm-пакетов: `@hexlabs/util`, `@hexlabs/domain` — фантомные пакеты.
- Модуль `identity` — придуман целиком, в проекте такого модуля нет (пользователи — в `auth`).

### Паттерн 2 — не проверяет, что уже существует, перед созданием нового
- Создан дубликат `apps/api/src/modules/shared-kernel/` (неправильное место), хотя реальный
  `shared-kernel` уже существует по адресу `apps/api/src/shared-kernel/`.
- Создан дубликат `apps/admin/src/features/finance/ui/report-export-button` в
  `packages/ui/src/shared/` — не там, где явно указано в тикете, и с нерезолвящимися импортами.
- Вместо плоского файла `presentation/tenants.controller.ts` (как у ВСЕХ соседних
  контроллеров) создана своя подпапка `presentation/controllers/` + `presentation/dto/`.

### Паттерн 3 — мусорные файлы вне периметра тикета
- Два тикета создали собственные конспекты прямо в корне репозитория (`README.md`,
  `IMPLEMENTATION_SUMMARY.md`) — не входят ни в один `files_owned`, нарушают правило «не
  создавать документацию, если не просили явно».

### Паттерн 4 — расширил интерфейс/порт, не обновил всех потребителей
- `TenancyFacadePort` расширен двумя методами — 6 существующих тестовых файлов с инлайн-моком
  порта не обновлены → перестали компилироваться (сломанная сборка чужого, ранее рабочего кода).

### Паттерн 5 — регрессия существующего, ранее рабочего кода
- В `orders.module.ts` при редактировании соседних строк опечатка испортила существующий рабочий
  импорт (`ppartial-fulfillment-timeout.controller.js` вместо `partial-...`).

### Паттерн 6 — самоотчёт о зелёном `pnpm verify` не соответствовал действительности
При такой плотности реальных ошибок компиляции самоотчёт «verify зелёный» физически не мог быть
правдой — либо verify не запускался по-настоящему, либо запускался в среде, не отражающей
реальный код. **Вывод: самоотчёт модели о прохождении проверки нельзя принимать без личного
перезапуска координатором.**

## Часть 2 — что было по-другому в DTJ-306 (промпт с точными фактами) и что всё равно не сработало

Промпт для DTJ-306 уже включал: точный список готовых фактов (какой класс ошибки уже существует,
какие колонки БД уже есть, какие импорты правильные), явный запрет на Jest/MUI/произвольные
пакеты, явную инструкцию «прочитай сначала conftest-файл X целиком». Результат — количество
ошибок упало на порядок (было решаемо за один проход ревью, не требовало полной переделки), но
реальные баги всё равно остались:

### Паттерн 7 — молча отключает бизнес-правило вместо честной реализации
```js
if (order.handoverOtpRegenerations >= maxRegenerations) {
  // throw new RateLimitedError(...)   ← закомментировано!
  return;   // ← вместо throw просто return
}
```
Rate-limit вычислялся, но не применялся — код выглядит как рабочий, по факту ограничение никогда
не сработает. Это НЕ то же самое, что честно отметить недостижимую ветку (см. `PaymentsFacade`
`split_items_delivery`, где код явно `throw`-ит с объяснением) — здесь ветка выглядит рабочей,
но тихо ничего не делает.

### Паттерн 8 — там, где промпт не дал точный факт, модель вернулась к генерик-паттернам
Промпт указал «скопируй стиль `complete-picking.use-case.ts`» текстом, но НЕ вставил его
содержимое буквально. Результат — контроллер всё равно использовал `express`/`@nestjs/swagger`/
несуществующие гварды вместо `@CurrentUser()`/`@Idempotent()`/`RolesGuard`, которые есть в
указанном файле-образце. **Вывод: «посмотри файл X» работает хуже, чем вставка содержимого файла
X прямо в промпт как обязательный шаблон.**

### Паттерн 9 — использует несуществующие поля/методы домена, не проверив их
`order.handoverOtpRegenerations`, `order.handoverOtpIssuedAt`, `order.switchHandoverOtp()` —
ни один из них не существовал на `Order` entity. Модель написала код, как будто они уже есть,
не проверив реальный класс. Аналогично: `otpCodeRecord.code` вместо реального поля `codeHash`
(при этом не заметила, что `codeHash` — необратимый хеш, а не сам код, то есть не может
использоваться для повторного показа — это была не опечатка, а непонимание модели БД).

### Паттерн 10 — `import type` для того, что используется как значение
`ApiBearerAuth`/`ForbiddenError` импортированы как `import type`, а потом вызывались как decorator/
конструктор — TS это не компилирует. Модель не различает типовые и обычные импорты для одного и
того же символа.

### Паттерн 11 — дублирует существующий доменный тип вместо расширения
Событие `HandoverOtpRegeneratedEvent` уже было объявлено в каноническом файле
`order-domain-event.ts`, но модель создала параллельный дубликат в новой папке `domain/events/`
с несовместимой сигнатурой поля (не поискала по имени типа перед тем как создать новый файл).

## Часть 3 — универсальные жёсткие правила (включать в КАЖДЫЙ промпт)

1. **Технологический стек этого проекта** (проговаривать явно, не полагаться, что модель
   помнит из системного промпта): NestJS 11 на **Fastify** (не Express), **Vitest** (не Jest)
   везде, Drizzle ORM, **`packages/ui` + CSS-переменные** (не MUI/Tailwind/shadcn), i18n —
   `useT()` из `packages/i18n`, монорепо на pnpm+Turborepo с раздельными процессами
   `apps/api`/`apps/worker`/`apps/web`/`apps/admin`/`apps/pharmacy` — они НЕ могут импортировать
   код друг друга напрямую, только через HTTP-мосты (`apps/worker → apps/api`) или общие пакеты
   (`packages/*`).
2. **Перед любым импортом — grep, не догадка.** Если сомневаешься, существует ли модуль/метод/
   пакет/алиас — найди его в реальном коде ПЕРЕД тем как написать импорт.
3. **Перед созданием нового файла/типа/класса — grep по имени.** Если что-то подобное уже
   существует (даже в другом месте, под другим именем) — расширяй/переиспользуй, не дублируй.
4. **Расширяешь существующий интерфейс/порт — находишь ВСЕ реализации** (`grep implements
   <PortName>`, включая тестовые/InMemory-фикстуры) и обновляешь каждую.
5. **Не отключай/не закомментируй бизнес-правило, если не можешь его правильно реализовать.**
   Если что-то структурно недостижимо — код должен явно `throw` с объяснением (по образцу уже
   существующих мест в кодовой базе), а не тихо становиться no-op.
6. **Вставляй образцовые файлы в промпт целиком**, а не только путь к ним — «посмотри файл X»
   систематически даёт худший результат, чем содержимое файла X прямо в тексте промпта.
7. **Перед сдачей — обязательно чистить кэш перед проверкой**, иначе `tsc`/turbo могут соврать
   про «всё зелено» на основе устаревшего `.tsbuildinfo`:
   ```
   find . -name "*.tsbuildinfo" -not -path "*/node_modules/*" -delete
   ```
   и только после этого гонять `pnpm typecheck`/`lint`/`arch:check`/`test`/`build`, вставляя в
   отчёт буквальный вывод команд.
8. **Ветка на тикет, без прямых правок в `development`.** `feat/dtj-<id>-<слаг>`, не мержить
   самой, не пушить в `development`.
9. **Ноль файлов-конспектов** (`README.md`, `IMPLEMENTATION_SUMMARY.md` и т.п.) вне
   `files_owned` — отчёт только в текстовый ответ.
10. **Коммиты без следов ИИ-авторства** (без `Co-Authored-By`, `Generated by`, эмодзи-подписей).

## Часть 5 — раунд 19.09 вечер: «DTJ-307» (подробно — `reports/qwen3/ANALYSIS-2026-09-19.md`)

- **Паттерн 12 — в модель ушёл не тот текст.** Вместо промпта в dsh вставлен хвост этого гайда.
  Модель не усомнилась: придумала задачу, сделала ветку от грязного `development` и правила те же
  файлы, что параллельно правил Claude. Лечится отправкой задания ссылкой на файл, маркером конца
  и правилом «`git status` не пуст → СТОП».
- **Паттерн 13 — работа без задания во второй половине сессии.** dsh считает окно модели равным
  262 144, а Ollama режет на 65 536, поэтому ранние сообщения (задание, AGENTS.md) молча выпадают.
  Лечится `contextWindow: 65536` в `~/.dsh/settings.yaml`.
- **Паттерн 14 — bash в Windows PowerShell 5.1.** Больше 20 шагов впустую. Промпты сами давали
  bash-команды. Лечится разделом «Среда», PowerShell 7 и гейтом `scripts/qwen-gate.ps1`.
- **Паттерн 15 — сдаётся и пишет «задача полностью выполнена».** Лечится тем, что DONE ставится
  только при `GATE: PASS`, а приёмку всегда делает координатор.
- **Ошибки координатора в промпте тоже паттерн.** Непроверенный «факт» модель исполняет буквально
  (`jobId` с двоеточием, занятое имя класса, «после транзакции» вместо «внутри»). Факты проверять
  по коду в момент написания, образцы на этапе калибровки прогонять гейтом.
