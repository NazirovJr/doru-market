## 1. Telegram Mini Apps: SDK, initData, темизация, платежи, ограничения

### 1.1 SDK и версии

Официальный клиентский API — `Telegram.WebApp` (легаси-объект, документирован в `core.telegram.org/bots/webapps`) [1]. Поверх него сообщество (`telegram-mini-apps-dev`) поддерживает типобезопасный SDK `@telegram-apps/sdk` (v2.x актуален на конец 2025) и React-обвязку `@telegram-apps/sdk-react` [2][3]. Charter уже фиксирует «Telegram Mini Apps SDK» как выбор — конкретизируем: использовать `@telegram-apps/sdk-react` поверх `apps/web`, не писать интеграцию с нуля на голом `window.Telegram.WebApp`, т.к. SDK инкапсулирует версионирование Mini Apps platform API (`platform/methods` меняется от версии к версии) [4].

### 1.2 Валидация `initData` на сервере — обязательный алгоритм

`initData` — query-string, который TWA передаёт клиенту при запуске; он **не является токеном авторизации сам по себе** и должен быть **перепроверен на бэкенде** при каждом первом обмене на серверную сессию. Алгоритм (по официальной доке и её типовым реализациям) [1][5][6]:

1. Распарсить `initData` как query-string → получить пары `key=value`, включая `hash`.
2. Убрать `hash` из набора пар.
3. Отсортировать оставшиеся пары по ключу **лексикографически**, собрать `data-check-string` — конкатенация `key=value` через `\n` (0x0A).
4. Вычислить `secret_key = HMAC-SHA256(key="WebAppData", data=BOT_TOKEN)`.
5. Вычислить `computed_hash = HMAC-SHA256(key=secret_key, data=data-check-string)`, представить как hex.
6. Сравнить `computed_hash` с полем `hash` из initData (constant-time compare).
7. Проверить `auth_date`: разница с текущим временем не должна превышать разумный порог (в комьюнити-реализациях и большинстве гайдов используется **5 минут**) [5][6] — значение не жёстко задано Telegram, поэтому это порог, который проект выбирает сам (рекомендация: 300 секунд, настраиваемо через ENV).
8. Только после успешной проверки — выдавать собственный JWT (Charter §3.1: access 15 мин / refresh 30 дней).

Готовые серверные реализации для референса: `@telegram-apps/init-data-node` (валидация на Node.js) [6], публичные gist-примеры на TS/Python [5].

**Инженерное следствие**: реализовать `TelegramAuthGuard` в `apps/api` как отдельный provider за тем же `AuthProvider`-интерфейсом, что и обычный OTP-логин (Provider Pattern, Charter §3.1) — TWA-режим не должен вводить второй, несовместимый механизм RBAC.

### 1.3 Темизация

`Telegram.WebApp.themeParams` / SDK-компонент `themeParams` отдают палитру хоста (`bg_color`, `button_color`, `header_bg_color`, `accent_text_color` и др.); метод `bindCssVars()` прокидывает их как CSS-переменные `--tg-theme-*` [7][8]. **Инженерное следствие**: дизайн-система `packages/ui` должна читать цвета через CSS-переменные с фоллбэком на дефолтную палитру DoruTJ — тот же механизм, что уже используется для White-Label брендинга тенантов (Charter §3.4), поэтому TWA-тема и tenant-тема должны каскадироваться без конфликта (порядок: tenant CSS vars → переопределение `--tg-theme-*`, если запущено внутри Telegram).

`viewport`-компонент SDK отдаёт `width/height/isExpanded/isFullscreen` — обязательно вызывать `viewport.expand()` при старте, иначе Mini App открывается в компактной высоте [4][8].

### 1.4 Платежи внутри Mini App

Критично для архитектуры: Telegram разделяет два режима Bot Payments API [9][10]:

- **Цифровые товары/услуги** — обязаны рассчитываться **только в Telegram Stars** (валюта `XTR`), это требование площадок (App Store/Google Play policy), не связанное с самим Telegram [10].
- **Физические товары и услуги** (наш случай — медикаменты и доставка) — можно использовать **любого стороннего платёжного провайдера** через `sendInvoice`/`createInvoiceLink` с `provider_token`, либо вообще не проводить оплату через Bot Payments API, а открывать собственный чек-аут (deep-link на Alif Mobi / DC Next), как и описано в module 3 ТЗ [9].

**Вывод**: Escrow-протокол ТЗ (checkout → deep-link в Alif/DC → webhook) корректен и **не обязан** интегрироваться с Bot Payments API/Stars — это отдельный трек, специфичный для цифровых товаров, который DoruTJ не продаёт. Не тратить спринт на интеграцию с `payments.sendStarsForm`/Stars [9][10][11].

### 1.5 Ограничения и best practices TWA

- Rate limit Bot API для исходящих сообщений (уведомления через бота, см. §5.2): **30 msg/sec на бота глобально**, 1 msg/sec на конкретный чат, ~20 msg/min в группу; превышение → `429 Too Many Requests` с `retry_after` [12][13]. Платный broadcast (Stars-баланс ≥100k и ≥100k MAU) поднимает лимит до 1000/sec — не актуально для MVP [12].
- Внутри Mini App нет доступа к файловой системе устройства и нет background-выполнения — все ограничения обычного sandboxed WebView применяются (см. §2 про PWA-ограничения, они те же для TWA-режима `apps/web`).
- initData **истекает** логически (см. `auth_date`), но сам объект не «протухает» на клиенте — сервер обязан быть источником истины по свежести.

### 1.6 Популярность Telegram в Таджикистане

Согласно агрегатору WMTips (данные по соцсетям в Таджикистане, 2026), Telegram занимает **~47% рынка** мессенджеров/соцсетей в стране, уступая только Instagram (~65%) [14]. **UNVERIFIED**: прямой фетч страницы вернул HTTP 403, поэтому цифра приведена только по краткому изложению поисковой выдачи, не по прочитанному первоисточнику — требует перепроверки перед использованием в маркетинговых материалах. Прямых достоверных данных о блокировках/троттлинге Telegram именно в Таджикистане в ходе поиска не найдено (найдены только кейсы РФ, Ирана, Китая, Вьетнама, Непала) [15] — **ASSUMPTION**: в отличие от России, специфичных подтверждённых блокировок Telegram в РТ не идентифицировано, но история региона (эпизодические блокировки мессенджеров вокруг экзаменов/протестов в других странах ЦА) означает, что **TWA не должен быть единственным клиентом** — PWA-режим (`apps/web` вне Telegram) обязателен как fallback-канал, что и заложено в Charter (веб приложение существует независимо от TWA-режима).

## 2. PWA на дешёвых Android-устройствах

### 2.1 Установка (installability)

Критерии, при которых Chrome/Android генерирует `beforeinstallprompt` [16][17]:

- HTTPS.
- Валидный Web App Manifest: `name`, `short_name`, `start_url`, `display: standalone` (или `fullscreen`), иконка **минимум 512×512**, `background_color`, `theme_color`.
- Зарегистрированный Service Worker с обработчиком `fetch`.
- Эвристика вовлечённости: пользователь должен взаимодействовать с доменом **не менее ~30 секунд** до появления промпта [17].

Android Go (обязателен для новых устройств с ≤2 ГБ RAM начиная с Android 11 [18]) — критерии installability не отличаются от обычного Android, но PWA в целом предпочтительнее нативного приложения на таких устройствах, т.к. не требует скачивания APK и занимает меньше памяти на диске [17][18] — это прямое обоснование отклонения №5 Charter (React PWA вместо Flutter для курьера/фармацевта).

**Инженерное следствие**: у `apps/pharmacy` и `apps/courier` обязателен кастомный install-prompt UI (перехват `beforeinstallprompt`, т.к. дефолтный браузерный баннер на Android Go часто подавляется/не показывается предсказуемо), с явной кнопкой «Установить приложение» на первом экране.

### 2.2 Офлайн-работа

Обычный паттерн: cache-first для статических ассетов (JS/CSS/иконки/шрифты через `precache` из Workbox), network-first с офлайн-фоллбэком для API-запросов каталога, и очередь исходящих мутаций (создание заказа/скан штрихкода) в IndexedDB с фоновой синхронизацией при восстановлении сети. Важное ограничение: **Background Sync API не поддерживается iOS Safari** [19] — на iOS фоновая синхронизация недоступна в принципе, значит для `apps/pharmacy`/`apps/courier` на iPad это дополнительный риск (см. §2.4) — рекомендовано ориентировать эти два приложения прежде всего на Android-планшеты/смартфоны, iOS — best-effort.

### 2.3 Сканер штрихкодов через камеру — сравнение библиотек

| Вариант | Поддержка | Комментарий |
|---|---|---|
| **`BarcodeDetector` (Barcode Detection API, нативный)** | Chrome/Android **151+** — полная поддержка; Samsung Internet **13+** — полная поддержка; **Safari iOS — отключён по умолчанию во всех текущих версиях (17.0–26.6)** [20] | Быстрее и легче всего (декодирование в браузерном/ОС движке), но **не работает на iOS** без полифилла |
| **`@zxing/library` (ZXing-js)** | Работает во всех современных браузерах (JS-декодер, без нативного API) | Более тяжёлый, декодирование на JS/WASM медленнее нативного, но кроссплатформенно, включая iOS [21][22] |
| **`html5-qrcode`** | Обёртка над ZXing-js с готовым UI | Само демо и авторы отмечают, что библиотека **слабо поддерживается** (maintenance mode ZXing-js внутри) [21] — не рекомендуется как основа для продуктового кода на 3+ года |

**Рекомендация (REQ-PWA-3)**: feature detection — при наличии `window.BarcodeDetector` использовать нативный API (макс. производительность на Android, включая слабые Android Go устройства — критично для сканирования в момент сборки заказа с SLA 7 минут), с фоллбэком на `@zxing/library` (не на `html5-qrcode`, из-за статуса поддержки) для iOS/старых браузеров. Не привязываться к одной библиотеке жёстко — обернуть в свой `BarcodeScannerProvider` (тот же Provider Pattern, что и внешние интеграции).

### 2.4 Геолокация в фоне

Ключевое ограничение **веб-платформы в целом**: **истинного фонового геотрекинга (когда приложение свёрнуто/экран выключен) в вебе не существует** [23]. Geolocation API работает, пока страница активна; при выключении экрана браузер может прекращать отдавать координаты [23]. `Wake Lock API` умеет удерживать **только экран** (Screen Wake Lock) — системного (CPU) wake lock для веба больше не существует (был выпилен из спецификации), и Screen Wake Lock работает только пока страница видима [23].

**Инженерное следствие (REQ-PWA-4/5)**:
- Курьерский PWA обязан держать экран включённым через `navigator.wakeLock.request('screen')` на весь активный рейс доставки и явно предупреждать курьера не сворачивать приложение — это компромисс, принятый вместе с отклонением №5 Charter (PWA вместо Flutter). Ограничение нужно внести в Charter как **известный компромисс**, а не тихо потерять на этапе разработки.
- Точки трека (для ETA клиенту) отправлять по heartbeat, пока приложение активно; при потере фокуса — деградировать до «последняя известная точка + время», не выдавать за live-tracking.

### 2.5 Web Push и ограничения iOS

- Push работает на iOS/iPadOS **только с версии 16.4+** (март 2023); на 2026 год ≥95% активных iPhone — на 16+ [24].
- На iOS push работает **только для PWA, установленного через «Добавить на экран Домой»** — открытая вкладка Safari пуши не получает [24].
- Safari 18.4+ добавил Declarative Web Push — упрощённый пуш без обязательного Service Worker для простых уведомлений [24].
- Badge API (счётчик на иконке) доступен с iOS 16.4 [24].
- **Background Sync на iOS Safari не поддерживается вообще** [19] (см. §2.2).

**Инженерное следствие**: `PushProvider` (Charter §3.1, `WebPushProvider`/`MockPushProvider`) обязан иметь graceful-деградацию: на iOS — принудительно подталкивать пользователя установить PWA на домашний экран (иначе push технически недоставим), и параллельно всегда дублировать критичные уведомления (статус заказа, прибытие курьера) через Telegram-бот (см. §5.2) как platform-independent канал.

## 3. Геоданные Таджикистана

### 3.1 Качество OpenStreetMap

По Душанбе задокументирован волонтёрский проект: студенты American Space Dushanbe в рамках HOT Tasking Manager с января по июль 2018 картировали строения (building polygons), а в июле 2018 — точки интереса (добавлено 500+ бизнесов) [25]. Это означает **разовый, немолодой массив данных**: сам источник отмечает возможные дубликаты и то, что данные могут отставать от реальной застройки/сноса [25]. Общий паттерн OSM — в развивающихся регионах покрытие заметно уступает Западной Европе/США по плотности и свежести [25][26]. Отдельных актуальных (2024–2026) аудитов по Худжанду/Бохтару в ходе поиска не найдено — **UNVERIFIED** для этих двух городов, требуется собственная выборочная проверка (сверить 20–30 адресов аптек через `nominatim.openstreetmap.org/ui/about.html` вручную перед стартом).

### 3.2 Карты/тайлы — что можно использовать легально и бесплатно

| Провайдер | Вердикт | Обоснование |
|---|---|---|
| **OSM raw tile server (tile.openstreetmap.org)** | Не использовать в проде напрямую | Usage Policy OSM разрешает только лёгкий трафик/тестирование, не production-нагрузку — нужен свой тайл-сервер |
| **MapLibre GL JS + собственный vector tile server (self-host, напр. `tileserver-gl`/`OpenMapTiles` из OSM-экстракта по Таджикистану)** | **Рекомендовано** | MapLibre — BSD-3-Clause, community-governed форк Mapbox GL JS, не привязан к одному вендору тайлов [27][28]; полностью самостоятельный хостинг = нет лицензионных ограничений на бизнес-модель |
| **Leaflet + растровые тайлы** | Резервный/более простой вариант | Более лёгкая либа, но растровые тайлы тяжелее по трафику, чем vector tiles MapLibre [27] |
| **2GIS (2gis.tj)** | Есть у 2GIS собственное покрытие Душанбе с точностью до дома, локальная команда поддерживает данные, доступно на тадж./рус. [29] | Коммерческий API (Geocoder API, Map Tiles API) требует ключ/подписку, бесплатен только демо-режим [30][31] — годится как визуальный референс/эталон качества данных, но не как бесплатная production-зависимость |
| **Yandex Maps API** | **Запрещено для нашего кейса** | Условия свободного использования API прямо запрещают: (а) использование в проектах с ограниченным/платным доступом, (б) **«использование для мониторинга и диспетчеризации» (monitoring and dispatching)** — т.е. именно курьерский трекинг [32]. Плюс явные санкционные оговорки, ограничивающие круг юрлиц-пользователей [32]. Использование Yandex Maps для платформы доставки с курьерским трекингом = прямое нарушение ToS |

**Рекомендация (REQ-GEO-1/2)**: стек — MapLibre GL JS на фронте + самостоятельно поднятый vector-tile-сервер из OSM-экстракта Таджикистана (обновление раз в 1–4 недели) + собственный (self-hosted) Nominatim инстанс для geocoding/reverse-geocoding служебных нужд (не как основной способ ввода адреса клиентом, см. §3.4). 2GIS можно использовать эпизодически как «второе мнение» для сверки координат аптек при onboarding сети, не как рантайм-зависимость. Yandex Maps исключить из стека полностью.

### 3.3 Геокодинг при отсутствии формальных адресов

Nominatim в среднем правильно геокодирует **~70% адресов**, тогда как лучшие коммерческие сервисы — **~90%** [33]; для хорошо картированных регионов (США/Европа/Япония) точность «до крыши», для менее покрытых регионов (наш случай, §3.1) результат хуже — вплоть до уровня улицы/района, а не дома [33][26]. **Прямой вывод**: полагаться на строковый геокодинг «адрес → координаты» как на основной механизм ввода для DoruTJ **нельзя**.

### 3.4 «Навигация по ориентирам» (landmark-based addressing) — конкретная реализация

Модель данных уже частично заложена в ТЗ/Charter (`landmark_tj`, `delivery_landmark`, `delivery_latitude/longitude`). Конкретизация:

- **Сохранённый адрес клиента** — не строка, а объект: `{ address_text (свободный текст), landmark_text (ориентир, напр. "пеши масҷиди Ансор"), lat, lng (пин, поставленный вручную на карте пользователем — НЕ результат геокодинга строки), entrance/floor/apartment (опционально), photo_url (опционально — фото подъезда/ворот) }`.
- UI сохранения адреса: карта (MapLibre) открывается на текущей геопозиции пользователя (`Geolocation API`, работает в PWA без ограничений в foreground [23]), пользователь **перетаскивает пин** на точную точку, дополнительно вводит текстовый ориентир — геокодинг строки используется только как *подсказка для первичного центрирования карты*, никогда как источник финальных координат.
- Курьерское приложение показывает: пин на карте + `landmark_text` + (если есть) `photo_url`, а не только текстовый адрес — это и есть практическая реализация «доставки по ориентирам» из ТЗ (проблема `«Хонаи 4-ошёна пеши масҷид»`).
- Reverse-geocoding (Nominatim self-host) используется только для **отображения человекочитаемого приближённого адреса** рядом с пином (UX-подсказка), не для валидации.

## 4. Операционка доставки

### 4.1 Расчёт стоимости доставки и зоны

ТЗ фиксирует поля `delivery_fee_tjs` в `orders`, но не формулу. Общепринятый паттерн последней мили — **зональное тарифицирование**: базовая ставка + ставка за км/зону, зоны нарезаны по городским районам, с ручной корректировкой тарифов через `tenant_settings`/admin (не хардкод) [34][35]. Практическое решение для MVP: `delivery_fee_tjs = base_fee + per_km_rate * haversine(pharmacy, delivery_point)`, с округлением зон (0–3 км / 3–7 км / 7+ км) и админ-конфигурируемыми ставками на тенанта (не на весь маркетплейс — сети должны иметь право на свой тариф, см. Charter §3.4 White-Label брендинг/конфиг без деплоя).

### 4.2 Назначение курьера (ручное/авто)

Индустриальные подходы — Hungarian Algorithm (оптимальное паросочетание заказ↔курьер) или Minimum Cost Flow для парка из многих курьеров и точек [36] — избыточны для MVP-масштаба (Charter: 12+ аптек, few couriers per pharmacy на старте). **Рекомендация для MVP**: простой greedy-алгоритм — «ближайший доступный курьер в радиусе N км от аптеки, сортировка по расстоянию + текущей загрузке (кол-во активных доставок)», с ручным override для `pharmacy_admin`/диспетчера. Оставить `courier_id` в `orders` изменяемым вручную (как и заложено в схеме ТЗ) — авто-алгоритм лишь предзаполняет предложение, финальное назначение — действие человека или явное авто-подтверждение по таймауту.

### 4.3 Подтверждение вручения кодом

Уже специфицировано в ТЗ/Charter (module 5, CUJ-3/CUJ-4): фармацевт жмёт «Передано курьеру» → генерируется 4-значный OTP; курьер вводит **клиентский** OTP при вручении → capture escrow. Важное уточнение по OTP на 4 цифры: 10 000 комбинаций — приемлемо только при (а) коротком TTL кода (предложение: код действителен пока заказ в статусе `picked_up`, не дольше нескольких часов), (б) лимите попыток ввода (rate-limit 5 попыток → блокировка на N минут), иначе брутфорс на слабом 4-значном коде тривиален.

### 4.4 Наличные и сдача (COD)

`payment_method = 'cash_courier'` уже есть в схеме, но требует отдельной логики, т.к. **ломает Escrow-модель** (нет банковского webhook для наличных): предложение полей — `cash_amount_given` (сколько купюр дал клиент, вводит курьер), `cash_change_due` (авто-расчёт сдачи), обязательное указание при оформлении заказа, нужна ли сдача и с какой купюры («сдача с 200 сомони»), чтобы курьер приходил подготовленным. Статус `paid_escrow` для cash-заказов должен проставляться не вебхуком, а **явным действием курьера** «Наличные получены» с обязательным вводом суммы (audit-log, т.к. это единственный способ оплаты без криптографической защиты от спора «я передал / мне не передали»). Рекомендуется ограничить COD (порог по сумме заказа, недоступен для дорогих/рецептурных заказов) — политика, не техническое ограничение, фиксируется в `tenant_settings`.

### 4.5 Отмены и возвраты

Предложение состояний отмены поверх `order_status`:
- До `paid_escrow` (пока не оплачено/не собрано) — свободная отмена клиентом, без штрафа.
- После `paid_escrow`, до `picked_up` (фармацевт ещё не начал сборку) — отмена клиентом с автоматическим освобождением escrow (без capture).
- После начала сборки (таймер SLA пошёл) — отмена требует подтверждения `pharmacy_admin` (частичные издержки на уже вскрытую/собранную позицию).
- После `picked_up` (у курьера) — только через возврат (return-to-pharmacy flow), нужен отдельный `return_status`, не предусмотренный в текущей схеме ТЗ — **пробел, который стоит закрыть отдельным ADR**.

### 4.6 Холодовая цепь

В схеме `medicines.storage_temperature` уже есть как поле-маркер. Индустриальный стандарт для инсулина и подобных препаратов — хранение и перевозка **2–8°C**, деградация необратима вне окна 2–8°C (кратковременно допустимо до комнатной температуры на ограниченный срок использования, но не для транспортировки партии) [37][38]. «Последняя миля» — самый уязвимый сегмter цепи (время на крыльце/у двери) [38][39]. **Инженерное следствие (REQ-DELIV-6)**: заказы, где хотя бы одна позиция имеет `storage_temperature` вне комнатной нормы, должны: (а) помечаться флагом `requires_cold_chain` на заказе, (б) иметь сокращённый целевой SLA доставки (напр. ≤45 минут от `picked_up`), (в) в фармацевт-терминале выводить чек-лист «упаковано в термопакет» перед разрешением статуса «Передано курьеру».

## 5. Нотификации

### 5.1 SMS-шлюзы в Таджикистане

Прямых публичных self-service API от местных операторов (Tcell, MegaFon Tajikistan, Babilon-Mobile, ZET Mobile/Beeline) в ходе поиска не обнаружено — рынок обслуживается через международных SMS-агрегаторов, у которых есть прямые маршруты к таджикским операторам: Messaggio (отдельные страницы интеграции по каждому оператору — Tcell, MegaFon, Babilon-Mobile, TT mobile) [40], D7 Networks [41], EasySendSMS [42]. Оценочная (агрегаторская, не официальная от регулятора) доля рынка операторов: Tcell ~36%, MegaFon ~28%, ZET Mobile(Beeline) ~20%, Babilon-Mobile ~15% [40] — **UNVERIFIED**, цифры из маркетингового материала SMS-агрегатора, не из отчёта регулятора «Хадамоти алоқа». Для легальной рассылки OTP/уведомлений через локальных операторов требуется соответствие требованиям регулятора связи Таджикистана [40] — конкретный процедурный регламент не найден, требуется отдельная юридическая проверка перед запуском.

Альтернатива для MVP/pilot без контракта с агрегатором: **SMS Gateway for Android (`sms-gate.app`, Apache-2.0, open-source)** — превращает обычный Android-телефон с местной SIM-картой в SMS-шлюз с REST API/webhooks, поддержка нескольких SIM на одном устройстве, self-hosted или облачный режим [43][44]. Это дёшево и подходит как «честный второй провайдер» за интерфейсом `SmsProvider` наравне с `MockSmsProvider` (Charter §3.1), пока не заключён контракт с агрегатором — важно: не полагаться на него как единственный прод-канал при масштабировании (throughput одного физического SIM ограничен и не рассчитан на пиковые нагрузки/антиспам-лимиты оператора).

### 5.2 Telegram-бот как канал уведомлений

Полностью бесплатен и не требует SMS-бюджета. Ограничения (см. §1.5): 30 msg/sec на бота глобально, 1 msg/sec на конкретный чат [12][13] — для MVP-масштаба (единицы-десятки заказов одновременно) достаточно с большим запасом. Обязательное условие: бот может писать пользователю только после того, как пользователь сам инициировал диалог (`/start`) — `chat_id` должен быть захвачен и сохранён при первом старте TWA/бота, иначе push недоставим. **Рекомендация (REQ-NOTIF-2)**: сделать Telegram-бот **основным** каналом статусных уведомлений (не SMS, не Web Push) для пользователей, у которых есть привязанный `chat_id` — это одновременно самый надёжный (нет ограничений iOS Push, см. §2.5) и самый дешёвый канал; SMS — фоллбэк для пользователей без Telegram или недоступного бота.

### 5.3 Звуковые оповещения на планшете аптеки

Браузерные политики автовоспроизведения звука требуют явного пользовательского жеста перед первым `audio.play()` без mute — для киоск-режима планшета фармацевта необходим экран «включить звук» при первом заходе смены (один клик разблокирует `AudioContext`/`<audio>` на всю сессию вкладки). Рекомендуется параллельно держать `navigator.wakeLock.request('screen')` активным на терминале в рабочие часы — иначе Android может притушить/заблокировать экран и звуковой сигнал не привлечёт внимание вовремя (тот же API, что и для курьера, см. §2.4).

## Требования, вытекающие из исследования

1. **REQ-TG-1**: Серверная валидация `initData` обязана быть реализована точным алгоритмом двойного HMAC-SHA256 (`secret_key = HMAC-SHA256("WebAppData", BOT_TOKEN)`, затем `HMAC-SHA256(secret_key, data-check-string)`), с отклонением запроса при несовпадении хэша или при `auth_date` старше настраиваемого порога (по умолчанию 300 секунд, ENV `TELEGRAM_INITDATA_MAX_AGE_SEC`).
2. **REQ-TG-2**: TWA-аутентификация обязана быть реализована как отдельный provider за общим `AuthProvider`-интерфейсом наравне с OTP-логином, выдающий тот же формат JWT (access 15 мин / refresh 30 дней).
3. **REQ-TG-3**: Оплата медикаментов/доставки внутри Mini App не должна использовать Telegram Stars/Bot Payments API — это платежи за физические товары, эскроу-протокол реализуется напрямую через Alif Mobi/DC Next deep-link + webhook, как в исходном ТЗ.
4. **REQ-TG-4**: Тема `apps/web` в TWA-режиме обязана читать `--tg-theme-*` CSS-переменные через `themeParams.bindCssVars()` и применять `viewport.expand()` при инициализации; порядок каскада — tenant-брендинг, затем Telegram-тема поверх, если приложение запущено внутри Telegram.
5. **REQ-TG-5**: Исходящие уведомления через Telegram-бота обязаны быть ограничены очередью с троттлингом ≤30 msg/sec суммарно и ≤1 msg/sec на chat_id, с обработкой `429`/`retry_after`.
6. **REQ-PWA-1**: `apps/pharmacy` и `apps/courier` обязаны предоставлять собственный (не браузерный дефолтный) install-prompt UI на основе перехвата `beforeinstallprompt`, с валидным манифестом (иконка ≥512×512, `display: standalone`) и Service Worker с `fetch`-обработчиком.
7. **REQ-PWA-2**: Офлайн-режим реализуется через cache-first для статики и network-first + IndexedDB-очередь мутаций для API; на iOS Safari учитывается отсутствие Background Sync API — там очередь мутаций обязана flush-иться по явному триггеру (открытие/фокус приложения), не полагаясь на фоновую синхронизацию.
8. **REQ-PWA-3**: `BarcodeScannerProvider` обязан фича-детектить нативный `BarcodeDetector` (используется на Android/Samsung Internet) с фоллбэком на `@zxing/library` (не на `html5-qrcode`) для iOS и браузеров без нативной поддержки.
9. **REQ-PWA-4**: Курьерское приложение обязано держать `navigator.wakeLock.request('screen')` активным на время доставки и явно предупреждать курьера не сворачивать/не блокировать экран — истинный фоновый геотрекинг веб-платформой не гарантируется.
10. **REQ-PWA-5**: Live-tracking координат курьера деградирует до «последняя известная точка + timestamp», когда приложение не в фокусе — это состояние обязано явно отображаться клиенту (не выдавать устаревшую точку за live-позицию).
11. **REQ-PWA-6**: Web Push обязателен как provider (`WebPushProvider`) с явной проверкой платформы: на iOS уведомления работают только если PWA установлен через «Добавить на экран Домой» и iOS ≥16.4; при недоступности — UI обязан направлять пользователя на установку, а критичные статусы дублируются через Telegram-бот.
12. **REQ-GEO-1**: Карты реализуются на MapLibre GL JS + самостоятельно хостируемый vector-tile-сервер из OSM-экстракта Таджикистана; использование Yandex Maps API запрещено техническим требованием (нарушает ToS Yandex — «monitoring and dispatching» прямо запрещён условиями бесплатного использования).
13. **REQ-GEO-2**: Геокодинг (Nominatim self-host) используется только как вспомогательная подсказка (центрирование карты, реверс-геокодинг для UX-подписи), а не как источник финальных координат доставки — координаты обязаны быть пином, установленным пользователем/курьером вручную на карте.
14. **REQ-GEO-3**: Модель `saved_address` расширяется полями `landmark_text`, `photo_url` (опционально), `entrance`/`floor`/`apartment` (опционально) сверх существующих `address_text`/`lat`/`lng` из схемы ТЗ.
15. **REQ-DELIV-1**: `delivery_fee_tjs` рассчитывается по формуле «базовая ставка + ставка за км × haversine-расстояние», с зональным округлением и тарифами, настраиваемыми per-tenant через `tenant_settings` (без редеплоя).
16. **REQ-DELIV-2**: Назначение курьера реализуется как «предложение» алгоритма (ближайший свободный курьер по радиусу и текущей загрузке) с обязательной возможностью ручного переназначения `pharmacy_admin`/диспетчером.
17. **REQ-DELIV-3**: 4-значный OTP подтверждения вручения обязан иметь TTL (действителен только в статусе `picked_up`, максимум N часов) и rate-limit на попытки ввода (блокировка после 5 неверных попыток).
18. **REQ-DELIV-4**: Заказы с `payment_method = 'cash_courier'` обязаны иметь поля учёта суммы и сдачи (`cash_amount_expected`, `cash_amount_given`, `cash_change_due`); перевод в `paid_escrow`/финальный статус для наличных выполняется явным действием курьера с фиксацией суммы в audit-log, а не банковским вебхуком.
19. **REQ-DELIV-5**: Правила отмены/возврата дифференцируются по стадии заказа (см. §4.5); для стадии «уже у курьера» — вводится отдельный return-flow (`return_status`), отсутствующий в исходной схеме ТЗ, оформляется отдельным ADR.
20. **REQ-DELIV-6**: Заказы, содержащие позиции с `storage_temperature`, требующим холодовой цепи, помечаются `requires_cold_chain`, получают сокращённый целевой SLA доставки и обязательный чек-лист «упаковано в термопакет» в фармацевт-терминале перед передачей курьеру.
21. **REQ-NOTIF-1**: `SmsProvider` реализуется минимум двумя провайдерами сверх мока: коммерческий агрегатор (Messaggio/D7/EasySendSMS — выбор на этапе интеграции) и/или self-hosted `sms-gate.app` для pilot-фазы без контракта с агрегатором.
22. **REQ-NOTIF-2**: Telegram-бот — основной канал статусных уведомлений для пользователей с привязанным `chat_id`; `chat_id` обязан захватываться и сохраняться при первом `/start` бота или первом запуске TWA.
23. **REQ-NOTIF-3**: Терминал фармацевта обязан требовать явную пользовательскую разблокировку звука при старте смены (один клик перед первым автовоспроизведением) и удерживать Screen Wake Lock в рабочие часы.

## Открытые вопросы

1. Точная доля Telegram в аудитории Таджикистана (47%, WMTips) не подтверждена прямым чтением первоисточника (fetch вернул 403) — нужна повторная проверка другим методом (например, ручной просмотр страницы) перед использованием в продуктовых/маркетинговых материалах.
2. Нет подтверждённых данных о фактах блокировки/троттлинга Telegram именно в Таджикистане (в отличие от РФ/Ирана/Китая) — нужно уточнение у локального юридического/комплаенс консультанта или локальных новостных источников на таджикском/русском, не найденных в ходе данного поиска.
3. Актуальное состояние OSM для Худжанда и Бохтара не проверено (найдены данные только по волонтёрскому проекту 2018 года в Душанбе) — требуется ручной аудит выборки адресов через Nominatim/openstreetmap.org перед запуском в этих городах.
4. Не найден официальный регламент таджикского регулятора связи («Хадамоти алоқа...») по правилам рассылки коммерческих/OTP SMS — нужна прямая консультация с локальным юристом/оператором перед выбором SMS-агрегатора.
5. Официальные лимиты Telegram `CloudStorage` (объём/кол-во ключей) не были предметом отдельной проверки в этом исследовании — если планируется использовать CloudStorage для офлайн-состояния TWA, нужна отдельная сверка с `core.telegram.org/bots/webapps#cloudstorage`.
6. Коммерческие условия и точный охват геокодинга/тайлов 2GIS для городов Таджикистана за пределами Душанбе (Худжанд, Бохтар) не проверены — требуется прямой запрос в 2GIS или тест демо-ключа.
7. Не определён точный порог суммы заказа/категории товара, при которых наличная оплата (COD) должна быть запрещена — это продуктовое/финансовое решение, не техническое, требует решения от Product/Architect.
8. Не проверена совместимость `sms-gate.app` (Android SMS gateway) с требованиями локальных операторов Таджикистана по антиспам-регламенту рассылок (может блокироваться оператором при массовой отправке с одной SIM) — нужен pilot-тест на реальной таджикской SIM-карте перед принятием решения об использовании в проде.
