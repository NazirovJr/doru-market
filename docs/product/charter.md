# DoruTJ — Устав проекта (Project Charter)

> Владелец документа: Architect / Tech Lead / Product Manager (оркестратор).
> Статус: **BASELINE v1.0**. Все агенты на всех этапах ОБЯЗАНЫ следовать этому документу.
> Источник требований: `tz.log` (исходное ТЗ заказчика).

---

## 1. Продукт

**DoruTJ** — национальный нейтральный фармацевтический маркетплейс Республики Таджикистан
+ White-Label платформа для аптечных сетей (multi-tenant).

**Ключевая ценность**: прозрачный подбор аналогов по МНН (экономия для пациента), защищённая
Escrow-оплата (никаких фейковых скриншотов), доставка по ориентирам, AI-разбор рецептов,
синхронизация остатков с учётной системой аптеки.

---

## 2. Что считается «готовым продуктом» (Definition of Product Done)

Монорепозиторий, который:

1. Поднимается одной командой `docker compose up -d` (полный стек).
2. Поднимается локально без Docker: `pnpm install && pnpm db:migrate && pnpm db:seed && pnpm dev`.
3. Содержит работающие сквозные пользовательские сценарии (E2E, Playwright) из §6.
4. Проходит `pnpm typecheck && pnpm lint && pnpm test && pnpm test:e2e` без ошибок.
5. Содержит seed-данные: ≥3 аптечные сети, ≥12 аптек, ≥300 медикаментов с МНН-связями,
   тестовые пользователи всех ролей, демо-заказы во всех статусах.
6. **Не содержит заглушек-«пустышек» в продуктовых путях**: любой mock — это ЯВНЫЙ провайдер
   за интерфейсом, выбираемый через ENV, с честной реализацией контракта.
7. Работает полностью **без единого внешнего API-ключа** (dev-профиль на Mock-провайдерах).

## 3. Технологический стек (решение архитектора)

> Заказчик делегировал выбор стека и инструментов. ТЗ трактуется как указание на **функцию**,
> а не на конкретный вендор. Ниже — итоговые решения с обоснованием отклонений.

### 3.1 Ядро

| Слой | Выбор | Обоснование |

### 3.3 Правило «Provider Pattern» (обязательное)

Каждая внешняя система закрыта интерфейсом с ≥2 реализациями: реальная + `Mock*` (детерминированная).
Выбор — через ENV. Это обеспечивает полную работоспособность и тестируемость без внешних ключей.

| Интерфейс | Реализации | ENV |
|---|---|---|
| `PaymentProvider` | `AlifMobiProvider`, `DcNextProvider`, `MockBankProvider` | `PAYMENT_DRIVER` |
| `PrescriptionOcrProvider` | `GeminiOcrProvider`, `MockOcrProvider` | `OCR_DRIVER` |
| `SpeechToTextProvider` | `WhisperSttProvider`, `MockSttProvider` | `STT_DRIVER` |
| `SmsProvider` | `SmsGatewayProvider`, `MockSmsProvider` (OTP в лог + БД) | `SMS_DRIVER` |
| `ObjectStorageProvider` | `S3Provider` (MinIO), `LocalFsProvider` | `STORAGE_DRIVER` |
| `SearchProvider` | `PostgresSearchProvider`, `ElasticSearchProvider` (опционально) | `SEARCH_DRIVER` |
| `PushProvider` | `WebPushProvider`, `MockPushProvider` | `PUSH_DRIVER` |

### 3.4 Мультитенантность (White-Label)

- Тенант резолвится middleware: `Host` (custom_domain) → `X-Tenant-Slug` → `neutral` (публичный DoruTJ).
- Изоляция: shared DB + обязательный `chain_id`-скоуп на уровне репозиториев + guard, запрещающий
  запрос без резолва тенанта. **Обязателен тест на утечку данных между тенантами.**
- Брендинг (палитра, лого, домен, telegram-бот, мерчант-креды банка) — в `tenant_settings`,
  применяется на фронте через CSS-переменные, редактируется в `apps/admin` без деплоя.
- Деньги тенанта идут на его мерчант-аккаунт напрямую (DoruTJ не является посредником для White-Label).

### 3.5 Отклонения от буквы ТЗ (утверждены архитектором, оформляются как ADR)

| № | ТЗ | Реализация | Причина |
|---|---|---|---|
| 1 | Elasticsearch 8 | **PostgreSQL FTS** (tsvector + pg_trgm + unaccent) как основной драйвер; ES — опциональный адаптер за тем же интерфейсом | Каталог ~10k SKU. PG FTS даёт нечёткий поиск (триграммы ≈ расстояние Левенштейна), морфологию ru, и убирает JVM-зависимость на ~1 ГБ RAM. Продукт запускается на ноутбуке и на дешёвом VPS. Миграция на ES = смена одной ENV. |
| 2 | RabbitMQ | **BullMQ поверх Redis** (Redis всё равно нужен для кэша/OTP) | Минус один инфраструктурный сервис. Из коробки: retry с backoff, DLQ, rate limiting, приоритеты, UI-мониторинг, идемпотентные job-id. Целевые 5,000 событий/сек достигаются пакетированием выгрузок. |
| 3 | Kong API Gateway | **Nginx** + guard'ы уровня Nest (rate-limit, auth, tenant) | Kong не даёт выигрыша на текущем масштабе и усложняет локальный запуск. |
| 4 | Микросервисы | **Модульный монолит** + отдельный worker-процесс | Границы контекстов соблюдены (межмодульные вызовы только через публичные сервисные интерфейсы). Извлечение в отдельные сервисы — механическая операция. Резко снижает операционную сложность MVP. |
| 5 | Flutter (курьер / фармацевт) | **ОТКЛОНЕНИЕ СНЯТО — реализуем по букве ТЗ на Flutter.** SDK установлен и проверен архитектором (Flutter 3.47.1 stable, Dart 3.13.1). Приложения `apps/pharmacy_mobile` и `apps/courier_mobile` пишутся на Flutter. | Тулчейн подтверждён `flutter doctor`. Обязательно соблюдение §3.6 (API-first), чтобы клиент оставался заменяемым. |
| 6 | Реальные Alif / DC Next / Gemini / Whisper | Провайдеры за интерфейсом, **Mock по умолчанию** | Нет продовых контрактов и ключей. Реальные адаптеры написаны по публичным спецификациям и включаются одной ENV. |

### 3.6 Правило переносимости клиентов (API-first) — ОБЯЗАТЕЛЬНО

Мобильные клиенты (терминал фармацевта, курьер) должны быть заменяемы БЕЗ единой правки в backend.
Поэтому:

1. **Ноль бизнес-логики в клиенте.** Расчёт цен, комиссий, SLA, валидация срока годности, переходы
   статусов заказа, генерация и проверка OTP вручения — только на сервере. Клиент — тонкий:
   рисует состояние и отправляет команды.
2. **Единственный контракт — REST/JSON + WebSocket**, описанный OpenAPI 3.1. Спека генерируется
   автоматически (`/api/docs/json`) и коммитится в `docs/api/openapi.json` на каждом релизе.
   Именно из неё Flutter-клиент генерирует свои модели (`openapi-generator` / `dart-mappable`).
3. **Никаких web-специфичных механизмов в контракте**: без cookie-сессий (только Bearer JWT),
   без server-rendered HTML, без зависимости от `Origin`, без form-data там, где хватает JSON.
   Загрузка файлов — `multipart/form-data` (поддерживается Flutter `http`/`dio` без плясок).
4. **Реалтайм — единый канал** `WS /api/v1/realtime` с JWT в первом кадре и событиями
   (`order.created`, `order.status_changed`, `courier.assigned`, ...). Никаких web-only SSE-хаков.
5. **Все справочники и enum'ы приходят с сервера** (`GET /api/v1/meta`), клиент их не хардкодит.
6. **Локализация**: словари `tj/ru/en` отдаются сервером (`GET /api/v1/i18n/:locale`), поэтому
   Flutter и React используют ОДИН источник строк.
7. Эпики «Терминал фармацевта» и «Курьер» в трекере оформляются как **клиент-агностичные**:
   отдельно тикеты API-контракта (не меняются при смене клиента) и отдельно тикеты реализации UI.

**Следствие для планирования**: смена PWA → Flutter затрагивает только тикеты слоя UI.
Backend, контракты, тесты API и E2E-сценарии на уровне API остаются в силе.

## 4. Роли и процесс (жёсткий конвейер)

```
Research → Analysis (SRS) → Tech Lead (тикеты) → Development → QA → Code Review → Architect Gate
```

- Между КАЖДЫМ переходом — приёмка оркестратором. Без приёмки этап не передаётся дальше.
- QA возвращает дефекты разработчикам циклом, пока дефектов нет.
- Review возвращает замечания разработчикам циклом, пока замечаний нет.
- Финальная ручная приёмка архитектором: сборка, запуск, прогон сценариев, проверка UI.

## 5. Инженерные стандарты (обязательны для всех разработчиков)

> **Базовый документ: [`docs/02-CLEAN-ARCHITECTURE-AND-CODE.md`](02-CLEAN-ARCHITECTURE-AND-CODE.md)** —
> чистая архитектура (слои domain/application/infrastructure/presentation, Правило Зависимостей,
> порты и адаптеры, границы контекстов) и Clean Code (измеримые пороги C1–C18).
> Он ОБЯЗАТЕЛЕН к исполнению и проверяется автоматически (`pnpm arch:check`, ESLint как `error`,
> пороги покрытия). Нарушение = блокирующее замечание ревью, тикет возвращается в разработку.
> Ниже — дополняющие правила уровня продукта.

- **TypeScript strict**: `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`.
  `any` запрещён (только с `// eslint-disable-next-line` и обоснованием в комментарии).
- **Валидация**: весь внешний ввод — через Zod-схемы из `packages/contracts`. DTO выводятся из Zod (`z.infer`).
- **Ошибки**: единый формат `{ error: { code, message, details? } }`; коды — enum в `packages/contracts`.
- **Логи**: pino, структурные, с `requestId` и `tenantId`. `console.log` в продуктовом коде = дефект.
- **Безопасность**: helmet, CORS whitelist, rate-limit, argon2 для секретов/API-ключей,
  JWT (access 15 мин / refresh 30 дней, ротация refresh), RBAC guard по роли,
  идемпотентность вебхуков, HMAC-подпись вебхуков банка,
  **категорический запрет** на изменение статуса оплаты чем-либо кроме серверного вебхука.
- **Деньги**: хранение `NUMERIC(10,2)`, вся арифметика — в целых дирамах (`int`, 1 TJS = 100 дирам).
  Float-вычисления денег = дефект.
- **Схема БД**: таблицы, ENUM'ы и поля из §II.2 ТЗ реализуются 1:1 (имена сохраняются); расширения допускаются.
- **i18n**: ВСЕ пользовательские строки — через словари `tj` / `ru` / `en`. Хардкод строки = дефект.
  Язык по умолчанию — `tj`; переключатель в шапке.
- **Тесты**: каждый модуль — unit-тесты бизнес-логики + интеграционные на HTTP-контракт.
- **Коммиты**: Conventional Commits со ссылкой на тикет — `feat(orders): add escrow capture (DTJ-042)`.
- **Доступность**: WCAG 2.1 AA — контраст ≥4.5:1, видимый фокус, aria-атрибуты, клавиатурная навигация.

## 7. Нефункциональные требования

- **Производительность**: p95 API < 300 мс на каталог/поиск; нагрузочный сценарий k6 в `tests/load`.
- **Пропускная способность**: приём выгрузок от 500+ аптек асинхронно, батчами, без блокировки БД.
- **Доступность**: WCAG 2.1 AA.
- **Мобильный трафик первичен**: бюджет JS первого экрана Customer Web ≤ 250 KB gzip.
- **Отказоустойчивость**: падение внешнего провайдера не роняет систему (circuit breaker + деградация).
- **Наблюдаемость**: `/health`, `/ready`, структурные логи, метрики очередей.
