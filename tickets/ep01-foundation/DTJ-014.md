## Задача

`users` — единая таблица идентичности для всех 6 ролей (не разделена по ролям на уровне схемы,
`SRS-API-017`), фундамент, на котором строится КАЖДЫЙ следующий эпик, где действует человек:
`orders.customer_id`, `pharmacy_inventory` через `pharmacist`, `delivery_assignments` через `courier`.
Без этой таблицы OTP verify (DTJ-024 того же эпика) не может создать пользователя при первом входе.

## Технический контекст

`SRS-API-017`: `users.tenant_id NOT NULL`, `UNIQUE(tenant_id, phone_number)` — один номер телефона
может иметь НЕЗАВИСИМЫЕ аккаунты в разных тенантах (изоляция White-Label). Персонал несёт
`pharmacy_id`/`chain_id`, `super_admin` — `tenant_id = NULL`. `SRS-DB-004`: `users` — с `deleted_at`
(право на удаление ПДн, soft delete). `SRS-DB-001`: PK — `gen_random_uuid()` как фолбэк уровня БД,
прикладной код передаёт UUID v7 явно через `IdGeneratorPort` (DTJ-006).

**Отложенные внешние ключи.** По `11-database-schema.md` DDL, `users.tenant_id REFERENCES tenants(id)`,
`users.pharmacy_id REFERENCES pharmacies(id)`, `users.chain_id REFERENCES pharmacy_chains(id)`. Ни
`tenants` (владелец схемы — EP-02, `tickets/00-EPICS.md`), ни `pharmacies`/`pharmacy_chains`
(владелец — EP-03) не существуют на момент этого тикета (EP-01 — первый эпик, ничего не блокирует по
графу зависимостей `tickets/00-EPICS.md`). Решение: колонки заводятся как `uuid`, **БЕЗ**
`.references(...)` в Drizzle-схеме этого тикета; ограничение внешнего ключа добавляется ОТДЕЛЬНОЙ
эволюционной миграцией, когда соответствующая таблица появится (аналог уже принятого архитектором
паттерна `0015_deferred_fks.sql` в `11-database-schema.md` §«Порядок миграций» — «отложенные FK» это
штатная, а не изобретённая здесь практика проекта). Ответственность добавить `ALTER TABLE users ADD
CONSTRAINT ... FOREIGN KEY` — у тикета, который создаёт целевую таблицу (EP-02 для `tenant_id`, EP-03
для `pharmacy_id`/`chain_id`), не у этого тикета.

## Что сделать

1. `users.schema.ts`:
   ```typescript
   export const users = pgTable('users', {
     id: uuid('id').primaryKey().defaultRandom(),
     tenantId: uuid('tenant_id').notNull(), // FK → tenants(id) добавляется EP-02, см. «Технический контекст»
     phoneNumber: varchar('phone_number', { length: 20 }).notNull(),
     role: userRoleEnum('role').notNull().default('customer'),
     fullName: varchar('full_name', { length: 255 }),
     pharmacyId: uuid('pharmacy_id'), // FK → pharmacies(id) добавляется EP-03
     chainId: uuid('chain_id'), // FK → pharmacy_chains(id) добавляется EP-03
     telegramChatId: bigint('telegram_chat_id', { mode: 'bigint' }),
     preferredLocale: varchar('preferred_locale', { length: 5 }).notNull().default('tj'),
     isActive: boolean('is_active').notNull().default(true),
     createdAt: timestamp('created_at', { withTimezone: true }).defaultNow(),
     deletedAt: timestamp('deleted_at', { withTimezone: true }),
   }, (table) => ({
     uniquePhonePerTenant: unique('unique_phone_per_tenant').on(table.tenantId, table.phoneNumber),
   }));
   ```
   Комментарий над таблицей в файле — дословно переносит обоснование «единая таблица для всех ролей,
   различие в guard/policy application-слоя» из `11-database-schema.md` COMMENT ON TABLE.
2. `user-addresses.schema.ts`: `user_addresses` 1:1 по DDL `11-database-schema.md` (`user_id`
   REFERENCES `users.id` ON DELETE CASCADE — этот FK НЕ отложен, `users` уже существует в этом же
   тикете; `address_text`, `landmark_text`, `landmark_photo_url`, `entrance`/`floor`/`apartment`,
   `latitude NUMERIC(10,8)`/`longitude NUMERIC(11,8)`, `is_default`, `created_at`).
3. `apps/api/migrations/0003_users_base.sql` — сгенерировано `drizzle-kit generate` из шагов 1-2.
4. Репозиторный миксин soft-delete (`infrastructure/base/soft-deletable.repository.ts`,
   `SRS-DB-004`) — НЕ входит в этот тикет (пока нет ни одного конкретного репозитория `users`, который
   бы его использовал; создание абстракции «на будущее» без второго потребителя — запах,
   `02-CLEAN-ARCHITECTURE-AND-CODE.md` C15). Первый конкретный `UsersRepository` (DTJ-024/DTJ-022) сам
   заведёт фильтр `WHERE deleted_at IS NULL`, миксин выделяется при появлении ВТОРОГО потребителя.

## Критерии приёмки

1. **Given** применена `0003_users_base.sql`, **When** `INSERT INTO users (tenant_id, phone_number)
   VALUES (:sameTenantId, '+992901234567')` дважды подряд для одного `tenant_id`, **Then** второй
   `INSERT` падает с нарушением `unique_phone_per_tenant`.
2. **Given** тот же номер телефона, **When** `INSERT` с ДРУГИМ `tenant_id`, **Then** успешно (изоляция
   тенантов на уровне constraint, `SRS-API-017`).
3. **Негативный:** **Given** `INSERT INTO users` без `tenant_id`, **When** выполнен, **Then** падает
   (`NOT NULL` constraint) — БД отклоняет запись без резолва тенанта на уровне схемы, не только на
   уровне application-guard'а (второй рубеж защиты, дублирует будущий `TenantScopeGuard` EP-02).

## Тест-план

- Integration: `unique_phone_per_tenant` — дубль в одном тенанте падает, в разных — проходит;
  `NOT NULL` на `tenant_id`; дефолт `role='customer'`, `preferred_locale='tj'`, `is_active=true`.
- Integration `user_addresses`: `ON DELETE CASCADE` — удаление `users`-строки каскадно удаляет её
  адреса.
- Coverage — неприменимо (чистая схема без прикладной логики в этом тикете).

## Риски и подводные камни

- **Главный риск тикета.** Отложенные FK — осознанное инженерное решение ЭТОГО тикета, не буквальная
  калька DDL `11-database-schema.md` (там `tenant_id UUID NOT NULL REFERENCES tenants(id)` дан как
  единая схема, будто все таблицы создаются одновременно). Причина расхождения: `tickets/00-EPICS.md`
  жёстко разводит владение файлами по эпикам и волнам (`tenants.ts` — EP-02, `pharmacies.ts`/
  `pharmacy_chains.ts` — EP-03), а EP-01 — первый эпик без зависимостей. Если EP-02/EP-03 НЕ добавят
  `ALTER TABLE users ADD CONSTRAINT` при реализации своих тикетов, `users.tenant_id`/`pharmacy_id`/
  `chain_id` навсегда останутся без реальной ссылочной целостности на уровне БД (только на уровне
  приложения) — это нужно явно передать в тикеты EP-02/EP-03 (не в моей зоне редактирования, но
  зафиксировано здесь как явное ожидание для координации тимлидов).
- `telegram_chat_id BIGINT` — колонка присутствует по DDL `11-database-schema.md` (используется позже
  уведомлениями EP-16), но реальная логика её заполнения (`/start` TWA) — вне зоны этого тикета,
  колонка просто существует и допускает `NULL`.
