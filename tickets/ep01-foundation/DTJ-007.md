## Задача

Каждый заказ, ledger-запись, комиссия и выплата в системе оперирует деньгами исключительно как
целыми дирамами (`Charter §5`, D-02) — ни один модуль (orders, payments, billing, delivery) не имеет
права делать арифметику в `NUMERIC`/`float`. `Money` — единственный VO, через который проходит КАЖДАЯ
денежная операция платформы; без него ни один следующий эпик (EP-09 Корзина, EP-10 Оплата) не может
начать домен заказа.

## Технический контекст

`SRS-DB-003`: колонки `tz.log` (`price_tjs`, `items_total_tjs`, ...) — `NUMERIC(10,2)`; НОВЫЕ денежные
поля (комиссии, ledger) — `BIGINT` дирамов. Конвертация `NUMERIC↔BIGINT` — ИСКЛЮЧИТЕЛЬНО в
`infrastructure`-мапперах через `Money.fromDbDecimalTjs()`/`money.toDbDecimalTjs()`; `domain`/
`application` НИКОГДА не видят `NUMERIC`. Место файла — `shared-kernel/domain`, не `modules/orders/domain`
(см. обоснование в DTJ-006 «Технический контекст» — Money используется множеством модулей).

## Что сделать

1. `money.vo.ts`: класс `Money` (immutable, приватный конструктор):
   - `Money.fromDiram(n: bigint, currency: Currency = 'TJS'): Money` — `n >= 0n`, иначе
     `InvalidMoneyError` (SRS-DOM-067: отрицательная сумма конструктором запрещена).
   - `Money.fromDbDecimalTjs(raw: string, currency: Currency = 'TJS'): Money` — парсинг строки вида
     `"123.45"` РАЗБИЕНИЕМ на целую/дробную часть (`split('.')`, `BigInt(integerPart) * 100n +
     BigInt(fractionalPart.padEnd(2, '0'))`), БЕЗ `parseFloat`/`Number()` (SRS-DOM-065).
   - `money.toDbDecimalTjs(): string` — обратное форматирование, целочисленное деление/остаток
     (`diram / 100n`, `diram % 100n`), без float, ровно 2 знака дробной части.
   - `money.add(other: Money): Money` / `money.subtract(other: Money): Money` — требуют одинаковой
     `currency`, иначе `CurrencyMismatchError`; `subtract`, дающий отрицательный результат, тоже
     бросает `CurrencyMismatchError`? — НЕТ: бросает отдельно `InvalidMoneyError` (результат
     конструктора `fromDiram` с `n < 0n` недопустим) — реализовать как явную проверку ДО вызова
     `fromDiram` внутри `subtract`, с понятным сообщением «результат вычитания отрицателен».
   - `money.multiplyByQuantity(qty: number): Money` — `qty` целое `> 0`, иначе `InvalidMoneyError`.
   - `money.allocate(ratios: readonly number[]): Money[]` — метод наибольшего остатка (largest
     remainder method): базовое распределение `floor(total * ratio / sumRatios)` на каждую долю, затем
     остаток `total - Σ(базовые доли)` дораспределяется по одному дираму долям с наибольшим дробным
     остатком (детерминированный тай-брейк — по индексу массива при равенстве); инвариант
     `Σ(allocate(ratios)) === original` — обязателен, покрыт тестом на нескольких неровных случаях.
   - `money.isNegative()`/`isZero()`/`isPositive()`, `money.equals(other)`/`isGreaterThan(other)`/
     `isLessThanOrEqual(other)` — все сравнения бросают `CurrencyMismatchError` при разных валютах
     (SRS-DOM-068).
   - Публичный API НЕ содержит `Money.fromDiram(n: number)` (перегрузки с `number` не существует —
     проверяется на уровне типов, TypeScript не даст вызвать с `number` без явного `BigInt(...)`).
2. `currency-mismatch.error.ts` / `invalid-money.error.ts`: расширяют `DomainError` из
   `packages/contracts` (см. DTJ-005), фиксированный `ErrorCode` (сверить точное соответствие — в
   каталоге `packages/contracts/src/errors.ts` нет отдельного кода `CURRENCY_MISMATCH`/`INVALID_MONEY`
   в явном виде из прочитанных SRS-таблиц; использовать `VALIDATION_ERROR` как ближайший существующий
   код с `details.reason` — см. «Риски»).

## Критерии приёмки

1. **Given** `Money.fromDbDecimalTjs("99.90")`, **When** `.toDbDecimalTjs()`, **Then** возвращается
   ровно `"99.90"` (round-trip без потери точности).
2. **Given** `Money.fromDiram(1000n).allocate([1, 1, 1])` (раздел 10.00 TJS на 3 равные доли), **When**
   суммируются результаты, **Then** сумма равна `1000n` (largest remainder гарантирует отсутствие
   потери дирама на округлении: `334 + 333 + 333 = 1000`).
3. **Негативный:** **Given** `Money.fromDiram(500n, 'TJS').add(Money.fromDiram(100n, 'USD'))`, **When**
   вызов, **Then** бросается `CurrencyMismatchError`, значение первого `Money` не изменено (иммутабельность).

## Тест-план

- Unit: round-trip `fromDbDecimalTjs`/`toDbDecimalTjs` на граничных значениях (`"0.00"`, `"0.01"`,
  `"99999999.99"` — максимум `NUMERIC(10,2)`).
- Unit: `add`/`subtract` — одинаковая валюта проходит, разная — `CurrencyMismatchError`; `subtract`,
  дающий отрицательный результат, — `InvalidMoneyError`.
- Unit: `multiplyByQuantity` — `qty <= 0` и `qty` нецелое — `InvalidMoneyError`.
- Unit: `allocate` — минимум 3 кейса с неровным делением (`allocate([1,1,1])` на суммы, не кратные 3;
  `allocate([70,30])` под сценарий доли курьера D-21), проверка инварианта суммы на каждом.
- Unit: сравнения (`equals`/`isGreaterThan`/`isLessThanOrEqual`) — корректность + `CurrencyMismatchError`
  при разных валютах.
- Порог покрытия `domain/` — ≥90% (`02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.4) — реалистично 100% для
  чистого VO без внешних зависимостей.

## Риски и подводные камни

- `packages/contracts/src/errors.ts` (DTJ-005) не содержит явного кода `CURRENCY_MISMATCH`/
  `INVALID_MONEY` в прочитанном реестре SRS — эти ошибки в проде маловероятны (программные ошибки
  вызывающего кода, не пользовательский ввод), поэтому используется общий `VALIDATION_ERROR` с
  `details.reason`, а не заводится новый специфичный код без опоры на SRS (инструкция «не выдумывай
  SRS-* идентификаторы» — это НЕ SRS-ID, а `ErrorCode`, но тот же принцип «не изобретать» применяется
  по духу задачи). Если ревью архитектора сочтёт нужным отдельный код — завести правкой
  `packages/contracts/src/errors.ts` отдельным PR, не блокируя этот тикет.
- `allocate()` с равными остатками (тай-брейк) — детерминированность по индексу массива важна для
  воспроизводимости тестов; задокументировать явно в JSDoc метода, чтобы будущий рефакторинг не
  поменял порядок тай-брейка незаметно.
