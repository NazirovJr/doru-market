## Задача

`apps/worker` — отдельный процесс (не HTTP-сервис) для фоновой обработки: релей `outbox` → очередь
доменных событий, будущие джобы синхронизации 1С, OCR, уведомлений. Charter §3.5 фиксирует
«микросервисы → модульный монолит + отдельный worker-процесс» как осознанное архитектурное
отклонение — этот тикет создаёт сам процесс и первую реальную джобу (`OutboxRelayWorker`), которая
нужна КАЖДОМУ последующему модулю, публикующему доменные события (`SRS-DOM-151/152`).

## Технический контекст

`01-TECH-BASELINE.md`: `bullmq ^6.3.0`, `ioredis ^5`, тот же набор `@nestjs/*` что у `apps/api`, но без
`platform-fastify` (worker не обслуживает HTTP-трафик клиентов, `SRS-NFR-037`) — только служебный
health-порт. `SRS-DOM-151`: доменное событие пишется в `outbox` в ОДНОЙ транзакции с изменением
агрегата; `SRS-DOM-152`: `OutboxRelayWorker`, упавший после публикации в очередь, но до
`mark_processed()`, обязан переопубликовать при рестарте (at-least-once) — каждый будущий потребитель
обязан быть идемпотентен по `event_id` (таблица `processed_events` из DTJ-016 того же эпика).

Таблицы `outbox`/`processed_events` создаёт другой тикет этого эпика (DTJ-016) — здесь только
СКЕЛЕТ джобы: подключение к очереди `domain-events`, чтение `outbox` через порт (реализация репозитория
появится вместе с DTJ-016, здесь — интерфейс + заглушка `NoopOutboxReaderAdapter` для проверки, что
джоба вообще запускается и работает по расписанию). Полноценная бизнес-логика чтения/публикации —
логическое продолжение DTJ-016 (том же эпике), не блокирует этот тикет.

## Что сделать

1. `apps/worker/package.json` + `tsconfig.json` — по аналогии с `apps/api` (DTJ-001), без
   `@nestjs/platform-fastify`/`@fastify/*`.
2. `apps/worker/src/main.ts`: `NestFactory.createApplicationContext(AppModule)` (не HTTP-приложение) +
   отдельный минимальный Fastify/`node:http`-сервер ТОЛЬКО для `GET /health` на
   `WORKER_HEALTH_PORT` (ENV, дефолт `3001`) — проверяет соединение с Redis/BullMQ (`SRS-NFR-037`:
   «`apps/worker` несёт свой `GET /health`... проверяет соединение с BullMQ/Redis»).
3. `apps/worker/src/config/config.module.ts` + `env.schema.ts`: `REDIS_URL`, `DATABASE_URL`,
   `WORKER_HEALTH_PORT`, `LOG_LEVEL` — тот же паттерн валидации ENV на старте, что в DTJ-001.
4. `apps/worker/src/queues/queue.constants.ts`: именованные константы очередей BullMQ —
   `QUEUE_NAMES.DOMAIN_EVENTS = 'domain-events'` (для outbox-релея), с заделом-комментарием на будущие
   очереди других эпиков (`inventory-sync`, `prescription-ocr`, `notifications` — НЕ создаются здесь,
   только упомянуты, чтобы имя константы не изобреталось заново каждым эпиком отдельно).
5. `apps/worker/src/jobs/outbox-relay/outbox-relay.processor.ts`: BullMQ `Worker` на
   scheduled-повторение (`repeat: { every: OUTBOX_POLL_INTERVAL_MS }`, ASSUMPTION 2000) — читает через
   порт `OutboxReaderPort.readPending(limit)` (интерфейс, реализация — DTJ-016), публикует каждую
   строку в очередь `domain-events` (`queue.add(event.eventType, event.payload, { jobId: event.id })`
   — `jobId = event.id` даёт BullMQ встроенную дедупликацию на уровне очереди как дополнительный
   рубеж поверх `processed_events`), помечает через `OutboxReaderPort.markPublished(id)`.
6. `apps/worker/src/jobs/outbox-relay/noop-outbox-reader.adapter.ts`: временная заглушка
   `OutboxReaderPort` (`readPending` возвращает `[]`) — используется до готовности DTJ-016; удаляется/
   заменяется в том тикете.
7. `apps/worker/Dockerfile` + `docker-entrypoint.sh` — по аналогии с `apps/api`, БЕЗ шага
   `db:migrate` (worker не владелец миграций, только читает БД).
8. `apps/worker/.env.example`.

## Критерии приёмки

1. **Given** `apps/worker` запущен с поднятым Redis, **When** `GET /health` на
   `WORKER_HEALTH_PORT`, **Then** `200`.
2. **Given** Redis недоступен, **When** `GET /health`, **Then** `503`.
3. **Given** `OutboxReaderPort` — заглушка `NoopOutboxReaderAdapter`, **When** процесс работает
   `OUTBOX_POLL_INTERVAL_MS`, **Then** джоба выполняется на расписании без падения процесса (лог
   подтверждает тик), даже когда `readPending()` всегда возвращает пустой массив.
4. **Негативный:** **Given** `REDIS_URL` не задан, **When** процесс стартует, **Then** завершается с
   ненулевым кодом до попытки подключения к очереди.

## Риски и подводные камни

- `jobId = event.id` для дедупликации BullMQ — не полная замена `processed_events` (BullMQ хранит job
  ограниченное время / до `removeOnComplete`), а дополнительный рубеж; не полагаться на него как на
  единственную гарантию идемпотентности — основная гарантия по-прежнему `processed_events` на стороне
  каждого КОНКРЕТНОГО потребителя (ответственность потребителя, не этого тикета).
- Пока `outbox`/`processed_events` не существуют (DTJ-016 в процессе параллельно), джоба работает на
  заглушке — при мерже DTJ-016 обязательно заменить `NoopOutboxReaderAdapter` на реальный адаптер и
  удалить заглушку файлом, не оставлять мёртвый код (C8).
- Файл `apps/worker/package.json` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
