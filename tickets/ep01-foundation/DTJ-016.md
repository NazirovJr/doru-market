## Задача

`outbox` — механизм transactional outbox: КАЖДЫЙ будущий модуль, порождающий доменное событие
(`OrderPaidEvent`, `PharmacySuspendedEvent`, ...), обязан писать строку в эту таблицу В ТОЙ ЖЕ
транзакции, что и изменение агрегата (`SRS-DOM-151`). Без реальной таблицы `OutboxRelayWorker`
(скелет — DTJ-002 этого же эпика) работает только на заглушке `NoopOutboxReaderAdapter`. Этот тикет
завершает пару: создаёт таблицы И подключает к worker'у реальный адаптер, удаляя заглушку.

## Технический контекст

`SRS-DOM-151`: строка `outbox` добавляется в тот же `unitOfWork`, что и изменение состояния агрегата.
`SRS-DOM-152`: at-least-once — `OutboxRelayWorker`, упавший после публикации в очередь, но до
`mark_processed()`, обязан переопубликовать при рестарте; КАЖДЫЙ потребитель обязан быть идемпотентен
по `event_id` через `processed_events(consumer_name, event_id)` (составной PK — конфликт вставки
значит «уже обработано»). `SRS-DB-024`: `outbox`/`audit_log` — append-only на уровне ПРИВИЛЕГИЙ роли
БД (`app_role` получает `GRANT INSERT, SELECT` без `UPDATE, DELETE`) — этот тикет создаёт таблицы;
сама настройка роли БД (`0017_triggers_and_checks.sql`/grant-скрипт) — по расписанию миграций
`11-database-schema.md`, зона общей инфраструктуры БД (не блокирует создание таблиц здесь, но
`UPDATE status='published'` со стороны `OutboxRelayWorker` обязан оставаться легальным — `GRANT
INSERT, SELECT` без `UPDATE` касается ТОЛЬКО `escrow_ledger`/`audit_log` по формулировке `SRS-DB-024`,
`outbox` явно допускает обновление `status`/`published_at` тем же `app_role`, иначе релей не сможет
пометить событие опубликованным — уточнить этот нюанс явно в реализации GRANT, зона EP-19/DBA-скрипта,
не блокирует этот тикет).

## Что сделать

1. `outbox.schema.ts`: `id uuid PK default gen_random_uuid()`, `eventType varchar(100) NOT NULL`,
   `aggregateType varchar(50) NOT NULL`, `aggregateId uuid NOT NULL`, `payload jsonb NOT NULL`,
   `tenantId uuid` (БЕЗ `.references(...)` — тот же паттерн отложенного FK, что DTJ-014, `tenants`
   ещё не существует), `status outboxStatusEnum NOT NULL default 'pending'`, `createdAt timestamptz
   NOT NULL default now()`, `publishedAt timestamptz`, `publishAttempts int NOT NULL default 0`.
   `outbox_status` enum (`'pending'|'published'|'failed'`) добавляется в `enums.schema.ts`
   (DTJ-013) этим же тикетом — ОДНА строка в существующий файл, по правилу «дописывать, не плодить».
2. `processed-events.schema.ts`: `consumerName varchar(100) NOT NULL`, `eventId uuid NOT NULL`,
   `processedAt timestamptz NOT NULL default now()`, составной `primaryKey({ columns: [consumerName,
   eventId] })` (не отдельный `id` — PK-конфликт при повторной вставке И ЕСТЬ механизм идемпотентности,
   `SRS-DOM-152`).
3. `apps/api/migrations/0005_outbox.sql` — из шагов 1-2 (+ добавленное значение enum в `0002_enums.sql`
   диффится как ОТДЕЛЬНАЯ строка в этой же новой миграции, если `outbox_status` не существовал в
   `0002` — `drizzle-kit generate` сам определит, новый ли это `CREATE TYPE` или требуется `ALTER TYPE`;
   на момент этого тикета `outbox_status` ещё не создавался — это просто новый `CREATE TYPE` внутри
   `0005`, не `ALTER TYPE ADD VALUE`, поэтому `SRS-DB-009` про транзакционные ограничения ADD VALUE
   здесь НЕ применяется).
4. `apps/worker/src/jobs/outbox-relay/drizzle-outbox-reader.adapter.ts`: реальный
   `OutboxReaderPort` (порт объявлен в DTJ-002) — `readPending(limit)`:
   `SELECT * FROM outbox WHERE status = 'pending' ORDER BY created_at LIMIT :limit` (никогда
   `SELECT *` без `ORDER BY`/`LIMIT` — предсказуемый порядок публикации); `markPublished(id)`:
   `UPDATE outbox SET status = 'published', published_at = now() WHERE id = :id`; на ошибке публикации
   в очередь (BullMQ `queue.add` бросил) — `UPDATE outbox SET publish_attempts = publish_attempts + 1`
   (НЕ `status='failed'` автоматически при первой неудаче — оставить `pending` для следующей попытки
   на следующем тике; `status='failed'` резервируется для будущего ручного разбора после N попыток,
   порог `publishAttempts` не вводится этим тикетом как автоматическая логика — только поле).
5. `apps/worker/src/jobs/outbox-relay/outbox-relay.processor.ts` (правка существующего файла из
   DTJ-002): заменить `NoopOutboxReaderAdapter` на `DrizzleOutboxReaderAdapter` в DI-конфигурации,
   удалить файл заглушки (C8 — мёртвый код).

## Критерии приёмки

1. **Given** строка `outbox` со `status='pending'`, **When** `OutboxRelayWorker` выполняет тик,
   **Then** событие опубликовано в очередь `domain-events` с `jobId = outbox.id`, и `outbox.status`
   становится `'published'` с заполненным `published_at`.
2. **Given** тот же `event_id` обработан потребителем `orders.on-delivered` (запись есть в
   `processed_events`), **When** это же событие приходит повторно (симуляция at-least-once), **Then**
   повторная вставка в `processed_events` с тем же `(consumer_name, event_id)` падает на PK-конфликте
   — потребитель трактует это как «уже обработано», не выполняет бизнес-логику повторно.
3. **Негативный:** **Given** BullMQ временно недоступен во время тика релея, **When** `readPending`
   возвращает строки, но `queue.add` бросает, **Then** `outbox.status` остаётся `'pending'` (НЕ
   помечается `published` ошибочно), `publish_attempts` увеличивается, следующий тик повторяет
   попытку.

## Тест-план

- Integration (реальный Postgres): `readPending` — сортировка по `created_at`, `LIMIT` соблюдается;
  `markPublished` — корректно проставляет оба поля; составной PK `processed_events` — конфликт при
  дубле.
- Integration (Postgres + BullMQ/Redis): полный цикл «pending → published» через реальный
  `OutboxRelayWorker` тик; сценарий сбоя публикации (приёмка 3) — мок BullMQ, бросающий исключение.
- Coverage `infrastructure/` — ≥70%.

## Риски и подводные камни

- `GRANT INSERT, SELECT, UPDATE` (не только `INSERT, SELECT`) на `outbox` для `app_role` — нужен, чтобы
  релей мог проставлять `status`/`published_at`. Формулировка `SRS-DB-024` дословно про «append-only
  на уровне привилегий» касается `escrow_ledger`/`audit_log`, но список «append-only» таблиц в
  `SRS-DB-004` отдельно перечисляет `otp_codes`/`refresh_tokens`(→`auth_sessions`)/`cart`/
  `inventory_sync_batches`/`outbox` как «операционные/очередные — hard delete по TTL, БЕЗ append-only
  ограничения привилегий» — то есть `outbox` НЕ входит в список append-only-по-привилегиям, `UPDATE`
  легален. Явно зафиксировано здесь, чтобы владелец фактического GRANT-скрипта (инфраструктура БД,
  зона, close to EP-19) не заблокировал `UPDATE` по ошибочной аналогии с `audit_log`.
- Отсутствие автоматической эскалации `publishAttempts → 'failed'` (шаг 4) — сознательно оставлено
  вне этого тикета (нет ни одного реального потребителя `outbox` ещё, некому проверять поведение
  «застрявшего» события за пределами unit-теста); если после нескольких волн окажется нужна,
  заводится отдельным тикетом эпика, ответственного за наблюдаемость (EP-19), не задним числом
  расширяется здесь без основания.
