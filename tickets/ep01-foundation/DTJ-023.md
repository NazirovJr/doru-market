## Задача

Шаг 1 OTP-логина — первый реальный продуктовый эндпоинт всего backend'а: без него ни один человек
(клиент, фармацевт, курьер) не может войти в систему. `04-SCOPE-DECISION-PIVOT.md` R1-12 — «Auth: OTP
по телефону... `MockSmsProvider`» — обязательный критерий приёмки R1 п.5 («Работает без единого
внешнего API-ключа»).

## Технический контекст

`SRS-API-018`: ответ ВСЕГДА `202 { data: { otpRequestId, expiresInSeconds: 300 } }`, независимо от
того, существует ли `users` с этим телефоном (защита от перебора существующих номеров).
`SRS-API-019`: лимиты по `phone` (`OTP_REQUEST_COOLDOWN_SECONDS=60`, `OTP_REQUEST_MAX_PER_10MIN=3`,
`OTP_REQUEST_MAX_PER_DAY=10`) + вторичный по IP (`OTP_REQUEST_MAX_PER_IP_PER_HOUR=20`) — реализуются
через `@RateLimit(...)` (DTJ-020), СИСТЕМА нескольких одновременных лимитов на один эндпоинт требует
трёх отдельных guard-проверок (не один `@RateLimit`, т.к. окна и ключи разные — 60с/10мин/24ч по
`phone`, отдельно 1ч по IP) — реализовать явным чекером внутри use case через `RateLimitGuard`'а
Redis-примитивы напрямую (порт `RateLimitCheckerPort`, тонкая обёртка над теми же Redis INCR/EXPIRE
операциями DTJ-020, не дублирование логики). `SRS-API-020`: невалидный формат телефона →
`400 INVALID_PHONE_FORMAT` — ПРОВЕРЯЕТСЯ ДО применения rate-limit (не тратить лимит на заведомо
невалидный номер).

## Что сделать

1. `sms-provider.port.ts`: `interface SmsProviderPort { sendOtp(phone: PhoneNumber, code: string):
   Promise<void> }` (Charter §3.3 Provider Pattern).
2. `mock-sms-provider.adapter.ts`: `MockSmsProviderAdapter implements SmsProviderPort` — пишет код в
   pino-лог (`level: 'info'`, поле `otpCode` — ТОЛЬКО если `NODE_ENV !== 'production'`, иначе не
   логировать сам код даже в mock-режиме — dev/staging удобство, не продовый риск) и в отдельную
   dev-таблицу/поле, доступное тестам (переиспользовать `otp_codes.code_hash` косвенно недостаточно
   для e2e-теста, читающего код «как пользователь» — задокументировать явную dev-возможность:
   `MOCK_SMS_EXPOSE_CODE_IN_RESPONSE` ENV-флаг, который, если `true` И `NODE_ENV !== 'production'`,
   кладёт код В ЛОГ структурированно с `otpRequestId`, чтобы E2E-раннер (Playwright, EP-19) мог его
   прочитать без похода в БД напрямую).
3. `otp-codes.repository.ts`: `OtpCodesRepository` — `create(otpCode: OtpCode, subjectRef: string):
   Promise<{ id: string }>` (маппинг VO → строка `otp_codes`, DTJ-015), `findById(id)`, `update(id,
   otpCode)` (для DTJ-024, но метод заводится здесь как часть репозитория того же агрегата — не
   дублировать репозиторий в другом тикете).
4. `request-otp.dto.ts`: Zod-схема `{ phone: z.string() }` (валидация формата — делегируется
   `PhoneNumber.parse` внутри use case, не в Zod-регэкспе — единственный источник правила формата,
   DTJ-008).
5. `request-otp.use-case.ts`: `RequestOtpUseCase.execute({ phone: string; ipAddress: string,
   tenantId: string }): Promise<Result<{ otpRequestId: string; expiresInSeconds: number },
   InvalidPhoneNumberFormatError | OtpRequestRateLimitedError>>`:
   1. `PhoneNumber.parse(phone)` — невалиден → возврат ошибки НЕМЕДЛЕННО (шаг 2-4 не выполняются,
      `SRS-API-020`).
   2. Проверка трёх лимитов по `phone` + одного по IP через `RateLimitCheckerPort` — превышение
      ЛЮБОГО → `OtpRequestRateLimitedError` (маппится в `429 OTP_REQUEST_RATE_LIMITED` с
      `Retry-After`, DTJ-018/020).
   3. `OtpGeneratorPort.generate('login')` (DTJ-010) → сырой код → `codeHash = sha256(code +
      otpRequestId)` (порядок: `otpRequestId` генерируется ДО хеширования — `IdGeneratorPort`,
      DTJ-006 — используется как соль, `SRS-API-021`).
   4. `OtpCode.issue('login', codeHash, clock.now())` (DTJ-010) → `OtpCodesRepository.create(...,
      subjectRef=phone.value)`.
   5. `SmsProviderPort.sendOtp(phone, code)` — сырой код передаётся провайдеру ДО того, как забыт
      (use case держит его только в памяти этого вызова, не персистирует plaintext нигде).
   6. Возврат `{ otpRequestId, expiresInSeconds: 300 }` — ВСЕГДА успех на этом этапе (find-or-create
      `users` происходит только на `verify`, не здесь, `SRS-API-018`).
6. `otp-request.controller.ts`: `POST /api/v1/auth/otp/request`, `@Public()` (DTJ-022 — до входа
   пользователь не аутентифицирован), без `@Roles(...)`. Тело — `RequestOtpDto`. Ответ — `202`
   (не `200`/`201` — конвенция `SuccessEnvelope` из DTJ-018 обязана поддерживать произвольный
   HTTP-статус успеха, не только `200`, сверить при реализации `response.interceptor.ts`, что он не
   принудительно переписывает статус).

## Критерии приёмки

1. **Given** валидный номер `+992901234567`, **When** `POST /auth/otp/request`, **Then** `202
   { data: { otpRequestId: "<uuid>", expiresInSeconds: 300 } }`, ответ ОДИНАКОВ независимо от
   существования пользователя с этим номером в БД.
2. **Given** запрос с телефоном без кода страны (`"901234567"`), **When** `POST /auth/otp/request`,
   **Then** `400 INVALID_PHONE_FORMAT`, ни один Redis-счётчик лимита НЕ инкрементирован (проверяется
   явно — второй запрос с тем же невалидным номером НЕ получает `429`, а получает тот же `400`).
3. **Негативный:** **Given** 4-й запрос на один валидный номер за 10 минут (лимит
   `OTP_REQUEST_MAX_PER_10MIN=3`), **When** `POST /auth/otp/request`, **Then** `429
   OTP_REQUEST_RATE_LIMITED` с заголовком `Retry-After`, SMS НЕ отправлена (`MockSmsProviderAdapter`
   не вызван — проверяется мок-шпионом).

## Тест-план

- Unit `RequestOtpUseCase`: успешный путь; невалидный телефон (лимиты не тронуты); каждый из 4
  лимитов по отдельности превышен (cooldown/10мин/сутки по телефону, час по IP); проверка, что
  `codeHash`, персистированный в репозиторий, НЕ равен сырому коду, переданному `SmsProviderPort`.
- Integration: реальный HTTP-запрос через `apps/api` тестовый инстанс + реальный Redis для лимитов +
  реальная БД для `otp_codes` — happy path + rate-limit path.
- Порог покрытия `application/` — ≥90% (`02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.4); `presentation/` —
  ≥70%.

## Риски и подводные камни

- Четыре независимых счётчика лимита (3 по телефону + 1 по IP) на один эндпоинт — не покрываются
  единственным `@RateLimit(...)` декоратором DTJ-020 «из коробки» (тот рассчитан на один лимит на
  маршрут). Решение — отдельный `RateLimitCheckerPort`, переиспользующий Redis-примитивы DTJ-020, но
  вызываемый явно четыре раза внутри use case, а не декоративно. Если это будет казаться избыточным
  усложнением на code review — альтернатива (составной ключ на все 4 условия в одной Lua-скрипт
  транзакции Redis) технически чище, но не обязательна для R1 — задокументировать выбор в PR.
- `TenantId`, требуемый сигнатурой `execute()`, на момент этого тикета РЕЗОЛВИТСЯ временным способом
  (см. DTJ-022 «Риски» — полноценный `TenantResolutionMiddleware` ещё не существует, EP-02 позже).
  Controller этого тикета обязан передавать `tenantId` из ЛЮБОГО доступного источника контекста
  (временный дефолт на `neutral`, если ничего не резолвлено) — явно задокументировать это как
  временное поведение, заменяемое EP-02 без изменения сигнатуры use case.
