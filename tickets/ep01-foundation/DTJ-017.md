## Задача

`Idempotency-Key` обязателен для эндпоинтов с финансовым/операционным побочным эффектом
(`SRS-API-009`: checkout, загрузка рецепта, возвраты, разрешение споров, приём наличных, ротация
1С-ключа) — без этой таблицы ни один из них не может быть реализован по спецификации. Таблица нужна
уже в R1 (первый потребитель — `POST /orders` в EP-09, но интерсептор идемпотентности как общий
механизм — часть API-конвенций EP-01, DTJ-019 того же эпика).

## Технический контекст

`SRS-API-010` — прямая цитата, дающая полный состав колонок: «Хранение: таблица
`idempotency_keys(user_id, endpoint, key, request_hash, status, response_status, response_body,
created_at)`, TTL `IDEMPOTENCY_KEY_TTL_HOURS` (ASSUMPTION 24), `UNIQUE(user_id, endpoint, key)`».
Эта таблица ОТСУТСТВУЕТ в 45-табличном DDL `docs/spec/11-database-schema.md` (сверено построчно по
списку `CREATE TABLE`) — упоминается только в прозе `12-api-conventions-auth-tenancy.md`. Это тот же
класс пробела, что уже зафиксирован архитектором для `SRS-DOM-372/585/909`
(`docs/STATE-AND-RESUME-POINT.md` §2.2.2 п.2) — не выдуманное требование, а реальный текст SRS,
которому не хватает записи в реестре DDL. Решение: реализовать по прямой цитате `SRS-API-010`, без
додумывания сверх сказанного.

`SRS-API-076`: истечение `IDEMPOTENCY_KEY_TTL_HOURS` — фоновая job очистки удаляет запись, повторный
запрос с тем же ключом после истечения обрабатывается КАК НОВЫЙ (не ошибка) — сама job очистки НЕ
входит в этот тикет (нет владельца конкретного планировщика BullMQ cron ещё; заводится вместе с
DTJ-019, где интерсептор идемпотентности реально начинает писать/читать эту таблицу).

## Что сделать

1. `idempotency-keys.schema.ts`:
   ```typescript
   export const idempotencyKeys = pgTable('idempotency_keys', {
     id: uuid('id').primaryKey().defaultRandom(),
     userId: uuid('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
     endpoint: varchar('endpoint', { length: 255 }).notNull(), // напр. 'POST /api/v1/orders'
     key: uuid('key').notNull(), // клиентский Idempotency-Key, UUID v4 (SRS-API-009)
     requestHash: varchar('request_hash', { length: 64 }).notNull(), // sha256(body), hex
     status: idempotencyKeyStatusEnum('status').notNull().default('processing'), // 'processing'|'completed'
     responseStatus: integer('response_status'), // заполняется на завершении
     responseBody: jsonb('response_body'), // заполняется на завершении
     createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
   }, (table) => ({
     uniqueUserEndpointKey: unique('unique_user_endpoint_key').on(table.userId, table.endpoint, table.key),
   }));
   ```
   `idempotency_key_status` enum (`'processing'|'completed'`) — добавляется в `enums.schema.ts`
   (DTJ-013) этим же тикетом, одной строкой. Значение `'processing'` — обязательно как ОТДЕЛЬНОЕ от
   `'completed'` состояние: `SRS-API-010` описывает гонку «Given запрос с `K` ещё обрабатывается
   (конкурентный дубль), Then второй запрос немедленно получает `409`» — это различимо ТОЛЬКО если
   строка со `status='processing'` уже существует до завершения первого запроса (INSERT сразу при
   получении заголовка, UPDATE на завершение), а не создаётся постфактум.
2. `apps/api/migrations/0006_idempotency_keys.sql` — из шага 1.
3. Точечно добавить в `docs/spec/11-database-schema.md` запись о таблице `idempotency_keys` (новая
   таблица «45а», между существующими 45 и §«Индексы» — не переписывать нумерацию остальных таблиц)
   со ссылкой на `SRS-API-009/010` как источник — закрывает документационный пробел этим же PR.

## Критерии приёмки

1. **Given** строка `idempotency_keys` со `status='processing'` для `(userId=A, endpoint=E, key=K)`,
   **When** повторная попытка `INSERT` той же тройки, **Then** падает на `unique_user_endpoint_key`
   (это физический механизм, реализующий гонку из `SRS-API-010` — интерсептор, ловящий это нарушение
   constraint, трактует как `409 IDEMPOTENCY_KEY_CONFLICT`, сама логика перехвата — DTJ-019, не этот
   тикет).
2. **Given** запись со `status='completed'`, `responseStatus=201`, `responseBody={"data":{"id":"..."}}`,
   **When** прочитана, **Then** все поля читаются без потерь (JSON round-trip через `jsonb`).
3. **Негативный:** **Given** `requestHash` отсутствует (`NOT NULL` без значения), **When** `INSERT`,
   **Then** падает — таблица физически не допускает запись идемпотентности без хеша тела (нельзя
   сверить «то же тело» без него).

## Тест-план

- Integration: `unique_user_endpoint_key` — конфликт при дубле тройки, отсутствие конфликта при
  различии любого из трёх полей; `NOT NULL` на `request_hash`; `ON DELETE CASCADE` от `users`.
- Coverage — неприменимо (чистая схема).

  централизованного тикета и закрыть пробел локально, чтобы не блокировать реализацию R1-12.
- `response_body jsonb` может хранить ПРОИЗВОЛЬНО большой ответ (например, список позиций заказа) —
  без ограничения размера в этой схеме; если на практике окажется проблемой (индекс/место), это
  тюнинг уровня эксплуатации, не блокирует R1 при текущем масштабе (аналогично обоснованию
  `SRS-DB-033` про порядок «сначала данные, потом индексы» — не имеет измеримого эффекта на объёме
  MVP).
