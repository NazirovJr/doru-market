## Задача

`OrderNumber` — человекочитаемый идентификатор заказа (`DTJ-260827-00001`), обязателен для EP-09
(Корзина/Checkout) с первого заказа. `ExpiryDate` — жёсткая блокировка продажи просроченного товара
(REQ-REG-6), нужна EP-04 (каталог)/EP-05 (остатки) раньше, чем EP-09. Оба VO — часть «полного списка
обязательных VO» `10-domain-model.md`, заводятся вместе с остальным `shared-kernel` этим эпиком, чтобы
ни один последующий эпик не изобретал их заново под своим модулем.

## Технический контекст

`SRS-DOM-085`: формат `DTJ-{YYMMDD}-{seq5}` (например `DTJ-260827-00001`, 16 символов, укладывается в
`VARCHAR(20)`); `seq5` — атомарный дневной счётчик через Redis `INCR order_seq:{YYMMDD}` с `EXPIRE` на
48 часов; при `seq5 > 99999` за день — `OrderNumberSequenceExhaustedError` (эксплуатационный алерт,
практически недостижимо при целевой нагрузке D-05). `SRS-DB-048`: Redis недоступен в момент генерации
— порт обязан явно пробросить ошибку (не проглатывать, не откатываться на `Math.random()`), вызывающий
`application`-код (EP-09) решает, как деградировать (не в зоне этого тикета — только контракт порта).

`SRS-DOM-087`: `ExpiryDate.isSellable(today): boolean` → `false`, если `date <= today` — ЖЁСТКАЯ
блокировка, значение не конфигурируется. `SRS-DOM-088`: `ExpiryDate.hasMinimumRemainingShelfLife(today,
minDays): boolean` — ОТДЕЛЬНОЕ мягкое правило для `restock()` (буфер `RETURN_RESTOCK_MIN_REMAINING_DAYS`,
ASSUMPTION 30 дней per-tenant), НЕ путать с `isSellable()` (буфер которого всегда 0).

## Что сделать

1. `order-number.vo.ts`: `OrderNumber` (immutable) — приватный конструктор, поле `value: string`.
   `OrderNumber.fromParts(dateYYMMDD: string, seq5: number): OrderNumber` — форматирует
   `` `DTJ-${dateYYMMDD}-${String(seq5).padStart(5, '0')}` `` (валидирует `seq5 ∈ [1, 99999]`,
   иначе `OrderNumberSequenceExhaustedError`). `OrderNumber.parse(raw: string): Result<OrderNumber,
   ValidationError>` — для восстановления из БД (`OrderNumber.restore`-подобный путь, регэксп
   `^DTJ-\d{6}-\d{5}$`). НЕТ метода `regenerate()` (SRS-DOM-086 — неизменяем после присвоения).
2. `order-number-generator.port.ts`: `interface OrderNumberGeneratorPort { generate(dateYYMMDD: string):
   Promise<OrderNumber> }` — принимает уже вычисленную календарную дату `Asia/Dushanbe` (вызывающий код
   получает её через `ClockPort.nowInTenantTz`, DTJ-006 — порт сам НЕ читает время, не знает о
   таймзонах, только оркестрирует Redis-счётчик по переданному ключу).
3. `redis-order-number-generator.adapter.ts`: `RedisOrderNumberGeneratorAdapter implements
   OrderNumberGeneratorPort` — `INCR order_seq:{dateYYMMDD}`, при первом инкременте на новый ключ —
   `EXPIRE order_seq:{dateYYMMDD} 172800` (48 часов в секундах — именованная константа, не магическое
   число); результат `INCR` > `99999` → бросает `OrderNumberSequenceExhaustedError` ДО вызова
   `OrderNumber.fromParts` (явная проверка на границе адаптера, не полагаться только на проверку
   внутри VO — двойной рубеж, т.к. ошибка на этом пути означает реальный операционный инцидент, не
   штатный путь). Ошибка соединения Redis — пробрасывается как есть (не оборачивается, не
   проглатывается, `SRS-DB-048`), тип ошибки — стандартная ошибка `ioredis`, НЕ доменная (это
   инфраструктурный сбой, не бизнес-правило).
4. `expiry-date.vo.ts`: `ExpiryDate.parse(raw: string): Result<ExpiryDate, ValidationError>` —
   формат `"YYYY-MM-DD"` (без времени, сравнение лексикографическое, `SRS-API-008`).
   `expiryDate.isSellable(today: ExpiryDate | Date): boolean` — `false` при `date <= today`
   (SRS-DOM-087, буфер 0, НЕ конфигурируется). `expiryDate.hasMinimumRemainingShelfLife(today,
   minDays: number): boolean` — отдельный метод с явным параметром `minDays` (вызывающий код передаёт
   `RETURN_RESTOCK_MIN_REMAINING_DAYS` из `tenant_settings`, VO не хардкодит 30 — SRS-DOM-088).
5. `order-number-sequence-exhausted.error.ts`: расширяет `DomainError` (нет отдельного `ErrorCode` в
   прочитанном каталоге §2.1/§«Доменные ошибки» — использовать `ErrorCode.INTERNAL_ERROR` с
   `details.reason = 'order_number_sequence_exhausted'`, это эксплуатационный алерт-путь, не
   пользовательская ошибка, HTTP-код `500` уместен).

## Критерии приёмки

1. **Given** `OrderNumber.fromParts('260827', 1)`, **When** `.value`, **Then**
   `'DTJ-260827-00001'` (ровно 16 символов, ведущие нули).
2. **Given** `RedisOrderNumberGeneratorAdapter.generate('260827')` вызван 99999 раз для одной даты
   подряд, **When** 100000-й вызов, **Then** бросается `OrderNumberSequenceExhaustedError` ДО
   обращения к `OrderNumber.fromParts`.
3. **Негативный:** **Given** `ExpiryDate.parse('2026-08-27')` и `today = new Date('2026-08-27')`
   (граничный день, товар просрочен СЕГОДНЯ), **When** `isSellable(today)`, **Then** `false`
   (`date <= today` — включительно просрочен в день истечения, не «ещё продаётся до конца дня»).

## Тест-план

- Unit `OrderNumber`: форматирование с разным `seq5` (1, 99999, граница), `parse` валидного/
  невалидного формата, отсутствие `regenerate()` (проверка API поверхности — нет такого публичного
  метода).
- Unit `RedisOrderNumberGeneratorAdapter` (с мок-Redis/ioredis-mock или testcontainers): последовательные
  вызовы дают монотонно растущий `seq5`, `EXPIRE` выставляется только на первый `INCR` нового ключа,
  превышение `99999` — исключение ДО создания VO, недоступность Redis — ошибка пробрасывается как есть.
- Unit `ExpiryDate`: `isSellable` — вчера/сегодня/завтра (граница `<=`), `hasMinimumRemainingShelfLife`
  — товар с запасом ≥minDays/<minDays, явно РАЗНЫЙ результат от `isSellable` на одной и той же дате
  (демонстрация, что это два независимых правила).
- Порог покрытия `domain/` — ≥90%, `infrastructure/` (Redis-адаптер) — ≥70%.

## Риски и подводные камни

- Тест на 99999 последовательных вызовов `INCR` — дорогой по времени интеграционный тест; допустимо
  сократить до параметризованной unit-проверки логики «> 99999» на мок-Redis, возвращающем нужное
  значение напрямую, вместо реального прогона 99999 раз — задокументировать выбор в самом тесте
  комментарием, чтобы не показалось упущением при ревью.
- `ExpiryDate` сравнивается лексикографически как строка `"YYYY-MM-DD"` (SRS-API-008) — это работает
  корректно ТОЛЬКО при строгом соблюдении формата с ведущими нулями; `parse()` обязан отклонять
  форматы без ведущих нулей (`"2026-8-7"`) явной валидацией регэкспом, а не полагаться на то, что
  `Date`-парсинг сам нормализует — не нормализует безопасно для лексикографического сравнения.
