## Задача

Каждый контроллер, который заведёт ЛЮБОЙ следующий эпик, обязан отвечать в едином формате
`{ data, meta? }`/`{ error: { code, message, details? } }` и передавать доменные ошибки через ОДИН
глобальный фильтр, а не собственный `try/catch` (`SRS-API-016`, `SRS-DOM-153` — «ни один контроллер не
содержит собственного `try/catch` с ручным маппингом кода»). Без этого тикета первый же контроллер
auth (DTJ-023/024) вынужден изобретать формат ответа локально, и все последующие модули будут
копировать несогласованные паттерны.

## Технический контекст

`SRS-API-014/015`: успешный ответ — `{ data, meta? }` (пустое действие — `{ data: { success: true } }`
со статусом `200`, НЕ `204`); ошибка — `{ error: { code: SCREAMING_SNAKE, message, details? } }`,
`message` локализован по `Accept-Language` (`tj` дефолт — полная локализация текста ошибок out of
scope этого тикета, т.к. требует готового `packages/i18n` серверной раздачи словаря, зона EP-18; этот
тикет возвращает `message` на русском как временный дефолт с явным `// TODO(EP-18)`, не блокирует
структуру ответа). `details` НИКОГДА не содержит stack trace в `NODE_ENV=production` — для `500
INTERNAL_ERROR` `details` принудительно опускается, остаётся только `requestId` (для связи с логом).

`SRS-API-016`: `DomainExceptionFilter` — ловит `DomainError` (и потомков, `packages/contracts/src/
domain-errors.ts`, DTJ-005) → код/статус из `ERROR_HTTP_STATUS` того же пакета. `TransportExceptionFilter`
— ловит остальное (`NestJS HttpException`, необработанные исключения → `500 INTERNAL_ERROR`). Оба —
`APP_FILTER`, порядок регистрации: `DomainExceptionFilter` первым (более специфичный), затем
`TransportExceptionFilter` как catch-all.

`SRS-API-004/005/006/007`: cursor-пагинация/сортировка/фильтрация — типы уже в `packages/contracts/src/
pagination.ts` (DTJ-005); этот тикет добавляет ИСПОЛЬЗУЮЩИЙ их NestJS `PipeTransform`
(`CursorQueryPipe`) — декодирует `cursor` query-параметр, на несовпадение типа `v` с ожидаемым —
`400 INVALID_CURSOR` (`SRS-API-005`), НЕ подгоняет курсор под тип принудительно.

## Что сделать

1. `response.interceptor.ts`: глобальный `NestInterceptor` — оборачивает ЛЮБОЕ возвращаемое
   контроллером значение в `{ data: <value> }`, если оно ещё не в форме `SuccessEnvelope`
   (используется хелпер `ok()` из `packages/contracts/src/envelope.ts`, DTJ-005, для явной сборки
   `meta.pagination` в списковых эндпоинтах — контроллер вызывает `ok(items, { pagination })`
   напрямую, интерсептор пропускает уже готовый конверт как есть, оборачивает только «голые» значения
   для эндпоинтов, где разработчик забыл явно собрать конверт — защитная сетка, не основной путь).
2. `domain-exception.filter.ts`: `@Catch(DomainError)` — читает `error.code`, резолвит HTTP-статус
   через `ERROR_HTTP_STATUS[error.code]` (DTJ-005), формирует `{ error: { code, message: error.message,
   details: error.details } }`; в `NODE_ENV=production` для статуса `500` — `details` заменяется на
   `{ requestId: RequestContext.current().requestId }` (`RequestContext` из DTJ-001), остальные поля
   `error.details` опускаются.
3. `transport-exception.filter.ts`: `@Catch()` (catch-all, регистрируется ПОСЛЕ
   `DomainExceptionFilter`, чтобы доменные ошибки не долетали сюда) — `NestJS HttpException` мапится
   1:1 (`404`→`NOT_FOUND`, стандартные Nest-исключения валидации → `VALIDATION_ERROR` и т.д.);
   необработанное `Error` → `500 INTERNAL_ERROR`, логируется через `pino` с полным стеком СЕРВЕРНОЙ
   стороны (в лог — да, в HTTP-ответ — нет, только `requestId`).
4. `cursor-query.pipe.ts`: `CursorQueryPipe` — принимает Zod-схему конкретного эндпоинта (расширяющую
   `cursorQuerySchema` из DTJ-005 полями `sort`), парсит query, при ошибке валидации `sort`/`filter`
   вне разрешённого enum'а — `400 VALIDATION_ERROR` с `details.field`; при несовпадении типа значения
   курсора — `400 INVALID_CURSOR` (`SRS-API-005`) — ДВА РАЗНЫХ кода на два разных случая, не сводить
   к одному общему.
5. `api-response.decorator.ts`: вспомогательный декоратор `@ApiSuccessResponse(dtoClass)` — тонкая
   обёртка для будущей интеграции с OpenAPI-генерацией (DTJ-021 того же эпика реально подключит его к
   `zod-to-openapi`; здесь — только контракт декоратора, не полная OpenAPI-генерация).

## Критерии приёмки

1. **Given** use case бросает `InsufficientStockError` (потомок `BusinessRuleViolationError`), **When**
   долетает до `DomainExceptionFilter`, **Then** ответ `422 { "error": { "code":
   "INSUFFICIENT_STOCK", "message": "...", "details"?: {...} } }`.
2. **Given** необработанное `TypeError` где-то внутри use case, **When** долетает до
   `TransportExceptionFilter`, **Then** ответ `500 { "error": { "code": "INTERNAL_ERROR", "message":
   "...", "details": { "requestId": "<uuid>" } } }` в `NODE_ENV=production`, БЕЗ stack trace в теле
   ответа (стек — только в pino-логе сервера).
3. **Негативный:** **Given** query `?cursor=eyJ2IjoxMjN9` (декодируется в `{ v: 123 }`, число вместо
   ожидаемой ISO-даты для эндпоинта, отсортированного по дате), **When** `CursorQueryPipe` обрабатывает,
   **Then** `400 INVALID_CURSOR` (не `500`, не тихая подгонка типа).

## Тест-план

- Unit: `DomainExceptionFilter` — маппинг для представителя каждой ветки иерархии ошибок
  (`ValidationError`, `ConflictError`, `NotFoundError`, `ForbiddenTransitionError`,
  `BusinessRuleViolationError`, `SecurityError`, `OtpError`) на правильный HTTP-статус; редакция
  `details` при `500` в production-режиме.
- Unit: `TransportExceptionFilter` — стандартные `HttpException` Nest, необработанная ошибка.
- Unit: `CursorQueryPipe` — валидный курсор, курсор с несовпадающим типом (`INVALID_CURSOR`),
  `sort`-поле вне разрешённого enum'а (`VALIDATION_ERROR`).
- Unit: `response.interceptor` — «голое» значение оборачивается в `{ data }`, уже готовый
  `SuccessEnvelope` не оборачивается дважды.
- Coverage `presentation`-подобного кода — ≥70% (по `02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.4, т.к.
  это не `domain`/`application`).

## Риски и подводные камни

- Полная локализация `message` по `Accept-Language` — НЕ реализована этим тикетом (зависит от готовой
  серверной раздачи словаря `packages/i18n`, зона EP-18/будущего эндпоинта `GET /api/v1/i18n/:locale`,
  который EP-01 не заводит, см. `tickets/00-EPICS.md`). Временное поведение — русский текст как
  единственная локаль ошибок до готовности EP-18; это явный, задокументированный технический долг, не
  скрытый пробел.
- `ERROR_HTTP_STATUS` (DTJ-005) — единственный источник маппинга кода на статус; если DTJ-005
  реализован с расхождением (например, забыт код), `DomainExceptionFilter` упадёт на
  `undefined`-статусе — тест-план явно требует проверку «представителя каждой ветки», чтобы поймать
  это на этапе тестов этого тикета, а не в проде другого эпика.
