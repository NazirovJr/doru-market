## Задача

`SRS-API-018`/`SRS-API-035` фиксируют жёсткое правило: самостоятельная регистрация через OTP работает
ТОЛЬКО для роли `customer` — `pharmacist`/`courier`/`pharmacy_admin`/`support_agent`/`super_admin`
заводятся ЗАРАНЕЕ административным use case, иначе для них структурно невозможен первый вход. Без
этого эндпоинта ни один E2E-сценарий с фармацевтом или курьером (CUJ-3'/CUJ-4', критический путь,
`tickets/00-EPICS.md`) не может даже начаться — некому будет войти в систему в этой роли.

## Технический контекст

`SRS-API-035`: персонал заводится через `POST /api/v1/staff-accounts` — `pharmacy_admin` создаёт
только `pharmacist` СВОЕЙ аптеки/сети; `courier` собственного флота (`chainId` заполнен) — тоже
`pharmacy_admin`; курьер платформенного пула (`chainId = NULL`) — только `super_admin`. `super_admin`
может создать ЛЮБУЮ роль (`SRS-API-038` таблица: `staff-accounts:create` — `pharmacy_admin` ✅
условно, `super_admin` ✅ любая роль).

Проверка владения («это его аптека/сеть») — по `SRS-API-036` ОБЯЗАНА жить в
`application/policies/*.policy.ts`, не в guard'е — этот тикет заводит `StaffAccountPolicy` именно
здесь, как первый конкретный пример такой политики в кодовой базе (образец для последующих модулей,
которым тоже понадобятся policy-файлы).

## Что сделать

1. `staff-account.policy.ts`: `StaffAccountPolicy.canCreate(actor: { role: UserRole; pharmacyId:
   string | null; chainId: string | null }, target: { role: UserRole; chainId: string | null }):
   boolean`:
   - `actor.role === 'super_admin'` → `true` всегда (любая целевая роль).
   - `actor.role === 'pharmacy_admin'`:
     - `target.role === 'pharmacist'` И `target.chainId === actor.chainId` → `true`.
     - `target.role === 'courier'` И `target.chainId === actor.chainId` И `target.chainId !== null`
       (собственный флот сети, НЕ платформенный пул — платформенный пул доступен только
       `super_admin`) → `true`.
     - Любая другая комбинация (в т.ч. `target.role ∈ {'pharmacy_admin', 'super_admin',
       'support_agent'}`, или `courier` с `target.chainId = null`) → `false`.
   - Любая другая `actor.role` → `false`.
2. `create-staff-account.dto.ts`: Zod `{ phone: z.string(); fullName: z.string(); role:
   z.enum(['pharmacist', 'courier', 'pharmacy_admin', 'support_agent', 'super_admin']); pharmacyId:
   z.string().uuid().optional(); chainId: z.string().uuid().optional() }`.
3. `create-staff-account.use-case.ts`: `CreateStaffAccountUseCase.execute({ actor, command }):
   Promise<Result<{ userId: string }, ForbiddenError | DuplicateTenantSlugError | ValidationError>>`:
   1. `PhoneNumber.parse(command.phone)` — невалиден → `ValidationError`.
   2. `StaffAccountPolicy.canCreate(actor, { role: command.role, chainId: command.chainId ?? null })`
      — `false` → `403 FORBIDDEN` (переиспользуется общий код, не заводится новый специфичный —
      `SRS-API-036` подтверждает, что это именно application-уровневая политика, `FORBIDDEN`, а не
      `INSUFFICIENT_ROLE`, который зарезервирован за грубой ролевой guard-проверкой, `SRS-API-039`).
   3. `UsersRepository.findByTenantAndPhone(actor.tenantId, phone)` — уже существует → `409
      CONFLICT` (нельзя завести второй аккаунт персонала на тот же телефон в том же тенанте — тот же
      `unique_phone_per_tenant` constraint БД, use case проверяет заранее для понятной ошибки, а не
      полагается только на исключение констрейнта).
   4. `UsersRepository.create({ tenantId: actor.tenantId, phoneNumber: phone.value, role: command.role,
      fullName: command.fullName, pharmacyId: command.pharmacyId ?? null, chainId: command.chainId ??
      null })`.
   5. Возврат `{ userId }` — БЕЗ выдачи токена (это не логин, персонал делает `POST /auth/otp/request`
      САМ при первом входе, как обычный человек, ПОСЛЕ того как строка `users` уже существует —
      `SRS-API-018` тогда сработает как «find», не «create»).
4. `staff-accounts.controller.ts`: `POST /api/v1/staff-accounts`, `@UseGuards(AuthGuard, RolesGuard)`,
   `@Roles('pharmacy_admin', 'super_admin')` (грубый фильтр — точная проверка владения аптекой/сетью
   и допустимости конкретной целевой роли — внутри use case через policy, шаг 2 выше, в точности
   разделение ответственности `SRS-API-036`).

## Критерии приёмки

1. **Given** `actor` — `pharmacy_admin` сети X, **When** создаёт `pharmacist` с `chainId=X`, **Then**
   `201 { data: { userId } }`, новая строка `users` с `role='pharmacist'`.
2. **Given** тот же `actor`, **When** пытается создать `courier` с `chainId=null` (платформенный
   пул), **Then** `403 FORBIDDEN` (только `super_admin` может заводить пуловых курьеров,
   `SRS-API-035`).
3. **Негативный:** **Given** `actor` — `pharmacy_admin` сети X, **When** пытается создать
   `pharmacist` с `chainId=Y` (ЧУЖАЯ сеть), **Then** `403 FORBIDDEN` — не создана строка `users` для
   чужой сети (проверка политики блокирует межсетевое создание персонала, ключевой сценарий
   изоляции).

## Риски и подводные камни

- `actor.tenantId`/`actor.chainId`/`actor.pharmacyId` берутся из JWT-claims текущего запроса
  (`@CurrentUser()`, DTJ-022) — это означает, что `pharmacy_admin`, чей JWT был выдан ДО того, как его
  собственный `chainId` был изменён администратором (гипотетический сценарий смены сети), продолжит
  действовать со СТАРЫМ `chainId` до истечения access-токена (максимум 15 минут) или следующего
  `refresh` (DTJ-025 уже перечитывает `users`-строку заново на каждой ротации — значит расхождение
  живёт не дольше 15 минут). Не блокирующий риск для R1, но задокументировать, т.к. неочевиден при
  первом чтении кода.
- `super_admin` создаёт ЛЮБУЮ роль, включая другого `super_admin` — сознательно НЕ ограничено этим
  тикетом (SRS даёт `super_admin` полный доступ без исключений в §4.1 матрицы) — если продуктово
  потребуется ограничение (например, «нельзя создать второго `super_admin` без двухфакторного
  подтверждения»), это отдельное продуктовое решение вне зоны текущего SRS, не добавляется
  самовольно.
