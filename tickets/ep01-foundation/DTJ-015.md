## Задача

Ротация refresh-токенов с обнаружением переиспользования (`SRS-API-026/027`) и список активных
устройств (`SRS-API-030`) — обязательная часть R1-12 (`04-SCOPE-DECISION-PIVOT.md`). Персистентность
`OtpCode` VO (DTJ-010) — таблица, без которой ни `RequestOtpUseCase`, ни `VerifyOtpUseCase` (DTJ-023/024
того же эпика) не могут хранить состояние выданного кода между запросом и проверкой.

## Технический контекст: расхождение источников (зафиксировано явно)

`docs/spec/11-database-schema.md` таблица 18 называет эту сущность `refresh_tokens` с колонками
`(id, user_id, token_hash, issued_at, expires_at, rotated_from, revoked_at)` — БЕЗ `family_id`,
`device_label`, `ip_address`, `last_seen_at`. Одновременно `docs/spec/12-api-conventions-auth-tenancy.md`
§3.2-3.4 (`SRS-API-024..030`) описывает функциональность, которая ФИЗИЧЕСКИ требует
`family_id`/`device_label`/`ip_address`/`last_seen_at` (обнаружение реюза «ВСЕ `auth_sessions` с тем же
`family_id`», список устройств с `deviceLabel`/`lastSeenAt`/`isCurrent`) и называет таблицу
`auth_sessions`, не `refresh_tokens`. Это два документа одного приоритетного уровня (`docs/spec/*.md`),
которые расходятся по имени и составу колонок одной и той же сущности — не выдумка этого тикета,
реальное расхождение источников (аналогичное уже известному `SRS-DOM-372`/`585`/`909`,
`docs/STATE-AND-RESUME-POINT.md` §2.2.2 п.2).

**Решение тикета**: реализовать `auth_sessions` по `12-api-conventions-auth-tenancy.md` — этот документ
даёт полный набор проверяемых Given/When/Then-требований (`SRS-API-024..030`), которые невозможно
удовлетворить укороченной схемой `refresh_tokens`; таблица `refresh_tokens` из `11-database-schema.md`
таблицы 18 НЕ создаётся. Разработчик тикета обязан также точечно обновить `11-database-schema.md`
(заменить таблицу 18 на актуальное описание `auth_sessions`) в том же PR — это не отдельный тикет, а
DoD-пункт данного (см. ниже), чтобы расхождение не осталось в документации для следующего читателя.

## Что сделать

1. `auth-sessions.schema.ts`:
   ```typescript
   export const authSessions = pgTable('auth_sessions', {
     id: uuid('id').primaryKey().defaultRandom(),
     userId: uuid('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
     familyId: uuid('family_id').notNull(), // общий для всей цепочки ротации одного устройства
     refreshTokenHash: text('refresh_token_hash').notNull().unique(), // sha256(refreshToken)
     deviceLabel: varchar('device_label', { length: 100 }), // напр. 'telegram_twa', User-Agent-эвристика
     userAgent: text('user_agent'),
     ipAddress: varchar('ip_address', { length: 45 }), // сырое значение; маскирование — presentation (SRS-API-149)
     sessionCreatedAt: timestamp('session_created_at', { withTimezone: true }).notNull(), // первая выдача цепочки, копируется при ротации
     issuedAt: timestamp('issued_at', { withTimezone: true }).notNull().defaultNow(), // выдача ИМЕННО этой записи
     absoluteExpiresAt: timestamp('absolute_expires_at', { withTimezone: true }).notNull(), // sessionCreatedAt + 30 дней, фиксировано, не продлевается
     lastSeenAt: timestamp('last_seen_at', { withTimezone: true }).notNull().defaultNow(),
     rotatedAt: timestamp('rotated_at', { withTimezone: true }),
     revokedAt: timestamp('revoked_at', { withTimezone: true }),
     revokeReason: varchar('revoke_reason', { length: 50 }), // 'user_logout' | 'reuse_detected' | 'admin_force_logout'
   });
   ```
   Обоснование `sessionCreatedAt` отдельно от `issuedAt`: `SRS-API-025` — `absoluteExpiresAt`
   фиксируется в момент ПЕРВОЙ выдачи и НЕ продлевается при ротации; `SRS-API-030` — «список активных
   устройств» обязан показывать `createdAt`/`lastSeenAt` НА УРОВНЕ УСТРОЙСТВА, а не на уровне
   отдельной ротации (иначе список «спамит» новой строкой при каждом `/auth/refresh`, которых может
   быть десятки за 30 дней сессии). Запрос активных сессий — `WHERE user_id = :id AND revoked_at IS
   NULL AND rotated_at IS NULL`, что по построению (только последнее звено цепочки не ротировано)
   даёт РОВНО одну строку на `family_id` — естественно соответствует «одно устройство = одна строка».
2. `otp-codes.schema.ts` — 1:1 по DDL `11-database-schema.md` таблица 17 (это расхождений не имеет):
   `id`, `purpose` (`otpPurposeEnum`), `subjectRef varchar(255)` (номер телефона для `login` или
   `delivery_assignment_id` для `delivery_handover`), `codeHash text`, `issuedAt timestamptz default
   now()`, `ttlSeconds int`, `attemptsUsed int default 0`, `maxAttempts int`, `consumedAt timestamptz`,
   `lockedAt timestamptz`.
3. `apps/api/migrations/0004_auth_sessions_otp.sql` — сгенерировано из шагов 1-2.
4. Точечно обновить `docs/spec/11-database-schema.md`: заменить блок «18. refresh_tokens» на
   «18. auth_sessions» с колонками из шага 1 и комментарием, ссылающимся на `SRS-API-024..030` как
   источник (используя правило проекта «правь точечно через Edit, не переписывай целиком»).

## Критерии приёмки

1. **Given** применена `0004_auth_sessions_otp.sql`, **When** `INSERT` двух строк `auth_sessions` с
   одинаковым `refresh_token_hash`, **Then** второй `INSERT` падает (`UNIQUE` constraint).
2. **Given** запрос `SELECT * FROM auth_sessions WHERE user_id = :id AND revoked_at IS NULL AND
   rotated_at IS NULL`, **When** у пользователя одна активная сессия из трёх ротаций одной цепочки
   (`family_id`), **Then** возвращается РОВНО одна строка (последнее звено).
3. **Негативный:** **Given** `otp_codes.max_attempts` не передан (`NOT NULL` без дефолта), **When**
   `INSERT` без этого поля, **Then** падает — приложение обязано ЯВНО резолвить `maxAttempts` по
   `purpose` до вставки (нет скрытого дефолта уровня БД, решение — в domain, `SRS-DOM-080`, DTJ-010).

## Тест-план

- Integration: `UNIQUE(refresh_token_hash)`, `ON DELETE CASCADE` от `users`, запрос «последнее звено
  цепочки» на фикстуре из 3 ротаций + 1 отозванной сессии другого `family_id`.
- Integration `otp_codes`: вставка с обоими `purpose`, `NOT NULL` на `ttl_seconds`/`max_attempts`.
- Coverage — неприменимо (чистая схема).

## Риски и подводные камни

- **Это единственный тикет эпика, вносящий точечную правку в `docs/spec/`** — оправдано тем, что
  расхождение блокирует корректную реализацию (нельзя одновременно удовлетворить оба документа), а не
  является предпочтением стиля. Правка — МИНИМАЛЬНА (одна таблица одного раздела), не переписывает
  документ. Если ревью архитектора не согласится с выбором «`12-api-conventions` побеждает
  `11-database-schema`» — откат тривиален (одна таблица), не требует пересмотра остальной схемы.
- Запрос «последнее звено = активная сессия» (приёмка 2) — неявный инвариант, не constraint БД
  (ничто физически не запрещает две нератированные нереотозванные строки одного `family_id`
  одновременно при ошибке в application-коде ротации). `RefreshUseCase` (DTJ-025) обязан гарантировать
  этот инвариант атомарно (транзакция с блокировкой строки) — если он этого не сделает, список сессий
  начнёт показывать дубли устройства без явной ошибки БД. Задокументировать это явно в DTJ-025.
