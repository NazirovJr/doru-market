## Задача

«Я потерял телефон» — реальный сценарий поддержки с первого дня продакшена; без `logout-all` и списка
устройств пользователь не может самостоятельно отозвать доступ с потерянного устройства, и это
неизбежно ляжет на `support_agent` вручную через БД. Завершает функциональный минимум R1-12.

## Технический контекст

`SRS-API-029`: `POST /auth/logout { refreshToken }` — отзывает ТОЛЬКО текущую `auth_sessions`-запись
(`revoked_at=now(), revoke_reason='user_logout'`), НЕ всю `family_id`-цепочку (в отличие от
reuse-detection). `POST /auth/logout-all` (требует валидный access-токен, без тела) — отзывает ВСЕ
сессии текущего `userId` независимо от `family_id`. `SRS-API-030`: `GET /auth/sessions` — список
активных устройств: `{ id, deviceLabel, ipAddress (маскирован), lastSeenAt, createdAt, isCurrent }`.
`DELETE /auth/sessions/:id` — отзыв конкретного устройства; владение проверяется
`session.userId === actor.userId`, иначе `403 FORBIDDEN` (ДАЖЕ для `super_admin` — принудительный отзыв
чужой сессии — отдельный административный эндпоинт `POST /admin/users/:id/force-logout`, НЕ в зоне
этого тикета — принадлежит `apps/admin`/EP-15, здесь только self-service). `SRS-API-149`: `ipAddress`
в ответе — МАСКИРОВАН (последний октет IPv4 / последний блок IPv6 заменён на `*`, presentation-уровневое
преобразование, не хранение — в БД `ip_address` остаётся полным для security-расследований).

## Что сделать

1. `logout.use-case.ts`: `LogoutUseCase.execute({ refreshToken: string, currentUserId: string }):
   Promise<Result<void, RefreshTokenInvalidError>>` — находит сессию по `sha256(refreshToken)`,
   проверяет `session.userId === currentUserId` (защита от логаута ЧУЖОЙ сессии через подставленный
   чужой refresh-токен в теле при своём валидном access-токене — оба должны принадлежать одному
   пользователю), `revoked_at=now(), revoke_reason='user_logout'`. Given сессия не найдена/не
   принадлежит текущему пользователю → идемпотентный успех (logout несуществующей/чужой сессии не
   должен раскрывать её существование — тихий `Result.ok`, не ошибка).
2. `logout-all.use-case.ts`: `LogoutAllUseCase.execute({ userId: string }): Promise<void>` —
   `AuthSessionsRepository.revokeAllByUserId(userId, reason='user_logout_all')` (один `UPDATE`, все
   `family_id` этого `userId`).
3. `list-sessions.use-case.ts`: `ListSessionsUseCase.execute({ userId: string, currentSessionId:
   string }): Promise<SessionSummary[]>` — читает АКТИВНЫЕ сессии (`revoked_at IS NULL AND rotated_at
   IS NULL` — см. обоснование в DTJ-015 «одна строка на устройство»), маппит `ipAddress` через
   `maskIpAddress()` хелпер (presentation-адjacent util, но вызывается уже в application для
   формирования DTO — приемлемо, т.к. маскирование не бизнес-правило, а форматирование вывода;
   альтернативно вынести в presentation-маппер, если ревью сочтёт более чистым — не блокирующее
   расхождение), `isCurrent = (row.id === currentSessionId)`.
4. `revoke-session.use-case.ts`: `RevokeSessionUseCase.execute({ sessionId: string, actorUserId:
   string }): Promise<Result<void, ForbiddenError>>` — `session.userId !== actorUserId` →
   `403 FORBIDDEN` (`SRS-API-030` — «даже для `super_admin`» этот путь не даёт обхода, use case не
   принимает признак роли вообще, только `actorUserId` — структурно невозможно обойти проверку
   владения ролью, что и есть смысл требования).
5. `sessions.controller.ts`: `POST /auth/logout` (`@Public()` — сам факт наличия access-токена не
   обязателен по духу `SRS-API-029` формулировки «отзывает текущую по refreshToken», но `currentUserId`
   нужен для проверки владения в шаге 1 — ТРЕБУЕТ `AuthGuard` (не `@Public()`), уточнение относительно
   черновой пометки выше: маршрут защищён `@UseGuards(AuthGuard)` БЕЗ `@Roles(...)` — доступен любой
   аутентифицированной роли для своей же сессии). `POST /auth/logout-all`, `GET /auth/sessions`,
   `DELETE /auth/sessions/:id` — все под `@UseGuards(AuthGuard)`, без `@Roles(...)` (доступны всем
   ролям для собственных сессий).

## Критерии приёмки

1. **Given** пользователь с 2 активными устройствами (2 разных `family_id`), **When** `GET
   /auth/sessions`, **Then** возвращается ровно 2 записи, `ipAddress` каждой замаскирован (например
   `"91.201.***.***"` для IPv4 — точный паттерн маскирования фиксируется тестом), ровно одна
   помечена `isCurrent: true` (сессия, чей `sessionId` совпадает с `sessionId` из JWT текущего
   запроса).
2. **Given** пользователь A пытается `DELETE /auth/sessions/:id`, где `:id` принадлежит пользователю
   B, **When** запрос, **Then** `403 FORBIDDEN`, сессия B НЕ отозвана.
3. **Негативный:** **Given** `POST /auth/logout-all`, **When** выполнен, **Then** ВСЕ сессии (включая
   ту, чьим access-токеном был выполнен сам запрос) отозваны — следующий запрос ТЕМ ЖЕ access-токеном
   (ещё не истёкшим по `exp`, до 15 минут) остаётся технически валиден по JWT-подписи (JWT
   самодостаточен, не проверяется против БД на каждый запрос по умолчанию) — но `refresh` этой сессии
   после logout-all уже невозможен (`401 REFRESH_TOKEN_INVALID`); зафиксировать этот нюанс явно как
   ОЖИДАЕМОЕ поведение (JWT короткоживущий, полный эффект logout-all наступает не позже 15 минут), не
   дефект.

## Риски и подводные камни

- Формулировка `SRS-API-029` буквально не требует access-токена для `/auth/logout` (только тело
  `{ refreshToken }`), но проверка владения из `SRS-API-030`/духа безопасности требует знать
  `currentUserId` — решение тикета: ВСЕ 4 эндпоинта требуют `AuthGuard`. Если это разойдётся с
  ожиданиями клиента (например, логаут при уже истёкшем access-токене, но валидном refresh) —
  клиентский код обязан сначала `refresh`, потом `logout` (или просто перестать использовать
  refresh-токен локально без похода на сервер — токен и так станет недействителен по
  `absoluteExpiresAt` максимум через 30 дней). Явно зафиксировать это архитектурное решение в PR,
  чтобы фронтенд-разработчик (DTJ-028 или позже) знал ограничение.
- `isCurrent` определяется по `sessionId` из JWT, а НЕ по `refreshToken` (в списке сессий нет
  refresh-токенов вообще, только метаданные) — `sessionId` берётся из `@CurrentUser()` claims
  (DTJ-022), необходимо, чтобы `RolesGuard`/`AuthGuard` действительно прокидывали его в контроллер.
