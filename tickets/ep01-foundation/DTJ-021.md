## Задача

`Charter §3.6` объявляет `docs/api/openapi.json` «единым источником правды для Dart-клиента» —
Flutter-приложения курьера/фармацевта (R2) генерируют модели ИЗ этого файла, не хардкодят формат
вручную. Спека обязана расти вместе с КАЖДЫМ следующим контроллером, поэтому механизм генерации
(из Zod-схем `packages/contracts`, не ручное описание) заводится сейчас, до первого реального
эндпоинта (DTJ-023/024 того же эпика — их контроллеры становятся первой проверкой, что механизм
реально работает).

## Технический контекст

`SRS-API-060`: спека OpenAPI 3.1 генерируется автоматически из Zod-схем `packages/contracts` через
`@asteasolutions/zod-to-openapi` (мост Zod→OpenAPI, единый источник правды — не дублирование описания
вручную). `SRS-API-061`: `GET /api/docs/json` (сырой JSON) и `GET /api/docs` (Swagger UI) — ОБА
эндпоинта `404`, когда `NODE_ENV=production` И `ENABLE_API_DOCS != true`. `SRS-API-062`: на каждый
релизный тег CI-джоба генерирует спеку и коммитит `docs/api/openapi.json`; отдельный CI-шаг
`pnpm openapi:check` (генерирует во временный файл, `diff` с закоммиченным) — CI-часть (workflow) вне
зоны этого тикета (EP-19 владеет `.github/workflows/**`), но САМ генератор (`pnpm openapi:generate`)
и скрипт сравнения (`pnpm openapi:check`, как npm-скрипт, не workflow) — да, этот тикет.

## Что сделать

1. `apps/api/package.json`: зависимость `@asteasolutions/zod-to-openapi` (сверить фактическую
   совместимость с `zod ^4.4.3`, зафиксированным в `01-TECH-BASELINE.md`, на момент реализации —
   при несовместимости версии зафиксировать ADR-подобную запись в PR, не откладывать без объяснения).
2. `openapi.builder.ts`: `OpenApiRegistry` (из `zod-to-openapi`) — регистрирует схемы
   `packages/contracts` (`envelope.ts`, `pagination.ts`, `errors.ts` — как компоненты `error`-схемы
   для документирования формата ошибок), метаданные проекта (`title: 'DoruTJ API'`, `version` из
   `package.json`); экспортирует функцию `buildOpenApiDocument(): OpenAPIObject`. Каждый контроллер,
   заводимый последующими эпиками, регистрирует СВОИ Zod DTO через `registry.registerPath(...)` —
   этот тикет создаёт только реестр и функцию сборки, не описывает несуществующие пока эндпоинты.
3. `openapi.module.ts`: `GET /api/docs/json` — `res.send(buildOpenApiDocument())`; `GET /api/docs` —
   Swagger UI (статический HTML, ссылающийся на `/api/docs/json`); оба маршрута — guard
   `ApiDocsAccessGuard`: `NODE_ENV !== 'production' || ENABLE_API_DOCS === true`, иначе `404`
   (не `403` — не раскрывать даже факт существования маршрута в проде без флага, `SRS-API-061`).
4. `apps/api/package.json` скрипты: `openapi:generate` (`tsx` скрипт, пишет
   `buildOpenApiDocument()` в `docs/api/openapi.json` корня репозитория, с `JSON.stringify(...,
   null, 2)` для читаемого diff в git); `openapi:check` (генерирует во временный файл, `diff` с
   закоммиченным `docs/api/openapi.json`, ненулевой код при расхождении — фактический CI workflow,
   вызывающий этот скрипт, заводит EP-19, не дублировать здесь).

## Критерии приёмки

1. **Given** `NODE_ENV=development`, **When** `GET /api/docs/json`, **Then** `200`, валидный OpenAPI
   3.1 JSON-документ (проверяется базовой JSON-Schema валидацией структуры, не полным конформанс-тестом).
2. **Given** `NODE_ENV=production` и `ENABLE_API_DOCS` не задан, **When** `GET /api/docs`, **Then**
   `404` (не `403`, не редирект).
3. **Негативный:** **Given** `pnpm openapi:generate` изменил `docs/api/openapi.json` (например,
   добавлен новый эндпоинт в коде, но файл не перегенерирован), **When** `pnpm openapi:check`,
   **Then** команда завершается с ненулевым кодом и понятным diff-выводом — не молчит и не
   перезаписывает файл автоматически (проверка, не мутация).

## Тест-план

- Integration: `GET /api/docs/json` — `200` в dev, `404` в проде без флага, `200` в проде С флагом
  `ENABLE_API_DOCS=true`.
- Unit: `buildOpenApiDocument()` — содержит базовые метаданные (`title`, `version`), не падает при
  пустом реестре путей (граничный случай — этот тикет не регистрирует ни одного реального эндпоинта).
- Unit: скрипт `openapi:check` — детектирует расхождение на фикстуре (заранее изменённый временный
  файл vs «текущая» генерация).
- Coverage — ≥70%.

## Риски и подводные камни

- Совместимость `@asteasolutions/zod-to-openapi` с `zod ^4.4.3` — не проверена архитектором явно в
  `01-TECH-BASELINE.md` (пакет не входит в зафиксированный список версий, только `zod` сам по себе);
  на момент написания этого тикета библиотека исторически отставала от мажорных версий Zod — первый
  шаг реализации ОБЯЗАН проверить актуальную совместимость и, при необходимости, зафиксировать
  отклонение как одну строку обоснования в PR (`01-TECH-BASELINE.md` §«Правила» п.3: «любой новый
  пакет вне списка требует одной строки обоснования»).
- Пустой реестр путей на момент этого тикета (нет ни одного зарегистрированного эндпоинта) — риск,
  что тест «валидный OpenAPI документ» слишком слаб, чтобы поймать реальные проблемы интеграции,
  которые проявятся только когда DTJ-023/024 зарегистрируют первый реальный путь; явно указать в PR,
  что полная проверка «раунд-трипа» контроллер→Zod-схема→OpenAPI откладывается на первый реальный
  потребитель, не на этот тикет.
- Файл `apps/api/src/common/openapi/openapi.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/package.json` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
