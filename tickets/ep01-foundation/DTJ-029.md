## Задача

Auth — единственный модуль R1, где ошибка молча превращается в дыру безопасности, а не в
пользовательский баг (брутфорс OTP, украденный refresh-токен, гонка двух вкладок). Каждый из этих
сценариев ЧАСТИЧНО покрыт unit-тестами внутри тикетов DTJ-023..026, но этот тикет — единственное
место, где они проверяются СКВОЗНЫМ интеграционным путём (реальный HTTP + реальная БД + реальный
Redis), как того требует критерий приёмки R1 п.2 (`docs/04-SCOPE-DECISION-PIVOT.md`: «покрытие
`domain`/`application` ≥90%» — этот тикет не про покрытие, а про то, что сценарии из
Given/When/Then каждого auth-тикета РЕАЛЬНО воспроизводимы end-to-end, не только на моках).

## Технический контекст

Консолидирует сквозную проверку требований, УЖЕ описанных построчно в DTJ-023 (`SRS-API-019/020` —
rate-limit + невалидный формат), DTJ-024 (`SRS-API-022/071` — брутфорс verify + гонка двух вкладок),
DTJ-025 (`SRS-API-027` — reuse detection), DTJ-014/017-API-017 (`SRS-API-017` — изоляция телефонов по
тенанту). Отдельный файл на каждый сценарий — не дублирование unit-тестов тех тикетов (те проверяют
логику use case на моках, эти — что вся цепочка HTTP→guard→use case→БД→Redis работает вместе).

## Что сделать

1. `otp-brute-force.spec.ts`: полный сценарий — `POST /auth/otp/request` для нового номера, затем 6
   подряд `POST /auth/otp/verify` с заведомо неверным кодом на реальный `apps/api` тестовый инстанс;
   проверка, что 1-5 попытки дают `400 OTP_MISMATCH` с уменьшающимся `attemptsLeft` в `details`, а
   6-я — `423 OTP_LOCKED`, ПОСЛЕ чего даже ПРАВИЛЬНЫЙ код (если бы был известен) отклоняется тем же
   кодом (fail-closed, `SRS-DOM-173`). Отдельно: сценарий `SRS-API-019` — 4-й запрос `/auth/otp/request`
   за 10 минут на один номер → `429 OTP_REQUEST_RATE_LIMITED` (реальный Redis, не мок таймера).
2. `refresh-reuse-detection.spec.ts`: полный цикл логина → 2 легитимные ротации refresh → атакующий
   предъявляет ПЕРВЫЙ (уже устаревший) токен из цепочки → `401 REFRESH_TOKEN_REUSE_DETECTED` →
   ПОСЛЕДНИЙ легитимный токен (третий по счёту) ТОЖЕ становится невалиден при попытке его
   использовать сразу после (`SRS-API-027` — «ВСЕ `auth_sessions` с тем же `family_id`»).
3. `otp-verify-race.spec.ts`: `Promise.all([verify(code), verify(code)])` — два конкурентных запроса
   с ОДНИМ `otpRequestId` и ОДНИМ верным кодом; проверка, что ровно один получает `200` с валидной
   парой токенов, второй — `400 OTP_MISMATCH` (`alreadyConsumed`), и что создана РОВНО одна
   `auth_sessions`-запись, не две (`SRS-API-071`).
4. `phone-tenant-isolation.spec.ts`: два разных тенанта (используя минимальный тестовый сетап —
   прямая вставка двух строк-заглушек в тестовую БД в обход отсутствующего пока `tenants`-модуля
   EP-02, т.к. `tickets/00-EPICS.md` явно указывает, что тест на утечку между тенантами обязателен
   «Charter §3.4», а не может ждать полной готовности EP-02 — ЭТОТ конкретный тест целенаправленно
   создаёт МИНИМАЛЬНУЮ фикстуру двух `tenant_id` без реального модуля тенантности, что допустимо, т.к.
   `users.tenant_id` — просто `uuid`-колонка, не требующая существования полноценной сущности `Tenant`
   для проверки `UNIQUE(tenant_id, phone_number)`): один и тот же номер телефона регистрируется через
   `verify` в обоих тенантах (два разных `otpRequestId`, два разных `X-Tenant-Slug` — упрощённый
   заголовок, читаемый временным резолвером тенанта, см. риски DTJ-023/024) → создаются ДВЕ РАЗНЫЕ
   строки `users` с разными `id`, оба JWT содержат корректный СВОЙ `tenantId`, попытка использовать
   JWT тенанта A для доступа к тестовому защищённому маршруту, эмулирующему проверку тенанта B, —
   ОТМЕЧЕНА как заглушка/`it.todo`, полноценная проверка `SRS-API-045/046` (кросс-тенантный доступ к
   ресурсу) — целиком зона EP-02 `CUJ-7'`, не дублируется здесь.

## Критерии приёмки

1. **Given** запущен полный сьют этого тикета, **When** `pnpm --filter @dorutj/api test:integration`,
   **Then** все 4 файла проходят на реальных Postgres+Redis (docker-compose тестовое окружение или
   testcontainers), без флейков при 3 последовательных прогонах подряд (гонки — самый частый источник
   нестабильных тестов, явно требовать повторяемость).
2. **Given** намеренно испорчена реализация (например, временно закомментирована проверка
   `rotated_at IS NOT NULL` в DTJ-025), **When** `refresh-reuse-detection.spec.ts` запущен, **Then**
   тест ПАДАЕТ — это верификационная санити-проверка самого тест-сьюта перед сдачей тикета (ловушка
   должна ловить, `02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1 «ловушка, которая перестала ловить,
   молчит об этом» — тот же принцип, применённый к security-тестам, а не только к линтерам).
3. **Негативный:** **Given** `otp-verify-race.spec.ts` запущен 10 раз подряд (нестабильные гонки
   иногда «случайно» проходят без реальной защиты), **When** каждый прогон, **Then** КАЖДЫЙ раз ровно
   одна `auth_sessions`-запись создаётся — не «обычно одна, иногда две».

## Тест-план

Этот тикет САМ является тест-планом (интеграционные security-тесты). Дополнительно:
- Прогон каждого файла с сознательно внесённой регрессией (приёмка 2) — фиксируется как ручной шаг
  ревью, не автоматизируется в CI (временная порча кода не коммитится).
- Все 4 файла — часть `pnpm test:integration` в `apps/api/package.json`, включены в `pnpm verify`
  через `turbo.json` пайплайн (сверить, что `test` таска включает `test:integration`, не только
  unit — если раздельные таски, добавить `test:integration` явным шагом `pnpm verify` или CI, в
  координации с EP-19, не переопределяя чужой `turbo.json`/CI-конфиг самостоятельно).

## Риски и подводные камни

- Тесты гонок (`otp-verify-race.spec.ts`, часть `otp-brute-force.spec.ts`) исторически самые
  нестабильные в любой кодовой базе — `Promise.all` не гарантирует ИСТИННУЮ одновременность на
  уровне сетевых пакетов, только параллельный старт на клиенте. Если тест окажется флейковым не
  из-за бага, а из-за характера теста, — уменьшать таймауты БД-транзакций/добавлять `SELECT ...
  FOR UPDATE` было проверено в самих use case тикетах (DTJ-024/025), а не здесь; если флейк
  сохраняется — эскалировать как находку, не «стабилизировать» увеличением задержек искусственно
  (это скрыло бы реальную гонку, а не проверило её).
- Фикстура «двух тенантов» в `phone-tenant-isolation.spec.ts` — намеренное упрощение (вставка сырых
  UUID вместо реальных `Tenant`-сущностей EP-02); если резолвер тенанта, который появится в EP-02, не
  будет принимать произвольный `X-Tenant-Slug`, а потребует реального существования тенанта в БД, этот
  тест придётся адаптировать при интеграции с EP-02 — не блокирует сдачу ЭТОГО тикета сейчас, но
  явный follow-up для владельца EP-02 на этапе его собственной приёмки.
