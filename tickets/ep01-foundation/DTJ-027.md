## Задача

R1-13 (`04-SCOPE-DECISION-PIVOT.md`) требует режим Telegram Mini App с первого дня — Telegram основной
канал в РТ (D-23), дешевле SMS. `identity`-контекст явно включает Telegram TWA как второй
`AuthProvider` (`10-domain-model.md` §«Ограниченные контексты»), поэтому реализуется в этом же эпике,
не откладывается на EP-16 (уведомления — отдельная зона, только КАНАЛ отправки, не аутентификация).

## Технический контекст: ещё один документационный пробел

`SRS-API-031` шаг 9 ссылается на таблицу `user_telegram_identities(user_id, telegram_user_id,
tenant_id)`, которая ОТСУТСТВУЕТ в 45-табличном DDL `docs/spec/11-database-schema.md` (та же природа
пробела, что уже зафиксирована для `idempotency_keys` в DTJ-017 и `auth_sessions` vs `refresh_tokens`
в DTJ-015). Решение — реализовать по прямой цитате `SRS-API-031`, минимальный состав колонок, без
додумывания сверх сказанного; точечно дополнить `11-database-schema.md`.

`SRS-API-031` — точный десятишаговый алгоритм проверки подписи Telegram WebApp `initData` (см. полный
текст в `docs/spec/12-api-conventions-auth-tenancy.md` §3.5, шаги 1-10, дословно):
1. Распарсить `initData` как `application/x-www-form-urlencoded`.
2. Извлечь и удалить поле `hash` (не участвует в контрольной строке).
3. Отсортировать ОСТАВШИЕСЯ пары по ключу лексикографически, собрать `data_check_string`
   (`"{key1}={value1}\n{key2}={value2}\n..."`, значения — как есть).
4. `secret_key = HMAC_SHA256(key="WebAppData", data=TELEGRAM_BOT_TOKEN)` (байтовый результат).
5. `computed_hash = HEX(HMAC_SHA256(key=secret_key, data=data_check_string))`.
6. Сравнить `computed_hash` с полем `hash` **constant-time** (`crypto.timingSafeEqual`) — несовпадение
   → `401 INVALID_TELEGRAM_INIT_DATA`.
7. Проверить `auth_date`: `now() - auth_date <= TELEGRAM_INIT_DATA_MAX_AGE_SECONDS` (ENV, дефолт 300)
   — просрочено → `401 TELEGRAM_AUTH_DATE_EXPIRED`.
8. Распарсить JSON-поле `user` (`{ id, first_name, last_name?, username?, language_code? }`).
9. Найти/создать `User` по `(tenant_id, telegram_user_id)` через `user_telegram_identities` — телефон
   НЕ обязателен на этом шаге.
10. Выпустить JWT/refresh как в `SRS-API-024/025`, `AuthSession.deviceLabel = 'telegram_twa'`.

`SRS-API-032`: `TELEGRAM_BOT_TOKEN` — per-tenant, из `tenant_settings.telegram_bot_token_ref`
(ссылка на секрет, не сам токен в открытом виде). Given тенант БЕЗ настроенного бота → `503
SERVICE_UNAVAILABLE`, `details.reason='telegram_bot_not_configured'` (не `404` — временное состояние
конфигурации). **Этот тикет НЕ может полноценно резолвить `tenant_settings.telegram_bot_token_ref`**
— таблица `tenant_settings` принадлежит EP-02 (ещё не существует по графу зависимостей волн, EP-01
первый). Решение: `TelegramInitDataVerifierPort` принимает `botToken: string` уже РЕЗОЛВЛЕННЫМ
параметром (не резолвит сам через `tenant_settings`) — вызывающий код (controller/use case) на
момент EP-01 передаёт `botToken` из простого ENV `TELEGRAM_BOT_TOKEN_NEUTRAL` (единственный
нейтральный бот, White-Label per-tenant боты — R3 функциональность, `04-SCOPE-DECISION-PIVOT.md` §5).

## Что сделать

1. `user-telegram-identities.schema.ts`: `id uuid PK`, `userId uuid NOT NULL REFERENCES users(id) ON
   DELETE CASCADE`, `telegramUserId bigint NOT NULL`, `tenantId uuid NOT NULL` (отложенный FK на
   `tenants`, тот же паттерн DTJ-014), `createdAt timestamptz NOT NULL default now()`, `UNIQUE
   (tenant_id, telegram_user_id)`.
2. `apps/api/migrations/0007_user_telegram_identities.sql`.
3. `telegram-init-data-verifier.port.ts`: `interface TelegramInitDataVerifierPort { verify(rawInitData:
   string, botToken: string, clock: ClockPort): Result<TelegramInitData,
   InvalidTelegramInitDataError | TelegramAuthDateExpiredError> }`, `TelegramInitData = { telegramUserId:
   number; firstName: string; lastName?: string; username?: string; languageCode?: string }`.
4. `telegram-init-data-verifier.adapter.ts`: реализация алгоритма шагов 1-8 выше дословно;
   `crypto.timingSafeEqual` для шага 6 (НЕ строковое `===` — таймингова атака иначе возможна).
5. `user-telegram-identities.repository.ts`: `findByTenantAndTelegramId(tenantId, telegramUserId)`,
   `create(userId, telegramUserId, tenantId)`.
6. `telegram-auth.use-case.ts`: `TelegramAuthUseCase.execute({ initData, tenantId, botToken,
   deviceLabel: 'telegram_twa' }): Promise<Result<{ accessToken, refreshToken }, ...>>` — шаги 9-10:
   найти `user_telegram_identities` → существует → взять `userId`; не существует → создать `User` с
   `role='customer'`, `phoneNumber=null`-подобное состояние (уточнение: `users.phone_number` —
   `NOT NULL` по схеме DTJ-014! Telegram-путь не имеет телефона на этом шаге — РЕШЕНИЕ: временный
   плейсхолдер `phoneNumber` невозможен без нарушения `unique_phone_per_tenant`/формата VO. Этот
   тикет фиксирует это как ОТКРЫТЫЙ ВОПРОС, требующий либо ослабления `NOT NULL` на
   `users.phone_number` отдельной эволюционной миграцией (пересмотр DTJ-014 схемы), либо отдельной
   таблицы `telegram_only_users`. Для R1 — принимается временное МИНИМАЛЬНОЕ решение: столбец
   `phone_number` делается `NULLABLE` этой же миграцией (шаг 2, `ALTER TABLE users ALTER COLUMN
   phone_number DROP NOT NULL` — дописывается в `0007_...sql`), `unique_phone_per_tenant` constraint
   в Postgres по умолчанию ИГНОРИРУЕТ строки с `NULL` в уникальном индексе (стандартное поведение
   `UNIQUE` — `NULL` не равен `NULL`), так что множественные Telegram-пользователи без телефона не
   конфликтуют друг с другом на этом constraint — задокументировать этот нюанс явно как ОБОСНОВАННОЕ,
   а не случайное поведение), затем `create` в `user_telegram_identities`; выпуск JWT/refresh
   переиспользует ТЕ ЖЕ порты, что DTJ-024 (`JwtSignerPort`, `AuthSessionsRepository`) — НЕ дублирует
   логику выдачи токенов.
7. `telegram-auth.dto.ts`: Zod `{ initData: z.string() }`.
8. `telegram-auth.controller.ts`: `POST /api/v1/auth/telegram`, `@Public()`. Резолвинг `botToken` —
   временно `process.env.TELEGRAM_BOT_TOKEN_NEUTRAL` (см. «Технический контекст»); отсутствует ENV →
   `503 SERVICE_UNAVAILABLE` с `details.reason='telegram_bot_not_configured'` (`SRS-API-032`,
   упрощённая версия без per-tenant резолва).

## Критерии приёмки

1. **Given** корректно подписанный `initData` (тестовая фикстура с известным `TELEGRAM_BOT_TOKEN` и
   вручную посчитанным `hash` по алгоритму), **When** `POST /auth/telegram`, **Then** `200` с парой
   токенов, создана строка `user_telegram_identities`.
2. **Given** `initData` с подделанным полем `user.id` (hash не пересчитан под изменение), **When**
   запрос, **Then** `401 INVALID_TELEGRAM_INIT_DATA` (constant-time сравнение отклоняет).
3. **Негативный:** **Given** валидный по подписи `initData`, но `auth_date` старше
   `TELEGRAM_INIT_DATA_MAX_AGE_SECONDS`, **When** запрос, **Then** `401
   TELEGRAM_AUTH_DATE_EXPIRED` (отдельный код от `INVALID_TELEGRAM_INIT_DATA` — разные причины).

## Тест-план

- Unit `TelegramInitDataVerifierAdapter`: валидная подпись (фикстура с реально посчитанным HMAC по
  тестовому боту-токену — не мок, реальный алгоритм на известных входных данных), подделанная подпись,
  просроченный `auth_date` (граница включительно/исключительно — сверить точную формулировку
  `SRS-API-031` шаг 7 «`<=`» при реализации).
- Unit `TelegramAuthUseCase`: новый Telegram-пользователь (создание с `phoneNumber=null`), повторный
  вход того же `telegramUserId` (find, не create дважды).
- Integration: `ALTER COLUMN phone_number DROP NOT NULL` не ломает существующие тесты DTJ-014/024
  (регрессионная проверка — `unique_phone_per_tenant` по-прежнему отклоняет дубли НЕ-null телефонов).
- Порог покрытия `application/` — ≥90%, `infrastructure/` (crypto-адаптер) — ≥70%.

## Риски и подводные камни

- **Самый существенный архитектурный риск тикета**: снятие `NOT NULL` с `users.phone_number` —
  решение, принятое ЭТИМ тикетом задним числом относительно DTJ-014, а не заложенное изначально в
  DDL `11-database-schema.md` (там `phone_number VARCHAR(20) NOT NULL` дан без оговорок). Это
  прямое следствие требования `SRS-API-031` шаг 9 («телефон НЕ обязателен на этом шаге») —
  расхождение между DDL-таблицей 15 и прозой auth-документа, которое всплывает ТОЛЬКО при реализации
  Telegram-пути. Если архитектор на ревью не согласится с этим решением, альтернатива — отдельная
  таблица для Telegram-only идентичностей БЕЗ строки `users` вовсе до момента, пока клиент не укажет
  телефон при оформлении первого заказа (что ближе к букве `SRS-API-031` «телефон запрашивается
  отдельно при оформлении заказа»); эта альтернатива сложнее (два разных типа «пользователя без
  телефона» в системе) — решение тикета выбирает ПРОСТОТУ (одна таблица, nullable-поле) как более
  соответствующую духу `02-CLEAN-ARCHITECTURE-AND-CODE.md` C15 (не городить абстракцию без второго
  явного требования).
- `TELEGRAM_BOT_TOKEN_NEUTRAL` — упрощение относительно полного `SRS-API-032` (per-tenant токен из
  `tenant_settings`); когда EP-02/White-Label появится, эта временная ENV-переменная должна быть
  заменена на резолвинг из `tenant_settings.telegram_bot_token_ref` — не блокирует R1 (нейтральный
  тенант — единственный реально используемый в MVP по `04-SCOPE-DECISION-PIVOT.md`), но зафиксировать
  как явный технический долг для перехода к White-Label (R3).
