## Задача

Access-токен живёт 15 минут (`SRS-API-024`) — без ротации refresh-токена ни один клиент (`apps/web`,
будущие Flutter-приложения R2) не может поддерживать сессию дольше этого окна без повторного OTP.
Обнаружение переиспользования — единственная защита от кражи refresh-токена (например, из
скомпрометированного `localStorage`/лога): если украденный токен использован раньше легитимного
клиента, атака обнаруживается на следующей ротации легитимного клиента.

## Технический контекст

`SRS-API-026`: сервер находит `auth_sessions` по `sha256(refreshToken)`. Валиден → (1) текущий refresh
помечается `rotated_at=now()`; (2) выпускается НОВЫЙ access + НОВЫЙ refresh (тот же `family_id`, тот
же `absoluteExpiresAt`); (3) старый refresh больше не годен ни для чего, кроме проверки реюза.
`SRS-API-027`: предъявлен токен, чей хеш совпадает с записью, УЖЕ имеющей `rotated_at IS NOT NULL`
(звено из ПРОШЛОГО, не текущее) → обнаружение переиспользования: ВСЕ `auth_sessions` с тем же
`family_id` немедленно `revoked_at=now(), revoke_reason='reuse_detected'`, ответ `401
REFRESH_TOKEN_REUSE_DETECTED`, структурное `warn`-событие в `pino` (не пользовательский `audit_log`).
`SRS-API-028`: токен просрочен по `absoluteExpiresAt`, но НЕ был использован повторно → `401
REFRESH_TOKEN_INVALID` (штатное истечение, не атака).

## Что сделать

1. `refresh.dto.ts`: Zod `{ refreshToken: z.string() }`.
2. `refresh-token.use-case.ts`: `RefreshTokenUseCase.execute({ refreshToken: string }):
   Promise<Result<{ accessToken: string; refreshToken: string }, RefreshTokenInvalidError |
   RefreshTokenReuseDetectedError>>`:
   1. `tokenHash = sha256(refreshToken)` → `AuthSessionsRepository.findByTokenHash(tokenHash)`.
   2. Given не найдено → `RefreshTokenInvalidError` (`401 REFRESH_TOKEN_INVALID`) — не раскрывать
      причину подробнее (не отличать «никогда не существовал» от «давно истёк и вычищен»).
   3. Given найдено, `rotated_at IS NOT NULL` (это прошлое звено цепочки, не текущее) →
      **обнаружение переиспользования**: `AuthSessionsRepository.revokeAllByFamilyId(familyId,
      reason='reuse_detected')` (одним `UPDATE ... WHERE family_id = :familyId AND revoked_at IS
      NULL`, атомарно), лог `pino.warn({ userId, familyId, ipAddress, msg: 'refresh token reuse
      detected' })`, возврат `RefreshTokenReuseDetectedError` (`401
      REFRESH_TOKEN_REUSE_DETECTED`).
   4. Given найдено, `revoked_at IS NOT NULL` (уже отозвана — logout или предыдущий reuse) →
      `RefreshTokenInvalidError` (не reuse — уже обработанный случай, повторный reuse-алерт на
      мёртвую сессию не несёт новой информации).
   5. Given `absoluteExpiresAt < clock.now()` → `RefreshTokenInvalidError` (штатное истечение,
      `SRS-API-028`, НЕ reuse detection — проверяется ДО и НЕЗАВИСИМО от проверки `rotated_at`, чтобы
      не спутать «просрочен» с «переиспользован»).
   6. Given всё валидно → транзакция: `rotated_at = now()` на текущей строке; создать НОВУЮ строку
      `auth_sessions` с тем же `familyId`, `sessionCreatedAt` (скопирован от текущей — НЕ
      `now()`), `absoluteExpiresAt` (тот же, не продлевается, `SRS-API-025`), новый `refreshTokenHash`;
      выпустить новый `accessToken` (`JwtSignerPort.sign`, DTJ-022, те же `role`/`tenantId`/... что
      были в исходном JWT — читаются из `users`-строки заново на КАЖДОЙ ротации, не кэшируются в
      `auth_sessions`, чтобы смена роли пользователем администратором отражалась на следующем refresh).
   7. Возврат новой пары токенов.
3. `refresh.controller.ts`: `POST /api/v1/auth/refresh`, `@Public()` (сам refresh-токен — механизм
   аутентификации этого запроса, не JWT `Authorization`-заголовок).

## Критерии приёмки

1. **Given** валидный, не ротированный refresh-токен, **When** `POST /auth/refresh`, **Then** `200`
   с НОВОЙ парой токенов, старый refresh-токен помечен `rotated_at`, `family_id` новой строки равен
   `family_id` старой.
2. **Given** refresh-токен, который УЖЕ был использован для ротации ранее (предъявлен повторно —
   симуляция кражи), **When** `POST /auth/refresh`, **Then** `401
   REFRESH_TOKEN_REUSE_DETECTED`, И легитимный НОВЫЙ токен (выданный на шаге 1 этого сценария) ТОЖЕ
   становится невалиден (проверяется отдельным вызовом `/auth/refresh` с новым токеном сразу после —
   тоже `401`, т.к. `revoked_at` теперь заполнен на всей цепочке).
3. **Негативный:** **Given** refresh-токен старше `absoluteExpiresAt` (симуляция — тестовая фикстура
   с `absoluteExpiresAt` в прошлом), **When** `POST /auth/refresh`, **Then** `401
   REFRESH_TOKEN_INVALID` (НЕ `REUSE_DETECTED`, даже если случайно `rotated_at` тоже был бы заполнен —
   проверка порядка условий в use case гарантирует правильный код).

## Тест-план

- Unit: все ветки `execute()` (не найден, reuse, уже отозван, просрочен, успех) — мок-репозиторий.
- Integration: реальная последовательная ротация 3 раза подряд — каждый следующий токен работает,
  предыдущий больше не годен для НОВОЙ ротации (но остаётся годен для проверки reuse на нём самом,
  если предъявлен — задокументировать явно этот нюанс тестом: предъявление ПЕРВОГО из трёх токенов
  ПОСЛЕ третьей ротации всё ещё триггерит reuse detection, не «токен не найден»).
- Integration: полный сценарий кражи (приёмка 2) — легитимный refresh, кража старого токена
  (гипотетически), атакующий использует украденный СТАРЫЙ (уже ротированный легитимным клиентом)
  токен → reuse detected → легитимная НОВАЯ сессия тоже отозвана (задокументированное
  security-поведение: жертва вынуждена перелогиниться, это ожидаемо и корректно).

## Риски и подводные камни

- Порядок проверок (просрочка ПЕРЕД reuse-detection, шаг 2.5 до подразумеваемого использования
  `rotated_at`) — важен для корректности кода ошибки (приёмка 3); если разработчик поменяет порядок
  местами, тесты этого тикета обязаны это поймать — явно включить негативный кейс «одновременно
  `rotated_at` заполнен И `absoluteExpiresAt` в прошлом» в unit-тесты, не полагаться только на
  раздельные позитивные кейсы.
- `absoluteExpiresAt`/`sessionCreatedAt` копируются на КАЖДОЙ ротации из предыдущей строки — если
  разработчик по ошибке пересчитает `absoluteExpiresAt = now() + 30 дней` заново при ротации,
  сессия станет ПРОДЛЕВАЕМОЙ бесконечно при регулярном использовании — прямое нарушение `SRS-API-025`
  («фиксирован в момент ПЕРВОЙ выдачи... НЕ продлевается»). Тест-план явно требует проверку этого
  инварианта на 3 последовательных ротациях (не только на одной).
