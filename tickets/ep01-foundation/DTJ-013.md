## Задача

`enums.schema.ts` — ОДИН общий файл на всю систему (не по модулю на файл), куда `drizzle-kit generate`
диффит `CREATE TYPE`; `11-database-schema.md` §«Маппинг на Drizzle» показывает пример именно с
несколькими enum'ами разных модулей (`orderStatusEnum`, `controlCategoryEnum`, `escrowEntryTypeEnum`)
в одном файле `enums.schema.ts`. Этот тикет создаёт файл и заводит в него ДВА enum'а, реально нужных
EP-01 (`user_role`, `otp_purpose`) — по аналогии с правилом `packages/contracts` (DTJ-005): последующие
эпики ДОПИСЫВАЮТ свои `pgEnum(...)` в конец ЭТОГО ЖЕ файла, не создают отдельные файлы на модуль.

## Технический контекст

`SRS-DB-008`: каждый enum, управляющий state machine, — единственный источник допустимых значений на
уровне БД (первый рубеж защиты), сами переходы валидируются в domain. `SRS-DB-009`: добавление НОВОГО
значения в СУЩЕСТВУЮЩИЙ enum (`ALTER TYPE ... ADD VALUE`) — отдельная миграция ВНЕ транзакции
(например будущая `0019_order_status_add_confirmed.sql` из D-25, зона EP-09/EP-10, не этого тикета) —
этот тикет создаёт ТОЛЬКО начальные `CREATE TYPE`, не про эволюцию существующих значений.

`user_role` — из `10-domain-model.md`/`12-api-conventions-auth-tenancy.md`: `customer`, `pharmacist`,
`courier`, `pharmacy_admin`, `super_admin`, `support_agent` (расширение REQ-DISPUTE-18 поверх
`tz.log` §II.2, значения аддитивны, не переименованы). `otp_purpose` — `'login' | 'delivery_handover'`
(SRS-DOM-080).

## Что сделать

1. `apps/api/src/infrastructure/db/schema/enums.schema.ts`:
   ```typescript
   import { pgEnum } from 'drizzle-orm/pg-core';

   export const userRoleEnum = pgEnum('user_role', [
     'customer', 'pharmacist', 'courier', 'pharmacy_admin', 'super_admin', 'support_agent',
   ]);

   export const otpPurposeEnum = pgEnum('otp_purpose', ['login', 'delivery_handover']);

   // Следующие эпики добавляют СВОИ pgEnum(...) СЮДА ЖЕ (см. DTJ-013 файла-владельца, EP-01) —
   // не заводить отдельный enums-файл на модуль. Конфликты слияния при параллельной разработке
   // решаются rebase (низкий риск — только добавление новых export-констант в конец файла).
   ```
2. `apps/api/migrations/0002_enums.sql` (сгенерировано `drizzle-kit generate` из шага 1):
   `CREATE TYPE user_role AS ENUM (...)`, `CREATE TYPE otp_purpose AS ENUM (...)`.
3. Проверить порядок применения: `0002` идёт СТРОГО после `0001_extensions.sql` (enum'ы не зависят от
   расширений напрямую, но нумерация — по порядку создания файлов, `drizzle-kit generate` присваивает
   номер автоматически).

## Критерии приёмки

1. **Given** применена `0002_enums.sql` на чистой БД (после `0001`), **When** `SELECT
   unnest(enum_range(NULL::user_role))`, **Then** возвращает ровно 6 значений в порядке, указанном
   в `enums.schema.ts`.
2. **Given** тот же запрос для `otp_purpose`, **When** выполнен, **Then** ровно 2 значения
   (`login`, `delivery_handover`).
3. **Негативный:** **Given** попытка вставить в колонку типа `user_role` значение `'dispatcher'`
   (несуществующая роль — упомянута в `12-api-conventions-auth-tenancy.md` §4.1 как ЯВНО НЕ заводимая
   отдельной ролью), **When** `INSERT`, **Then** Postgres отклоняет с ошибкой `invalid input value for
   enum user_role` — БД, а не только приложение, отвергает произвольную строку (SRS-DB-008).

## Риски и подводные камни

- Порядок значений в `pgEnum([...])` (TS-массив) — это порядок `CREATE TYPE`, не порядок
  бизнес-логики; для `user_role`/`otp_purpose` порядок не несёт семантики (в отличие от, например,
  `order_status`, где `SRS-DB-049` явно требует `ADD VALUE 'confirmed' BEFORE 'paid_escrow'` —
  этого тикета не касается, но следующий эпик, добавляющий `order_status` в этот же файл, ОБЯЗАН
  прочитать `SRS-DB-049`/D-25 прежде чем менять порядок).
- Единый файл `enums.schema.ts`, растущий всеми эпиками, — предсказуемая точка конфликтов слияния при
  параллельной разработке волны 6+ (несколько эпиков одновременно добавляют свои enum'ы) — та же
  природа риска, что и `packages/contracts` баррель (`tickets/00-EPICS.md` §«Пересекающееся владение»
  п.3), решается rebase, не архитектурным пересмотром.
