## Задача

OTP-запрос (DTJ-023 этого же эпика) — первый реальный потребитель специфичного, более строгого
лимита, чем глобальный дефолт (`SRS-API-012`: «`POST /api/v1/auth/otp/request` — см. §3.1
(специфичный, ниже общего)»). Без общего механизма rate-limit каждый следующий эндпоинт с особым
лимитом (1С-батч, поиск, ...) реализовывал бы его по-своему — этот тикет даёт декоратор
`@RateLimit(...)`, переиспользуемый любым модулем.

## Технический контекст

`SRS-API-012`: двухуровневая модель — глобальный дефолт на инстанс (`RATE_LIMIT_ANON_PER_MIN=100` по
IP, `RATE_LIMIT_USER_PER_MIN=300` по `userId`) + переопределение per-route декоратором
`@RateLimit({ max, windowSec, keyBy })`. `SRS-API-013`: превышение → `429 { error: { code:
'RATE_LIMITED', ... } }` + заголовки `X-RateLimit-Limit`/`X-RateLimit-Remaining`/`X-RateLimit-Reset`/
`Retry-After`; заголовки `X-RateLimit-*` присутствуют на КАЖДОМ ответе лимитируемого маршрута, не
только при `429`.

Специфичные лимиты `POST /auth/otp/request` (`OTP_REQUEST_COOLDOWN_SECONDS=60`,
`OTP_REQUEST_MAX_PER_10MIN=3`, `OTP_REQUEST_MAX_PER_DAY=10`, `OTP_REQUEST_MAX_PER_IP_PER_HOUR=20`) и
`POST /auth/otp/verify` (`OTP_VERIFY_MAX_ATTEMPTS=5` по `otpRequestId`) — реализуются в DTJ-023/024
(используют декоратор/guard ЭТОГО тикета, но конкретные числа и ключи — их зона, не дублировать здесь
заранее без контроллера, которому это принадлежит).

## Что сделать

1. `rate-limit.module.ts`: регистрирует `@fastify/rate-limit` с Redis store (`@fastify/rate-limit`
   поддерживает кастомный store через `redis`-опцию — использовать существующее `ioredis`-соединение,
   не отдельный клиент); глобальный дефолт — два уровня: анонимный по IP (`RATE_LIMIT_ANON_PER_MIN`),
   аутентифицированный по `userId` из `RequestContext` (`RATE_LIMIT_USER_PER_MIN`) — выбор ключа
   зависит от того, есть ли `userId` в контексте на момент запроса (заполняется `AuthGuard`, DTJ-022,
   значит порядок middleware/guard важен — `RateLimitGuard` обязан выполняться ПОСЛЕ `AuthGuard`,
   чтобы `userId` уже был в контексте; задокументировать порядок явно в `app.module.ts`).
2. `rate-limit.decorator.ts`: `@RateLimit({ max: number; windowSec: number; keyBy: 'ip' | 'userId' |
   ((req) => string) })` — `SetMetadata`, читается `RateLimitGuard`.
3. `rate-limit.guard.ts`: `RateLimitGuard implements CanActivate` — читает metadata через `Reflector`,
   если отсутствует — применяется ТОЛЬКО глобальный дефолт (уже обеспечен `@fastify/rate-limit` на
   уровне плагина, guard в этом случае не добавляет ничего сверх); если задан `@RateLimit(...)` —
   выполняет собственную проверку через Redis (`INCR` + `EXPIRE` окна, ключ
   `` `ratelimit:${routeId}:${resolvedKey}` ``), превышение → бросает `RateLimitedError`
   (расширяет `DomainError`/использует существующий `ErrorCode.RATE_LIMITED` из `packages/contracts`,
   DTJ-005) — маппится `TransportExceptionFilter`/`DomainExceptionFilter` (DTJ-018) в `429` с телом
   по `SRS-API-013`; ЛЮБОЙ ответ (успех/429) этого маршрута получает заголовки `X-RateLimit-*`
   (проставляются в `onSend`-хуке Fastify или интерсептором — не только в ветке ошибки).

## Критерии приёмки

1. **Given** глобальный дефолт `RATE_LIMIT_ANON_PER_MIN=100`, **When** анонимный клиент делает 101-й
   запрос за минуту с одного IP, **Then** `429`, заголовок `Retry-After` присутствует и корректен
   (секунды до сброса окна).
2. **Given** эндпоинт с `@RateLimit({ max: 3, windowSec: 600, keyBy: 'ip' })`, **When** 4-й запрос
   за 10 минут с того же IP, **Then** `429 RATE_LIMITED`, заголовки `X-RateLimit-Limit=3`,
   `X-RateLimit-Remaining=0` присутствуют.
3. **Негативный:** **Given** тот же эндпоинт, **When** запросы идут ПОД лимитом (например 2 из 3),
   **Then** заголовки `X-RateLimit-Remaining` корректно уменьшаются на каждом успешном ответе, а не
   только появляются при превышении.

## Тест-план

- Unit: `RateLimitGuard` — резолвинг ключа для всех трёх вариантов `keyBy` (`'ip'`, `'userId'`,
  функция), поведение при отсутствии metadata (глобальный дефолт не дублируется guard'ом).
- Integration (реальный Redis): окно `windowSec` — счётчик сбрасывается по истечении, не раньше;
  параллельные запросы (гонка на `INCR`) не дают «просочиться» лишнему запросу сверх лимита.
- Coverage — ≥70%.
