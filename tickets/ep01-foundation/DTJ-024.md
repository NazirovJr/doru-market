## Задача

Шаг 2 OTP-логина — единственный путь получить JWT для человеческих ролей вне Telegram TWA. Это тикет,
после которого критический путь `EP-01→EP-02→EP-03→...` впервые может авторизовать реального
пользователя — все последующие защищённые эндпоинты ЛЮБОГО эпика опираются на токен, выданный здесь.

## Технический контекст

`SRS-API-021`: сравнение по `sha256(candidateCode + otpRequestId)` против сохранённого `code_hash`.
`SRS-API-022`: счётчик неверных попыток — по `otpRequestId` (не по `phone`), `OTP_VERIFY_MAX_ATTEMPTS=5`
— 6-я попытка (ЛЮБОЙ код) → `423 OTP_LOCKED`, `otpRequestId` окончательно недействителен. Это
ПРЕСЕНТЕЙШН-уровневый лимит, ОТДЕЛЬНЫЙ от `maxAttempts` внутри самого `OtpCode` VO (который для
`purpose='login'` равен `Infinity`, DTJ-010) — то есть блокировка на 5-й попытке реализуется здесь, в
use case/эндпоинте, явным счётчиком, ПОВЕРХ вызова `otpCode.verify(...)`, который сам по себе
никогда не заблокирует `login`-код по числу попыток.

`SRS-API-023`: код верен и не истёк → (1) find-or-create `User` по `(tenantId, phone)` (создание —
ТОЛЬКО с ролью `customer`, `SRS-API-018`); (2) создаётся `auth_sessions`-запись (device fingerprint из
`User-Agent`, `ipAddress`); (3) выпускается пара токенов; (4) `otpRequestId` помечается `consumed`
— повторный `verify` с тем же `otpRequestId`, даже верным кодом, → `400 OTP_MISMATCH`
(`SRS-DOM-082 alreadyConsumed`). `SRS-API-071` (гонка двух вкладок): первая, дошедшая до БД, помечает
`consumed=true` внутри транзакции с блокировкой строки (`SELECT ... FOR UPDATE`).

## Что сделать

1. `auth-sessions.repository.ts`: `AuthSessionsRepository` — `create(command): Promise<{ id: string;
   refreshToken: string }>` (генерирует опаковый refresh-токен через `crypto.randomBytes(32)`,
   персистирует ТОЛЬКО `sha256(refreshToken)`, возвращает сырой токен вызывающему коду ровно один раз
   — он больше нигде не хранится в открытом виде, `SRS-API-025`), `findActiveByUserId(userId)`
   (для будущего DTJ-026), поддержка транзакционного `unitOfWork`-паттерна для атомарности с
   `otp_codes.consumed_at` (шаг 2 ниже).
2. `verify-otp.dto.ts`: Zod-схема `{ otpRequestId: z.string().uuid(); code: z.string().length(6) }`.
3. `verify-otp.use-case.ts`: `VerifyOtpUseCase.execute({ otpRequestId, code, tenantId, deviceLabel,
   userAgent, ipAddress }): Promise<Result<{ accessToken: string; refreshToken: string; user: {...}
   }, OtpExpiredError | OtpMismatchError | OtpAttemptsExceededError>>`:
   1. Открывает транзакцию (`unitOfWork.run`), внутри — `SELECT ... FOR UPDATE` строки `otp_codes`
      по `otpRequestId` (пессимистичная блокировка — реализует `SRS-API-071` против гонки двух
      конкурентных вкладок).
   2. Given строка не найдена → `OtpMismatchError` (не раскрывать «не существует» отдельным кодом —
      единообразие с обычным неверным кодом, не давать способ перебором узнавать валидность
      `otpRequestId`).
   3. Given `presentationAttemptsCounter(otpRequestId) >= OTP_VERIFY_MAX_ATTEMPTS` (счётчик — ОТДЕЛЬНОЕ
      Redis-поле `otp_verify_attempts:{otpRequestId}`, НЕ поле БД `otp_codes.attempts_used`, которое
      принадлежит domain-модели VO с иной семантикой попыток) → `OtpAttemptsExceededError`
      (`423 OTP_LOCKED`), БЕЗ сравнения кода, `otpRequestId` помечается недействительным навсегда
      (например, отдельным флагом или просто оставлением `consumed_at` не заполненным, но counter
      навсегда `>= max` — Redis-ключ без TTL-сброса до истечения самого `otpRequestId`, задать TTL
      counter'а равным `ttlSeconds` OTP, т.к. после истечения кода счётчик всё равно бессмыслен).
   4. `codeHash = sha256(code + otpRequestId)` → `otpCode.verify(codeHash, clock)` (VO из DTJ-010).
      Given `Result.err` (истёк/несовпадение) → инкремент Redis-счётчика попыток, персистировать
      обновлённый `OtpCode` (для несовпадения — `attemptsUsed` растёт и на уровне VO тоже, хотя он не
      блокирует `login` сам по себе — сохраняется для аудита/консистентности данных), вернуть
      соответствующую ошибку.
   5. Given успех → find-or-create `User` (`UsersRepository.findByTenantAndPhone`, при отсутствии —
      `UsersRepository.create({ tenantId, phoneNumber: phone, role: 'customer' })` — `phone`
      восстанавливается из `otp_codes.subject_ref`, НЕ передаётся отдельно клиентом в `verify`-запросе,
      что дополнительно защищает от подмены номера между `request` и `verify`).
   6. `AuthSessionsRepository.create({ userId, deviceLabel, userAgent, ipAddress })` — новый
      `family_id` (первая сессия цепочки), `sessionCreatedAt = issuedAt = now()`,
      `absoluteExpiresAt = now() + 30 дней`.
   7. `JwtSignerPort.sign({ sub: user.id, role: user.role, tenantId: user.tenantId, pharmacyId:
      user.pharmacyId, chainId: user.chainId, sessionId: authSession.id, jti: idGenerator.generate() })`
      (DTJ-022).
   8. Помечает `otp_codes.consumed_at = now()` (та же транзакция, шаг 1).
   9. Коммит транзакции → возврат `{ accessToken, refreshToken, user }`.
4. `otp-verify.controller.ts`: `POST /api/v1/auth/otp/verify`, `@Public()`. Извлекает `deviceLabel`
   (эвристика из `User-Agent`, простая — не полноценный UA-parser, «browser/mobile-app» достаточно
   для R1), `userAgent`/`ipAddress` из запроса. Ответ — `200 { data: { accessToken, refreshToken,
   user: { id, role, tenantId, phoneNumber, fullName } } }`.

## Критерии приёмки

1. **Given** корректный `otpRequestId`+код, новый номер телефона, **When** `POST /auth/otp/verify`,
   **Then** `200`, создана строка `users` с `role='customer'`, создана `auth_sessions`-запись,
   `accessToken` декодируется валидным JWT с корректными claims.
2. **Given** тот же `otpRequestId` вызван ПОВТОРНО с ВЕРНЫМ кодом после успешного первого `verify`,
   **When** запрос, **Then** `400 OTP_MISMATCH` (`alreadyConsumed`), НЕ создаётся вторая
   `auth_sessions`-запись.
3. **Негативный:** **Given** 6-я подряд попытка (5 неверных + эта, независимо от того, верен ли код
   именно этой попытки) на один `otpRequestId`, **When** `POST /auth/otp/verify`, **Then** `423
   OTP_LOCKED`, канонический текст ошибки — `ux.error.otp_locked` («...Запросите новый код через
   SMS/Telegram», `docs/spec/30-ux-screens-and-flows.md` §5) в `error.message`.

## Тест-план

- Unit `VerifyOtpUseCase`: успех с новым пользователем; успех с существующим пользователем (не
  дублирует `users`-строку); истёкший код; неверный код (счётчик растёт); 6-я попытка блокирует
  независимо от корректности кода (приёмка 3); повторный `verify` уже потреблённого `otpRequestId`.
- Integration: гонка двух конкурентных запросов с одним `otpRequestId` и верным кодом (`Promise.all`)
  — ровно ОДИН успешен, второй получает `OTP_MISMATCH` (реальная БД с `SELECT FOR UPDATE`, не мок).
- Integration: полный HTTP-путь `request` → `verify` → декодирование `accessToken` → запрос к
  защищённому тестовому маршруту с `@Roles('customer')` проходит.
- Порог покрытия `application/` — ≥90%.

## Риски и подводные камни

- Redis-счётчик `otp_verify_attempts:{otpRequestId}` — ОТДЕЛЬНАЯ сущность от
  `otp_codes.attempts_used` (поле VO из DTJ-010). Их назначение РАЗНОЕ (presentation-лимит на
  попытки verify для `login` vs domain-модель попыток, которая для `login` не блокирует сама по
  себе) — риск, что будущий разработчик решит, что это дублирование, и уберёт один из счётчиков,
  сломав или анти-брутфорс, или аудит. Явно задокументировано в шаге 3.3/3.4.
- `deviceLabel` из `User-Agent` — простая эвристика, НЕ полноценный парсер устройств; если понадобится
  точная детекция (для UI списка сессий, DTJ-026), это улучшение можно внести туда же без изменения
  схемы `auth_sessions` (поле уже `varchar`, вмещает любую строку).
- `TenantId`/`TenantResolutionMiddleware` — тот же временный риск, что в DTJ-023 (EP-02 ещё не
  готов на момент этого тикета в критическом пути волн) — контроллер передаёт `tenantId` тем же
  временным механизмом.
