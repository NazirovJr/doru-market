## Задача

`POST /api/v1/orders` (EP-09), загрузка рецепта (EP-23 модуль), возвраты, разрешение споров, приём
наличных курьером, ротация 1С-ключа — ВСЕ обязаны требовать `Idempotency-Key` (`SRS-API-009`). Эти
эндпоинты появятся в других эпиках позже, но сам механизм — общая API-конвенция, которую логично
завести один раз здесь: последующий эпик просто ставит декоратор `@Idempotent()` на свой контроллер,
не переизобретая логику сравнения тел запроса и обработки гонки.

## Технический контекст

`SRS-API-010`: `Idempotency-Key = K` уже сохранён для `(userId, endpoint)` с ЗАВЕРШЁННЫМ ответом →
повторный запрос с тем же `K` И тем же телом (`sha256(body)` совпадает) → возвращается СОХРАНЁННЫЙ
ответ БЕЗ повторного выполнения. Тот же `K`, тело отличается → `409 IDEMPOTENCY_KEY_CONFLICT`. Запрос
с `K` ЕЩЁ обрабатывается (конкурентный дубль) → `409 IDEMPOTENCY_KEY_CONFLICT` немедленно (не
блокируется в ожидании первого). `SRS-API-076`: истечение TTL (`IDEMPOTENCY_KEY_TTL_HOURS`, ASSUMPTION
24) → запрос с тем же ключом после очистки обрабатывается КАК НОВЫЙ.

Таблица `idempotency_keys` — из DTJ-017 (тот же эпик). Уникальный `INSERT` до выполнения use case — и
есть механизм обнаружения гонки (см. DTJ-017 «Что сделать» шаг 1: `status='processing'` создаётся
СРАЗУ при получении заголовка).

## Что сделать

1. `idempotent.decorator.ts`: `@Idempotent()` — method decorator, устанавливает metadata-флаг,
   читаемый интерсептором (по аналогии с `@Roles(...)` из будущего DTJ-022 — тот же паттерн Nest
   `SetMetadata`/`Reflector`).
2. `idempotency-keys.repository.ts`: `IdempotencyKeysRepository` — `findByTriple(userId, endpoint, key)`,
   `createProcessing(userId, endpoint, key, requestHash)` (`INSERT ... status='processing'` — ошибка
   `UNIQUE`-constraint пробрасывается как есть, интерсептор её ловит), `markCompleted(id, responseStatus,
   responseBody)`.
3. `idempotency.interceptor.ts`: `IdempotencyInterceptor implements NestInterceptor` — активен только
   на маршрутах с `@Idempotent()` (через `Reflector`):
   1. Given маршрут помечен `@Idempotent()` И заголовок `Idempotency-Key` отсутствует →
      `400 IDEMPOTENCY_KEY_REQUIRED` (`SRS-API-009`), ДО вызова контроллера.
   2. Given заголовок есть, но НЕ валидный UUID v4 → `400 VALIDATION_ERROR` (не молчаливое принятие
      произвольной строки).
   3. `requestHash = sha256(JSON.stringify(rawBody))` (канонический порядок сериализации — из уже
      распарсенного Fastify body, не пересобирать заново; задокументировать нюанс, что порядок ключей
      JSON влияет на хеш — риск ложного `409` на семантически одинаковом, но по-другому
      сериализованном теле, зафиксировать как известное ограничение, не решать сортировкой ключей в
      этом тикете без явного запроса — усложнение без второго требования, C15).
   4. `findByTriple(userId, endpoint, key)`: НЕ найдено → `createProcessing(...)`, при успехе — вызов
      контроллера, на завершение — `markCompleted(...)`, ответ возвращается клиенту как обычно.
      `createProcessing` бросил `UNIQUE`-конфликт (гонка, кто-то вставил параллельно) →
      `409 IDEMPOTENCY_KEY_CONFLICT` немедленно, use case НЕ вызывается.
   5. Найдено, `status='processing'` → `409 IDEMPOTENCY_KEY_CONFLICT` (ещё обрабатывается).
   6. Найдено, `status='completed'`, `requestHash` совпадает → возвращается СОХРАНЁННЫЙ
      `responseStatus`/`responseBody`, use case НЕ вызывается повторно.
   7. Найдено, `status='completed'`, `requestHash` НЕ совпадает → `409 IDEMPOTENCY_KEY_CONFLICT`.
4. `idempotency-cleanup.processor.ts` (`apps/worker`): BullMQ repeatable job (cron, раз в час,
   ASSUMPTION) — `DELETE FROM idempotency_keys WHERE created_at < now() - INTERVAL
   'IDEMPOTENCY_KEY_TTL_HOURS hours'` (значение из ENV, не магическое число) — реализует `SRS-API-076`
   (после удаления повторный запрос с тем же `K` обрабатывается как новый, естественное следствие
   отсутствия строки).

## Критерии приёмки

1. **Given** первый запрос с `Idempotency-Key=K` завершился `201`, **When** повторный запрос с тем же
   `K` и тем же телом, **Then** возвращается тот же `201` с тем же телом, БЕЗ повторного создания
   ресурса (use case вызван ровно один раз — проверяется мок-шпионом на use case в тесте).
2. **Given** два запроса с одним `K` отправлены КОНКУРЕНТНО (симуляция гонки — оба доходят до
   `createProcessing` почти одновременно), **When** оба обрабатываются, **Then** ровно один получает
   `200`/`201` (успешный путь use case), второй немедленно `409 IDEMPOTENCY_KEY_CONFLICT` — не ждёт
   первого.
3. **Негативный:** **Given** тот же `K`, но тело запроса отличается от первого по значению хотя бы
   одного поля, **When** повторный запрос, **Then** `409 IDEMPOTENCY_KEY_CONFLICT` (не выполняет
   use case, не возвращает сохранённый ответ первого запроса).

## Риски и подводные камни

- `sha256(JSON.stringify(rawBody))` чувствителен к порядку ключей — два семантически идентичных, но
  по-разному сериализованных клиентом тела (маловероятно для типового JSON-клиента, но теоретически
  возможно) дадут РАЗНЫЙ хеш → ложный `409 IDEMPOTENCY_KEY_CONFLICT` вместо возврата кэша. Осознанное
  упрощение (детерминированная канонизация JSON — усложнение без прямого требования в SRS), задокументировано
  явно в шаге 3 «Что сделать» — если станет реальной проблемой на практике, canonicalization
  (сортировка ключей) добавляется отдельным follow-up.
- Интерсептор читает `userId` из `RequestContext`/JWT (DTJ-022 того же эпика, но по времени волны
  этот тикет реализуется ПОСЛЕ него — `depends_on` не включает DTJ-022 явно, т.к. интерсептор технически
  МОЖЕТ быть написан раньше с заглушкой `userId`, но реальное тестирование end-to-end потребует
  готового `AuthGuard`; если порядок реализации внутри эпика пойдёт иначе, скорректировать
  `depends_on` вручную при планировании спринта — граф эпика это не блокирует, `orders:create`
  (первый реальный потребитель `@Idempotent()`) всё равно относится к EP-09, что заведомо позже).
