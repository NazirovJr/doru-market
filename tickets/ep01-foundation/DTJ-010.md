## Задача

`OtpCode` — единственный VO с ДВУМЯ независимыми потребителями с первого дня R1: OTP-логин
(`purpose='login'`, этот же эпик, DTJ-024) и вручение заказа курьером (`purpose='delivery_handover'`,
EP-13, позже по волнам). Оба потребителя обязаны использовать ОДИН и тот же VO с одинаковым контрактом
`verify()` — иначе логика TTL/попыток продублируется и разойдётся. Заводится в `shared-kernel`, а не в
`modules/auth/domain`, именно по этой причине.

## Технический контекст

`SRS-DOM-080`: `purpose: 'login' | 'delivery_handover'` — `login`: 6 цифр, `ttlSeconds` ASSUMPTION 300,
без встроенного лимита попыток в самом VO (анти-брутфорс на уровне `presentation`/rate-limit — DTJ-020,
DTJ-023 этого эпика); `delivery_handover`: 4 цифры, `ttlSeconds` ASSUMPTION 900, `maxAttempts = 5`.
`SRS-DOM-081`: генерация ИСКЛЮЧИТЕЛЬНО через `OtpGeneratorPort` (крипто-стойкий ГПСЧ), не
`Math.random()`. `SRS-API-021`: код хранится как `sha256(code + otpRequestId)`, не в открытом виде,
не `argon2` (избыточен для короткоживущего кода). `SRS-DOM-172`: сравнение TTL включительное
(`now <= issuedAt + ttlSeconds`), просрочка НА долю секунды после границы — уже `OtpExpiredError`.
`SRS-DOM-173`: 5-я неверная попытка → `OtpAttemptsExceededError`, БЕЗ проверки самого кода (fail-closed
— даже верный код на 6-й попытке отклоняется).

## Что сделать

1. `otp-code.vo.ts`: класс `OtpCode` (immutable value object, представляет состояние ОДНОГО OTP на
   момент проверки — персистентность/загрузка из БД делает `infrastructure`-репозиторий модуля,
   который этот VO использует; здесь — чистая бизнес-логика):
   - Конструктор (приватный) принимает `{ purpose, codeHash, issuedAt, ttlSeconds, attemptsUsed,
     maxAttempts, consumedAt, lockedAt }`.
   - `OtpCode.issue(purpose, codeHash, issuedAt): OtpCode` — фабрика для НОВОГО кода:
     `ttlSeconds`/`maxAttempts` резолвятся по `purpose` (login: `LOGIN_OTP_TTL_SECONDS = 300`,
     `delivery_handover`: `DELIVERY_OTP_TTL_SECONDS = 900`, `DELIVERY_OTP_MAX_ATTEMPTS = 5`, для
     `login` — `maxAttempts` НЕ ограничивается на уровне VO, передаётся `Number.POSITIVE_INFINITY`
     с явным комментарием, что анти-брутфорс для `login` живёт в presentation-слое, SRS-DOM-080).
   - `otpCode.verify(candidateHash: string, clock: ClockPort): Result<void, OtpExpiredError |
     OtpMismatchError | OtpAttemptsExceededError>` (принимает УЖЕ посчитанный хеш кандидата, не сырой
     код — хеширование `sha256(code + otpRequestId)` происходит на границе `application`, VO работает
     только со строками-хешами, не знает про crypto напрямую):
     1. Given `consumedAt !== null` → `OtpMismatchError` (повторное использование невозможно,
        SRS-DOM-082 «alreadyConsumed»).
     2. Given `lockedAt !== null` ИЛИ `attemptsUsed >= maxAttempts` → `OtpAttemptsExceededError`, БЕЗ
        сравнения кода (SRS-DOM-173, fail-closed).
     3. Given `clock.now() > issuedAt + ttlSeconds * 1000` (строго больше — включительная граница,
        SRS-DOM-172) → `OtpExpiredError`.
     4. Given `candidateHash !== codeHash` → `OtpMismatchError` + новый `OtpCode` с
        `attemptsUsed + 1` (метод ВОЗВРАЩАЕТ новый экземпляр — immutable VO, не мутирует `this`;
        вызывающий код обязан персистировать возвращённое состояние).
     5. Успех → новый `OtpCode` с `consumedAt = clock.now()`.
   - Метод возвращает `Result<OtpCode, OtpError>` (не `Result<void, ...>` — уточнение относительно
     первого черновика сигнатуры выше: на успехе и на неверном коде с инкрементом попытки вызывающему
     коду нужен ОБНОВЛЁННЫЙ `OtpCode` для персистентности, поэтому `T = OtpCode`, финальная сигнатура
     `verify(candidateHash, clock): Result<OtpCode, OtpExpiredError | OtpMismatchError |
     OtpAttemptsExceededError>`).
2. `otp-generator.port.ts`: `interface OtpGeneratorPort { generate(purpose: OtpPurpose): string }` —
   возвращает СЫРОЙ код (строка цифр нужной длины по `purpose`), не хеш.
3. `crypto-otp-generator.adapter.ts`: `CryptoOtpGeneratorAdapter implements OtpGeneratorPort` —
   `crypto.randomInt(0, 10)` на каждую цифру (криптостойкий ГПСЧ Node.js, не `Math.random()`), длина —
   6 для `login`, 4 для `delivery_handover`.
4. `otp-expired.error.ts`/`otp-mismatch.error.ts`/`otp-attempts-exceeded.error.ts`: расширяют
   `OtpError` из `packages/contracts/src/domain-errors.ts` (DTJ-005) — эти классы УЖЕ описаны в
   каталоге DTJ-005 (`OtpExpiredError`, `OtpMismatchError`, `OtpAttemptsExceededError` — потомки
   `OtpError`), этот тикет их ИСПОЛЬЗУЕТ, не создаёт заново; если DTJ-005 реализован раньше — просто
   `import`, файлы из `files_owned` этого тикета в таком случае не заводятся отдельно (пометка для
   разработчика: сверить при старте, не дублировать классы).

## Критерии приёмки

1. **Given** `OtpCode.issue('login', hash, issuedAt=T)`, **When** `verify(hash, clockAt(T + 300_000мс))`
   (ровно на границе TTL), **Then** `Result.ok` — граница включительная (SRS-DOM-172).
2. **Given** та же ситуация, **When** `verify(hash, clockAt(T + 300_001мс))` (на 1мс позже границы),
   **Then** `Result.err(OtpExpiredError)`.
3. **Негативный:** **Given** `OtpCode` с `purpose='delivery_handover'`, `attemptsUsed=5`,
   `maxAttempts=5`, **When** `verify(correctHash, clock)` (код в этот раз ВЕРНЫЙ), **Then**
   `Result.err(OtpAttemptsExceededError)` — верный код на заблокированном OTP всё равно отклоняется
   (fail-closed, SRS-DOM-173).

## Тест-план

- Unit: `verify` — успех, неверный код (инкремент `attemptsUsed` в возвращённом объекте), истечение
  TTL (граница включительно и сразу за ней), повторное использование `consumedAt !== null`,
  превышение попыток (включая случай «попытка verify с ВЕРНЫМ кодом после исчерпания» — приёмка 3).
- Unit: `OtpCode.issue` — корректные `ttlSeconds`/`maxAttempts` по `purpose` (`login` vs
  `delivery_handover`).
- Unit: `CryptoOtpGeneratorAdapter` — длина результата (6 для login, 4 для delivery_handover), только
  цифры, статистическая проверка отсутствия тривиального паттерна (не строгий крипто-тест, санити).
- Порог покрытия `domain/` — ≥90%, `infrastructure/` (адаптер) — ≥70%.

## Риски и подводные камни

- Сигнатура `verify()` менялась в процессе описания тикета (см. шаг 1 «Что сделать» — от `Result<void,
  ...>` к финальному `Result<OtpCode, ...>`) — реализующий разработчик должен использовать ИМЕННО
  финальную сигнатуру, возвращающую обновлённый `OtpCode`, иначе вызывающий `application`-код
  (DTJ-023/024) не сможет корректно персистировать `attemptsUsed`/`consumedAt` после каждой попытки.
- `login`-OTP не имеет `maxAttempts` на уровне VO (`Number.POSITIVE_INFINITY`) — это НЕ означает
  отсутствие защиты от брутфорса вообще: защита обязательна на уровне `presentation`
  (`OTP_VERIFY_MAX_ATTEMPTS = 5` per `otpRequestId`, SRS-API-022) и реализуется в DTJ-024, не в этом
  VO. Если разработчик DTJ-024 не прочитает эту оговорку — риск, что `login`-OTP окажется без лимита
  попыток вовсе.
