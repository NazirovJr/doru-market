## Задача

Первый реальный экран продукта, который видит покупатель — вход по номеру телефона. `04-SCOPE-DECISION-
PIVOT.md` R1-12 требует Auth как основание всего; `tickets/00-EPICS.md` явно называет этот экран
«Первый фронтовый потребитель Auth». Визуальная ссылка — `docs/spec/32-design-reference.md`
§«Customer-приложение» → `Login` (`.dc.html:1021-1078`), но с ОБЯЗАТЕЛЬНЫМИ отклонениями от дизайна,
зафиксированными в том же документе (§«Статус» расхождения №1, №2, №4, №5, №7 — все ниже).

## Технический контекст

`docs/spec/32-design-reference.md` §«Статус», расхождения, обязательные к реализации ПОВЕРХ дизайна:
- №1: порог блокировки — **5** неверных попыток (не 3, как в `.dc.html`), совпадает с `SRS-API-022`.
- №2: текст блокировки — канонический `ux.error.otp_locked` («...Запросите новый код через
  SMS/Telegram»), путь восстановления — ПОВТОРНЫЙ ЗАПРОС КОДА (кнопка), НЕ таймер ожидания 5 минут.
- №4: тап-зоны — визуальный размер OTP-ячеек может остаться как в дизайне, но реальная область
  нажатия ≥48×48px (padding/hit-slop, не раздувание видимого элемента).
- №5: фокус-кольцо — из `--brand-primary` (`SRS-UX-018`), НЕ фиксированный `rgba(14,165,233,.4)`
  дизайна.
- №7: радиусы — по формуле `--radius-sm/md/lg/full` от `--brand-radius` (`SRS-UX-017`), не
  произвольные px дизайна.

`SRS-UX-002`: минимум 48×48 CSS px для тап-зон. `SRS-UX-019`: WCAG — видимый `--focus-ring` на
каждом шаге клавиатурной навигации, порядок фокуса совпадает с визуальным. `SRS-UX-023`: текст —
ТОЛЬКО ключи `ux.*`/`auth.*` из `packages/i18n` (DTJ-004), не литералы в компоненте. `SRS-UX-027`:
`LanguageSwitcher` (плейсхолдер из `apps/web` layout, DTJ-003) — доступен и на `/login` (не только
на главном экране, вопреки тому, что дизайн показывает переключатель только там).

## Что сделать

1. `auth-store.ts` (Zustand, заменяет пустой `authStore` из DTJ-003): `{ accessToken: string | null;
   refreshToken: string | null; user: {...} | null; setSession(tokens, user): void; clear(): void }`,
   персистентность `refreshToken` в `localStorage` (`accessToken` — ТОЛЬКО в памяти, не персистируется
   — компромисс XSS-риска, задокументировать явно), гидратация при старте приложения (если
   `refreshToken` в `localStorage` — попытка `/auth/refresh` до первого рендера защищённого контента).
2. `login-flow.model.ts`: чистая функция/reducer состояния шагов `'phone' | 'code' | 'locked'`,
   счётчик `attemptsLeft` (5 минус попытки — считается КЛИЕНТСКИ для UX-подсказки, финальное решение
   всегда за сервером — `423` может прийти и раньше клиентского счётчика при рассинхроне, обрабатывается
   единообразно), таймер `resendCooldownSeconds` (60с, синхронизирован с `OTP_REQUEST_COOLDOWN_SECONDS`).
3. `use-request-otp.ts`/`use-verify-otp.ts`: TanStack Query мутации поверх `http-client` (DTJ-003) —
   вызывают `POST /auth/otp/request`/`verify` (DTJ-023/024), маппят коды ошибок
   (`INVALID_PHONE_FORMAT`, `OTP_REQUEST_RATE_LIMITED`, `OTP_EXPIRED`, `OTP_MISMATCH`, `OTP_LOCKED`)
   на состояние `login-flow.model.ts`.
4. `phone-step.tsx`: поле телефона с фиксированным префиксом `+992` (маска `XX XXX XX XX`), кнопка
   «Отправить код» — `disabled` до 9 цифр (по образцу дизайна), текст — `t('auth.login.phone_title')`/
   `t('auth.login.phone_hint')` (DTJ-004). Использует ВРЕМЕННЫЕ базовые HTML/Tailwind-элементы вместо
   `packages/ui` компонентов, если те ещё не готовы на момент реализации (см. DTJ-003 «Риски») — с
   явным `// TODO(EP-18)`.
5. `code-step.tsx`: 6-ячеечный OTP-ввод, авто-переход между ячейками, авто-submit на последней цифре
   (соответствует дизайну — эта часть НЕ входит в список расхождений). Состояния: ввод / ошибка (счётчик
   `t('ux.error.otp_mismatch', { attemptsLeft })`) / заблокировано (`t('ux.error.otp_locked')` +
   кнопка «Запросить новый код», ведущая обратно на шаг `'phone'` с предзаполненным номером — расхождение
   №2, НЕ таймер обратного отсчёта). Кнопка «Отправить код повторно» — активна только после
   `resendCooldownSeconds` истёк, показывает `t('auth.login.resend_countdown', { seconds })` до этого.
6. `login-page.tsx`: композиция `phone-step`/`code-step` по состоянию `login-flow.model.ts`, на
   успешный `verify` — `authStore.setSession(...)`, редирект на сохранённый `intent`-путь (если
   пользователь был отправлен на `/login` с защищённого маршрута) или на `/` по умолчанию.

## Критерии приёмки

1. **Given** пользователь вводит валидный номер и нажимает «Отправить код», **When** ответ `202`,
   **Then** экран переключается на шаг ввода кода, показывает `t('auth.login.code_sent_to', { phone
   })`.
2. **Given** 6 подряд неверных попыток кода (сервер вернул `423 OTP_LOCKED` на 6-й), **When**
   отображается экран блокировки, **Then** текст — дословно канонический `ux.error.otp_locked`, кнопка
   ведёт на повторный запрос кода (НЕ таймер 5 минут — проверка отсутствия любого countdown-компонента
   на этом экране).
3. **Негативный:** **Given** сеть недоступна в момент отправки кода, **When** запрос падает
   (`fetch` reject / таймаут), **Then** показывается `t('ux.error.network_offline')` (DTJ-004), форма
   остаётся заполненной (не сбрасывает введённые данные пользователя при сетевой ошибке).

## Тест-план

- Unit: `login-flow.model.ts` — переходы состояний `phone→code→locked`, счётчик `attemptsLeft`,
  таймер cooldown.
- Unit: `auth-store.ts` — `setSession`/`clear`, персистентность `refreshToken` (не `accessToken`) в
  `localStorage`.
- Integration (Testing Library + `msw` мок-сервер, без реального backend): полный happy path
  ввод телефона → код → редирект; путь блокировки на 6-й попытке; сетевая ошибка не теряет ввод.
- Проверка a11y: `Tab`-навигация по полю телефона/OTP-ячейкам до кнопки — видимый `--focus-ring` на
  каждом шаге (соответствует `TC-UX-005` из `30-ux-screens-and-flows.md`, тест — снапшот
  computed-style фокус-состояния или axe-подобная проверка).
- Coverage — ≥70%.

## Риски и подводные камни

- Зависимость от `packages/ui` (не в зоне EP-01, минимальный бутстрап — параллельный поток «Волны 1»
  `tickets/00-EPICS.md`) — если готовых компонентов нет на момент реализации, экран временно верстается
  на голых Tailwind-классах с `// TODO(EP-18): заменить на packages/ui`; ревью не должно блокировать
  тикет из-за отсутствия чужого пакета — фиксируется как известный долг, переносимый в отдельный
  follow-up тикет EP-18 (`tickets/00-EPICS.md` §«Пересекающееся владение» п.6 — «временно кладёт
  локальный компонент... заводит тикет на перенос в течение того же спринта»).
- Клиентский счётчик `attemptsLeft` — ЛОКАЛЬНАЯ эвристика для UX, не источник истины (сервер считает
  независимо, DTJ-024). Рассинхрон возможен (например, две вкладки одного пользователя) — экран
  ОБЯЗАН корректно реагировать на `423` от сервера даже если клиентский счётчик ещё не дошёл до 5 (не
  полагаться на клиентский счётчик как единственный триггер состояния `'locked'`).
- Экран `/login` не входит в перечень маршрутов, требующих `TenantResolutionMiddleware` полноценно
  (EP-02 ещё не готов) — временный `tenantId`-резолв на backend (см. DTJ-023/024 «Риски») означает,
  что multi-tenant White-Label вход НЕ тестируется этим тикетом, только нейтральный тенант.
