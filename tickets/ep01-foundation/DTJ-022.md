## Задача

Этот тикет создаёт САМ модуль `modules/auth` (`identity` контекст по `10-domain-model.md`
§«Ограниченные контексты») как NestJS-модуль с публичным фасадом и общими guard'ами RBAC, на который
все последующие тикеты этого эпика (DTJ-023..027, DTJ-030) добавляют СВОИ use case'ы/контроллеры —
без переписывания сборки модуля каждый раз (по аналогии с правилом `packages/contracts` баррель,
`tickets/00-EPICS.md`). Это первая точка, где появляется реальная проверка JWT — необходима КАЖДОМУ
защищённому эндпоинту, который заведёт ЛЮБОЙ последующий эпик (`orders`, `payments`, `inventory`, ...).

## Технический контекст

`SRS-API-024`: access-токен — JWT `RS256` (асимметричный, публичный ключ можно раздавать другим
сервисам), `exp=15 минут`, claims `sub`(userId), `role`, `tenantId`(nullable для `super_admin`),
`pharmacyId`/`chainId`(nullable), `sessionId`(`auth_sessions.id`), `iat`, `exp`, `jti`.

`SRS-API-036`: `RolesGuard` (presentation) проверяет ТОЛЬКО (1) валиден ли JWT, (2) входит ли
`token.role` в список `@Roles(...)` — ГРУБАЯ проверка роли. Условная авторизация («это ЕГО заказ» и
т.п.) — ВСЕГДА в `application/policies/*.policy.ts` конкретного модуля, НЕ в guard'е (этот тикет НЕ
заводит ни одной политики — политики принадлежат модулям, которым нужна условная проверка владения;
`modules/auth` сам по себе такой политики не требует, кроме тривиального «это его собственная
сессия», см. `SRS-API-030`, которое реализует DTJ-026).

`SRS-API-037`: роли `user_role` — уже enum БД (DTJ-013). `SRS-API-038`: формат permission-строки
`<resource>:<action>[:<scope>]` — константы уже в `packages/contracts/src/permissions.ts` (DTJ-005);
этот тикет использует их через `@Roles(...)` НА УРОВНЕ РОЛЕЙ (не permission-строк напрямую — сверить:
`SRS-API-036` явно говорит guard проверяет `token.role` против списка ролей декоратора `@Roles(...)`,
а не permission-строку; permission-строки — для application-политик уточнения `scope`, которые заводит
КАЖДЫЙ модуль под свою сущность — этот тикет даёт ТОЛЬКО грубый guard по ролям).

## Что сделать

1. `jwt-signer.port.ts`: `interface JwtSignerPort { sign(claims: JwtClaims): string; verify(token:
   string): Result<JwtClaims, JwtVerificationError> }`, `type JwtClaims = { sub: string; role:
   UserRole; tenantId: string | null; pharmacyId: string | null; chainId: string | null; sessionId:
   string; jti: string }` (`iat`/`exp` — управляются библиотекой подписи, не часть входного объекта
   порта).
2. `rs256-jwt-signer.adapter.ts`: `Rs256JwtSignerAdapter implements JwtSignerPort` — через
   `@nestjs/jwt`/`jsonwebtoken`, ключи из `JWT_PRIVATE_KEY`/`JWT_PUBLIC_KEY` (PEM, ENV — добавить в
   `env.schema.ts` из DTJ-001), `algorithm: 'RS256'`, `expiresIn: '15m'`, заголовок `kid: JWT_KID`
   (ENV, дефолт `'v1'` — задел на будущую ротацию ключей, `SRS-NFR-024`-подобный механизм упомянут в
   `31-nfr-security-testing-devops.md`, но САМА многоключевая верификация с несколькими активными
   `kid` одновременно — НЕ входит в этот тикет, только заголовок присутствует в токене; полноценная
   ротация — follow-up при реальной эксплуатации, не блокирует R1).
3. `users.repository.ts`: `UsersRepository` — `findByTenantAndPhone(tenantId, phoneNumber)`,
   `findById(id)`, `create(command)`, `update(id, patch)` — Drizzle-запросы к `users.schema.ts`
   (DTJ-014), маппинг строки БД → доменный тип `User` через `user.mapper.ts` (тонкий DTO, НЕ полноценный
   rich-агрегат — `10-domain-model.md` не описывает `User` как агрегат со сложными инвариантами,
   только как сущность идентичности; методы-намерения не нужны сверх того, что уже валидируют VO при
   создании).
4. `auth.guard.ts`: `AuthGuard implements CanActivate` — читает `Authorization: Bearer <JWT>`,
   `JwtSignerPort.verify(...)`; при отсутствии заголовка на маршруте БЕЗ `@Public()` →
   `401 UNAUTHENTICATED`; истёкший токен → `401 TOKEN_EXPIRED`; невалидная подпись/формат →
   `401 TOKEN_INVALID`; на успехе — заполняет `RequestContext.patch({ userId: claims.sub, role:
   claims.role, tenantId: claims.tenantId })` (расширение `RequestContext` из DTJ-001 — теперь реально
   заполняется, не остаётся `null`) и прокидывает `claims` в `request['authClaims']` для
   `@CurrentUser()`.
5. `roles.guard.ts` + `roles.decorator.ts`: `@Roles('pharmacy_admin', 'super_admin')` (`SetMetadata`)
   — `RolesGuard` выполняется ПОСЛЕ `AuthGuard` (порядок в `app.module.ts`/за счёт порядка в массиве
   `@UseGuards(AuthGuard, RolesGuard)` на контроллерах), читает `claims.role` из `request['authClaims']`,
   при отсутствии в списке декоратора → `403 INSUFFICIENT_ROLE` (`SRS-API-039`: маршрут физически
   недоступен роли, не «условно запрещён»).
6. `public.decorator.ts`: `@Public()` — маркер маршрутов, пропускаемых `AuthGuard` целиком (тот же
   декоратор, упомянутый как заготовка в DTJ-001 для `/health`/`/ready` — этот тикет формализует его
   финальную реализацию, `AuthGuard` читает через `Reflector`).
7. `current-user.decorator.ts`: `@CurrentUser()` — параметр-декоратор контроллера, достаёт
   `request['authClaims']` типизированно.
8. `auth.module.ts`: собирает `UsersRepository`, `Rs256JwtSignerAdapter` (DI на порт),
   `AuthGuard`/`RolesGuard` как провайдеры модуля (НЕ глобальные `APP_GUARD` — каждый контроллер
   явно ставит `@UseGuards(...)`, чтобы `/health`/`/ready`/`@Public()`-маршруты оставались
   исключением без риска забыть глобальный обход); экспортирует guard'ы и декораторы для использования
   другими модулями через `modules/auth/index.ts` (публичный фасад — `AuthFacade`-подобный экспорт
   пока не нужен как отдельный класс, т.к. другим модулям нужны именно guard'ы/декораторы, а не
   вызовы бизнес-логики auth — реальный `AuthFacade.verifySession(...)`-подобный метод заводится,
   если появится КОНКРЕТНЫЙ второй потребитель, не заранее, C15).
9. `index.ts`: барабанный экспорт `AuthModule`, `AuthGuard`, `RolesGuard`, `@Roles`, `@Public`,
   `@CurrentUser`, `JwtClaims`.

## Критерии приёмки

1. **Given** валидный JWT с `role='pharmacist'`, **When** запрос к маршруту с `@UseGuards(AuthGuard,
   RolesGuard)` и `@Roles('pharmacist', 'pharmacy_admin')`, **Then** запрос пропущен, `@CurrentUser()`
   в контроллере получает корректные `claims`.
2. **Given** валидный JWT с `role='customer'`, **When** тот же маршрут, **Then** `403
   INSUFFICIENT_ROLE`, контроллер НЕ вызван (проверяется мок-шпионом).
3. **Негативный:** **Given** JWT с истёкшим `exp`, **When** любой защищённый маршрут, **Then**
   `401 TOKEN_EXPIRED` (отдельно от `401 TOKEN_INVALID` — разные коды на разные причины, клиент
   различает «нужен refresh» от «токен сфабрикован»).

## Тест-план

- Unit: `Rs256JwtSignerAdapter` — `sign`→`verify` round-trip, невалидная подпись (токен подписан
  другим ключом) → ошибка, истёкший `exp` → ошибка.
- Unit: `AuthGuard` — все ветки (нет заголовка+`@Public()`, нет заголовка без `@Public()`, истёкший,
  невалидный, валидный — заполнение `RequestContext`).
- Unit: `RolesGuard` — роль в списке/не в списке, `@Roles()` отсутствует на маршруте (поведение —
  явно определить: доступен всем аутентифицированным по умолчанию ИЛИ требует явного decorator —
  выбрать «требует явного» как безопасный дефолт, задокументировать в JSDoc).
- Unit: `UsersRepository` — маппинг строки БД в доменный тип, `findByTenantAndPhone` с несуществующей
  парой возвращает `null`, не бросает.
- Порог покрытия `application`/`presentation` данного модуля — ≥70% (не `domain`, т.к. `User` не
  заведён как rich domain entity в этом тикете); `packages/contracts`-примыкающий код — уже покрыт
  DTJ-005.

## Риски и подводные камни

- Полная RBAC-матрица `12-api-conventions-auth-tenancy.md` §4.1 (permission-строки с `scope`) НЕ
  реализуется этим тикетом — только грубый guard по ролям (`SRS-API-036` явно разделяет
  ответственность). Каждый следующий модуль (`orders`, `disputes`, ...) обязан САМ завести
  `application/policies/*.policy.ts` для условной части — если разработчик модуля не прочитает эту
  оговорку, есть риск, что он попытается впихнуть проверку владения В `RolesGuard`, нарушив
  `SRS-API-036` — явно предупредить в комментарии guard'а.
- Ротация JWT-ключа (`kid`) — только поле в токене, без реальной поддержки НЕСКОЛЬКИХ одновременно
  активных публичных ключей на верификации (`Rs256JwtSignerAdapter.verify` проверяет ТОЛЬКО текущий
  `JWT_PUBLIC_KEY`). Если ключ будет отозван/сменён на проде без grace-периода — все выданные ранее
  access-токены (до 15 минут жизни, риск минимален) станут невалидны разом. Явно зафиксировано как
  упрощение R1, не полная реализация `SRS-NFR`-требования по ротации.
- `TenantResolutionMiddleware` (EP-02) физически ещё не существует на момент этого тикета — `claims.tenantId`
  заполняется из JWT (выданного при логине, DTJ-024), а НЕ из резолва тенанта текущего запроса; проверка
  «`token.tenantId !== resolvedTenantId`» (`SRS-API-045`, кросс-тенантная защита) — ЗОНА EP-02, не
  реализуется здесь. Явный технический долг до готовности EP-02 — задокументировать как известный
  пробел безопасности R1 raннего периода (митигируется тем, что EP-02 идёт следующей волной сразу
  после EP-01 по графу, а не отложен на конец).
- Файл `apps/api/src/modules/auth/auth.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/src/modules/auth/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
