## Задача

`apps/api` — единственный входной HTTP-процесс продукта: без него ни один последующий модуль (каталог,
заказы, платежи, терминал аптеки) не имеет куда положить контроллер. Этот тикет создаёт «пустой, но
живой» NestJS+Fastify сервис — с health-check'ами, структурным логированием, безопасными транспортными
заголовками и Docker-образом — на который все остальные эпики R1 добавляют свои `modules/<context>/**`,
не трогая корневую сборку. Это буквально первый коммит продуктового кода в репозитории.

## Технический контекст

`01-TECH-BASELINE.md`: `@nestjs/core`/`common`/`platform-fastify`/`config`/`terminus` `^11.2.3`,
`fastify` через `platform-fastify`, `@fastify/helmet`, `@fastify/cors`, `@fastify/multipart`,
`@fastify/rate-limit`, `pino`/`pino-http` `^10.3.1`. `02-CLEAN-ARCHITECTURE-AND-CODE.md` §1 — модуль
= `domain/application/infrastructure/presentation`; этот тикет НЕ создаёт ни одного `modules/<context>`
(это «пустая коробка», задача каждого следующего эпика — положить туда свой контекст), только корневую
инфраструктуру `apps/api/src/{main.ts,app.module.ts,config,common}`.

`SRS-NFR-037` — `GET /health` (liveness, без внешних зависимостей) отдельно от `GET /ready` (readiness:
Postgres `SELECT 1` таймаут 2с + Redis `PING`); оба эндпоинта — **вне** `TenantResolutionMiddleware` и
вне аутентификации. Postgres/Redis клиенты для readiness-проверки создаются здесь как минимальные
DI-провайдеры (`pg`/`ioredis`), полноценные репозитории/очереди появятся в тикетах, которым они нужны.

`SRS-NFR-038` — обязательные поля pino на каждую запись: `requestId`, `tenantId`, `userId`, `role`,
`method`, `path`, `statusCode`, `durationMs`. `requestId` — из `X-Request-Id`, если валидный UUID
(`SRS-API-011`), иначе генерируется сервером; распространяется через `AsyncLocalStorage`
(`RequestContext`, `apps/api/src/common/context/request-context.ts`) на все логи запроса. `tenantId`/
`userId`/`role` на этом этапе читаются из того же `RequestContext`, но заполняются `null` — реальное
заполнение появится в EP-02 (тенант) и EP-01/DTJ-022 (JWT-роль); контракт полей заводится сейчас, чтобы
EP-02 не переписывал формат лога, а только начал заполнять уже существующее поле.

`SRS-API-064/065/066/067` — `@fastify/helmet` (CSP `default-src 'self'`, HSTS, `X-Content-Type-Options`),
CORS allowlist (`CORS_STATIC_ORIGINS` из ENV, `http://localhost:*` только при `NODE_ENV=development`),
лимиты тела (`1 MB` JSON дефолт, `10 MB` multipart, `5 MB` для `/inventory/batch-update` — этот
конкретный оверрайд НЕ здесь, а в тикете EP-05, здесь только глобальный дефолт), таймаут запроса
`REQUEST_TIMEOUT_MS` (ASSUMPTION 30000) через `connectionTimeout` Fastify.

## Что сделать

1. `apps/api/package.json`: зависимости из `01-TECH-BASELINE.md` §Backend, скрипты `start:dev`
   (`nest start --watch`), `build` (`nest build`), `start:prod` (`node dist/main.js`), `typecheck`.
2. `apps/api/src/main.ts`: `NestFactory.create(AppModule, new FastifyAdapter())`, регистрация
   `@fastify/helmet`, `@fastify/cors` (allowlist из `ConfigService`), глобальный `ValidationPipe`
   **не** используется (валидация — Zod в `packages/contracts`, не `class-validator` — заводится
   позже вместе с контроллерами); `app.listen(port, '0.0.0.0')`.
3. `apps/api/src/config/config.module.ts` + `env.schema.ts`: `@nestjs/config` с Zod-валидацией ENV
   на старте (`NODE_ENV`, `PORT`, `DATABASE_URL`, `REDIS_URL`, `LOG_LEVEL`, `CORS_STATIC_ORIGINS`,
   `REQUEST_TIMEOUT_MS`) — невалидный/отсутствующий обязательный ENV **валит процесс на старте**
   с понятным сообщением, не падает на первом запросе.
4. `apps/api/src/common/context/request-context.ts`: `AsyncLocalStorage<RequestContext>` c полями
   `{ requestId: string; tenantId: string | null; userId: string | null; role: string | null }`;
   `RequestContextMiddleware` (глобальный, `app.use`) — читает/валидирует `X-Request-Id`
   (`SRS-API-011`: валиден — используется, невалиден/отсутствует — генерируется новый), инициализирует
   контекст с `tenantId=null,userId=null,role=null` (заполняются позже другими guard'ами через
   `RequestContext.patch(...)`).
5. `apps/api/src/common/logging/logger.module.ts`: `pino-http` фабрика, читающая поля из
   `RequestContext` (`mixin` pino) — формат записи 1:1 по `SRS-NFR-038`; `redact` для
   `req.headers.authorization`/`req.headers['x-pharmacy-api-key']`.
6. `apps/api/src/common/health/health.module.ts` + `health.controller.ts`
   (`@nestjs/terminus`): `GET /health` — только `process`-индикатор (event loop lag ниже порога),
   БЕЗ БД/Redis. `GET /ready` — `PostgresHealthIndicator` (`SELECT 1`, timeout 2000ms) +
   `RedisHealthIndicator` (`PING`); при недоступности одной зависимости ответ `503` явно называет,
   какая именно (`SRS-NFR-037`). Оба маршрута регистрируются ДО любого tenant/auth guard'а (простой
   `@Public()`-подобный маркер декоратором, который EP-02 обязан научиться пропускать в
   `TenantResolutionMiddleware`, — задокументировать это явно в JSDoc декоратора).
7. `apps/api/Dockerfile`: `node:22.12-slim` (не `alpine` — `argon2` нативные аддоны), multi-stage
   build (`deps` → `build` → `runtime`), непривилегированный пользователь.
8. `apps/api/docker-entrypoint.sh`: перед `node dist/main.js` выполняет `pnpm db:migrate`
   (`SRS-DB-032` — единственная команда применения миграций в docker-контексте); скрипт — заглушка,
   реально работающая с первой миграцией из DTJ-012.
9. `apps/api/.env.example`: перечисляет все ENV из шага 3 с безопасными dev-дефолтами.
10. `apps/api/src/app.module.ts`: подключает `ConfigModule`, `LoggerModule`, `HealthModule`; пустой
    массив `imports` для будущих `modules/<context>` с комментарием-инструкцией для следующих эпиков.

## Критерии приёмки

1. **Given** `apps/api` собран и запущен с валидным `.env`, **When** `GET /health`, **Then** `200`
   с телом `{ "data": { "status": "ok" } }` даже если Postgres/Redis недоступны.
2. **Given** Postgres недоступен (`docker compose stop postgres`), **When** `GET /ready`, **Then**
   `503`, тело явно называет `postgres` как упавшую зависимость, `redis` при этом отдельно помечен
   `ok` (детализация по зависимостям, не общий флаг).
3. **Given** запрос без заголовка `X-Request-Id`, **When** любой эндпоинт, **Then** ответ содержит
   сгенерированный `requestId`, и структурная запись pino этого запроса содержит то же значение в
   поле `requestId`.
4. **Негативный:** **Given** ENV `DATABASE_URL` не задан, **When** процесс стартует, **Then** процесс
   завершается с ненулевым кодом и понятным сообщением об отсутствующей переменной ДО открытия порта
   (не падает на первом входящем запросе).

## Тест-план

- Unit: `env.schema.ts` — валидный конфиг проходит, отсутствие обязательного поля бросает; `RequestContextMiddleware` — генерация `requestId` при невалидном заголовке, проброс валидного как есть.
- Integration (supertest + testcontainers/docker-compose тестовый Postgres/Redis): `GET /health` всегда `200`; `GET /ready` — `200` при поднятых зависимостях, `503` с детализацией при остановленном Postgres и отдельно при остановленном Redis.
- Порог покрытия для `common/` (не domain/application) — ≥70% по `02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.4.

## Риски и подводные камни

- `TenantResolutionMiddleware` (EP-02) должна выполняться ДО остальных guard'ов, но ПОСЛЕ
  `RequestContextMiddleware` этого тикета (нужен `requestId` уже в логах ошибок резолвинга тенанта) —
  порядок регистрации middleware зафиксировать явным комментарием в `app.module.ts`, чтобы EP-02 не
  вставил её раньше по ошибке.
- `@Public()`-декоратор для `/health`/`/ready` — временный, пока не существует единого `AuthGuard`
  (появится в DTJ-022 того же эпика). Если DTJ-022 введёт СВОЙ механизм публичных маршрутов
  (`@Public()` NestJS-паттерн уже занят) — переиспользовать этот же декоратор, не заводить второй.
- Метрики Prometheus (`SRS-NFR-039`, `GET /metrics`) НЕ входят в этот тикет — заведён отдельно не был
  ввиду объёма; каждый модуль, которому нужна бизнес-метрика, добавляет её инкрементально. Базовый
  `http_request_duration_seconds`/`http_requests_total` — риск, что без явного тикета никто не заведёт
  `prom-client`; зафиксировать как известный технический долг для ревью EP-19 перед приёмкой R1.
- Файл `apps/api/package.json` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/tsconfig.json` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/src/app.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
