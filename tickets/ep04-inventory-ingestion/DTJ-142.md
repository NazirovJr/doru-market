## Задача

Baseline-схема `11-database-schema.md` не содержит полей, необходимых конкретно для механики
многоканального приёма (пагинация full-снапшота, группировка Excel-загрузки, ретроактивное
применение резолюции очереди, ключи 1С на уровне сети, диагностический код ошибки воркера) — это
явно задокументировано в `docs/spec/22-module-inventory-sync-1c.md` §10 «Дополнения к схеме БД» с
обоснованием по каждому пункту. Этот тикет переносит все пять пунктов в реальные миграции.

## Технический контекст

Ровно 5 изменений, дословно по `22-module-inventory-sync-1c.md` §10 (строки 699-793):
1. `inventory_sync_batches` +`full_sync_session_id UUID`, +`page_number INT DEFAULT 1`,
   +`is_last_page BOOLEAN DEFAULT true`, +`source_upload_id UUID`, +CHECK
   `chk_sync_batches_session_only_for_full`, +индекс `ix_inventory_sync_batches_session`.
2. Новая таблица `inventory_sync_raw_items` (промежуточное хранилище payload для воркера,
   `ON DELETE CASCADE` от `inventory_sync_batches`).
3. `catalog_match_queue` +`raw_stock_quantity INT`, +`raw_expiry_date DATE`,
   +`raw_batch_number VARCHAR(100)`, +`source_batch_id UUID REFERENCES inventory_sync_batches`,
   +`source_sync_timestamp TIMESTAMPTZ NOT NULL DEFAULT NOW()`.
4. `pharmacy_api_keys`: `pharmacy_id` → `DROP NOT NULL`, +`chain_id UUID REFERENCES
   pharmacy_chains`, +CHECK `chk_pharmacy_api_keys_exactly_one_scope` (ровно один скоуп заполнен).
5. `ALTER TYPE inventory_sync_row_error_code ADD VALUE 'processing_failed'` — ОТДЕЛЬНАЯ миграция
   вне транзакции (`SRS-DB-009`, PostgreSQL запрещает использовать новое значение enum в той же
   транзакции, где оно добавлено — см. `11-database-schema.md` SRS-DB-049 для точного паттерна).
   **[ИЗМЕНЕНО]** не выполнено так, как описано: enum `inventory_sync_row_error_code` нигде не
   создан (`CREATE TYPE` отсутствует), см. примечание после frontmatter — источник истины кодов
   ошибок строк теперь TS-юнион, ошибки строк не персистятся pg enum'ом.

**Кросс-модульное владение — прочитать перед началом**: пп. 3 и 4 меняют таблицы, чьё БАЗОВОЕ
`CREATE TABLE` не принадлежит `modules/inventory` (`catalog_match_queue` — контекст `moderation`,
`pharmacy_api_keys` — контекст `onboarding`, миграция `0013_onboarding.sql` по `11
-database-schema.md` §«Порядок миграций»). Это ТОЧЕЧНЫЕ `ALTER TABLE` в ОТДЕЛЬНОМ файле миграции,
не редактирование чужого `CREATE TABLE` — конфликтов на уровне файла быть не должно, но необходима
координация по ПОРЯДКУ применения: эта миграция обязана идти ПОСЛЕ `0013_onboarding.sql` и после
создания `catalog_match_queue` (миграция DTJ-141 этого же эпика, `0007_inventory.sql` — уже
внутреннняя зависимость).

## Критерии приёмки

1. **Given** применены `0007_inventory.sql` и `0013_onboarding.sql`, **When** применяется
   `0015a_inventory_sync_extensions.sql`, **Then** `\d inventory_sync_batches` показывает 4 новые
   колонки и CHECK `chk_sync_batches_session_only_for_full`, `\d pharmacy_api_keys` показывает
   `chain_id` и снятый `NOT NULL` на `pharmacy_id`.
2. **Given** `INSERT INTO inventory_sync_batches (sync_type='delta', full_sync_session_id=<uuid>)`,
   **When** выполняется вставка, **Then** `23514 check_violation`
   (`chk_sync_batches_session_only_for_full`) — негативный сценарий, соответствует SRS-INV-005.
3. **Given** `INSERT INTO pharmacy_api_keys (pharmacy_id=NULL, chain_id=NULL)`, **When** выполняется
   вставка, **Then** `23514 check_violation` (`chk_pharmacy_api_keys_exactly_one_scope`) — негативный
   сценарий: ни один скоуп не заполнен.
4. **Given** `0015a` уже применена, **When** применяется `0015b` ВНУТРИ той же транзакции, что и
   любая другая DDL (искусственный тест ошибки конфигурации раннера), **Then** тест фиксирует, что
   `pnpm db:migrate` фактически выполняет `0015b` отдельным подключением (не в общей транзакции с
   соседними файлами) — интеграционный тест, воспроизводящий SRS-DB-046.
   **[ИЗМЕНЕНО] Неприменимо** — `0015b` удалена, см. примечание после frontmatter.
