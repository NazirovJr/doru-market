## Задача

Если инфраструктурный сбой (не бизнес-ошибка строки — та обрабатывается внутри одной попытки и не
считается провалом job, DTJ-148) валит job все 5 попыток подряд, батч не должен зависнуть в
`processing` бесконечно — `pharmacy_admin` обязан увидеть явную ошибку, а on-call получить алерт.
Это единственный путь, которым `InventorySyncBatch` попадает в `failed_validation` НЕ из бизнес-кода
использования, а из инфраструктурного обработчика события BullMQ `failed`.

## Технический контекст

`attempts: 5, backoff: exponential 5000мс` уже настроены при постановке job (DTJ-153) — до ~155с до
финального провала, укладывается в SLA 5 минут даже при нескольких переотправках. Новое значение
enum `inventory_sync_row_error_code = 'processing_failed'` уже добавлено миграцией DTJ-142 п.5.

## Что сделать

1. `inventory-sync-failed-job.handler.ts`: `InventorySyncFailedJobHandler` — подписчик на событие
   `failed` очереди `inventory-sync-queue` (BullMQ `QueueEvents('inventory-sync-queue').on('failed',
   ...)` — регистрируется В `apps/worker`, слушает ТОЛЬКО финальный провал после исчерпания всех
   попыток, не каждую промежуточную неудачную попытку — BullMQ `failed`-событие на `QueueEvents`
   срабатывает и на промежуточных попытках, поэтому обработчик обязан проверять
   `job.attemptsMade >= job.opts.attempts` перед действием, иначе статус будет выставлен
   преждевременно на первой же неудачной попытке из пяти).
2. При подтверждённом финальном провале: загрузить `InventorySyncBatch` по `job.data.batchId`,
   вызвать `.markFailedValidation()` (DTJ-144 — если батч уже в терминальном статусе к этому
   моменту — например, успел завершиться до окончательного failed-события гонкой — перехватить
   `IllegalBatchStatusTransitionError` и залогировать предупреждение, не бросать дальше: это
   ожидаемая гонка, не баг).
3. Записать ОДНУ синтетическую строку `inventory_sync_errors(error_code='processing_failed',
   error_detail=<последняя ошибка стека, БЕЗ секретов>)` — санитизация `error_detail`: исключить
   значения заголовков `X-Pharmacy-*`/токены/пароли из текста стека перед записью (переиспользовать
   `pino` `redact`-паттерны EP-01, если применимо, или явный `sanitizeErrorDetail()` хелпер).
4. Опубликовать алерт-событие для on-call (тот же принцип, что DTJ-152 — `InventoryOutboxPort`,
   конкретная доставка вне этого тикета).

## Критерии приёмки

1. **Given** job падает 5 раз подряд (симулированное исключение инфраструктуры — например,
   недоступность БД, замоканная в тесте), **When** BullMQ помечает job `failed` окончательно (5-я
   попытка исчерпана), **Then** `status='failed_validation'`, `inventory_sync_errors` содержит
   ОДНУ строку `error_code='processing_failed'`, батч не завис в `processing` — точное соответствие
   TC-INV-018.
2. **Given** job падает на 2-й из 5 попыток (промежуточная неудача, retry ещё продолжается), **When**
   BullMQ эмитит промежуточное `failed`-событие этой попытки, **Then** обработчик НЕ переводит
   `InventorySyncBatch` в `failed_validation` (проверка `attemptsMade < opts.attempts` отсекает
   промежуточные попытки) — негативный сценарий, критичный для корректности (иначе батч ложно
   провалится на первой же временной ошибке).
3. **Given** `error_detail` содержит в тексте исключения значение заголовка
   `X-Pharmacy-Signature: abc123...`, **When** строка `inventory_sync_errors` записывается,
   **Then** секрет НЕ попадает в сохранённый `error_detail` — второй негативный сценарий (защита
   от утечки секретов в отчёт, видимый `pharmacy_admin`).
4. **Given** батч уже успел перейти в `completed_partial_success` (гонка — воркер успел
   финализировать статус до прихода финального `failed`-события от другого source), **When**
   обработчик пытается `.markFailedValidation()`, **Then** `IllegalBatchStatusTransitionError`
   перехвачен и залогирован, исключение НЕ всплывает наружу и не роняет процесс `apps/worker`.

## Тест-план

Unit (`inventory-sync-failed-job.handler.spec.ts`, порты/BullMQ event замоканы):
- `финальный провал (attemptsMade===opts.attempts) переводит батч в failed_validation`
- `промежуточная неудача (attemptsMade < opts.attempts) не меняет статус батча`
- `записывается ровно одна строка inventory_sync_errors с error_code=processing_failed`
- `error_detail не содержит значения заголовков X-Pharmacy-*/секретов` (тест с фикстурой стека,
  содержащей заведомо чувствительное значение)
- `гонка с уже терминальным статусом батча перехватывается без падения процесса`
Интеграционный: полный BullMQ retry-цикл с реальным Redis, симуляция 5 подряд неудачных попыток
через тестовый процессор, бросающий исключение безусловно — подтверждение, что реальное BullMQ
`failed`-событие приходит с ожидаемым `attemptsMade`. Порог покрытия `infrastructure/` — 70%.

## Риски и подводные камни

- Различение «финальный провал» vs «промежуточная попытка» через `attemptsMade >= opts.attempts` —
  это поведение конкретной версии BullMQ (`^6.3.0`); сверить точное имя полей `job.attemptsMade`/
  `job.opts.attempts` с фактическим API на момент реализации, поведение между мажорными версиями
  BullMQ менялось.
- Санитизация секретов в `error_detail` — если у EP-01 уже есть готовый `pino redact`-хелпер для
  логов, лучше переиспользовать ЕГО набор путей/паттернов, а не изобретать параллельный список
  чувствительных полей (риск расхождения списков — один защищён, другой забыт).
