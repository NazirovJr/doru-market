## Задача

Второй таб экрана `/inventory` (DTJ-167 создал первый таб «Точечное редактирование») — таблица
массового редактирования остатков своей аптеки + загрузка Excel/CSV с шаблоном, выбором режима
(«Добавить/обновить» vs «Полная замена») и ОДНИМ агрегированным прогресс-баром, скрывающим от
пользователя, что импорт физически разбит на N батчей (CUJ-6' шаги 2-3).

## Технический контекст

Компонент `ProgressBar` (doc 30 §«Ключевые UI-компоненты») — «агрегирует N фоновых батчей
(SRS-INV-014)». Backend — `POST /inventory-excel-import` (DTJ-161, синхронный ответ с
`sourceUploadId`+`totalBatches`), опрос агрегированного статуса — `GET
/inventory-sync-batches?filter[sourceUploadId]=...` (DTJ-163, расширить фильтр списка полем
`sourceUploadId`, если DTJ-163 его ещё не предусмотрел — координировать точечной правкой контракта).
Шаблон — `GET /inventory-import-template` (DTJ-159). Отчёт об ошибках — `GET
/inventory-sync-batches/:sourceUploadId/error-report` (DTJ-164).

## Что сделать

1. `BulkEditGrid.tsx` — таблица (не полноценный spreadsheet-виджет, простая редактируемая
   HTML-таблица с инлайн-инпутами по строкам, `CursorTable`/`CursorList` из `packages/ui` как база
   пагинации, doc 30) — колонки: медикамент (readonly, выбран ранее ЛИБО подгружен из текущего
   остатка аптеки для редактирования существующих позиций), цена, остаток, срок годности, партия.
   Пагинация по 50-100 строк на экран (SRS-INV-015 п.б — «практически кабинет пагинирует сетку»).
   «Сохранить» отправляет ТОЛЬКО изменённые строки одним `POST /inventory-manual-entry` (DTJ-162,
   `rows.length <= 1000`, переиспользование ТОГО ЖЕ backend-эндпоинта, что точечное редактирование
   DTJ-167 — массовая сетка это НЕ Excel-канал, это тот же `manual_entry`-канал батчем).
2. `ExcelImportDropzone.tsx` — `FileDropzone` (`packages/ui`, doc 30), принимает `.xlsx`/`.csv`,
   превью имени файла + размера ДО отправки, радио-переключатель режима «Добавить/обновить» /
   «Полная замена ассортимента» (обязательный явный выбор — SRS-INV-014, кнопка «Загрузить»
   неактивна без выбранного режима), ссылка «Скачать шаблон» (`GET /inventory-import-template`,
   прямая ссылка на скачивание, не через `fetch`+blob, если backend отдаёт файл напрямую по URL с
   query-параметром авторизации/через тот же `http-client` с ответственным типом blob — выбрать
   реализацию так, чтобы `Authorization`-заголовок долетал до запроса, обычная `<a href>` этого не
   гарантирует для защищённых эндпоинтов — вероятно, `fetch` + `URL.createObjectURL`).
3. `use-excel-import.ts` — `useMutation` на `POST /inventory-excel-import`, при успехе получает
   `sourceUploadId`+`totalBatches`, запускает `ImportProgressBar` в режиме опроса.
4. `import-progress.model.ts` — чистая функция `computeAggregateProgress(batches: readonly {
   status: BatchStatus }[]): { percent: number; isComplete: boolean; hasErrors: boolean }` —
   `percent = (завершённые батчи / totalBatches) * 100`, `isComplete` когда ВСЕ батчи в терминальном
   статусе, `hasErrors` если хотя бы один `completed_partial_success`/`failed_validation`.
5. `ImportProgressBar.tsx` — TanStack Query `useQuery` с `refetchInterval` (например 2с, пока
   `!isComplete`) на `GET /inventory-sync-batches?filter[sourceUploadId]=...`, отображает
   `computeAggregateProgress` визуально; по завершении с ошибками — кнопка «Скачать отчёт об
   ошибках» (DTJ-164) + краткая сводка «Принято X из Y, ошибок Z».
6. Инвалидация кэша поиска после завершения импорта (аналог CUJ-6' шаг 4 «переходит на /search,
   находит только что загруженный товар») — этот тикет НЕ реализует сам `/search` (чужой модуль),
   но обязан корректно завершить свой прогресс-бар, чтобы пользователь понимал, когда переходить
   проверять результат.

## Критерии приёмки

1. **Given** файл на 2500 строк загружен, режим «Добавить/обновить» выбран, **When** «Загрузить»
   нажимается, **Then** `POST /inventory-excel-import` вызывается, ОДИН прогресс-бар отображается
   (не 3 отдельных индикатора для 3 батчей).
2. **Given** прогресс-бар опрашивает статус, 2 из 3 батчей завершены, **When** данные обновляются,
   **Then** `percent = 66.67%` (округление до целого в UI — `67%`), `isComplete=false`.
3. **Given** все 3 батча завершены, 1 с `completed_partial_success` (частичные ошибки), **When**
   опрос завершается, **Then** `isComplete=true`, `hasErrors=true`, кнопка «Скачать отчёт об
   ошибках» отображается.
4. **Given** файл загружается БЕЗ выбранного режима импорта, **When** пользователь пытается нажать
   «Загрузить», **Then** кнопка неактивна/показана инлайн-ошибка «Выберите режим импорта» —
   негативный сценарий (SRS-INV-014 — явный выбор, не эвристика).
5. **Given** массовая сетка, пользователь изменил цену у 3 из 80 строк, **When** «Сохранить»
   нажимается, **Then** запрос содержит ТОЛЬКО 3 изменённые строки, не все 80 (оптимизация трафика,
   не строгое SRS-требование, но разумная UX-практика — если не реализовано, зафиксировать как
   допустимое упрощение в PR, не критичный дефект).

## Тест-план

Unit/component (Vitest + Testing Library):
- `computeAggregateProgress: 2 из 3 завершённых батчей даёт percent≈67, isComplete=false`
- `computeAggregateProgress: все батчи терминальны даёт isComplete=true`
- `computeAggregateProgress: хотя бы один completed_partial_success/failed_validation даёт
  hasErrors=true`
- `computeAggregateProgress: 0 батчей (граничный случай) не делит на ноль`
- `ExcelImportDropzone: кнопка Загрузить неактивна без выбранного режима`
- `BulkEditGrid: Сохранить отправляет только изменённые строки`
- `ImportProgressBar: опрос останавливается (refetchInterval выключается) после isComplete=true`
E2E (Playwright): полный проход «скачать шаблон → заполнить (программно) → загрузить → дождаться
прогресс-бара → скачать отчёт об ошибках» против dev-API с намеренно ошибочным файлом. Порог
покрытия `frontend` — 70%.

## Риски и подводные камни

- `refetchInterval`-опрос без остановки — частая утечка в TanStack Query, если `isComplete` не
  корректно передан обратно в опцию `refetchInterval: (data) => data?.isComplete ? false : 2000` —
  явно протестировать (см. тест-план), не полагаться на визуальную проверку.
- Зависит от того, что DTJ-163 (список батчей) поддерживает фильтр `filter[sourceUploadId]` — если
  контракт DTJ-163 не предусматривает этот фильтр на момент реализации, координировать точечное
  расширение (небольшая правка Zod-схемы + SQL `WHERE`, не архитектурное изменение).
- Массовая сетка переиспользует `POST /inventory-manual-entry` (DTJ-162) для батча ИЗМЕНЁННЫХ
  строк — если реальная сетка содержит >1000 строк остатков аптеки одновременно (крупная точка с
  большим ассортиментом), пагинация сохранения по чанкам потребуется — для R1 предполагается, что
  типичная аптека не превышает 1000 позиций одновременно редактируемых за раз (реалистично, учитывая
  UI-пагинацию по 50-100 строк на экран) — зафиксировать как известное ограничение.
