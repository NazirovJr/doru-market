## Задача

Первый реальный экран `apps/pharmacy` (по `00-EPICS.md`, «первый экран — ручной ввод остатков») —
фармацевт/`pharmacy_admin` находит медикамент через существующий каталожный поиск и вводит
цену/остаток одной позиции. Без composite-матчинга (медикамент уже выбран интерфейсом) — самый
простой из трёх каналов с точки зрения UX, но первый, который делает кабинет полезным для аптеки
без 1С с первого дня (R1-5).

## Технический контекст

Автокомплит — `GET /api/v1/medicines?search=...` (существующий поисковый эндпоинт `catalog`-модуля,
EP-04/EP-06, НЕ специфицируется этим эпиком — переиспользуется как есть, SRS-INV-015). Debounce
150-300мс на клиенте (`SRS-DB-019`). Backend-эндпоинт — `POST /inventory-manual-entry` (DTJ-162).
Тап-зона ≥56×56px для критичных действий кабинета аптеки (`docs/spec/32-design-reference.md`
строка 32).

## Что сделать

1. `MedicineAutocomplete.tsx` — `entities`-уровня переиспользуемый компонент (если аналогичный
   автокомплит уже есть в `packages/ui`/`entities` от EP-06/EP-04 — переиспользовать, не
   дублировать; создаётся здесь ТОЛЬКО если ничего подходящего не существует к волне 4): debounce
   200мс, `TanStack Query` для запроса `/medicines?search=`, отображает `tradeName` +
   `dosageForm`/`dosageStrength` для различения похожих позиций.
2. `PointEditForm.tsx` — форма: выбранный медикамент (из автокомплита) + поля `Цена (TJS)`,
   `Остаток`, `Срок годности` (date picker), `Партия` (опционально), кнопка «Сохранить» (тап-зона
   56×56px). Ссылка/кнопка «Товара нет в списке» — согласно SRS-INV-016 ведёт на ОТДЕЛЬНЫЙ путь
   (эндпоинт `catalog`/`moderation`, вне этого тикета) — реализуется как заглушка/переход,
   отображающая сообщение «Функция появится позже» ЕСЛИ соответствующий эндпоинт другого модуля ещё
   не готов к волне 4 (не блокировать этот тикет ожиданием чужого API — см. риски).
3. `manual-entry-form.model.ts` — чистые функции валидации формы (цена `>0`, остаток `>=0`, дата не
   в прошлом — клиентская UX-подсказка, финальная валидация всё равно на backend) — покрыты unit-
   тестами, БЕЗ React в этом файле (`02` §5 — вычисления/ветвления правил в `model/`).
4. `use-manual-entry.ts` — TanStack Query `useMutation`, вызывает `POST /inventory-manual-entry` с
   ОДНОЙ строкой (`rows: [row]`), инвалидирует релевантный query cache (список остатков, если уже
   закэширован).
5. `InventoryPage.tsx` (`pages/inventory`) — композиция: переключатель вкладок «Точечное
   редактирование» / «Массовое редактирование» (`Tabs`-компонент из `packages/ui`, второй таб —
   заглушка до DTJ-168).
6. Toast-уведомление об успехе/ошибке (компонент `Toast`, `packages/ui`) — автозакрытие 4с при
   успехе, остаётся до действия при ошибке (§«Ключевые UI-компоненты», doc 30).

## Критерии приёмки

1. **Given** фармацевт вводит «цитрамон» в автокомплит, **When** результаты появляются, **Then**
   список показывает совпадающие медикаменты с формой выпуска/дозировкой для различения похожих
   позиций (не только название).
2. **Given** медикамент выбран, введены валидные цена/остаток/срок годности, **When** «Сохранить»
   нажимается, **Then** `POST /inventory-manual-entry` вызывается с `resolved: true` строкой,
   успешный ответ показывает Toast «Остаток обновлён», форма очищается для следующего ввода.
3. **Given** цена = `0` или отрицательная, **When** пользователь пытается сохранить, **Then**
   кнопка «Сохранить» неактивна ИЛИ инлайн-ошибка показана ДО отправки запроса (клиентская
   валидация) — негативный сценарий предотвращает бесполезный запрос к API.
4. **Given** запрос к API вернул `403 INSUFFICIENT_ROLE` (роль `pharmacist`, если backend решит
   ограничить — см. DTJ-162 «Риски»), **When** ответ получен, **Then** понятное сообщение об
   отсутствии прав показано пользователю, не сырой JSON ошибки — второй негативный сценарий.

## Тест-план

Unit/component (Vitest + Testing Library):
- `manual-entry-form.model: валидация отклоняет цену <= 0`
- `manual-entry-form.model: валидация отклоняет отрицательный остаток`
- `manual-entry-form.model: валидная форма проходит без ошибок`
- `MedicineAutocomplete debounce не отправляет запрос на каждое нажатие клавиши`
- `PointEditForm блокирует отправку при невалидной форме`
- `useManualEntry успешный вызов инвалидирует query cache и показывает Toast`

подтверждение» против dev-API. Порог покрытия `frontend` — 70%.

## Риски и подводные камни

- «Товара нет в списке» ведёт на эндпоинт другого модуля (`catalog`/`moderation`), который может
  быть не готов к волне 4 — заглушка допустима временно, но зафиксировать в PR как известный
  технический долг с ссылкой на то, какой эпик должен предоставить реальный эндпоинт.
- Зависит от готовности `MedicineAutocomplete`-подобного компонента в `packages/ui`/`entities` —
  если EP-06 (поиск) ещё не создал переиспользуемый компонент к волне 4 (EP-06 стартует В волне 5,
  ПОСЛЕ EP-05 волны 4 — по графу зависимостей `00-EPICS.md`), этот тикет реализует локальную версию
  первым, и EP-06 позже либо переиспользует её, либо мигрирует на свою — уточнить порядок с Tech
  Lead, если критично для избежания дублирования.
- **Более серьёзный риск того же рода**: сам эндпоинт `GET /api/v1/medicines?search=...`, который
  module 22 называет «уже существующим», принадлежит поиску (EP-06) или базовому каталогу (EP-04).
  EP-06 стартует ПОСЛЕ EP-05 по графу волн — если к моменту реализации этого тикета (волна 4) EP-04
  предоставляет только модель каталога БЕЗ поиска по тексту (поиск — явно зона EP-06,
  `20-module-catalog-search.md` §2-5), автокомплит на этом экране придётся временно реализовать
  поверх ГРУБОГО эндпоинта (например, `GET /medicines?tradeNameStartsWith=` от EP-04, если такой
  есть) или отложить полноценный автокомплит до готовности EP-06, показывая упрощённый список
  первое время. Зафиксировать фактическую готовность `catalog`-поиска на старте волны 4 как первое,
  что нужно проверить перед началом этого тикета — не тратить время на реализацию против
  несуществующего API.
