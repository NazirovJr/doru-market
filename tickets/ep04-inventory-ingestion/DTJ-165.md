## Задача

Charter §3.3 требует Provider Pattern: порт закладывается сразу, реальная реализация — по решению
пивота (`04-SCOPE-DECISION-PIVOT.md` §0 таблица) отложена в R2. Этот тикет ЗАКРЫВАЕТ R1-часть
контракта: интерфейс + детерминированный Mock, тестирующий форму контракта на фиксированном
XML-фикстуре — достаточно для E2E-теста и для пилотных сетей, согласных прислать реальный экспорт
для последующей вычитки формата в R2. Реальный `CommerceMl205ParserAdapter` (`fast-xml-parser`,
полный XML-парсер) — ЯВНО НЕ входит в этот тикет и не должен реализовываться.

## Технический контекст

ENV-переключатель `COMMERCE_ML_PARSER_DRIVER` (`mock` | `real`) — тот же паттерн, что у остальных
provider-портов платформы (OCR/STT/платежи — переиспользовать существующий DI-паттерн
`useFactory`/`ConfigService`, если EP-01 уже установил конвенцию для такого переключения, не
изобретать свою). В R1 `real`-значение НЕ реализовано — при попытке выбрать его приложение обязано
падать на старте с понятной ошибкой конфигурации, не молча использовать mock.

## Что сделать

1. `commerce-ml-parser.port.ts`: `CommerceMlParserPort.parse(xml: Buffer):
   Promise<CommerceMlParseResult>`, где `CommerceMlParseResult = { rows: readonly
   UnresolvedCommerceMlRow[] }` (форма, совместимая с unresolved-веткой `InventoryRowCommand`,
   DTJ-145) — интерфейс МИНИМАЛЬНЫЙ, чтобы R2 могла заменить реализацию без изменения потребителей.
2. `mock-commerce-ml-parser.adapter.ts`: `MockCommerceMlParserAdapter implements
   CommerceMlParserPort` — НЕ парсит переданный `xml` реально, а детерминированно возвращает
   ФИКСИРОВАННЫЙ набор строк (например, 3 строки с заведомо известными `internalSku`/`tradeName`/
   `priceDiram`/`quantity`), ЕСЛИ входной `xml` структурно похож на минимальный валидный CommerceML
   2.05 (наличие корневого тега `<КоммерческаяИнформация>` — простая проверка присутствия строки в
   буфере, не полный XSD) — при отсутствии этого маркера бросает
   `CommerceMlMalformedXmlError` (SRS-INV-018), чтобы контракт «невалидный файл → 400» тестировался
   даже с мок-реализацией.
3. Тестовый XML-фикстур — `apps/api/test/fixtures/commerce-ml/valid-offer-package.xml` (минимальная
   структура `<КоммерческаяИнформация><ПакетПредложений>`, НЕ полный реальный экспорт 1С — просто
   маркер для мок-адаптера) и `invalid-not-commerce-ml.xml` (произвольный XML без нужного корневого
   тега).
4. DI-регистрация в `InventoryModule` (DTJ-140): `{ provide: COMMERCE_ML_PARSER_PORT, useFactory:
   (config) => config.get('COMMERCE_ML_PARSER_DRIVER') === 'real' ? throwNotImplementedInR1() :
   new MockCommerceMlParserAdapter() }` — явный `throw` с понятным сообщением, если кто-то в R1
   попытается включить `real`.
5. Presentation-контроллер (`POST /api/v1/inventory-commerce-ml-import`, multipart XML) — ЯВНО НЕ
   входит в этот тикет (порт+мок без потребителя допустимо оставить неподключённым к HTTP в R1,
   т.к. реальных клиентов 1С в R1 нет — если продукт решит выставить REST-эндпоинт для приёма
   CommerceML уже в R1 поверх мока для демонстрации, это отдельный тикет, не создавать его здесь
   без явного запроса).

## Критерии приёмки

1. **Given** валидный (по маркеру мока) XML-файл, **When** `MockCommerceMlParserAdapter.parse(xml)`,
   **Then** возвращается детерминированный фиксированный набор из 3 строк, идентичный при повторном
   вызове с тем же входом (воспроизводимость для тестов).
2. **Given** XML без корневого тега `<КоммерческаяИнформация>`, **When** `parse(xml)` вызывается,
   **Then** бросается `CommerceMlMalformedXmlError` — точное соответствие TC-INV-030 (`400
   VALIDATION_ERROR`, батч не создаётся вовсе — маппинг в HTTP делается потребителем порта, не этим
   тикетом, если контроллер не входит в scope R1).
3. **Given** `COMMERCE_ML_PARSER_DRIVER=real` в конфигурации, **When** приложение стартует и
   пытается резолвить `COMMERCE_ML_PARSER_PORT`, **Then** старт падает с понятной ошибкой
   («CommerceML real-парсер не реализован в R1, используйте driver=mock») — негативный сценарий на
   уровне конфигурации, не тихая деградация к моку.
4. **Given** `COMMERCE_ML_PARSER_DRIVER` не задан (дефолт), **When** приложение стартует, **Then**
   используется `mock` (дефолтное значение ENV — R1 не требует явной конфигурации для работы «из
   коробки»).

## Тест-план

Unit (`mock-commerce-ml-parser.adapter.spec.ts`):
- `валидный маркерный XML даёт детерминированный фиксированный результат`
- `повторный вызов с тем же входом даёт идентичный результат` (детерминизм)
- `XML без корневого тега бросает CommerceMlMalformedXmlError` (TC-INV-030)
- `пустой Buffer бросает CommerceMlMalformedXmlError`
DI-тест (`inventory.module.spec.ts` или отдельный конфигурационный тест):
- `driver=real падает на старте с понятной ошибкой`
- `driver не задан использует mock по умолчанию`

## Риски и подводные камни

- Если к моменту R2 (другой проект/итерация) `CommerceMlParseResult`/порт потребуют расширения
  (реальный CommerceML 2.05 несёт больше метаданных, чем мок) — это ожидаемо, порт спроектирован
  МИНИМАЛЬНЫМ намеренно, расширение интерфейса в R2 не считается нарушением текущего контракта.
- Отсутствие HTTP-контроллера в R1 означает, что этот порт технически «мёртвый код» с точки зрения
  реального пользовательского пути до R2 — это ОСОЗНАННОЕ решение Charter §3.3 (Provider Pattern
  закладывается заранее), не нарушение C8 «мёртвый код запрещён» (порт+мок — инфраструктурная
  заготовка с явным техническим обоснованием, не забытый недописанный код).
