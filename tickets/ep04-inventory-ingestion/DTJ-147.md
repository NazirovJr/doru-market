## Задача

Строки, не найденные ни кэшем, ни точным штрихкодом (DTJ-146), проходят trigram fuzzy-поиск с
жёстким дозировочным фильтром и защитой от ложного авто-матча при неоднозначности — ядро
дефектного решения D-06 («прямой `WHERE barcode = ?` — дефект»). Без явной защиты от
неоднозначности (шаг 4) система рискует автоматически подставить НЕ ТОТ медикамент — критично для
лекарственного маркетплейса (два похожих дженерика с близкими названиями — типичный ложный
авто-матч).

## Технический контекст

SQL-запрос — дословно `22-module-inventory-sync-1c.md` строки 394-406, расширение готового запроса
`11-database-schema.md` §«Готовые SQL-запросы поиска» п.4 (порог `SRS-DB-018 = 0.35`). Дозировочный
фильтр — `Dosage.isEquivalentTo()` VO (`10-domain-model.md` SRS-DOM-078, shared kernel, как и
Barcode). Порог неоднозначности — `CATALOG_MATCH_AMBIGUITY_GAP` (ENV, ASSUMPTION `0.05`).
Публикация несматченной строки — `UnmatchedInventoryRowEvent` через `outbox` В ТОЙ ЖЕ транзакции,
что запись `inventory_sync_errors` (SRS-INV-027, `10-domain-model.md` SRS-DOM-151 — outbox-паттерн
уже реализован EP-01, этот тикет ТОЛЬКО формирует событие и вызывает существующий
`OutboxPort.append(event)`, не переизобретает механизм).

## Что сделать

1. Дополнить `CompositeInventoryMatcherService` методом `resolveFuzzyCandidates(pharmacyId: string,
   rows: readonly NeedsFuzzyRow[]): Promise<readonly FuzzyMatchResult[]>`, вызываемым для строк с
   `outcome: 'needs_fuzzy'` из DTJ-146.
2. Порт `CatalogFacade.findFuzzyCandidates(rows: readonly { rawTradeName: string; rawDosageForm?:
   string; rawManufacturerName?: string }[]): Promise<ReadonlyMap<number, readonly {
   medicineId: string; combinedScore: number; dosageStrength: string }[]>>` — ОДИН пакетный запрос
   через временную таблицу + `LATERAL JOIN` (SRS-INV-052 п.2, метод существует на стороне
   `CatalogFacade`, EP-04 — этот тикет потребляет, не реализует SQL внутри `catalog`).
3. Шаг 3 — фильтр после ранжирования: для топ-5 кандидатов каждой строки, `Dosage.parse(candidate.
   dosageStrength).isEquivalentTo(Dosage.parse(row.rawDosageStrength))` — несовпадающие ОТБРАСЫВАЮТСЯ
   целиком, даже при высоком `combinedScore` (SRS-INV-025).
4. Шаг 4 — после фильтра: если 0 кандидатов → `outcome: 'unmatched', reason: 'no_candidate'`; если
   ≥2 кандидата и `top1.combinedScore - top2.combinedScore < CATALOG_MATCH_AMBIGUITY_GAP` →
   `outcome: 'unmatched', reason: 'ambiguous'`; если ровно 1 кандидат ИЛИ разрыв ≥ порога →
   `outcome: 'matched', medicineId: top1.medicineId` (и сразу `pharmacy_sku_mapping.upsert(...,
   matchedVia='fuzzy_trigram')`, SRS-INV-023).
5. Для строк с `outcome: 'unmatched'` — сформировать `UnmatchedInventoryRowEvent { pharmacyId,
   rawRowPayload, reason }` и вызвать `OutboxPort.append(event)` В ТОЙ ЖЕ единице работы
   (`unitOfWork`), что запись `inventory_sync_errors(error_code='unmatched_medicine')` — это делает
   вызывающий use case (DTJ-148), данный сервис только ВОЗВРАЩАЕТ решение `unmatched` +
   сформированный event-payload, не пишет в БД сам (application-сервис матчинга — чистая логика
   резолюции, побочный эффект персистенции — ответственность use case, разделение по `02` §3).
6. `inventory-outbox.port.ts` — узкий порт `InventoryOutboxPort.append(event:
   UnmatchedInventoryRowEvent): void` (в рамках текущего `unitOfWork`, без собственного commit) —
   если общий `OutboxPort` EP-01 уже покрывает это по сигнатуре, использовать его напрямую и НЕ
   создавать дублирующий порт (см. риски).
7. Дедупликация по `(pharmacyId, internalSku)` (SRS-INV-027) — реализуется в DTJ-149/DTJ-148 через
   `ON CONFLICT` на стороне `catalog_match_queue` (владение `moderation`), этот сервис её не
   реализует — только формирует корректный payload события с обоими полями для дальнейшей
   дедупликации потребителем.

## Критерии приёмки

1. **Given** `raw_trade_name='Цитрамон П'`, ближайший кандидат `similarity=0.28`, **When**
   выполняется fuzzy-резолюция, **Then** результат — `outcome: 'unmatched', reason: 'no_candidate'`
   (ниже порога `0.35` — фильтруется ещё на уровне SQL `WHERE`) — точное соответствие TC-INV-010.
2. **Given** кандидат с `combinedScore=0.9`, но его `dosageStrength` НЕ эквивалентна
   `Dosage.isEquivalentTo()`, **When** применяется шаг 3, **Then** кандидат отброшен целиком,
   переход к следующему из топ-5 — негативный сценарий, точное соответствие TC-INV-011.
3. **Given** топ-1 `score=0.40`, топ-2 `score=0.38` (разница `0.02 < 0.05`), **When** резолюция
   завершена, **Then** `outcome: 'unmatched', reason: 'ambiguous'`, авто-выбор НЕ производится —
   точное соответствие TC-INV-012.
4. **Given** ровно один кандидат прошёл фильтры (единственный, `score=0.37`), **When** резолюция
   завершена, **Then** `outcome: 'matched'` — правило неоднозначности НЕ применяется при единственном
   кандидате (сравнивать не с чем).
5. **Given** строка с `outcome: 'unmatched'`, **When** сервис возвращает результат, **Then** объект
   результата содержит корректно заполненный `UnmatchedInventoryRowEvent`-payload с полем `reason`,
   соответствующим фактической причине (`no_candidate`/`ambiguous`).

## Тест-план

Unit (`composite-inventory-matcher.service.spec.ts`, продолжение файла DTJ-146, порты замоканы):
- `score ниже 0.35 даёт unmatched/no_candidate`
- `несовпадение dosageStrength отбрасывает кандидата с высоким textual score`
- `отброшенный кандидат уступает место следующему из топ-5`
- `разница score < CATALOG_MATCH_AMBIGUITY_GAP даёт unmatched/ambiguous`
- `разница score >= CATALOG_MATCH_AMBIGUITY_GAP даёт matched с top1`
- `единственный кандидат даёт matched без проверки на неоднозначность`
- `успешный fuzzy-матч обновляет pharmacy_sku_mapping с matchedVia=fuzzy_trigram`
- `findFuzzyCandidates вызывается одним пакетным запросом на весь набор needs_fuzzy строк батча`
Интеграционный: `catalog.findFuzzyCandidates` тестируется на стороне `catalog`-модуля (EP-04), этот
тикет мокает порт — не дублирует SQL-тест чужого модуля. Порог покрытия `application/` — 90%.
