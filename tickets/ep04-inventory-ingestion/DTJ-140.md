## Задача

EP-05 — первый и единственный эпик, владеющий каталогом `modules/inventory/**`. Прежде чем можно
будет параллельно писать use case'ы, адаптеры и контроллеры (следующие ~25 тикетов эпика), нужен
единый скелет: структура 4 слоёв Clean Architecture, файл модуля с DI-заготовкой, публичный фасад
(`index.ts`) и подпапка контрактов `packages/contracts/src/inventory/`. Без этого тикета остальные
тикеты эпика не имеют куда класть файлы, а параллельные разработчики будут конфликтовать на
создании одних и тех же базовых файлов.

## Технический контекст

Структура — буквально по дереву файлов `docs/spec/22-module-inventory-sync-1c.md` §1:
`modules/inventory/{domain,application,infrastructure,presentation}`. Правило Зависимостей —
`02-CLEAN-ARCHITECTURE-AND-CODE.md` §1: `presentation → application → domain ← infrastructure`,
`domain` — ноль импортов фреймворка. Публичный фасад — `02` §1.2: `modules/inventory/index.ts`
экспортирует только `InventoryFacade` (интерфейс), публичные типы и доменные события — ничего
внутреннего.

`apps/worker` — отдельное NestJS-приложение (см. `01-TECH-BASELINE.md`), которое поднимает BullMQ
`Worker` для `inventory-sync-queue` (§6 модуля 22). Т.к. `apps/api/src/modules/inventory/**` и
`apps/worker/src/jobs/inventory-sync/**` — два разных files_owned эпика (см. `00-EPICS.md` §«Владение
файлами»), процессор очереди (`infrastructure/workers/inventory-sync-batch.processor.ts`) физически
живёт в `apps/api/src/modules/inventory/infrastructure/workers/`, а `apps/worker/src/jobs/
inventory-sync/inventory-sync.module.ts` — тонкий bootstrap-модуль `apps/worker`, который
импортирует `InventoryModule` (или отдельно экспортируемый `InventoryWorkerModule`, который
регистрирует ТОЛЬКО провайдеры процессора+портов, без HTTP-контроллеров) через общий алиас
`@/modules/inventory` (оба приложения используют один `tsconfig.base.json`, monorepo `pnpm`/`turbo`).
Это предположение (ASSUMPTION) — конкретный механизм шаринга кода между `apps/api` и `apps/worker`
не описан явно ни в одном документе иерархии; см. «Риски».

Контракты (`packages/contracts`): по правилу «Пересекающееся владение» п.3 (`00-EPICS.md`) EP-01
владеет барабанным `packages/contracts/src/index.ts` и общими файлами (`errors.ts`,
`permissions.ts`); каждый следующий эпик добавляет ТОЛЬКО новый файл в свою подпапку. Для EP-05 это
`packages/contracts/src/inventory/*`. Единственное разрешённое касание чужого файла — одна строка
`export * from './inventory';` в существующем `packages/contracts/src/index.ts` (созданном EP-01
раньше по волнам выполнения).

## Что сделать

1. Создать структуру папок `apps/api/src/modules/inventory/{domain,application/{use-cases,ports,
   services},infrastructure/{adapters,workers,jobs},presentation/{controllers,guards,mappers}}`.
2. `apps/api/src/modules/inventory/inventory.module.ts` — `@Module({...})` класс `InventoryModule`
   с пустыми массивами `controllers`/`providers`/`exports` (заполняются последующими тикетами через
   `replace_symbol_body`, не через переписывание файла) и комментарием `// TODO(DTJ-14x): …` на
   каждую секцию, перечисляющим, каким тикетом она будет заполнена — ориентир для параллельных
   разработчиков, не мусор (не блокирующий C11, т.к. это временная навигационная разметка эпика).
3. `apps/api/src/modules/inventory/index.ts` — публичный фасад: экспортирует пока только тип
   `InventoryFacade` (пустой интерфейс-заглушка с комментарием, какие методы добавит какой тикет:
   `applyRetroactiveMatch` — DTJ-149) и реэкспорт `InventoryModule`. Правило: ничего из `domain/**`,
   `application/**` (кроме фасада), `infrastructure/**` не реэкспортируется отсюда.
4. Зарегистрировать `InventoryModule` в корневом `AppModule` (`apps/api/src/app.module.ts`,
   владеет EP-01, но регистрация нового модуля — однострочное дополнение, разрешённое как
   «гостевая правка» по аналогии с правилом роутинга `apps/admin` в `00-EPICS.md`).
5. `apps/worker/src/jobs/inventory-sync/inventory-sync.module.ts` — тонкий `InventoryWorkerModule`,
   пока с пустым провайдером-заглушкой (`useValue: null` под токеном-плейсхолдером), заполняется
   тикетом DTJ-154. Зарегистрировать в `apps/worker/src/app.module.ts` (та же логика гостевой правки).
6. `packages/contracts/src/inventory/index.ts` — пустой барабанный файл с комментарием-планом
   (`batch-update.schema.ts` — DTJ-157, `manual-entry.schema.ts` — DTJ-162,
   `excel-import.schema.ts` — DTJ-161, `sync-batches.schema.ts` — DTJ-163).
7. В `packages/contracts/src/index.ts` добавить строку `export * from './inventory';`.
8. Настроить `apps/api/src/modules/inventory/**` и `apps/worker/src/jobs/inventory-sync/**` в
   соответствующих `tsconfig.json` (`include`), чтобы `projectService: true` (см. `02` §6.1) не
   ронял линт «файл-сирота» на пустых заглушках.
9. Прогнать `pnpm arch:check` и `pnpm lint` — новый пустой модуль обязан проходить оба чисто.

## Критерии приёмки

1. **Given** свежий чекаут ветки, **When** запускается `pnpm --filter api build` и
   `pnpm --filter worker build`, **Then** сборка проходит без ошибок TypeScript, `InventoryModule` и
   `InventoryWorkerModule` импортируются в соответствующие `AppModule` без циклических зависимостей.
2. **Given** `dependency-cruiser`-конфиг (`.dependency-cruiser.cjs`, владение EP-01), **When**
   запускается `pnpm arch:check`, **Then** новый модуль не нарушает Правило Зависимостей (нет
   импортов `infrastructure` в `application`, нет прямых импортов `domain` из `presentation`) — по
   факту пока нечего нарушать (файлы пустые), тест фиксирует БАЗОВУЮ линию для последующих тикетов.
3. **Given** попытка добавить в `packages/contracts/src/inventory/index.ts` прямой импорт из
   `apps/api/**` (негативный сценарий — контракты не должны знать о backend-реализации), **When**
   запускается `pnpm lint`, **Then** `import/no-relative-parent-imports`/границы workspace-пакетов
   (`packages/contracts` не имеет `apps/*` в зависимостях `package.json`) ловят нарушение красным CI.
4. **Given** `packages/contracts/src/index.ts` уже содержал реэкспорты других подпапок (`errors`,
   `permissions`), **When** добавляется `export * from './inventory'`, **Then** остальные
   реэкспорты не удалены и не переупорядочены произвольно (точечная правка, не перезапись файла).

## Тест-план

Unit-тестов в этом тикете содержательно нет (пустые заглушки) — вместо этого:
- `tests/arch/inventory-module-boundaries.spec.ts` — фикстура-нарушитель (временный файл с
  запрещённым импортом `application → infrastructure` внутри `modules/inventory`), тест проверяет,
  что `pnpm arch:check` отклоняет его (по аналогии с требованием `02` §6.1 «ловушку нужно проверять
  ловушкой» — этот тикет первый в модуле, разумно закрыть эту гарантию сразу, не откладывать).
- Интеграционный: `apps/api` и `apps/worker` поднимаются в CI (`pnpm --filter api test:e2e --
  --testPathPattern=health`) и health-check (`@nestjs/terminus`, EP-01) остаётся зелёным после
  регистрации нового модуля.
- E2E не требуется (нет пользовательского сценария).
- Порог покрытия 90% для `domain/application` в этом тикете неприменим (нет бизнес-логики) —
  фиксируется как валидный нулевой результат, не нарушение.

## Риски и подводные камни

- **Механизм шаринга кода `apps/api` ↔ `apps/worker` не описан явно ни в одном документе
  иерархии.** Раздел «Технический контекст» фиксирует ASSUMPTION (общий алиас `@/modules/inventory`
  через `tsconfig.base.json`, `apps/worker` импортирует providers из `apps/api`). Если Architect на
  старте эпика решит иначе (например, вынести общую бизнес-логику в `packages/domain-inventory` как
  отдельный workspace-пакет), этот тикет и структура `files_owned` последующих тикетов потребуют
  правки — сделать это ПЕРВЫМ, до начала параллельной работы над DTJ-141+.
- Пустые `.gitkeep`-заглушки — временный приём, чтобы зарезервировать структуру папок под git
  (git не хранит пустые директории). Следующий тикет, кладущий первый файл в папку, удаляет
  соответствующий `.gitkeep`.
- Регистрация `InventoryModule` в `AppModule` до появления в нём контроллеров/провайдеров может
  формально быть no-op — важно не оставить забытую регистрацию, если DI-граф позже перестроится.
- Файл `apps/api/src/modules/inventory/inventory.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
