## Задача

EP-05 — первый эпик, которому нужен `apps/pharmacy` (кабинет аптеки), поэтому по `00-EPICS.md`
(«Scaffolding `apps/pharmacy` — EP-05, первый экран — ручной ввод остатков») этот тикет создаёт
базовый каркас приложения: без него DTJ-167/168/169 (экраны кабинета) не имеют куда монтироваться.
EP-12 (сборка заказа, волна 8) позже добавит свои экраны в отдельный `features/order-fulfillment/**`
поверх ЭТОГО каркаса, не переписывая его.

## Технический контекст

Структура — `02-CLEAN-ARCHITECTURE-AND-CODE.md` §5: `app → pages → features → entities → shared`.
Стек — `01-TECH-BASELINE.md`: React 19, Vite 7, Tailwind v4 (CSS-first, `@theme`), TanStack Query 5,
`react-router` 7, Zustand 5. Авторизация — OTP-вход, ТОТ ЖЕ контракт `/auth/otp/request`/`verify`,
что `apps/web`/`apps/admin` (`SRS-API-018..023`, EP-01) — этот тикет переиспользует существующий
auth-flow (компоненты/хуки из `packages/ui`/`shared`, если EP-01 уже вынес их переиспользуемо;
дублировать OTP-форму с нуля — нарушение C15, если общий компонент уже существует к волне 4).

**Именование маршрутов**: `docs/spec/30-ux-screens-and-flows.md` описывает экраны кабинета аптеки
под префиксом `/admin/...` (например `/admin/inventory`), тогда как `01-TECH-BASELINE.md` явно
перечисляет `apps/pharmacy` ОТДЕЛЬНЫМ приложением от `apps/admin`. Это расхождение — см. «Риски».
Решение этого тикета: маршруты `apps/pharmacy` используют СВОЙ собственный неймспейс без префикса
`/admin` (например `/inventory`, `/inventory/sync-history`, `/order-queue`), т.к. приложение и так
физически изолировано от `apps/admin` на уровне сборки/домена — префикс `/admin` внутри ОТДЕЛЬНОГО
приложения избыточен и вводит в заблуждение.

## Что сделать

1. `apps/pharmacy/package.json` — по образцу `apps/web`/`apps/admin` (если уже существуют к волне
   4 — копировать структуру зависимостей оттуда, не с нуля), версии строго по
   `01-TECH-BASELINE.md`.
2. `vite.config.ts` — `@vitejs/plugin-react`, `@tailwindcss/vite`, алиас `@/` на `src/`.
3. `src/app/App.tsx` — корневой компонент, `QueryClientProvider` (TanStack Query),
   `RouterProvider`.
4. `src/app/router.tsx` — `react-router` 7 конфигурация: `/login` (публичный), `/` (редирект на
   `/inventory` после авторизации), остальные маршруты — заглушки `<Suspense>`+`lazy()` для
   DTJ-167/168/169 (регистрируются пустыми, следующие тикеты заполняют).
5. `src/shared/auth/auth-guard.tsx` — `RequireAuth` HOC/компонент, редиректит на `/login` при
   отсутствии валидного access-токена (переиспользование `shared/auth`-инфраструктуры EP-01, если
   уже вынесена в общий пакет; иначе — минимальная локальная реализация с TODO на дедупликацию).
6. `src/pages/login/LoginPage.tsx` — OTP-форма (телефон → 6-значный код), переиспользует
   `packages/ui` компоненты (`OTP-ячейки`, `SearchBar`-подобные инпуты — по факту готовности
   дизайн-системы к волне 4).
7. `src/shared/api/http-client.ts` — `axios`/`fetch`-обёртка с интерцептором `Authorization:
   Bearer`, обработкой `401 TOKEN_EXPIRED` → один retry через `/auth/refresh` (тот же паттерн, что
   `SRS-API-035` описывает для Flutter-клиентов — здесь веб-эквивалент).
8. Брендинг/токены дизайн-системы — подключить `packages/ui` CSS-переменные (White-Label,
   `02` §5 — «ноль хардкодных цветов»), даже если `apps/pharmacy` пока не поддерживает White-Label
   активно (аптеки видят нейтральный DoruTJ или свою сеть — уточнить по факту готовности
   `tenancy`-инфраструктуры к волне 4, механизм тот же, что у `apps/web`).
9. `i18n` — подключить `packages/i18n`, `useT()` доступен с первого экрана (`LoginPage`).

## Критерии приёмки

1. **Given** `pnpm --filter pharmacy dev`, **When** приложение открывается в браузере, **Then**
   отображается `LoginPage` (неавторизованный доступ к `/inventory` редиректит на `/login`).
2. **Given** успешный OTP-вход (`pharmacy_admin`/`pharmacist`), **When** пользователь
   авторизован, **Then** редирект на `/inventory` (пока пустая заглушка до DTJ-167).
3. **Given** access-токен истёк, **When** запрос к API возвращает `401 TOKEN_EXPIRED`, **Then**
   `http-client` автоматически вызывает `/auth/refresh` ОДИН РАЗ и повторяет исходный запрос;
   повторный `401` после рефреша → редирект на `/login`, НЕ бесконечный цикл — негативный сценарий
   защиты от зацикливания (SRS-API-035 аналог для веба).
4. **Given** роль `customer`/`courier` (не персонал аптеки) пытается авторизоваться через
   `apps/pharmacy`, **When** попытка входа выполняется, **Then** доступ отклонён (кабинет — только
   для `pharmacist`/`pharmacy_admin`/`super_admin`) — второй негативный сценарий, скоуп приложения.

## Тест-план

- `AuthGuard редиректит неавторизованного пользователя на /login`
- `AuthGuard пропускает авторизованного пользователя`
- `http-client повторяет запрос один раз после успешного refresh`
- `http-client редиректит на /login после повторного 401`
- `LoginPage валидирует формат телефона перед отправкой OTP-запроса`

(`02` §6 п.4, не 90% — это не domain/application backend).

## Риски и подводные камни

- **Расхождение именования маршрутов `/admin/...` (доку 30) vs отдельное приложение `apps/pharmacy`
  (tech baseline) — решение этого тикета (свой неймспейс без префикса) требует подтверждения
  архитектором/Tech Lead до того, как DTJ-167/168/169 закрепят конкретные пути в коде.** Если
  решение будет иным (например, `apps/pharmacy` и `apps/admin` на самом деле один физический билд с
  разным входом), это тикет и все последующие фронтенд-тикеты эпика требуют пересмотра — поднять
  вопрос ПЕРВЫМ в очереди эпика, не после того, как 3 экрана уже реализованы на неверном допущении.
