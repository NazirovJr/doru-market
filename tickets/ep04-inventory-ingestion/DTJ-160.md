## Задача

Файл, загруженный аптекой, может содержать до `EXCEL_IMPORT_MAX_ROWS` (20 000) строк с переставленными
столбцами, неоднозначными датами, пустыми опциональными полями. Этот тикет — единственное место, где
байты файла превращаются в типизированный массив `InventoryRowCommand`-совместимых строк, с явным
отказом вместо угадывания там, где формат неоднозначен (SRS-INV-013 — «явная ошибка лучше молчаливой
порчи данных»).

## Технический контекст

Валидация — ПО ЗАГОЛОВКУ, не по позиции столбца (аптека может переставить столбцы в Excel без
последствий, SRS-INV-012). Заголовки — переиспользуются из `INVENTORY_IMPORT_TEMPLATE_HEADERS`
(константа, введённая DTJ-159 — см. риск синхронизации там). Дата — строго `ДД.ММ.ГГГГ`; любое
отклонение (включая формально валидные, но иначе оформленные даты типа `MM/DD/YYYY` или
`ГГГГ-ММ-ДД`) → `error_code='ambiguous_date_format'`, БЕЗ эвристики угадывания (SRS-INV-013).

## Что сделать

1. `excel-inventory-parser.port.ts`: `ExcelInventoryParserPort.parse(file: Buffer, mimeType:
   string): Promise<{ rows: readonly ParsedExcelRow[]; rejectedRows: readonly { rowIndex: number;
   errorCode: InventorySyncRowErrorCode; rawRow: Record<string, unknown> }[] }>`, где
   `ParsedExcelRow` — форма, совместимая с unresolved-веткой `InventoryBatchUpsertRow` (DTJ-145) ДО
   конструирования VO (парсер отдаёт примитивы, VO конструируется в контроллере/маппере DTJ-161, не
   здесь — разделение ответственности: парсер знает формат файла, не знает доменных инвариантов).
2. `xlsx-excel-inventory-parser.adapter.ts`: `XlsxExcelInventoryParserAdapter implements
   ExcelInventoryParserPort` — на `exceljs` (тот же пакет, что DTJ-159, обоснование уже дано там —
   не дублировать обоснование нового пакета повторно в PR этого тикета).
3. Определение MIME/расширения (`.xlsx` vs `.csv`) — читать оба формата единым внутренним
   представлением (для CSV — `exceljs` не парсит CSV нативно в общем случае; использовать `exceljs
   .csv.read()` API либо, если формат/кодировка CSV нестандартны, отдельный лёгкий CSV-парсер —
   решить по факту тестирования реальных файлов из Excel; зафиксировать выбор в коде комментарием).
4. Чтение заголовков первой строки — построить `Map<string, columnIndex>` по фактическому файлу,
   сверить с обязательными заголовками из `INVENTORY_IMPORT_TEMPLATE_HEADERS`; отсутствие ЛЮБОЙ
   обязательной колонки → весь файл отклоняется целиком (`ExcelTemplateHeaderMismatchError`,
   application-уровень, ДО построчной обработки — это ошибка структуры файла, не строки).
5. Построчный разбор (после заголовка): для каждой строки — маппинг по индексам найденных колонок
   (не по позиции!), валидация:
   - `Внутренний код (SKU)`/`Торговое название`/`Цена (TJS)`/`Остаток (шт.)`/`Срок годности` —
     обязательны; пусто → `error_code='missing_required_field'`.
   - `Штрихкод` — если непусто, должен быть РОВНО 13 цифр, иначе сохраняется как есть для аудита
     (не блокирует строку, SRS-DOM-076/177 — тот же принцип, что и невалидный EAN-13 в матчинге).
   - `Цена (TJS)` — число `> 0`; иначе `error_code='invalid_price'`.
   - `Остаток (шт.)` — целое `>= 0`; иначе `error_code='invalid_quantity'`.
   - `Срок годности` — РЕГУЛЯРНОЕ выражение `^\d{2}\.\d{2}\.\d{4}$` СТРОГО; при несовпадении (в том
     числе если ячейка выглядит как валидная дата в другом формате) →
     `error_code='ambiguous_date_format'` — парсер НЕ пытается угадать (SRS-INV-013).
6. Строки, провалившие построчную валидацию, попадают в `rejectedRows` (НЕ в `rows`) — остальные
   строки файла продолжают обрабатываться (частичный успех уже на уровне парсинга, не только на
   уровне use case).
7. Лимит `EXCEL_IMPORT_MAX_ROWS` (ASSUMPTION `20000`, ENV) — превышение → весь файл отклоняется
   целиком с понятной ошибкой (не построчно).

## Критерии приёмки

1. **Given** корректный файл с переставленными столбцами (`Цена (TJS)` идёт раньше `Торговое
   название`, но заголовки на месте), **When** парсинг выполняется, **Then** данные читаются
   ПРАВИЛЬНО (по заголовку, не по позиции) — точное соответствие требованию SRS-INV-012.
2. **Given** ячейка `Срок годности` = `15/03/2028` (неоднозначный формат — американский `MM/DD/
   YYYY`), **When** `XlsxExcelInventoryParserAdapter` разбирает файл, **Then** строка отклонена с
   `error_code='ambiguous_date_format'`, ОСТАЛЬНЫЕ строки файла обработаны штатно — точное
   соответствие TC-INV-006.
3. **Given** файл БЕЗ колонки `Остаток (шт.)` вовсе (пользователь случайно удалил столбец), **When**
   парсинг выполняется, **Then** весь файл отклоняется целиком с
   `ExcelTemplateHeaderMismatchError` — негативный сценарий на уровне структуры файла, не строки.
4. **Given** файл из 25000 строк (> `EXCEL_IMPORT_MAX_ROWS=20000`), **When** парсинг выполняется,
   **Then** файл отклоняется целиком до построчной обработки — второй негативный сценарий на уровне
   структуры.
5. **Given** штрихкод `'123'` (не 13 цифр), **When** строка парсится, **Then** строка НЕ отклоняется
   целиком — `rawBarcode` сохраняется как есть, остальные поля строки обрабатываются штатно
   (штрихкод — не блокирующее поле).

## Тест-план

Unit (`xlsx-excel-inventory-parser.adapter.spec.ts`, реальные тестовые `.xlsx`-фикстуры — генерация
через `exceljs` в `beforeAll` теста, не бинарные файлы в репозитории):
- `корректный файл с переставленными колонками парсится верно по заголовку`
- `дата в формате ДД.ММ.ГГГГ принимается`
- `дата в формате MM/DD/YYYY отклоняется как ambiguous_date_format` (TC-INV-006)
- `дата в формате ГГГГ-ММ-ДД отклоняется как ambiguous_date_format`
- `отсутствие обязательной колонки отклоняет весь файл`
- `пустое обязательное поле в строке даёт missing_required_field, не блокируя остальные строки`
- `цена <= 0 даёт invalid_price`
- `остаток отрицательный даёт invalid_quantity`
- `штрихкод не из 13 цифр сохраняется как есть, не блокирует строку`
- `файл сверх EXCEL_IMPORT_MAX_ROWS отклоняется целиком`
- `CSV-файл с тем же набором заголовков парсится идентично XLSX` (если реализован единый путь)
Порог покрытия `infrastructure/` — 70%, но парсер — чистая функция преобразования без побочных
эффектов, разумно стремиться к более высокому фактическому покрытию.

## Риски и подводные камни

- CSV-парсинг через `exceljs` может быть не полностью надёжен для файлов, сохранённых разными
  локалями Excel (разделитель `;` вместо `,`, кодировка `cp1251` вместо `UTF-8`) — если тестирование
  на реальных файлах выявит проблему, рассмотреть отдельный лёгкий пакет (`csv-parse`) ТОЛЬКО для
  CSV-ветки с явным обоснованием нового пакета в PR; не блокировать тикет ожиданием идеального
  покрытия всех локалей Excel — R1 фиксирует одну поддерживаемую кодировку (UTF-8), остальное —
  известное ограничение, зафиксировать в PR.
- Память: файл до 20000 строк, читаемый целиком в память (`exceljs` по умолчанию не потоковый для
  `.xlsx`) — приемлемо для MVP-масштаба, но зафиксировать как потенциальную точку роста при реальных
  объёмах (потоковый режим `exceljs` доступен, но сложнее в реализации — не требуется для R1).
