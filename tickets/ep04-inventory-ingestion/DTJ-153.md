## Задача

Job постановки в очередь `inventory-sync-queue` обязана создаваться В ТОЙ ЖЕ транзакции БД, что и
вставка строки `inventory_sync_batches` — иначе при падении процесса между коммитом БД и постановкой
в Redis job теряется безвозвратно (принятый `202` клиенту, но батч никогда не обработается). D-05
уже отклонил ad-hoc продюсер как ненадёжный путь — этот тикет подключает `inventory-sync-queue` к
УЖЕ существующему механизму `outbox`/`OutboxRelayWorker` (EP-01), не создаёт параллельный.

## Технический контекст

`OutboxRelayWorker` (EP-01, `10-domain-model.md` §«Доменные события», SRS-DOM-151/152) читает
`outbox WHERE status='pending' ORDER BY created_at`, публикует в целевую очередь, помечает
`published`. Этот тикет — потребительская сторона: подписка `OutboxRelayWorker` на
`event_type='InventoryBatchQueuedEvent'` → постановка BullMQ job. `jobId = batchId` (SRS-INV-032 —
дедупликация постановки при at-least-once доставке outbox). Приоритет — SRS-INV-034 (`rest_api`/
`manual_entry` delta = `1`, `excel_import` delta = `5`, любой `full` = `10`).

## Что сделать

1. `inventory-sync-queue.port.ts`: `InventorySyncQueuePort.enqueue(job: InventorySyncJobData):
   Promise<void>` — интерфейс на стороне `application`, используется контроллерами каналов
   (DTJ-157/161) КОСВЕННО — через публикацию `InventoryBatchQueuedEvent` в общий `OutboxPort`
   (EP-01), не через прямой вызов этого порта из контроллера (иначе транзакционная гарантия
   теряется — прямой вызов `enqueue` из HTTP-хендлера БЕЗ outbox нарушал бы саму цель этого
   тикета). Порт нужен только на стороне BullMQ-адаптера, который РЕАЛЬНО кладёт job в Redis, когда
   `OutboxRelayWorker` вызывает подписчика.
2. `InventorySyncJobData` тип — дословно `22-module-inventory-sync-1c.md` строки 468-473:
   `{ batchId: string; pharmacyId: string; channel: InventorySyncChannel; syncType: 'full' |
   'delta' }` — БЕЗ самих строк `items` (SRS-INV-031 — job не несёт payload, воркер читает
   `inventory_sync_raw_items` по `batchId`).
3. `bullmq-inventory-sync-queue.adapter.ts`: `BullmqInventorySyncQueueAdapter implements
   InventorySyncQueuePort` — оборачивает `Queue('inventory-sync-queue')` (BullMQ, `ioredis`
   соединение — переиспользование общего Redis-клиента EP-01, не новое соединение). Метод
   `enqueue(job)`:
   - `jobId: job.batchId` (SRS-INV-032).
   - `priority`: функция `resolveJobPriority(channel, syncType): number` — чистая функция,
     `rest_api`/`manual_entry` + `delta` → `1`; `excel_import` + `delta` → `5`; ЛЮБОЙ `syncType===
     'full'` → `10` (SRS-INV-034) — покрыть таблицей, не цепочкой `if/else if` (C6/C10, читаемость).
   - `attempts: 5, backoff: { type: 'exponential', delay: 5000 }` (SRS-INV-035 — параметры retry
     задаются здесь при постановке, обработка исчерпания retry — DTJ-155).
4. `InventoryBatchQueuedEventHandler` (или эквивалент точки интеграции с `OutboxRelayWorker` —
   конкретный механизм подписки зависит от того, как EP-01 спроектировал `OutboxRelayWorker`:
   реестр обработчиков по `event_type` vs единая шина — использовать существующий паттерн EP-01,
   НЕ изобретать новый способ подписки; если `OutboxRelayWorker` ожидает регистрацию через DI-токен
   `OUTBOX_EVENT_HANDLERS`, зарегистрировать `BullmqInventorySyncQueueAdapter.handle(event)` там).
5. Регистрация адаптера под токеном `InventorySyncQueuePort` в `InventoryModule` (DTJ-140).

## Критерии приёмки

1. **Given** событие `InventoryBatchQueuedEvent{ batchId: 'B1', channel: 'rest_api', syncType:
   'delta' }`, **When** `OutboxRelayWorker` доставляет его обработчику, **Then** в BullMQ-очередь
   `inventory-sync-queue` кладётся job с `jobId='B1'`, `priority=1`.
2. **Given** тот же batchId `'B1'`, **When** обработчик вызывается ПОВТОРНО (симуляция at-least-once
   доставки `OutboxRelayWorker`, SRS-DOM-152), **Then** BullMQ отклоняет вторую постановку job с тем
   же `jobId` (проверяется через `Queue.getJob('B1')` — существует ровно один job, не два) — точное
   соответствие TC-INV-015.
3. **Given** событие с `channel='excel_import', syncType='delta'`, **When** job ставится, **Then**
   `priority=5`.
4. **Given** событие с `syncType='full'` (любой канал, включая `manual_entry`, если такое в принципе
   возможно — full-режим Excel), **When** job ставится, **Then** `priority=10` — негативный
   сценарий в смысле «не наследует priority=1 канала, если syncType=full переопределяет его».

## Тест-план

Unit (`bullmq-inventory-sync-queue.adapter.spec.ts`, BullMQ `Queue` замокан или тестируется через
`ioredis-mock`/тестовый Redis-контейнер — выбрать в зависимости от того, что уже настроено EP-01
для тестов очередей; если ничего не настроено, использовать `bullmq`'s тестовый режим с реальным
Redis в Docker для интеграционного слоя, а unit — с полным моком `Queue`):
- `resolveJobPriority(rest_api, delta) === 1`
- `resolveJobPriority(manual_entry, delta) === 1`
- `resolveJobPriority(excel_import, delta) === 5`
- `resolveJobPriority(любой_канал, full) === 10` (параметризованный тест по всем 4 каналам)
- `enqueue вызывает Queue.add с jobId=batchId`
- `enqueue передаёт attempts=5 и exponential backoff с delay=5000`
Интеграционный (`bullmq-inventory-sync-queue.adapter.integration.spec.ts`, реальный Redis):
- `повторная постановка job с тем же jobId не создаёт дубликат в очереди` (TC-INV-015 буквально)
Порог покрытия `infrastructure/` — 70%, `resolveJobPriority` как чистая функция можно вынести и
покрыть на 100% отдельно.

## Риски и подводные камни

- Точный механизм подписки на `OutboxRelayWorker` (реестр обработчиков по `event_type` vs что-то
  иное) зависит от реализации EP-01, которая на момент написания этого тикета ещё не создана
  (EP-01 — первый эпик, но конкретные внутренности `OutboxRelayWorker` могут быть решены позже
  волны 1). Если к волне 4 интерфейс подписки ещё не задокументирован — читать код EP-01 напрямую
  (`apps/api/src/infrastructure/outbox/**`, ожидаемое расположение) перед реализацией, не гадать.
- BullMQ `^6.3.0` — `Queue.add(name, data, { jobId, priority, attempts, backoff })` — сверить точную
  сигнатуру опций с фактической версией пакета на момент реализации (мажорные версии BullMQ меняли
  форму `backoff`).
