## Задача

Третий и последний экран инвентарной части кабинета аптеки: сводная история ВСЕХ каналов
(REST/Excel/ручной ввод) с раскрываемыми построчными ошибками — точка, где `pharmacy_admin` наконец
видит, что произошло с батчем 1С, который он не отправлял сам (в отличие от Excel/ручного ввода,
которые видны через свой собственный UI-поток немедленно).

## Технический контекст

Backend — `GET /inventory-sync-batches` + `GET .../:id/errors` (DTJ-163), счётчик модерации
(SRS-INV-046). Пометка устаревания (SRS-INV-048) — `pharmacy_inventory.last_synced_at` относится к
ОТДЕЛЬНОМУ экрану (карточка товара в поиске, вне EP-05/apps/pharmacy — принадлежит `catalog`/EP-06),
но краткая индикация «последняя синхронизация: N часов назад» на ЭТОМ экране (не бейдж поиска,
локальная сводка для аптеки) — уместна и специфицирована здесь как UX кабинета.

## Что сделать

1. `use-sync-batches.ts` — TanStack Query `useQuery` с курсорной пагинацией (`CursorList`,
   `hasMore`/«Показать ещё» вместо номеров страниц, doc 30), фильтр по каналу (чипы «Все» / «1С» /
   «Excel» / «Ручной ввод»).
2. `SyncBatchesTable.tsx` — строки: канал (иконка/лейбл), тип (полная/дельта), статус (цветной
   бейдж — `completed_full_success` зелёный, `completed_partial_success` жёлтый,
   `failed_validation`/`queued`/`processing` — соответствующие состояния), принято/отклонено,
   время получения/завершения. Клик по строке с ошибками раскрывает `BatchErrorsAccordion`.
3. `BatchErrorsAccordion.tsx` — раскрываемый список ошибок батча (`GET .../:id/errors`, ленивая
   загрузка при раскрытии, не при рендере всей таблицы), для Excel-батчей — кнопка «Скачать отчёт
   об ошибках» (DTJ-164, доступна только если `sourceUploadId` есть и `hasErrors`).
4. `StaleDataBadge.tsx` — небольшой индикатор в шапке экрана: агрегированное «последняя
   синхронизация: N часов назад» по САМОМУ СВЕЖЕМУ батчу аптеки; если превышен
   `INVENTORY_DELTA_SLA_MINUTES`/`INVENTORY_MANUAL_STALE_HOURS` (значения — из `GET /meta`,
   `tenant_settings`, EP-01/EP-02 инфраструктура) — визуально акцентировать (`--brand-warning`).
5. Счётчик очереди модерации (SRS-INV-046) — небольшая карточка/баннер «N позиций ожидают проверки
   каталогом» (`GET .../pending-moderation-count`, DTJ-163), БЕЗ ссылки на саму очередь (аптека не
   имеет доступа, только счётчик — информационный индикатор).
6. `SyncHistoryPage.tsx` — композиция всего выше, доступна по маршруту `/inventory/sync-history`.

## Критерии приёмки

1. **Given** 25 батчей за месяц, **When** экран открывается, **Then** первые 20 отображаются с
   кнопкой «Показать ещё», клик подгружает следующие 5 без дублей.
2. **Given** батч со `status='completed_partial_success'` и 12 ошибками, **When** строка
   раскрывается, **Then** все 12 ошибок отображаются с человекочитаемым текстом (не сырым
   `error_code`), запрос на ошибки уходит ТОЛЬКО при раскрытии (не при первом рендере таблицы) —
   негативный сценарий в смысле «не создаёт N запросов на N строк таблицы сразу».
3. **Given** Excel-батч с ошибками, `sourceUploadId` заполнен, **When** строка раскрыта, **Then**
   кнопка «Скачать отчёт об ошибках» видна и ведёт на DTJ-164 эндпоинт.
4. **Given** REST-батч (1С) с ошибками, **When** строка раскрыта, **Then** кнопка «Скачать отчёт»
   ОТСУТСТВУЕТ (SRS-INV-045 — исправление на стороне 1С, кабинет не предлагает эту опцию для канала
   без `sourceUploadId`) — второй негативный сценарий, разграничение по каналу.
5. **Given** самая свежая синхронизация — 3 часа назад, `INVENTORY_DELTA_SLA_MINUTES=5`, **When**
   экран открывается, **Then** `StaleDataBadge` показывает акцентное предупреждение об устаревании.

## Тест-план

Unit/component (Vitest + Testing Library):
- `SyncBatchesTable отображает статусные бейджи с корректным цветом по статусу`
- `BatchErrorsAccordion загружает ошибки лениво при раскрытии, не при монтировании таблицы`
- `кнопка отчёта об ошибках видна только для батчей с sourceUploadId`
- `кнопка отчёта об ошибках отсутствует для REST-батчей`
- `StaleDataBadge акцентирует предупреждение при превышении порога`
- `курсорная пагинация подгружает следующую страницу без дублирования уже отображённых батчей`
- `фильтр по каналу корректно сужает список (query-параметр передан в use-sync-batches)`
E2E (Playwright): полный проход «открыть историю → раскрыть батч с ошибками → скачать отчёт»
против dev-API с заранее известными фикстурами батчей. Порог покрытия `frontend` — 70%.

  (`tenant_settings`) — если этот эндпоинт ещё не отдаёт эти конкретные поля к волне 4 (владение

  не блокировать тикет ожиданием готовности чужого API — но зафиксировать TODO явно в PR.
- Синхронизация цветовой кодировки статусов (`completed_full_success` зелёный и т.д.) с общей
  дизайн-системой `packages/ui` — если токены для статусных цветов ещё не определены к волне 4,
  согласовать с владельцем дизайн-системы (`32-design-reference.md`), не изобретать свои имена
  CSS-переменных в обход общего набора.
