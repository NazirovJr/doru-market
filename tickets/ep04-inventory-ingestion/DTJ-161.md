## Задача

Файл до 20 000 строк не помещается в лимит одного батча (1000, REQ-SYNC-4) — этот контроллер
парсит файл СИНХРОННО (быстро, чтение файла — не запись в БД), затем создаёт `N = ceil(rows/1000)`
батчей ТЕМ ЖЕ путём, что REST-канал (одна строка `inventory_sync_batches` + raw items + outbox-
событие на батч), объединённых одним `sourceUploadId`, чтобы аптека видела ОДИН агрегированный
прогресс-бар вместо N разрозненных статусов.

## Технический контекст

Режим «Полная замена ассортимента» (чекбокс UI, DTJ-168) → все N батчей получают ОДИН
`full_sync_session_id` (переиспользует `syncType='full'`, обнуление отсутствующих позиций сработает
после ПОСЛЕДНЕГО батча этой сессии — `is_last_page=true` выставляется на батче с наибольшим
`page_number`, DTJ-151 логика применяется без изменений). Режим «Добавить/обновить» → N НЕЗАВИСИМЫХ
`delta`-батчей БЕЗ `full_sync_session_id`, каждый со своим `sourceUploadId` для группировки (поле
`source_upload_id` переиспользуется как группирующий признак даже для delta-режима — SRS-INV-014,
не только для full). Приоритет очереди для этих job — `excel_import` + `delta` = `5`, ЛЮБОЙ `full`
= `10` (DTJ-153).

## Что сделать

1. `packages/contracts/src/inventory/excel-import.schema.ts`: `InventoryExcelImportRequestSchema` —
   `multipart/form-data` (файл `.xlsx`/`.csv`, лимит `10 MB` общего мультипарт-лимита, SRS-API-066
   — НЕ 5 МБ батч-лимита), поле `mode: z.enum(['append_update', 'full_replace'])` (явный выбор
   пользователя UI, не эвристика).
2. `inventory-excel-import.controller.ts`: `@Post('/api/v1/inventory-excel-import')`,
   `@UseGuards(RolesGuard, TenantScopeGuard)` `@Roles('pharmacy_admin', 'super_admin')` (permission
   `inventory:ingest`, тот же RBAC, что DTJ-159/DTJ-162), `@fastify/multipart` лимит `10MB`.
3. Вызвать `ExcelInventoryParserPort.parse(fileBuffer, mimeType)` (DTJ-160) синхронно — если
   `rejectedRows` покрывает 100% файла (все строки провалили парсинг) — вернуть `400
   VALIDATION_ERROR` без создания ни одного батча (пустой валидный импорт бессмыслен).
4. Разбить `rows` (успешно распарсенные) на чанки по 1000: `sourceUploadId = uuidv4()` (генерируется
   СЕРВЕРОМ здесь, в отличие от `batch_id`, который для REST-канала генерируется клиентом — фронт
   Excel-загрузки не обязан сам генерировать группирующий ID, это внутренняя деталь оркестрации
   импорта). `fullSyncSessionId = mode==='full_replace' ? sourceUploadId : undefined` (переиспользуется
   тот же UUID для простоты — оба поля физически разные колонки, но одно и то же значение допустимо
   использовать, если это не создаёт путаницы; альтернатива — два разных UUID, выбрать один подход и
   задокументировать).
5. Для каждого чанка (`page_number` = 1-based индекс чанка, `is_last_page` = чанк последний) —
   ТА ЖЕ последовательность, что DTJ-157 п.6: своя строка `inventory_sync_batches` (`channel=
   'excel_import'`, свой сгенерированный СЕРВЕРОМ `batch_id` — `uuidv4()` на каждый чанк, т.к.
   клиент/файл не несёт естественного `batch_id`), свои raw items, своё outbox-событие
   `InventoryBatchQueuedEvent`. Вынести общую часть (создание батча + raw items + outbox) в
   переиспользуемый internal helper `PersistInventorySyncBatchService` (третий потребитель после
   REST DTJ-157 — по правилу C15/DRY третье повторение обязывает выделение общей абстракции; при
   реализации DTJ-157 такого сервиса ещё не было, вынести его СЕЙЧАС, точечно отрефакторив DTJ-157
   на использование того же сервиса, не копируя логику).
6. ВСЕ N батчей персистируются в ОДНОЙ транзакции HTTP-запроса (весь импорт атомарен на уровне
   постановки — либо все N батчей поставлены, либо ни один, при сбое посередине), но каждый батч
   ОБРАБАТЫВАЕТСЯ независимо воркером после коммита.
7. Ответ: `202` с `{ data: { sourceUploadId, totalBatches: N, totalRows, rejectedByParser:
   rejectedRows.length } }` — фронт использует `sourceUploadId` для агрегированного опроса прогресса
   (DTJ-163/168).

## Критерии приёмки

1. **Given** валидный файл на 2500 строк, режим `append_update`, **When** `POST
   /inventory-excel-import`, **Then** создаётся 3 батча (`ceil(2500/1000)`) с общим
   `sourceUploadId`, БЕЗ `full_sync_session_id`, каждый `channel='excel_import'`.
2. **Given** тот же файл, режим `full_replace`, **When** `POST`, **Then** 3 батча создаются с ОБЩИМ
   `full_sync_session_id`, третий (последний) батч имеет `is_last_page=true`, первые два —
   `is_last_page=false`.
3. **Given** файл, где 5 из 2500 строк отклонены парсером (SRS-INV-013), остальные валидны, **When**
   `POST`, **Then** 3 батча создаются из 2495 валидных строк, ответ содержит
   `rejectedByParser: 5` — эти 5 строк НЕ попадают ни в один батч и не создают запись
   `inventory_sync_errors` НА ЭТОМ ЭТАПЕ (парсер-ошибки — структурные, до постановки в очередь;
   более полный отчёт с ними — DTJ-164).
4. **Given** файл, где ВСЕ строки отклонены парсером (например, полностью неверный шаблон), **When**
   `POST`, **Then** `400 VALIDATION_ERROR`, ни один батч не создан — негативный сценарий.
5. **Given** запрос без обязательного поля `mode`, **When** `POST`, **Then** `400
   VALIDATION_ERROR`, `details.field='mode'` — второй негативный сценарий (режим — явный выбор, не
   эвристика, SRS-INV-014).

## Тест-план

Unit (`inventory-excel-import.controller.spec.ts`, парсер и репозитории замоканы):
- `2500 строк дают 3 батча с общим sourceUploadId`
- `режим full_replace выставляет одинаковый full_sync_session_id на все батчи, is_last_page=true
  только на последнем`
- `режим append_update НЕ выставляет full_sync_session_id ни на одном батче`
- `частично отклонённый парсером файл создаёт батчи только из валидных строк, rejectedByParser
  корректен в ответе`
- `полностью невалидный файл (0 валидных строк) не создаёт ни одного батча, 400`
- `отсутствие поля mode отклоняется 400 VALIDATION_ERROR`
- `PersistInventorySyncBatchService переиспользуется, не дублирует логику DTJ-157` (структурный
  тест — импорт общего сервиса, не собственная копия кода)
Интеграционный: полный проход `POST` с реальным `.xlsx`-файлом на 2500 строк → 3 строки
`inventory_sync_batches` в БД, 3 outbox-события. Порог покрытия `presentation/` — 70%.

## Риски и подводные камни

- Рефакторинг DTJ-157 «постфактум» для выноса `PersistInventorySyncBatchService» — риск конфликта
  слияния, если DTJ-157 к этому моменту уже находится в отдельной ветке/PR другого разработчика.
  Координировать по времени (этот тикет логически идёт ПОСЛЕ мержа DTJ-157, не параллельно).
- Реализация «одна транзакция на N батчей» при N до 20 (20000/1000) — потенциально долгая
  транзакция БД, блокирующая соединение; если нагрузочный тест (DTJ-170) покажет проблему, обсудить
  ослабление до транзакции НА БАТЧ (N отдельных коротких транзакций вместо одной длинной) — компромисс
  между атомарностью «всё или ничего» и временем удержания соединения; текущее решение — атомарность
  предпочтительнее, менять только по факту измеренной проблемы.
- Выбор одного UUID для `sourceUploadId` и `fullSyncSessionId` в режиме full — если ревью сочтёт это
  запутывающим (две разные по смыслу колонки с одинаковым значением), альтернатива — два независимых
  `uuidv4()` с явным маппингом; решить на review, не менять контракт в одностороннем порядке после
  того, как DTJ-163/168 уже начали полагаться на конкретное поведение.
