## Задача

Фармацевт/`pharmacy_admin` кабинета уже ВЫБРАЛ медикамент через каталожный автокомплит — строка
приходит с уже известным `medicineId`, composite-матчинг избыточен (нет сырого текста для
сопоставления). Это единственный канал, где ВСЕ строки — `resolved: true`. Учитывая малый
практический объём (UI пагинирует сетку по 50-100 строк на экран) и отсутствие потребности в
matching-инфраструктуре, use case вызывается СИНХРОННО прямо из контроллера — без похода через
BullMQ-очередь.

## Технический контекст

**Архитектурное решение этого тикета** (зафиксировать явно, т.к. не описано дословно ни в одном
документе иерархии для этого конкретного канала — см. «Технический контекст» DTJ-148): в отличие от
REST (DTJ-157, асинхронно через очередь) и Excel (DTJ-161, асинхронно через N батчей), ручной ввод
вызывает `IngestInventoryBatchUseCase.execute(command)` НАПРЯМУЮ в теле HTTP-обработчика, ответ
`200`/`201` содержит РЕАЛЬНЫЙ финальный результат (не промежуточный `202 queued`), т.к. resolved-
строки не проходят дорогой fuzzy-матчинг и объём (≤1000, практически ≤100) не создаёт риска для
времени ответа. Строка `inventory_sync_batches` СОЗДАЁТСЯ и переводится сразу в терминальный статус
в рамках того же запроса (для единообразия отчётности — `/admin/inventory/sync-history`, DTJ-163,
должен видеть ручные правки наравне с батчами других каналов).

**RBAC — расхождение документов, разрешено в пользу нормативного**: `22-module-inventory-sync-1c.md`
SRS-INV-015 говорит «фармацевт/`pharmacy_admin`», но `12-api-conventions-auth-tenancy.md` §4
(permission-матрица, документ помечен «ЗАКОН» преамбулой module 22) даёт `inventory:ingest` ТОЛЬКО
`pharmacy_admin` и `super_admin` — `pharmacist` строка матрицы `❌`. По иерархии документов этого
эпика (`03-ARCHITECT-DECISIONS.md`/архитектурные основы выше по приоритету, `12` явно помечена
нормативной для формы permission) применяется `12`: только `pharmacy_admin`/`super_admin`. Если
продуктовая команда решит иначе на старте эпика — это ADR-уровня изменение, не молчаливая правка
кода без обновления `12`.

## Что сделать

1. `packages/contracts/src/inventory/manual-entry.schema.ts`: `ManualEntryRowSchema = z.object({
   medicineId: z.string().uuid(), priceTjs: z.number().positive(), quantity: z.number().int().min(0),
   expiryDate: z.string().regex(/^\d{4}-\d{2}-\d{2}$/), batchNumber: z.string().max(100).optional(),
   op: z.enum(['upsert', 'delete']).default('upsert') })`, `ManualEntryRequestSchema = z.object({
   rows: z.array(ManualEntryRowSchema).min(1).max(1000) })` — общий лимит §2.3 (SRS-INV-015),
   покрывает и точечное редактирование (`rows.length===1`), и массовую сетку.
2. `inventory-manual-entry.controller.ts`: `@Post('/api/v1/inventory-manual-entry')`,
   `@UseGuards(RolesGuard, TenantScopeGuard)` `@Roles('pharmacy_admin', 'super_admin')`.
3. `manual-entry-request-to-command.mapper.ts`: строит `IngestInventoryBatchCommand` с
   `channel='manual_entry'`, `syncType='delta'`, все `rows` — `resolved: true` (DTJ-145),
   `batchNumber` — если не передан явно UI, требуется ЯВНОЕ решение (см. риски DTJ-145 п.3 — эта
   ветка НЕ применяет `AUTO-{internalSku}`, т.к. `internalSku` отсутствует в resolved-строках);
   решение этого тикета — `batchNumber ?? 'MANUAL-{medicineId}-{today ISO date}'` как детерминированный
   дефолт (одна ручная партия в день на медикамент — упрощённый случай FEFO, аналогично
   `AUTO-{internalSku}`, но для канала без SKU).
4. Сгенерировать `batch_id` СЕРВЕРОМ (`uuidv4()`), создать строку `inventory_sync_batches`
   (`channel='manual_entry'`), НЕ ставить в очередь — сразу вызвать
   `IngestInventoryBatchUseCase.execute(command)` синхронно в рамках той же транзакции/юнита работы.
5. Ответ: `200` с `{ data: { batchId, status, acceptedRows, rejectedRows, errors: [...] } }` —
   полный финальный результат, не промежуточный `202`.
6. Пункт «Товара нет в списке» (SRS-INV-016) — этот контроллер НЕ вызывается вовсе для этого
   сценария (отдельный эндпоинт создания черновика `catalog_match_queue`, принадлежит
   `catalog`/`moderation`, вне EP-05) — зафиксировать в JSDoc контроллера явной пометкой «не
   обрабатывает создание нового товара», чтобы фронт (DTJ-167) не пытался переиспользовать этот
   эндпоинт для этого случая.

## Критерии приёмки

1. **Given** `pharmacy_admin`, точечное редактирование одной позиции (`rows.length===1`, валидный
   `medicineId`), **When** `POST /inventory-manual-entry`, **Then** `200` с
   `acceptedRows=1, rejectedRows=0`, `pharmacy_inventory` обновлён СРАЗУ (проверяется чтением после
   ответа, без ожидания асинхронной очереди) — точное соответствие TC-INV-007 (composite-матчинг НЕ
   вызывается).
2. **Given** массовая сетка из 80 строк, 3 из которых с `priceTjs<=0` (ошибка пользователя при
   ручном вводе), **When** `POST`, **Then** `200` с `acceptedRows=77, rejectedRows=3`, `errors`
   содержит 3 объекта с `error_code='invalid_price'` — частичный успех работает и для этого канала.
3. **Given** запрос от роли `pharmacist`, **When** `POST /inventory-manual-entry`, **Then** `403
   INSUFFICIENT_ROLE` — негативный сценарий, закрывающий расхождение документов в пользу `12`
   (см. «Технический контекст»).
4. **Given** `rows.length = 0` (пустой массив), **When** `POST`, **Then** `400 VALIDATION_ERROR` —
   второй негативный сценарий (Zod `.min(1)`).

## Тест-план

Unit (`inventory-manual-entry.controller.spec.ts`, `IngestInventoryBatchUseCase` замокан):
- `точечное редактирование вызывает execute() с одной resolved-строкой, matcher не вызывается`
  (TC-INV-007)
- `массовая сетка с частичными ошибками возвращает корректные acceptedRows/rejectedRows`
- `роль pharmacist получает 403` (закрывает расхождение документов)
- `роль pharmacy_admin/super_admin проходит guard`
- `пустой массив rows отклоняется 400`
- `batchNumber по умолчанию формируется как MANUAL-{medicineId}-{today}` при отсутствии явного
  значения
- `ответ содержит финальный статус (не queued) — синхронный путь подтверждён тестом на форму ответа`
Интеграционный: полный проход `POST` → чтение `pharmacy_inventory` СРАЗУ после ответа (без polling)
подтверждает синхронность. Порог покрытия `presentation/` — 70%.

## Риски и подводные камни

- **RBAC-расхождение документов (пункт «Технический контекст») — самый заметный риск этого тикета.**
  Если продуктовая команда/Tech Lead на старте эпика решит, что `pharmacist` ДОЛЖЕН иметь доступ
  (буквальное прочтение SRS-INV-015), решение меняется в ОДНОМ месте (`@Roles(...)` декоратор) —
  зафиксировать это явно в PR как открытый вопрос для подтверждения перед мержем, не решать
  тихой правкой позже.
- Синхронный путь (без очереди) — если реальная нагрузка окажется выше ожидаемой (сеть с 500
  точками, каждая делает частые ручные правки), может потребоваться пересмотр в сторону асинхронной
  обработки по аналогии с Excel — не блокирует R1, зафиксировать как решение, подлежащее ревизии по
  метрикам после запуска.
- `batchNumber = 'MANUAL-{medicineId}-{today}'` — если фармацевт вводит ОДИН И ТОТ ЖЕ медикамент
  дважды за один день с разными партиями физически (два разных срока годности реального товара),
  этот дефолт СХЛОПНЕТ их в одну партию (`ON CONFLICT` перезапишет). Для R1 это принимается как
  известное упрощение ручного канала (партийный учёт полноценно доступен только через реальные
  каналы 1С/Excel с явным `batch_number`) — если это неприемлемо, эскалировать перед реализацией:
  альтернатива — обязательное поле `batchNumber` в UI ручного ввода, а не автогенерация.
