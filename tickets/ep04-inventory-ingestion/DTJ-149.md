## Задача

Когда оператор каталога (`apps/admin`, `moderation`-модуль) резолвит запись `catalog_match_queue`
как `matched`/`created_new`, отложенный остаток/цена ДОЛЖНЫ применяться к `pharmacy_inventory` — но
сама логика применения (staleness-guard, FEFO, инварианты `PharmacyInventory`) принадлежит
`inventory`. Этот use case — единственная точка, которую `moderation`-модуль вызывает СИНХРОННО
сразу после установки `resolved_medicine_id`, не дублируя логику применения остатка у себя.

## Технический контекст

`catalog_match_queue` физически не принадлежит `inventory` (см. DTJ-141/DTJ-142), но этот use case
ЧИТАЕТ из неё расширенные поля `raw_stock_quantity`/`raw_expiry_date`/`raw_batch_number`/
`source_sync_timestamp` (добавлены DTJ-142 п.3) через собственный узкий репозиторий-порт — это
осознанное исключение из «модуль не трогает чужие таблицы», обоснованное тем же образом, что и
чтение `medicines`/`pharmacies` через FK в других портах: доступ на ЧТЕНИЕ конкретных полей одной
таблицы через явный порт — не то же самое, что импорт чужого домена (`02` §1.2 запрещает
межмодульные импорты `domain/application` кода, не запрещает infrastructure-адаптеру читать таблицу,
владение которой у другого bounded context, если это явно оформлено портом с узким контрактом).
Вызывающая сторона (`moderation`) взаимодействует с этим use case ЧЕРЕЗ `InventoryFacade`
(DTJ-140), не импортирует `application/use-cases/*` напрямую.

## Что сделать

1. `catalog-match-queue.repository.port.ts`: узкий порт
   `CatalogMatchQueueReadPort.findResolvedItemById(queueItemId: string): Promise<{
   pharmacyId: string; resolvedMedicineId: string; resolution: 'matched' | 'created_new';
   rawStockQuantity: number | null; rawExpiryDate: string | null; rawBatchNumber: string | null;
   sourceSyncTimestamp: Date } | null>` — ТОЛЬКО чтение, никаких write-методов на чужую таблицу.
2. `resolve-catalog-match-queue-item.use-case.ts`: класс `ResolveCatalogMatchQueueItemUseCase`,
   метод `execute(cmd: { queueItemId: string }): Promise<{ applied: boolean; reason?: 'stale' |
   'rejected_resolution' }>`.
3. Given `resolution === 'rejected'` — этот use case не вызывается вовсе (per SRS-INV-028, таблица
   резолюций: `rejected` не порождает применение остатка) — если всё же вызван с этим значением,
   вернуть `{ applied: false, reason: 'rejected_resolution' }` без побочных эффектов (defensive
   guard, не должен происходить штатно, но не должен падать необработанным исключением).
4. Для `matched`/`created_new`: если `rawStockQuantity === null` (запись создана до DTJ-142,
   старые данные без расширенных полей) — `{ applied: false, reason: 'stale' }` с логированием
   предупреждения (не бросать исключение — так же штатно, как обычный staleness-guard).
5. Иначе — загрузить/создать `PharmacyInventory` через `PharmacyInventoryRepositoryPort` (DTJ-148)
   по `(pharmacyId, resolvedMedicineId)`, вызвать `.applyDelta({ batchNumber: rawBatchNumber ??
   'AUTO-QUEUE-{queueItemId}', priceDiram: <из raw_price_tjs, конвертация через
   Money.fromNumberTjs>, quantity: rawStockQuantity, expiryDate: rawExpiryDate, syncTimestamp:
   sourceSyncTimestamp })` — ТОТ ЖЕ путь, что обычная строка батча (SRS-INV-028 буквально: «тем же
   путём»), staleness-guard работает автоматически через саму сущность (DTJ-143).
6. Сохранить агрегат, вернуть `{ applied: result.applied, reason: result.reason }`.
7. `control_category` НЕ трогается этим use case (D-08, SRS-INV-029 — дефолт `'none'` уже
   устанавливается на стороне `catalog` при создании черновика, это НЕ ответственность inventory).

## Критерии приёмки

1. **Given** запись `catalog_match_queue` резолвлена как `matched`, `raw_stock_quantity=50,
   raw_expiry_date='2027-01-01'`, **When** `execute({ queueItemId })`, **Then**
   `pharmacy_inventory`/`inventory_batches` обновлены количеством 50 через `applyDelta`, `applied:
   true` — точное соответствие TC-INV-014.
2. **Given** та же запись, но `PharmacyInventory` для `(pharmacyId, medicineId)` уже имеет более
   свежую партию с тем же `batchNumber` (`lastSyncedAt > sourceSyncTimestamp` резолюции — резолюция
   недельной давности), **When** `execute()` вызывается, **Then** `{ applied: false, reason:
   'stale' }`, данные НЕ перезаписаны — негативный сценарий, staleness-guard защищает отложенное
   применение (SRS-INV-028 обоснование в DTJ-142).
3. **Given** `resolution: 'rejected'` (не должно вызываться штатно, но защитный сценарий), **When**
   `execute()` вызывается, **Then** `{ applied: false, reason: 'rejected_resolution' }` без записи в
   `pharmacy_inventory` — второй негативный сценарий.
4. **Given** `rawStockQuantity === null` (запись создана до появления расширенных полей), **When**
   `execute()` вызывается, **Then** `{ applied: false, reason: 'stale' }`, use case не бросает
   необработанное исключение (`TypeError` на `null`).

## Тест-план

Unit (`resolve-catalog-match-queue-item.use-case.spec.ts`, порты замоканы):
- `matched-резолюция с валидными raw-полями применяет остаток через applyDelta`
- `created_new-резолюция применяет остаток тем же путём, что matched`
- `более свежая партия защищена staleness-guard (applied=false, reason=stale)`
- `resolution=rejected возвращает applied=false без побочных эффектов`
- `rawStockQuantity=null возвращает applied=false, reason=stale, без исключения`
- `queueItemId, не найденный в catalog_match_queue, возвращает null-результат без падения` (граница
  контракта порта — use case обрабатывает `null` из `findResolvedItemById`)
Интеграционный: применение к реальному `PharmacyInventory` через Postgres, проверка каскада
триггера `trg_recompute_fefo` (косвенно, через `pharmacy_inventory.stock_quantity` после коммита).
Порог покрытия `application/` — 90%.

## Риски и подводные камни

- Реальный вызывающий код (`moderation`-модуль) не входит в диапазон EP-05 — контракт метода
  `InventoryFacade.applyRetroactiveMatch` фиксируется этим тикетом одним из первых, чтобы не
  заблокировать `moderation`-эпик на интеграции; при расхождении в сигнатуре с ожиданиями
  `moderation` — менять по согласованию, не в одностороннем порядке.
- Если `moderation`-эпик ещё не создал `catalog_match_queue` (координация с DTJ-142) — этот тикет
  логически блокируется тем же внешним риском, что и DTJ-142 п.3.
