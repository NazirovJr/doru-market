## Задача

Это входная точка, ради которой существует весь REST-канал: 1С/сторонний ERP отправляет до 1000
позиций остатков одним HTTP-запросом и получает немедленный `202 Accepted`, не дожидаясь тяжёлой
обработки. Контроллер обязан быть МАКСИМАЛЬНО тонким — вся бизнес-логика уже в
`IngestInventoryBatchUseCase` (DTJ-148), здесь только: валидация формы, идемпотентность на уровне
`batch_id`, персистенция batch+raw-строк+outbox-события в одной транзакции, возврат `202`.

## Технический контекст

Zod-схема — дословно `22-module-inventory-sync-1c.md` строки 124-147 (SRS-INV-002). Лимиты —
`items.length<=1000` И тело `<=5MB`, проверяется ПОТОКОВО по `Content-Length` ДО парсинга JSON
целиком (SRS-INV-003, Fastify `bodyLimit` — конфигурация на уровне роута, не в Zod). Идемпотентность
— `inventory_sync_batches.id = batch_id` UNIQUE, `ON CONFLICT (id) DO NOTHING RETURNING *`, при
пустом `RETURNING` — `SELECT` существующей строки, тело НЕ сверяется побайтово (SRS-INV-009,
отличие от общего `Idempotency-Key`-механизма SRS-API-010). `PharmacyApiKeyGuard` (DTJ-156) уже
отработал ДО этого контроллера и положил `request.principal.{pharmacyId, chainId}`.

## Что сделать

1. `packages/contracts/src/inventory/batch-update.schema.ts`: `InventoryBatchItemSchema` +
   `InventoryBatchUpdateRequestSchema` — дословно Zod-схема SRS-INV-002, включая refine
   `sync_type==='delta' → full_sync_session_id===undefined` (SRS-INV-005, иначе `400
   VALIDATION_ERROR`, `details.field='full_sync_session_id'`).
2. `inventory-batch-update.controller.ts`: `@Post('/api/v1/inventory/batch-update')`,
   `@UseGuards(PharmacyApiKeyGuard)`, `@RateLimit({ max: 20, windowSec: 60, keyBy: 'pharmacyId' })`
   (`RATE_LIMIT_1C_BATCH_PER_MIN`, EP-01 декоратор), Fastify route-level `bodyLimit: 5 * 1024 *
   1024`.
3. Проверка `PHARMACY_NOT_IN_CHAIN_SCOPE` (DTJ-156 п.5): если `request.principal.chainId !== null`
   — после Zod-парсинга проверить `pharmacies WHERE id=:pharmacy_guid AND chain_id=:chainId`, при
   несовпадении → `403 PHARMACY_NOT_IN_CHAIN_SCOPE`, батч НЕ создаётся.
4. Идемпотентность: `InventorySyncBatchRepositoryPort.createIfNotExists(batchId, ...): Promise<{
   batch: InventorySyncBatch; created: boolean }>` — реализует `ON CONFLICT (id) DO NOTHING
   RETURNING *` + fallback `SELECT`.
5. Given `created === false` (дубль) — вернуть `202` с УЖЕ известным статусом батча немедленно, БЕЗ
   повторной вставки raw-строк и БЕЗ повторной публикации outbox-события (SRS-INV-009/SRS-INV-055).
6. Given `created === true` — в ОДНОЙ транзакции: (а) вставить `inventory_sync_batches` строку
   (`status='queued'`, `channel='rest_api'`), (б) `rest-inventory-request-to-command.mapper.ts`:
   `RestInventoryRequestToCommandMapper.toCommand(dto, principal)` — строит `IngestInventoryBatchCommand`
   с `channel='rest_api'`, все `rows` — `resolved: false`, `Money.fromNumberTjs(item.price_tjs)`
   (НЕ `fromDbDecimalTjs` — конвертация напрямую из числа JSON, SRS-INV-011), (в) `COPY`/batched
   `INSERT` строк в `inventory_sync_raw_items` (по одной на элемент `items`, `row_index` = индекс в
   массиве), (г) публикация `InventoryBatchQueuedEvent` через `OutboxPort` (EP-01).
7. Ответ `202`: `{ data: { batchId, status: 'queued', acceptedForProcessing: true } }` (SRS-INV-007).
8. `GET /api/v1/inventory-import-template`? — НЕ в этом тикете (DTJ-159).

## Критерии приёмки

1. **Given** валидный батч из 500 строк, новый `batch_id`, **When** `POST
   /inventory/batch-update`, **Then** `202` с `{ batchId, status: 'queued', acceptedForProcessing:
   true }`, строка `inventory_sync_batches` создана, 500 строк в `inventory_sync_raw_items`, событие
   `InventoryBatchQueuedEvent` в `outbox`.
2. **Given** `batch_id=X`, уже существующий с `status='completed_partial_success'` (сетевой ретрай
   1С), **When** `POST` повторяется с тем же `batch_id` и СЛЕГКА другим порядком полей JSON, **Then**
   `202` с сохранённым `status='completed_partial_success'` возвращается СРАЗУ, вторая строка
   `inventory_sync_batches` не создаётся — точное соответствие TC-INV-001.
3. **Given** тело запроса 6 МБ, **When** `POST /inventory/batch-update`, **Then** `413
   PAYLOAD_TOO_LARGE` ДО полного разбора JSON (проверяется тем, что БД не получает ни одной записи
   и обработчик не успевает вызвать Zod) — негативный сценарий, точное соответствие TC-API-043/
   TC-INV-002.
4. **Given** `items.length = 1001`, **When** `POST`, **Then** `400 VALIDATION_ERROR`,
   `details.field='items'` — второй негативный сценарий, точное соответствие TC-INV-003.
5. **Given** `sync_type='delta'`, `full_sync_session_id` передан, **When** `POST`, **Then** `400
   VALIDATION_ERROR`, `details.field='full_sync_session_id'` — третий негативный сценарий, точное
   соответствие TC-INV-004.
6. **Given** ключ выдан на `chain_id=C1`, тело содержит `pharmacy_guid`, принадлежащий сети `C2`,
   **When** `POST`, **Then** `403 PHARMACY_NOT_IN_CHAIN_SCOPE`, батч не создаётся — точное
   соответствие TC-INV-027.

## Тест-план

Unit (`inventory-batch-update.controller.spec.ts`, порты замоканы):
- `новый batch_id создаёт батч, raw items и outbox-событие в одной транзакции`
- `повторный batch_id возвращает сохранённый статус без повторной записи` (TC-INV-001)
- `RestInventoryRequestToCommandMapper строит команду с channel=rest_api, все rows resolved=false`
- `Money.fromNumberTjs применяется для priceDiram, не fromDbDecimalTjs`
- `chain-scoped ключ с чужим pharmacy_guid отклоняется PHARMACY_NOT_IN_CHAIN_SCOPE` (TC-INV-027)
- `pharmacy-scoped ключ (chainId=null) пропускает проверку сети без ошибки`
Contract-тест (`packages/contracts` уровень): Zod-схема отклоняет `items.length=1001` (TC-INV-003),
отклоняет `sync_type=delta` + заполненный `full_sync_session_id` (TC-INV-004).
Интеграционный (реальный Fastify + БД + Redis): полный проход `202` для валидного запроса; `413` на
6 МБ теле (TC-INV-002); полный цикл guard→контроллер→БД для дубля `batch_id` (TC-INV-001).
Порог покрытия `presentation/` — 70%.

## Риски и подводные камни

- Транзакционная запись `inventory_sync_batches`+`inventory_sync_raw_items`+`outbox` внутри одного
  HTTP-запроса с батчем 1000 строк — потенциально заметная задержка ACK при пиковой нагрузке; целевой
  p95 `<300мс` (SRS-INV-054) — если `COPY` для raw items не используется здесь (в отличие от
  DTJ-154, где `COPY` применяется к применению строк, не к сырому payload), обычный batched `INSERT`
  на 1000 строк может не уложиться — при первых признаках превышения бюджета времени в
  интеграционном/нагрузочном тесте (DTJ-170) вернуться и заменить на `COPY` аналогично DTJ-154.
- `RestInventoryRequestToCommandMapper` — общая логика построения `IngestInventoryBatchCommand` во
  многом ПОВТОРЯЕТСЯ маппером Excel-канала (DTJ-161) и CommerceML (DTJ-165, R2) — на третьем
  повторе (C15) вынести общий хелпер `buildUnresolvedRowsFromRaw(items)`, не раньше (DTJ-161,
  вероятно, второй повтор — вынос делать по факту при реализации DTJ-161, не заранее).
