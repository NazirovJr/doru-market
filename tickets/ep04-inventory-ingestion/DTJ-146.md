## Задача

D-06 требует composite-матчинг вместо ненадёжного `WHERE barcode = ?`. Первые два шага (валидация
EAN-13 + кэш «однажды сматченного» + точное совпадение по глобальному штрихкоду) закрывают
подавляющее большинство повторных синхронизаций дёшево, БЕЗ обращения к дорогому trigram-fuzzy
(DTJ-147) — архитектурно это ранний выход, критичный для производительности (SRS-INV-052:
резолв `pharmacy_sku_mapping` для ВСЕХ `internal_sku` батча одним запросом, не по циклу).

## Технический контекст

Barcode VO — уже существует в shared kernel (`10-domain-model.md` §«Value Objects»/Barcode,
владение EP-01/EP-04, живёт в общем пакете, ДОСТУПНОМ обоим модулям `catalog` и `inventory` — НЕ
прямой импорт `catalog/domain/*`, см. `SRS-INV-019`). Этот тикет ТОЛЬКО использует
`Barcode.parse(raw)`, не создаёт его заново — если к моменту реализации общий пакет ещё не готов,
см. «Риски».

Порядок шага 2 (SRS-INV-021, первое совпадение побеждает):
1. `pharmacy_sku_mapping WHERE pharmacy_id = :pharmacyId AND internal_sku = :internalSku` — кэш.
2. Если кэш пуст И штрихкод классифицирован как глобальный (`Barcode.isValidEan13()===true &&
   Barcode.isInternalPrefix()===false`) — `medicines WHERE barcode = :rawBarcode` точное совпадение
   (доступ через `CatalogFacade`, не прямой SQL к чужой таблице — `10-domain-model.md` матрица
   взаимодействий `inventory → catalog [F]`).
3. Иначе — делегирование в DTJ-147 (fuzzy).

`pharmacy_sku_mapping` — таблица, физически созданная DTJ-141; репозиторий-порт для НЕЁ создаётся
здесь (это единственная таблица из группы D, чей репозиторий-порт целиком относится к матчингу, а не
к агрегатам `PharmacyInventory`/`InventorySyncBatch`).

## Что сделать

1. `pharmacy-sku-mapping.repository.port.ts`: интерфейс
   `PharmacySkuMappingRepositoryPort.findManyByPharmacyAndSkus(pharmacyId: string, skus: readonly
   string[]): Promise<ReadonlyMap<string, { medicineId: string; matchedVia: string }>>` — ОДИН
   запрос на весь набор SKU батча (SRS-INV-052 п.1, `WHERE pharmacy_id = :id AND internal_sku =
   ANY(:skus)`), НЕ метод «по одному SKU».
2. `.upsert(pharmacyId, internalSku, medicineId, matchedVia): Promise<void>` — `INSERT ... ON
   CONFLICT (pharmacy_id, internal_sku) DO UPDATE SET medicine_id=..., matched_via=...,
   matched_at=now()` (SRS-INV-023).
3. `drizzle-pharmacy-sku-mapping.repository.ts` — реализация обоих методов через Drizzle,
   используя схему из DTJ-141.
4. `composite-inventory-matcher.service.ts`: класс `CompositeInventoryMatcherService` с методом
   `matchBatch(pharmacyId: string, rows: readonly UnresolvedRowInput[]): Promise<readonly
   MatchResult[]>`, где `MatchResult = { row: UnresolvedRowInput } & ({ outcome: 'cached' |
   'exact_barcode'; medicineId: string } | { outcome: 'needs_fuzzy' })` — этот тикет реализует
   ветки `cached`/`exact_barcode`/`needs_fuzzy` (fuzzy-логика — заглушка-делегат, реализуется
   DTJ-147 через тот же интерфейс, точечно дополняющий этот файл).
5. Шаг 1: для каждой строки батча — `Barcode.parse(row.rawBarcode ?? null)`, классификация по
   таблице SRS-INV-020 (`format`, `isInternalPrefix()`) — результат `barcodeCandidate: string |
   null` идёт в шаг 2.
6. Шаг 2.1: батчевый вызов `findManyByPharmacyAndSkus` для ВСЕХ `internalSku` сразу — строки,
   найденные в карте, помечаются `outcome: 'cached'`.
7. Шаг 2.2: для оставшихся строк с `barcodeCandidate !== null` — батчевый вызов
   `CatalogFacade.findMedicineIdsByBarcodes(barcodes: string[]): Promise<ReadonlyMap<string,
   string>>` (порт `CatalogFacade` — публичный фасад модуля `catalog`, EP-04, уже существует к
   волне 4) — найденные помечаются `outcome: 'exact_barcode'`, для НИХ сразу вызывается `upsert()`
   кэша (SRS-INV-023 — успешный матч ЛЮБЫМ путём обновляет кэш).
8. Оставшиеся строки — `outcome: 'needs_fuzzy'`, передаются в DTJ-147.

## Критерии приёмки

1. **Given** `pharmacy_sku_mapping` уже содержит `(pharmacyId, 'SKU-042') → medicineId=M1`, **When**
   `matchBatch` вызывается с батчем, содержащим строку `internalSku='SKU-042'` и ИЗМЕНИВШИМСЯ
   `tradeName`, **Then** результат — `{ outcome: 'cached', medicineId: 'M1' }`, `CatalogFacade` для
   этой строки не вызывается вовсе — точное соответствие TC-INV-009.
2. **Given** штрихкод `'2001234567890'` (валидный EAN-13, префикс `'2'`), **When** классифицируется
   шагом 1, **Then** `isInternalPrefix()===true` → штрихкод НЕ участвует в шаге 2.2 даже если
   совпадает с чужим `medicines.barcode` — негативный сценарий, точное соответствие TC-INV-008.
3. **Given** батч из 50 строк без совпадения в кэше, **When** `matchBatch` выполняется, **Then**
   `findManyByPharmacyAndSkus` вызывается РОВНО ОДИН РАЗ (не 50 раз) — проверяется через mock/spy
   счётчик вызовов, точное соответствие SRS-INV-052 п.1.
4. **Given** строка сматчена точным штрихкодом, **When** обработка строки завершена, **Then**
   `pharmacy_sku_mapping.upsert` вызван с `matchedVia='barcode'` — кэш обновлён для следующей
   синхронизации.

## Тест-план

Unit (`composite-inventory-matcher.service.spec.ts`, порты замоканы — БЕЗ реальной БД,
соответствует порогу `application/` 90%):
- `строка с найденным SKU в кэше возвращает outcome=cached, CatalogFacade не вызывается`
- `штрихкод с префиксом 2 не участвует в точном совпадении`
- `невалидный EAN-13 (неверная контрольная цифра) не участвует в точном совпадении, но сохраняется в
  результате для аудита`
- `штрихкод без префикса 2, валидный EAN-13, найден в medicines — outcome=exact_barcode`
- `успешный точный матч обновляет pharmacy_sku_mapping через upsert()`
- `findManyByPharmacyAndSkus вызывается ровно один раз на весь батч независимо от числа строк`
- `строка без barcode вовсе (rawBarcode отсутствует) сразу передаётся на fuzzy (outcome=needs_fuzzy)`
- `строка без совпадения ни в кэше, ни по штрихкоду помечается needs_fuzzy`
Интеграционный (`drizzle-pharmacy-sku-mapping.repository.integration.spec.ts`, реальный Postgres):
- `findManyByPharmacyAndSkus корректно возвращает Map по набору из N SKU одним запросом`
- `upsert идемпотентен при повторном вызове с тем же (pharmacyId, internalSku)`
E2E не требуется на этом тикете.
