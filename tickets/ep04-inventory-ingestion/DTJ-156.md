## Задача

REST push-канал (1С и сторонние ERP) — единственный канал, где принципал не человек с JWT, а
система, аутентифицирующаяся ключом+HMAC-подписью тела. Без этого guard'а `POST
/inventory/batch-update` (DTJ-157) не может существовать безопасно — это первый барьер перед
контроллером, реализующий ПОЛНЫЙ 10-шаговый алгоритм D-11, дословно нормативно зафиксированный в
`12-api-conventions-auth-tenancy.md` §3.6.

## Технический контекст

Алгоритм — `12-api-conventions-auth-tenancy.md` строки 428-464 (SRS-API-033), 10 шагов, ни один не
пропускается. `pharmacy_api_keys` — физическая таблица `onboarding`-эпика (расширена DTJ-142 п.4
полем `chain_id`). Redis nonce-ключ (`SET pharmacy_nonce:{pharmacyId}:{nonce} 1 NX EX 300`) —
переиспользование общего Redis-клиента EP-01. `X-SSL-Client-Verify: SUCCESS` — заголовок,
устанавливаемый ТОЛЬКО Nginx на границе инфраструктуры (EP-19/DevOps), guard доверяет ему как
данности, не проверяет TLS сам.

## Что сделать

1. `pharmacy-api-key-verification.port.ts`: `PharmacyApiKeyVerificationPort.verify(input: { keyId:
   string; secret: string; timestamp: string; nonce: string; signature: string; method: string;
   path: string; rawBody: Buffer; mtlsVerifiedHeader?: string }): Promise<{ pharmacyId: string;
   chainId: string | null }>` — бросает типизированные ошибки при каждом шаге неудачи (см. п.3).
2. `drizzle-pharmacy-api-key-verification.adapter.ts`: реализация всех 10 шагов SRS-API-033:
   1. Парсинг `keyId.secret` по первому `.` → `PharmacyApiKeyInvalidError` при отсутствии точки.
   2. `SELECT * FROM pharmacy_api_keys WHERE key_prefix=:keyId AND revoked_at IS NULL` → не найдено
      → `PharmacyApiKeyInvalidError` (единая ошибка, не раскрывающая существование `keyId`).
   3. `argon2.verify(key_hash, secret)` → несовпадение → та же `PharmacyApiKeyInvalidError`.
   4. `require_mtls=true` И заголовок `X-SSL-Client-Verify !== 'SUCCESS'` →
      `MtlsRequiredError`.
   5. `|now() - timestamp| > PHARMACY_SIGNATURE_WINDOW_SECONDS` (ENV, 300) →
      `PharmacyTimestampOutOfWindowError`.
   6. Redis `SET pharmacy_nonce:{pharmacyId}:{nonce} 1 NX EX 300` — отказ →
      `PharmacyRequestReplayedError`.
   7. `canonical = "{METHOD}\n{path}\n{timestamp}\n{nonce}\n{hex(sha256(rawBody))}"`.
   8. `expected = hex(HMAC_SHA256(key=secret, data=canonical))`.
   9. `crypto.timingSafeEqual(expected, signature)` — несовпадение →
      `PharmacySignatureInvalidError`.
   10. Успех → вернуть `{ pharmacyId, chainId }`.
3. Ошибки — тонкие классы в `presentation`-слое (не domain — это транспортная аутентификация, не
   бизнес-инвариант), маппятся в HTTP через `TransportExceptionFilter` (EP-01, уже существующий
   маппинг): `PHARMACY_API_KEY_INVALID` → 401, `MTLS_REQUIRED` → 401, `PHARMACY_TIMESTAMP_OUT_OF_
   WINDOW` → 401, `PHARMACY_REQUEST_REPLAYED` → 401, `PHARMACY_SIGNATURE_INVALID` → 401.
4. `pharmacy-api-key.guard.ts`: `PharmacyApiKeyGuard implements CanActivate` — извлекает 4
   заголовка (`X-Pharmacy-API-Key`, `X-Pharmacy-Timestamp`, `X-Pharmacy-Nonce`,
   `X-Pharmacy-Signature`) + `X-SSL-Client-Verify` из запроса, читает `rawBody` (ВАЖНО: тело должно
   быть доступно КАК СЫРЫЕ БАЙТЫ до Zod-парсинга — Fastify обязан быть сконфигурирован сохранять
   `rawBody`, координировать с EP-01, если общий `bodyParser` уже перезаписывает буфер), вызывает
   порт, при успехе прокидывает `{ type: 'pharmacy_system', pharmacyId, chainId }` в
   `request.principal` (та же форма «текущий актор», что и JWT-принципал, для унификации логирования
   — SRS-API-033 шаг 10).
5. Дополнительная проверка scope сети (DTJ-142 п.4, `PHARMACY_NOT_IN_CHAIN_SCOPE`): если
   `chainId !== null` (ключ выдан на сеть) — guard САМ не проверяет `pharmacy_guid` тела (тело ещё
   не распарсено на этом этапе Zod-схемой) — эта проверка переносится в контроллер (DTJ-157, ПОСЛЕ
   Zod-валидации тела), guard только прокидывает `chainId` дальше для использования там. Явно
   задокументировать это разделение ответственности в JSDoc guard'а, чтобы не потерялось.

## Критерии приёмки

1. **Given** корректные `keyId`/`secret`, валидная подпись, `timestamp` в пределах окна, **When**
   запрос проходит guard, **Then** `request.principal = { type: 'pharmacy_system', pharmacyId,
   chainId }` установлен, запрос доходит до контроллера.
2. **Given** корректный `keyId`/`secret`, но `X-Pharmacy-Timestamp` на 10 минут в прошлом, **When**
   guard выполняется, **Then** `401 PHARMACY_TIMESTAMP_OUT_OF_WINDOW` — точное соответствие
   TC-API-025.
3. **Given** тот же `X-Pharmacy-Nonce`, отправленный дважды в течение 5 минут, **When** второй
   запрос проходит guard, **Then** `401 PHARMACY_REQUEST_REPLAYED` — негативный сценарий, точное
   соответствие TC-API-026.
4. **Given** тело подписано корректно, но изменено ПОСЛЕ подписи (симуляция MITM в тесте — байты
   тела отличаются от тех, что участвовали в вычислении подписи клиента), **When** guard
   выполняется, **Then** `401 PHARMACY_SIGNATURE_INVALID` — второй негативный сценарий, точное
   соответствие TC-API-027.
5. **Given** `pharmacy_api_keys.require_mtls=true`, запрос без `X-SSL-Client-Verify: SUCCESS`,
   **When** guard выполняется, **Then** `401 MTLS_REQUIRED` — точное соответствие TC-API-028.

## Тест-план

Unit (`pharmacy-api-key.guard.spec.ts` + `drizzle-pharmacy-api-key-verification.adapter.spec.ts`,
Redis/БД замоканы для guard-уровня, реальные для адаптера в интеграционном слое):
- `валидный запрос устанавливает request.principal и пропускает дальше`
- `отсутствие точки в X-Pharmacy-API-Key -> PHARMACY_API_KEY_INVALID`
- `keyId не найден в pharmacy_api_keys -> PHARMACY_API_KEY_INVALID` (не раскрывает существование)
- `неверный secret (argon2 mismatch) -> PHARMACY_API_KEY_INVALID`
- `require_mtls=true без заголовка Nginx -> MTLS_REQUIRED`
- `timestamp вне окна 300с -> PHARMACY_TIMESTAMP_OUT_OF_WINDOW` (TC-API-025)
- `повторный nonce -> PHARMACY_REQUEST_REPLAYED` (TC-API-026)
- `неверная HMAC-подпись -> PHARMACY_SIGNATURE_INVALID` (TC-API-027)
- `изменённое тело при корректной старой подписи -> PHARMACY_SIGNATURE_INVALID` (MITM-имитация)
- `revoked_at в прошлом -> PHARMACY_API_KEY_INVALID` (батч не создаётся вовсе, TC-INV-024/SRS-INV-058)
Интеграционный: полный проход guard'а с реальным Redis (nonce) и реальной БД (ключ), генерация
корректной подписи тестовым HMAC-хелпером (переиспользуемым и в тестах DTJ-157).
Порог покрытия `presentation/` — 70% (не `application`, но guard критичен по безопасности — держать
выше минимума практически).

## Риски и подводные камни

- **Доступ к сырым байтам тела** — самая частая практическая ловушка HMAC-аутентификации в Fastify:
  если `@fastify/formbody`/встроенный JSON-парсер уже потребил поток до guard'а, `rawBody`
  недоступен. Требует конфигурации Fastify `addContentTypeParser` с сохранением сырого буфера ДО
  стандартного JSON-парсинга — координировать с EP-01 (общая конфигурация Fastify), не решать
  изолированно только для этого модуля, если другие модули (`payments`-вебхук банка) уже решали ту
  же проблему — переиспользовать их подход.
- Проверка `PHARMACY_NOT_IN_CHAIN_SCOPE` разнесена между guard (прокидывает `chainId`) и
  контроллером (сверяет с `pharmacy_guid` тела) — если это разделение окажется неудобным на
  практике, альтернатива — guard читает `pharmacy_guid` из ещё не провалидированного JSON тела
  напрямую (небезопасно, тело может быть невалидным JSON) — выбранное разделение предпочтительнее,
  зафиксировать как решение, не как временный компромисс.
