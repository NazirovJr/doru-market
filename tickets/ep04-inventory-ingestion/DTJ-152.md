## Задача

Если 1С заявила многостраничный full-снапшот, но последняя страница (`is_last_page=true`) так и не
пришла (сбой сети со стороны 1С), шаг «обнуление отсутствующих позиций» (DTJ-151) НИКОГДА не
запустится штатным путём — партии останутся с данными первых N-1 страниц бессрочно, а
`pharmacy_admin` не узнает о проблеме. Этот тикет — защитная фоновая job, которая явно помечает
такую сессию «зависшей» и намеренно НЕ выполняет зануление по неполным данным (лучше не занулить
существующий товар ошибочно, чем занулить по неполной информации).

## Технический контекст

`FULL_SYNC_SESSION_TIMEOUT_MINUTES` (ASSUMPTION `60`, ENV) — таймаут с момента получения ПОСЛЕДНЕЙ
полученной страницы этой сессии (не с момента её начала). Cron каждые 10 минут (`@nestjs/schedule`).
Алерт `pharmacy_admin`+on-call — публикация доменного события, реальная доставка (email/SMS/Slack)
— инфраструктура уведомлений (`notifications`-модуль, вне EP-05), этот тикет только публикует
событие через `InventoryOutboxPort`.

## Что сделать

1. `detect-stuck-full-sync-sessions.use-case.ts`: `DetectStuckFullSyncSessionsUseCase.execute():
   Promise<{ stuckSessionsCount: number }>` — запрос через
   `InventorySyncBatchRepositoryPort.findIncompleteFullSyncSessions(olderThanMinutes: number):
   Promise<readonly { fullSyncSessionId: string; pharmacyId: string; lastPageReceivedAt: Date }[]>`
   (новый метод порта — `SELECT full_sync_session_id, pharmacy_id, MAX(received_at) FROM
   inventory_sync_batches WHERE sync_type='full' AND full_sync_session_id IS NOT NULL GROUP BY
   full_sync_session_id, pharmacy_id HAVING bool_and(is_last_page)=false AND MAX(received_at) <
   now() - interval 'N minutes'`).
2. Для каждой найденной сессии — публиковать `FullSyncSessionStuckEvent { fullSyncSessionId,
   pharmacyId, lastPageReceivedAt }` через `InventoryOutboxPort` (переиспользование порта DTJ-147).
3. Пометить сессию как обработанную, чтобы не алертить повторно на каждый прогон cron (10 минут) —
   добавить поле `stuck_alert_sent_at` в `inventory_sync_batches`? НЕТ — это раздувает схему ради
   одного флага; вместо этого дедупликация через сам факт: алерт шлётся один раз при первом
   обнаружении, дальнейшие прогоны cron идемпотентно пропускают уже заалерченную сессию по наличию
   `FullSyncSessionStuckEvent` в `outbox` за последние `FULL_SYNC_SESSION_TIMEOUT_MINUTES` для того
   же `fullSyncSessionId` (запрос к `outbox` по `event_type + aggregate_id`, если такой индекс
   существует у EP-01; если нет — согласовать альтернативу на review, не блокировать тикет).
4. `full-sync-session-watchdog.cron.ts`: `@Cron('*/10 * * * *')` вызывает use case.
5. Шаг зануления (DTJ-151) для зависшей сессии НЕ вызывается вовсе (уже применённые страницы 1..N-1
   остаются штатно применёнными — этот тикет ничего не откатывает, только диагностирует).

## Критерии приёмки

1. **Given** full-сессия из 5 ожидаемых страниц, 5-я (`is_last_page=true`) не пришла за
   `FULL_SYNC_SESSION_TIMEOUT_MINUTES` (60 минут) с момента получения 4-й страницы, **When**
   `execute()` вызывается, **Then** сессия помечена «зависшей» (событие опубликовано),
   `stuckSessionsCount === 1` — точное соответствие TC-INV-026.
2. **Given** та же сессия, **When** событие уже опубликовано, страницы 1-4 применены штатно
   (проверяется отдельно тестами DTJ-148/151), **Then** зануление отсутствующих позиций (DTJ-151)
   НЕ выполняется — критерий негативный: watchdog НЕ вызывает `FullSyncCompletionPort`.
3. **Given** full-сессия, последняя страница пришла 5 минут назад (`< 60` минут), **When**
   `execute()` вызывается, **Then** эта сессия НЕ считается зависшей — второй негативный сценарий
   (окно таймаута соблюдается, ранняя незавершённая сессия не алертится преждевременно).
4. **Given** сессия уже была заалерчена на предыдущем прогоне cron, **When** `execute()` вызывается
   повторно 10 минут спустя (сессия всё ещё не завершена), **Then** повторное событие НЕ
   публикуется (дедупликация) — третий сценарий, защита от алерт-спама on-call.

## Тест-план

Unit (`detect-stuck-full-sync-sessions.use-case.spec.ts`, порты замоканы):
- `сессия старше таймаута без последней страницы помечается зависшей`
- `сессия моложе таймаута не помечается`
- `сессия с полученной последней страницей не считается зависшей` (`bool_and(is_last_page)=true`
  исключает её из выборки порта — тест мока порта, не проверяет сам SQL здесь)
- `повторный прогон не дублирует событие для уже заалерченной сессии`
- `несколько зависших сессий разных аптек обрабатываются независимо, каждая даёт своё событие`
Интеграционный: реальный SQL-запрос порта `findIncompleteFullSyncSessions` против Postgres с
фикстурами (сессия 4/5 страниц, сессия 5/5, сессия с недавней последней страницей).
Порог покрытия `application/` — 90%.

## Риски и подводные камни

- Дедупликация алерта через опрос `outbox` — прагматичное решение без изменения схемы, но зависит
  от наличия индекса `outbox(event_type, aggregate_id)`; если такого индекса нет у EP-01, запрос
  дедупликации может быть медленным на большом `outbox` — обсудить с владельцем `outbox`-инфры перед
  реализацией, альтернатива — отдельная маленькая таблица `inventory_sync_session_alerts(session_id
  PK, alerted_at)`, если это чище архитектурно (решение — на усмотрение реализующего разработчика
  по согласованию на review, не блокирует написание тикета).
- Реальная доставка алерта on-call (Slack/email/PagerDuty) — вне этого тикета и вне EP-05 целиком;
  зависит от готовности `notifications`-модуля подписаться на `FullSyncSessionStuckEvent`.
