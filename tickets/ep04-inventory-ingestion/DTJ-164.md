## Задача

Для REST/CommerceML исправление ошибок происходит на стороне 1С — кабинет не предлагает
редактирование. Но для Excel-канала аптека — человек, работающий в самом Excel: ей нужен файл ТОГО
ЖЕ шаблона, содержащий ТОЛЬКО отклонённые строки + колонку «Причина ошибки», который она правит и
загружает заново как НОВЫЙ импорт (не патч старого — терминальные батчи неизменяемы).

## Технический контекст

Источник данных — ДВА места: (а) строки, отклонённые ПАРСЕРОМ (DTJ-160, `rejectedRows` — эти строки
никогда не попадали ни в один `inventory_sync_batches`, DTJ-161 их не персистирует нигде кроме
ответа `POST`, значит их нужно ЛИБО персистировать отдельно при импорте, ЛИБО отчёт покрывает ТОЛЬКО
пост-парсинговые ошибки из `inventory_sync_errors` — см. решение ниже), (б) строки, отклонённые
`IngestInventoryBatchUseCase` уже ПОСЛЕ постановки в очередь (`inventory_sync_errors` по всем
батчам одного `sourceUploadId`).

**Решение по (а)**: DTJ-161 ДОПОЛНЯЕТСЯ (небольшая правка в рамках этого тикета, не создание нового
файла — координировать через `Edit`, не переписывание) — строки, отклонённые парсером, ТОЖЕ
записываются в `inventory_sync_errors`, но привязанные к СИНТЕТИЧЕСКОМУ батчу-контейнеру
«parser-errors» с тем же `sourceUploadId` (`channel='excel_import', status='failed_validation',
total_rows=0`, создаётся ТОЛЬКО если `rejectedRows.length > 0`) — так ВСЕ ошибки одной загрузки
(парсинг + бизнес-логика) оказываются в одной таблице под одним `sourceUploadId`, отчёт этого
тикета читает единый источник.

## Что сделать

1. Точечно дополнить `inventory-excel-import.controller.ts` (DTJ-161, `Edit`, не переписывание):
   если `rejectedRows.length > 0` — создать синтетический батч-контейнер (см. выше) и записать
   `rejectedRows` в `inventory_sync_errors` с `error_code`, уже определённым парсером
   (`ambiguous_date_format`/`missing_required_field`/`invalid_price`/`invalid_quantity`).
2. `inventory-excel-error-report.controller.ts`: `@Get('/api/v1/inventory-sync-batches/
   :sourceUploadId/error-report')`, `@UseGuards(RolesGuard, TenantScopeGuard)`
   `@Roles('pharmacy_admin', 'super_admin')`, та же проверка владения, что DTJ-163 (404 при чужом
   `sourceUploadId`).
3. Собрать ВСЕ `inventory_sync_errors` по всем `inventory_sync_batches WHERE source_upload_id =
   :sourceUploadId` (включая синтетический parser-errors батч из п.1).
4. Сгенерировать `.xlsx` (`exceljs`, тот же пакет, что DTJ-159/160) — ТЕ ЖЕ заголовки шаблона
   (`INVENTORY_IMPORT_TEMPLATE_HEADERS`, DTJ-159) + дополнительная 11-я колонка `Причина ошибки`
   (локализованный текст `errorCode → i18n`), заполненная данными из `rawRow` каждой ошибочной
   строки.
5. Given `sourceUploadId` без ни одной ошибки (полностью успешный импорт) — `404 NOT_FOUND` с
   понятным сообщением («отчёт об ошибках недоступен — импорт завершился без ошибок»), не пустой
   файл.
6. Ответ — файл-вложение, как DTJ-159 (`Content-Disposition: attachment`).

## Критерии приёмки

1. **Given** импорт `sourceUploadId=X` с 12 отклонёнными строками (5 — парсером, 7 — use case
   бизнес-логикой), **When** `GET .../error-report`, **Then** `200` с `.xlsx`, содержащим РОВНО 12
   строк данных + заголовок + колонка `Причина ошибки`, заполненная для каждой строки.
2. **Given** тот же файл, **When** колонка `Причина ошибки` читается для строки с
   `error_code='ambiguous_date_format'`, **Then** значение — локализованный человекочитаемый текст
   (не сырой код enum) на языке аптеки (`Accept-Language`/сохранённая локаль профиля — уточнить
   источник локали при реализации, вероятно параметр запроса, как и остальные локализуемые ответы).
3. **Given** `sourceUploadId`, импорт которого завершился ПОЛНОСТЬЮ успешно (0 ошибок), **When**
   `GET .../error-report`, **Then** `404 NOT_FOUND` — негативный сценарий (нет смысла скачивать
   пустой отчёт).
4. **Given** `sourceUploadId` чужой аптеки, **When** `GET .../error-report`, **Then** `404
   NOT_FOUND` — второй негативный сценарий, изоляция.

## Тест-план

Unit (`inventory-excel-error-report.controller.spec.ts`, БД замокана):
- `отчёт объединяет ошибки парсера и ошибки use case в один файл`
- `колонка Причина ошибки содержит локализованный текст, не код enum`
- `полностью успешный импорт (0 ошибок) даёт 404`
- `чужой sourceUploadId даёт 404`
- `структура заголовков файла отчёта совпадает с шаблоном импорта + 11-я колонка`
Интеграционный: полный цикл — импорт файла с намеренными ошибками (DTJ-161) → скачивание отчёта →
парсинг скачанного файла тем же `exceljs` и сверка содержимого со списком ожидаемых ошибок. Порог
покрытия `presentation/` — 70%.

## Риски и подводные камни

- Правка чужого (своего же эпика, но уже смерженного) файла DTJ-161 — риск конфликта, если DTJ-161
  на момент этого тикета уже в проде и активно используется другими тестами; делать точечно
  (`replace_symbol_body`/`Edit`), прогнать regression-тесты DTJ-161 после правки.
- Синтетический батч-контейнер «parser-errors» с `total_rows=0` — нестандартная строка
  `inventory_sync_batches` (обычно `total_rows` отражает реальный размер батча); убедиться, что
  DTJ-163 (список батчей) либо ФИЛЬТРУЕТ такие синтетические записи из основного списка (чтобы не
  путать пользователя строкой «0 из 0 успешно»), либо явно помечает их — решить на review, добавить
  флаг `isParserErrorContainer`/аналог, если потребуется различать в UI (DTJ-169).
