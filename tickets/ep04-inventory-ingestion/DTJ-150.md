## Задача

D-04 требует ежедневную полную сверку остатков для аптек, интегрированных по REST/CommerceML.
DoruTJ не может «вытащить» данные из 1С активно — только попросить (webhook-триггер на
`one_c_endpoint`). Этот use case решает, КОГО и КОГДА триггерить, распределяя нагрузку по часовому
окну, а не единомоментно в 03:00:00 (что создало бы thundering herd на несколько сотен внешних
1С-инсталляций одновременно).

## Технический контекст

Cron `0 3 * * *` в `Asia/Dushanbe` = `0 22 * * *` UTC (`@nestjs/schedule`, EP-01-инфраструктура,
без перехода на летнее время — Таджикистан не переходит на летнее время). Только аптеки со
`status='active'` И имеющие `channel` в `pharmacy_api_keys` (то есть реально интегрированные по
REST/CommerceML — Excel/ручные аптеки НЕ имеют автоматической ночной синхронизации, для них полная
сверка — кнопка «Обновить весь ассортимент» в кабинете, реализуется на стороне DTJ-161/167 через
явный full-режим импорта, не этим тикетом). Распределение — `sync_slot = hash(pharmacy_guid) mod
NIGHTLY_SYNC_WINDOW_MINUTES` (ASSUMPTION `60`), детерминированно (не `Math.random()` — домен и
application не используют случайность без порта, `02` §2 п.6 применяется здесь и к application по
аналогии для воспроизводимости тестов).

## Что сделать

1. `pharmacy-api-key.read.port.ts`: узкий порт `PharmacyApiKeyReadPort.findActivePharmaciesWithKeys():
   Promise<readonly { pharmacyId: string; oneCEndpoint: string | null }[]>` — читает
   `pharmacies WHERE status='active'` JOIN `pharmacy_api_keys WHERE revoked_at IS NULL`, фильтрует
   аптеки с непустым `one_c_endpoint` (поле уже существует в `pharmacies`, владение `onboarding`).
2. `run-nightly-full-sync-fanout.use-case.ts`: `RunNightlyFullSyncFanoutUseCase.execute(): Promise<{
   triggeredCount: number }>` — для каждой аптеки из порта вычисляет `syncSlot = hashToInt(
   pharmacyId) % NIGHTLY_SYNC_WINDOW_MINUTES` (детерминированная хеш-функция, например `djb2` или
   переиспользование `crypto.createHash('sha1')` усечённого до `int32` — зафиксировать одну
   конкретную реализацию, покрыть тестом на воспроизводимость).
3. Публикует `FullSyncTriggerRequestedEvent { pharmacyId, oneCEndpoint, scheduledAt: 03:00 +
   syncSlot минут }` через `InventoryOutboxPort` (переиспользование существующего порта, не новый
   HTTP-вызов из use case — реальная отправка webhook'а на `one_c_endpoint` — ответственность
   отдельного infrastructure-адаптера/подписчика события, ВНЕ этого тикета, т.к. не специфицирована
   явно ни в module 22, ни в files_owned EP-05 как отдельный компонент; см. «Риски»).
4. `nightly-full-sync-fanout.cron.ts` (infrastructure): `@Cron('0 22 * * *', { timeZone: 'UTC' })`
   (эквивалент `Asia/Dushanbe 03:00`, задокументировать оба представления в комментарии) вызывает
   `RunNightlyFullSyncFanoutUseCase.execute()`.
5. Приоритет job в очереди для итогового full-sync батча = `10` (SRS-INV-034) — это применяется НЕ
   здесь (это касается DTJ-153, который читает `syncType` при постановке job), но зафиксировать
   ссылкой в комментарии, чтобы не потерялось.

## Критерии приёмки

1. **Given** 300 аптек с `status='active'` и заполненным `one_c_endpoint`, **When**
   `execute()` вызывается, **Then** `triggeredCount === 300`, для каждой аптеки опубликовано ровно
   одно событие `FullSyncTriggerRequestedEvent`.
2. **Given** аптека `pharmacy_guid=X`, **When** вычисляется `syncSlot`, **Then** результат
   ДЕТЕРМИНИРОВАН — повторный вызов с тем же `pharmacy_guid` даёт тот же `syncSlot` (воспроизводимо
   для тестов, SRS-INV-039).
3. **Given** аптека со `status='suspended'` (приостановлена), **When** `execute()` собирает список,
   **Then** эта аптека НЕ попадает в `triggeredCount` — негативный сценарий (полная синхронизация не
   триггерится для неактивных точек).
4. **Given** аптека `status='active'`, но `pharmacy_api_keys` пуст (только Excel/ручной канал),
   **When** `execute()` собирает список, **Then** эта аптека НЕ попадает в выборку (нет
   автоматической ночной синхронизации без интеграции — второй негативный сценарий).

## Тест-план

Unit (`run-nightly-full-sync-fanout.use-case.spec.ts`, порт замокан):
- `все активные интегрированные аптеки получают событие триггера`
- `syncSlot детерминирован для одного и того же pharmacyId`
- `syncSlot распределён по диапазону [0, NIGHTLY_SYNC_WINDOW_MINUTES) для разных pharmacyId`
  (статистическая проверка на выборке из ≥100 UUID — не идеальная равномерность, но отсутствие
  вырождения в одну константу)
- `suspended-аптека исключена из выборки`
- `аптека без pharmacy_api_keys исключена из выборки`
- `triggeredCount соответствует фактическому числу опубликованных событий`
Интеграционный: cron регистрируется в `@nestjs/schedule` без ошибок конфигурации таймзоны.
E2E — не в этом тикете (полный сценарий CUJ-6' ночной части закрывается E2E-тикетом EP-19, вне
этого эпика; здесь unit+интеграционный достаточны). Порог покрытия `application/` — 90%.

## Риски и подводные камни

- **Фактическая отправка webhook'а на `one_c_endpoint` НЕ специфицирована ни одним документом
  иерархии как отдельный компонент** — module 22 говорит только «публикует webhook-триггер», не
  уточняя HTTP-клиент/retry-политику/таймаут этого исходящего вызова. Этот тикет ограничен
  публикацией доменного события; реальный HTTP-адаптер, слушающий `FullSyncTriggerRequestedEvent` и
  вызывающий `one_c_endpoint`, требует отдельного тикета — если Tech Lead решит, что он входит в
  диапазон EP-05, добавить дополнительный тикет; если это неопределённая часть, требующая ADR
  (таймаут/retry внешнего вызова, которого 1С может не поддерживать) — эскалировать архитектору до
  реализации, не изобретать протокол самостоятельно.
- Часовой пояс `Asia/Dushanbe` без DST — `@nestjs/schedule`/`node-cron` должны быть сконфигурированы
  ИМЕННО с `timeZone` опцией, не с ручным пересчётом UTC-смещения в коде (иначе ошибка при смене
  версии Node/системного `tzdata`).
