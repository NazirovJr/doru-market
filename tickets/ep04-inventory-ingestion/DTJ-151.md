## Задача

Когда полный снапшот (`sync_type='full'`) завершён (последняя страница применена), партии, чей
`internal_sku` не встретился НИ НА ОДНОЙ странице этого снапшота, обязаны получить `quantity=0`
(товар физически закончился/снят с продажи в 1С) — но БЕЗ физического удаления строки (аудит) и
БЕЗ обнуления партий, обновлённых ПОЗЖЕ момента снапшота гонкой с параллельной дельтой (SRS-INV-042).
Это единственный шаг ингеста, реализуемый как прямой SQL-запрос, а не построчная доменная логика —
осознанное исключение из «домен защищает свои инварианты», обоснованное требованием производительности
(SRS-INV-052) и уже задокументированное в module 22.

## Технический контекст

Порт объявлен в DTJ-148 (`FullSyncCompletionPort.zeroOutMissing(pharmacyId, fullSyncTimestamp,
touchedBatchNumbers)`), этот тикет реализует его инфраструктурным адаптером — прямой SQL, дословно
`22-module-inventory-sync-1c.md` строки 559-568 (SRS-INV-041), с критичным условием
`ib.last_synced_at < :fullSyncTimestamp` (SRS-INV-042 — защита от гонки «дельта после снапшота, но
партия физически применена ДО прихода последней страницы снапшота»).

## Что сделать

1. `full-sync-completion.port.ts`: интерфейс `FullSyncCompletionPort.zeroOutMissing(pharmacyId:
   string, fullSyncTimestamp: Date, touchedBatchNumbers: readonly string[]): Promise<{
   zeroedLotsCount: number }>`.
2. `drizzle-full-sync-completion.adapter.ts`: реализация — ОДИН SQL-запрос (Drizzle raw SQL или
   query builder, что даёт корректный `UPDATE ... FROM ... WHERE` с параметризованным
   `ANY(:touchedBatchNumbers)`), дословно повторяющий условия SRS-INV-041:
   `ib.pharmacy_inventory_id = pi.id AND pi.pharmacy_id = :pharmacyId AND ib.last_synced_at <
   :fullSyncTimestamp AND ib.batch_number NOT IN (:touchedBatchNumbers) AND ib.quantity > 0`, `SET
   quantity = 0, last_synced_at = :fullSyncTimestamp`.
3. Вызывается ИЗ `IngestInventoryBatchUseCase` (DTJ-148, шаг 5) только когда `isLastPage &&
   syncType==='full'` — этот адаптер сам не решает, когда его вызывать (чистая инфраструктурная
   функция).
4. `touchedBatchNumbers` — накапливается use case'ом (DTJ-148) по ходу применения строк текущего
   `full_sync_session_id` (все страницы, не только последняя — если `full_sync_session_id`
   многостраничный, `touchedBatchNumbers` обязан включать `batch_number` со ВСЕХ ранее применённых
   страниц этой сессии, не только последней; чтение этого списка — через
   `InventorySyncBatchRepositoryPort` по `full_sync_session_id`, реализуется здесь как
   вспомогательный метод адаптера `.findTouchedBatchNumbersForSession(sessionId): Promise<string[]>`
   ИЛИ передаётся use case'ом явно, если он уже трекает список в памяти обработки одной сессии —
   выбрать реализацию по факту: если сессия многостраничная и обрабатывается разными job'ами
   воркера (что типично — DTJ-154 конкурентность), список ОБЯЗАН читаться из БД, не из памяти одного
   процесса; зафиксировать метод чтения из БД как основной путь).
5. Не удалять партию физически — только `UPDATE quantity = 0` (аудит/история, тот же принцип, что
   просроченные партии, SRS-DB-020).

## Критерии приёмки

1. **Given** full-снапшот, `internal_sku='SKU-777'` (партия с `batch_number` для этого SKU)
   отсутствует ни на одной из его страниц, **When** `zeroOutMissing` вызывается на
   `is_last_page=true`, **Then** партия `SKU-777` получает `quantity=0`, строка НЕ удалена
   физически (`SELECT COUNT(*) FROM inventory_batches WHERE batch_number=...` не уменьшается) —
   точное соответствие TC-INV-020.
2. **Given** full-снапшот `sync_timestamp=03:00:00`; отдельная REST-дельта того же SKU с
   `sync_timestamp=03:02:00` применена РАНЬШЕ шага зануления (партия уже имеет
   `last_synced_at=03:02:00`), **When** `zeroOutMissing(fullSyncTimestamp=03:00:00)` выполняется,
   **Then** эта партия НЕ обнуляется (`last_synced_at=03:02:00 > fullSyncTimestamp` исключает её из
   `WHERE`) — негативный сценарий (в смысле «не должна сработать»), точное соответствие TC-INV-021.
3. **Given** партия, чей `batch_number` присутствует в `touchedBatchNumbers` (была применена этим же
   снапшотом на одной из страниц), **When** `zeroOutMissing` выполняется, **Then** эта партия НЕ
   зануляется (`NOT IN` исключает её) — второй негативный сценарий: свежепримененные партии не
   зануляются как «отсутствующие».
4. **Given** партия уже имеет `quantity=0` (была обнулена ранее), **When** `zeroOutMissing`
   выполняется повторно, **Then** запрос идемпотентен (`quantity > 0` в `WHERE` исключает
   уже-нулевые партии из `UPDATE`, `zeroedLotsCount` не считает их повторно).

## Тест-план

Интеграционный (`drizzle-full-sync-completion.adapter.integration.spec.ts`, реальный Postgres —
это SQL-логика, unit-тест с моком БД не даёт достаточной уверенности в корректности запроса):
- `партия, отсутствующая в снапшоте, зануляется`
- `партия с более свежим last_synced_at чем fullSyncTimestamp НЕ зануляется` (гонка SRS-INV-042)
- `партия в touchedBatchNumbers НЕ зануляется`
- `партия другой аптеки (pharmacy_id≠target) НЕ затрагивается`
- `повторный вызов идемпотентен, zeroedLotsCount не растёт на уже-нулевых партиях`
- `zeroedLotsCount корректно отражает число реально изменённых строк`
Порог покрытия для `infrastructure/` — 70% (`02` §6 п.4), но т.к. это критичная SQL-логика без
domain-обёртки, интеграционные тесты выше — обязательный минимум независимо от процентного порога.

## Риски и подводные камни

- Способ получения `touchedBatchNumbers` для многостраничной сессии, обрабатываемой разными
  воркерами конкурентно — главный источник багов этого тикета. Если реализовать неверно (например,
  трекать в памяти одного процесса вместо чтения из БД), при реальной многостраничной сессии с
  несколькими параллельными job'ами шаг зануления затрёт корректно применённые страницы. Решать
  ЧТЕНИЕМ ИЗ БД, не оптимизировать в память без крайней необходимости.
- Список `touchedBatchNumbers` может быть большим (до нескольких тысяч `batch_number` для крупной
  сети) — `NOT IN (:list)` с очень большим списком параметров может деградировать по
  производительности; при реальных объёмах рассмотреть `NOT IN (SELECT ... FROM inventory_batches
  WHERE inventory_sync_batches.full_sync_session_id = :sessionId)` как подзапрос вместо передачи
  списка параметром — не блокирует MVP, но зафиксировать как известное ограничение в PR.
