## Задача

D-12 — все четыре канала обязаны идти через ОДИН use case, без собственной копии бизнес-правил.
Это тикет, реализующий саму гарантию D-12: получает нормализованную команду (уже построенную
маппером канала), матчит несматченные строки через `CompositeInventoryMatcherService`, применяет
резолвленные строки к `PharmacyInventory`, ведёт построчные ошибки и переводит `InventorySyncBatch`
по состояниям. Это самый крупный и самый критичный тикет эпика — без него ни один канал не
работает целиком, даже если у каждого готовы presentation-контроллеры.

## Технический контекст

Вызывается АСИНХРОННО из BullMQ worker-процессора (DTJ-154) для каналов REST/Excel/CommerceML —
контроллеры этих каналов (DTJ-157/161) только персистируют `inventory_sync_batches`+
`inventory_sync_raw_items`+outbox-событие и возвращают `202` немедленно (SRS-INV-007). Для канала
ручного ввода (DTJ-162) этот use case вызывается СИНХРОННО прямо из контроллера — решение
зафиксировано в DTJ-162 (маленькие резолвленные батчи, composite-матчинг не требуется, нет причины
уходить в очередь — задокументировано там же как явное архитектурное решение этого эпика).

Идемпотентность повторного `batch_id` (SRS-DOM-168/SRS-INV-009) обрабатывается ДО постановки в
очередь, на уровне репозитория `inventory_sync_batches` (`ON CONFLICT (id) DO NOTHING RETURNING *`)
— это ответственность DTJ-157/DTJ-153, НЕ этого use case. К моменту вызова `execute()` батч уже
гарантированно новый (BullMQ `jobId=batchId` дополнительно защищает от повторной постановки самой
джобы, SRS-INV-032, DTJ-153).

## Что сделать

1. `pharmacy-inventory.repository.port.ts`: `PharmacyInventoryRepositoryPort` —
   `findOrCreateManyByMedicineIds(pharmacyId: string, medicineIds: readonly string[]): Promise<
   ReadonlyMap<string, PharmacyInventory>>` (батчево, SRS-INV-052 п.4 set-based upsert агрегатов) и
   `saveMany(aggregates: readonly PharmacyInventory[]): Promise<void>` (персистирует изменённые
   партии через set-based `ON CONFLICT DO UPDATE`, реализация — DTJ-154, здесь только интерфейс).
2. `inventory-sync-batch.repository.port.ts`: `InventorySyncBatchRepositoryPort.save(batch:
   InventorySyncBatch): Promise<void>`, `.appendErrors(batchId: string, errors: readonly
   InventorySyncRowError[]): Promise<void>`, `.findRawItems(batchId: string): Promise<readonly
   RawInventoryRow[]>` (чтение из `inventory_sync_raw_items`, DTJ-141 п.2).
3. `ingest-inventory-batch.use-case.ts`: класс `IngestInventoryBatchUseCase` с конструктором,
   принимающим все порты (`PharmacyInventoryRepositoryPort`, `InventorySyncBatchRepositoryPort`,
   `CompositeInventoryMatcherService`, `Clock`, `UnitOfWork`) и единственным публичным методом
   `execute(cmd: IngestInventoryBatchCommand): Promise<IngestInventoryBatchResult>`.
4. Шаг 1 — загрузить агрегат `InventorySyncBatch` по `cmd.batchId`, вызвать `markProcessing()`.
5. Шаг 2 — разделить `cmd.rows` на `resolved: true` (готовы к применению немедленно) и
   `resolved: false` (передать в `CompositeInventoryMatcherService.matchBatch` → при необходимости
   `.resolveFuzzyCandidates`, DTJ-146/DTJ-147).
6. Шаг 3 — для каждой резолвленной строки (изначально resolved:true ИЛИ успешно сматченной) —
   найти/создать соответствующий агрегат `PharmacyInventory` (батчево, через
   `findOrCreateManyByMedicineIds`), вызвать `.applyDelta(...)` или `.applyDelete(...)`; накопить
   ошибки валидации (`InvalidPriceError` и т.п., пойманные как `try/catch` НЕ пустой — `catch`,
   обогащающий `InventorySyncRowError`, C12) как `inventory_sync_errors` с соответствующим
   `error_code` (`invalid_price`, `invalid_quantity`).
7. Шаг 4 — для строк с `outcome: 'unmatched'` из шага 2 — сформировать
   `inventory_sync_errors(error_code='unmatched_medicine')` + вызвать `OutboxPort.append` (через
   `InventoryOutboxPort`, DTJ-147) В ТОЙ ЖЕ единице работы, что и остальная запись батча.
8. Шаг 5 — если `cmd.isLastPage && cmd.syncType === 'full'` — делегировать в
   `FullSyncZeroOutMissingLotsService` (DTJ-151, порт вызывается здесь, реализуется отдельным
   тикетом — этот use case ТОЛЬКО вызывает порт `FullSyncCompletionPort.zeroOutMissing(pharmacyId,
   fullSyncTimestamp, touchedBatchNumbers)`, не содержит SQL сам).
9. Шаг 6 — посчитать `acceptedRows`/`rejectedRows`, вызвать `batch.markCompletedFullSuccess()` (0
   ошибок) или `batch.markCompletedPartialSuccess(accepted, rejected)` (≥1 ошибка) — НИКОГДА
   `failed_validation` из этого метода (этот статус — ТОЛЬКО путь инфраструктурного отказа очереди,
   DTJ-155, не бизнес-ошибок строк, SRS-INV-035 vs SRS-INV-056 — разные причины, разные обработчики).
10. Всё выполняется в одной `unitOfWork.run(...)` транзакции (`02` §3 п.3 — границы транзакции
    задаются в use case).
11. `IngestInventoryBatchResult` — `{ batchId, status, acceptedRows, rejectedRows }`, тонкий, без
    сущностей БД наружу.

## Критерии приёмки

1. **Given** батч из 1000 строк, 12 из которых проваливают матчинг/валидацию (8
   `unmatched_medicine`, 3 `invalid_price`, 1 `ambiguous_date_format`* — последнее приходит уже
   отфильтрованным парсером канала, не этим use case), **When** `execute()` завершается, **Then**
   988 строк применены к `pharmacy_inventory`, `status='completed_partial_success'`,
   `acceptedRows=988`, `rejectedRows=12`, записано 12 строк `inventory_sync_errors` — точное
   соответствие TC-INV-006/SRS-INV-056 (кроме `ambiguous_date_format`, который относится к
   Excel-парсеру DTJ-160, здесь тестируется только доля use case — 11 строк типов, обрабатываемых
   этим use case).
2. **Given** батч, где ВСЕ строки валидны и сматчены, **When** `execute()` завершается, **Then**
   `status='completed_full_success'`, `rejectedRows=0`.
3. **Given** строка с `priceDiram <= 0 && quantity > 0` внутри батча из 5 строк (остальные 4
   валидны), **When** `execute()` обрабатывает батч, **Then** невалидная строка НЕ блокирует
   остальные 4 (они применены), `inventory_sync_errors` содержит ровно одну запись
   `error_code='invalid_price'` — негативный сценарий на уровне отдельной строки, REQ-SYNC-9
   буквально.
4. **Given** `IngestInventoryBatchUseCase.execute()` вызывается для батча, чей агрегат
   `InventorySyncBatch` уже в терминальном статусе (баг вызывающего кода — не должно происходить
   штатно, но должно быть безопасно), **When** `execute()` пытается `markProcessing()`, **Then**
   бросается `IllegalBatchStatusTransitionError` (из DTJ-144), транзакция откатывается целиком —
   второй негативный сценарий, use case не «тихо продолжает» с некорректным состоянием агрегата.

## Тест-план

Unit (`ingest-inventory-batch.use-case.spec.ts`, ВСЕ порты замоканы, включая
`CompositeInventoryMatcherService` — БЕЗ реальной БД):
- `все строки валидны и сматчены -> completed_full_success`
- `частичный провал -> completed_partial_success с корректными счётчиками`
- `невалидная цена одной строки не блокирует остальные строки батча`
- `unmatched-строка формирует inventory_sync_errors + вызывает OutboxPort.append`
- `resolved:true строки применяются без вызова CompositeInventoryMatcherService`
- `resolved:false строки обязательно проходят через matchBatch`
- `isLastPage && syncType=full вызывает FullSyncCompletionPort.zeroOutMissing`
- `syncType=delta НЕ вызывает FullSyncCompletionPort ни при каком isLastPage`
- `попытка execute() на батче в терминальном статусе бросает IllegalBatchStatusTransitionError`
- `вся обработка батча выполняется в одной unitOfWork.run(...)` (проверка через spy на `UnitOfWork`)
Интеграционный (`ingest-inventory-batch.use-case.integration.spec.ts`, реальный Postgres, реальные
репозитории DTJ-154): полный прогон TC-INV-006-сценария (988/12) от команды до строк в БД.
Порог покрытия `application/` — 90% обязателен, это самый крупный файл модуля — уделить тест-плану
дополнительное внимание на code review.

## Риски и подводные камни

- Это САМЫЙ большой риск сложности во всём эпике — если декомпозиция на приватные методы не
  сделана заранее, легко упереться в C1/C3 пороги и потребовать рефакторинг на review. Рекомендация:
  спроектировать приватные методы `#matchUnresolvedRows`, `#applyResolvedRows`,
  `#recordRowErrors`, `#finalizeBatchStatus` ДО написания теста, не после.
- `FullSyncCompletionPort` (DTJ-151) — циклическая зависимость по срокам: этот тикет вызывает порт,
  которого ещё нет физически до DTJ-151. Смягчение — интерфейс порта объявляется ЗДЕСЬ (в этом
  тикете, `application/ports/full-sync-completion.port.ts`, файл добавить в `files_owned` при
  реализации), реализация — в DTJ-151/DTJ-154; use case тестируется с моком порта независимо от
  готовности реализации.
- Разделение «инфраструктурный сбой → `failed_validation`» (DTJ-155) vs «бизнес-ошибки строк →
  `completed_partial_success`» — лёгкая точка спутать при реализации; тест-план критерия 4 существует
  именно для явной защиты от этой путаницы.
