## Задача

Все последующие тикеты эпика (domain-репозитории, use case'ы, контроллеры) читают/пишут в шесть
таблиц контекста `inventory`. Без Drizzle-схемы и применённой миграции ни один интеграционный тест
эпика не запустится. Этот тикет — единственное место, где вводится физическая схема БД для
`inventory`, буквально по `docs/spec/11-database-schema.md` §«Группа D» (таблицы 7–12), без единого
отклонения — документ помечен «ЗАКОН» для этого модуля.

## Технический контекст

`apps/api/src/infrastructure/db/schema/*.schema.ts` — единственный источник истины схемы (`11`
§«Файлы схемы»), один файл на bounded context. Миграции генерируются `drizzle-kit generate` из
TS-схемы, порядок файлов — топологический (`11` §«Порядок миграций»): `0007_inventory.sql` —
зарезервированное имя для этого контекста в общей последовательности `0001..0018` (расширения enum
`inventory_sync_channel`/`inventory_sync_type`/`inventory_sync_batch_status`/
`inventory_sync_row_error_code` создаются в `0002_enums.sql`, владение EP-01 — этот тикет ТОЛЬКО
использует уже существующие типы, не создаёт их; если к моменту реализации `0002_enums.sql` ещё не
содержит нужные enum'ы — дополнить его точечно, не переписывая).
   **[ИЗМЕНЕНО]** по факту `0002_enums.sql` НЕ содержит `inventory_sync_row_error_code` — этот
   enum не был создан ни в одной миграции, соответствующий `pgEnum` удалён из `enums.schema.ts`
   как мёртвый и расходящийся с рантаймом (код эмитит `'unmatched_medicine'`, которого не было
   в enum). Источник истины по кодам ошибок строк — TS-юнион
   `InventorySyncRowError['errorCode']` (`inventory-sync-batch.repository.port.ts`); таблица
   `inventory_sync_errors` будет `VARCHAR` + `CHECK` по конвенции `0012`, не pg enum.

Таблицы (полные определения — `11-database-schema.md` строки 419-546, воспроизводить дословно):
`pharmacy_inventory`, `inventory_batches`, `pharmacy_sku_mapping`, `catalog_match_queue` (структура
БАЗОВОЙ версии без полей из «Дополнений» — они добавляются DTJ-142 отдельной миграцией другого
модуля-владельца), `inventory_sync_batches`, `inventory_sync_errors`.

**Важно**: `catalog_match_queue` в домене принадлежит контексту `moderation`, не `inventory` (см.
`22-module-inventory-sync-1c.md` §1: «не владеет: catalog_match_queue»). Тем не менее физическая
таблица должна существовать до того, как inventory сможет писать в неё построчные ошибки/читать её
при резолюции (DTJ-149) — т.к. `moderation`-эпик не входит в зарезервированный диапазон EP-05 и его
точный номер/сроки неизвестны, эта таблица включается в СХЕМУ этого тикета (создание DDL), но её
доменная модель/CRUD-эндпоинты НЕ реализуются здесь — inventory только читает и точечно апдейтит её
через свой репозиторий (DTJ-149), полноценное владение (создание записей, курация) — за
`moderation`-эпиком. Если к моменту интеграции окажется, что `moderation`-эпик уже создал эту
таблицу первым — этот тикет пересматривается на code review, дублирующий `CREATE TABLE` удаляется
(идемпотентная миграция, `IF NOT EXISTS` не используется по конвенции `drizzle-kit`, конфликт
решается вручную).

   `unique_pharmacy_medicine`, `chk_inventory_batches_quantity_nonneg`,

   `pharmacies.schema.ts`/`medicines.schema.ts` (EP-03/EP-04), не дублировать их определение.
3. Сгенерировать миграцию: `pnpm --filter api drizzle-kit generate --name inventory`, проверить,
   что результат = `0007_inventory.sql` (переименовать при необходимости под топологический порядок
   `11` §«Порядок миграций», если `drizzle-kit` сгенерировал другой номер — файлы `NNNN_*.sql`
   именуются вручную под зафиксированную последовательность, не автонумерацией `drizzle-kit`).
4. Индексы `ix_pharmacy_inventory_pharmacy`, `ix_pharmacy_inventory_medicine`,
   `ix_inventory_batches_fefo`, `ix_inventory_batches_stale`, `ix_catalog_match_queue_status`,
   `ix_inventory_sync_batches_pharmacy`, `ix_inventory_sync_errors_batch` — согласно `11` §«Порядок
   миграций» индексы выносятся в ОТДЕЛЬНУЮ `0016_indexes.sql` (владение — координируется с EP-01/
   последним эпиком, трогающим эту миграцию перед волной 4; если файл уже существует к волне 4,
   добавить точечно секцию индексов inventory, не переписывать файл).
5. Триггер `trg_recompute_fefo` (`11` §«Готовые SQL-триггеры», SRS-DB-021) — выносится в
   `0017_triggers_and_checks.sql` по тому же принципу совместного владения, п.4.
6. Написать `apps/api/src/infrastructure/db/migrations/0007_inventory.down.sql` (SRS-DB-034 —
   таблицы новые, `down` тривиален: `DROP TABLE IF EXISTS ... CASCADE` в обратном топологическом
   порядке).
7. Применить `pnpm db:migrate` локально против dev-контейнера Postgres 16 (`docker-compose`,
   владение EP-19), убедиться, что миграция идёт по номерам без конфликта.

## Критерии приёмки

1. **Given** чистая БД после `0001..0006`, **When** применяется `0007_inventory.sql`, **Then** все
   шесть таблиц создаются, `\d pharmacy_inventory` показывает `unique_pharmacy_medicine`,
   `\d inventory_batches` показывает оба CHECK-constraint'а из п.1.
2. **Given** попытка вставить в `inventory_batches` строку с `quantity = -1`, **When** выполняется
   `INSERT`, **Then** `23514 check_violation` (`chk_inventory_batches_quantity_nonneg`).
3. **Given** попытка вставить в `inventory_sync_batches` строку с `total_rows = 1500`, **When**
   выполняется `INSERT`, **Then** `23514 check_violation` (`chk_sync_batches_row_limit`) — негативный
   сценарий, точное соответствие TC-DB-020 из `11-database-schema.md`.
4. **Given** `pnpm db:migrate` уже применил `0007_inventory.sql` один раз, **When** команда
   запускается повторно, **Then** миграция идемпотентно пропускается (журнал `drizzle` `__drizzle_
   migrations`), схема не дублируется и не падает ошибкой.

## Риски и подводные камни

- Совместное владение `0016_indexes.sql`/`0017_triggers_and_checks.sql`/`0002_enums.sql` с другими
  эпиками — реальный риск merge-конфликтов при параллельной разработке волны 2-4. Смягчение:
  маленькие точечные диффы (добавление секции, не переписывание файла), координация по волнам
  выполнения (`00-EPICS.md` — EP-05 стартует в волне 4, к этому моменту EP-01/EP-02/EP-03/EP-04 уже
  должны были создать свои секции этих файлов).
- `catalog_match_queue` — пограничный случай владения (см. «Технический контекст»). Если
  `moderation`-эпик ещё не начат к моменту этого тикета, EP-05 создаёт таблицу первым — тогда
  `moderation`-эпику потребуется миграция-дополнение, а не `CREATE TABLE`; зафиксировать это в PR
  явно, чтобы не потерялось при передаче.
- Реальный номер `0007_inventory.sql` зависит от того, что уже успели закоммитить EP-01/EP-03/EP-04
  к моменту старта волны 4 — если фактическая последовательность разошлась с `11
  -database-schema.md` §«Порядок миграций» (например, `0005`/`0006` заняты другим содержимым),
  ориентироваться на СОДЕРЖИМОЕ («после org_base/tenancy_identity, до orders_cart»), не на
  жёсткий номер.
