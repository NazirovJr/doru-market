## Задача

`PharmacyInventory` — центральный агрегат модуля: единственное место, где живут правила «что
считается остатком», «какая цена/срок годности показываются в каталоге» (FEFO) и «когда входящая
строка синхронизации отбрасывается как устаревшая». Все три канала (REST/Excel/ручной ввод) и
ночная полная синхронизация в конечном счёте мутируют состояние ЧЕРЕЗ методы этой сущности — если
инварианты не защищены здесь, они неизбежно расползутся по use case'ам трёх разных каналов
(нарушение C15/DRY и прямое нарушение `02-CLEAN-ARCHITECTURE-AND-CODE.md` §2 п.1).

## Технический контекст

Инварианты — `docs/spec/10-domain-model.md` строки 244-265 (SRS-DOM-018..024), уже нормативно
зафиксированы, этот тикет их РЕАЛИЗУЕТ, не переопределяет. Партии (`InventoryBatch`, не путать с
`InventorySyncBatch` из DTJ-144 — разные сущности с похожими именами, см. предупреждение ниже) —
дочерние объекты агрегата, физически хранятся в отдельной таблице `inventory_batches`
(`pharmacy_inventory_id` FK), но в домене моделируются как часть одного агрегата
`PharmacyInventory` (агрегатный корень владеет коллекцией партий, наружу отдаёт только вычисляемые
проекции `stock_quantity`/`displayPrice`/`displayExpiryDate`).

**Терминологическая ловушка**: в `22-module-inventory-sync-1c.md` `InventoryBatch` (VO входящей
команды строки, см. DTJ-145) и `InventorySyncBatch` (агрегат состояния батча-запроса, DTJ-144) —
это НЕ одно и то же с партией товара (`inventory_batches`, дочерний объект ЭТОГО агрегата). Имена
файлов/классов в этом тикете: партия товара внутри агрегата называется `InventoryLot` (не
`InventoryBatch`) — намеренное расхождение с именем таблицы БД, чтобы визуально не путать с двумя
другими сущностями с похожим названием (ADR-уровня решение этого тикета, зафиксировать в JSDoc
класса).

Порты `Clock`/`IdGenerator` — из `10-domain-model.md` §«Правила домена», уже определены EP-01
(`packages/domain-kernel` или `apps/api/src/common/ports/` — уточнить фактическое расположение по
факту готовности EP-01, использовать существующий порт, не создавать новый).

## Что сделать

1. `pharmacy-inventory.entity.ts`: класс `PharmacyInventory` — приватный конструктор, фабрики
   `PharmacyInventory.create(pharmacyId: PharmacyId, medicineId: MedicineId): PharmacyInventory` и
   `PharmacyInventory.restore(snapshot): PharmacyInventory` (без валидации инвариантов повторно —
   restore доверяет БД).
2. Приватное поле `lots: InventoryLot[]` (VO/дочерняя сущность: `batchNumber`, `priceDiram: Money`,
   `quantity: number`, `expiryDate: ExpiryDate`, `lastSyncedAt: Date`).
3. Геттер `get stockQuantity(): number` — `Σ(lot.quantity)` для `lot.quantity > 0 AND
   lot.expiryDate.isAfter(today)` (SRS-DOM-019), `today` приходит параметром метода (домен не читает
   часы сам, `Clock`-порт вызывается в application).
4. Метод `getFefoLot(today: Date): InventoryLot | null` — партия с минимальным `expiryDate` среди
   `quantity > 0 AND expiryDate > today`, используется для `displayPrice`/`displayExpiryDate`
   (SRS-DOM-020).
5. `applyDelta(lotUpsert: { batchNumber, priceDiram, quantity, expiryDate, syncTimestamp: Date }):
   { applied: boolean; reason?: 'stale' }` — ищет партию по `batchNumber`; если
   `syncTimestamp <= existingLot.lastSyncedAt` → `{ applied: false, reason: 'stale' }`, иначе
   создаёт/обновляет партию, возвращает `{ applied: true }` (SRS-DOM-022). Бросает `InvalidPriceError`
   при `priceDiram <= 0 && quantity > 0` (SRS-DOM-024).
6. `applyDelete(batchNumber: string): void` — партия с этим `batchNumber` получает `quantity = 0`
   (не удаляется физически из агрегата — репозиторий решает вопрос физического UPDATE vs DELETE
   строки при персистенции, домен просто обнуляет).
7. `reserveForOrder(qty: number, today: Date): void` — уменьшает `quantity` партий по FEFO-порядку
   (сначала партии с ближайшим сроком годности среди непросроченных); бросает
   `InsufficientStockError`, если суммарного непросроченного `stockQuantity` не хватает
   (SRS-DOM-021).
8. `releaseReservation(qty: number, lotId: string): void` — возврат зарезервированного количества в
   конкретную партию (для отмены заказа — используется другими модулями через фасад, здесь только
   метод сущности).
9. `restock(quantity: number, reason: string, sourceOrderId: string): void` — только аддитивная
   (`quantity > 0`, иначе `InvalidRestockQuantityError`), идемпотентна по `sourceOrderId` (агрегат
   хранит `Set<string>` применённых `sourceOrderId` в приватном поле `appliedRestockOrderIds` —
   повторный вызов с тем же `sourceOrderId` — no-op, SRS-DOM-023).
10. Ошибки — `apps/api/src/modules/inventory/domain/errors/inventory.errors.ts` (см. DTJ-145,
    зависимость по файлу, не по коду — писать в этом тикете класс `InvalidPriceError` только если
    DTJ-145 ещё не создал файл; при конфликте — не переписывать, дополнять).

## Критерии приёмки

1. **Given** агрегат с двумя партиями (A: `qty=5, expiry=+10д`, B: `qty=3, expiry=+30д`), **When**
   вызывается `stockQuantity`, **Then** возвращается `8` (сумма непросроченных).
2. **Given** та же пара партий, **When** вызывается `getFefoLot(today)`, **Then** возвращается
   партия A (ближайший срок), даже если её `priceDiram` выше партии B.
3. **Given** партия с `lastSyncedAt = T2`, **When** `applyDelta({ syncTimestamp: T1 })` с `T1 < T2`,
   **Then** возвращается `{ applied: false, reason: 'stale' }`, состояние партии НЕ меняется —
   негативный сценарий, точное соответствие SRS-DOM-022/TC-DOM-037.
4. **Given** `stockQuantity = 5` (после исключения просроченных), **When**
   `reserveForOrder(6, today)`, **Then** бросается `InsufficientStockError`, состояние агрегата не
   меняется (транзакционность метода — либо применяется целиком, либо не применяется вовсе).
5. **Given** `restock(10, 'return', orderId='O1')` уже применён, **When** `restock(10, 'return',
   orderId='O1')` вызывается повторно, **Then** количество увеличивается только один раз (идемпотент
   по `sourceOrderId`), не удваивается.

## Тест-план

Unit (`pharmacy-inventory.entity.spec.ts`, БЕЗ БД/фреймворка — чистый домен):
- `create() устанавливает пустой список партий`
- `stockQuantity суммирует только непросроченные партии с положительным количеством`
- `stockQuantity исключает партию с quantity=0`
- `getFefoLot возвращает партию с минимальным expiryDate среди валидных`
- `getFefoLot возвращает null, если все партии просрочены или обнулены`
- `applyDelta создаёт новую партию при первом upsert`
- `applyDelta обновляет существующую партию по batchNumber при более новом syncTimestamp`
- `applyDelta отклоняет устаревшую строку (stale), не меняя state`
- `applyDelta бросает InvalidPriceError при priceDiram<=0 и quantity>0`
- `applyDelete обнуляет quantity партии, не удаляя её из коллекции`
- `reserveForOrder списывает по FEFO-порядку среди нескольких партий`
- `reserveForOrder бросает InsufficientStockError при нехватке непросроченного остатка`
- `restock идемпотентен по sourceOrderId`
- `restock бросает InvalidRestockQuantityError при quantity<=0`

сдачей. Интеграционные/E2E тесты не нужны — чистый домен без БД.

- Терминологическая коллизия трёх похожих имён (`InventoryLot` в агрегате / `InventoryBatchUpsertRow`
  VO команды DTJ-145 / `InventorySyncBatch` агрегат состояния запроса DTJ-144) — реальный риск
  путаницы у следующего разработчика. Смягчение — явный комментарий-глоссарий в начале файла.
  Если ревью решит, что тройное имя избыточно запутывает, допустимо переименовать при условии
  единообразного применения во ВСЕХ тикетах, ссылающихся на этот класс (потребует правки README).
- `reserveForOrder`/`releaseReservation` вызываются модулем `orders` (EP-09) через фасад — сигнатура
  метода должна быть согласована на старте, иначе EP-09 заблокирован на интеграции; зафиксировать
  сигнатуру в `InventoryFacade` (DTJ-140) как можно раньше.
