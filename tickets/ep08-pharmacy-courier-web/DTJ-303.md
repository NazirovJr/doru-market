## Задача

Когда фармацевт физически не может укомплектовать позицию (нет на полке, испорчена, истёк срок и нет
замены), терминал обязан дать явный путь пометить позицию проблемной, вместо того чтобы сборка зависала
без объяснения. Это предпосылка для частичной сборки (DTJ-304) — без явного `report-issue` невозможно
узнать, какие позиции требуют согласия клиента на изменённый состав заказа.

## Технический контекст

`apps/api/src/modules/orders/application/pharmacy-terminal/report-item-issue.use-case.ts`. Этот файл
разделяет `pharmacy-terminal-items.controller.ts` с DTJ-302 (тот же ресурс `/items/:itemId`, другой
метод/маршрут) — при слиянии веток решается rebase на общий файл контроллера, не блокирует параллельную
разработку (оба use case независимы). Использует `InventoryFacade` (тот же порт, что и DTJ-302).

## Что сделать

1. `POST /api/v1/orders/:id/items/:itemId/report-issue`, тело
   `{ reason: 'out_of_stock' | 'expired_on_shelf' | 'damaged_packaging', note?: string }`.
   `Idempotency-Key` обязателен.
2. `ReportItemIssueUseCase.execute()`: требует `orderItem.fulfillmentStatus === 'pending'` (нельзя
   пожаловаться на уже отсканированную позицию) — иначе `422 BUSINESS_RULE_VIOLATION`.
3. Успех: `orderItem.fulfillmentStatus = 'unavailable'`, `itemIssueReason = reason`.
4. Given `reason === 'out_of_stock'`, дополнительно вызвать `InventoryFacade.reconcileZeroStock(medicineId,
   batchId)` (существующая инфраструктурная операция восстановления учёта — расхождение уходит в лог
   ручной сверки, НЕ блокирует ответ пользователю — вызов fire-and-forget через `unitOfWork`/событие после
   коммита транзакции, не синхронно внутри неё).
5. Ответ `200 OK` с обновлённой позицией.
6. RBAC: `pharmacist` (own pharmacy).

## Критерии приёмки

Given позиция `pending`, When `report-issue { reason: 'out_of_stock' }`, Then `200 OK`,
`fulfillmentStatus='unavailable'`, `itemIssueReason='out_of_stock'`, вызван
`InventoryFacade.reconcileZeroStock` (TC-PHT-008).

Given позиция уже `scanned_ok`, When `report-issue` вызван для неё, Then `422 BUSINESS_RULE_VIOLATION`
(негативный тест — нельзя пожаловаться на уже подтверждённую позицию).

Given товар физически отсутствует, хотя `stock_quantity > 0` (расхождение учёта и полки), When
`report-issue(reason='out_of_stock')`, Then позиция помечается `unavailable` БЕЗ попытки подобрать другой
штрихкод — `reconcileZeroStock` асинхронно сигнализирует расхождение (SRS-PHT-071).

## Тест-план

Unit: `ReportItemIssueUseCase` — три допустимых `reason`, precondition-guard на `fulfillmentStatus`,
вызов `reconcileZeroStock` только при `out_of_stock` (мок-проверка отсутствия вызова для двух других
причин).
Интеграционные: TC-PHT-008, precondition-негатив (позиция не `pending`), `Idempotency-Key` повтор не
дублирует переход в `unavailable`/повторный вызов `reconcileZeroStock`.
Порог покрытия application — 90%.
