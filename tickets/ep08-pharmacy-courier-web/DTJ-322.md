## Задача

Стоимость доставки — не константа: она зависит от зоны, дистанции, времени суток и минимальной суммы
заказа. Этот тикет доводит `DeliveryFacade.calculateDeliveryFee` (объявленный заглушкой в DTJ-314) до
полной реализации и даёт диспетчеру/`super_admin` управление тарифами и зонами через REST — иначе любое
изменение цены доставки требовало бы деплоя.

## Технический контекст

Завершает контракт `DeliveryFacade` из DTJ-314 — этот тикет РЕАЛИЗУЕТ метод, чья сигнатура уже
стабильна и используется чекаутом модуля `orders` (EP-09) с волны 6. `PUT` на `delivery-pricing-rules` —
паттерн «история ставок, не перезапись» (та же механика, что `tenant_courier_payout_rules`/
`commission_rates`, уже существует в других модулях — переиспользовать идею, не изобретать заново).

## Что сделать

1. `DeliveryFacade.calculateDeliveryFee(pharmacyGeoPoint, customerGeoPoint, tenantId, itemsTotalDiram,
   atMoment)` — заменить заглушку DTJ-314 на полную реализацию (SRS-DELIV-048):
   1. Найти покрывающую `delivery_zones` строку (`ST_DWithin(center_geo_point, customerGeoPoint,
      radius_km*1000)`, приоритет — наименьший `priority`, при равенстве — наименьший `radius_km`); если
      ни одна не покрывает — `DeliveryZoneNotCoveredError`.
   2. Найти действующую `delivery_pricing_rules` строку для `(tenantId, zoneId, atMoment ∈
      [effective_from, effective_to))`; при отсутствии зональной — строка `zone_id IS NULL` (дефолт
      тенанта); при отсутствии тенантной — глобальная (`tenant_id IS NULL`).
   3. Given `itemsTotalDiram < rule.minOrderAmountDiram`, Then `DeliveryMinOrderNotMetError`.
   4. `distanceKm = pharmacyGeoPoint.distanceTo(customerGeoPoint) / 1000` (существующий VO-метод).
   5. `feeDiram = rule.baseRateDiram + round(rule.ratePerKmDiram × distanceKm)`.
   6. Given `atMoment` (через `ClockPort.nowInTenantTz()`, НЕ в domain) попадает в
      `[nightTariffStartTime, nightTariffEndTime)` (диапазон через полночь обрабатывается явно —
      `start > end` означает «через полночь»), Then `feeDiram += rule.nightTariffExtraDiram`.
   7. Given `rule.freeDeliveryThresholdDiram IS NOT NULL AND itemsTotalDiram >=
      rule.freeDeliveryThresholdDiram`, Then `feeDiram = 0` (бесплатная доставка перекрывает ночной
      тариф).
   8. Результат — `Money` (целые дирамы); конвертация в `TJS` — на границе `infrastructure` модуля
      `orders` (не здесь).
2. Given `atMoment` не передан, Then use case ОБЯЗАН получить его через `ClockPort.now()`, НИКОГДА
   `new Date()` (`02` §2.6).
3. `GET/PUT /api/v1/delivery-pricing-rules` — тенант резолвится из `TenantContext` (не из пути,
   SRS-API-041), `super_admin` может явно указать чужой `X-Tenant-Slug` (SRS-API-044, логируется
   `crossTenantOverride=true`). `PUT` создаёт НОВУЮ строку с `effective_from=now()` и закрывает
   предыдущую (`effective_to=now()`) — история ставок не перезаписывается.
4. `GET/POST/PATCH /api/v1/delivery-zones` — CRUD зон, роль `super_admin` (глобальные) /
   `pharmacy_admin` (только для своего тенанта, если применимо по бизнес-правилу — уточнить у продукта,
   является ли управление зонами платформенной или тенантной операцией; по умолчанию реализовать как
   `super_admin`-only, т.к. `04-SCOPE-DECISION` не даёт явного делегирования тенанту, ASSUMPTION,
   зафиксировать в PR).
5. Given отсутствие покрывающей зоны для тенанта, где `courierSourcingMode` требует зональности, Then
   деградация к конфигурации «вся территория» — `delivery_zones` с `radius_km` ASSUMPTION 30 км от
   единственной аптеки тенанта, если явных зон не заведено (НЕ блокировка чекаута автоматически — это
   fallback-поведение, реализуемое как часть операционного онбординга тенанта, не runtime-логики
   `calculateDeliveryFee` — зафиксировать разграничение ответственности в PR).

## Критерии приёмки

Given координаты клиента вне всех `delivery_zones` тенанта, When `calculateDeliveryFee(...)`, Then
`DeliveryZoneNotCoveredError` → чекаут блокирован кодом `422 DELIVERY_ZONE_NOT_COVERED` на стороне
вызывающего модуля `orders` (TC-DELIV-023).

Given `itemsTotal=3000` diram, `minOrderAmountDiram=5000`, When `calculateDeliveryFee(...)`, Then
`DeliveryMinOrderNotMetError` → `422 DELIVERY_MIN_ORDER_NOT_MET` (негативный тест, TC-DELIV-024).

Given `itemsTotal=60000`, `freeDeliveryThresholdDiram=50000`, ночное время, `nightTariffExtra=1000`, When
`calculateDeliveryFee(...)`, Then `feeDiram=0` (бесплатная доставка перекрывает ночной тариф,
TC-DELIV-025).

Given `baseRate=1000, ratePerKm=200`, дистанция `3.4км`, вне ночного окна, When
`calculateDeliveryFee(...)`, Then `feeDiram = 1000 + round(200×3.4) = 1680` (TC-DELIV-026).

## Тест-план

Unit: `CalculateDeliveryFeeUseCase` — все 8 шагов формулы отдельными кейсами, включая диапазон через
полночь (`start=22:00, end=06:00`, момент `23:30` попадает, момент `10:00` — нет), отсутствие зональной
строки → фолбэк на дефолт тенанта → фолбэк на глобальную.
Интеграционные: TC-DELIV-023..026, `PUT delivery-pricing-rules` создаёт новую строку и закрывает
предыдущую (история сохранена, не перезаписана), `X-Tenant-Slug` override логируется в `audit_log`.
Порог покрытия application — 90%.

## Риски и подводные камни

Заглушка `calculateDeliveryFee` из DTJ-314 уже используется чекаутом EP-09 с волны 6 — замена на полную
реализацию должна быть backward-compatible по сигнатуре (не менять контракт метода), иначе ломает уже
интегрированный код чекаута; координировать момент замены (мердж этого тикета) с владельцем EP-09, чтобы
не получить регрессию стоимости доставки в уже прошедших ручную проверку сценариях. Делегирование
управления зонами `pharmacy_admin` — не подтверждено явно в SRS (ASSUMPTION в этом тикете) — уточнить у
продукта до реализации CRUD-эндпоинта зон, чтобы не создать RBAC-дыру или, наоборот, излишнее
ограничение, которое придётся снимать отдельным тикетом.
