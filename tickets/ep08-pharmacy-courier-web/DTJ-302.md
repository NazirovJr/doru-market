## Задача

Ядро физической сборки: фармацевт сканирует (камерой в R2, вручную с клавиатуры уже в R1) штрихкод
коробки и система подтверждает, что это правильный препарат, правильная партия (не просроченная) и
позиция ещё не отсканирована. Без этого шага заказ физически не может считаться собранным — это самый
частый вызов терминала за время одной сборки (по одному на каждую позицию заказа).

## Технический контекст

`apps/api/src/modules/orders/application/pharmacy-terminal/scan-order-item.use-case.ts` — оркестрирует
уже существующие доменные VO/сервисы, сам НЕ принимает решений (`02` §3.2): `Barcode.parse()`
(SRS-DOM-074..076, существующий VO), `CatalogFacade.resolveMedicineByComposite()` (существующий публичный
метод фасада каталога — импортируется ТОЛЬКО через `CatalogFacade`, не напрямую из `modules/catalog/domain`,
`02` §1.2), `InventoryFacade.releaseReservation()`/`reserveForOrder()` (существующие методы, инвентарь —
чужой модуль, доступ ТОЛЬКО через порт/фасад — добавить `InventoryFacadePort` в `application/ports`, если
такого порта ещё нет в контексте `orders` на момент реализации; если уже есть от EP-09 — переиспользовать,
не дублировать). Ошибки и VO из DTJ-300.

## Что сделать

1. `POST /api/v1/orders/:id/items/:itemId/scan`, тело
   `{ rawBarcode: string, manualEntry: boolean, scannedBatchNumber?: string, scannedExpiryDate?: string }`.
   `Idempotency-Key` обязателен (SRS-PHT-039 — офлайн-очередь клиента может продублировать один и тот же
   скан).
2. Пайплайн валидации `ScanOrderItemUseCase.execute()`, строго по шагам (SRS-PHT-011..016):
   а. `Barcode.parse(rawBarcode)` — невалидный EAN-13 (контрольная цифра/длина) НЕ ошибка, трактуется как
      `format='internal_sku'` (D-06), пайплайн продолжается.
   б. `CatalogFacade.resolveMedicineByComposite(barcode, tenantId)` → `resolvedMedicineId`.
   в. Given `resolvedMedicineId !== orderItem.medicineId`, Then `404 ORDER_ITEM_NOT_FOUND`
      (`ItemNotInOrderError`) — позиция остаётся `pending`, повторная попытка разрешена без ограничений
      (это НЕ «использованная» попытка, в отличие от г).
   г. Given `orderItem.fulfillmentStatus !== 'pending'`, Then `409 ITEM_ALREADY_SCANNED`
      (`ItemAlreadyScannedError`).
   д. Проверка партии: given `scannedBatchNumber` присутствует И отличается от `orderItem.inventoryBatchId`
      — вызвать `InventoryFacade.releaseReservation(oldBatchId, qty)` +
      `InventoryFacade.reserveForOrder(newBatchId, qty)`, ТОЛЬКО если `newBatch.pharmacyInventoryId ===
      orderItem.pharmacyInventoryId` (та же аптека/товар) И `newBatch.expiryDate.isSellable(today)`.
      Given партия просрочена → `422 EXPIRED_STOCK` (существующий `ExpiredStockError`, переиспользуется).
      Given недостаточно `quantity` в новой партии → `422 BATCH_NOT_AVAILABLE`
      (`BatchNotAvailableForSubstitutionError`). Given `scannedBatchNumber` отсутствует — валидация партии
      пропускается, используется изначально зарезервированная по FEFO партия без замены.
   е. Успех: `orderItem.fulfillmentStatus = 'scanned_ok'`, `scannedBatchId`, `scannedAt = ClockPort.now()`
      (порт, НЕ `new Date()`, `02` §2.6), `scannedBy = actor.userId`. Given `manualEntry: true` —
      дополнительно пишет `order_items.scan_method = 'manual'`; иначе `'camera'`.
3. Ручной ввод — НЕ отдельный эндпоинт, а тот же пайплайн с `manualEntry: true` (DRY, SRS-PHT-016).
4. `PharmacyTerminalItemsController` — маппинг доменных ошибок на HTTP-коды строго по таблице выше,
   ответ `200 OK` с обновлённой позицией на успех.
5. RBAC: `pharmacist` (own pharmacy) — единственная допустимая роль на этот эндпоинт.

## Критерии приёмки

Given позиция заказа — Парацетамол 500мг, When `scan` со штрихкодом Ибупрофена, Then
`404 ORDER_ITEM_NOT_FOUND`, позиция остаётся `pending` (SRS-PHT-012/TC-PHT-004).

Given позиция уже `scanned_ok`, When повторный `scan` той же позиции (тем же или другим валидным
штрихкодом), Then `409 ITEM_ALREADY_SCANNED` (SRS-PHT-013/TC-PHT-005) — негативный сценарий, партия НЕ
переоформляется повторно.

Given `scannedBatchNumber` ссылается на партию с `expiry_date = today - 1 день`, When `scan`, Then
`422 EXPIRED_STOCK`, позиция НЕ переходит в `scanned_ok`, резерв старой партии НЕ освобождён (транзакция
атомарна — TC-PHT-006).

Given `scannedBatchNumber` — валидная партия того же товара/аптеки с достаточным `quantity`, When `scan`,
Then `200 OK`, `scannedBatchId` обновлён, старая партия — `releaseReservation`, новая —
`reserveForOrder` (TC-PHT-007).

Given новая партия того же товара, но ДРУГОЙ аптеки (`pharmacy_inventory_id` не совпадает), When `scan` с
чужой партией, Then `422 BATCH_NOT_AVAILABLE` — замена между аптеками запрещена (негативный тест,
TC-PHT-029).

## Тест-план

Unit: `ScanOrderItemUseCase` с замоканными `CatalogFacade`/`InventoryFacade`/`ClockPort` — каждая ветвь
пайплайна (а-е) отдельным кейсом, включая `internal_sku`-путь (TC-PHT-028, невалидный EAN-13, но резолвится
в верный `medicine_id` → успех).
Интеграционные: TC-PHT-004..007, TC-PHT-029, полный сценарий scan→scan (второй с другой валидной партией
после report-issue не применим здесь — см. DTJ-303), проверка `Idempotency-Key` на этом эндпоинте (повтор
с тем же ключом и телом не выполняет use case дважды, партия не списывается дважды).
Порог покрытия application — 90%.
