## Задача

Финальный шаг сборки: фармацевт подтверждает, что сейф-пакет опечатан, все позиции разрешены, и система
генерирует 4-значный OTP вручения, которым позже курьер подтвердит доставку клиенту. Этот момент —
триггер создания `DeliveryAssignment` в модуле `delivery` (`OrderPickedUpEvent`, EP-13) — граница между
работой аптеки и работой курьера.

## Технический контекст

`CompletePickingUseCase` в `apps/api/src/modules/orders/application/pharmacy-terminal/**`. Вызывает
существующий `order.markPickedUp(handoverOtp)` (SRS-DOM-094), генерацию OTP — ИСКЛЮЧИТЕЛЬНО через
`OtpGeneratorPort` (существующий порт, SRS-DOM-081, НЕ `Math.random()`). Публикует `OrderPickedUpEvent`
(существующее событие) — модуль `delivery` (EP-13) подписан на него для создания `DeliveryAssignment`;
это межмодульная граница через `outbox`, этот тикет НЕ вызывает `delivery` напрямую (`02` §1.2).

## Что сделать

1. `POST /api/v1/orders/:id/complete-picking`, тело `{ sealConfirmed: true }`. `Idempotency-Key`
   обязателен. Given `sealConfirmed !== true`, Then `400 SEAL_CONFIRMATION_REQUIRED`
   (`SealConfirmationRequiredError`) — аудит-запись фиксирует `actor.userId` + значение `sealConfirmed`
   на КАЖДУЮ попытку, включая отклонённую (аудит финансово/операционно значимого действия).
2. Предусловия `CompletePickingUseCase` (проверяются ДО `order.markPickedUp()`):
   а. Все `order_items.fulfillmentStatus ∈ {'scanned_ok', 'unavailable'}` — иначе
      `422 BUSINESS_RULE_VIOLATION` (`details.unresolvedItemIds`).
   б. Given ≥1 позиция `unavailable`, ОБЯЗАН существовать `order_partial_fulfillment_requests` со
      `status ∈ {'confirmed', 'auto_confirmed_timeout'}` для ЭТОГО заказа — иначе
      `409 PARTIAL_FULFILLMENT_PENDING` (`PendingCustomerConfirmationError`).
   в. Повторная проверка: ни одна выбранная партия (`scannedBatchId` каждой `scanned_ok`-позиции) НЕ
      просрочена НА МОМЕНТ вызова (защита от гонки «партия истекла за минуты ожидания подтверждения
      клиента») — переиспользует существующий `ExpiredStockError`.
3. Успех: `order.markPickedUp(handoverOtp)` — OTP генерируется через `OtpGeneratorPort`
   (`purpose='delivery_handover'`, TTL 15 минут — SRS-DOM-080, уже определён). Публикует
   `OrderPickedUpEvent(orderId, handoverOtpIssuedAt, sealedBagConfirmed)`.
4. Ответ `200 OK`: `{ data: { orderId, status: 'picked_up', handoverOtp: { code, expiresAt,
   purpose: 'delivery_handover' } } }` — код возвращается СРАЗУ в ответе, без отдельного `GET`.
5. RBAC: `pharmacist` (own pharmacy).

## Критерии приёмки

Given все позиции решены корректно, When `complete-picking(sealConfirmed=false)`, Then
`400 SEAL_CONFIRMATION_REQUIRED`, заказ НЕ переходит в `picked_up` (негативный тест, TC-PHT-015).

Given все позиции `scanned_ok`, `sealConfirmed=true`, When `complete-picking`, Then `200 OK`,
`status='picked_up'`, `handoverOtp.code` — ровно 4 цифры, `expiresAt = now + 15 минут` (TC-PHT-016).

Given 1 позиция `unavailable` БЕЗ связанного `order_partial_fulfillment_requests` (пропущен шаг
DTJ-304), When `complete-picking(sealConfirmed=true)`, Then `409 PARTIAL_FULFILLMENT_PENDING`
(TC-PHT-014).

## Тест-план

Unit: `CompletePickingUseCase` — три precondition-ветки (а/б/в) каждая отдельным кейсом с моком
`ClockPort`/`OtpGeneratorPort`; проверка, что `OtpGeneratorPort.generate()` вызывается РОВНО один раз на
успешный вызов (не в `domain`, а через порт — недетерминированность изолирована).
Интеграционные: TC-PHT-014, TC-PHT-015, TC-PHT-016, гонка «партия истекла между сканом и подтверждением
клиента» — партия помечается просроченной МЕЖДУ `scan` и `complete-picking`, ожидается `422 EXPIRED_STOCK`
на `complete-picking`, а не тихий проход.
Порог покрытия application — 90%.
