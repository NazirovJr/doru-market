## Задача

После старта смены курьер должен увидеть текущий оффер доставки (полноэкранная карточка с обратным
отсчётом) и иметь возможность принять/отклонить его, а также самостоятельно выбрать назначение из
открытого пула, если цепочка последовательных офферов до него не дошла. Это точка входа в конкретную
доставку — без неё курьер видит только абстрактную «смену начата», но не может фактически начать
работать.

## Технический контекст

`apps/courier/src/features/{offers,pool}/**` — маршруты `/offers`, `/pool`. Использует
`GET /delivery-offers?status=pending`, `POST .../accept`, `POST .../decline` (DTJ-315),
`GET /delivery-assignments/available-pool`, `POST .../claim` (DTJ-316). WS-подписка на `courier:{id}`
(DTJ-323) для `delivery.offer_created`/`delivery.offer_expired`.

## Что сделать

1. `OffersPage` (`/offers`) — состояние «ожидание оффера» (пусто, информационный текст) / «оффер
   активен» (полноэкранная карточка: дистанция, состав заказа БЕЗ адреса клиента — `pharmacy.name`/
   `addressText`, `orderSummary.itemsCount`/`requiresColdChain`/`paymentMethod`/
   `estimatedDeliveryFeeDiram`, `CountdownTimer` до `expiresAt`, кнопки «Принять»/«Отклонить») / «истёк»
   (авто-переход обратно в «ожидание» по получении WS `delivery.offer_expired` или локальному истечению
   таймера — сверяется с сервером, не полагается только на клиентские часы).
2. Кнопка «Принять» → `POST /delivery-offers/:id/accept`. Given `409 OFFER_EXPIRED` (гонка — истёк между
   отображением и кликом), Then сообщение «Оффер истёк» + автоматический рефетч `GET /delivery-offers`.
   Given `409 OFFER_ALREADY_RESPONDED`, Then аналогичная обработка. Успех → редирект на `/active/:id`.
3. Кнопка «Отклонить» → модалка причины (опционально) → `POST /delivery-offers/:id/decline`. Успех →
   возврат в состояние «ожидание оффера», следующий оффер (если есть) приходит через WS.
4. WS-подписка: `delivery.offer_created` → показать новую карточку оффера БЕЗ рефетча всей страницы;
   `delivery.offer_expired` → если это ТЕКУЩИЙ отображаемый оффер, вернуться в состояние ожидания.
5. `PoolPage` (`/pool`) — список доступных назначений по дистанции (`GET
   .../available-pool?radiusKm=5&sort=distance:asc`), карточка на каждое (тот же урезанный вид, что и
   оффер), кнопка «Взять» → `POST .../claim`. Given `409 ASSIGNMENT_ALREADY_CLAIMED` (гонка — другой
   курьер успел раньше), Then сообщение «Уже взято другим курьером», карточка удаляется из списка,
   список остаётся доступным для выбора другого назначения (не блокирующая ошибка).
6. Доступ к `/pool` — из навигации/баннера на `OffersPage` при пустом состоянии («Нет текущих офферов —
   посмотреть доступный пул»).

## Критерии приёмки

Given оффер активен, обратный отсчёт идёт, When нажата «Принять» ДО истечения, Then запрос отправлен,
успешный ответ → редирект на `/active/:id`.

Given оффер истёк МЕЖДУ отображением и кликом (сервер уже пометил `expired`), When нажата «Принять»,
Then `409 OFFER_EXPIRED`, показывается сообщение, список офферов автоматически обновляется (негативный
сценарий гонки).

Given два устройства одного курьера (или два курьера — для пула) одновременно нажимают «Взять»/«Принять»
на одно назначение, When второй запрос приходит ПОСЛЕ первого успешного, Then второй получает `409
ASSIGNMENT_ALREADY_CLAIMED`/`OFFER_ALREADY_RESPONDED`, UI показывает понятное сообщение, НЕ технический
код ошибки напрямую.

## Тест-план

Unit: `model` — переходы состояний офферной карточки (ожидание→активен→истёк/принят/отклонён), логика
локального countdown vs серверная сверка.
Компонентные: `OffersPage` — happy path accept/decline, ветки `409`; `PoolPage` — список, `claim`
успех/конфликт.
E2E: полный путь «начать смену → получить оффер (мок WS) → принять → редирект на активную доставку» —
основа для CUJ-4' в EP-19.
Порог покрытия — 70%.

## Риски и подводные камни

Обратный отсчёт до `expiresAt` — чисто клиентский таймер, подверженный рассинхронизации часов
устройства; сервер — источник истины (ответ `409 OFFER_EXPIRED` при клике после реального истечения) —
не пытаться синхронизировать точное серверное время дополнительным запросом ради этого таймера
(избыточная сложность для 45-секундного окна, `02` C15) — просто корректно обрабатывать `409` как
штатный, а не аварийный сценарий.
