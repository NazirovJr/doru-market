## Задача

Не каждая доставка доходит до `delivered` по прямому пути: клиент может быть недоступен, адрес — не
найден, клиент может отказаться на пороге, а заказ может быть форс-отменён администратором, пока курьер
уже в пути. Без явной обработки этих веток курьер физически остаётся с товаром на руках и без понятного
следующего шага, а система — с назначением, зависшим в нетерминальном статусе навсегда.

## Технический контекст

`apps/api/src/modules/delivery/application/**`. `OrderForceCancelledHandler` подписывается на
существующие `OrderCancelledEvent`/`OrderAutoCancelledEvent` (публикуются модулем `orders` при
`AdminForceCancelOrderUseCase`, вне этого модуля) — межмодульная граница через `outbox`. Публикует
`DeliveryFailedEvent`/`OrderRefusedAtDoorEvent`, потребляемые модулем `returns` (EP-11) для создания
`OrderReturn` — этот тикет НЕ создаёт `OrderReturn` сам, только публикует событие.

## Что сделать

1. `POST /api/v1/delivery-assignments/:id/report-issue { issueType: 'customer_unreachable' |
   'address_not_found' | 'other', notes? }` — только `en_route_to_customer`. Инкрементирует
   `contact_attempts_count`, `last_contact_attempt_at=now()`. Given `issueType='address_not_found'` —
   ЭТО НЕ увеличивает `contact_attempts_count` (тот считает попытки связаться с КЛИЕНТОМ, не попытки
   найти дом) — событие уходит в `platform:ops` НЕМЕДЛЕННО, не ждёт порога попыток (SRS-DELIV-043).
2. `POST /api/v1/delivery-assignments/:id/mark-failed { reason: 'customer_unreachable' }`. Given
   `issueType='customer_unreachable'` И `contact_attempts_count >= 3` (ASSUMPTION
   `DELIVERY_MAX_CONTACT_ATTEMPTS`) И `now() - first_attempt >= 30 минут` (ASSUMPTION
   `DELIVERY_CONTACT_WINDOW_MINUTES`), Then разрешён переход `en_route_to_customer → delivery_failed`
   (SRS-DOM-143), публикует `DeliveryFailedEvent(deliveryAssignmentId, orderId, reason,
   contactAttemptsCount)` → `returns` создаёт `OrderReturn(reason='undeliverable')` (граница события, не
   эта команда). Ниже порога — `422 CONTACT_ATTEMPTS_INSUFFICIENT`.
3. `POST /api/v1/delivery-assignments/:id/refuse-at-door { reason: 'refused_at_door', notes? }` — клиент
   отказался принять на пороге. Только `en_route_to_customer`. Переход `en_route_to_customer →
   delivery_failed` НЕ используется — вместо этого публикует `OrderRefusedAtDoorEvent` (`orders`
   переводит заказ, `returns` создаёт `OrderReturn(reason='refused_at_door')` — SRS-DOM-096 уже определяет
   эту ветвь на уровне `Order`, этот эндпоинт — триггер со стороны курьера).
4. `OrderForceCancelledHandler`: given форс-отмена заказа (`AdminForceCancelOrderUseCase`, вне этого
   модуля) И у заказа есть активное (нетерминальное) `DeliveryAssignment`, Then перевести
   `DeliveryAssignment → delivery_failed` с `failed_reason='order_force_cancelled'` (переиспользует
   терминальный статус — отдельного статуса `cancelled` НЕТ и не вводится), остановить геотрекинг,
   освободить курьера (нагрузка уменьшается немедленно для алгоритма назначения следующих заказов).
5. `CourierSilentWatchdogProcessor` — фоновая job (переиспользует BullMQ-инфраструктуру `delivery-offer-
   timeout`, отдельная периодическая проверка, не delayed job на конкретный `assignmentId`): given нет
   `courier-locations` пингов `> COURIER_LOCATION_STALE_MINUTES` (15) ПРИ активном назначении, Then
   публикует `SlaBreachedEvent(entityType='courier_silent')` в `platform:ops`/`chain:{chainId}` — ТОЛЬКО
   уведомление, БЕЗ авто-действий (товар физически у курьера, принудительный `reassign` не возвращает
   товар — решение всегда за человеком).

## Критерии приёмки

Given `issueType='customer_unreachable'`, `contact_attempts_count=1`, When `POST .../mark-failed`, Then
`422 CONTACT_ATTEMPTS_INSUFFICIENT` (негативный тест, TC-DELIV-014).

Given `contact_attempts_count=3`, окно 30 минут истекло, When `POST .../mark-failed`, Then `200`,
`status='delivery_failed'`, `DeliveryFailedEvent` опубликован (TC-DELIV-015).

Given `en_route_to_customer`, When `POST .../refuse-at-door`, Then `OrderRefusedAtDoorEvent` опубликован,
проверка на границе события (интеграционный тест на факт публикации, не на реализацию `returns`)
(TC-DELIV-016).

Given `picked_up` (эквивалент активного назначения курьера), `super_admin` вызывает форс-отмену заказа,
When `AdminForceCancelOrderUseCase → OrderCancelledEvent`, Then `DeliveryAssignment.status=
'delivery_failed'`, `failed_reason='order_force_cancelled'`, курьер освобождён
(`activeAssignmentsCount` -1 для него) (TC-DELIV-017).

## Тест-план

Unit: `ReportDeliveryIssueUseCase` — ветка `address_not_found` НЕ инкрементирует `contact_attempts_count`
(явный негативный тест на эту разницу); `MarkDeliveryFailedUseCase` — оба порога (попытки И окно времени)
проверяются независимо (4 комбинации: оба пройдены/один/другой/ни один); `OrderForceCancelledHandler` —
идемпотентность при повторной доставке события (уже `delivery_failed` — обработчик не падает).
Интеграционные: TC-DELIV-014..017, `CourierSilentWatchdogProcessor` — периодический запуск на тестовом
наборе назначений с разным «возрастом» последнего пинга.
Порог покрытия application — 90%.

## Риски и подводные камни

Частичный отказ на пороге (клиент принимает часть позиций) — СОЗНАТЕЛЬНО НЕ поддерживается в R1
(SRS-DELIV-068, схема `order_returns` не поддерживает возврат на уровне отдельных позиций) — курьер либо
убеждает клиента принять всё, либо весь заказ уходит через `refuse-at-door`; это задокументированное
ограничение, не баг этого тикета — НЕ пытаться реализовать частичный API для этого случая, это
территория модуля `returns` (EP-11) и открытый вопрос, зафиксированный в самом SRS-документе.
`AdminForceCancelOrderUseCase` — эндпоинт вне этого модуля (владеет `orders`/`admin`, EP-15/EP-09) —
свериться, что событие, на которое подписан обработчик, действительно публикуется этим use case на
момент интеграции, не полагаться только на спецификацию.
