## Задача

Курьер, клиент, аптека и диспетчер должны узнавать о каждом статусном переходе доставки мгновенно, а не
через ручное обновление страницы. Этот тикет подключает уже существующий WS-шлюз к семи событиям модуля
`delivery` в правильные комнаты — без него DTJ-315..319 функционально работают, но клиенты видят
изменения только после ручного REST-рефетча.

## Технический контекст

WS-инфраструктура (`/api/v1/realtime`, комнаты `courier:{id}`/`customer:{id}`/`pharmacy:{id}`/
`chain:{id}`/`platform:ops`, аутентификация, реконнект-протокол) уже существует (EP-01, `12-api-
conventions...md` §6). Этот тикет — только подписка на outbox-события DTJ-315/316/317/318 и публикация в
уже существующие комнаты, за ИСКЛЮЧЕНИЕМ `delivery.location_updated`, которая уже реализована в DTJ-319
(не через outbox — не дублировать здесь).

## Что сделать

1. Подключить обработчики outbox-событий → WS-кадры (таблица `25-module-courier-delivery.md` §A.7):
   `DeliveryOfferCreatedEvent` → `delivery.offer_created` в `courier:{courierId}`;
   `DeliveryOfferExpiredEvent` → `delivery.offer_expired` в `courier:{courierId}` (снять карточку из UI);
   `DeliveryEscalatedToPoolEvent` → `delivery.escalated_to_pool` в `platform:ops`, `chain:{chainId}`;
   внутренние переходы `DeliveryAssignment` (`assign`/`depart`/`depart-to-customer`, без отдельного
   доменного события верхнего уровня, маппятся из уже существующих доменных вызовов) →
   `delivery.departed_to_pharmacy`/`.picked_up_from_pharmacy`/`.departed_to_customer` в
   `customer:{customerId}`; `DeliveryFailedEvent` → `delivery.failed` в `customer:{customerId}`,
   `pharmacy:{pharmacyId}`, `platform:ops`; `OrderRefusedAtDoorEvent` → `delivery.refused_at_door` в
   `customer:{customerId}`, `pharmacy:{pharmacyId}`.
2. Задокументировать (комментарий модуля) обязательность REST catch-up (`GET
   /delivery-assignments/mine`) ДО повторной подписки на комнату `courier:{id}` после реконнекта
   (SRS-API-053/054) — правило уже установлено на уровне протокола, фиксируется применимость для ЭТОГО
   клиента.
3. Регрессионный тест на роутинг комнат: каждое из семи событий уходит РОВНО в заявленные комнаты, не
   шире и не уже (частая ошибка копипаста между похожими publisher-обработчиками — уже отмечена как риск
   в DTJ-308 для родственного модуля, тот же класс ошибки актуален здесь).

## Критерии приёмки

Given `DeliveryOfferCreatedEvent` опубликовано, When проверяется доставка, Then кадр `delivery.offer_created`
приходит ТОЛЬКО в `courier:{courierId}` конкретного адресата оффера, не всем подписанным курьерам.

Given `DeliveryFailedEvent` опубликовано, When проверяется доставка, Then кадр приходит В ТРИ комнаты
одновременно (`customer:{customerId}`, `pharmacy:{pharmacyId}`, `platform:ops`) — негативный тест на
недостающую комнату (легко забыть одну из трёх при реализации).

Given курьер реконнектится после разрыва WS, When клиент подписывается на `courier:{id}` СРАЗУ, минуя
`GET /delivery-assignments/mine`, Then это нарушение протокола документируется тестом-предупреждением
(проверка, что backend НЕ полагается на клиента для консистентности — сам факт пропуска REST catch-up не
может быть предотвращён сервером, но задокументирован как контракт для фронтенд-тикетов DTJ-327/328).

## Тест-план

Unit: маппинг «доменное событие → WS-тип → набор комнат» — таблица из семи строк, каждая — отдельный
кейс с мок-`RealtimeGateway`, проверяющий ТОЧНЫЙ набор комнат (не подмножество/надмножество).
Интеграционные: реальный WS-тестовый клиент подписывается на несколько комнат одновременно, эмулируется
публикация каждого события через outbox-воркер, проверяется получение корректного кадра каждым
подписанным клиентом и НЕполучение неподписанными.
Порог покрытия — 70% (presentation/infrastructure).

## Риски и подводные камни

`delivery.departed_to_pharmacy`/`.picked_up_from_pharmacy`/`.departed_to_customer` НЕ имеют отдельного
доменного события верхнего уровня (маппятся из уже существующих вызовов `depart()`/
`depart-to-customer()` в DTJ-317) — решить механику публикации (прямой вызов из use case после
успешного перехода, либо подписка на изменение поля `status` через триггер/интерцептор) на этапе
реализации; предпочтительно — явный вызов `RealtimeGateway.publish(...)` из соответствующего use case
DTJ-317 сразу после коммита транзакции, а не скрытая магия на уровне репозитория (прозрачность потока
управления, `02` C18 — функция без сюрпризов).
