## Задача

SLA сборки (7 минут по умолчанию, D-19) должен реально принуждаться, иначе он превращается в декларацию.
Этот тикет — два BullMQ-джоба, ставящиеся в момент `accept` (DTJ-301): мягкая эскалация операторам при
превышении 7 минут (без остановки сборки) и жёсткий автоматический отказ с полным рефандом при
превышении 7+5 минут, если сборка так и не завершена. Это единственный способ, которым платформа гарантирует,
что деньги клиента не «зависают» в escrow бесконечно из-за забытого заказа.

## Технический контекст

`SlaWatchdogProcessor` — BullMQ-обработчик (application+infrastructure слой, `job-обработчик` по
классификации SRS-PHT-002). Планируется `ScheduleSlaWatchdogUseCase`, вызываемым ИЗ `AcceptOrderUseCase`
(DTJ-301) сразу после старта `processing` — этот тикет добавляет вызов планирования в существующий
use case DTJ-301 (согласовать порядок мержа: DTJ-307 физически модифицирует файл, созданный DTJ-301,
через добавление одного вызова, не переписывает его).

## Что сделать

1. `ScheduleSlaWatchdogUseCase` — вызывается из `AcceptOrderUseCase.execute()` (DTJ-301) сразу после
   `startProcessing()`. Ставит ДВА BullMQ delayed job:
   а. Мягкий: `delay = tenant_settings.pickup_sla_minutes` (дефолт 7), `jobId = 'soft:' + orderId`.
   б. Жёсткий: `delay = pickup_sla_minutes + pickup_sla_buffer_minutes` (дефолт 7+5=12),
      `jobId = 'hard:' + orderId`.
2. Мягкий обработчик: given `order.status` всё ещё `'processing'` на момент срабатывания, Then
   публикует `SlaBreachedEvent(entityType='pharmacy_order', orderId)` → WS `ops.sla_breached` в комнату
   `platform:ops` (существующий маршрут, `12-api-conventions...md` §6.3). НЕ пересылается в
   `pharmacy:{id}` — терминал вычисляет просрочку локально по уже известному `sla_deadline_at`, не
   ждёт серверной команды.
3. Жёсткий обработчик: given по истечении `pickup_sla_minutes + pickup_sla_buffer_minutes` `order.status`
   всё ещё `'processing'`, Then вызывает `order.cancel('pickup_sla_exceeded', system)` — полный
   `PaymentProvider.refund()` (через `PaymentsFacade`), `EscrowLedger.refund`, восстановление резерва
   ВСЕХ ещё не выданных партий (через `InventoryFacade`), публикует `OrderAutoCancelledEvent`
   (существующее событие).
4. Given заказ уже завершён (`complete-picking` успел раньше срабатывания джоба) — оба обработчика
   идемпотентно завершаются без действия (проверка `order.status` — первый шаг каждого обработчика).
5. Явно НЕ реализовывать переназначение заказа на другую аптеку при просрочке (SRS-PHT-035 —
   архитектурный запрет, доменная модель не поддерживает смену `orders.pharmacy_id`).

## Критерии приёмки

Given `processing`, `now = processing_started_at + 7мин01с`, When мягкий watchdog-джоб срабатывает, Then
публикуется `SlaBreachedEvent` → WS `ops.sla_breached`, заказ ОСТАЁТСЯ `processing` (TC-PHT-021).

Given `processing`, `now = processing_started_at + 12мин01с`, сборка НЕ завершена, When жёсткий
watchdog-джоб срабатывает, Then `status='cancelled'`, полный рефанд, `OrderAutoCancelledEvent`
опубликовано (TC-PHT-022).

Given заказ переведён в `picked_up` до срабатывания жёсткого джоба (сборка успела завершиться), When
джоб всё же срабатывает (сеть/таймер джоба сработал с опозданием), Then джоб идемпотентно завершается
БЕЗ повторной отмены/рефанда (негативный тест на гонку между `complete-picking` и watchdog).

## Тест-план

Unit: `SlaWatchdogProcessor` — оба обработчика с замоканным репозиторием заказов: срабатывание при
`processing` (действие выполняется), срабатывание при уже терминальном статусе (нет действия — идемпотент-
ность), корректность вычисления `delay` из `tenant_settings`.
Интеграционные: TC-PHT-021, TC-PHT-022, тест с реальным BullMQ+Redis тестовым инстансом — джоб
действительно ставится при `accept` и действительно срабатывает по истечении `delay` (используя
управляемые часы теста, не реальное ожидание 7 минут).
Порог покрытия application/infrastructure — 90%/70% соответственно (`02` §6).
