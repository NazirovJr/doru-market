## Задача

Одиннадцать эндпоинтов части A терминала (DTJ-301..306) реализовывались параллельно шестью тикетами —
каждый отдельно покрыл свою бизнес-логику, но нет ни одного теста, проверяющего ВСЮ поверхность сразу на
два сквозных инварианта, которые ломаются чаще всего именно на стыке: (1) фармацевт одной аптеки не может
трогать заказ чужой аптеки/сети/тенанта; (2) `Idempotency-Key` реально обязателен там, где это заявлено
таблицей SRS-PHT-039, а не забыт на одном из одиннадцати маршрутов. Это тикет-предохранитель, закрывающий
класс ошибок «в каждом тикете по отдельности правильно, а всей поверхностью — дыра».

## Технический контекст

Интеграционные тесты (`apps/api/test/integration/pharmacy-terminal/**`), поднимающие реальное тестовое
приложение (NestJS test module + тестовая БД), НЕ юнит-тесты отдельных use case (те уже написаны в
DTJ-301..306). Проверяет `RolesGuard`/`TenantResolutionMiddleware` (существующая инфраструктура EP-01/
EP-02, здесь не создаётся, только используется как есть) в применении именно к маршрутам этого эпика.

## Что сделать

1. `rbac-isolation.spec.ts` — таблица из 11 эндпоинтов части A (`accept`, `reclaim`, `scan`, `report-issue`,
   `propose-partial-fulfillment`, `complete-picking`, `GET handover-otp`, `regenerate`, `GET /orders`
   очередь, плюс `GET /orders/:id`) × 4 сценария каждый:
   а. `pharmacist` чужой аптеки → `403`/`404` (заказ не принадлежит его `pharmacyId`).
   б. `pharmacist` своей аптеки → допуск (позитивный, уже покрыт в DTJ-301..306, здесь регрессия одним
      прогоном по всем 11 маршрутам после интеграции).
   в. `pharmacy_admin` чужой сети → `403`/`404`.
   г. `super_admin` → `403 INSUFFICIENT_ROLE` на все МУТИРУЮЩИЕ действия (accept/reclaim/scan/report-issue/
      propose/complete-picking/regenerate) — SRS-PHT-004: наблюдение через `platform:ops`, без права
      сканировать/завершать сборку чужой аптеки; допуск ТОЛЬКО на чтение (`GET /orders`, `GET
      handover-otp`) при явном `X-Tenant-Slug` override (SRS-API-044, с проверкой `audit_log`
      `crossTenantOverride=true`).
2. `idempotency.spec.ts` — для семи эндпоинтов из таблицы SRS-PHT-039 (`accept`, `reclaim`, `scan`,
   `report-issue`, `propose-partial-fulfillment`, `complete-picking`, `regenerate`): (а) запрос без
   заголовка `Idempotency-Key` → `400 IDEMPOTENCY_KEY_REQUIRED`; (б) два идентичных запроса с одним и тем
   же ключом и телом → второй возвращает СОХРАНЁННЫЙ ответ первого БЕЗ повторного побочного эффекта
   (партия не списана дважды, заказ не отменён дважды и т.п. — специфичная для каждого эндпоинта
   проверка «не задвоилось»); (в) тот же ключ, другое тело → `409 IDEMPOTENCY_KEY_CONFLICT`.
3. НЕ реализовывать RBAC-guard'ы/идемпотентность заново — этот тикет только проверяет уже реализованное
   в DTJ-301..306; найденные дыры (например, забытый `Idempotency-Key` на каком-то маршруте) фиксируются
   как баг-фикс В ТЕХ тикетах через мелкую точечную правку (Edit, не переписывание), не переносятся сюда.

## Критерии приёмки

Given `pharmacist` аптеки X, When он вызывает ЛЮБОЙ из 11 эндпоинтов для заказа аптеки Y, Then ответ —
`403`/`404` (не `200`) на КАЖДОМ из 11 маршрутов без исключения (сводная таблица теста).

Given `super_admin` БЕЗ `X-Tenant-Slug` override, When вызывает `POST /orders/:id/accept` для любого
заказа, Then `403 INSUFFICIENT_ROLE` — подтверждает, что наблюдательная роль не может выполнять
операционные действия терминала (негативный тест, ключевой для SRS-PHT-004).

Given `POST /orders/:id/items/:itemId/scan` вызван дважды подряд с одинаковым `Idempotency-Key` и телом,
When второй запрос отправлен ДО завершения первого (гонка), Then второй получает
`409 IDEMPOTENCY_KEY_CONFLICT` (SRS-API-010, негативный тест на конкурентный дубль).

## Тест-план

Только интеграционные тесты (это тестовый тикет по определению) — см. «Что сделать» пп.1-2 для полного
перечня кейсов (11×4 + 7×3 = минимум 65 assert-сценариев, часть переиспользует общие хелперы для
сокращения дублирования кода теста, не самой проверки). Порог покрытия — неприменим напрямую (тесты не
production-код), но каждый кейс обязан фактически проваливаться при откате соответствующего guard'а
(мутационная проверка вручную при ревью: временно ослабить guard — тест должен покраснеть).

## Риски и подводные камни

Этот тикет физически может стартовать только когда DTJ-301..306 уже смержены (иначе нечего тестировать
сквозным прогоном) — это единственный тикет эпика с настоящей жёсткой зависимостью от ВСЕХ предыдущих, а
не от одного-двух. Если в процессе обнаружится системная дыра (например, `RolesGuard` в принципе не
проверяет `pharmacyId`-скоуп для одной из ролей) — это может означать баг в общей RBAC-инфраструктуре
EP-01/EP-02, а не в конкретном use case терминала; в этом случае эскалировать владельцу EP-02, не чинить
локальным костылём внутри `orders`-модуля.
