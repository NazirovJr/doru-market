## Задача

Когда цепочка последовательных офферов (DTJ-315) исчерпана — заказ не должен зависнуть без курьера.
Этот тикет даёт два пути восстановления: самостоятельный выбор ЛЮБЫМ доступным курьером из открытого
пула и ручное вмешательство диспетчера (`pharmacy_admin`/`super_admin`), которое ВСЕГДА доступно как
override, даже пока цепочка офферов ещё идёт (REQ-DELIV-2 «обязательный ручной override»).

## Технический контекст

`apps/api/src/modules/delivery/application/**`, продолжает DTJ-315/DTJ-314. `ClaimDeliveryAssignmentUseCase`
использует ОПТИМИСТИЧНУЮ блокировку (`UPDATE ... WHERE status='unassigned'`), в отличие от пессимистичной
`SELECT FOR UPDATE` в терминале фармацевта (DTJ-301) — обоснование: конкуренция за claim из пула редка,
ре-попытка дешева (SRS-DELIV-016).

## Что сделать

1. `GET /api/v1/delivery-assignments/available-pool?radiusKm=5&sort=distance:asc` —
   эскалированные назначения (после исчерпания последовательных офферов), видимые ЛЮБОМУ приемлемому
   `on_shift` курьеру в радиусе (тенантный guard SRS-DOM-037 применяется К ФИЛЬТРАЦИИ списка, не только к
   `assign`). «В пуле» — структурное определение: `status='unassigned'` И нет `pending`/`accepted`
   офферов для назначения (не отдельный статус БД). Поля ответа — тот же урезанный вид, что в
   `GET /delivery-offers` (без точного адреса клиента).
2. `POST /api/v1/delivery-assignments/:id/claim` — `ClaimDeliveryAssignmentUseCase`. Given назначение
   `unassigned` И присутствует в пуле (все предыдущие офферы `expired`) И курьер проходит
   тенантный/cold-chain guard, When claim, Then `UPDATE delivery_assignments SET status='assigned',
   courier_id=:X WHERE id=:id AND status='unassigned'` — первый успешный `UPDATE` побеждает. Given
   `0 rows affected` (уже заявлен другим курьером) → `409 ASSIGNMENT_ALREADY_CLAIMED`. `Idempotency-Key`
   опционален (операция сама атомарна).
3. `POST /api/v1/delivery-assignments/:id/assign-manual { courierId, reason? }` — `pharmacy_admin` (свой
   флот, `courier.chainId === actor.chainId`) / `super_admin` (любой курьер, включая пул). Отменяет ВСЕ
   `pending`-офферы этого назначения (`superseded`), вызывает `DeliveryAssignment.assign(courierId)`
   напрямую — обходит алгоритм и очередь предложений целиком.
4. `POST /api/v1/delivery-assignments/:id/reassign { courierId, reason }` — `reason` ОБЯЗАТЕЛЕН (не
   опционален, в отличие от `assign-manual`). Доступно в ЛЮБОЙ нетерминальной стадии
   (`assigned`..`en_route_to_customer`). Роли — как в `assign-manual`.
5. `GET /api/v1/delivery-assignments?filter[status][in]=...&sort=createdAt:desc` — операционный дашборд
   диспетчера. `pharmacy_admin` — только своя сеть (implicit `chainId`-скоуп); `super_admin` — все,
   включая пул.
6. `CourierDepartSlaWatchdogProcessor` — BullMQ delayed job, планируется при `assign` (`delay =
   COURIER_DEPART_SLA_MINUTES`, ASSUMPTION 10). Given `assigned` (оффер принят), но курьер НЕ вызвал
   `depart` дольше этого срока, Then публикует `SlaBreachedEvent(entityType='delivery_assignment')` в
   `platform:ops`/`chain:{chainId}` — НЕ отменяет назначение автоматически (курьер мог быть на пути
   физически), решение — за диспетчером через `reassign`.

## Критерии приёмки

Given назначение в пуле, курьер А и курьер Б одновременно вызывают `claim`, When конкурентные запросы,
Then один получает `200`, другой — `409 ASSIGNMENT_ALREADY_CLAIMED` (TC-DELIV-006/072).

Given `pharmacy_admin` вызывает `assign-manual` с курьером, When назначение имело активные `pending`-
офферы, Then все они переходят в `superseded`, назначение немедленно `assigned` на выбранного курьера
(позитивный override-тест).

Given `assigned`, курьер НЕ вызвал `depart` дольше `COURIER_DEPART_SLA_MINUTES`, When watchdog-джоб
срабатывает, Then публикуется `SlaBreachedEvent` диспетчеру, назначение ОСТАЁТСЯ `assigned` (НЕ
авто-переназначается) — негативный (в смысле «намеренно не делает») тест, TC-DELIV-063.

## Тест-план

Unit: `ClaimDeliveryAssignmentUseCase` — успешный/неуспешный (0 rows) путь с замоканным репозиторием;
`AssignManualUseCase`/`ReassignDeliveryUseCase` — `reason` обязателен на `reassign`, опционален на
`assign-manual`, скоуп `pharmacy_admin` (`chainId` matching) vs `super_admin` (без ограничения).
Интеграционные: TC-DELIV-006, TC-DELIV-072 (реальная конкурентная транзакция на тестовой БД), TC-DELIV-063
(watchdog не отменяет), `available-pool` — фильтрация по радиусу и тенантному guard.
Порог покрытия application — 90%.

## Риски и подводные камни

`assign-manual`/`reassign` для `pharmacy_admin` требуют точного правила «свой флот»
(`courier.chainId === actor.chainId`) — если курьер платформенного пула (`chainId IS NULL`),
`pharmacy_admin` НЕ может его назначить вручную (только `super_admin`) — легко перепутать направление
проверки (`IS NULL` vs конкретный `chainId`), покрыть отдельным негативным тестом на эту границу.
