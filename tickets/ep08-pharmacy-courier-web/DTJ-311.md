## Задача

Основной рабочий экран фармацевта: список позиций заказа, поле ручного ввода штрихкода (R1-веб — БЕЗ
камеры, `manualEntry: true` путь, `30-ux` §3.2 `/admin/order-queue/:id`), кнопка «Товар недоступен» с
причинами. Здесь проходит бо́льшая часть времени сборки одного заказа — от него зависит, насколько быстро
фармацевт успевает уложиться в 7-минутный SLA.

## Технический контекст

`apps/pharmacy/src/features/order-fulfillment/picking/**` — маршрут `/orders/:id`. Использует
`GET /orders/:id` (существующий эндпоинт детали заказа) для первичной загрузки, дальше — точечные мутации
через `POST .../scan` (DTJ-302) и `POST .../report-issue` (DTJ-303). `model/picking.model.ts` — чистые
функции вычисления производного UI-состояния позиции (badge-статус, доступность действий) — вычисления
НЕ в компоненте (`02` §5).

## Что сделать

1. `PickingPage` — список позиций заказа (`MedicineName`, `quantity`, статус-бейдж: `pending` (нейтральный)
   / `scanned_ok` (зелёный, иконка+текст, не только цвет — SRS-UX-019) / `unavailable` (красный, причина)),
   SLA-таймер сверху (`CountdownTimer` — переиспользовать из `packages/ui`, если уже готов EP-18, иначе
   временный локальный компонент с тикетом на перенос — `tickets/00-EPICS.md` «Пересекающееся владение» п.6).
2. Поле «Ввести штрихкод» (Input, крупный, автофокус после выбора позиции) — при выборе конкретной строки
   позиции открывается поле ввода ДЛЯ ЭТОЙ позиции (не общее поле на экране — снижает риск скана не той
   позиции). Отправка → `POST /orders/:id/items/:itemId/scan { rawBarcode, manualEntry: true }`
   (`manualEntry: true` — В R1 ВСЕГДА true, камера — только R2 Flutter). `Idempotency-Key = uuid.v4()`
   генерируется при каждой отправке формы.
3. Обработка ответов: `200` → позиция красится в `scanned_ok`, поле очищается, фокус переходит на
   следующую нерешённую позицию (эргономика последовательного сканирования); `404
   ORDER_ITEM_NOT_FOUND` → inline-ошибка «Это не тот препарат — отсканирован {resolvedName}»
   (используется резолвленное имя из деталей ошибки, если сервер его возвращает — иначе универсальный
   текст `ux.error.wrong_barcode`), поле НЕ очищается, позиция остаётся `pending`; `409
   ITEM_ALREADY_SCANNED` → сообщение «Уже отсканировано», позиция помечается как решённая на клиенте
   (синхронизация с фактическим состоянием); `422 EXPIRED_STOCK`/`422 BATCH_NOT_AVAILABLE` → inline-ошибка
   с точным текстом причины, позиция остаётся `pending`.
4. Кнопка «Товар недоступен» на каждой нерешённой позиции → модалка/панель с чипами причин («Нет в
   наличии», «Истёк срок годности», «Повреждена упаковка», «Другое» — маппится на
   `out_of_stock`/`expired_on_shelf`/`damaged_packaging`), опциональное поле заметки → `POST
   .../report-issue`. Успех — позиция красится в `unavailable` с зачёркиванием (визуальный паттерн из
   дизайн-референса) + причина рядом.
5. Каждое действие получает видимый отклик ≤150мс (`loading`-состояние кнопки/поля, SRS-UX-006) — переход
   `default → loading → success/error` НЕ меняет размеры элемента (SRS-UX-020, недопустим «прыжок»
   layout).
6. WS-подписка на `pharmacy:{pharmacyId}` (переиспользует клиент из DTJ-310) для получения
   `order.cancelled` — если открыт экран сборки, When приходит это событие, Then блокирующий диалог «Заказ
   отменён клиентом», дальнейшие действия на экране недоступны (SRS-PHT-068).
7. Тап-зоны критичных элементов (галочка/действие позиции) — ≥56×56px реальной области попадания
   (визуально можно компактнее, hit-slop через padding — `32-design-reference.md` расхождение №4).

## Критерии приёмки

Given позиция заказа — Парацетамол 500мг, When вводится штрихкод Ибупрофена и отправляется, Then
показывается inline-ошибка с именем неверно отсканированного препарата, позиция остаётся `pending`, поле
ввода доступно для повторной попытки без ограничений.

Given партия просрочена (`422 EXPIRED_STOCK`), When ответ получен, Then позиция НЕ переходит в
`scanned_ok`, показывается сообщение с предложением попробовать другую партию либо сообщить о проблеме —
кнопка «Товар недоступен» остаётся доступной на этой позиции.

Given заказ отменён клиентом ПОКА открыт экран сборки, When приходит WS `order.cancelled`, Then
немедленно показывается блокирующий диалог «Заказ отменён клиентом», дальнейшие сканы/report-issue
недоступны (кнопки задизейблены) — негативный/защитный сценарий (SRS-PHT-068).

## Тест-план

Unit (`model/picking.model.ts`): вычисление badge-статуса позиции по `fulfillmentStatus`/`itemIssueReason`,
доступность кнопок по состоянию заказа (заблокировано после `order.cancelled`).
Компонентные: `PickingPage` — happy-path скана (позиция становится `scanned_ok`, фокус переходит дальше),
ветка `404`/`409`/`422` каждая отдельным кейсом с мок-API, модалка report-issue (выбор причины → успех).
E2E: полный проход сборки заказа из 2 позиций (1 успешный скан, 1 report-issue) до состояния «все решены»
(без самого complete-picking — см. DTJ-312).
Порог покрытия — 70% (frontend).

## Риски и подводные камни

Поле ручного ввода штрихкода без камеры (R1) — фармацевту придётся переписывать штрихкод глазами с
упаковки, что медленнее и подвержено опечаткам сильнее, чем сканирование; это принятое архитектурное
ограничение R1 (камера — R2 Flutter), не дефект этого тикета, но стоит убедиться, что поле поддерживает
быстрый ввод (числовая раскладка на мобильных браузерах через `inputmode="numeric"`, если терминал
используется на планшете с сенсорной клавиатурой). `CountdownTimer`/иконки статусов — зависят от
готовности `packages/ui` (EP-18); при отсутствии готового компонента на момент тикета — использовать
временную локальную реализацию в `features/order-fulfillment/picking/ui/**` с обязательным тикетом на
перенос в `packages/ui` в том же спринте (`tickets/00-EPICS.md` п.6 «Пересекающееся владение»).
