## Задача

Финальная пара экранов доставки: фиксация полученных от клиента наличных (для `cash_courier`-заказов) и
ввод 4-значного кода вручения. Это единственный способ, которым заказ переходит в `delivered` — без
успешного прохождения этих экранов деньги не капчурятся из escrow, а курьер не может закрыть доставку.

## Технический контекст

`apps/courier/src/features/{cash-collection,otp-entry}/**` — маршруты `/cash/:id`, `/otp/:id`. Использует
`POST .../record-cash` (обязательный `Idempotency-Key`), `POST .../deliver` (DTJ-317). Ручной ввод суммы
клиентом на этом экране — ЕДИНСТВЕННЫЙ разрешённый путь подтверждения оплаты для `cash_courier`
(SRS-UX-008 — интерфейс НЕ содержит поля для ручного ввода «номера транзакции»/скриншота как способа
подтверждения платежа, единственный путь для наличных — этот экран).

## Что сделать

1. `CashCollectionScreen` (`/cash/:id`) — поле «Сколько дал клиент» (числовой ввод), авторасчёт «Сдача»
   = `collectedDiram - order.totalAmountDiram` (живой пересчёт при вводе, НЕ отдельная кнопка
   «посчитать»). Кнопка «Подтвердить» → `POST .../record-cash { collectedDiram, changeDiram }` с
   `Idempotency-Key = uuid.v4()`, генерируемым при ПЕРВОЙ отправке формы (переиспользуется при
   автоматическом ретрае той же попытки, не при повторном ручном нажатии после явной правки суммы —
   правка суммы = новая попытка = новый ключ).
2. Given `422 CASH_AMOUNT_MISMATCH`, Then показать сообщение о несовпадении суммы с точными числами
   («получено X, сдача Y, ожидается получить ровно Z») — НЕ просто «ошибка», курьер должен понять, что
   именно пересчитать.
3. Успех → переход на `/otp/:id`.
4. `OtpEntryScreen` (`/otp/:id`) — 4 ячейки цифрового ввода, автопереход между ячейками, авто-сабмит на
   4-й цифре (переиспользовать `OtpInput`-компонент из `packages/ui`/`apps/web`, если уже вынесен
   переиспользуемым — та же UI-механика, что и OTP-логин, только 4 ячейки вместо 6). Подсказка «Попросите
   клиента назвать код из SMS».
5. Отправка → `POST .../deliver { otpCode }`. Given `400 OTP_EXPIRED` → сообщение с рекомендацией
   попросить фармацевта/поддержку перевыпустить код (`reissue-handover-otp`, вне доступа курьера — только
   текстовая инструкция, кто может помочь). Given `400 OTP_MISMATCH` → «Неверный код», счётчик оставшихся
   попыток, если сервер его возвращает. Given `423 OTP_LOCKED` → блокирующее сообщение с той же
   рекомендацией обратиться к фармацевту/поддержке за перевыпуском.
6. Успех → экран подтверждения «Доставлено» (иконка успеха) → редирект на `/offers` (готовность к
   следующему офферу).

## Критерии приёмки

Given `order.total=6000`, When в поле «Сколько дал клиент» введено `6000`, Then «Сдача» автоматически
показывает `0` без дополнительного действия.

Given `collected:6000, change:500` при `order.total=6000` (курьер ошибся при ручном расчёте), When
отправлено, Then `422 CASH_AMOUNT_MISMATCH`, показано точное сообщение с ожидаемыми числами, форма
остаётся заполненной для правки (не сбрасывается).

Given верный код введён в 4 ячейки, When 4-я цифра введена, Then авто-сабмит срабатывает БЕЗ отдельного
нажатия кнопки «Подтвердить», успешный ответ ведёт на экран «Доставлено».

## Тест-план

Unit: `model` авторасчёта сдачи (несколько комбинаций сумм, включая отрицательную сдачу как
UI-предупреждение до отправки — «сдача не может быть отрицательной», клиентская валидация ДО запроса).
Компонентные: `CashCollectionScreen` — happy path + `422`-ветка; `OtpEntryScreen` — авто-сабмит, три
ветки ошибок OTP.
E2E: завершение сценария DTJ-327/328 — от `/active/:id` через `/cash/:id` → `/otp/:id` → «Доставлено» —
полный CUJ-4' happy-path.
Порог покрытия — 70%.

## Риски и подводные камни

Клиентская валидация «сдача не может быть отрицательной» ДО отправки — полезный UX-щит, но НЕ заменяет
серверную проверку `CASH_AMOUNT_MISMATCH` (домен — источник истины, `02` §2.6); не пропускать серверную
обработку ошибки, полагаясь только на клиентскую валидацию. Курьер не имеет собственного пути
перевыпуска OTP (`reissue-handover-otp` — роли `pharmacist`/`support_agent`/`super_admin`, не `courier`,
SRS-DELIV-023) — экран обязан явно объяснить, ЧТО делать при истёкшем/заблокированном коде, а не просто
показать тупиковую ошибку.
