## Задача

Не каждая доставка идёт по плану: клиент может быть недоступен, адрес — не найден, клиент может
отказаться принять заказ на пороге. Этот экран даёт курьеру явный, структурированный способ сообщить о
проблеме, вместо того чтобы оставаться на активном экране без понятного следующего действия.

## Технический контекст

`apps/courier/src/features/delivery-issue/**` — маршрут `/issue/:id`, доступен из `ActiveDeliveryPage`
(DTJ-328) кнопкой «Проблема». Использует `POST .../report-issue`, `POST .../mark-failed`,
`POST .../refuse-at-door` (DTJ-318).

## Что сделать

1. `IssueReportScreen` — список причин (`customer_unreachable`/`address_not_found`/`other`), опциональное
   фото (загрузка через существующий `FileDropzone`/загрузчик, если уже есть в `packages/ui`; иначе —
   простой `<input type="file">` с превью, тикет на перенос в `packages/ui`), поле заметки. Отправка →
   `POST .../report-issue`.
2. Given `contact_attempts_count` достиг порога (сервер сообщает текущее значение через `GET
   .../:id`, DTJ-317), Then показать кнопку «Клиент недоступен — не удалось доставить» →
   `POST .../mark-failed { reason: 'customer_unreachable' }`. Given `422
   CONTACT_ATTEMPTS_INSUFFICIENT` (курьер попытался раньше порога), Then сообщение «Нужно ещё N попыток
   связаться с клиентом» (используя разницу между текущим и требуемым количеством, если сервер её
   возвращает, иначе — общий текст с рекомендацией продолжить попытки).
3. Отдельная кнопка «Клиент отказался принять заказ» (доступна из `ActiveDeliveryPage` напрямую или с
   этого экрана — решение по UX-компоновке на усмотрение разработчика, главное — доступность без глубокой
   навигации) → модалка подтверждения (необратимое действие — заказ уходит в возврат) →
   `POST .../refuse-at-door { reason: 'refused_at_door', notes? }`.
4. После успешной отправки `report-issue` — возврат на `ActiveDeliveryPage` (проблема зафиксирована,
   доставка продолжается — курьер может пробовать снова). После успешного `mark-failed`/`refuse-at-door`
   — переход на `/offers` (доставка завершена как неуспешная, курьер готов к следующей).

## Критерии приёмки

Given заказ `en_route_to_customer`, When выбрана причина «Клиент недоступен» и отправлено, Then
`contact_attempts_count` инкрементируется (проверяется через последующий `GET .../:id`), курьер остаётся
на активной доставке.

Given `contact_attempts_count` ниже порога, When курьер пытается «Не удалось доставить», Then `422
CONTACT_ATTEMPTS_INSUFFICIENT`, показано понятное сообщение, доставка НЕ завершается (негативный тест).

Given курьер подтверждает «Клиент отказался принять заказ» в модалке, When подтверждение отправлено,
Then `POST .../refuse-at-door` вызван, курьер перенаправлен на `/offers`, попытка вернуться на
`/active/:id` этого же назначения (например, кнопкой «назад» браузера) показывает терминальное состояние,
не позволяет повторных действий.

## Тест-план

Unit: `model` доступности кнопки «Не удалось доставить» по текущему `contact_attempts_count`/порогу.
Компонентные: `IssueReportScreen` — отправка причины, ветка `422` на `mark-failed`, модалка отказа на
пороге (подтверждение/отмена).
Порог покрытия — 70%.

## Риски и подводные камни

Точная формулировка «сколько ещё попыток нужно» зависит от того, возвращает ли backend (DTJ-318) разницу
до порога в ответе, или только сырые `contact_attempts_count`/`DELIVERY_MAX_CONTACT_ATTEMPTS` (если
последнее — константа НЕ раскрывается клиенту напрямую как магическое число, а вычисляется на фронтенде
из `GET /api/v1/meta`, если она там присутствует, либо просто используется универсальный текст без
точного счётчика — не хардкодить значение `3` в компоненте, C6).
