## Задача

Завершающая часть сборки: если есть недоступные позиции — предложить клиенту изменённый состав и
дождаться его решения; когда все позиции решены — подтвердить опечатку сейф-пакета и показать 4-значный
код вручения крупно на экране, чтобы фармацевт мог назвать/передать его курьеру. Без этого экрана сборка
физически не может считаться завершённой в системе, даже если все товары уже физически упакованы.

## Технический контекст

`apps/pharmacy/src/features/order-fulfillment/{partial-fulfillment,handover}/**` — продолжение экрана
`/orders/:id` из DTJ-311 (те же маршрут/страница, дополнительные под-состояния Cubit-подобной модели
`picking.model.ts`, расширяемой этим тикетом, а не переписываемой). Использует эндпоинты DTJ-304
(`propose-partial-fulfillment`), DTJ-305 (`complete-picking`), DTJ-306 (`GET`/`regenerate handover-otp`).

## Что сделать

1. Given все позиции решены (`pending`-позиций нет) И ≥1 `unavailable`, Then показать кнопку/баннер
   «Предложить клиенту изменённый состав» → `POST .../propose-partial-fulfillment`. Успех → баннер
   ожидания «Ждём подтверждения клиента: часть позиций недоступна» (не блокирует просмотр списка позиций,
   но блокирует кнопку «Завершить сборку» до разрешения).
2. WS-подписка на `order.partial_fulfillment_resolved` (комната `pharmacy:{pharmacyId}`, из DTJ-308) —
   получение снимает баннер ожидания, разблокирует «Завершить сборку», показывает итоговую (уменьшенную)
   сумму заказа.
3. Given все позиции решены И (нет `unavailable` ИЛИ частичная сборка уже подтверждена/авто-подтверждена),
   Then кнопка «Завершить сборку» активна. Чекбокс/переключатель «Пакет опечатан» (`sealConfirmed`,
   обязательный, отдельный явный элемент — НЕ подразумевается по умолчанию) — кнопка «Завершить сборку»
   задизейблена, пока чекбокс не отмечен (соответствует SRS-PHT-024/025, дизайн-референс отмечает
   отсутствие этого чекбокса в canvas-демо как пробел, реализовать по письменной спецификации).
4. Отправка → `POST /orders/:id/complete-picking { sealConfirmed: true }`. Given `409
   PARTIAL_FULFILLMENT_PENDING` (гонка — клиент не успел подтвердить), Then показать баннер ожидания
   вместо перехода к OTP-экрану (не показывать пользователю сырую ошибку). Given `422 EXPIRED_STOCK`
   (партия истекла за время ожидания), Then вернуть фармацевта к списку позиций с подсветкой просроченной
   позиции для повторного скана/report-issue.
5. Успех → `HandoverOtpScreen`: крупный 4-значный код по центру экрана (моноширинный шрифт, крупный
   размер — легко прочитать/продиктовать), таймер обратного отсчёта до `expiresAt` (15 минут). По
   истечении таймера — кнопка «Обновить код» (НЕ автоматическая регенерация — частая механическая
   регенерация «на всякий случай» тратит лимит, SRS-PHT-029) → `POST .../regenerate`, замена кода на
   экране, перезапуск локального таймера. Given `429 RATE_LIMITED` (лимит регенераций исчерпан), Then
   сообщение с инструкцией обратиться к `support_agent`/`super_admin`.
6. Экран OTP доступен также ПОВТОРНО через `GET .../handover-otp` при возврате на заказ из очереди со
   статусом `picked_up` (например, экран был случайно закрыт).
7. После успешного завершения — переход к следующему заказу очереди (кнопка «К следующему заказу» →
   `/`).

## Критерии приёмки

Given все позиции решены, ≥1 `unavailable`, When нажата «Предложить клиенту изменённый состав», Then
показывается баннер ожидания, кнопка «Завершить сборку» недоступна, пока не придёт
`order.partial_fulfillment_resolved`.

Given все позиции `scanned_ok`, чекбокс «Пакет опечатан» НЕ отмечен, When нажата «Завершить сборку»
(кнопка должна быть задизейблена, но проверяется и серверный негативный путь на случай обхода UI), Then
запрос не отправляется с клиента ЛИБО сервер отвечает `400 SEAL_CONFIRMATION_REQUIRED` — в обоих случаях
экран остаётся на списке позиций, ошибка отображается пользователю.

Given экран `HandoverOtpScreen` открыт, код истёк (`now > expiresAt`), When нажата «Обновить код», Then
новый код отображается, старый код визуально заменяется полностью (не остаётся на экране рядом с новым) —
негативный тест против «показа двух кодов одновременно» (путаница при диктовке курьеру).

## Тест-план

Unit: логика доступности кнопки «Завершить сборку» по комбинации (все решены × наличие `unavailable` ×
статус запроса частичной сборки) — таблица истинности, минимум 5 кейсов.
Компонентные: `PartialFulfillmentBanner` (ожидание → разблокировка по WS-событию), `HandoverOtpScreen`
(таймер, регенерация, `429`-ветка).
E2E: продолжение сценария DTJ-311 — заказ с 1 `unavailable`-позицией доходит до `propose` →
(мок-подтверждение клиента) → `complete-picking` → отображение кода — полный CUJ-3' happy-path с частичной
сборкой (для EP-19 harness).
Порог покрытия — 70% (frontend).

## Риски и подводные камни

Гонка между истечением SLA-таймера сборки (DTJ-307, жёсткий автоотказ на 12-й минуте) и ожиданием
подтверждения частичной сборки клиентом (таймаут по умолчанию 10 минут) — если оба таймера близки, экран
может внезапно получить `order.cancelled` ПОКА фармацевт ждёт ответа клиента; обработка та же, что в
DTJ-311 (блокирующий диалог отмены), явно перепроверить на этом под-экране отдельным тестом, т.к. это
состояние специфично для окна ожидания частичной сборки, не для обычного сканирования.
