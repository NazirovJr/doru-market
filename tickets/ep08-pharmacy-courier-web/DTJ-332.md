## Задача

Без периодической отправки координат курьер не появляется на живой карте клиента/диспетчера, а ETA не
пересчитывается. Без офлайн-очереди статусные действия (записать наличные, ввести OTP), выполненные при
слабом сигнале сотовой сети (частая ситуация в пути), просто теряются вместо того чтобы отправиться после
восстановления связи. Это сквозная инфраструктура, используемая ВСЕМИ экранами активной доставки
(DTJ-328/329/330).

## Технический контекст

`apps/courier/src/shared/{geolocation,offline-queue}/**` — переиспользуемая инфраструктура, не привязанная
к одному экрану (`shared/`, `02` §5). Браузерный `navigator.geolocation.watchPosition` (веб-эквивалент
`geolocator` из R2-Flutter, SRS-DELIV-050) — БЕЗ foreground-service (веб не может гарантировать фон, явно
сообщается курьеру баннером). Офлайн-очередь — `IndexedDB` (веб-эквивалент `drift`, SRS-DELIV-050).

## Что сделать

1. `useGeolocationTracking()` — хук, активируется на маршрутах активной доставки (`/active/:id`,
   `/cash/:id`, `/otp/:id`), троттлинг по состоянию назначения (та же логика, что и Flutter-версия, но
   применимая к вебу: реже, когда просто `on_shift` без назначения — если этот хук вообще используется вне
   активной доставки; в R1-вебе достаточно активировать трекинг ТОЛЬКО на экранах активной доставки,
   упрощённая версия без фоновой отправки при простое, т.к. веб не гарантирует фон). Отправка через
   `POST /courier-locations` (батчем раз в `LOCATION_FLUSH_INTERVAL_SECONDS`, ASSUMPTION 15, НЕ один
   запрос на одну точку GPS).
2. Given `navigator.geolocation` недоступна/пользователь отклонил разрешение, Then баннер «Включите
   геолокацию, чтобы клиент видел ваше примерное время прибытия» — НЕ блокирует остальной функционал
   экрана (курьер может продолжать доставку без геолокации, просто ETA у клиента не обновляется).
3. Явный баннер «Держите вкладку открытой во время доставки» (SRS-DELIV-050 — известное ограничение веба
   без foreground-service) — постоянно видим на экранах активной доставки.
4. `offlineActionQueue` (IndexedDB) — generic очередь: `{ id, endpoint, method, payload, idempotencyKey,
   createdAt, status: 'queued'|'sending'|'sent'|'failed', retryCount }`. Given сеть недоступна, When
   курьер нажимает статусную кнопку (`depart`/`depart-to-customer`/`record-cash`/`deliver`/
   `report-issue`), Then действие СРАЗУ пишется в очередь, UI оптимистично обновляется с пометкой «не
   синхронизировано» (иконка часов), фоновый воркер пытается отправить с экспоненциальным backoff (`5с,
   10с, 20с, 40с, макс 120с`).
5. `Idempotency-Key` для действий, требующих его (`record-cash`) — генерируется В МОМЕНТ постановки в
   очередь, НЕ в момент фактической отправки.
6. Конфликт очереди: given несколько статусных действий для ОДНОГО `deliveryAssignmentId` в очереди,
   Then отправляются СТРОГО FIFO по `createdAt`; given сервер отвечает `409
   INVALID_STATE_TRANSITION` на одно из отложенных действий, Then это конкретное действие отбрасывается
   из очереди (логируется, НЕ ретраится бесконечно), обработка продолжается со следующим.
7. `OfflineBanner` — единый компонент состояния сети (переиспользовать из `packages/ui`, если готов),
   индикатор количества отложенных действий в очереди.
8. Правило деградации (SRS-UX-024): при полной потере сети НЕ блокировать весь экран — показывать
   последнее известное состояние read-only с постоянным баннером, действия, требующие сети, помечаются
   `disabled` с подсказкой при попытке нажатия, а не молча ничего не делают.

## Критерии приёмки

Given сеть недоступна, When курьер нажимает «Доставлено» (ввод OTP), Then действие немедленно пишется в
очередь, UI показывает «не синхронизировано», НЕ блокирует дальнейшую навигацию по приложению.

Given сеть восстанавливается, When в очереди 2 действия для одного `deliveryAssignmentId`
(`depart-to-customer`, затем `deliver`), Then они отправляются строго в этом порядке, не параллельно и
не в обратном порядке.

Given отложенное действие получает `409 INVALID_STATE_TRANSITION` при отправке (состояние на сервере уже
изменилось иначе, пока курьер был офлайн), When ответ получен, Then действие удаляется из очереди без
показа технической ошибки пользователю (если оно уже неприменимо — например, коллега/диспетчер изменил
состояние), следующее действие очереди продолжает обрабатываться.

## Тест-план

Unit: `offlineActionQueue` — постановка/извлечение FIFO, генерация `Idempotency-Key` при постановке (не
при отправке), backoff-расписание ретраев, обработка `409` (удаление без ретрая) vs `5xx`/сетевая ошибка
(ретрай).
Компонентные: `OfflineBanner` — состояния (онлайн/офлайн/N отложенных действий), баннер «держите вкладку
открытой» на экранах активной доставки.
Интеграционные (мок IndexedDB через `fake-indexeddb` или аналог): полный цикл «действие поставлено в
очередь офлайн → сеть восстановлена → отправлено → удалено из очереди».
Порог покрытия — 70%.

## Риски и подводные камни

Веб-версия принципиально не может гарантировать фоновую отправку координат при свёрнутой/неактивной
вкладке (в отличие от Flutter foreground-service, R2) — это ЗАДОКУМЕНТИРОВАННОЕ ограничение R1
(SRS-DELIV-050), не дефект реализации; explicit баннер — единственное доступное смягчение. Порядок
инициализации `useGeolocationTracking`/`offlineActionQueue` относительно роутинга между экранами
DTJ-328/329/330 — общий провайдер на уровне `app/` (из DTJ-325), не переинициализировать очередь заново
на каждом переходе между `/active/:id`→`/cash/:id`→`/otp/:id` (иначе теряется состояние отправки между
экранами одной доставки).
