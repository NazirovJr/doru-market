## Задача

Курьер должен видеть, сколько заработал и когда получит выплату — без прозрачности заработка платформа
теряет доверие партнёрских курьеров пула. Клиент должен иметь возможность оценить курьера после
получения заказа — единственный источник данных для будущей калибровки алгоритма подбора (`ratingScore`
в DTJ-314).

## Технический контекст

`GET /courier-earnings`/`GET /courier-payouts` — READ-ONLY эндпоинты поверх уже существующих таблиц
`courier_earnings`/`courier_payouts` (базовая схема EP-01, группа H, `11-database-schema.md`). Этот
тикет НЕ реализует генерацию `courier_payouts`-батчей (та логика — воркер выплат, вероятная зона
ответственности EP-10/`apps/worker/src/jobs/payout/**` — см. риски) — только чтение. `SubmitCourierRatingUseCase`
атомарно пересчитывает `couriers.rating_avg`/`rating_count` в одной транзакции со вставкой строки
`courier_ratings`.

## Что сделать

1. `GET /api/v1/courier-earnings?cursor=&limit=` — `implicit scope: own` для `courier`;
   `filter[courierId]` обязателен для `super_admin`. Возвращает `amount_diram`, `is_return_fee`,
   `recognized_at`, `payoutBatchId` (если уже включена в батч) — курсорная пагинация (`12-api-
   conventions...md` §«Пагинация», уже установлен паттерн).
2. `GET /api/v1/courier-payouts` — история батчей выплат. `courier` видит только свои, `super_admin` —
   все/по фильтру.
3. `POST /api/v1/courier-ratings { orderId, rating: 1..5, comment? }` — роль `customer`, только владелец
   заказа, только `order.status='delivered'`, один раз (`409 RATING_ALREADY_SUBMITTED` при повторе,
   `UNIQUE(order_id)`). `SubmitCourierRatingUseCase`: вставка строки `courier_ratings` атомарно
   инкрементирует `couriers.rating_count` и пересчитывает `rating_avg = (rating_avg × rating_count_before
   + rating) / rating_count_after` В ТОЙ ЖЕ транзакции. Публикует `CourierRatedEvent(orderId, courierId,
   rating)` → потребитель `analytics` (влияет на будущий скоринг, вне зоны владения этого тикета).

## Критерии приёмки

Given `order.status='delivered'`, оценка ещё не оставлена, When `POST /courier-ratings {rating:5}`, Then
`200`, `couriers.rating_count += 1`, `rating_avg` пересчитан по формуле (TC-DELIV-032).

Given оценка уже существует для `order_id`, When повторный `POST /courier-ratings`, Then
`409 RATING_ALREADY_SUBMITTED` (негативный тест, TC-DELIV-033).

Given `super_admin` вызывает `GET /courier-earnings` БЕЗ `filter[courierId]`, When запрос выполняется,
Then `400`/явная ошибка валидации (обязательность фильтра для этой роли — негативный тест на попытку
получить данные всех курьеров без явного намерения).

## Тест-план

Unit: `SubmitCourierRatingUseCase` — корректность формулы пересчёта скользящего среднего на нескольких
последовательных оценках (2-3 кейса с разными стартовыми `rating_count`); precondition `order.status`/
владелец заказа/уже оставленная оценка — каждый отдельным кейсом.
Интеграционные: TC-DELIV-032/033, курсорная пагинация `courier-earnings` (2 страницы, `hasMore`
корректен), RBAC-разграничение `own` vs `super_admin` с обязательным фильтром.
Порог покрытия application — 90%.

## Риски и подводные камни

Генерация `courier_payouts`-батчей (сама выплата, а не её просмотр) НЕ входит в этот тикет — если к
моменту реализации не выяснено, чья это зона ответственности (вероятно `apps/worker/src/jobs/payout/**`,
владелец EP-10 по аналогии с `escrow-timeouts`), зафиксировать это явно в PR-описании как открытый
вопрос координации между тимлидами, не браться за реализацию генерации батчей внутри этого тикета —
`GET /courier-payouts` должен работать даже если batches создаются вручную/скриптом на первых порах.
Формула `rating_avg` при `rating_count_before=0` — граничный случай (первая оценка), убедиться, что
деление на ноль не происходит (`rating_count_after=1`, формула упрощается до `rating`).
