## Задача

`DeliveryFacade` — единственная разрешённая точка входа для других модулей (`orders`, `payments`,
`billing`, `returns`) в модуль `delivery` (`02` §1.2) — без неё межмодульная интеграция вынуждена была бы
нарушать границы контекста. Алгоритм подбора курьера — сердце автоматизации доставки: без него каждый
заказ требовал бы ручного назначения диспетчером, что не масштабируется за пределы пилотных объёмов.

## Технический контекст

`apps/api/src/modules/delivery/application/**`. `DeliveryFacade` экспортирует методы: `createAssignment`,
`assign`, `reassign`, `hasActiveAssignment`, `getActiveAssignment`, `calculateDeliveryFee`,
`assignReturnCourier` (последний — заглушка/интерфейс в этом тикете, полная реализация — вне R1-скоупа
курьерского модуля, используется модулем `returns`, EP-11, который уже определён в графе как
независимый поток). `CourierCandidatePort` — интерфейс в application, реализация в infrastructure
(Drizzle-запрос с PostGIS `ST_DWithin`, `02` §1.3 — порт объявлен один раз, связывание в
`delivery.module.ts`).

## Что сделать

1. `modules/delivery/index.ts` — публичный фасад-баррель: экспортирует ТОЛЬКО `DeliveryFacade`, его
   публичные типы и доменные события модуля. Ничего из `domain/**`/`application/**` внутренних деталей
   наружу (`02` §1.2) — прямой импорт `modules/delivery/domain/*` из другого модуля = блокирующее
   нарушение ревью.
2. `CourierCandidatePort.findEligibleCandidates(pharmacyGeoPoint, tenantId, requiresColdChain,
   courierSourcingMode): CourierCandidate[]` — интерфейс, реализация — `PostgisCourierCandidateAdapter`
   (Drizzle + `ST_DWithin(couriers.last_known_*, pharmacyGeoPoint, COURIER_CANDIDATE_RADIUS_KM*1000)`).
3. `SuggestNearestCourierUseCase.execute()` — шаги SRS-DELIV-038:
   а. Жёсткий фильтр приемлемости: `couriers.status='active'` (`pending_verification` исключён
      структурно, SRS-DOM-137/REQ-COUR-10); `shift_status='on_shift'`; тенантный guard (SRS-DOM-037:
      `chainId IS NULL` ИЛИ `chainId = order.pharmacy.chainId`, с учётом `tenant.courierSourcingMode` —
      `own_fleet` исключает `chainId IS NULL`, `platform_pool` исключает `chainId=X`, `hybrid` включает
      оба, ранжирует `own_fleet` выше при равном скоре); cold-chain guard (SRS-DOM-038, если
      `requiresColdChain` — `courier.coldChainCertified` обязателен); текущая нагрузка
      `< MAX_CONCURRENT_ASSIGNMENTS_PER_COURIER` (ASSUMPTION 2, конфигурируемо per-tenant); дистанция
      `≤ COURIER_CANDIDATE_RADIUS_KM` (ASSUMPTION 8, per-tenant); `last_location_at` не старше
      `COURIER_LOCATION_STALE_MINUTES` (ASSUMPTION 15).
   б. Скоринг: `distanceScore = max(0, 1 - distanceKm / COURIER_CANDIDATE_RADIUS_KM)`;
      `workloadScore = 1 / (1 + activeAssignmentsCount)`; `ratingScore = courier.ratingAvg / 5`;
      `totalScore = W_DISTANCE×distanceScore + W_WORKLOAD×workloadScore + W_RATING×ratingScore`
      (ASSUMPTION `W_DISTANCE=0.5, W_WORKLOAD=0.3, W_RATING=0.2`, `Σ=1`, ENV-конфигурируемо per-tenant —
      НЕ хардкод-константы в коде, а читаемые из конфигурации тенанта/дефолт из ENV, C6).
   в. Возвращает отсортированный по `totalScore` убыв. список кандидатов — сам НЕ создаёт офферы (это
      DTJ-315).
4. `DeliveryFacade.calculateDeliveryFee` — сигнатура объявляется здесь (используется чекаутом EP-09/
   EP-10 уже в волне 6, до готовности DTJ-322), полная реализация формулы — DTJ-322; в этом тикете —
   временная реализация, бросающая `NotImplementedError`, ЛИБО минимальная заглушка с фиксированной
   ставкой, явно помеченная TODO со ссылкой на DTJ-322 (решение — на усмотрение разработчика, главное —
   сигнатура стабильна для потребителей с первого дня).
5. `DeliveryFacade.hasActiveAssignment(orderId)`/`getActiveAssignment(orderId)` — простые query-методы
   поверх репозитория (нетерминальный статус — не `delivered`/`delivery_failed`).

## Критерии приёмки

Given 2 кандидата в радиусе: А (1км, загрузка 0, рейтинг 4.0), Б (0.5км, загрузка 1, рейтинг 5.0) с
весами по умолчанию (0.5/0.3/0.2), When `SuggestNearestCourierUseCase.execute()`, Then скоры вычислены по
формуле, победитель — с бо́льшим `totalScore` (детерминированный unit-тест на конкретных числах,
TC-DELIV-034).

Given курьер `shift_status='off_shift'`, When тот же запрос выполняется, Then курьер исключён из
кандидатского списка на шаге фильтра (негативный тест, TC-DELIV-035).

Given курьер `chain_id='X'` (свой флот), заказ сети `Y`, When алгоритм оценивает кандидата, Then кандидат
исключён из скоринга тенантным guard'ом (SRS-DOM-037, негативный тест, TC-DELIV-007 применительно к
алгоритму, не к прямому `assign-manual`).

## Тест-план

Unit: `SuggestNearestCourierUseCase` с замоканным `CourierCandidatePort` — фильтр приемлемости (7
независимых условий, каждое отдельным кейсом отключения одного кандидата), формула скоринга (детерминиро-
ванный расчёт на фиксированных числах), сортировка результата.
Интеграционные: `PostgisCourierCandidateAdapter` — реальный `ST_DWithin`-запрос на тестовой БД с несколькими
курьерами на разных дистанциях, проверка корректности возвращаемой дистанции.
Порог покрытия application — 90%.

## Риски и подводные камни

`calculateDeliveryFee` нужен модулю `orders`/чекауту (EP-09, волна 6) РАНЬШЕ, чем этот модуль (`delivery`,
волна 9) успевает его полноценно реализовать (DTJ-322) — таймлайн-конфликт, зафиксированный самим SRS
документом как открытый вопрос («Открытые вопросы» модуля 25 п.2 косвенно, здесь — прямая временна́я
нестыковка волн). Решение: объявить сигнатуру и вернуть заглушку с ЯВНОЙ пометкой в PR-описании и уведомить
владельца EP-09 о временном поведении, чтобы чекаут не считал заглушечное значение финальным без
дополнительной проверки после готовности DTJ-322. Точные веса/радиусы/таймауты — ASSUMPTION, подлежат
калибровке по эксплуатационным данным (SRS-DELIV-038, `04-SCOPE-DECISION-PIVOT.md` §7) — не блокирует
реализацию, но требует конфигурируемости с первого дня, не хардкода «на потом».
- Файл `apps/api/src/modules/delivery/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
