## Задача

Первый экран после логина: курьер обязан явно начать смену, прежде чем ему начнут поступать офферы
(алгоритм подбора фильтрует по `shift_status='on_shift'`, DTJ-314) — без этого экрана курьер не может
попасть в рабочий поток вовсе.

## Технический контекст

`apps/courier/src/features/shift/**` — маршрут `/shift`. Использует `POST /courier-shifts`/
`POST /courier-shifts/:id/end` (DTJ-320). Первый экран приложения после `/login` — редирект сюда
происходит автоматически.

## Что сделать

1. `ShiftPage` — состояние `off_shift`: кнопка «Начать смену» (крупная, ≥56×56px — критичное действие
   старта рабочего потока). Состояние `on_shift`: сводка текущей смены (`opening_cash_on_hand_diram`,
   собрано за смену — `courier_shifts.cash_collected_diram`, живой счётчик, обновляется при получении
   заказов), кнопка «Закончить смену».
2. Кнопка «Начать смену» → `POST /courier-shifts`. Given `409 SHIFT_ALREADY_ACTIVE` (гонка — смена уже
   была начата с другого устройства), Then показать текущее состояние смены вместо ошибки (не блокировать
   пользователя техническим кодом).
3. Кнопка «Закончить смену» → форма ввода `cashSubmittedDiram` (числовое поле, подсказка «сколько сдаёте»)
   → `POST /courier-shifts/:id/end`. Given `422 ACTIVE_ASSIGNMENT_BLOCKS_SHIFT_END`, Then сообщение
   «Нельзя закончить смену — у вас есть активная доставка» со ссылкой на переход к `/active/:id`.
4. Успешное завершение смены → показать `discrepancy_diram`, если он не равен нулю (информационное
   сообщение, не блокирующее — курьер физически уже закончил работу).
5. Каждое действие — видимый отклик ≤150мс, `loading`-состояние не меняет размеры кнопки (SRS-UX-020).

## Критерии приёмки

Given `off_shift`, When нажата «Начать смену» и запрос успешен, Then экран переключается в состояние
`on_shift`, показывается сводка с нулевым «собрано за смену».

Given есть активная доставка, When курьер пытается «Закончить смену», Then показывается блокирующее
сообщение со ссылкой на активную доставку, смена НЕ закрывается (негативный тест).

Given смена закрыта с расхождением `discrepancy_diram=500`, When подтверждение отправлено, Then экран
показывает информацию о расхождении, курьер переводится обратно в состояние `off_shift`/на экран логина
следующей смены.

## Тест-план

Unit: `model` вычисления сводки смены (форматирование сумм, состояние disabled кнопки «Закончить смену»
при активном назначении, если это состояние доступно клиенту заранее).
Компонентные: `ShiftPage` — оба состояния (`off_shift`/`on_shift`), обработка `409`/`422`.
Порог покрытия — 70%.

## Риски и подводные камни

Живой счётчик «собрано за смену» технически требует либо периодического рефетча, либо WS-события —
модуль `delivery` (DTJ-320) не публикует отдельного WS-события на изменение `cash_collected_diram`;
простое решение — обновлять сводку по факту завершения каждой доставки (`delivery.failed`/успешный
`deliver` — событие приходит на активную доставку, DTJ-323), не заводить отдельный WS-канал специально
для этого счётчика (минимальная сложность, `02` C15).
