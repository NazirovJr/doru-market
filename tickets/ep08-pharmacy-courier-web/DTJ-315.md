## Задача

Как только фармацевт завершает сборку (`OrderPickedUpEvent`, DTJ-305 модуля EP-12), система обязана
немедленно начать искать курьера — иначе собранный заказ физически лежит в аптеке без движения. Этот
тикет — вся цепочка «создать назначение → предложить первому кандидату → курьер принимает/отклоняет →
при отказе/таймауте эскалировать следующему», реализующая REQ-DELIV-2 без участия диспетчера в
happy-path.

## Технический контекст

`OrderPickedUpEventHandler` подписан на существующее доменное событие `OrderPickedUpEvent` (публикуется
модулем `orders`, DTJ-305 из EP-12) через `outbox` — межмодульная граница, НЕ прямой вызов (`02` §1.2).
Использует `SuggestNearestCourierUseCase` (DTJ-314) для получения кандидата, `OrdersFacade` (публичный
фасад модуля `orders`, уже существует) для чтения снапшота адреса/суммы заказа при необходимости.

## Что сделать

1. `OrderPickedUpEventHandler` → `CreateDeliveryAssignmentUseCase.execute(orderId)`: given уже есть
   активное (нетерминальное) назначение для `orderId` (идемпотентность обработчика при повторной доставке
   события, SRS-DOM-036), Then завершить без действия. Иначе: `DeliveryAssignment.create()`,
   `requiresColdChain` вычисляется в этот же момент как `OR` по всем `order_items.medicine_id →
   medicines.requires_cold_chain` заказа (снапшот, НЕ живой JOIN при каждой проверке — стабильность
   аудита). В ТОЙ ЖЕ транзакции — вызвать `SuggestNearestCourierUseCase`, создать первый
   `delivery_offers(sequence_no=1, status='pending', expires_at = now + OFFER_ACCEPT_TIMEOUT_SECONDS)`
   (ASSUMPTION 45с), запланировать BullMQ delayed job `delivery-offer-timeout` (`jobId=offerId`).
   Публикует `DeliveryOfferCreatedEvent` → WS `delivery.offer_created` в `courier:{courierId}` (комнату
   создаёт/использует DTJ-323).
2. `GET /api/v1/delivery-offers?status=pending` — офферы, адресованные ТЕКУЩЕМУ курьеру (`courierId` из
   JWT, implicit scope `own`). Точный адрес/ориентир/телефон клиента НЕ раскрывается до `accept`
   (минимизация утечки ПДн). Ответ: `id, deliveryAssignmentId, sequenceNo, distanceMeters, expiresAt,
   pharmacy: { name, addressText, geoPoint }, orderSummary: { itemsCount, requiresColdChain,
   paymentMethod, estimatedDeliveryFeeDiram }`.
3. `POST /api/v1/delivery-offers/:id/accept` — `AcceptDeliveryOfferUseCase`. Given `status='pending'` И
   `courier.id=актор` И `now() <= expires_at`, When accept, Then атомарно: `offer.status='accepted'`,
   `responded_at=now()`, `DeliveryAssignment.assign(courierId)` (тенантный/cold-chain guard'ы применяются
   здесь через доменный метод), BullMQ-таймаут ЭТОГО оффера отменяется, публикуется
   `CourierAssignedEvent`/WS `delivery.courier_assigned` (комнаты `customer:{id}`, `pharmacy:{id}`,
   `courier:{id}` — уточняется в DTJ-323). Given `now() > expires_at` (гонка) → `409 OFFER_EXPIRED`. Given
   `status != 'pending'` → `409 OFFER_ALREADY_RESPONDED`.
4. `POST /api/v1/delivery-offers/:id/decline { reason?: string }` — `DeclineDeliveryOfferUseCase`. Given
   оффер `pending` и принадлежит актору, Then `offer.status='declined'`, немедленно триггерится эскалация
   к следующему кандидату (вызов того же механизма, что и обработчик таймаута — общий приватный метод
   `escalateToNextCandidate`, не дублировать логику, `02` C15).
5. `DeliveryOfferTimeoutProcessor` (BullMQ, `delay=OFFER_ACCEPT_TIMEOUT_SECONDS`, `jobId=offerId`
   идемпотентен при повторном планировании): given оффер всё ещё `pending` на момент срабатывания, Then
   `offer.status='expired'`, следующий кандидат из уже вычисленного списка (кэшированного на весь цикл
   эскалации ОДНОГО назначения) получает `sequence_no+1` оффер; список пересчитывается, если прошло
   `> RECANDIDATE_AFTER_MINUTES` (ASSUMPTION 5) с момента исходного расчёта. Given список кандидатов
   исчерпан (все `pending`→`expired`/`declined`) — публикует `DeliveryEscalatedToPoolEvent` (§A.6) →
   `platform:ops` + `chain:{chainId}` (для `own_fleet`).
6. RBAC: `GET`/`accept`/`decline` — роль `courier`, только собственные офферы (`courierId` из JWT).

## Критерии приёмки

Given оффер `pending`, `expires_at` в будущем, курьер — адресат, When `POST .../accept`, Then `200`,
`DeliveryAssignment.status='assigned'`, WS `delivery.courier_assigned` опубликовано (TC-DELIV-001).

Given оффер `pending`, `expires_at` в прошлом (гонка), When `POST .../accept`, Then `409 OFFER_EXPIRED`
(негативный тест, TC-DELIV-002).

Given список кандидатов исчерпан (все `declined`/`expired`), When таймаут последнего оффера срабатывает,
Then `DeliveryEscalatedToPoolEvent` опубликовано, назначение видно в `GET .../available-pool` (DTJ-316,
интеграционный чек через прямой запрос к БД в рамках этого теста — TC-DELIV-005).

Given два устройства курьера одновременно жмут «Принять» на один оффер, When конкурентные запросы,
Then `ux_delivery_offers_one_pending_per_assignment` + проверка `status='pending'` в транзакции делают
вторую попытку неатомарной — один получает `200`, другой `409 OFFER_ALREADY_RESPONDED` (негативный тест,
TC-DELIV-071).

## Тест-план

Unit: `CreateDeliveryAssignmentUseCase` — идемпотентность при повторном `OrderPickedUpEvent`,
`requiresColdChain` вычисление (снапшот из нескольких позиций); `AcceptDeliveryOfferUseCase`/
`DeclineDeliveryOfferUseCase` — все ветки ошибок; общий метод эскалации — вызывается корректно и из
таймаут-джоба, и из `decline` (проверка отсутствия дублирования логики).
Интеграционные: TC-DELIV-001..005, TC-DELIV-071 (реальная конкурентная транзакция), тест полной цепочки
эскалации на 3 кандидатах (первый declines → второй молчит до timeout → третий accepts).
Порог покрытия application — 90%.

## Риски и подводные камни

Зависит от того, что `OrderPickedUpEvent` в EP-12 (DTJ-305) публикует ТОЧНО тот payload
(`orderId, handoverOtpIssuedAt, sealedBagConfirmed`), который ожидается здесь — свериться перед
реализацией, а не полагаться на предположение. Кэширование списка кандидатов «на весь цикл эскалации» —
требует явного решения, где он хранится (Redis с TTL, отдельная таблица, in-memory джоб-контекст) —
зафиксировать выбор в PR, минимальная сложность предпочтительна (`02` C15) — вероятно, Redis-ключ
`delivery-candidates:{assignmentId}` с TTL `RECANDIDATE_AFTER_MINUTES`.
