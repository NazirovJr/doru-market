## Задача

Терминал фармацевта (`24-module-pharmacy-terminal.md`, Часть A) реализуется поверх уже существующего
контекста `orders`, но требует доменных расширений, отсутствующих в базовой схеме `11-database-schema.md`:
прогресс сканирования позиции, мягкую блокировку «кто ведёт сборку», запрос подтверждения частичной
сборки и параметры SLA/OTP терминала в `tenant_settings`. Это подготовительный тикет — все последующие
use case-тикеты EP-12 (DTJ-301..309) физически не могут стартовать без этих таблиц/VO/ошибок/событий,
и дублирование их создания в каждом тикете нарушило бы DRY (`02` C15).

## Технический контекст

Слой `domain` модуля `orders` (`apps/api/src/modules/orders/domain/**`). Новый backend-модуль
`pharmacy-terminal` НЕ создаётся (SRS-PHT-001) — это presentation-поверхность над `orders`. Все
дополнения — аддитивные (`ALTER TABLE`/новые таблицы), базовые имена/типы колонок `11-database-schema.md`
не меняются (Charter §5). Domain-ошибки — свои классы (`02` §2.5), не `HttpException`; маппинг на HTTP
происходит в `presentation` (тикеты DTJ-301..306). Zod-контракты — в `packages/contracts` (Charter §3.2),
барабанный `index.ts` уже владеет EP-01 (см. `tickets/00-EPICS.md` «Пересекающееся владение» п.3) — этот
тикет добавляет ТОЛЬКО новый файл в `src/orders/` и одну строку экспорта в существующий баррель, не
трогает сам баррель-файл целиком.

## Что сделать

1. Миграция `apps/api/migrations/00xx_pharmacy_terminal_schema.sql` (номер — следующий свободный после
   последней миграции EP-10/EP-11 на момент старта; согласовать по `git log` миграций перед PR):
   - `CREATE TYPE order_item_fulfillment_status AS ENUM ('pending', 'scanned_ok', 'unavailable');`
   - `ALTER TABLE orders ADD COLUMN assigned_pharmacist_id UUID REFERENCES users(id) ON DELETE SET NULL;`
   - `ALTER TABLE order_items ADD COLUMN fulfillment_status order_item_fulfillment_status NOT NULL DEFAULT 'pending', ADD COLUMN scanned_batch_id UUID REFERENCES inventory_batches(id) ON DELETE SET NULL, ADD COLUMN scanned_at TIMESTAMPTZ, ADD COLUMN scanned_by UUID REFERENCES users(id) ON DELETE SET NULL, ADD COLUMN scan_method VARCHAR(10) CHECK (scan_method IN ('camera','manual') OR scan_method IS NULL), ADD COLUMN item_issue_reason VARCHAR(30) CHECK (item_issue_reason IN ('out_of_stock','expired_on_shelf','damaged_packaging') OR item_issue_reason IS NULL);`
   - `CREATE TYPE partial_fulfillment_status AS ENUM ('awaiting_customer', 'confirmed', 'rejected', 'auto_confirmed_timeout');`
   - `CREATE TABLE order_partial_fulfillment_requests (...)` — точная структура из
     `24-module-pharmacy-terminal.md` §«Дополнения к схеме БД» (включая `chk_partial_fulfillment_amounts`
     и `ux_partial_fulfillment_one_active`).
   - `ALTER TABLE tenant_settings ADD COLUMN partial_fulfillment_confirmation_timeout_minutes INT NOT NULL DEFAULT 10, ADD COLUMN handover_otp_max_regenerations_per_order INT NOT NULL DEFAULT 20, ADD COLUMN handover_otp_regenerate_min_interval_seconds INT NOT NULL DEFAULT 60, ADD CONSTRAINT chk_tenant_settings_pht_ranges CHECK (...);`
2. Обновить Drizzle-схемы: `apps/api/src/db/schema/orders.ts` (новый enum + колонки `order_items`/`orders`),
   новый файл `order-partial-fulfillment-requests.ts`, обновить `tenant-settings.ts`.
3. `OrderItemFulfillmentStatus` — VO-обёртка над enum (не примитивная строка в сигнатурах use case, `02` §2.3).
4. Семь доменных ошибок (файл на класс, `02` C17): `OrderAlreadyClaimedError` (409/`ORDER_ALREADY_CLAIMED`),
   `ItemNotInOrderError` (404/`ORDER_ITEM_NOT_FOUND`), `ItemAlreadyScannedError` (409/`ITEM_ALREADY_SCANNED`),
   `BatchNotAvailableForSubstitutionError` (422/`BATCH_NOT_AVAILABLE`), `SealConfirmationRequiredError`
   (400/`SEAL_CONFIRMATION_REQUIRED`), `PendingCustomerConfirmationError` (409/`PARTIAL_FULFILLMENT_PENDING`),
   `HandoverOtpNotFoundError` (404/`HANDOVER_OTP_NOT_FOUND`). Каждая несёт `code`-константу, используемую
   presentation-мапперами последующих тикетов.
5. Пять доменных событий (payload — см. таблицу модуля 24 «Новые доменные события»): `OrderClaimedEvent`,
   `OrderReclaimedEvent`, `PartialFulfillmentProposedEvent`, объединённое семейство
   `PartialFulfillmentConfirmedEvent`/`RejectedEvent`/`AutoConfirmedEvent` (один файл, три экспортируемых
   класса с общим базовым payload-типом — оправданная общая абстракция, у неё уже 3 потребителя
   изначально, `02` C15), `HandoverOtpRegeneratedEvent`. Публикация через `outbox` — существующий паттерн

6. `packages/contracts/src/orders/pharmacy-terminal.contracts.ts` — Zod-схемы запросов/ответов для ВСЕХ
   эндпоинтов части A (тела `accept`/`reclaim`/`scan`/`report-issue`/`propose-partial-fulfillment`/

   последующими тикетами как единственный источник DTO-типов (Charter §3.2, генерация клиента из
   `openapi.json` в R2 опирается на эти же схемы).
7. Добавить одну строку экспорта новых Zod-схем в существующий баррель `packages/contracts/src/index.ts`

## Критерии приёмки

Given применена миграция `00xx_pharmacy_terminal_schema.sql` на чистой БД с уже накатанной базовой схемой,
When выполняется `pnpm db:migrate`, Then миграция проходит без ошибок и `order_item_fulfillment_status`/
`partial_fulfillment_status` видны в `information_schema.enum`.

Given таблица `order_partial_fulfillment_requests` содержит одну запись `status='awaiting_customer'` для
`order_id=X`, When приложение пытается вставить вторую запись `status='awaiting_customer'` для того же
`order_id`, Then вставка отклоняется констрейнтом `ux_partial_fulfillment_one_active` (негативный тест).

Given `items_total_before_diram=10000`, `items_total_after_diram=7000`, `refund_amount_diram=2000`,
When строка вставляется, Then констрейнт `chk_partial_fulfillment_amounts` проходит; при
`refund_amount_diram=1999` (не равном разнице) — вставка отклоняется (негативный тест).

## Тест-план

Unit: `OrderItemFulfillmentStatus` VO — валидные/невалидные значения; каждый доменный класс ошибки —
корректный `code`/`httpStatus`; сериализация каждого доменного события в payload, соответствующий таблице
спецификации. Zod-контракты — round-trip parse/serialize для каждого тела запроса части A с валидными и
заведомо невалидными данными (пустой `rawBarcode`, `sealConfirmed` не boolean).
Интеграционные: миграция вверх/вниз (`db:migrate`/rollback) на тестовой БД; констрейнты БД (см. критерии
приёмки выше) — выполняются реальными SQL-запросами к тестовому контейнеру Postgres, не моками.
Порог покрытия domain — 90% (`02` §6).

## Риски и подводные камни

Номер файла миграции конфликтует при параллельной разработке с EP-11 (Возвраты) и EP-16 — оба тоже
активны в соседних волнах и могут занять тот же порядковый номер; решается rebase перед мержем, не
блокирует работу. `assigned_pharmacist_id` и `order_items.*` — колонки таблиц, принадлежащих базовой схеме
EP-01 (`orders`, `order_items`) — технически это ALTER чужой таблицы; так же поступает и модуль 25
(`orders.delivery_entrance` и т.п.) — паттерн одобрен архитектором (`Charter §5: «расширения допускаются»`),
но требует ревью совместно с владельцем `apps/api/src/modules/orders/domain,application/{cart,checkout}`
(EP-09/EP-10), чтобы не конфликтовать с их одновременными миграциями той же таблицы.
