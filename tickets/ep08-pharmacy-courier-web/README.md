## Область R1 этого пакета тикетов

- **EP-12** — Часть A модуля 24 (API-контракт терминала фармацевта) целиком + веб-реализация в
  `apps/pharmacy`. **Часть B (Flutter `apps/pharmacy_mobile`) — R2, вне этого пакета.**
- **EP-13** — Часть A модуля 25 (API-контракт курьера/диспетчера) целиком + веб-реализация в
  `apps/courier`. **Часть B (Flutter `apps/courier_mobile`) — R2, вне этого пакета.**

## Важное решение: разрешение конфликта между `01-TECH-BASELINE.md` и `docs/spec/30-ux-screens-and-flows.md`

`docs/spec/30-ux-screens-and-flows.md` описывает терминал фармацевта как раздел `/admin/order-queue`
внутри `apps/admin`, а курьера — как раздел `/courier/*` внутри `apps/web`. Одновременно
`01-TECH-BASELINE.md` §«Frontend» (приоритет ВЫШЕ, чем `docs/spec/*`, по иерархии документов проекта)
явно перечисляет **четыре раздельных** фронтенд-приложения: `apps/web`, `apps/pharmacy`, `apps/courier`,
`apps/admin`. `tickets/00-EPICS.md` (владение файлами по эпикам) согласуется именно с
`01-TECH-BASELINE.md`.

**Решение, принятое этим пакетом тикетов**: реализовать `apps/pharmacy` (DTJ-310..312) и `apps/courier`
(DTJ-325..332) как ОТДЕЛЬНЫЕ React-приложения со своими корневыми маршрутами (без префиксов
`/admin`/`/courier` — они больше не подразделы чужого приложения), сохранив контент/поведение/тексты
каждого экрана из `30-ux` без изменений. Причина — `01-TECH-BASELINE.md` стоит выше `docs/spec/30-ux` в
иерархии документов проекта. Это решение зафиксировано в DTJ-310 и DTJ-325 и требует синхронизации с
тимлидами `apps/web`/`apps/admin`, чтобы те же экраны не были продублированы в их приложениях.

## Известные точки координации с другими эпиками

- **DTJ-300 / DTJ-313** — оба ALTER'ят таблицу `orders`, принадлежащую EP-09/EP-10/EP-12 совместно;
  согласовать порядок номеров миграций перед мержем.
- **DTJ-304** — частичный рефанд использует `PaymentProvider.capabilities()`/`partiallyRefund()` —
  сверить точный контракт с EP-10 (Payments) до реализации.
- **DTJ-306 / DTJ-317** — регенерация/перевыпуск OTP вручения дублируются между модулями (терминал и
  курьер обращаются к одному и тому же переключению `handover_otp_id`); согласовать общий доменный
  сервис, не дублировать логику.
- **DTJ-314** — `DeliveryFacade.calculateDeliveryFee` нужен чекауту EP-09 раньше, чем этот эпик успевает
  его полноценно реализовать (DTJ-322) — временная заглушка с явным уведомлением владельца EP-09.
- **DTJ-306 / DTJ-320** — оба используют `AuditLogPort`, инфраструктура которого — зона EP-16 (более
  поздняя волна); допустим временный локальный адаптер с последующей заменой.
- **DTJ-318** — подписывается на `AdminForceCancelOrderUseCase`/`OrderCancelledEvent`, реализуемые вне
  этого модуля (EP-09/EP-15) — сверить фактический payload события.
- **DTJ-321** — генерация батчей `courier_payouts` (сама выплата) не входит в этот пакет тикетов —
  вероятная зона EP-10 (`apps/worker/src/jobs/payout/**`), уточнить владение отдельно.
- **DTJ-310 / DTJ-325** — архитектурное решение «отдельные приложения `apps/pharmacy`/`apps/courier`»
  требует синхронизации с тимлидами `apps/web`/`apps/admin`, чтобы избежать дублирования экранов.
- **DTJ-325** — регистрация нового workspace `apps/courier` в корневых конфигах — согласовать с
  владельцем EP-19 (единственный владелец корневых конфигов).

## Пропущенные/отсутствующие SRS-ссылки

Все `srs_refs` во всех 33 тикетах проверены на фактическое существование в `docs/spec/*.md`
(`SRS-PHT-*`, `SRS-DELIV-*`, `SRS-DOM-*`, `SRS-API-*`, `SRS-DB-*`, `SRS-UX-*`) — пропусков не
обнаружено. Единственный содержательный открытый вопрос без ID — механика перехода
`en_route_to_pharmacy → picked_up_from_pharmacy` (SRS-DOM-140) не имеет отдельного REST-эндпоинта нигде
в письменной спецификации модуля 25; решение зафиксировано в DTJ-317/DTJ-328 (атомарное объединение с
`depart-to-customer`) на основании визуального дизайн-референса, не отдельного письменного требования —
подлежит подтверждению при ревью архитектором.
