## Задача

Первый экран, который видит фармацевт, открыв терминал: список заказов, ждущих сборки, разбитый на
«Новые» (`paid_escrow`/`confirmed`) и «В сборке» (`processing`), с обязательным звуковым+визуальным
оповещением на новый заказ (SRS-UX-007 — двойной канал для критичных событий, применимо и к R1-веб). Это
UX-точка входа во всю сборку — без неё фармацевт физически не узнаёт о новом заказе иначе как вручную
обновляя страницу.

## Технический контекст

`apps/pharmacy/src/features/order-fulfillment/**` — новая фича внутри `apps/pharmacy` (feature-oriented,
`02` §5), НЕ трогает `features/inventory-manual/**` (владение EP-05, «Пересекающееся владение» п.2
`tickets/00-EPICS.md`). Примечание по разрешению конфликта источников: `tickets/00-EPICS.md` (владение
файлами) фиксирует `apps/pharmacy` как отдельное React-приложение — это СОГЛАСУЕТСЯ с
`01-TECH-BASELINE.md` §«Frontend» (`apps/web`, `apps/pharmacy`, `apps/courier`, `apps/admin` — четыре
раздельных приложения), который стоит ВЫШЕ `docs/spec/30-ux-screens-and-flows.md` в иерархии документов;
там, где `30-ux` описывает те же экраны как `/admin/order-queue` внутри `apps/admin`, здесь ЭТО
ПЕРЕОПРЕДЕЛЕНИЕ РАЗРЕШЕНО в пользу `01-TECH-BASELINE.md` — реализовать как корневые маршруты `/`
(список) и `/orders/:id` (сборка) ВНУТРИ `apps/pharmacy`, приняв контент/поведение экрана из `30-ux`
(секции, состояния, тексты) без изменений, только с другим физическим приложением-контейнером. Данные —
TanStack Query (`02` §5), WS — общий `RealtimeClient` (уже развёрнутая инфраструктура, переиспользуется).

## Что сделать

1. `OrderQueuePage` (маршрут `/`) — две секции: «Новые» (`status IN paid_escrow, confirmed`, сортировка
   FIFO) и «В сборке» (`status='processing'`, сортировка по `slaDeadlineAt`), карточка заказа —
   `orderNumber`, `itemsCount`, `itemsTotalTjs`, `paymentMethod`-иконка, `prescriptionRequired`-бейдж,
   `assignedPharmacistName` (если занят — бейдж «В работе: Фарзона М.», кнопка «Принять» СКРЫТА, доступно
   долгое нажатие/контекстное меню «Перехватить»).
2. `GetOrderQueueUseCase`-обёртка через TanStack Query хук `useOrderQueue()` — REST-запрос
   `GET /orders?filter[pharmacyId]&filter[status][in]=paid_escrow,confirmed,processing&sort=priority`;
   для `pharmacy_admin` без явного выбора точки — агрегированный вид по `meta.groupedBy` (заголовок
   секции — название точки).
3. Кнопка «Принять» на карточке «Новые» → `POST /orders/:id/accept` с `Idempotency-Key = uuid.v4()`,
   генерируемым В МОМЕНТ клика (не при монтировании компонента) — оптимистичный UI-переход карточки в
   «В сборке» до подтверждения ответа, откат при ошибке `409 ORDER_ALREADY_CLAIMED` с уведомлением «Заказ
   уже принят коллегой».
4. WS-подписка на комнату `pharmacy:{pharmacyId}` (DTJ-308 события): `order.paid`/`order.claimed`/
   `order.reclaimed`/`order.cancelled` — точечный патч списка (insert/remove/update одной карточки), БЕЗ
   полного рефетча (минимизация моргания списка). При реконнекте — ОБЯЗАТЕЛЬНЫЙ REST catch-up ДО
   повторной подписки (SRS-PHT-037).
5. Звуковое+визуальное оповещение на `order.paid` (SRS-UX-007/025): `<audio>`-элемент, разблокируемый
   явным жестом пользователя на экране (например, кнопка «Начать смену» ИЛИ первое взаимодействие со
   страницей — браузерная политика автовоспроизведения требует жеста; выбрать конкретный жест-триггер и
   зафиксировать в реализации) + мигающий/полноэкранный визуальный баннер «Новый заказ №{orderNumber}».
   Отдельный аудио-ассет для нового заказа (НЕ путать со звуком синхронизации 1С/SLA-эскалации — те вне
   зоны этого тикета).
6. При потере WS-соединения — `OfflineBanner` «Нет соединения — новые заказы могут не отображаться
   немедленно» + активный REST-поллинг раз в 10 секунд как деградация (SRS-UX-025), до восстановления
   `auth_ok`.
7. `LanguageSwitcher` в шапке (SRS-UX-027 — доступен на ВСЕХ экранах, не только на этом).
8. Тап-зоны карточек/кнопок ≥48×48px, критичные действия («Принять») — ≥56×56px (кабинет аптеки,
   `32-design-reference.md` расхождение №4).

## Критерии приёмки

Given открыт `/` (очередь), новый заказ поступает через WS `order.paid`, When событие получено, Then
карточка появляется в секции «Новые» БЕЗ полного рефетча, воспроизводится звук + показывается визуальный
баннер (после разблокировки звука явным жестом ранее в сессии).

Given WS-соединение разорвано на 30 секунд, When эмулируется сетевой сбой, Then REST-поллинг очереди
происходит раз в 10с, виден баннер «Нет соединения», после восстановления связи очередь синхронизируется
через REST-дельту (TC-UX-016).

Given фармацевт нажимает «Принять» на карточке, которую в этот момент уже принял коллега (гонка), When
ответ `409 ORDER_ALREADY_CLAIMED` приходит, Then оптимистичное обновление карточки откатывается, карточка
показывает «В работе: {имя коллеги}», кнопка «Принять» скрывается (негативный сценарий).

## Тест-план

Unit (`model/order-queue.model.ts`): сортировка/группировка секций, точечный WS-патч списка (insert/
remove/update — три отдельных кейса), логика деградации до поллинга.
Компонентные: `OrderQueuePage` — рендер обеих секций, состояние офлайн-баннера, состояние оптимистичного
accept + откат.
E2E (Playwright, интеграция с EP-19 harness): один заказ появляется через WS → «Принять» → карточка
переходит в «В сборке» — базовый happy-path для CUJ-3' (флаг для EP-19, не блокирует этот тикет).
Порог покрытия — 70% (frontend, `02` §6).

## Риски и подводные камни

Разрешение конфликта источников (`apps/pharmacy` vs `/admin/order-queue`) — сознательное решение этого
тикета в пользу более высокоприоритетного `01-TECH-BASELINE.md`; если тимлид другого эпика (владелец
`apps/admin`) уже начал строить `/admin/order-queue` по букве `30-ux`, требуется явная синхронизация
между тимлидами ДО начала реализации, чтобы не задвоить экран в двух приложениях — зафиксировать выбор в
README эпика (см. `tickets/ep08-pharmacy-courier-web/README.md`). Автовоспроизведение звука без жеста
пользователя блокируется всеми современными браузерами — точный UX разблокировки (кнопка/баннер «Включить
звук») требует отдельного дизайн-решения, не покрытого `32-design-reference.md` явно для этого экрана.
