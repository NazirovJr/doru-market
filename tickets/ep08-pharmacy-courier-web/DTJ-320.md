## Задача

Смена — единица физического учёта наличных курьера: сколько было на начало, сколько собрано за
`cash_courier`-заказы, сколько сдано при закрытии. Без явного открытия/закрытия смены нет опорной точки
для алгоритма назначения (`shift_status='on_shift'` — жёсткий фильтр приемлемости, DTJ-314) и нет способа
зафиксировать расхождение наличных для последующего административного разбора.

## Технический контекст

`apps/api/src/modules/delivery/application/**`, работает с `courier_shifts` (DTJ-313). Расхождение при
закрытии смены пишется в `audit_log` с новым значением enum `cash_reconciliation_discrepancy` (добавлено
DTJ-313 отдельной миграцией вне транзакции, SRS-DB-009) — использует существующий `AuditLogPort`
(тот же, что EP-12/DTJ-306 использует для `handover-otp`-просмотров).

## Что сделать

1. `POST /api/v1/courier-shifts` (без тела) — начать смену. Given уже есть `active`-смена (частичный
   уникальный индекс `ux_courier_shifts_one_active`), Then `409 SHIFT_ALREADY_ACTIVE`. Успех:
   `couriers.shift_status='on_shift'`, `courier_shifts` строка создаётся с
   `opening_cash_on_hand_diram = couriers.current_cash_on_hand_diram` (перенос остатка с прошлой смены,
   если инкассация не была полной).
2. `POST /api/v1/courier-shifts/:id/end { cashSubmittedDiram }` — завершить смену. Given есть активное
   (нетерминальное, `assigned`..`en_route_to_customer`) `delivery_assignments` у курьера, Then
   `422 ACTIVE_ASSIGNMENT_BLOCKS_SHIFT_END` — нельзя закрыть смену, пока заказ физически у курьера. Given
   нет активных назначений, When end, Then `status='closed'`, `ended_at=now()`,
   `discrepancy_diram = cash_collected_diram + opening_cash_on_hand_diram - cashSubmittedDiram`,
   `couriers.shift_status='off_shift'`, `couriers.current_cash_on_hand_diram = 0` (передано/
   инкассировано). Given `discrepancy_diram != 0`, Then публикует `CashReconciliationDiscrepancyEvent`
   (не блокирует закрытие смены — курьер физически ушёл домой, расхождение разбирается административно)
   → запись в `audit_log(category='cash_reconciliation_discrepancy')`.
3. RBAC: обе операции — только сам курьер (`courierId` из JWT), над собственной сменой.

## Критерии приёмки

Given активная смена уже есть, When повторный `POST /courier-shifts`, Then `409 SHIFT_ALREADY_ACTIVE`
(негативный тест, TC-DELIV-018).

Given активное назначение (`assigned`) у курьера, When `POST /courier-shifts/:id/end`, Then
`422 ACTIVE_ASSIGNMENT_BLOCKS_SHIFT_END` (негативный тест, TC-DELIV-019).

Given `cash_collected=10000`, `opening=0`, `cashSubmitted=9500`, When `POST /courier-shifts/:id/end`, Then
`discrepancy_diram=500`, `CashReconciliationDiscrepancyEvent` → `audit_log(category=
'cash_reconciliation_discrepancy')` (TC-DELIV-020).

## Тест-план

Unit: `StartCourierShiftUseCase` — перенос `opening_cash_on_hand_diram` из остатка предыдущей смены;
`EndCourierShiftUseCase` — блокировка при активном назначении, вычисление `discrepancy_diram` (три
случая: положительное/отрицательное/нулевое расхождение — событие публикуется только в первых двух).
Интеграционные: TC-DELIV-018..020, полный цикл старт→доставка (мок через прямую вставку тестового
`delivery_assignment`)→попытка закрыть смену (блок)→доставка завершена→успешное закрытие.
Порог покрытия application — 90%.

## Риски и подводные камни

Формула `discrepancy_diram = cash_collected + opening - cashSubmitted` предполагает, что курьер либо
сдаёт ВСЮ сумму, либо часть остаётся при нём на следующую смену (тогда `opening` следующей смены её
учтёт) — если продукт ожидает другую семантику (например, обязательную полную инкассацию каждую смену),
это ASSUMPTION спецификации (SRS-DELIV-006), не решение этого тикета; реализовать строго по формуле
документа, не домысливать бизнес-правило. Зависимость от `AuditLogPort` — та же, что у DTJ-306 (EP-12) —
если инфраструктура ещё не готова к моменту этого тикета, см. риск, описанный там (временный локальный
адаптер с последующей заменой).
