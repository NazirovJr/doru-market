## Задача

Первый тикет фронтенда EP-13: пустой, но полностью настроенный React-проект `apps/courier`
(`01-TECH-BASELINE.md` §«Frontend» — четвёртое из четырёх фронтенд-приложений монорепозитория), с
роутером, авторизацией, API-клиентом и WS-подключением, на который все следующие тикеты (DTJ-326..332)
навешивают конкретные экраны. Без этого скелета ни один экран курьера не имеет места, куда его положить.

## Технический контекст

`apps/courier/**` — новое приложение, структура `02` §5 (`app/pages/features/entities/shared`).
**Разрешение конфликта источников** (то же решение, что в DTJ-310 для `apps/pharmacy`):
`01-TECH-BASELINE.md` §«Frontend» (`apps/web`, `apps/pharmacy`, `apps/courier`, `apps/admin`) стоит выше
в иерархии документов, чем `docs/spec/30-ux-screens-and-flows.md` §3.1, который описывает курьерский
модуль как секцию `/courier/*` ВНУТРИ `apps/web`. Реализовать `apps/courier` как ОТДЕЛЬНОЕ приложение с
корневыми маршрутами `/shift`, `/offers`, `/pool`, `/active/:id`, `/cash/:id`, `/otp/:id`, `/issue/:id`,
`/earnings` (без префикса `/courier`, т.к. это уже не подраздел `apps/web`) — контент/поведение каждого
экрана берётся из `30-ux` §3.1 без изменений, только физический контейнер другой. Зафиксировать это
решение в README эпика (`tickets/ep08-pharmacy-courier-web/README.md`).

## Что сделать

1. Инициализировать `apps/courier` по `01-TECH-BASELINE.md` §«Frontend» (react 19.2, vite 7.3, Tailwind
   v4 CSS-first `@theme`, `react-router` 7, `@tanstack/react-query` 5, `zustand` 5) — те же версии, что
   уже зафиксированы для `apps/web`/`apps/pharmacy`/`apps/admin` (переиспользовать корневые
   `pnpm.overrides`, НЕ дублировать версии локально).
2. `app/` — точка входа, провайдер TanStack Query, провайдер `packages/i18n` (`useT()`), роутер
   (`react-router` 7), глобальные стили (Tailwind + `--brand-*`/`--space-*`/`--radius-*` токены из
   `packages/ui`, если уже готовы к моменту тикета — иначе временный локальный набор токенов с тикетом
   на перенос).
3. Экран `/login` — переиспользовать `PhoneInput`/`OtpInput`-компоненты и поток OTP-логина из
   существующей реализации `apps/web`/`packages/ui` (роль `courier` — тот же `POST /auth/otp/request`/
   `verify`, существующий эндпоинт EP-01, отличается только последующий редирект: на `/shift` вместо `/`).
   НЕ переизобретать логику OTP-логина — переиспользовать существующий хук/фичу, если она уже вынесена в
   `packages/ui`/общий пакет; если нет — минимальная локальная копия с тикетом на вынос в общий пакет
   (`tickets/00-EPICS.md` п.6).
4. `shared/api/` — REST-клиент (TanStack Query хуки поверх `fetch`, НЕ `fetch` напрямую в компонентах,
   `02` §5), JWT-интерцептор (переиспользовать существующий паттерн из `apps/web`).
5. `shared/ws/` — обёртка WS-клиента (`RealtimeClient`, переиспользовать из общего пакета, если уже
   вынесен; иначе — минимальная локальная реализация с реконнектом по экспоненциальному backoff, тот же
   паттерн, что и у других клиентов, SRS-API-054), REST catch-up перед подпиской (SRS-API-053).
6. Circuit breaker на уровне UI (SRS-UX-026): 3 последовательных `502`/`503`/таймаута к одному
   эндпоинту → 60с статичное сообщение вместо повторных попыток по каждому клику, кнопка «Повторить»
   активна только по истечении паузы/pull-to-refresh — реализовать как переиспользуемый хук
   `shared/lib/useCircuitBreaker.ts` (первый потребитель этого приложения, но потенциально переносим в
   `packages/ui` при втором потребителе — не выносить преждевременно, `02` C15).
7. `LanguageSwitcher` в шапке КАЖДОГО экрана (SRS-UX-027), деградация до последнего кэша при полной
   потере сети на read-only экранах (SRS-UX-024).

## Критерии приёмки

Given чистый чекаут репозитория, When выполняется `pnpm --filter courier dev`, Then приложение поднимается
локально, экран `/login` рендерится без ошибок в консоли.

Given курьер вводит верный OTP на `/login`, When логин завершается успешно, Then редирект на `/shift`,
JWT сохранён, последующие API-запросы несут `Authorization: Bearer`.

Given 3 подряд запроса к одному эндпоинту завершились `503`, When четвёртая попытка происходит
автоматически (не по клику), Then запрос НЕ отправляется — показывается статичное сообщение с таймером
60с, кнопка «Повторить» задизейблена до истечения паузы (негативный/защитный тест на UI circuit
breaker).

## Тест-план

Unit: `useCircuitBreaker` — открытие/закрытие по количеству ошибок, автоматический сброс по таймеру.
Компонентные: рендер `app/` shell без роутов внутри (только layout + `LanguageSwitcher` присутствует),
`/login` — happy path и ошибка кода.

## Риски и подводные камни

Регистрация нового `apps/courier` workspace в корневых конфигах (`tsconfig.json`, `turbo.json`,
возможно `.dependency-cruiser.cjs`) формально принадлежит EP-19 («Корневые конфиги… принадлежат только
EP-19», `tickets/00-EPICS.md` «Пересекающееся владение» п.5) — минимальную точечную правку (добавление
пути нового приложения) согласовать с владельцем EP-19 ДО мержа, не редактировать корневые конфиги
самостоятельно без согласования. Если владелец `apps/admin`/`apps/web` уже реализовал курьерский раздел
по `/courier/*` внутри своего приложения к моменту этого тикета — немедленно эскалировать конфликт
тимлидам, это дублирование усилий, которое дешевле остановить на старте, чем после параллельной
разработки полного набора экранов.
