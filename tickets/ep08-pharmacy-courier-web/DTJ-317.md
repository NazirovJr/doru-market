## Задача

Основной рабочий путь курьера после принятия заказа: доехать до аптеки, забрать, доехать до клиента,
получить наличные (если применимо), подтвердить вручение кодом. Это самая длинная и часто вызываемая
цепочка эндпоинтов модуля — прямая реализация CUJ-4' («Доставка через курьерский веб-модуль»).

## Технический контекст

`apps/api/src/modules/delivery/application/**`, все use case вызывают методы существующего (из DTJ-313)
агрегата `DeliveryAssignment`. `record-cash` — единственный эндпоинт всего модуля с ОБЯЗАТЕЛЬНЫМ
`Idempotency-Key` (уже в общей таблице `SRS-API-009` doc 12). `deliver` использует существующий
`OtpCode.verify()` (домен-kernel, SRS-DOM-082) — капчур эскроу идёт ЧЕРЕЗ событие `OrderDeliveredEvent` →
`payments`, НЕ прямой вызов (`02` §1.2 межмодульная граница).

## Что сделать

1. `GET /api/v1/delivery-assignments/mine?status=active|history` — назначения текущего курьера.
   `active` — нетерминальные; `history` — терминальные, курсорная пагинация. ОБЯЗАТЕЛЕН для REST
   catch-up после WS-реконнекта — клиент вызывает его ПЕРВЫМ делом при восстановлении соединения.
2. `GET /api/v1/delivery-assignments/:id` — полная детализация: адрес аптеки, `landmarkText`/
   `landmarkPhotoUrl`/`entrance`/`floor`/`apartment`/`deliveryComment` клиента (только ПОСЛЕ `assign`,
   т.е. `status != 'unassigned'` — иначе `403 FORBIDDEN`), `requiresColdChain`, `paymentMethod`,
   `estimatedDeliveryFeeDiram`, `otpIssued: boolean` (НИКОГДА сам код), `contactAttemptsCount`. Клиентские
   поля адреса читаются через `OrdersFacade.getDeliverySnapshot(orderId)` (не прямой доступ к таблице
   `orders`). Роль `customer` (для СВОЕГО заказа) видит УРЕЗАННУЮ версию: `courierEtaMinutes` вместо
   точных координат курьера (полная реализация ETA — DTJ-319, здесь — заглушка контракта поля).
   Дополнительно — `customerContact: { phoneNumber, isMasked }` через `MaskedCallingPort` (интерфейс +
   `MockMaskedCallingProvider`/`DirectPhoneCallingProvider` — реальная реализация MVP возвращает прямой
   номер, `isMasked: false`, маскирующий шлюз — вне R1, SRS-DELIV-044).
3. `POST /api/v1/delivery-assignments/:id/depart` — `assigned → en_route_to_pharmacy`. Только назначенный
   курьер, иначе `403 FORBIDDEN`.
4. `POST /api/v1/delivery-assignments/:id/depart-to-customer { coldChainBagConfirmed? }` —
   `picked_up_from_pharmacy → en_route_to_customer`. Промежуточный переход `en_route_to_pharmacy →
   picked_up_from_pharmacy` (SRS-DOM-140, актор «courier+pharmacist», условие «заказ уже
   `order.status='picked_up'`, OTP сгенерирован» — ОБА уже истинны к этому моменту, т.к.
   `OrderPickedUpEvent` создаёт `DeliveryAssignment` уже ПОСЛЕ `order.markPickedUp()`, EP-12/DTJ-305) НЕ
   имеет отдельного REST-эндпоинта нигде в части A — `32-design-reference.md` подтверждает это как
   намеренное поведение дизайна: подпись «Забрал» на кнопке курьера показывается «авто, недоступна
   вручную». Реализовать `depart-to-customer` как ОДИН атомарный вызов, переводящий агрегат ЧЕРЕЗ оба
   перехода (`en_route_to_pharmacy → picked_up_from_pharmacy → en_route_to_customer`) за один HTTP-запрос
   — отдельного клиентского действия на промежуточное состояние нет и не вводится. Given
   `requiresColdChain=true` И `coldChainBagConfirmed` отсутствует/`false`, Then
   `422 COLD_CHAIN_BAG_NOT_CONFIRMED`. Успех: `cold_chain_bag_confirmed=true`,
   `cold_chain_bag_confirmed_at=now()`.
5. `POST /api/v1/delivery-assignments/:id/record-cash { collectedDiram, changeDiram }` —
   `Idempotency-Key` ОБЯЗАТЕЛЕН. Только `payment_method='cash_courier'`. Given
   `collectedDiram - changeDiram !== order.totalAmountDiram`, Then `422 CASH_AMOUNT_MISMATCH`. Успех:
   `delivery_assignments.cash_collected_diram/cash_change_diram` заполняются,
   `couriers.current_cash_on_hand_diram += collectedDiram`, инкрементирует
   `courier_shifts.cash_collected_diram` активной смены. Обязателен ДО `deliver` (домен требует —
   SRS-DOM-040).
6. `POST /api/v1/delivery-assignments/:id/deliver { otpCode }` — `en_route_to_customer → delivered`.
   Использует существующий `OtpCode.verify()` → `400 OTP_EXPIRED`/`400 OTP_MISMATCH`/`423 OTP_LOCKED`.
   Успех: публикует `OrderDeliveredEvent` (→ `payments` — `EscrowLedger.captureOnDelivery`, событийно, не
   напрямую), `courier_earnings` строка создаётся ТОЛЬКО для `chainId IS NULL` (REQ-COUR-3), закрывает
   `contact_attempts_count`. Given дубль команды `deliver` ПОСЛЕ успеха (двойной тап/повторная офлайн-
   отправка) — `OtpCode.verify()` уже финализирует OTP при успехе, повторный вызов → `400 OTP_MISMATCH`
   (не `500`, SRS-DELIV-075).
7. `POST /api/v1/delivery-assignments/:id/reissue-handover-otp` — роли `pharmacist`/`support_agent`/
   `super_admin` (НЕ сам курьер — предотвращает перебор кода без участия клиента). `Idempotency-Key` не
   требуется (естественно идемпотентна). Механизм переключения `handover_otp_id` — переиспользовать ТУ ЖЕ
   логику, что и `RegenerateHandoverOtpUseCase` из EP-12 (DTJ-306), если она вынесена в общий
   переиспользуемый доменный сервис; если нет — согласовать с владельцем DTJ-306 общий сервис вместо
   дублирования кода переключения FK (`02` C15).

## Критерии приёмки

Given `payment_method='cash_courier'`, `order.total=6000` diram, When `record-cash {collected:6000,
change:0}`, Then `200`, `couriers.current_cash_on_hand_diram += 6000`,
`courier_shifts.cash_collected_diram += 6000` (TC-DELIV-010).

Given `collected:6000, change:500` при `order.total=6000`, When `record-cash`, Then
`422 CASH_AMOUNT_MISMATCH` (6000-500≠6000, негативный тест, TC-DELIV-011).

Given верный OTP, TTL не истёк, When `POST .../deliver`, Then `200`, `status='delivered'`,
`OrderDeliveredEvent` опубликован, `courier_earnings` строка создана (если `chainId IS NULL`)
(TC-DELIV-013).

Given `cash_courier`-заказ, `recordCash` НЕ вызван, When `POST .../deliver`, Then домен отклоняет
(`recordCash` — предусловие, негативный тест, TC-DELIV-012).

## Тест-план

Unit: каждый use case отдельно — `DepartUseCase`/`DepartToCustomerUseCase` (guard `actor.courierId ===
assignment.courierId`), `RecordCashUseCase` (сумма-констрейнт), `DeliverUseCase` (три ветки OTP-ошибок +
успех + дубль-после-успеха), `ReissueHandoverOtpUseCase` (роли).
Интеграционные: TC-DELIV-009..013, TC-DELIV-075 (дубль deliver после успеха — не `500`), полный
последовательный проход `assigned→en_route_to_pharmacy→picked_up_from_pharmacy→en_route_to_customer→
delivered` одним интеграционным сценарием.
Порог покрытия application — 90%.

## Риски и подводные камни

Дублирование логики регенерации/переключения `handover_otp_id` между EP-12 (DTJ-306) и этим тикетом —
явный риск нарушения DRY (`02` C15, третье повторение уже здесь: терминал регенерирует, курьер
регенерирует через `reissue`, оба — по сути одна операция); согласовать с владельцем DTJ-306 общий
доменный сервис `HandoverOtpReissueService` В МОМЕНТ реализации, а не постфактум рефакторингом. Точное
поведение `courierEtaMinutes` (полная формула через `GeoPoint.distanceTo` + `AVERAGE_COURIER_SPEED_KMH`)
реализуется в DTJ-319 — здесь поле контракта существует, но реальный расчёт временно может возвращать
`null`/грубую оценку, с явной пометкой TODO на DTJ-319.
