## Задача

Основной рабочий экран курьера на время доставки: карта аптека→клиент, кнопка со сменной подписью
статуса («Выехал»→«Забрал»(авто)→«В пути к клиенту»→«Доставлено»), карточка ориентира с фото дома и
кнопкой звонка. Это самый длительный по времени пребывания экран во всей доставке — от него напрямую
зависит, насколько быстро и без ошибок курьер физически находит адрес.

## Технический контекст

`apps/courier/src/features/active-delivery/**` — маршрут `/active/:id`. Использует `GET
/delivery-assignments/:id`, `POST .../depart`, `POST .../depart-to-customer` (DTJ-317). `MapView` —
обёртка `MapLibre GL JS`/`react-leaflet` над OSM-тайлами (REQ-GEO-1, без проприетарных SDK/ключей;
`32-design-reference.md` отмечает, что дизайн даёт только заглушку-контейнер — реальный компонент
проектируется по требованиям `30-ux`/модуля каталога, здесь — первая реализация для курьерского
контекста, маршрут аптека→клиент, не полноценная turn-by-turn навигация).

## Что сделать

1. `ActiveDeliveryPage` — `MapView` (точка аптеки, точка клиента, без турн-бай-турн — курьер
   использует штатное приложение навигации телефона через `deep link`, п.5), статусная кнопка с
   подписью по текущему `delivery_assignment_status`: `assigned` → «Выехал» (клик → `POST .../depart`);
   `en_route_to_pharmacy` → «Забрал» — ЭТА подпись показывается АВТОМАТИЧЕСКИ и НЕДОСТУПНА для клика
   (`32-design-reference.md`: «Забрал (авто, недоступна вручную)» — промежуточный переход
   `en_route_to_pharmacy → picked_up_from_pharmacy` не имеет отдельного REST-вызова, он выполняется
   backend'ом атомарно ВНУТРИ следующего вызова `depart-to-customer`, см. DTJ-317); фактически кнопка на
   этом статусе визуально показывает «Забрал» как статичную промежуточную подпись, а клик по ней
   немедленно вызывает `depart-to-customer` (следующий шаг, п. ниже) — то есть с точки зрения курьера это
   один физический жест «я забрал заказ и еду к клиенту»; `picked_up_from_pharmacy`-состояние на клиенте
   отдельно не отображается. `en_route_to_customer` (после `depart-to-customer`) → кнопка «В пути к
   клиенту» неактивна/декоративна, следующий явный клик — «Доставлено» (клик → переход на `/otp/:id`
   ЛИБО сначала `/cash/:id`, если `paymentMethod='cash_courier'` и наличные ещё не зафиксированы — см.
   маршрутизацию п.4). Чек-бокс «Термосумка закрыта» — ОБЯЗАТЕЛЕН перед кликом «Забрал/В пути к клиенту»,
   если `requiresColdChain=true` (иначе клиент не отправляет запрос — сервер всё равно перепроверит и
   вернёт `422 COLD_CHAIN_BAG_NOT_CONFIRMED`, если UI-блокировку обойти).
2. `NavigationDetailSheet` — карточка ориентира: превью `landmarkPhotoUrl` НАД картой (не под ней — курьер
   должен увидеть визуальный ориентир ДО сверки с картой), текст `landmarkText`, `entrance`/`floor`/
   `apartment`/`deliveryComment`, кнопка звонка клиенту (`tel:{customerContact.phoneNumber}` из ответа
   `GET .../:id`, DTJ-317 — работает одинаково независимо от того, замаскирован номер или нет, клиент об
   этом не знает).
3. Given `requiresColdChain=true`, Then показать индикатор холодовой цепи на карточке заказа (бейдж
   «Требует холодовой цепи») ещё ДО перехода `depart-to-customer`, чтобы курьер заранее подготовил
   термосумку, не в момент клика.
4. Маршрутизация после «Доставлено»: given `paymentMethod='cash_courier'` И наличные ещё НЕ
   зафиксированы (`delivery_assignments.cash_collected_diram IS NULL`), Then переход на `/cash/:id`
   (DTJ-329) ПЕРЕД `/otp/:id`; иначе — сразу на `/otp/:id`.
5. Кнопка «Проблема» (переход на `/issue/:id`, DTJ-330) — доступна на протяжении всего активного статуса
   `en_route_to_customer`.
6. Deep-link на штатную навигацию: `geo:{lat},{lon}`/`google.navigation:q={lat},{lon}` через
   `window.open` — используется как дополнение к встроенной карте, не замена (SRS-DELIV-055 по духу,
   применимо к веб-версии как best-effort — не все браузеры/ОС поддерживают `geo:` схему одинаково,
   деградация — просто открыть карту в новой вкладке с координатами, если deep-link не сработал).
7. WS-подписка на `courier:{id}` для собственных статусных апдейтов (в редких случаях изменённых с
   другого устройства/диспетчером — `reassign`) — при получении `delivery.escalated_to_pool`/явной потере
   назначения (переназначено диспетчером на другого курьера) — блокирующее сообщение «Заказ переназначен»
   с редиректом на `/offers`.

## Критерии приёмки

Given `assigned`, When нажата «Выехал», Then `POST .../depart` отправлен, статус на экране переходит в
`en_route_to_pharmacy`, кнопка автоматически становится недоступной (ожидание аптеки).

Given `requiresColdChain=true`, чек-бокс «Термосумка закрыта» НЕ отмечен, When нажата «В пути к
клиенту», Then запрос либо не отправляется с клиента, либо сервер отвечает `422
COLD_CHAIN_BAG_NOT_CONFIRMED` — в обоих случаях статус НЕ переходит в `en_route_to_customer`, ошибка
показана курьеру.

Given заказ переназначен диспетчером на другого курьера ПОКА этот курьер смотрит на экран активной
доставки, When приходит соответствующий WS-сигнал, Then блокирующее сообщение «Заказ переназначен»,
редирект на `/offers` — курьер не может продолжать действия над чужим теперь назначением (негативный/
защитный сценарий).

## Тест-план

Unit: `model` — маппинг `delivery_assignment_status → подпись кнопки/доступность`, маршрутизация после
«Доставлено» (cash vs non-cash ветка).
Компонентные: `ActiveDeliveryPage` — каждый статусный переход отдельным кейсом, `NavigationDetailSheet`
рендер всех полей, cold-chain чек-бокс блокирует кнопку.
E2E: продолжение сценария DTJ-327 — от `assigned` до перехода на `/otp/:id` (без самого ввода OTP) для
заказа БЕЗ холодовой цепи и БЕЗ наличных (простейший путь).
Порог покрытия — 70%.

## Риски и подводные камни

`MapView` — первая полноценная реализация карты в этом эпике (дизайн даёт только заглушку-контейнер) —
координировать визуальный подход с `packages/ui`/EP-18, чтобы не создать несовместимый с будущим общим
компонентом API. Слияние UI-подписи «Забрал»/«В пути к клиенту» в один клик (см. «Что сделать» п.1) —
решение, принятое этим тикетом на основании `32-design-reference.md`; если владелец DTJ-317 в процессе
реализации backend придёт к другому выводу (например, найдёт отдельный эндпоинт для промежуточного
перехода) — синхронизировать до релиза, не расходиться молча.
