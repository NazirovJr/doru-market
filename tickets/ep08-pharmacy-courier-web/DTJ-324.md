## Задача

Как и в EP-12 (DTJ-309), поверхность модуля `delivery` собиралась параллельно восемью тикетами (DTJ-315
..322) — каждый закрыл свою бизнес-логику, но ни один не проверил ВСЮ поверхность сразу на инвариант,
который здесь особенно критичен: `customer` НИКОГДА не должен видеть точные координаты курьера/аптеки
сборки/данные назначения до `assign`, курьер одной сети не должен трогать заказы чужой, а
`⚠`-условия из RBAC-таблицы `25-module-courier-delivery.md` §A.1 — реализованы как `application`-политики
(SRS-DELIV-011), не как разрозненные `if` в контроллерах.

## Технический контекст

`DeliveryAssignmentOwnershipPolicy`/`CourierShiftPolicy` — явные классы политик в `application`
(`02` §3.4: авторизация «может ли этот пользователь это сделать» — в application, guard'ы делают только
грубую проверку роли). Этот тикет формализует их как переиспользуемые классы (если DTJ-315..322 уже
содержат разрозненную логику проверки владения — этот тикет РЕФАКТОРИТ её в эти два класса, устраняя
дублирование, `02` C15 — третье повторение уже видно по 8 use case).

## Что сделать

1. `DeliveryAssignmentOwnershipPolicy.canAct(actor, assignment, action)` — единая точка проверки
   владения/скоупа для ВСЕХ действий над `DeliveryAssignment`: `courier` — только назначенный на СЕБЯ
   (`assignment.courierId === actor.courierId`); `pharmacy_admin` — только свой флот
   (`courier.chainId === actor.chainId`); `super_admin` — без ограничения. Рефакторинг: заменить
   разрозненные проверки `actor.courierId === assignment.courierId` в DTJ-317/318 на вызов этого метода.
2. `CourierShiftPolicy.canManage(actor, shift)` — только сам курьер над собственной сменой (DTJ-320).
3. Таблица RBAC `25-module-courier-delivery.md` §A.1 (14 permission-строк) × сценарии на КАЖДЫЙ маршрут
   модуля (17 эндпоинтов из DTJ-315..322):
   а. `customer` (не владелец заказа) → `403`/`404` на все курьерские/диспетчерские эндпоинты; на
      `GET /delivery-assignments/:id` СВОЕГО заказа → урезанный ответ (см. п.б).
   б. `customer` (владелец заказа) на `GET .../:id` для назначения `status='unassigned'` → `403 FORBIDDEN`
      (SRS-DELIV-018 — клиент не видит деталей чужого/ещё неназначенного заказа даже по прямому `id`).
   в. `courier` НЕ являющийся адресатом оффера/назначения → `403`/`404` на все действия над ЧУЖИМ
      оффером/назначением.
   г. `courier` с `chainId='X'` (свой флот) над заказом сети `Y` → кандидат исключён из скоринга,
      `assign-manual`/`claim` для чужого назначения → `403 COURIER_TENANT_MISMATCH`.
   д. `pharmacy_admin` чужой сети → `403`/`404` на `assign-manual`/`reassign`/`GET
      /delivery-assignments` дашборд для чужих назначений.
   е. `super_admin` без `X-Tenant-Slug` override → доступ ко ВСЕМ назначениям (включая пул) без
      ограничения — позитивный контрастный тест к «д».
4. `idempotency.spec.ts` — для эндпоинта с обязательным `Idempotency-Key` (`record-cash`, единственный в
   этом модуле по таблице SRS-API-009) — три сценария (отсутствие заголовка/повтор с тем же ключом и
   телом/повтор с тем же ключом, другим телом), как в DTJ-309 для другого модуля.

## Критерии приёмки

Given `customer` — владелец заказа, назначение `status='unassigned'` (курьер ещё не назначен), When
`GET /delivery-assignments/:id`, Then `403 FORBIDDEN` (негативный тест — клиент не видит деталей
неназначенного заказа, SRS-DELIV-018).

Given курьер `chain_id='X'`, заказ сети `Y`, When он пытается `POST /delivery-assignments/:id/claim` для
назначения этого заказа, Then `403 COURIER_TENANT_MISMATCH` (негативный тест, покрывает и алгоритм
подбора DTJ-314, и прямую попытку через API).

Given `POST /delivery-assignments/:id/record-cash` вызван БЕЗ `Idempotency-Key`, When запрос отправлен,
Then `400 IDEMPOTENCY_KEY_REQUIRED`.

## Тест-план

Только интеграционные тесты (как DTJ-309) — 14 permission-строк × применимые эндпоинты + 3
идемпотентность-сценария на `record-cash`. Мутационная проверка при ревью: временно ослабить одну из
политик — соответствующий тест должен покраснеть.
