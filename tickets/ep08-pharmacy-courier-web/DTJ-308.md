## Задача

Без realtime-обновлений каждый из нескольких терминалов одной аптеки видел бы устаревшее состояние
заказа (кто его принял, отменён ли он, разблокирована ли частичная сборка) до следующего ручного
обновления страницы. Этот тикет подключает уже существующий WS-шлюз `RealtimeGateway` к пяти доменным
событиям терминала, публикуемым тикетами DTJ-301/304/305, в комнату `pharmacy:{pharmacyId}`.

## Технический контекст

WS-инфраструктура (`/api/v1/realtime`, комнаты, аутентификация, реконнект-протокол) уже существует
(EP-01/базовая инфраструктура, `12-api-conventions...md` §6). Этот тикет НЕ создаёт новый gateway —
только добавляет обработчики outbox-событий, публикующие в уже существующую комнату `pharmacy:{id}`
(роль `pharmacist`, уже определена).

## Что сделать

1. Подписать `pharmacy-terminal-events.publisher.ts` на outbox-события: `OrderClaimedEvent` → WS
   `order.claimed` (заказ помечается «в работе у X» на устройствах ДРУГИХ фармацевтов, кнопка «Принять»
   недоступна); `OrderReclaimedEvent` → WS `order.reclaimed` (обновление имени ответственного);
   `PartialFulfillmentConfirmedEvent`/`AutoConfirmedEvent`/rejection-путь → WS
   `order.partial_fulfillment_resolved` (разблокирует экран завершения сборки); `PartialFulfillmentProposedEvent`
   → WS `order.partial_fulfillment_proposed`, НО в комнату `customer:{customerId}`, не `pharmacy:*`
   (проверить корректный роутинг комнаты per событие, не публиковать всё в одну комнату по умолчанию).
   Существующие `OrderPaidEvent`/`OrderCancelledEvent`/`OrderAutoCancelledEvent` УЖЕ публикуются в
   `pharmacy:{id}` предыдущими эпиками — этот тикет их не трогает, только документирует ожидаемое
   поведение терминала в тест-плане (регрессионная проверка, что они не сломались).
2. Задокументировать (в README/комментарии модуля, НЕ хардкодить в клиенте) обязательность REST
   catch-up (`GET /orders?filter[pharmacyId]=...&filter[status][in]=paid_escrow,confirmed,processing`)
   ДО повторной подписки на комнату после реконнекта (SRS-PHT-037/SRS-API-053) — правило уже установлено
   на уровне протокола, здесь фиксируется применимость для ЭТОГО клиента.
3. Идемпотентная обработка на публикующей стороне: событие публикуется РОВНО один раз на доменное
   изменение (существующий `outbox`-паттерн, SRS-DOM-151, гарантирует at-least-once на стороне
   доставки — клиентская идемпотентность на приёме кадра — забота фронтенд-тикетов DTJ-310/311/312, не
   этого).

## Критерии приёмки

Given заказ свободен, 2 терминала подписаны на `pharmacy:{id}`, When фармацевты A и B почти одновременно
нажимают «Принять», Then терминал B немедленно получает WS `order.claimed`, ДАЖЕ если REST-ответ на его
собственный запрос ещё не долетел (WS может обогнать REST-response) — обработка на клиенте идемпотентна
(проверяется интеграционным тестом на порядок доставки, SRS-PHT-066).

Given подписка на `pharmacy:{id}`, When `ResolvePartialFulfillmentUseCase` завершает частичную сборку
(явно или по таймауту), Then событие `order.partial_fulfillment_resolved` доставляется в комнату РОВНО
одному подписанному тестовому клиенту-моку (проверка роутинга комнаты, не широковещательная рассылка во
все комнаты).

Given `PartialFulfillmentProposedEvent` опубликовано, When проверяется комната доставки, Then кадр уходит
В `customer:{customerId}`, А НЕ в `pharmacy:{pharmacyId}` (негативный тест на неверный роутинг —
частая ошибка копипаста между похожими publisher-обработчиками).

## Тест-план

Unit: маппинг «доменное событие → WS-тип события → комната» — таблица из пяти строк, каждая проверена
отдельным кейсом с мок-`RealtimeGateway`.
Интеграционные: реальный WS-клиент (тестовый) подписывается на `pharmacy:{id}`, эмулируется публикация
каждого из событий через outbox-воркер, проверяется получение корректного кадра; регрессионный тест на
`order.claimed` race (SRS-PHT-066).
Порог покрытия — 70% (infrastructure/presentation, `02` §6).

## Риски и подводные камни

Порядок доставки WS относительно REST-ответа НЕ гарантирован (SRS-PHT-066 явно это описывает) — клиент
обязан быть идемпотентным к получению `order.claimed` для заказа, который уже считает «в работе»; это
требование к фронтенду (DTJ-310), но публикующая сторона (этот тикет) обязана гарантировать, что событие
публикуется ровно один раз, чтобы не усугублять проблему дублированием на уровне сервера.
