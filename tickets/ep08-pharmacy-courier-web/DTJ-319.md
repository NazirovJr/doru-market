## Задача

Живая карта — ключевая часть UX и диспетчерского контроля: клиент должен видеть примерное время до
прибытия курьера, диспетчер/аптека — точные координаты для операционных решений, но клиент НИКОГДА не
должен видеть точные координаты курьера напрямую (защита от геолокационного отслеживания третьими
лицами через API клиента). Этот тикет — единственная точка приёма координат от курьера и единственная
точка их производной раздачи разным ролям с разной степенью детализации.

## Технический контекст

`apps/api/src/modules/delivery/application/**`. `GeoPoint.distanceTo` — существующий VO-метод
(гаверсинус, SRS-DOM-073), переиспользуется без изменений. `LocationBroadcastPublisher` — ЕДИНСТВЕННЫЙ
WS-путь модуля delivery, НЕ проходящий через `outbox`/at-least-once гарантию (публикуется НАПРЯМУЮ из
обработчика `POST /courier-locations`, троттлировано) — исключение из общего паттерна, зафиксировать
явно в коде комментарием «почему» (`02` C11).

## Что сделать

1. `POST /api/v1/courier-locations { lat, lon, capturedAt, accuracyM?, speedKmh? }` ИЛИ батч
   `{ pings: [...] }`. Роль `courier`. `Idempotency-Key` НЕ требуется (естественно идемпотентна —
   повторная отправка той же точки безвредна). Given `capturedAt` старше `LOCATION_PING_MAX_AGE_MINUTES`
   (ASSUMPTION 30), Then точка молча пропускается (не ошибка). КАЖДАЯ принятая точка обновляет
   `couriers.last_known_latitude/longitude/at` ТОЛЬКО если `capturedAt` новее уже сохранённого (защита от
   переупорядочивания батча). Ответ: `{ data: { accepted: N, skippedStale: M } }`. Rate-limit
   `RATE_LIMIT_COURIER_LOCATION_PER_MIN = 30` на курьера.
2. `CalculateCourierEtaUseCase` — `courierEtaMinutes = GeoPoint.distanceTo(courier.lastKnown,
   order.deliveryPoint) / AVERAGE_COURIER_SPEED_KMH * 60` (ASSUMPTION `AVERAGE_COURIER_SPEED_KMH=15`,
   конфигурируемо). Используется `GET /delivery-assignments/:id` (DTJ-317) для роли `customer` —
   заполняет реальный расчёт вместо временной заглушки того тикета.
3. `LocationBroadcastPublisher` — на каждый принятый пинг публикует WS `delivery.location_updated`,
   троттлировано `LOCATION_BROADCAST_THROTTLE_MS` (ASSUMPTION 5000, не чаще раза в 5с в комнату клиента,
   вне зависимости от частоты пингов курьера): в `customer:{customerId}` (ТОЛЬКО пока
   `en_route_to_customer`, содержит `courierEtaMinutes`, НЕ точные координаты); в
   `pharmacy:{pharmacyId}`/`chain:{chainId}` (точные координаты — операционная необходимость).
4. Given роль `customer`, When `delivery.location_updated`/ответ `GET .../:id` для СВОЕГО заказа, Then
   payload содержит `courierEtaMinutes`, но НЕ содержит `courier.lastKnownLatitude/longitude`.
   `pharmacy_admin`/`super_admin`/сам `courier` получают точные координаты.
5. Задокументировать (комментарий в коде + PR-описание), что клиент, реконнектнувшийся после разрыва,
   ОБЯЗАН вызвать `GET /delivery-assignments/:id` (не полагаться на пропущенные `location_updated`
   кадры) — WS здесь чисто UX-хинт, REST — источник истины (SRS-API-053, `delivery.location_updated` —
   единственное исключение из at-least-once гарантии outbox).

## Критерии приёмки

Given батч из 3 пингов, 1 старше `LOCATION_PING_MAX_AGE_MINUTES`, When `POST /courier-locations
{pings:[...]}`, Then `{accepted:2, skippedStale:1}`, `couriers.last_known_*` обновлён только самой
свежей из принятых (TC-DELIV-021).

Given роль `customer`, активная доставка, When `GET /delivery-assignments/:id`, Then ответ содержит
`courierEtaMinutes`, НЕ содержит `courier.lastKnownLatitude/longitude` (негативный тест на утечку
координат, TC-DELIV-022).

Given `pharmacy_admin` своего флота, When `GET /delivery-assignments/:id` для активной доставки, Then
ответ содержит точные координаты курьера (позитивный контраст к предыдущему кейсу — подтверждает, что
ограничение специфично для роли `customer`, не глобальное).

## Тест-план

Unit: `RecordCourierLocationsUseCase` — устаревшие пинги пропускаются, переупорядоченный батч обновляет
только по самой свежей `capturedAt`, rate-limit срабатывает на 31-м запросе в минуту; `CalculateCourierEtaUseCase`
— корректность формулы на фиксированных координатах (детерминированный расчёт).
Интеграционные: TC-DELIV-021, TC-DELIV-022, `LocationBroadcastPublisher` — троттлинг (10 пингов за 2
секунды → не более 1 WS-кадра клиенту за этот интервал), проверка разных payload для разных комнат
(`customer:*` без координат vs `pharmacy:*` с координатами).
Порог покрытия application — 90%; presentation/infrastructure — 70%.

## Риски и подводные камни

Rate-limit на уровне HTTP (30/мин) — нужен существующий rate-limit middleware/guard (уточнить, есть ли
общая инфраструктура rate-limiting из EP-01, переиспользовать её, не писать свою реализацию с нуля).
Троттлинг WS-публикации по времени (не по количеству) требует состояния «последняя публикация в эту
комнату» — простое решение через Redis с TTL `LOCATION_BROADCAST_THROTTLE_MS` на ключ
`location-throttle:{assignmentId}`, не in-memory Map (сервер может быть многоинстансным).
