## Задача

Это первая рабочая поверхность терминала: список заказов, доступных аптеке для сборки, и явная
«приёмка» заказа конкретным фармацевтом — момент, запускающий SLA-таймер сборки (D-19, 7 минут по
умолчанию) и переводящий заказ `paid_escrow`/`confirmed → processing` (SRS-DOM-091/178). Без этого шага
ни один следующий тикет части A (сканирование, завершение сборки) не имеет входной точки — фармацевт
физически не может начать работу с заказом.

## Технический контекст

`apps/api/src/modules/orders/application/pharmacy-terminal/**` — новые use case поверх уже существующего
агрегата `Order` (методы `startProcessing()`, состояние машины — `10-domain-model.md`). Заказ переводится
атомарно транзакцией с `SELECT ... FOR UPDATE` на строку `orders` (пессимистичная блокировка — конкуренция
здесь реальна и частая, в отличие от `claim` в модуле delivery, где используется оптимистичный `UPDATE`).
RBAC: `pharmacist` (own pharmacy, `actor.pharmacyId === order.pharmacyId`), `pharmacy_admin` (агрегирует
все точки своей сети — `implicit chainId scope`, уже определён `12-api-conventions...md` §4.1 для
`orders:read:pharmacy`). Использует `OrderItemFulfillmentStatus`/ошибки/события из DTJ-300.

## Что сделать

1. `GetOrderQueueUseCase` — `GET /api/v1/orders?filter[pharmacyId]=<id>&filter[status][in]=paid_escrow,confirmed,processing&sort=priority:asc&cursor=&limit=20`.
   `sort=priority` резолвится в application (НЕ поле БД): (1) `status='processing'` по
   `sla_deadline_at ASC NULLS LAST`; (2) `status IN ('paid_escrow','confirmed')` (ещё не приняты) по
   `created_at ASC` (FIFO), после группы 1. Ответ на позицию: `id, orderNumber, status, itemsCount,
   itemsTotalTjs, paymentMethod, prescriptionRequired, slaDeadlineAt (nullable), assignedPharmacistId
   (nullable), assignedPharmacistName (nullable), createdAt`.
2. Given `actor.role === 'pharmacy_admin'` И запрос БЕЗ `filter[pharmacyId]`, Then сервер возвращает заказы
   ВСЕХ точек сети актора, `meta.groupedBy = 'pharmacyId'` в ответе (SRS-PHT-005a) — НЕ отдельный эндпоинт.
3. `AcceptOrderUseCase` — `POST /api/v1/orders/:id/accept`. `OrderQueuePolicy.canAccept(actor, order)`:
   `actor.pharmacyId === order.pharmacyId` И `order.status IN ('paid_escrow', 'confirmed')`. Транзакция:
   `SELECT ... FOR UPDATE` на строку `orders`, `order.startProcessing(actor.userId)` (существующий метод
   домена), `orders.assigned_pharmacist_id = actor.userId`, `sla_deadline_at = now +
   tenant_settings.pickup_sla_minutes` (дефолт 7). Публикует `OrderProcessingStartedEvent` (существующее)
   И `OrderClaimedEvent` (DTJ-300). `Idempotency-Key` ОБЯЗАТЕЛЕН (переиспользовать общий
   Idempotency-механизм `SRS-API-009/010`, уже развёрнутый EP-01 — НЕ писать собственную реализацию).
4. Given второй фармацевт вызывает `accept` после того, как первый уже получил `200 OK`, Then
   `SELECT FOR UPDATE` сериализует запросы — второй видит `assigned_pharmacist_id IS NOT NULL` и получает
   `409 ORDER_ALREADY_CLAIMED` с `details: { assignedPharmacistId, assignedPharmacistName, claimedAt }`.
5. `ReclaimOrderUseCase` — `POST /api/v1/orders/:id/reclaim { reason: 'colleague_unavailable' |
   'shift_change' | 'other', note?: string }`. Доступен ЛЮБОМУ `pharmacist` той же аптеки (RBAC-скоуп
   `pharmacy`, НЕ владелец приёмки — SRS-PHT-038: блокировка «кто ведёт сборку» — UX-механизм, не мера
   безопасности). Обновляет только `assigned_pharmacist_id`; НЕ трогает `sla_deadline_at`, НЕ сбрасывает
   прогресс сканирования. Публикует `OrderReclaimedEvent`. `Idempotency-Key` обязателен.
6. `PharmacyTerminalQueueController` — REST-контроллер, DTO↔domain через `pharmacy-terminal.mapper.ts`
   (presentation не знает доменных инвариантов, `02` §1.1).
7. RBAC guard: роли `pharmacist`/`pharmacy_admin` на все три эндпоинта; `super_admin` — НЕ допускается
   (наблюдение через отдельный `platform:ops`-канал, не через этот терминал, SRS-PHT-004).

## Критерии приёмки

Given заказ `status='paid_escrow'`, `assigned_pharmacist_id IS NULL`, When `pharmacist` A вызывает
`POST /orders/:id/accept` с валидным `Idempotency-Key`, Then `200 OK`, `data.status='processing'`,
`data.slaDeadlineAt = now + pickup_sla_minutes`, `data.assignedPharmacistId = A.id` (SRS-PHT-008).

Given заказ уже принят фармацевтом A, When фармацевт B (та же аптека) вызывает `accept` ПОСЛЕ ответа A,
Then `409 ORDER_ALREADY_CLAIMED`, `details.assignedPharmacistId = A.id` (SRS-PHT-009) — заказ остаётся
`processing` за A, повторного перевода статуса НЕ происходит.

Given заказ в работе у A, When B вызывает `POST /orders/:id/reclaim { reason: 'shift_change' }`, Then
`200 OK`, `assignedPharmacistId = B.id`, `slaDeadlineAt` НЕ изменился (SRS-PHT-010).

Given `pharmacy_admin` сети из 3 точек вызывает `GET /orders` БЕЗ `filter[pharmacyId]`, Then ответ содержит
заказы всех 3 точек СВОЕЙ сети, `meta.groupedBy` присутствует, заказы ЧУЖОЙ сети отсутствуют (негативный
тест на межтенантную/межсетевую изоляцию, SRS-PHT-005a/TC-PHT-030).

Given `POST /orders/:id/accept` вызван БЕЗ заголовка `Idempotency-Key`, Then `400 IDEMPOTENCY_KEY_REQUIRED`
(негативный тест, SRS-API-009).

## Тест-план

Unit (application, порты замоканы): `OrderQueueSortPolicy` — сортировка смешанного набора
`processing`/`paid_escrow` по правилу приоритета (несколько кейсов: пустой список, только `processing`,
только `paid_escrow`, смешанный с `NULL sla_deadline_at`); `AcceptOrderUseCase.canAccept` — allow/deny по
роли и статусу; `ReclaimOrderUseCase` — не трогает `sla_deadline_at`/сканы.
Интеграционные: `TC-PHT-001` (accept успех), `TC-PHT-002` (двойной accept), `TC-PHT-003` (reclaim),
`TC-PHT-005a`/`TC-PHT-030` (агрегация сети `pharmacy_admin`, межтенантная изоляция), `TC-PHT-023`
(конкурентный accept с двух «терминалов» — реальная параллельная транзакция, не мок).
Порог покрытия application — 90%.

## Риски и подводные камни

`SELECT ... FOR UPDATE` под нагрузкой при высоком параллелизме одного заказа может создать короткую
очередь блокировок — приемлемо для MVP-масштаба (один заказ разбирают ≤2-3 фармацевта одновременно), но
требует индекса на `orders.id` (уже PK, не требует доп. действий). `meta.groupedBy` — новое поле envelope,
не описанное в базовой конвенции `12-api-conventions...md` §2 — согласовать формат с ревьюером API
(разумный вариант: `meta.groupedBy: { pharmacyId: [...orderIds] }` или плоское поле `pharmacyId` на каждой
позиции — решение фиксируется в Zod-контракте DTJ-300, здесь только используется).
