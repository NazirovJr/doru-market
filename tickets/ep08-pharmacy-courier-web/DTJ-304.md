## Задача

Когда часть позиций заказа физически недоступна (DTJ-303 пометил их `unavailable`), сборка не может
просто продолжиться с меньшим составом без согласия клиента — это изменение того, за что клиент заплатил.
Этот тикет реализует запрос подтверждения изменённого состава: клиент явно соглашается, отказывается
целиком, либо система трактует молчание как согласие по истечении таймаута (D-10, стратегия частичного
рефанда). Это самый юридически/финансово чувствительный узел терминала — единственное место, где
фармацевт-инициированное действие напрямую меняет сумму заказа и запускает частичный рефанд.

## Технический контекст

`ProposePartialFulfillmentUseCase`/`ResolvePartialFulfillmentUseCase` в
`apps/api/src/modules/orders/application/pharmacy-terminal/**`, работают с
`order_partial_fulfillment_requests` (DTJ-300). `ResolvePartialFulfillmentUseCase(confirmed: boolean)`
вызывается ДВУМЯ путями: (1) явно клиентским эндпоинтом (реализуется в зоне ответственности Customer Web
App — вне этого эпика, но use case и его домен-эффект — источник правды здесь, presentation-обёртку для
клиента добавит владелец `apps/web`); (2) BullMQ-джобом по таймауту (`auto_confirmed_timeout`), который
владеет ЭТОТ тикет. Частичный рефанд идёт через `PaymentsFacade`/`EscrowLedger` (существующие методы,
доступ только через фасад — прямой импорт `modules/payments/domain` запрещён, `02` §1.2).

## Что сделать

1. `POST /api/v1/orders/:id/propose-partial-fulfillment` (`Idempotency-Key` обязателен).
   `ProposePartialFulfillmentUseCase`: given ≥1 позиция `unavailable` И ВСЕ остальные позиции
   `scanned_ok`/`unavailable` (решение принято по каждой) — создать
   `order_partial_fulfillment_requests(status='awaiting_customer', itemsSnapshot, itemsTotalBeforeDiram,
   itemsTotalAfterDiram, refundAmountDiram, expiresAt = now + tenant_settings.
   partial_fulfillment_confirmation_timeout_minutes)`. `itemsTotalAfterDiram` — через существующий
   `Order.recalculateTotals()` БЕЗ `unavailable`-позиций. Опубликовать `PartialFulfillmentProposedEvent`
   (DTJ-300) → WS `order.partial_fulfillment_proposed` в `customer:{customerId}`.
   Given найдена ≥1 позиция `pending` (решение НЕ принято), Then `422 BUSINESS_RULE_VIOLATION`
   (`details.unresolvedItemIds`).
2. Планирование BullMQ delayed job `partial-fulfillment-timeout` с `delay =
   partial_fulfillment_confirmation_timeout_minutes`, `jobId = requestId` (идемпотентно при повторном
   планировании) — в ТОЙ ЖЕ транзакции, что и создание запроса.
3. `ResolvePartialFulfillmentUseCase(requestId, confirmed: boolean, source: 'customer' | 'timeout')`:
   - `confirmed=true` (явно ИЛИ `source='timeout'`): (а) `status → 'confirmed'`/`'auto_confirmed_timeout'`;
     (б) `Order.recalculateTotals()` фиксирует новый `items_total_tjs`; (в) частичный рефанд по
     `SRS-DOM-162` (D-10): given `PaymentProvider.capabilities().supportsPartialRefund === false`
     (MVP-дефолт) И раздельный биллинг — рефанд транзакции `items_total`; иначе — полный `refund()` +
     `escrow_ledger.entry_type='adjustment'`; (г) публикует `PartialFulfillmentConfirmedEvent`/
     `AutoConfirmedEvent` → WS `order.partial_fulfillment_resolved` в `pharmacy:{pharmacyId}`.
   - `confirmed=false`: весь заказ → `order.cancel('customer_rejected_partial_fulfillment', customer)`
     (существующий метод, SRS-DOM-093) — полный рефанд, восстановление резерва ВСЕХ позиций. Публикует
     `PartialFulfillmentRejectedEvent`.
4. `PartialFulfillmentTimeoutProcessor` (BullMQ worker): на `expires_at` — given
   `status === 'awaiting_customer'` (ещё не отвечен), Then вызвать `ResolvePartialFulfillmentUseCase(...,
   confirmed=true, source='timeout')`. Given статус уже изменился (клиент успел ответить раньше) — job
   идемпотентно завершается без действия.
5. Given `PaymentProvider.refund()`/`partiallyRefund()` недоступен (circuit breaker), Then
   `503 PAYMENT_PROVIDER_UNAVAILABLE`, НО `order_partial_fulfillment_requests.status` уже `'confirmed'`
   ОСТАЁТСЯ (клиент согласился) — создать отложенную retry-задачу через `outbox`, НЕ откатывать статус
   запроса и НЕ блокировать `complete-picking` этим сбоем (SRS-PHT-075).
6. `PartialFulfillmentController` — `presentation`-обёртка эндпоинта `propose-partial-fulfillment`
   (эндпоинт клиентского `confirm`/`reject` — не в зоне владения этого тикета, только use case).

## Критерии приёмки

Given все позиции решены, ≥1 `unavailable`, When `propose-partial-fulfillment`, Then `201`, создан
`order_partial_fulfillment_requests(status='awaiting_customer')`, WS `order.partial_fulfillment_proposed`
клиенту (TC-PHT-009).

Given ≥1 позиция ещё `pending`, When `propose-partial-fulfillment`, Then `422 BUSINESS_RULE_VIOLATION`,
`details.unresolvedItemIds` непусто (негативный тест, TC-PHT-010).

Given запрос `awaiting_customer`, When `ResolvePartialFulfillmentUseCase(confirmed=true, source='customer')`,
Then `status='confirmed'`, `items_total_tjs` уменьшен, в `EscrowLedger` появляется запись частичного
рефанда, WS `order.partial_fulfillment_resolved` уходит терминалу (TC-PHT-011).

Given запрос `awaiting_customer`, `expires_at` наступил, клиент НЕ ответил, When BullMQ-джоб срабатывает,
Then `status='auto_confirmed_timeout'`, эффект идентичен явному подтверждению (TC-PHT-013/SRS-PHT-023a).

Given запрос `awaiting_customer`, When клиент отклоняет (`confirmed=false`), Then весь заказ →
`cancelled`, полный рефанд, резерв ВСЕХ позиций восстановлен (негативный по отношению к «продолжить
сборку» сценарий, TC-PHT-012).

## Тест-план

Unit: `ProposePartialFulfillmentUseCase` — precondition (все позиции решены/есть нерешённые),
`recalculateTotals` вызван с правильным набором позиций; `ResolvePartialFulfillmentUseCase` — три ветки
(`confirmed=true`/`false`/`timeout`), включая ветку `PAYMENT_PROVIDER_UNAVAILABLE` (мок бросает ошибку —
статус запроса НЕ откатывается, retry-задача создана).
Интеграционные: TC-PHT-009..013, тест таймаут-джоба с реальным BullMQ (тестовый Redis) — джоб не
срабатывает повторно на уже `confirmed` запрос (идемпотентность при race между явным ответом клиента и
таймером).
Порог покрытия application — 90%.

## Риски и подводные камни

Кросс-констрейнт `partial_fulfillment_confirmation_timeout_minutes < pickup_sla_minutes +
pickup_sla_buffer_minutes` НЕ проверяется автоматически (SRS-PHT-073, минимальная инженерная сложность,
`02` C15) — если тенант настроит наоборот, заказ будет отменён общим SLA-watchdog (DTJ-307) НЕЗАВИСИМО от
незавершённого запроса подтверждения; это ожидаемое (документированное) поведение, не баг. Реальная
реализация частичного рефанда зависит от того, что `PaymentProvider.capabilities().supportsPartialRefund`
и `partiallyRefund()` уже существуют в модуле `payments` (EP-10) — если на момент тикета их ещё нет,
согласовать точный контракт с владельцем EP-10 до реализации, не изобретать параллельный API.
