## Задача

Модуль `modules/delivery` не существует до этого тикета — весь курьерский веб-модуль (EP-13) физически
не может начаться без своей схемы БД и доменных сущностей. Это подготовительный тикет эпика: расширяет
уже существующие базовые таблицы `couriers`/`delivery_assignments` (созданы в фундаменте EP-01 по
`11-database-schema.md` группа H) новыми колонками и создаёт пять новых таблиц/сущностей, специфичных
именно для курьерского модуля (`DeliveryOffer`, `CourierShift`, `CourierRating`, `DeliveryZone`,
`DeliveryPricingRule`) — доменных сущностей самого модуля `delivery`, не переиспользуемых из общего
domain-kernel.

## Технический контекст

`apps/api/src/modules/delivery/{domain,application,infrastructure,presentation}/**` — новый backend-
контекст (единственный разрешённый способ, которым `orders`/`payments`/`billing`/`returns` будут
взаимодействовать с ним, — публичный фасад `DeliveryFacade`, создаваемый в DTJ-314). Переиспользует из
общего domain-kernel `10-domain-model.md` §4 (НЕ дублирует): `OtpCode`, `GeoPoint`, `Money`,
`PhoneNumber`, `TenantId`. Базовые таблицы `couriers`/`delivery_assignments`/`courier_earnings`/
`courier_payouts` уже существуют (созданы EP-01 согласно `11-database-schema.md` группа H) — этот тикет
их РАСШИРЯЕТ (`ALTER TABLE`), не создаёт заново.

## Что сделать

1. Миграция (следующий свободный номер): `ALTER TABLE couriers ADD COLUMN last_known_latitude
   NUMERIC(10,8), last_known_longitude NUMERIC(11,8), last_location_at TIMESTAMPTZ, shift_status
   courier_shift_status NOT NULL DEFAULT 'off_shift', rating_avg NUMERIC(3,2) NOT NULL DEFAULT 5.00,
   rating_count INT NOT NULL DEFAULT 0, current_cash_on_hand_diram BIGINT NOT NULL DEFAULT 0` +
   `CREATE TYPE courier_shift_status AS ENUM ('off_shift','on_shift')` + констрейнты
   `chk_couriers_rating_range`/`chk_couriers_cash_nonneg`.
2. `ALTER TABLE delivery_assignments ADD COLUMN requires_cold_chain BOOLEAN NOT NULL DEFAULT false,
   cold_chain_bag_confirmed BOOLEAN, cold_chain_bag_confirmed_at TIMESTAMPTZ, contact_attempts_count INT
   NOT NULL DEFAULT 0, last_contact_attempt_at TIMESTAMPTZ, distance_meters INT`.
3. `CREATE TABLE delivery_offers` (+ `delivery_offer_status` enum, `ux_delivery_offers_one_pending_per_assignment`,
   `ix_delivery_offers_courier_pending`) — точная структура `25-module-courier-delivery.md` §D.3.
4. `CREATE TABLE courier_shifts` (+ `courier_shift_record_status` enum, `ux_courier_shifts_one_active`) —
   §D.4.
5. `CREATE TABLE courier_ratings` (+ `chk_courier_ratings_range`, `UNIQUE(order_id)`) — §D.5.
6. `CREATE TABLE delivery_zones` + `CREATE TABLE delivery_pricing_rules` (+ `ix_delivery_zones_geo`
   GiST-индекс) — §D.6.
7. `ALTER TYPE audit_action_category ADD VALUE 'cash_reconciliation_discrepancy'` — ОТДЕЛЬНОЙ миграцией
   вне транзакции (`SRS-DB-009`, PostgreSQL-ограничение на новое значение enum).
8. `[cross-module]` `ALTER TABLE orders ADD COLUMN delivery_entrance VARCHAR(20), delivery_floor
   VARCHAR(20), delivery_apartment VARCHAR(20), delivery_comment TEXT, delivery_landmark_photo_url TEXT` —
   СОГЛАСОВАТЬ с владельцем `apps/api/src/modules/orders/**` (EP-09/EP-10) ДО написания этой миграции:
   если эти поля уже добавлены их миграциями к моменту старта тикета — пропустить этот пункт и только
   свериться с фактическими именами колонок; если ещё не добавлены — согласовать порядок номеров миграций
   (после чекаут-миграции orders, см. «Открытые вопросы» модуля 25 §2).
9. Доменные сущности (приватный конструктор + фабрика, `02` §2.2): `DeliveryAssignment` (агрегат,
   инкапсулирует state machine `delivery_assignment_status` по таблице `10-domain-model.md`
   `unassigned→assigned→en_route_to_pharmacy→picked_up_from_pharmacy→en_route_to_customer→
   {delivered|delivery_failed}`, методы-намерения `assign()`, `depart()`, `departToCustomer()`,
   `recordCash()`, `markDelivered()`, `reassign()`), `Courier`, `DeliveryOffer`, `CourierShift`,
   `CourierRating`, `DeliveryZone`, `DeliveryPricingRule`.
10. Двенадцать доменных ошибок (файл на класс) — таблица `25-module-courier-delivery.md` §A.9:
    `OfferExpiredError` (409), `OfferAlreadyRespondedError` (409), `AssignmentAlreadyClaimedError` (409),
    `CourierNotOnShiftError` (422), `CourierMaxConcurrentAssignmentsError` (422),
    `DeliveryZoneNotCoveredError` (422), `DeliveryMinOrderNotMetError` (422),
    `ColdChainBagNotConfirmedError` (422), `ShiftAlreadyActiveError` (409), `NoActiveShiftError` (422),
    `ActiveAssignmentBlocksShiftEndError` (422), `ContactAttemptsInsufficientError` (422),
    `RatingAlreadySubmittedError` (409).
11. Доменные события (таблица §A.6): `DeliveryOfferCreatedEvent`, `DeliveryOfferExpiredEvent`,

12. `packages/contracts/src/delivery/delivery.contracts.ts` — Zod-схемы для всех тел запросов части A

## Критерии приёмки

Given применена миграция на чистой БД с уже накатанной базовой схемой (включая группу H), When выполняется
`pnpm db:migrate`, Then миграция проходит без ошибок, `delivery_offers`/`courier_shifts`/
`courier_ratings`/`delivery_zones`/`delivery_pricing_rules` существуют с заявленными констрейнтами.

Given две попытки вставить `delivery_offers(status='pending')` для одного `delivery_assignment_id`, When
вторая вставка выполняется, Then она отклоняется `ux_delivery_offers_one_pending_per_assignment`
(негативный тест).

Given `DeliveryAssignment.create()` вызван для `orderId`, у которого УЖЕ есть нетерминальное назначение,
When вызов происходит повторно (идемпотентность обработчика `OrderPickedUpEvent`), Then домен отклоняет
создание дубля (SRS-DOM-036, негативный тест на уровне сущности, без БД).

## Тест-план

Unit: каждая доменная сущность — фабрика создаёт валидный объект и отклоняет невалидные входные данные;
`DeliveryAssignment` — таблица переходов state machine (позитивные и недопустимые переходы, включая
попытку `depart()` из `unassigned` — должна быть отклонена доменной ошибкой); двенадцать доменных ошибок —
корректные `code`/`httpStatus`; семь доменных событий — сериализация payload.
Интеграционные: миграция вверх/вниз на тестовой БД; констрейнты БД (частичные уникальные индексы,
`chk_*`) — реальными SQL-запросами.
Порог покрытия domain — 90%.
