## Задача

CUJ-9/CUJ-10 закрывают возможности R1-11 (админ-панель) и R1-12 (Auth) — ранее проверявшиеся
только модульными тестами, без сквозного сценария (`docs/spec/31-nfr-security-testing-devops.md`
§«E2E-спецификации CUJ-9..13»: «пять возможностей R1 не имели ни одного сквозного сценария»). Эти
два сценария полностью специфицированы архитектором на уровне, достаточном для написания кода без
уточнений (`SRS-NFR-073`/`SRS-NFR-074`) — этот тикет реализует их буквально по спецификации.

## Технический контекст

Оба сценария детально описаны в `docs/spec/31-nfr-security-testing-devops.md`
§«E2E-спецификации: CUJ-9..13 и смена бренда (D-01)». Использует `getOtpFromMockSms` (DTJ-417) для
входа `super_admin`. CUJ-9 требует тестовый файл лицензии (`license-valid.pdf`, создаётся этим
тикетом как минимальный валидный PDF-заглушка). CUJ-10 напрямую манипулирует истечением JWT
(подстановка токена с истёкшим `exp`) — тестовый приём, не требующий реального ожидания 15 минут.

## Критерии приёмки

1. Given заявка `pending_review` одобрена, When повторно выполнен поиск того же медикамента
   `customer`-сессией ПОСЛЕ approve, Then медикамент виден в `GET /medicines/search` И на карте
   аптек (сравнение с состоянием ДО approve на шаге 5 сценария, где он был НЕВИДИМ — обе проверки
   ОБЯЗАНЫ быть в одном тесте, не раздельно).
2. Given `pharmacy_admin` пытается вызвать `approve`, When запрос отправлен, Then
   `403 INSUFFICIENT_ROLE`.
3. Given access-токен с истёкшим `exp`, When запрос к защищённому эндпоинту, Then
   `401 TOKEN_EXPIRED` (конкретный код ошибки, не generic `401`).
4. Given старый (уже использованный на шаге 5) refresh-токен предъявлен повторно, When
   `POST /auth/refresh`, Then `401 REFRESH_TOKEN_REUSE_DETECTED`, И после этого момента в
   `auth_sessions` для этой `family_id` НЕТ ни одной строки с `revoked_at IS NULL` (проверка через
   БД/API, не только код ответа).
5. Given `customer`-роль, When `GET /audit-log`, Then `403 INSUFFICIENT_ROLE`.

## Риски и подводные камни

Искусственная подстановка JWT с истёкшим `exp` требует либо тестового helper'а для подписи токена
ТЕМ ЖЕ ключом, что использует бэкенд (создаёт зависимость от `JWT_PRIVATE_KEY` тестового профиля —
координировать с владельцем Auth-модуля точный механизм: либо тест получает валидный токен и сам
модифицирует `exp` перед повторной подписью тем же секретом, известным тестовому окружению, либо
существует debug-эндпоинт, выдающий заведомо истёкший токен), либо использование
`FixedClockAdapter`-продвижения времени на бэкенде (аналогично риску DTJ-420) — выбор конкретного
механизма фиксируется в PR при первой реализации, не диктуется этим тикетом жёстко. `SRS-ADM-006`
(поля `pharmacy_accounts`) — точный состав полей определяется модулем онбординга (EP-03), тест
пишется по контракту минимально необходимых полей для чек-листа, не по исчерпывающей схеме.
