## Задача

`docs/spec/31-nfr-security-testing-devops.md` §«Готовность к продакшену» — чек-лист из 20+
пунктов, разбитый на «Безопасность», «Данные», «Наблюдаемость», «Функциональность»,
«Юридическое/организационное» — БЕЗ письменного runbook эти шаги существуют только как список в
документе, который легко упустить в момент реального первого деплоя (обычно — стрессовая ситуация,
не время читать 1500-строчный SRS-документ заново). `SRS-NFR-062`/`SRS-NFR-063` специфицируют
КОНКРЕТНЫЙ безопасный порядок rolling-деплоя и отката — это операционная процедура, а не только
описание, поэтому она реализуется исполняемыми скриптами, не только текстом.

## Технический контекст

`scripts/deploy/**` и `docs/RUNBOOK-PRODUCTION-READINESS.md` — владение EP-19. Скрипты работают
поверх `docker-compose.yml`/`docker-compose.prod.yml` (DTJ-412) — `rolling-deploy.sh` реализует
последовательность `SRS-NFR-062`: `docker compose pull` → `migrate`-контейнер (`SRS-NFR-055`,
уже гарантировано порядком `depends_on` в compose, скрипт лишь оркестрирует вызов) → `docker compose
up -d --no-deps api worker` (только stateless-сервисы) → healthcheck нового контейнера ДО остановки
старого при `replicas: 2`. `rollback.sh` — откат к предыдущему тегу образа. `backup-restore-drill.sh`
— операционализирует ежеквартальные восстановительные учения (`RTO ≤4ч`/`RPO ≤15мин`, строки 9/10
таблицы `SRS-NFR-036`).

## Что сделать

1. `scripts/deploy/rolling-deploy.sh` — принимает `IMAGE_TAG` (версия релиза) аргументом: (1)
   `docker compose -f docker-compose.yml -f docker-compose.prod.yml pull` (новые образы по тегу);
   (2) запуск `migrate`-контейнера, ожидание `service_completed_successfully` (явный `docker
   compose up migrate --exit-code-from migrate` или эквивалент, скрипт явно завершается с ошибкой,
   если миграция провалилась — НЕ продолжает деплой на сломанной схеме); (3) `docker compose up -d
   --no-deps api worker` (пересоздаёт ТОЛЬКО эти два сервиса, БД/Redis/MinIO не трогаются,
   `SRS-NFR-062`); (4) поллинг `GET /ready` нового контейнера ДО завершения (по одному инстансу за
   раз при `replicas: 2` — скрипт не считает деплой успешным, пока healthcheck не пройден);
   (5) вывод итогового статуса (успех/откат требуется).
2. `scripts/deploy/rollback.sh` — принимает `PREVIOUS_IMAGE_TAG`: пересоздаёт `api`/`worker` со
   старым тегом (`docker compose up -d --no-deps api worker` с явным переопределением тега образа
   через ENV/compose override) — скрипт печатает явное ПРЕДУПРЕЖДЕНИЕ, если релиз, с которого
   откатываются, содержал ИЗМЕНЕНИЕ существующей таблицы БЕЗ `down`-миграции (`SRS-NFR-063`: откат
   схемы в этом случае невозможен автоматически, требует ручного вмешательства DBA) — механизм
   определения «была ли миграция ALTER без down» — проверка наличия файла `*.down.sql` рядом с
   последней применённой `*.up.sql` миграцией (простая файловая проверка, не парсинг SQL).
3. `scripts/deploy/backup-restore-drill.sh` — операционализирует пункт чек-листа «`pg_dump`/WAL-
   архивирование настроено и ПРОВЕРЕНО реальным восстановлением»: скрипт выполняет восстановление
   ИЗ последнего доступного бэкапа/WAL-архива НА ОТДЕЛЬНЫЙ, изолированный тестовый инстанс Postgres
   (не production!), запускает базовые проверочные запросы (например, `SELECT count(*) FROM
   orders` — подтверждение, что данные реально читаемы после восстановления, не только что
   `pg_restore` завершился без ошибки), печатает время выполнения (для сверки с целевым RTO
   `≤4ч`) — скрипт предназначен для регулярного (ежеквартального) РУЧНОГО запуска оператором, НЕ
   для автоматического CI (восстановление production-объёма данных — дорогая операция).
4. `docs/RUNBOOK-PRODUCTION-READINESS.md` — переносит ПОЛНЫЙ чек-лист `docs/spec/31-nfr-security-
   testing-devops.md` §«Готовность к продакшену» (все 5 подразделов: Безопасность/Данные/
   Наблюдаемость/Функциональность/Юридическое) в формат исполняемого runbook — каждый пункт
   становится чекбоксом `- [ ]` с ССЫЛКОЙ на конкретный скрипт/команду, которая его проверяет,
   где применимо (например, пункт «Тест на утечку между тенантами — зелёный» ссылается на
   `pnpm test:security -- tenant-isolation-idor` из DTJ-425, пункт «Смена `BRAND_NAME`... не
   оставляет старой строки» ссылается на `pnpm test:e2e -- brand-invariant` из DTJ-423) — этот
   документ становится единственной точкой входа для человека, готовящего первый прод-релиз, не
   требует повторного чтения всего `31-nfr-security-testing-devops.md`.
5. Явно зафиксировать в runbook пункты, которые ОСТАЮТСЯ ручными/организационными и НЕ
   автоматизируются никаким скриптом (юридическая проверка товарного знака D-01, утверждение
   ставок комиссии D-03, минимум 2 человека с `super_admin`-доступом) — не пытаться
   автоматизировать то, что по своей природе — решение человека/организации.

## Критерии приёмки

1. Given `rolling-deploy.sh v1.2.0` запущен против DTJ-412 стека, When миграция намеренно
   сконфигурирована упасть (тестовая проверка), Then скрипт завершается ненулевым кодом ДО
   попытки пересоздать `api`/`worker` — старые контейнеры продолжают работать (деплой безопасно
   прерван, не оставляет систему в промежуточном состоянии).
2. Given успешный `rolling-deploy.sh`, When `replicas: 2` для `api`, Then в любой момент процесса
   деплоя минимум 1 инстанс `api` отвечает `200` на `/ready` (синтетическая проверка — параллельный
   поллинг во время выполнения скрипта, `TC-NFR-062`-подобная проверка).
3. Given релиз содержал `ALTER TABLE`-миграцию БЕЗ файла `*.down.sql`, When `rollback.sh`
   запущен для отката ЭТОГО релиза, Then скрипт печатает явное предупреждение о невозможности
   автоматического отката схемы ДО выполнения отката кода приложения (человек видит
   предупреждение, принимает информированное решение продолжать или нет).
4. Given `backup-restore-drill.sh` запущен против тестового бэкапа, When восстановление завершено,
   Then проверочный запрос возвращает ожидаемое количество строк (данные реально восстановлены, не
   пустая БД), время выполнения залогировано.

## Тест-план

Инфраструктурные bash-скрипты — юнит-тестов в классическом смысле нет. Верификация:
- `rolling-deploy.sh`: ручной прогон против DTJ-412 стека с намеренно проваленной миграцией
  (критерий приёмки 1) и с успешным сценарием (критерий приёмки 2) — оба прогона при ревью тикета,
  результат прикладывается к PR.
- `rollback.sh`: ручной прогон с тестовой миграцией, у которой намеренно отсутствует `*.down.sql`
  — подтверждение появления предупреждения.
- `backup-restore-drill.sh`: ручной прогон против тестового `pg_dump`/WAL-архива (может быть
  минимальным синтетическим дампом на этом тикете, не production-объёмом) на отдельном
  Postgres-контейнере.
- `docs/RUNBOOK-PRODUCTION-READINESS.md`: ревью-проверка — каждый пункт исходного чек-листа
  `31-nfr-security-testing-devops.md` присутствует в runbook, ни один не потерян при переносе
  (построчная сверка).

## Риски и подводные камни

Скрипты пишутся и проверяются на ТЕСТОВОМ/локальном Docker-стеке (DTJ-412), не на реальной
production-инфраструктуре, которая на момент этого тикета не существует — финальная валидация
«реального» деплоя (включая реальный registry, реальные секреты, реальный `GitHub Environments`
approval-gate из DTJ-414) — операционный шаг, выполняемый владельцем продукта при первом реальном
релизе R1, вне объёма разработки. `backup-restore-drill.sh` на реальных production-объёмах данных
(если/когда они появятся) может занимать часы — скрипт этого тикета проверяет МЕХАНИЗМ
восстановления на малом тестовом дампе, реальный RTO-замер `≤4ч` — отдельная организационная
проверка перед первым прод-релизом (пункт чек-листа `SRS-NFR-065`, помечен в runbook как требующий
повторного прогона на реальном объёме данных непосредственно перед запуском, не одноразово на
этом тикете).
