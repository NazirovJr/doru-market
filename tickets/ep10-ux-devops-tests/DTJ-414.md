## Задача

`docs/04-SCOPE-DECISION-PIVOT.md` критерий приёмки R1 №2: «`pnpm verify` — зелёный» — но локальная
зелёность у одного разработчика не гарантирует зелёность в PR другого; CI — единственный
объективный гейт, применяемый одинаково ко всем эпикам, начиная с первого коммита
(`00-EPICS.md` §«Обязательные сквозные тикеты»: «CI... с первого коммита — lint/arch:check/prettier
уже зелёные»). Без CI-пайплайна нарушения C1–C18/Правила Зависимостей будут обнаруживаться только
на code review человеком (медленно, ненадёжно) вместо автоматического блокирования PR.

## Технический контекст

`.github/workflows/ci.yml` — единоличное владение EP-19. Семь стадий (jobs), параллельные там, где
нет зависимости: `typecheck-lint-arch` (быстрый статический гейт, без БД) → `unit-tests` (матрица
по `apps/{api,worker,web,admin}`) и `integration-tests` (Postgres/Redis через нативные `services:`
GitHub Actions, НЕ через `docker-compose.test.yml` — два разных механизма, см. риск DTJ-413) и
`security-audit` — три параллельно после статического гейта → `build` (матрица по приложениям,
Docker-образы) → `e2e` (полный `docker-compose.yml`+`docker-compose.test.yml` из DTJ-412/413) →
`release-tag-only` (только по тегу `vX.Y.Z`, требует зелёных `e2e`+`security-audit`).

## Что сделать

1. Job `typecheck-lint-arch`: `actions/checkout@v4` → `pnpm/action-setup@v4` →
   `actions/setup-node@v4` (`node-version: '22.12'`, `cache: 'pnpm'`) → `pnpm install
   --frozen-lockfile` → `actions/cache@v4` для `.turbo` (ключ `turbo-${{ github.sha }}`,
   `restore-keys: turbo-`) → `pnpm turbo run typecheck lint arch:check --cache-dir=.turbo`.
2. Job `unit-tests`: `needs: typecheck-lint-arch`, `strategy.matrix.app: [api, worker, web,
   admin]` — по одному параллельному прогону на приложение, `pnpm turbo run test:unit
   --filter=${{ matrix.app }} -- --coverage`, `actions/upload-artifact@v4` для каждого coverage-
   отчёта (`coverage-${{ matrix.app }}`).
3. Job `integration-tests`: `needs: typecheck-lint-arch`, `services: { postgres: {image:
   postgres:16, env: {POSTGRES_PASSWORD: test}, options: --health-cmd pg_isready --health-interval
   5s --health-retries 10}, redis: {image: redis:7, options: --health-cmd "redis-cli ping"} }` —
   изолированный сервис НА ДЖОБУ (обязательное свойство, проверяемое TC-NFR-066 — два параллельных
   PR не видят данные друг друга), затем `pnpm db:migrate` → `pnpm test:integration` →
   `pnpm test:contracts` → `pnpm openapi:check`.
4. Job `security-audit`: `needs: typecheck-lint-arch`, `pnpm audit --audit-level=high` →
   `pnpm test:security` (сам тест-сьют — предмет тикета DTJ-425, эта job лишь вызывает
   `pnpm test:security` как отдельную команду, не содержит тестов сама).
5. Job `build`: `needs: [unit-tests, integration-tests]`, `strategy.matrix.app: [api, worker, web,
   admin]`, `docker/build-push-action@v6` с `push: false` (сборка образа без публикации — только
   проверка, что Dockerfile из DTJ-412 реально собирается), кэш слоёв `cache-from`/`cache-to: gha`.
6. Job `e2e`: `needs: build`, `docker compose -f infra/docker/docker-compose.yml -f
   infra/docker/docker-compose.test.yml up -d` → `pnpm wait-on http://localhost:3000/ready -t
   60000` → `pnpm db:seed` → `pnpm test:e2e` → `if: always(): docker compose ... down -v`
   (снос стека ДАЖЕ при падении тестов — не оставлять зомби-контейнеры на раннере).
7. Job `release-tag-only`: `if: startsWith(github.ref, 'refs/tags/v')`, `needs: [e2e,
   security-audit]`, `pnpm generate:openapi && git diff --exit-code docs/api/openapi.json`
   (падает, если сгенерированная спека разошлась с закоммиченной) → `docker/build-push-action@v6`
   реальный `push: true` с тегом релиза → комментарий о ручном approval-gate через GitHub
   Environments protection rule (настройка окружения в самом GitHub — операционный шаг вне
   YAML-файла, задокументировать инструкцию в PR description, не блокирует сам тикет).
8. Кэш-стратегия: `pnpm` store через встроенный `cache: 'pnpm'` `actions/setup-node`, Turborepo
   `.turbo` по SHA с restore-keys на предыдущий кэш, Docker layer cache `type=gha`.
9. Матрица БЕЗ кросс-браузерного Playwright в R1 (только Chromium по умолчанию, `SRS-NFR-059` —
   Firefox/WebKit — Should, не Must, добавляется отдельным `matrix.browser` шагом позже, не в
   этом тикете).

## Критерии приёмки

1. Given PR с намеренно проваленным unit-тестом в `apps/api` (тестовая фикстура-нарушитель,
   аналог `TC-NFR-057`), When push в PR, Then job `unit-tests` (matrix `api`) — красный, `build`/
   `e2e` НЕ запускаются (соблюдена цепочка `needs`).
2. Given два параллельных PR одновременно запускают `integration-tests`, When оба workflow
   выполняются, Then каждый использует СВОЙ изолированный Postgres-контейнер (`TC-NFR-066`) —
   проверяется тем, что данные, записанные одним прогоном, не видны другому (тест на уровне
   самого `integration-tests` сьюта, не CI-конфига напрямую, но зависит от изоляции, которую эта
   job обеспечивает).
3. Given push тега `v1.0.0` при зелёном `main`, When workflow запускается, Then job
   `release-tag-only` выполняется ПОСЛЕ `e2e` и `security-audit`, генерирует `openapi.json` и
   падает, если сгенерированный файл отличается от закоммиченного.
4. Given обычный push в feature-ветку (не тег), When workflow запускается, Then job
   `release-tag-only` НЕ запускается вовсе (условие `if` корректно фильтрует).
5. Given `.turbo`-кэш из предыдущего прогона на том же коммите, When повторный запуск, Then
   неизменившиеся таски `typecheck`/`lint`/`arch:check` пропускаются турбо-кэшем (видно в логе
   как `cache hit`), сокращая время прогона.

## Тест-план

Инфраструктурный YAML-пайплайн — юнит-тестов не пишется на сам пайплайн. Верификация — намеренные
пробные PR с фикстурами-нарушителями (переиспользует те же фикстуры, что `tests/arch/` из DTJ-415,
и намеренно проваленный тест из критерия приёмки 1), запускаемые ОДИН раз при ревью тикета для
подтверждения, что каждая job реально ловит соответствующий класс нарушения — тот же принцип
«ловушка проверяется ловушкой» (`02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1), применённый к CI-уровню.

## Definition of Done

- [ ] Код соответствует `docs/02-CLEAN-ARCHITECTURE-AND-CODE.md` (слои, C1-C18) — неприменимо
      напрямую к YAML
- [ ] `pnpm verify` зелёный локально
- [ ] Все 7 job проверены хотя бы одним пробным PR каждая (лог прогона приложен к PR этого тикета)
- [ ] Нет хардкода строк (i18n) и цветов (CSS-переменные) — неприменимо
- [ ] Изоляция параллельных `integration-tests` job подтверждена (`TC-NFR-066`)
- [ ] `release-tag-only` не запускается на обычных push, только на теги `vX.Y.Z`

## Риски и подводные камни

Пайплайн опирается на команды (`pnpm test:unit`, `pnpm test:integration`, `pnpm test:contracts`,
`pnpm openapi:check`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm generate:openapi`), часть из которых
определяется другими тикетами этого же эпика (DTJ-416/417) или другими эпиками (`pnpm db:seed` —
EP-04, `pnpm openapi:check`/`generate:openapi` — вероятно EP-01 контракты) — на момент реализации
этого тикета часть команд может ещё не существовать в `package.json` соответствующих пакетов;
пайплайн пишется по КОНТРАКТУ имён команд (зафиксировать точные имена в PR как согласованный
интерфейс), реальная сквозная зелёность всех job наступит только после появления кода всех
зависимых эпиков — это ожидаемо для тикета волны 1 и не является дефектом самого пайплайна.
`docker/build-push-action@v6` с `push: true` в `release-tag-only` требует настроенных секретов
registry (`DOCKER_REGISTRY_TOKEN` и т.п.) — конфигурация секретов в GitHub — операционный шаг вне
кода, задокументировать в PR как отдельный чек-лист-пункт для владельца репозитория.
- Файл `.github/workflows/ci.yml` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
