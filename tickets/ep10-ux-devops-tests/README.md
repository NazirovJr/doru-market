# EP-18 (Слой UX) + EP-19 (CI/DevOps/тестовая пирамида) — оглавление тикетов

> Владелец: Tech Lead EP-18/EP-19. Диапазон ID: **DTJ-400 .. DTJ-449** (использовано 400–428, 29
> тикетов, запас 21 ID до границы диапазона). Источники приоритета — см. `tickets/00-EPICS.md` и
> иерархию документов в корне тикета этого агента.

Оба эпика владеют непересекающимися каталогами файлов (`packages/ui`/`packages/i18n` у EP-18,
`infra/docker`, `.github/workflows`, `tests/{e2e,load,arch}` у EP-19, плюс новый пакет
`packages/testing-kit`, заведённый тикетом DTJ-416 — см. «Архитектурные решения» ниже), поэтому
внутри каждого эпика — своя цепочка волн, между эпиками жёсткой зависимости по файлам нет. Порядок
ниже — рекомендованный порядок выполнения по волнам готовности, не жёсткое требование одновременного
старта.

## Архитектурные решения этого Tech Lead, зафиксированные для координации с другими эпиками

1. **Новый пакет `packages/testing-kit`** (DTJ-416) — не входит в исходную таблицу владения файлами
   `tickets/00-EPICS.md` (там перечислены только `packages/contracts`/`packages/i18n`/`packages/ui`).
   Заведён как независимый pnpm-workspace пакет для детерминированных тест-дублёров (`FixedClockAdapter`,
   `SequentialTestIdGenerator`, `FixedOtpGeneratorAdapter`) и generic builder-утилиты — сознательно
   НЕ размещён внутри `apps/api/src/infrastructure/testing/**`, т.к. на момент планирования `apps/api`
   ещё не существовал (EP-01 не начат). Владельцы backend-эпиков (EP-01 и далее) импортируют классы
   из этого пакета как реализацию своих доменных портов `ClockPort`/`IdGenerator`/`OtpGeneratorPort`
   (`docs/spec/10-domain-model.md` §2.6) при появлении реального кода.
2. **`GET /api/v1/i18n/:locale`** (`SRS-API-058`) — backend-эндпоинт, раздающий словари из
   `packages/i18n` (DTJ-402), НЕ входит в зону владения EP-18 — реализуется владельцем базовых
   API-конвенций (вероятно EP-01). `packages/i18n` — единственный источник ПРАВДЫ для содержимого
   словарей, эндпоинт их только раздаёт.
3. **`GET /api/v1/_test/last-otp`** (`SRS-NFR-033`) — backend debug-эндпоинт, потребляемый хелпером
   `tests/e2e/helpers/get-otp-from-mock-sms.ts` (DTJ-417), НЕ реализуется этим эпиком — реализуется
   владельцем Auth-модуля (вероятно EP-01) по контракту, уже зафиксированному SRS.
4. **`TELEGRAM_API_BASE_URL`** — ENV-переменная, позволяющая перенаправить `TelegramNotifyProvider`
   на локальный стаб (`tests/e2e/helpers/mock-telegram-bot-api-server.ts`, DTJ-417) в тестовом
   профиле — согласовать точное имя/поведение с владельцем EP-16 (NotificationService) при первой
   интеграции.
5. **Отсутствующие SRS-* идентификаторы**: тикет DTJ-415 (`tests/arch/`) сознательно оставлен без
   `srs_refs` — требование происходит из `docs/02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1, который не
   входит в нумерованный корпус `docs/spec/*.md` и не имеет собственного SRS-ID.
