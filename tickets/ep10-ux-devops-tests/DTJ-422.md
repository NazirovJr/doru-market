## Задача

CUJ-11 закрывает R1-13 (Telegram-канал уведомлений — основной в РТ, дешевле SMS) отдельно от уже
покрытого TWA Mini App режима (`SRS-NFR-075` явно отделяет эти два сценария). CUJ-12 закрывает
R1-14 (i18n tj/ru/en) — единственная автоматическая проверка, что переключение языка МЕНЯЕТ 100%
видимых строк экрана, а не только часть (частая i18n-ошибка — забытый хардкод одной строки при
добавлении нового экрана).

## Технический контекст

CUJ-11 использует `mock-telegram-bot-api-server` (DTJ-417) вместо реального Telegram API,
переопределяя `TELEGRAM_API_BASE_URL` в тестовом ENV — тот же класс `TelegramNotifyProvider`, что и
в проде (не отдельный Mock-класс, `SRS-ADM-051`), только исходящий HTTP-вызов перехватывается
локально. CUJ-12 использует `@axe-core/playwright` (через `runAxeCheck`, DTJ-417) для снимка DOM
до/после переключения языка — сравнение множества видимых строк, не точечная проверка отдельных
элементов.

## Что сделать

1. `tests/e2e/cuj-11-telegram-notifications.e2e-spec.ts` — точно по `SRS-NFR-075`: (1) тестовый
   пользователь с уже привязанным `telegram_chat_id` (seed, без прогона реального `/start`-
   диплинка); (2) как `customer`, оформить заказ до статуса, порождающего
   `OrderProcessingStartedEvent` (канал `telegram → web_push`, без `sms`); (3) прочитать тело
   запроса, полученное стабом (`sendMessage`, `chat_id` совпадает, текст на языке профиля
   пользователя) через `mockTelegramBotApiServer.getReceivedCalls()`; (4) убедиться, что
   `notifications` содержит РОВНО одну строку `channel='telegram', status='sent'` с
   `source_event_id`, равным id события заказа; (5) повторно опубликовать ТО ЖЕ доменное событие
   в `outbox` (симуляция at-least-once доставки — через тестовый API-триггер повторной публикации,
   если предоставлен, иначе — прямая манипуляция БД в тестовом окружении) → дедупликация
   (`SRS-ADM-057`, `uq_notifications_dedup`) НЕ создаёт вторую строку/второй вызов стаба; (6)
   `mockTelegramBotApiServer.simulateOutage()` → следующее уведомление (`OrderCancelledEvent`, есть
   фолбэк `sms`) доставляется каналом `sms` (`notifications(channel='sms').status='sent'`),
   `telegram` для этого события помечен `failed` (`SRS-ADM-060`-подобная фолбэк-логика).
2. `tests/e2e/cuj-12-i18n.e2e-spec.ts` — точно по `SRS-NFR-076`: (1) НЕ авторизованный контекст,

   переключить `LanguageSwitcher` → `ru` → снимок DOM (текст, `alt`, `title`, `aria-label`) ДО и
   ПОСЛЕ переключения — 100% видимых строк изменились (включая `brand.name`, не хардкод);
   количество упаковок в демо-заказе (1/2/5, из seed, `SRS-UX-032`) отображено с корректной
   русской плюрализацией; (3) переключить → `en` → аналогичная проверка снимка DOM; (4)
   переключить → `tj` → карточка количества использует ЕДИНУЮ неизменяемую форму с
   классификатором (НЕ «сломанную» русскую плюрализацию по ошибке — явная негативная проверка,
   что старый `ru`-текст не остался); (5) заполнить частично форму `/pharmacy-application` на
   `ru` (используя `tests/fixtures/i18n/partial-application-form.json` из DTJ-417), переключить на

   метки/плейсхолдеры — на `tj`; (6) прямой запрос `GET /api/v1/i18n/:locale` для всех трёх

3. Утилита сравнения снимков DOM (`tests/e2e/helpers/dom-text-snapshot.ts`, если ещё не создана

   + значимые атрибуты (`alt`/`title`/`aria-label`), переиспользуется также E2E-инвариантом бренда
   (DTJ-423) — координация по общему хелперу, не дублирование логики снятия снимка (C15).

## Критерии приёмки

1. Given стаб Telegram получил ровно один вызов на первое событие, When то же доменное событие
   опубликовано повторно (симуляция at-least-once), Then стаб НЕ получает второго вызова, в
   `notifications` — по-прежнему ровно одна строка `channel='telegram'` для этого `source_event_id`.
2. Given стаб временно недоступен (`simulateOutage`), When событие с фолбэком `sms` порождается,
   Then доставка происходит каналом `sms` УСПЕШНО, `telegram` для этого конкретного события
   зафиксирован как `failed`, сценарий уведомлений НЕ падает целиком.
3. Given переключение `tj → ru`, When снимок DOM сравнивается до/после, Then множество видимых
   строк меняется на 100% (пересечение множеств «до» и «после» — пусто, за вычетом чисто
   графических/неизменных элементов вроде иконок без текста).
4. Given форма частично заполнена на `ru`, When язык переключён на `tj` БЕЗ отправки формы, Then
   `value` каждого заполненного поля идентичен введённому (посимвольное сравнение), метки полей —
   на `tj`.
5. Given прямой запрос `GET /api/v1/i18n/tj`, `/ru`, `/en`, When ответы получены, Then каждый —
   непустой JSON-словарь (не пустой объект, не `404`, не таймаут).

## Риски и подводные камни

Симуляция «повторной публикации ТОГО ЖЕ доменного события» для проверки дедупликации (CUJ-11 шаг
5) требует тестового способа форсировать at-least-once доставку — специфический механизм не
описан ни одним SRS-документом дословно (только требование результата — дедупликация должна
сработать) — конкретный API/приём для теста согласовать с владельцем EP-16 (NotificationService)
при реализации, задокументировать выбранный подход в PR. Снимок DOM для CUJ-12 (`captureVisible
TextSnapshot`) чувствителен к динамическому контенту (случайные ID заказов, временные метки) —
утилита обязана явно исключать/нормализовывать такие узлы (например, по `data-testid`-маркеру
«не проверять» или регэксп-фильтру чисто числовых значений) — иначе тест будет ложно-положительно
детектировать «изменение текста» на статичных числовых ID, не связанных с локалью.
