## Задача

`SRS-UX-034` требует чек-лист доступности на КАЖДОМ PR, затрагивающем `packages/ui`, и
автоматический axe-прогон в Storybook/CI (`SRS-UX-035`). Если этот инструментарий не готов ДО
первого компонента (DTJ-404), проверка доступности останется ручной и необязательной — риск того,
что нарушения накопятся к 30+ компонентам и их придётся чинить пакетно вместо предотвращения по
одному. Целевая аудитория продукта — пожилые пациенты со слабым зрением на дешёвых Android-устройствах
(`docs/spec/30-ux-screens-and-flows.md` §1) — это не формальное требование WCAG «для галочки», а
прямое условие того, что продукт вообще открывается основной аудиторией.

## Технический контекст

Слой — `packages/ui/src/a11y/**`, переиспользуемые React-хуки + тестовые утилиты, без прямой связи
с конкретными компонентами (компоненты DTJ-404+ импортируют эти утилиты, не наоборот — соблюдается
правило зависимостей `entities`/`shared` из `02-CLEAN-ARCHITECTURE-AND-CODE.md` §5). Storybook уже
настроен с `@storybook/addon-a11y` тикетом DTJ-400 — этот тикет добавляет ВТОРОЙ, независимый
канал проверки: `vitest`-юниты, которые могут гонять axe против отрендеренного через
`@testing-library/react` компонента без поднятия Storybook (быстрее в CI, часть `pnpm test:unit`).

## Что сделать

1. `packages/ui/src/a11y/use-reduced-motion.ts` — хук `useReducedMotion(): boolean`, обёртка над
   `window.matchMedia('(prefers-reduced-motion: reduce)')` с подпиской на изменение в рантайме
   (пользователь может переключить системную настройку не перезагружая страницу) — используется
   ВСЕМИ анимированными компонентами (`SRS-UX-020`: переход `default → loading → success/error`
   ≤200мс ОБЯЗАН уважать это предпочтение, декоративные переходы отключаются полностью, функциональные
   сокращаются до мгновенной смены).
2. `packages/ui/src/a11y/use-focus-trap.ts` — хук `useFocusTrap(containerRef, isActive: boolean)`
   для `Modal`/`BottomSheet` (DTJ-406): при активации — фокус переходит на первый интерактивный
   элемент контейнера, `Tab`/`Shift+Tab` циклируются ВНУТРИ контейнера, `Escape` вызывает переданный
   `onClose`, при деактивации — фокус возвращается на элемент, который был активен ДО открытия
   (`SRS-UX-034` строка «Клавиатурная навигация»).
3. `packages/ui/src/a11y/assert-hit-area.ts` — тестовая утилита `assertHitArea(element: HTMLElement,
   minSizePx: number)`, вычисляющая ЭФФЕКТИВНУЮ область попадания (включая `padding`, НЕ только
   визуальный `border-box`, через `getComputedStyle` + `getBoundingClientRect`) и бросающая
   читаемую ошибку с фактическим/требуемым размером при нарушении — переиспользуется КАЖДЫМ
   интерактивным компонентом (`SRS-UX-002`: 48×48px везде, 56×56px для критичных действий
   кабинета аптеки).
4. `packages/ui/src/a11y/test-utils.ts` — обёртка `renderWithA11yCheck(ui: ReactElement):
   Promise<{ container; axeResults }>`, рендерит через `@testing-library/react` и синхронно
   прогоняет `axe-core` (`vitest-axe` или `jest-axe`-подобный адаптер под Vitest), возвращает
   структурированный результат, готовый к `expect(axeResults).toHaveNoViolations()`.
5. `packages/ui/vitest.config.ts` — конфигурация Vitest для `packages/ui` (`jsdom`-окружение,
   `@testing-library/jest-dom`-матчеры, покрытие через `@vitest/coverage-v8`), интегрируется с
   корневым `turbo.json` таргетом `test:unit`.
6. Документировать (короткий `packages/ui/src/a11y/README.md` ИЛИ JSDoc-комментарий на
   `test-utils.ts` — на усмотрение разработчика, не отдельный файл если JSDoc покрывает) правило:
   «нарушений уровня `critical`/`serious` — ноль, `moderate`/`minor` — предупреждение, не блокирует
   CI» (согласовано с `SRS-UX-035` порогом для E2E-уровня, применяется по аналогии к unit-уровню).

## Критерии приёмки

1. Given кнопка с визуальным размером 40×40px и `padding` 4px с каждой стороны (эффективная область
   48×48px), When `assertHitArea(button, 48)`, Then проверка проходит (эффективная область, не
   визуальная, — критично для расхождения №4 `32-design-reference.md`: визуал можно сохранить
   маленьким, если hit-area достаточна).
2. Given кнопка 32×32px без компенсирующего padding, When `assertHitArea(button, 48)`, Then
   бросается ошибка с текстом, включающим фактический размер `32×32` и требуемый `48×48`.
3. Given компонент с намеренно убранным `outline`/фокус-индикатором (тестовая фикстура-нарушитель),
   When `renderWithA11yCheck` + `axe`, Then результат содержит нарушение (тест ЛОВИТ регресс, не
   просто «зелёный по умолчанию» — тот же принцип «ловушка проверяется ловушкой»,
   `02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1).
4. Given `prefers-reduced-motion: reduce` включён (мокается через `matchMedia` в тесте), When
   `useReducedMotion()`, Then возвращает `true`, и повторный вызов после мока изменения на `false`
   (симуляция переключения настройки в рантайме через `dispatchEvent`) возвращает `false` без
   перемонтирования компонента.

## Тест-план

Unit (`packages/ui/src/a11y/assert-hit-area.spec.ts`):
- `passes when effective hit area (including padding) meets minimum`
- `fails with readable actual/required size when hit area is too small`
- `accounts for negative margin hit-slop technique correctly` (если применяется в компонентах —
  граничный случай, задокументировать поведение явно, даже если ответ «не поддерживается в v1»)

Unit (`packages/ui/src/a11y/use-reduced-motion.spec.ts`):
- `returns current matchMedia state on mount`
- `reacts to runtime preference change via change event`

Интеграционный самопроверочный тест (фикстура-нарушитель, аналог `tests/arch/` паттерна из
`02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1, но для a11y-гварда пакета `packages/ui`):
`packages/ui/src/a11y/__fixtures__/broken-focus-button.tsx` (компонент без видимого фокуса) +
тест, подтверждающий, что `renderWithA11yCheck` РЕАЛЬНО ловит это нарушение — если тест зелёный
без нарушений, значит сама проверка сломана и ловушка перестала ловить.

Порог покрытия — 90% для `assert-hit-area.ts`/`use-reduced-motion.ts`/`use-focus-trap.ts`.

## Риски и подводные камни

`axe-core` под `jsdom` не проверяет реальный computed contrast так же надёжно, как настоящий
браузер (`jsdom` не рендерит CSS полностью) — контрастные нарушения текста могут быть ложно-
отрицательными на unit-уровне; финальная сеть контрастных проверок — Playwright `@axe-core/playwright`
в реальном браузере на E2E-уровне (тикет DTJ-417/418+), unit-уровень здесь ловит структурные
нарушения (`aria-*`, `role`, порядок табуляции, отсутствие `alt`), не пиксельный контраст. Это
ограничение, не дефект — явно зафиксировать в комментарии к `test-utils.ts`, чтобы будущие
разработчики не считали unit-прогон axe достаточным для контрастных требований `SRS-UX-003`.
