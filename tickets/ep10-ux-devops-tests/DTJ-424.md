## Задача

`03-ARCHITECT-DECISIONS.md` D-04/D-05 зафиксировали КОНКРЕТНЫЕ проектные цели производительности
(500 item-events/сек устойчиво, burst 2000/сек; латентность поиска <250мс кэш-промах), явно
отклонив цифры из `tz.log` как «завышенные на 2 порядка... over-engineering запрещён». Без
нагрузочных тестов эти цифры остаются недоказанными заявлениями — `docs/spec/31-nfr-security-testing-devops.md`
§«NFR и их проверка» требует измеримой проверки КАЖДОЙ строки таблицы, не только качественного
«работает быстро».

## Технический контекст

`tests/load/**` — владение EP-19. k6-сценарии запускаются НЕ на каждый PR (слишком дорого,
`SRS-NFR-059`), а вручную перед релизом + еженедельно по расписанию (`.github/workflows/load-tests.yml`,
`cron: '0 2 * * 0'`). Целевые значения — таблица `SRS-NFR-036` (полная, уже прочитана при
подготовке этого набора тикетов).

## Что сделать

1. `tests/load/catalog-search.k6.js` — сценарий против `GET /medicines/search`: `stages` с
   постепенным ростом до целевого RPS, ассерты p95 `< 250мс` (кэш-промах, `SRS-CAT-061` точная
   таблица), отдельный сценарий/`stages` для кэш-хита `< 30мс` и для запроса аналогов `< 300мс`.
2. `tests/load/inventory-sync.k6.js` — сценарий против `POST /inventory/batch-update`: устойчивая
   фаза `≥500 item-events/сек`, burst-фаза (резкий подъём, окно ≤5 мин) `≥2000/сек` БЕЗ деградации
   ACK `p95 < 300мс` (D-05), метрика `inventory_sync_items_processed_total` — assert на итоговый
   throughput, не только код ответа.
3. `tests/load/checkout.k6.js` (НОВЫЙ сценарий, не существовавший ранее ни в одном модульном SRS-
   документе явно, но перечислен таблицей пирамиды `SRS-NFR-028`) — нагрузка на `POST
   /api/v1/orders` (наличный путь, самый частый в R1), целевое значение — общий Charter-порог
   `<300мс p95` (строка 2 таблицы `SRS-NFR-036`, checkout — синхронная операция, не подпадает под
   исключение асинхронных OCR/STT).
4. `.github/workflows/load-tests.yml` — отдельный workflow (НЕ часть `ci.yml` из DTJ-414, чтобы не
   замедлять обычный PR-pipeline), `on: { schedule: [{ cron: '0 2 * * 0' }], workflow_dispatch: {} }`
   (ручной запуск перед релизом через `workflow_dispatch`), поднимает полный `docker-compose.yml`
   (DTJ-412), `pnpm db:seed` для реалистичного объёма данных, запускает все три `.k6.js`-сценария,
   публикует результат как artifact/summary, красный статус — уведомление (issue/Slack, конкретный
   канал — операционное решение, зафиксировать хотя бы `actions/upload-artifact` с summary как
   минимальный вариант).

## Критерии приёмки

1. Given `tests/load/catalog-search.k6.js` запущен против стека с реалистичным объёмом seed-данных
   (≥300 медикаментов), When тест завершён, Then p95 латентности кэш-промаха `< 250мс` — иначе
   выход k6 ненулевой (threshold fail).
2. Given `tests/load/inventory-sync.k6.js`, When устойчивая фаза выполнена, Then throughput
   `≥500 item-events/сек`; When burst-фаза выполнена, Then `≥2000/сек` при ACK `p95 < 300мс`.
3. Given `tests/load/checkout.k6.js`, When тест завершён, Then p95 `< 300мс` для `POST /orders`
   (наличный путь, без внешнего платёжного провайдера в критическом пути).
4. Given `load-tests.yml` запущен вручную (`workflow_dispatch`), When один из трёх сценариев
   проваливает threshold, Then весь workflow завершается с ненулевым кодом (виден как красный в
   Actions), НЕ блокирует при этом обычные PR (workflow полностью независим от `ci.yml`).

## Тест-план

Сами k6-сценарии — это и есть «тест», в классическом unit/integration смысле проверять нечего
(нет бизнес-логики, только нагрузочные сценарии + встроенные k6 `thresholds`). Верификация тикета —
ручной прогон каждого сценария при ревью против локально поднятого стека (DTJ-412) с seed-данными,
подтверждающий, что threshold-конфигурация k6 реально приводит к ненулевому коду выхода при
намеренно заниженном пороге (временная проверка: поставить `p(95)<1` вместо `p(95)<250` — тест
обязан упасть, подтверждая, что threshold реально проверяется, не просто присутствует в файле).

## Риски и подводные камни

Реалистичный прогон нагрузочных тестов на актуальный целевой RPS невозможен до появления
реализованных backend-эндпоинтов поиска/1С-ingestion/checkout (EP-06/EP-05/EP-09/EP-10) — этот
тикет пишет сценарии ПО КОНТРАКТУ эндпоинтов, финальная калибровка thresholds и подтверждение
реального прохождения — после соответствующих волн. Целевые цифры D-04/D-05 — ASSUMPTION
(`03-ARCHITECT-DECISIONS.md` явно помечает как рабочие дефолты до утверждения) — если по факту
реализации выяснится, что цели недостижимы на выбранной инфраструктуре, это эскалируется
архитектору как ADR, не тихо ослабляется в k6-скрипте разработчиком. `tests/load/checkout.k6.js` —
единственный из трёх сценариев БЕЗ явного SRS-* референса на конкретное k6-имя файла (упомянут
только меткой «НОВЫЙ» в таблице `SRS-NFR-028`) — уточнить точное имя файла и целевые параметры не
расходится с ожиданиями владельца EP-09/EP-10 при первой интеграции.
- Файл `.github/workflows/load-tests.yml` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
