## Задача

CUJ-13 — КРИТИЧЕСКИЙ сценарий: без него нельзя автоматически подтвердить входные данные для
kill-критериев `docs/04-SCOPE-DECISION-PIVOT.md` §7 — то есть без него невозможно принять решение о
судьбе продукта после 6–8 недель эксплуатации R1 (`SRS-NFR-077`). Инвариант смены бренда — прямое
следствие решения владельца продукта D-01 (`03-ARCHITECT-DECISIONS.md`): «хардкод строки бренда...
блокирующий дефект ревью», единственный способ доказать это автоматически, а не полагаться на
код-ревью «на глаз» (`docs/04-SCOPE-DECISION-PIVOT.md` §8).

## Технический контекст

CUJ-13 пошагово — `docs/spec/31-nfr-security-testing-devops.md` §«E2E-спецификации» `SRS-NFR-077`.
Требует ИЗОЛИРОВАННОГО среза `product_events` (обнулённого/отфильтрованного по тестовому
`sessionId`/`period`), чтобы точные числовые ассерты не зависели от прочих E2E-тестов, выполнявшихся
в том же прогоне БД — критично, т.к. это единственный CUJ-тест с точными числовыми (не только
структурными) утверждениями. Инвариант бренда — `SRS-NFR-078`, та же спецификация, что уже
зафиксирована `SRS-TEN-017`/`TC-TEN-011` и `TC-UX-002` в других документах — этот тикет реализует
ЕДИНСТВЕННУЮ явную версию, на которую ссылаются остальные упоминания.

   цифры без новых событий).

## Критерии приёмки

1. Given изолированный срез событий, When полный проход воронки выполнен один раз, Then КАЖДЫЙ из
   пяти счётчиков воронки (`searchPerformed`..`orderPlaced`) равен РОВНО 1 (не ≥1) для этого среза.
2. Given числа шага 4 (`savingsDiram` показанного аналога) и шага 6 (`savingsDiramAtAdd`), When
   сравниваются с `totalSavingsShownDiram`/`totalSavingsRealizedDiram` из ответа `funnel`, Then
   совпадают ЧИСЛЕННО с точностью до дирама (не приблизительно, не «больше нуля»).
3. Given повторный вызов `GET /analytics/funnel` БЕЗ новых событий между вызовами, When ответы
   сравниваются, Then идентичны (идемпотентность).
4. Given `brandName` изменён на уникальную тестовую строку, When поиск СТАРОЙ строки бренда
   выполнен по всем перечисленным маршрутам на всех 3 локалях в DOM И в исходном HTML/JS, Then
   НОЛЬ совпадений — тест красный при ЛЮБОМ найденном вхождении, включая `<title>` вкладки и
   i18n-ключи с ошибочным хардкодом вместо `{{brand.name}}`.
5. Given этот тест уже красный при найденном хардкоде (проверка самого теста при ревью — временно
   вставить буквальную строку «DoruTJ» в тестовый компонент-фикстуру), When тест запущен, Then
   действительно падает с указанием маршрута/локали, где найдена строка (подтверждение, что
   ловушка реально ловит, `02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1 принцип, применённый к
   бренд-инварианту).

- `CUJ-13: totalSavingsRealizedDiram matches actual order savings exactly`
- `CUJ-13: overallShownToOrder conversion rate equals 1.0 for isolated slice`

## Риски и подводные камни

`totalSavingsRealizedDiram` требует связи между «ранее показанным аналогом» и конкретной позицией
заказа (`Σ savingsDiram по order_items, где medicine соответствует ранее показанному аналогу`,
`SRS-ADM-068`) — точный алгоритм этого сопоставления реализуется backend-модулем EP-17
(аналитика), тест пишется по контракту РЕЗУЛЬТАТА (числа сходятся), не по внутреннему алгоритму
сопоставления — если реализация EP-17 считает это иначе (например, по последнему показанному
аналогу за сессию, а не по точному совпадению `medicineId`), потребуется координация точной
семантики поля при первой реализации. Проверка исходного HTML/JS-бандла на отсутствие старой
строки бренда (шаг 4 инварианта) требует доступа к СОБРАННЫМ статическим файлам фронтенда (не
только рендеренному DOM) — тест обязан либо делать прямой HTTP-запрос к раздаваемым `.js`-чанкам
и грепать их текст, либо читать файлы из смонтированного тестового контейнера — конкретный
механизм закрепляется в PR, оба варианта допустимы, если результат — исчерпывающая проверка всего
отданного клиенту кода, не выборочная.
