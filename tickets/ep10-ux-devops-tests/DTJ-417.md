## Задача

Это подготовительный (scaffolding) тикет для всей серии E2E CUJ-тестов (DTJ-418..423) — конкретные
сценарии нельзя писать, пока нет: (1) конфигурации Playwright, указывающей на поднятый Docker-стек;
(2) способа получить OTP-код без реального SMS; (3) локального стаба Telegram Bot API для CUJ-11;
(4) единой точки подключения `@axe-core/playwright`, обязательной для КАЖДОГО сценария CUJ-1..8
(`SRS-UX-035`). Без этого каждый следующий CUJ-тикет заново изобретал бы свою обвязку — прямое
нарушение C15 (DRY после третьего повтора — здесь повторов заведомо 6+).

## Технический контекст

`tests/e2e/**` и `tests/fixtures/**` — владение EP-19 (`00-EPICS.md` §«Обязательные сквозные
тикеты»: «E2E-инфраструктура (Playwright harness, фикстуры CUJ, конфиг раннера) — EP-19»). Стек
для прогона — `docker-compose.yml`+`docker-compose.test.yml` (DTJ-412/413), поднимается ВНЕШНЕ по
отношению к этому тикету (в CI — job `e2e` из DTJ-414; локально — разработчик поднимает вручную
командой из комментария DTJ-413). Debug-эндпоинт `GET /api/v1/_test/last-otp?phone=...`
(`SRS-NFR-033`) и локальный стаб Telegram Bot API — backend-часть НЕ входит в этот тикет (эндпоинт
реализуется владельцем Auth-модуля, вероятно EP-01, по контракту `SRS-NFR-033`; стаб-СЕРВЕР —
именно тестовый HTTP-хелпер, легитимно принадлежит `tests/e2e/helpers/**`, этот тикет).

## Что сделать

1. `tests/e2e/playwright.config.ts` — `baseURL` из ENV (`E2E_BASE_URL`, дефолт
   `http://localhost:3000`), `projects: [{ name: 'chromium', use: devices['Desktop Chrome'] }]`
   (ТОЛЬКО Chromium в R1, `SRS-NFR-059`), таймауты (`timeout`, `expect.timeout`) с запасом под
   `Slow 3G`-подобные сценарии, `reporter: ['list', 'html']`, `retries: 0` локально /
   `retries: 1` в CI (`process.env.CI`-ветвление — компенсирует редкую сетевую флакиность
   Docker-стека, НЕ маскирует реальные баги, зафиксировать явно в комментарии конфига «retries
   не заменяют детерминированность, `SRS-NFR-030` остаётся обязательным»).
2. `tests/e2e/helpers/wait-for-ready.ts` — обёртка над `pnpm wait-on` логикой (или прямой fetch-
   поллинг) для `GET /ready`, используемая в `globalSetup` Playwright — гарантирует, что тесты не
   стартуют раньше готовности бэкенда (дополняет CI-шаг `wait-on` из DTJ-414 защитой на случай
   локального запуска без него).
3. `tests/e2e/helpers/get-otp-from-mock-sms.ts` — функция `getOtpFromMockSms(phone: string):
   Promise<string>`, реализующая ОБА пути `SRS-NFR-033`: основной — `GET
   /api/v1/_test/last-otp?phone=...` (доступен только при `NODE_ENV=test`), запасной —
   опциональный параметр `fallbackToSmsLog: boolean`, читающий последнюю запись
   `notifications(channel='sms')` через прямой REST-эндпоинт (если он существует на момент
   использования) — реализовать основной путь ПОЛНОСТЬЮ рабочим, запасной — заглушка с явным
   `throw new Error('not implemented — see SRS-NFR-033(б)')`, чтобы не блокировать тикет
   отсутствием ещё не построенного REST-эндпоинта чтения `notifications`.
4. `tests/e2e/helpers/mock-telegram-bot-api-server.ts` — локальный HTTP-сервер (Node `http`/`fastify`,
   на выбор разработчика — минимальная зависимость предпочтительна), поднимаемый ТОЛЬКО в
   тестовом окружении, эмулирующий `POST /bot<token>/sendMessage` Telegram Bot API: сохраняет
   каждый входящий вызов в памяти (доступно тесту через `server.getReceivedCalls()`), метод
   `server.simulateOutage(durationMs)` — временно отвечает `500` на все запросы (для проверки
   circuit breaker/фолбэк-канала в CUJ-11, DTJ-422); `TELEGRAM_API_BASE_URL` ENV должен указывать
   на этот сервер в тестовом окружении (значение проставляется CI/локальным `.env.test`, не этим
   файлом).
5. `tests/e2e/helpers/axe-check.ts` — функция `runAxeCheck(page: Page): Promise<void>`,
   обёртка над `@axe-core/playwright` (`AxeBuilder`), утверждающая НОЛЬ нарушений уровня
   `critical`/`serious` (`SRS-UX-035`), вызывается КАЖДЫМ CUJ-сценарием на финальном состоянии
   экрана — единая точка, чтобы порог нарушений менялся в одном месте, а не в каждом тесте.
6. `tests/fixtures/README.md` — документирует стандартную точку отсчёта (`FixedClockAdapter`
   эпоха из DTJ-416, `2026-08-27T09:00:00.000Z`), структуру папок фикстур, соглашение об именах
   тестовых файлов рецептов (`high-confidence-caps.jpg`/`low-confidence-blurry.jpg`/
   `unrecognized-filename.jpg` — используются `MockOcrProvider`, `SRS-NFR-035`, реальные файлы-
   заглушки создаются владельцем EP-модуля рецептов при потребности, не этим тикетом).
7. `tests/fixtures/onboarding/.gitkeep`, `tests/fixtures/prescriptions/.gitkeep` — резервируют
   структуру каталогов для файлов, которые добавят DTJ-421 (лицензия аптеки) и модуль рецептов
   (флаг R1), не создавая сами бинарные файлы здесь (вне зоны этого тикета — только скелет).
8. `tests/fixtures/i18n/partial-application-form.json` — тестовые значения частично заполненной
   формы `/pharmacy-application` (поля «название юрлица», «телефон») для CUJ-12 (DTJ-422),
   создаётся здесь, т.к. используется ОБЩЕЙ инфраструктурой фикстур, не специфична для конкретного
   CUJ-теста по смыслу (переиспользуемая тестовая заготовка).

## Критерии приёмки

1. Given Docker-стек поднят (DTJ-412/413) и debug-эндпоинт доступен (`NODE_ENV=test`), When
   `getOtpFromMockSms('+992901234567')` вызван сразу после `POST /auth/otp/request` для этого
   номера, Then возвращает 6-значный код, идентичный тому, что реально сохранён бэкендом (либо
   фиксированному `483920` при `FixedOtpGeneratorAdapter`, если он подключён на бэкенде).
2. Given `mockTelegramBotApiServer` запущен, When тестовый код вызывает эндпоинт, эмулирующий
   отправку сообщения ботом (через реальный HTTP-вызов от бэкенда, настроенного на
   `TELEGRAM_API_BASE_URL`), Then `server.getReceivedCalls()` содержит ровно один вызов с
   ожидаемым `chat_id`/текстом.
3. Given `server.simulateOutage(5000)` вызван, When любой запрос приходит на сервер в течение
   следующих 5 секунд, Then сервер отвечает `500`, после истечения интервала — снова `200`-подобное
   поведение по умолчанию.
4. Given страница с намеренно убранным `aria-label` у иконки-кнопки (тестовая фикстура-нарушитель
   для проверки самого хелпера), When `runAxeCheck(page)`, Then промис отклоняется/тест падает с
   сообщением, включающим описание нарушения (подтверждает, что хелпер реально ловит нарушения,
   не проходит «зелёным» всегда).

## Тест-план

Это инфраструктурный (helper) тикет — «тесты» здесь означают самопроверку каждого хелпера:
- `mock-telegram-bot-api-server`: unit/интеграционный тест самого хелпера (Vitest, БЕЗ Playwright) —
  сервер стартует на случайном свободном порту, принимает POST, накапливает вызовы, `simulateOutage`
  реально возвращает 500 в указанный интервал и восстанавливается после.
- `axe-check.ts`: самопроверочный Playwright-тест против МИНИМАЛЬНОЙ статической HTML-страницы
  (не требующей полного бэкенда) с намеренным нарушением (та же фикстура-нарушитель, что критерий
  приёмки 4) — подтверждает, что обёртка реально ловит нарушения, аналог принципа `tests/arch/`.
- `wait-for-ready.ts`: unit-тест логики поллинга (мок `fetch`, возвращающий `503` N раз подряд,
  затем `200` — утилита корректно ждёт и не завершает раньше времени; таймаут — утилита бросает
  понятную ошибку по истечении лимита, не висит бесконечно).

Полноценные E2E CUJ-сценарии, использующие эту инфраструктуру, — отдельные тикеты DTJ-418..423.

## Риски и подводные камни

`GET /api/v1/_test/last-otp` — backend-эндпоинт, специфицированный `SRS-NFR-033`, но НЕ входящий в
файлы владения EP-19 (реализуется владельцем Auth-модуля) — на момент этого тикета `apps/api` ещё
не существует (волна 1), поэтому `getOtpFromMockSms` пишется по контракту эндпоинта и не может
быть полностью интеграционно проверена до появления реального Auth-модуля; зафиксировать это как
явную зависимость по КОНТРАКТУ (не по файлам) от соответствующего эпика в PR. `mock-telegram-bot-
api-server` слушает `TELEGRAM_API_BASE_URL` — переменная окружения должна быть согласована с
владельцем NotificationService (вероятно EP-16), чтобы реальный `TelegramNotifyProvider` в тестовом
профиле реально указывал на этот стаб, а не на `https://api.telegram.org` — координация имени ENV
зафиксирована в реестре `SRS-NFR-053`, риск — расхождение в написании имени переменной между
эпиками, проверить точное совпадение строки при первой реальной интеграции.
