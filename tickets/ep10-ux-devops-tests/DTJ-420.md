## Задача

Эти два сценария — самая длинная непрерывная цепочка критического пути R1
(`00-EPICS.md` §«Критический путь»: «...EP-09 → EP-10 → EP-12 → EP-13...», единственный путь,
физически проходящий через все статусы заказа от `confirmed` до `delivered`). CUJ-3' проверяет SLA-
таймер сборки с автоматической отменой по таймауту (`SRS-PHT-034`) — денежно значимая логика
(полный рефанд), CUJ-4' проверяет OTP-вручение и приём наличных курьером — последний шаг, замыкающий
весь заказ.

## Технический контекст

Оба сценария пошагово — `docs/spec/30-ux-screens-and-flows.md` §4, таблицы CUJ-3'/CUJ-4'. SLA-
таймер (7 минут, D-19) проверяется через продвижение `FixedClockAdapter` (DTJ-416) на бэкенде
(тестовое окружение) — тест НЕ ждёт реальные 7+5 минут (`SRS-NFR-030` п.1, `TC-NFR-030` — идентичный
результат двух прогонов CI). Оба сценария продолжают заказ, оформленный по логике CUJ-2' (DTJ-419) —
переиспользовать хелпер оформления наличного заказа как общую подготовку (`test.beforeEach` или
отдельная переиспользуемая функция `placeCashOrder()` в `tests/e2e/helpers/`, не дублировать шаги
checkout внутри этих двух файлов — C15).

## Что сделать

1. `tests/e2e/cuj-3-pharmacy-assembly.e2e-spec.ts`: (1) как `pharmacist`, открыть
   `/admin/order-queue` ПОСЛЕ нажатия «Начать смену» (разблокировка звука, `SRS-UX-007`), убедиться,
   что новый оплаченный заказ появляется в секции «Новые» (WS `order.paid`, `SRS-PHT-036`);
   (2) нажать «Принять» → SLA-таймер стартует (`POST /orders/:id/accept`, `SRS-PHT-007`); (3) для
   каждой позиции ввести штрихкод вручную (`POST /orders/:id/items/:itemId/scan { manualEntry:
   true }`, `SRS-PHT-011`); (4) негативная ветка — ввод штрихкода несуществующей позиции →
   `404 ORDER_ITEM_NOT_FOUND`, инлайн-ошибка; (5) негативная ветка — партия с истёкшим сроком
   годности (FEFO-проверка, `SRS-PHT-014`) → `422 EXPIRED_STOCK`, кнопка «Товар недоступен»;
   (6) все позиции решены → «Завершить сборку» с чекбоксом «Пакет опечатан»
   (`POST /orders/:id/complete-picking { sealConfirmed: true }`, `SRS-PHT-024/027`); (7) экран
   показывает 4-значный `handoverOtp` крупным шрифтом; (8) ОТДЕЛЬНЫЙ тест — второй заказ, где
   `pharmacist` НЕ завершает сборку, тестовый бэкенд-`FixedClockAdapter` продвигается на 7+5+1
   минуту → заказ АВТОМАТИЧЕСКИ отменяется с полным рефандом (`SRS-PHT-034`), UI показывает
   модальное «Заказ отменён по таймауту»; (9) негативная ветка — заказ уже принят другим
   сотрудником (эмулируется второй параллельной сессией) → кнопка «Принять» не отображается вовсе
   (`assignedPharmacistName`, `SRS-PHT-061`).
2. `tests/e2e/cuj-4-courier-delivery.e2e-spec.ts`: продолжает заказ из шага 7 сценария CUJ-3'
   (получен `handoverOtp`): (1) как `courier`, `/courier/offers` — полноэкранная карточка оффера с
   обратным отсчётом (`GET /delivery-offers?status=pending`, `SRS-DELIV-012`); (2) принять оффер
   (`POST /delivery-offers/:id/accept`), нажать «Выехал» → «Забрал» (`POST .../depart`,
   `SRS-DELIV-013/019`); (3) убедиться, что `landmark_text` + фото дома + пин на карте показаны
   ОДНОВРЕМЕННО (`REQ-UX-7`, `SRS-DELIV-018`); (4) на месте — экран приёма наличных, ввести
   правильную сумму → сдача считается автоматически (`POST .../record-cash`, `SRS-DELIV-021`);
   (5) негативная ветка — введённая сумма не сходится → `422 CASH_AMOUNT_MISMATCH`, поле
   подсвечено, кнопка «Доставлено» заблокирована до исправления; (6) ввести правильный
   `handoverOtp` из CUJ-3' (`POST .../deliver { otpCode }`, `SRS-DELIV-022`) → заказ переходит в
   `delivered`; (7) негативная ветка — оффер истёк до принятия (эмулируется продвижением
   `FixedClockAdapter`) → `409 OFFER_EXPIRED` при попытке accept; (8) негативная ветка — 5
   неверных попыток ввода OTP вручения → `423 OTP_LOCKED`, экран «Обратитесь в аптеку/поддержку»
   (курьер САМ не может перевыпустить код, `SRS-DELIV-023`).
3. Общий переиспользуемый хелпер `tests/e2e/helpers/place-cash-order.ts` (создаётся ЭТИМ тикетом,
   т.к. первый реальный потребитель, но физически может быть перемещён/переиспользован из
   DTJ-419 при обнаружении дублирования на code review — координация между двумя тикетами по C15).

## Критерии приёмки

1. Given заказ принят фармацевтом, When все позиции сканированы и «Завершить сборку» нажато с
   `sealConfirmed: true`, Then возвращённый `handoverOtp` — ровно 4 цифры, используемый ПОЗЖЕ в
   CUJ-4' сценарии для успешного `deliver`.
2. Given заказ принят, но НЕ завершён, When тестовый `FixedClockAdapter` продвинут на 13 минут
   (7+5+1), Then заказ автоматически переходит в отменённый статус С ПОЛНЫМ рефандом (проверяется
   через API/БД состояние `escrow_ledger`/`payout_schedule`, не только UI-модалку).
3. Given курьер вводит неверную сумму наличных, When «Доставлено» нажато, Then запрос отклонён
   `422 CASH_AMOUNT_MISMATCH`, статус заказа НЕ меняется на `delivered`.
4. Given 5 неверных попыток OTP вручения, When 6-я попытка (даже с верным кодом), Then
   `423 OTP_LOCKED`, курьерский UI НЕ показывает способ самостоятельно перевыпустить код.
5. Given два прогона всего сценария CUJ-3' (включая таймаут-ветку) в CI подряд, When сравниваются
   результаты, Then идентичны по времени срабатывания эскалации/отмены (`TC-NFR-030` —
   детерминированность, не флапающий реальный таймер).

## Риски и подводные камни

Продвижение `FixedClockAdapter` НА БЭКЕНДЕ из E2E-теста требует тестового API/механизма
(например, debug-эндпоинт `POST /api/v1/_test/advance-clock`, по аналогии с `SRS-NFR-033`
debug-эндпоинтом OTP) — этот механизм НЕ специфицирован явно ни одним SRS-документом для SLA-
таймеров конкретно (только общий принцип `SRS-NFR-030` «продвигают часы явным вызовом
`clock.advance(minutes)`») — зафиксировать в PR предложенный debug-эндпоинт как расширение
контракта `SRS-NFR-033`-подобного паттерна, согласовать с владельцем EP-10/EP-12 при реализации.
Сценарий требует трёх одновременных ролевых сессий в одном тесте (`pharmacist`, `courier`, и
опционально второй `pharmacist` для негативной ветки «уже принят») — Playwright
`browser.newContext()` на каждую роль, внимательно следить за отсутствием утечки состояния между
контекстами (каждый контекст — своя cookie/localStorage изоляция).
