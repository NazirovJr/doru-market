## Задача

`PhoneInput` и `OtpInput` — единственный вход в продукт: экран `/login` (`SRS-UX-021`) использует
их первыми, до любой другой функциональности. Ошибка в маске телефона или логике авто-перехода OTP
блокирует буквально весь продукт для всех ролей (5 ролей RBAC входят через один и тот же `/login`).
`Select`/`RadioGroup`/`Checkbox`/`Switch` — стандартные элементы форм чекаута, онбординга аптеки,
настроек профиля, необходимые каждому следующему фронтовому эпику.

## Технический контекст

Наследуют визуальный контракт `Input` из DTJ-404 (высота, состояния, токены). `PhoneInput`
форматирует значение по маске `+992 XX XXX XX XX`, валидация формата на `blur` — согласуется с VO
`PhoneNumber` (`SRS-DOM-069`, backend-контракт), но компонент НЕ импортирует backend-код, только
воспроизводит формат клиентской валидацией для мгновенной обратной связи (финальная валидация —
всегда на сервере). `OtpInput` — 4/6 отдельных ячеек с `inputmode="numeric"`, авто-переход между
ячейками и авто-submit на последней цифре (поведение уже проверено в демо-канвасе
`.dc.html:1307-1319`, дизайн подтверждён как соответствующий спецификации).

## Что сделать

1. `PhoneInput` — фиксированный неизменяемый префикс `+992`, маска `XX XXX XX XX` для оставшихся 9
   цифр, `onChange` отдаёт наружу normalized E.164-подобную строку (`+992XXXXXXXXX`), визуально
   форматированное отображение — внутреннее состояние компонента; `blur`-валидация вызывает
   переданный `onValidate`/показывает `error`-слот `Input` при неполном номере.
2. `OtpInput` — `length: 4 | 6` (4 — вручение курьеру, 6 — логин), состояния `default`/`error`
   (тряска `shakeX` ≤200мс, уважает `useReducedMotion`)/`locked` (все ячейки `disabled`,
   визуально приглушены); `onComplete(code: string)` вызывается автоматически при заполнении
   последней ячейки (авто-submit); `paste`-обработчик распределяет вставленный код по всем ячейкам
   разом (частый паттерн для копирования кода из SMS/Telegram); ячейки — 44×54px (логин) /
   56×64px (курьер) визуально, эффективная область кликабельности — не менее 48×48px каждая
   (`SRS-UX-002`, `assertHitArea`).
3. `Select` — `closed`/`open` состояния, список опций с выделением текущей, полная клавиатурная
   навигация (`ArrowUp`/`ArrowDown`/`Enter`/`Escape`), `aria-expanded`/`role="listbox"`.
4. `RadioGroup` — группа радио-кнопок с общим `name`, `role="radiogroup"`, стрелки перемещают
   выбор внутри группы (нативное поведение `<input type="radio">` переиспользуется, не
   реализуется вручную поверх `<div>`).
5. `Checkbox` — визуальный чекбокс поверх нативного `<input type="checkbox">` (не полностью
   кастомный `<div>` без семантики — сохраняет встроенную клавиатурную/screen-reader поддержку),
   минимум 48×48px эффективной области (визуальный квадрат может быть меньше, `assertHitArea`).
6. `Switch` — тумблер `on`/`off`, `role="switch"` + `aria-checked`, анимация переключения
   уважает `useReducedMotion`.
7. Обновить `packages/ui/src/index.ts`.

## Критерии приёмки

1. Given `<OtpInput length={6} onComplete={fn} />`, When пользователь вводит 6 цифр подряд (Tab
   между ячейками эмулируется автоматически компонентом, не пользователем), Then `fn` вызывается
   РОВНО один раз с полной строкой из 6 символов.
2. Given `<OtpInput length={4} />`, When пользователь вставляет (paste) строку «1234» в первую
   ячейку, Then все 4 ячейки заполняются соответствующими цифрами и `onComplete` вызывается.
3. Given `<OtpInput locked />`, When попытка ввода в любую ячейку, Then значение не меняется,
   `aria-disabled="true"` присутствует на каждой ячейке.
4. Given `<PhoneInput onChange={fn} />`, When пользователь вводит «901234567», Then `fn` получает
   `+992901234567`, визуальное поле показывает «+992 90 123 45 67».
5. Given `<Checkbox>` с видимым размером 20×20px, When `assertHitArea`, Then эффективная область
   ≥48×48px.

## Тест-план

Unit (по файлу на компонент):
- `PhoneInput`: маска применяется корректно посимвольно; `onChange` отдаёт нормализованное
  значение, не форматированное; `blur` с неполным номером показывает `error`.
- `OtpInput`: авто-переход между ячейками при вводе; авто-submit на последней цифре; `paste`
  распределяет код по ячейкам; `Backspace` на пустой ячейке возвращает фокус на предыдущую;
  `locked`-состояние блокирует ввод; `renderWithA11yCheck` — ноль нарушений для всех 3 состояний.
- `Select`: клавиатурная навигация стрелками меняет выделение без открытия второго списка;
  `Escape` закрывает без изменения значения; выбор мышью и клавиатурой дают идентичный результат.
- `RadioGroup`/`Checkbox`/`Switch`: `assertHitArea` ≥48px; ARIA-роли и состояния корректны;
  управляемость (controlled component — значение не меняется без вызова `onChange` потребителем).

## Риски и подводные камни

Авто-submit `OtpInput` на последней цифре — источник частой UX-ошибки «пользователь исправляет
опечатку в середине кода, а форма уже отправилась» — компонент обязан позволять редактирование
ЛЮБОЙ ячейки ПОСЛЕ авто-submit (не блокировать поля сразу после вызова `onComplete`, блокировка —
только через явный проп `locked`, управляемый потребителем после реального ответа сервера, не
самим компонентом). Клавиатура `inputmode="numeric"` на некоторых Android-клавиатурах показывает
дополнительные символы (запятая/точка) — не блокирующая проблема для этого тикета, но фиксировать
в Storybook-заметке как известное ограничение платформы, не решаемое на уровне React-компонента.
- Файл `packages/ui/src/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
