## Задача

`pnpm db:seed` сейчас сидит только каталог (310 препаратов, i18n-оверрайды, флаги, шаблоны
уведомлений). Состав SRS-NFR-031 (сети, аптеки, остатки, пользователи каждой роли, White-Label
тенант, заказы во всех статусах) не реализован ни одним тикетом, а на нём стоят все E2E DTJ-418..423:
в CI после `docker compose up` выполняется только `pnpm db:seed`, других данных нет. Найдено
координатором при подготовке волны E2E (2026-09-27).

## Контракт

Идентификаторы, телефоны и кластер аналогов, которые обязан создать сид, зафиксированы в
`packages/testing-kit/src/seed-contract.ts` (`SEED_TENANTS`, `SEED_CHAINS`, `SEED_PHARMACIES`,
`SEED_USERS`, `SEED_ANALOG_CLUSTER`). Сид импортирует эти константы, а не дублирует их. E2E-спеки
пишутся против этого же файла параллельно. Менять значения контракта — только через координатора
(в отчёте: что и почему).

## Что сделать

1. Расширить `pnpm db:seed` (идемпотентно, повторный запуск не плодит строк и не падает):
   White-Label тенант `sifat` с отличающейся палитрой/названием в `tenant_settings`; ≥3 сети
   разного профиля (1С / Excel / ручной ввод) + сеть White-Label; ≥12 аптек, среди них все из
   контракта и ≥1 соло-аптека; координаты — Душанбе, у разных аптек разные.
2. Остатки: на seed-препараты, разные цены одного и того же препарата в разных аптеках; кластер
   `SEED_ANALOG_CLUSTER` — референт дороже дженериков, все позиции в наличии в `oneCCenter` и
   `excelCenter`. Если в домене аналогов есть признак референта — выставить его.
3. Пользователи — все из `SEED_USERS` (≥2 на роль, pharmacist/pharmacy_admin на каждую сеть).
4. Заказы — по ≥1 во всех статусах `order_status` (включая `return_in_progress`, `refunded`),
   с согласованными платёжными/доставочными записями настолько, чтобы админка и кабинет аптеки
   открывали их без ошибок. Споры/возвраты — по ≥1 образцу нетерминального и каждого терминального статуса.
5. Всё — через существующий механизм сидов (`seed-catalog.run.ts`, раздельные функции
   по образцу `tenants/neutral.seed.ts`), в одной команде `pnpm db:seed`.

## Критерии приёмки

1. Given пустая БД после миграций, When `pnpm db:seed` дважды, Then второй запуск не меняет
   количество строк ни в одной таблице (интеграционный тест).
2. Given засеянная БД, When `POST /auth/otp/request` + verify для каждого телефона `SEED_USERS`,
   Then вход успешен и роль в токене совпадает с контрактом.
3. Given засеянная БД, When `GET /medicines/search` по МНН кластера около `oneCCenter`, Then
   референт и оба дженерика в выдаче, у референта аналоги с `savingsDiram > 0`.
4. Given засеянная БД, When super_admin открывает список заказов в админке, Then представлены все
   статусы `order_status`.

## Тест-план

Интеграционный тест идемпотентности и контракта на своей тестовой БД; живой прогон на E2E-стенде
координатора (API :3300, БД `dorutj_e2e`).
