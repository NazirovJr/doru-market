## Задача

CUJ-2' проверяет самый длинный технически критичный переход R1: гость → OTP-логин → checkout →
`confirmed`-статус наличного заказа (`03-ARCHITECT-DECISIONS.md` D-25 — специально введённый статус,
чтобы не врать о несуществующем эскроу). CUJ-7' — единственный автоматический тест, доказывающий,
что мультитенантность (`SRS-TEN-012`, обязательный по `00-EPICS.md` §«Волны выполнения» блокирующий
тест) реально работает, а не только описана в схеме — оба входят в критерий приёмки R1 №4
(`docs/04-SCOPE-DECISION-PIVOT.md` §3.2).

## Технический контекст

CUJ-2' пошагово — `docs/spec/30-ux-screens-and-flows.md` §4 таблица CUJ-2'. Использует
`getOtpFromMockSms` (DTJ-417) для получения кода без реального SMS, `MockBankProvider` НЕ участвует
(наличный путь не создаёт `payment_transaction_id`, `SRS-ORD-027`). CUJ-7' пошагово — та же секция
§4 таблица CUJ-7' — требует минимум двух резолвящихся тенантов (нейтральный `neutral` + демо
White-Label `sifat.dorutj.local`, `SRS-NFR-031`) и заказов, принадлежащих разным тенантам, для
проверки изоляции.

## Что сделать

1. `tests/e2e/cuj-2-cash-checkout.e2e-spec.ts`: (1) открыть `/cart` с товарами из 2 разных аптек
   (предварительно добавленными в `test.beforeEach` через API), убедиться в баннере «Будет
   оформлено 2 отдельных заказа» (`SRS-ORD-002`); (2) как гость, перейти в `/checkout` → редирект
   на `/login`, ввести тестовый телефон, получить код через `getOtpFromMockSms`, ввести →
   авторизован (`SRS-API-018..023`); (3) на `/checkout` выбрать/добавить адрес перетаскиванием
   пина + текстовый ориентир (`SRS-DOM-072`), выбрать `Наличными курьеру` (единственный активный
   вариант); (4) нажать «Оформить» — `POST /api/v1/orders` с авто-сгенерированным
   `Idempotency-Key`; (5) убедиться, что заказ СИНХРОННО перешёл в `confirmed` (НЕ `paid_escrow` —
   ключевая проверка инварианта D-25, `SRS-ORD-027`), `/orders/:id` показывает «Оплачено, ждёт
   сборки»; (6) негативная ветка №1 — 5 неверных попыток ввода OTP на шаге 2 → `423 OTP_LOCKED`,
   экран блокировки с текстом запроса нового кода (`ux.error.otp_locked`, DTJ-402); (7) негативная
   ветка №2 — двойной быстрый тап по «Оформить» → второй запрос получает
   `409 IDEMPOTENCY_KEY_CONFLICT`, кнопка блокируется мгновенно после первого клика (не создаётся
   два заказа).
2. `tests/e2e/cuj-7-tenant-isolation.e2e-spec.ts`: (1) открыть домен нейтрального тенанта →
   `TenantResolutionMiddleware` резолвит `neutral` (`SRS-API-041`), проверить нейтральную палитру;
   (2) открыть домен демо White-Label тенанта → проверить, что палитра/лого ОТЛИЧАЮТСЯ от
   нейтрального (`GET /tenant/branding` bootstrap, `SRS-TEN-015`); (3) как `customer` тенанта A,
   получить `orderId` СВОЕГО заказа, попытаться `GET /orders/:orderId` через контекст тенанта B
   (другая вкладка/сессия с JWT тенанта B) → `404 NOT_FOUND` (НЕ `403` — не подтверждает
   существование заказа другому тенанту, `SRS-API-046`); (4) запрос с намеренно опечатанным
   `X-Tenant-Slug` (для мобильного/TWA-контекста, если применимо к веб-тесту — альтернативно через
   заголовок напрямую в API-вызове теста) → `404 UNKNOWN_TENANT_SLUG`, НЕ тихий fallback на
   `neutral`; (5) обязательный тест на утечку данных между тенантами (`TC-API-030`, `SRS-TEN-012`)
   — прямой API-запрос списка заказов от имени тенанта A НЕ содержит НИ ОДНОГО заказа тенанта B,
   даже при попытке манипуляции query-параметрами пагинации/фильтров.

## Критерии приёмки

1. Given наличный заказ оформлен, When проверяется `order.status` в БД/через API сразу после
   `POST /orders`, Then значение строго `confirmed`, НЕ `paid_escrow`; связанный `escrow_ledger`
   для этого заказа — пуст (ноль записей) — прямая проверка инварианта D-25 п.4.
2. Given 5 подряд неверных попыток ввода OTP, When 6-я попытка с ПРАВИЛЬНЫМ кодом, Then всё равно
   `423 OTP_LOCKED` (правильный код не спасает после исчерпания попыток).
3. Given двойной клик «Оформить», When оба запроса дошли до сервера, Then создан РОВНО один заказ
   (не два), второй запрос вернул `409`.
4. Given чужой `orderId` тенанта B запрошен в контексте тенанта A, When `GET /orders/:id`, Then
   `404`, не `403` (проверка конкретного кода ответа, не просто «доступ запрещён»).
5. Given список заказов запрошен тенантом A с попыткой манипуляции параметрами пагинации, When
   ответ получен, Then ни один `orderId`, принадлежащий тенанту B, не встречается — проверяется
   исчерпывающе (сравнение полного множества id, не выборочно).

## Риски и подводные камни

Инвариант D-25 (`confirmed` вместо `paid_escrow` для наличных) — относительно свежее архитектурное
решение (пересмотрено 27.08.2026, см. `03-ARCHITECT-DECISIONS.md` часть B2) — при реализации
backend-модуля EP-10 существует риск, что разработчик реализует ПЕРВОНАЧАЛЬНО отклонённый вариант
(синхронный переход в `paid_escrow`) по невнимательности — этот E2E-тест является ГЛАВНОЙ страховкой
от регресса именно этой ошибки, приоритет его написания и поддержания в актуальном состоянии —
высокий. CUJ-7' требует РЕАЛЬНО настроенного второго домена/поддомена для White-Label тенанта в
тестовом окружении (`sifat.dorutj.local`) — конфигурация DNS/hosts-файла тестового раннера — вне
кода этого тикета, координируется с DTJ-412/414 (Docker/CI сеть); альтернатива — резолвинг через
заголовок `X-Tenant-Slug` вместо реального second-level домена в тестовом профиле, если так дешевле
для CI (решение фиксируется в PR).
