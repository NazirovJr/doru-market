## Задача

`docs/spec/31-nfr-security-testing-devops.md` §«Модель угроз (STRIDE)» перечисляет 21 конкретную
угрозу (`SRS-NFR-001..021`) с митигацией, УЖЕ спроектированной в других слоях (Drizzle
параметризованные запросы, Zod-валидация, CSP-заголовки и т.п.) — но спроектированная митигация
без автотеста, доказывающего её работу, является недоказанным утверждением. `pnpm test:security`
— обязательная отдельная стадия CI (`SRS-NFR-028` таблица пирамиды, строка «Безопасности»),
блокирующая релизный тег наравне с E2E.

## Технический контекст

`tests/security/**` — владение EP-19, часть интеграционного уровня тестовой пирамиды (обращается к
реальному поднятому API, не к моку) — переиспользует `docker-compose.test.yml` (DTJ-413), запускается
CI job `security-audit` (DTJ-414). Каждый файл соответствует конкретным `TC-NFR-*` сценариям из
`docs/spec/31-nfr-security-testing-devops.md` §«Тестовые сценарии», которые уже полностью
специфицированы точными Given/When/Then — этот тикет реализует их буквально.

## Что сделать

1. `tests/security/sql-injection.spec.ts` (`TC-NFR-014`, `SRS-NFR-014`) — `GET /medicines/search?
   q=' OR '1'='1` и 5 других OWASP SQLi-паттернов из `tests/security/payloads/sqli.json` (создать
   этот файл с минимум 6 канонических OWASP-пейлоадов) → на КАЖДЫЙ пейлоад: `400`/пустой корректный
   результат, НЕ `500`; количество строк `medicines` не изменилось после прогона (проверка через
   прямой подсчёт в тестовой БД до/после).
2. `tests/security/xss.spec.ts` (`TC-NFR-015`, `SRS-NFR-015`) — seed-медикамент с названием,
   содержащим `<img src=x onerror=alert(1)>` (санитизированное тестовое значение) → рендер
   карточки товара в браузере (Playwright, не чистый API-тест — XSS проверяется в реальном DOM) →
   DOM НЕ содержит выполнившегося `onerror`-обработчика, текст отображается экранированным.
3. `tests/security/ssrf.spec.ts` (`TC-NFR-017`, `SRS-NFR-017`) — попытка передать `imageUrl`
   (внешний URL, например `http://169.254.169.254/` — метаданные облака, классический SSRF-вектор)
   вместо файла в `POST /prescriptions` → `400 VALIDATION_ERROR`/`415
   UNSUPPORTED_MEDIA_TYPE` — эндпоинт принимает ТОЛЬКО `multipart/form-data`, поля для URL не
   существует в Zod-схеме вовсе.
4. `tests/security/rate-limiting.spec.ts` (`TC-NFR-018`, `SRS-NFR-018`) — 101-й запрос
   `GET /medicines/search` за минуту с одного анонимного IP → `429 RATE_LIMITED`, `Retry-After`
   присутствует и `> 0`.
5. `tests/security/file-upload-abuse.spec.ts` (`TC-NFR-020`, `SRS-NFR-020`) — файл `fake.jpg`,
   реально являющийся текстовым файлом (magic bytes не совпадают с JPEG) → `POST /prescriptions` с
   этим файлом → `415 UNSUPPORTED_MEDIA_TYPE`, файл НЕ передан в `PrescriptionOcrProvider`
   (проверяется через spy/mock провайдера — вызов НЕ произошёл).
6. `tests/security/tenant-isolation-idor.spec.ts` (`TC-NFR-005`, `SRS-NFR-005`) — заказ `O1`
   тенанта A существует → `GET /orders/O1` c JWT `tenantId=A`, но через `Host` тенанта B →
   `403 CROSS_TENANT_ACCESS_DENIED` на уровне guard'а, репозиторий тенанта B НЕ вызывается ВООБЩЕ
   (spy на репозиторий подтверждает нулевое количество вызовов — не только код ответа, но и то,
   что запрос отсечён РАНЬШЕ доступа к данным). Дополнительно (`TC-NFR-006`, `SRS-NFR-006`) —
   `PUT /admin/tenants/:id/branding` с `brand_palette["--brand-primary"] = "url(javascript:alert(1))"`
   → `400 VALIDATION_ERROR`, значение НЕ сохранено в БД (переиспользовать
   `tests/security/payloads/branding-injection.json`, синхронизировать набор пейлоадов с unit-
   тестами `validateBrandingPayload` из DTJ-401 — один и тот же список пейлоадов, не два
   независимых источника истины, C15).
7. `tests/security/otp-bruteforce.spec.ts` (`TC-NFR-011`/`TC-NFR-012`, `SRS-NFR-011`/`SRS-NFR-012`) —
   логин: `otpRequestId=X`, 5 неверных попыток verify исчерпаны → 6-я попытка с ПРАВИЛЬНЫМ кодом →
   `423 OTP_LOCKED`; вручение курьером: `delivery_assignment` в `picked_up_from_pharmacy`, 5
   неверных попыток `markDelivered(otp)` → 6-я попытка с правильным OTP →
   `OtpAttemptsExceededError`/`423`, требуется `ReissueHandoverOtpUseCase`.
8. `tests/security/log-pii-leakage.spec.ts` (`TC-NFR-010`, `SRS-NFR-010`) — `POST
   /auth/otp/verify` с `phone`/`code` в теле → структурный лог этого запроса захвачен (через
   тестовый лог-коллектор/перехват stdout контейнера) → поле `phone` замаскировано
   `+992******NN`; поле `code`/`otp.code` ОТСУТСТВУЕТ ЦЕЛИКОМ (не пустая строка — ключ отсутствует
   в JSON-объекте лога).
9. Job `security-audit` (уже создана DTJ-414) — этот тикет добавляет фактическое содержимое
   `pnpm test:security`, вызываемое той job; `pnpm audit --audit-level=high` — 0 находок без
   явного `pnpm audit --ignore` с обоснованием в PR (сама команда `pnpm audit` — встроенная,
   ничего не пишется этим тикетом, только гарантируется её вызов и договорённость о политике 0
   находок).

## Критерии приёмки

1. Given каждый из 6 SQLi-пейлоадов из `sqli.json`, When отправлен в `GET /medicines/search`,
   Then НИ ОДИН не возвращает `500`, количество строк `medicines` идентично до/после ВСЕХ 6
   запросов.
2. Given XSS-пейлоад в названии медикамента, When карточка товара отрендерена в реальном браузере,
   Then `page.evaluate` подтверждает отсутствие выполненного `alert`/скрипта (не просто текстовое
   сравнение HTML — реальная проверка выполнения в DOM).
3. Given cross-tenant запрос заказа, When выполнен, Then `403`, И спай на репозиторий тенанта B
   зафиксировал НОЛЬ вызовов метода получения заказа.
4. Given 101 запрос поиска за минуту с одного IP, When 101-й отправлен, Then `429` с
   `Retry-After > 0`; предыдущие 100 — не блокированы (проверка точной границы, не «примерно
   сотня»).
5. Given структурный лог запроса верификации OTP захвачен, When JSON-запись парсится, Then ключ
   `code`/`otp.code` отсутствует в объекте (`expect(logEntry).not.toHaveProperty('code')`,
   не `expect(logEntry.code).toBe('')`).

## Тест-план

Все файлы из `files_owned` — интеграционный уровень (`apps/api/test/integration`-подобный,
физически расположены в `tests/security/`, часть стадии CI `security-audit`), Given/When/Then
списаны буквально из таблицы `TC-NFR-*` (см. «Что сделать» выше — каждый пункт уже содержит
конкретные шаги). Дополнительно — сверка, что каждый файл покрывает ОБЕ ветки, где применимо
(позитивная — легитимный запрос проходит, негативная — атакующий пейлоад отклонён), не только
негативную.

## Риски и подводные камни

Все 8 файлов требуют РЕАЛЬНО работающих эндпоинтов (`/medicines/search`, `/prescriptions`,
`/orders`, `/auth/otp/verify`, `/admin/tenants/:id/branding`, `/delivery-assignments/:id/deliver`)
— физически проверяемы только после соответствующих backend-эпиков (EP-01, EP-06, EP-10, EP-13,
EP-15). Тикет пишется по контракту уже полностью специфицированных `TC-NFR-*` сценариев —
приоритетная задача при первой реальной интеграции — не ослаблять пороги (например, из
`423 OTP_LOCKED` в `429` «для простоты») при обнаружении расхождения с реализацией: расхождение
эскалируется как баг backend-модуля, а не как повод переписать security-тест под фактическое
(возможно ошибочное) поведение. Захват структурного лога (`log-pii-leakage.spec.ts`) требует
доступа к stdout контейнера `api` из теста — механизм захвата (Docker logs API/файловый sink в
тестовом профиле) согласовать при реализации, не специфицирован SRS-документом на уровне
конкретного инструмента.
