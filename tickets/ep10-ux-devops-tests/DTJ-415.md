## Задача

`docs/02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1 формулирует это явно как обязательный тикет:
«ловушка, которая перестала ловить, молчит об этом: ловушку нужно проверять ловушкой». Архитектор
лично проверил конфигурацию `dependency-cruiser`/ESLint на живых нарушениях 27.08.2026 (задокументировано
в том же разделе) — но это была разовая ручная проверка при первоначальной настройке. Без
постоянного автоматического теста ничто не помешает будущему PR (например, при обновлении версии
ESLint/dependency-cruiser или рефакторинге конфига) молча ослабить правило — CI останется зелёным,
хотя граница архитектуры перестала охраняться.

## Технический контекст

`tests/arch/**` — единоличное владение EP-19. Каждая фикстура — МИНИМАЛЬНЫЙ, синтетический
TypeScript-файл (не настоящий бизнес-код), намеренно нарушающий ОДНО конкретное правило из
`.dependency-cruiser.cjs`/`eslint.config.mjs` (оба файла уже существуют в репозитории — владелец
EP-19, этот тикет их ПОТРЕБЛЯЕТ, не создаёт заново, `00-EPICS.md` §«Пересекающееся владение» п.5).
Тест `run-fixture-check.spec.ts` программно запускает `arch:check`/`lint` ПРОТИВ каждой фикстуры
(например, через дочерний процесс `execa`/`child_process` с временно подключённым отдельным
`tsconfig`/`.dependency-cruiser.cjs`-таргетом на папку фикстур) и утверждает, что каждая
завершается с ненулевым кодом возврата и ожидаемым текстом сообщения.

## Что сделать

1. `tests/arch/fixtures/domain-imports-drizzle/order.entity.ts` — файл в псевдо-`domain/`-пути,
   импортирующий `drizzle-orm` (воспроизводит нарушение из таблицы `02-CLEAN-ARCHITECTURE-AND-CODE.md`
   §6.1 «`domain/` импортирует `drizzle-orm`»).
2. `tests/arch/fixtures/domain-uses-date-now/otp.entity.ts` — вызов `Date.now()` внутри
   псевдо-`domain/`-файла (нарушение «Домен чист... время... через порты», §2 п.6).
3. `tests/arch/fixtures/magic-number/pricing.ts` — магическое число (например, буквальное `7919`,
   как в примере архитектора) вне именованной константы (нарушение C6).
4. `tests/arch/fixtures/application-imports-infrastructure/place-order.use-case.ts` —
   `application/`-файл, импортирующий что-то из `infrastructure/` того же псевдо-модуля (нарушение
   §1.1 таблицы).
5. `tests/arch/fixtures/cross-module-deep-import/payments-importing-orders-domain.ts` — глубокий
   импорт `modules/orders/domain/order.entity` из псевдо-`modules/payments` в обход фасада
   (нарушение §1.2, dependency-cruiser правило `no-cross-module-deep-import`).
6. `tests/arch/fixtures/frontend-horizontal-feature-import/checkout-importing-cart-internals.tsx` —
   фронтовый `features/checkout/` файл, импортирующий внутренний (не-публичный) модуль
   `features/cart/model/internal-helper` напрямую (нарушение §5 «горизонтальные импорты
   feature-a → feature-b запрещены»).
7. `tests/arch/run-fixture-check.spec.ts` (Vitest) — для каждой фикстуры: запускает
   `pnpm eslint <путь-фикстуры>` и/или `pnpm arch:check` с таргетом на папку фикстур (в зависимости
   от того, какой инструмент по конфигу должен поймать конкретное нарушение — часть ловится
   ESLint, часть dependency-cruiser, некоторые — обоими, сверяется с таблицей §6.1 документа) →
   `expect(exitCode).not.toBe(0)` → `expect(stderr/stdout).toContain(<ожидаемая часть сообщения
   из таблицы §6.1, например "Слой domain обязан быть чистым">)`.
8. `tests/arch/README.md` — короткая инструкция: назначение папки (ловушка для ловушки, не
   пример для копирования), как добавить новую фикстуру при появлении нового архитектурного
   правила, явное предупреждение «эти файлы ДОЛЖНЫ падать при `arch:check`/`lint` — если они
   вдруг проходят, конфигурация сломана, не удаляйте фикстуру, чините конфиг».
9. Убедиться, что сами файлы фикстур ИСКЛЮЧЕНЫ из обычного `pnpm verify`/сборки продукта (не
   попадают в `tsconfig.json`-проекты продукта, не собираются как часть `apps/*`) — они существуют
   ТОЛЬКО для потребления этим специальным тестом, который сам их явно таргетирует.

## Критерии приёмки

1. Given `tests/arch/fixtures/domain-imports-drizzle/order.entity.ts`, When
   `run-fixture-check.spec.ts` запускает `arch:check`/`lint` против этого файла, Then команда
   завершается ненулевым кодом и сообщение содержит указание на нарушение чистоты domain-слоя.
2. Given ВСЕ 6 фикстур, When тест-раннер прогоняет весь `run-fixture-check.spec.ts`, Then КАЖДАЯ
   фикстура ловится ХОТЯ БЫ ОДНИМ из двух инструментов (ESLint/dependency-cruiser) — тест
   явно перечисляет, каким именно инструментом ожидается поймать каждую фикстуру, не полагается
   на «один из двух поймает, неважно какой».
3. Given намеренно закомментированное правило `no-restricted-imports` в `eslint.config.mjs`
   (временная локальная проверка при ревью тикета, НЕ коммитится), When тест на фикстуру
   `domain-imports-drizzle` перезапускается, Then тест `run-fixture-check.spec.ts` КРАСНЕЕТ
   (подтверждает, что тест реально зависит от рабочего правила, а не проходит «сам по себе»
   независимо от конфига — финальная ручная проверка при код-ревью этого PR, не автоматизируется
   постоянно).
4. Given фикстуры не подключены к `tsconfig.json` продукта, When `pnpm --filter api build`, Then
   сборка НЕ падает из-за содержимого `tests/arch/fixtures/**` (фикстуры физически изолированы от
   продуктовой сборки).

## Тест-план

Единственный тестовый файл этого тикета — сам `run-fixture-check.spec.ts` (Vitest, часть
`test:unit` или отдельная команда `test:arch`, включаемая в `pnpm verify` наравне с `arch:check`,
согласовать точное включение с конфигом `turbo.json`/`package.json` — решение фиксируется в PR).
Кейсы — по одному на каждую фикстуру (перечислены в разделе «Что сделать» п.7) плюс один общий
smoke-кейс «все фикстуры вместе не проходят проверку одним batch-вызовом» (защита от того, что
инструмент молча пропускает файлы вне явно указанного пути при batch-запуске).

## Риски и подводные камни

SRS-документы (`docs/spec/*.md`) НЕ содержат отдельного SRS-* идентификатора для этого требования —
источник требования дословно `docs/02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1 (документ уровня 3 в
иерархии тикета, не входит в нумерованный корпус SRS §6 «`docs/spec/*.md`»), поэтому `srs_refs`
этого тикета осознанно пустой — это не пропуск поиска, а факт отсутствия SRS-ID для внутреннего
инженерного стандарта. Namespace-конфликт: если `.dependency-cruiser.cjs`/`eslint.config.mjs`
(уже существующие в репозитории на момент этого тикета) настроены с `exclude`-паттерном,
случайно захватывающим `tests/arch/fixtures/**` целиком (что логично для обычного кода, но
контрпродуктивно именно здесь, т.к. фикстуры ДОЛЖНЫ проверяться) — необходимо явно убедиться, что
эти конкретные фикстуры НЕ исключены из зоны действия правил, только из зоны обычной сборки/тестов
продукта — это два разных списка исключений, их легко перепутать при настройке.
