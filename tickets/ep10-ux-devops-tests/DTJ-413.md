## Задача

`test:integration` и `test:e2e` не могут переиспользовать dev/staging compose (DTJ-412) напрямую —
им нужна БЫСТРАЯ, ИЗОЛИРОВАННАЯ, эфемерная база без Nginx/certbot, с данными, не переживающими
рестарт. Без отдельного файла каждый прогон тестов рискует зацепить состояние, оставшееся от
предыдущего прогона (нарушение детерминированности, `SRS-NFR-030` п.5) или конфликтовать портами
с локальным dev-стеком разработчика, работающим параллельно.

## Технический контекст

`infra/docker/docker-compose.test.yml` — оверлей, ПОДКЛЮЧАЕМЫЙ поверх базового
`docker-compose.yml` (`docker compose -f docker-compose.yml -f docker-compose.test.yml up -d`,
как показано в CI-пайплайне `SRS-NFR-057` стадия `e2e`), а не отдельный самостоятельный стек — так
образы/сети переиспользуются, оверлей меняет только `postgres`/`redis`/`minio` (никакого `nginx`/
`certbot`) на `tmpfs`-volumes и убирает публикацию портов на фиксированные значения (случайные
эфемерные порты Docker, чтобы параллельные CI-джобы не конфликтовали, дополняется `TC-NFR-066`
требованием изоляции параллельных прогонов).

## Что сделать

1. `infra/docker/docker-compose.test.yml` — переопределения для `postgres`/`redis`/`minio`:
   `volumes` заменяются на `tmpfs: /var/lib/postgresql/data` (и аналогично для Redis/MinIO data-
   директорий) — данные физически не пишутся на диск хоста, максимальная скорость, обнуляются при
   `down`.
2. Явно НЕ включать `nginx`/`certbot`/`seed` (профиль `dev`) сервисы в этот оверлей — тесты идут
   напрямую к `api`/`worker` по внутреннему порту (без TLS-терминации, не нужна для локальных/CI
   прогонов).
3. Добавить сервисный алиас-документацию (комментарий в файле) с точной командой поднятия/сноса:
   `docker compose -f infra/docker/docker-compose.yml -f infra/docker/docker-compose.test.yml up -d`
   / `... down -v` — команда переиспользуется буквально в CI-пайплайне (DTJ-414) и локальной
   инструкции для разработчиков (`README` — не создаётся этим тикетом отдельно, комментарий в
   самом compose-файле достаточен).
4. Убедиться, что healthcheck-интервалы ускорены относительно dev-профиля (`interval: 2s` вместо
   `5s` — тестовый прогон не должен ждать дольше необходимого на каждом CI-старте).

## Критерии приёмки

1. Given `docker compose -f docker-compose.yml -f docker-compose.test.yml up -d`, When стек
   поднят, Then `postgres`/`redis`/`minio` используют `tmpfs`, `nginx`/`certbot` НЕ запущены
   (отсутствуют в `docker compose ps`).
2. Given стек поднят и в БД записаны тестовые данные, When `docker compose -f docker-compose.yml -f
   docker-compose.test.yml down -v` и повторный `up -d`, Then БД пуста (данные предыдущего прогона
   не пережили пересоздание — `tmpfs` подтверждён).
3. Given два параллельных вызова поднятия этого оверлея с РАЗНЫМИ project-именами Docker Compose
   (`-p test-run-1`/`-p test-run-2`, тот же паттерн, что использует GitHub Actions с изолированными
   `services:` в `TC-NFR-066`), When оба стека работают одновременно, Then порты не конфликтуют
   (эфемерные/динамические порты, не фиксированные `5432:5432`).

## Тест-план

Инфраструктурный тикет без юнит-тестов. Проверка — ручная (критерии приёмки выше выполняются
локально разработчиком при ревью) плюс постоянная эксплуатационная проверка каждым последующим
запуском `test:integration`/`test:e2e` в CI (DTJ-414) — если этот compose-файл сломан, все
последующие тестовые стадии CI становятся красными, что само по себе служит регресс-сигналом.

## Риски и подводные камни

`tmpfs` для Postgres на некоторых CI-раннерах с ограниченным RAM может исчерпать память при
большом объёме тестовых данных (маловероятно для R1 масштаба — seed ≥300 позиций каталога плюс
тестовые заказы, но стоит держать в уме при росте фикстур в будущих релизах) — не блокирует этот
тикет, фиксируется как известное ограничение подхода. Если CI-раннер (GitHub Actions `services:`)
использует СВОЙ механизм подъёма сервисов вместо этого compose-файла напрямую (как показано в
`SRS-NFR-057` для стадии `integration-tests` — там Postgres/Redis поднимаются через `services:`
GitHub Actions, а НЕ через `docker-compose.test.yml`) — этот compose-файл используется ТОЛЬКО
стадией `e2e` пайплайна (полный docker-стек), не стадией `integration-tests` (которая идёт без
Docker Compose вовсе, см. DTJ-414) — важно не спутать два разных механизма подъёма БД для двух
разных уровней тестовой пирамиды.
