## Задача

`docs/00-PROJECT-CHARTER.md` §7 и `docs/spec/30-ux-screens-and-flows.md` §8 (`SRS-UX-036`)
фиксируют жёсткий бюджет: ≤250KB gzip для первого экрана `apps/web` (`/`, главный экран поиска —
самый частый вход, включая гостя). Целевая аудитория — дешёвые Android-устройства на нестабильном
2G/3G (`research §7.2`) — превышение бюджета не «немного медленнее», а буквально решает, открывается
ли продукт вообще у значимой доли целевых пользователей. Без автоматического гейта бюджет
неизбежно «расползётся» по мере добавления фич каждым фронтовым эпиком — один PR редко добавляет
заметный вес, но сумма из 15+ эпиков легко превышает порог незаметно для каждого отдельного автора.

## Технический контекст

`SRS-NFR-036` строка 7 фиксирует измерение: `pnpm build` + анализ бандла (`rollup-plugin-visualizer`/
`vite-bundle-visualizer`), CI-шаг `pnpm size-check`, порог — блокирующий именно для `pnpm verify`.
Измеряется ТОЛЬКО код, необходимый ДО интерактивности главного маршрута `/` (`SRS-UX-036`):
HTML + критический CSS + JS, ИСКЛЮЧАЯ шрифты (Google Fonts, кэшируются CDN отдельно) и изображения.
Код-сплиттинг по границам `features/*` (`SRS-UX-037`) — предпосылка того, что измерение вообще
имеет смысл: без правильного роутового `lazy()`-сплиттинга весь код приложения (включая
`/admin/*`/`/courier/*`, которые НИКОГДА не должны попадать в бандл гостевого главного экрана)
оказался бы в одном неделимом чанке.

## Что сделать

1. `scripts/size-check.ts` — читает вывод сборки `apps/web` (`vite build` с `build.rollupOptions`
   или встроенным `vite-bundle-visualizer`/эквивалентным JSON-репортом статистики чанков),
   вычисляет суммарный gzip-размер чанков, реально загружаемых ДО интерактивности маршрута `/`
   (вечнозелёный `app`/`shared`/`entities`-чанк + чанк самого маршрута `/`, БЕЗ чанков
   `checkout`/`prescription-upload`/`courier`/`admin` и т.п., загружаемых лениво) — сравнивает с
   порогом `250 * 1024` байт (константа `MAX_FIRST_SCREEN_BUNDLE_BYTES`, именованная, не
   магическое число — C6), ненулевой код выхода при превышении с читаемым отчётом (какие чанки
   учтены, их размер, на сколько байт превышен порог).
2. Скрипт ИСКЛЮЧАЕТ из подсчёта: файлы шрифтов (`.woff2`/`.woff`), изображения
   (`.png`/`.jpg`/`.webp`/`.svg`, кроме инлайн-SVG внутри JS-бандла, которые технически часть JS-
   веса и ДОЛЖНЫ считаться) — фильтрация по расширению файла в манифесте сборки.
3. Добавить npm-скрипт `size-check` в `apps/web/package.json` (файл появится с EP-06/scaffolding
   `apps/web` из EP-01 — на момент этого тикета создаётся контракт имени команды, реальное
   подключение — точечная правка при появлении `apps/web`) и корневой `turbo.json`-таргет,
   агрегирующий `size-check` по фронтовым приложениям, где применимо (в первую очередь `apps/web`
   — единственное приложение с явным бюджетом гостевого первого экрана; `apps/admin`/`apps/pharmacy`/
   `apps/courier` — авторизованные, не публичный вход, бюджет на них Charter'ом не
   специфицирован — этот тикет НЕ придумывает для них порог самостоятельно).
4. `.github/workflows/ci.yml` (точечная правка через Edit) — добавить `pnpm size-check` внутрь
   job `typecheck-lint-arch` ИЛИ отдельным шагом `build`-job ПОСЛЕ сборки `apps/web` (решение —
   после сборки логичнее, т.к. требует реального `dist/`-манифеста, а не может выполняться на
   статическом гейте до сборки — зафиксировать выбранное место в PR).

## Критерии приёмки

1. Given собранный `apps/web` с суммарным весом критических чанков 240KB gzip, When
   `pnpm size-check`, Then код выхода `0`, отчёт показывает «240KB / 250KB, запас 10KB».
2. Given суммарный вес критических чанков 260KB gzip (превышение), When `pnpm size-check`, Then
   ненулевой код выхода, отчёт явно указывает превышение на 10KB и перечисляет крупнейшие чанки,
   вошедшие в подсчёт.
3. Given маршрут `/admin/branding` (роль-специфичный, не гостевой) весит 500KB отдельным ленивым
   чанком, When `pnpm size-check` для главного экрана `/`, Then этот чанк НЕ учитывается в
   подсчёте бюджета (проверка правильной фильтрации по границе маршрута, не по общему весу всего
   приложения).
4. Given манифест сборки содержит файл шрифта `.woff2` объёмом 40KB, When `pnpm size-check`, Then
   этот файл исключён из подсчёта (бюджет применяется только к HTML/CSS/JS).

## Тест-план

Unit (`scripts/size-check.spec.ts`, Vitest):
- `sums only first-screen critical chunks, excludes lazily-loaded role-specific route chunks`
- `excludes font and image assets from the byte count`
- `passes when total is under threshold, with correct remaining margin reported`
- `fails with non-zero exit code and readable overage report when threshold exceeded`
- `MAX_FIRST_SCREEN_BUNDLE_BYTES is a named constant, not a magic literal inline in the comparison`
  (структурная проверка/линт-самопроверка соответствия C6, не обязательно рантайм-тест — можно
  проверить статическим анализом исходника скрипта в этом же тесте).

Тестовые данные — синтетический манифест сборки (JSON-фикстура `tests/fixtures/build-manifest-
sample.json`, создаётся этим тикетом при необходимости в `scripts/`-локальной папке фикстур или
переиспользует `tests/fixtures/`, если больше нигде не занято похожим именем — координировать при
реализации), не требует реальной сборки `apps/web` для unit-уровня.

## Риски и подводные камни

Скрипт физически не может быть окончательно проверен на РЕАЛЬНОМ бандле `apps/web` до появления
самого приложения (EP-01 scaffolding + EP-06 первый реальный маршрут поиска) — на этом тикете
реализуется логика анализа манифеста ПО КОНТРАКТУ формата вывода `vite build`/`vite-bundle-
visualizer`, точная структура JSON-манифеста уточняется при первой интеграции (возможна точечная
правка парсера под фактический формат выбранного инструмента визуализации бандла, без изменения
архитектуры скрипта). Разграничение «критический путь `/`» vs «ленивые роуты» технически опирается
на корректность код-сплиттинга, реализуемого КАЖДЫМ фронтовым эпиком по `SRS-UX-037` — если
конкретный эпик забудет вынести свою фичу в отдельный `lazy()`-чанк, `size-check` поймает
превышение бюджета КАК СЛЕДСТВИЕ (правильное поведение — гейт должен падать в этом случае), но
диагностика первопричины («чья фича раздула бандл») — ручная работа ревьюера по отчёту чанков, не
автоматизируется этим скриптом дальше базового перечисления крупнейших чанков.
