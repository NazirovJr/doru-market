## Задача

`docs/spec/31-nfr-security-testing-devops.md` §«Реестр переменных окружения» перечисляет ~70
переменных по 8 категориям (`SRS-NFR-053`) — без автоматической сверки этот реестр гарантированно
разойдётся с реальным кодом со временем: разработчик добавит новую ENV-переменную в код, забудет
про `.env.example`, и следующий разработчик, разворачивающий окружение с нуля, получит непонятный
крэш вместо явной ошибки конфигурации. Это прямое противоречие критерию приёмки R1 №1
(`docs/04-SCOPE-DECISION-PIVOT.md`: «`pnpm install && pnpm db:migrate && pnpm db:seed && pnpm dev`
работает без Docker» — недостижимо без полного и актуального `.env.example`).

## Технический контекст

`SRS-NFR-054` требует CI-шаг `pnpm env:check`, сравнивающий: (а) множество ключей, читаемых кодом
через `@nestjs/config`-схему Zod (`apps/api`), с (б) множеством имён в `.env.example` — расхождение
в ЛЮБУЮ сторону (переменная в примере, но не читаемая кодом, ИЛИ переменная, которую код читает, но
её нет в примере/схеме) — красный CI. `scripts/env-check.ts` — Node-скрипт корня монорепозитория
(не привязан к конкретному `apps/*`, т.к. читает Zod-схему конфигурации `apps/api`, которая на
момент этого тикета ещё не существует — см. «Риски»).

## Что сделать

1. `.env.example` — создать/дополнить (файл может частично существовать после EP-01 к моменту
   реализации — редактировать точечно через Edit, не пересоздавать) начальным содержимым по
   категориям из `SRS-NFR-053`: «Инфраструктура и рантайм», «Аутентификация и токены», «Provider
   Pattern», «Хранилище и шифрование», «Транспорт и безопасность», «WebSocket», «Тенантность/бренд»,
   «Наблюдаемость», «On-premise (R3)» — каждая переменная с плейсхолдер-значением `CHANGE_ME` для
   секретов ИЛИ dev-безопасным дефолтом для несекретных (например, `PORT=3000`), группировка —
   комментариями-разделителями по названию категории (совпадающими с заголовками таблиц
   `SRS-NFR-053` дословно, для трассируемости).
2. `scripts/env-check.ts` — читает (а) Zod-схему конфигурации приложения (путь к схеме — контракт,
   согласуется с EP-01: ожидаемое расположение `apps/api/src/config/env.schema.ts`, экспортирующее
   объект схемы с именами ключей); (б) парсит `.env.example` построчно (имена переменных до `=`,
   игнорируя комментарии/пустые строки) → строит два множества имён → сравнивает: печатает
   diff (что есть в схеме, но нет в примере / что есть в примере, но не читается схемой) →
   ненулевой код выхода при любом расхождении.
3. Добавить npm-скрипт `env:check` в корневой `package.json` (точечная правка через Edit —
   `package.json` уже существует), вызывающий `tsx scripts/env-check.ts`.
4. `.github/workflows/ci.yml` (уже создан DTJ-414 — точечная правка через Edit, добавить один шаг):
   добавить `run: pnpm env:check` внутрь job `typecheck-lint-arch` (быстрая статическая проверка,
   не требует БД — логично разместить рядом с `typecheck`/`lint`/`arch:check`).

## Критерии приёмки

1. Given `.env.example` содержит переменную `FOO_BAR`, которую НИ ОДИН модуль конфигурации не
   читает через Zod-схему, When `pnpm env:check`, Then ненулевой код выхода, сообщение указывает
   `FOO_BAR` как «лишнюю» переменную примера.
2. Given Zod-схема конфигурации объявляет переменную `BAZ_QUX`, отсутствующую в `.env.example`,
   When `pnpm env:check`, Then ненулевой код выхода, сообщение указывает `BAZ_QUX` как
   «отсутствующую в примере».
3. Given `.env.example` и Zod-схема полностью синхронны (тестовая фикстура с искусственно
   совпадающими множествами), When `pnpm env:check`, Then код выхода `0`, вывод подтверждает
   полное соответствие.
4. Given реальный `.env.example`, созданный этим тикетом, When `pnpm env:check` запускается ДО
   появления реальной Zod-схемы `apps/api` (переходный период до EP-01), Then скрипт явно
   сообщает «схема конфигурации не найдена по ожидаемому пути» (понятная ошибка, не падение с
   трудночитаемым stack trace) — не выдаёт ложноположительный «всё синхронно».

## Тест-план

Unit (`scripts/env-check.spec.ts`, Vitest, в корневом `tsconfig`/`vitest.config.ts` — уточнить
расположение теста для скриптов, не привязанных к конкретному workspace-пакету, при реализации):
- `parses .env.example key names correctly, ignoring comments and blank lines`
- `detects variable present in schema but missing from .env.example`
- `detects variable present in .env.example but not read by schema`
- `returns success (exit 0) when both sets match exactly`
- `handles missing schema file with a clear, actionable error message, not a stack trace`

## Риски и подводные камни

Главный риск — путь к Zod-схеме конфигурации `apps/api` НЕ существует на момент реализации этого
тикета (EP-01 — волна 1, может выполняться параллельно с EP-19, порядок готовности не гарантирован)
— скрипт обязан явно и понятно сообщать об отсутствии схемы (критерий приёмки 4), а не тихо
считать проверку пройденной или падать необъяснимо. Формат чтения Zod-схемы (статический анализ
AST vs рантайм-импорт и интроспекция объекта схемы) — выбор реализации за разработчиком; рантайм-
импорт (`import { envSchema } from '...'; Object.keys(envSchema.shape)`) — вероятно проще и
надёжнее статического AST-парсинга, но требует, чтобы схема была валидным ES-модулем без побочных
эффектов при импорте (чтение реального `process.env` при импорте схемы сломает скрипт в CI-
окружении без части переменных) — зафиксировать это требование к структуре схемы как согласованный
контракт с EP-01 в PR.
- Файл `.github/workflows/ci.yml` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- D-27: одна подволна с `DTJ-427` (оба дописывают новый job в `ci.yml`) — этот тикет первый,
  `DTJ-427` получил явный `depends_on: DTJ-426`, чтобы не редактировать файл параллельно.
