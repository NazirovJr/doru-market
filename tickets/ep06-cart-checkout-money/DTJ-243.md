## Задача

Банк — внешняя система, которую платформа не контролирует: вебхуки могут прийти не в том порядке,
дважды, для несуществующего заказа, или для заказа, который клиент/система уже успели отменить.
Каждый из этих случаев, обработанный наивно, либо создаёт спекулятивную запись леджера без
основания, либо реанимирует отменённый заказ, либо теряет деньги клиента без следа. Этот тикет
закрывает все документированные пограничные случаи явными, протестированными ветками поверх
`HandlePaymentWebhookUseCase` (DTJ-242, тот же файл — правка существующего кода того же тикета-
владельца, не новый файл).

## Технический контекст

Расширяет `handle-payment-webhook.use-case.ts` (DTJ-242) дополнительными ветками ПОСЛЕ шага
идемпотентности (успешно вставлена новая строка `payment_operations`), ДО коммита: определить тип
события и применить соответствующую политику. `LatePaymentRefundService` — выделенный сервис для
самого сложного случая (SRS-PAY-027), не встроенный inline в use case (C1 — предел длины функции).

## Что сделать

1. **Неизвестный платёж (SRS-PAY-028)**: Given `providerRef` не соответствует ни одной строке
   `payment_operations` (ни от `createInvoice`, ни от `refund`), Then: НЕ создаёт `escrow_ledger`/
   `payout_schedule`, НЕ меняет статус ни одного заказа; `audit_log(category='payment_override',
   metadata={providerRef, bankEventId, rawPayloadHash})`; `support_tickets(channel='system_auto',
   category='payment_issue', is_escrow_blocking=false, description='unknown providerRef in
   webhook')`; возвращает `200 OK` (не `404`/`400` — банк не должен ретраить бесконечно).
2. **Soft-deleted заказ (SRS-PAY-040)**: Given `orders.deleted_at IS NOT NULL` для `order_id`,
   Then трактуется КАК неизвестный платёж (та же ветка п.1) — soft-deleted заказ не валидная цель.
3. **Out-of-order refund (SRS-PAY-025)**: Given `type='refund_confirmed'`/`'refund_failed'`,
   Then искать `payment_operations(operation_type IN ('refund','partial_refund'),
   provider_ref=:providerRef, status='pending')` — Given строка НЕ найдена → трактуется как
   неизвестный платёж (п.1), НЕ создаёт спекулятивную запись ledger.
4. **Поздняя оплата после автоотмены (SRS-PAY-027)**: Given `type='payment_confirmed'` для заказа
   в `status='cancelled'` (SRS-DOM-102: запрещён любой переход `→ paid_escrow`, кроме как из
   `pending_payment`, `cancelled` терминален), Then `LatePaymentRefundService.handle(orderId,
   amountDiram, providerRef)` — В ОДНОЙ транзакции: `EscrowLedger.append(hold_created)` +
   НЕМЕДЛЕННО `EscrowLedger.append(refunded_to_customer)` (обе записи — аудиторский след, что
   деньги прошли через контур, а не «потерялись», НЕ вызывает `order.markPaidEscrow` — заказ
   ОСТАЁТСЯ `cancelled`), `PaymentProvider.refund(providerRef, idempotencyKey)` реальный вызов
   рефанда провайдеру, `orders.cancel_reason` для аудита уже проставлен ранее как
   `late_payment_after_cancellation` (используется DTJ-253/254, здесь только чтение),
   `support_tickets(category='payment_issue', is_escrow_blocking=false)`.
5. Регистрация карты типа события → обработчика (не длинная цепочка `if/else` — C4 глубина
   вложенности ≤3, использовать паттерн диспетчеризации по `type`).

## Критерии приёмки

1. **Given** вебхук ссылается на `providerRef`, никогда не созданный `createInvoice()`, **When**
   `POST /api/v1/payments/webhook`, **Then** `200 OK`, `support_tickets(category='payment_issue')`
   создан, ни один заказ не изменён.
2. **Given** `orders.deleted_at IS NOT NULL`, **When** вебхук для этого заказа, **Then**
   обработано как неизвестный платёж (тот же путь п.1).
3. **Given** `refund_confirmed`-вебхук без соответствующей `pending`-строки `payment_operations`,
   **When** обработка, **Then** трактуется как неизвестный платёж, `escrow_ledger` не изменён.
4. **Given** заказ уже `cancelled` (авто-отмена по таймауту), банковский `payment_confirmed`
   приходит с опозданием, **When** `POST /api/v1/payments/webhook`, **Then** заказ ОСТАЁТСЯ
   `cancelled` (не реанимирован), создана пара `hold_created`+`refunded_to_customer`,
   `PaymentProvider.refund` вызван ровно один раз, `support_ticket` создан.

## Риски и подводные камни

- **`LatePaymentRefundService` создаёт запись `hold_created` для заказа, который уже `cancelled`
  — это НАМЕРЕННОЕ отклонение от обычного правила «hold_created только для paid_escrow-пути»,
  сделанное ради аудиторского следа.** Явно задокументировать в JSDoc, чтобы `EscrowInvariantSpec`
  (DTJ-256) корректно интерпретировал этот случай — заказ `cancelled` с непустым `escrow_ledger`
  НЕ должен считаться нарушением инварианта SRS-DOM-180 (тот инвариант — про `status='paid_escrow'
  ⟺ ledger непуст`, а не про «cancelled ⟹ ledger пуст», это РАЗНЫЕ утверждения — свериться при
  реализации DTJ-256, не допустить ложного срабатывания).
- Риск двойного рефанда, если `LatePaymentRefundService` вызывается повторно (та же ситуация из-за
  ретрая банка) — защищено идемпотентностью на уровне `payment_operations.idempotency_key`
  (DTJ-242, шаг до этой ветки уже гарантирует однократность обработки одного `bankEventId`).
