## Задача

Последний экран перед реальным списанием/обязательством клиента — сводка по аптекам с доставкой,
пикер адреса с полем «Ориентир», сетка подъезд/этаж/квартира, список способов оплаты (наличные
активны, банковские — «Скоро», D-25/enabledPaymentMethods), кнопка «Оформить заказ» с защитой от
двойного клика на уровне UI (defense in depth поверх серверной идемпотентности, SRS-UX-050).

## Технический контекст

`apps/web/src/features/checkout/**`. Дизайн-референс `.dc.html:859-937` — сводка по аптекам,
карта-пикер адреса (`MapView` iframe-заглушка, `mode=picker`), поле «Ориентир» с примером-плейсхолдером,
список оплаты (нал активен, карта/кошелёк — badge «Скоро»), спиннер в кнопке при отправке. Формат
многошаговой формы — `model/checkout-form.model.ts` (чистое состояние формы, независимое от
`packages/i18n`-словаря, SRS-UX-054: переключение локали НЕ сбрасывает введённые данные).

## Что сделать

1. `useCreateOrder()` — мутация `POST /api/v1/orders` (DTJ-233), генерирует `Idempotency-Key`
   (UUID v4) ОДИН РАЗ на попытку отправки формы (не на каждый рендер) — ключ переиспользуется при
   ретрае того же запроса, новый генерируется только при явном изменении данных формы пользователем
   после провала.
2. `CheckoutScreen.tsx`: композиция `OrderSummarySection` (сводка по группам аптек с доставкой из
   `meta.pharmacyGroups`, полученных из корзины) + `AddressPickerSection` + `PaymentMethodSection`.
3. `AddressPickerSection.tsx`: выбор сохранённого адреса ИЛИ инлайн-ввод (карта-пикер, поле
   «Ориентир» с плейсхолдером-примером, сетка подъезд/этаж/квартира — сохраняются в
   `deliveryLandmark`/структурированное текстовое поле, не отдельные колонки БД — см. DTJ-229).
4. `PaymentMethodSection.tsx`: радио-выбор способа оплаты — «Наличными курьеру» активен, «Банковская
   карта»/«Онлайн-кошелёк» — задизейблены с бейджем «Скоро» (D-16/D-25, R1 дефолт
   `enabledPaymentMethods=['cash_courier']`) — состояние disabled ЖЁСТКО в коде для R1, не
   зависит от бэкенд-флага, который может быть недоступен (см. DTJ-229 «Риски»); когда бэкенд
   позже предоставит реальный список — заменить на динамическое чтение (follow-up, вне периметра
   этого тикета).
5. Защита от двойного клика (SRS-UX-050/TC-UX-004): кнопка «Оформить заказ» переходит в
   `disabled + loading` СИНХРОННО с первым кликом (не дожидаясь ответа сервера) — состояние
   `isSubmitting` в `model/`, не в самой кнопке.
6. Гонка WS/REST (SRS-UX-051): если WS-событие `order.paid` для заказа, которого ещё нет в
   локальном состоянии (`orderId` неизвестен клиенту до REST-ответа), приходит раньше — игнорируется
   (проверка в обработчике WS-подписки, если WS-инфраструктура уже подключена; если ещё нет —
   TODO, не блокирует тикет, WS — не в периметре EP-09/EP-10 backend).
7. Кнопка «Назад» браузера после отправки, до ответа (SRS-UX-052): запрос НЕ отменяется —
   `AbortController` НЕ используется для отмены `useCreateOrder` при `unmount`/навигации, результат
   синхронизируется на `/orders` при следующем открытии.
8. Переключение локали посреди формы (SRS-UX-054): состояние формы в `model/` не зависит от
   активного `useT()`-словаря — переключение локали меняет только текст меток.
9. `CheckoutPage.tsx` — тонкая композиция, ноль бизнес-логики.

## Критерии приёмки

1. **Given** форма валидна, **When** пользователь дважды быстро кликает «Оформить заказ», **Then**
   ровно ОДИН `POST /api/v1/orders` в сетевых логах, кнопка `loading` после первого клика
   (TC-UX-004).
2. **Given** ответ содержит `failedGroups` для одной из аптек, **When** экран успеха
   отрендерен, **Then** пользователь видит И оформленные заказы, И понятное объяснение по
   провалившейся группе (не «всё пропало»/не молчаливая потеря информации).
3. **Given** пользователь заполняет адрес, **When** переключает язык интерфейса, **Then** введённые
   данные (адрес, ориентир, этаж) сохраняются — меняются только метки полей.
4. **Given** список оплаты отрендерен для R1, **Then** «Наличными курьеру» — единственный активный
   вариант, банковские — задизейблены с «Скоро», клик по ним ничего не отправляет.
5. **Given** пользователь нажимает «Назад» браузера сразу после отправки, до получения ответа,
   **Then** запрос на сервере продолжает выполняться (не отменяется клиентом).

## Риски и подводные камни

- **`GET /orders/:id/payment-status`** возвращает `501` до готовности EP-10 (DTJ-233) — для R1
  это не блокирует наличные (единственный реальный путь), но экран НЕ должен падать, если позже
  тестовый non-cash тенант попытается открыть статус оплаты; обработать `501` как «статус
  недоступен», не как критическую ошибку UI.
- **WS-инфраструктура** (SRS-UX-051) — вне периметра backend-тикетов EP-09/EP-10; если общего
  WS-gateway ещё нет, обработчик гонки WS/REST реализуется как заготовка с TODO, не блокирует
  сдачу.
- Зависимость от `MapView`-компонента (карта-пикер адреса) — дизайн показывает iframe-заглушку;
  реальный `MapLibre GL JS` — компонент EP-08 (карта аптек)/EP-18, здесь допустима временная
  заглушка того же контракта (`mode=picker`), если общий компонент ещё не готов.
