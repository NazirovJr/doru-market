## Задача

Момент физического вручения товара — момент, когда деньги клиента ЮРИДИЧЕСКИ становятся
обязательством платформы перед аптекой (за вычетом комиссии). Этот use case — единственный
вызывающий код для `platform_fee_captured`/`captured_to_pharmacy`, подписанный на
`OrderDeliveredEvent`, а не вызываемый ни из одного контроллера напрямую (событийная связь модулей
delivery→payments, `10-domain-model.md` §«Ограниченные контексты»). Для наличных заказов — это
намеренный NOOP: комиссия за них взимается отдельным B2B-циклом (DTJ-251), а не через ledger.

## Технический контекст

`order-delivered.subscriber.ts` — подписчик `outbox`/`domain-events` очереди на `OrderDeliveredEvent`
(публикуется модулем `delivery`, EP-13, ВНЕ периметра этого тикета — здесь только сторона
потребителя). Идемпотентность — `processed_events(consumer_name, event_id)` таблица (уже в базовой
схеме, группа J, `11-database-schema.md`) — `INSERT` ПЕРЕД обработкой, конфликт PK = уже
обработано, no-op (SRS-DOM-152, at-least-once delivery).

## Что сделать

1. `CaptureEscrowUseCase.execute(orderId, deliveredAt, eventId)`:
   1. `INSERT INTO processed_events (consumer_name='payments.on-delivered', event_id=:eventId)
      ON CONFLICT DO NOTHING RETURNING *` — конфликт → return (уже обработано, SRS-PAY-012).
   2. `PaymentsOrdersPort.getOrderById(orderId)` (DTJ-236/242) → проверить `paymentMethod`.
   3. Given `paymentMethod === 'cash_courier'` → **NOOP с логированием** (`pino.info`, не ошибка —
      ожидаемая ветка, SRS-PAY-017/017a) — `escrow_ledger`/`payout_schedule` НЕ создаются вовсе,
      комиссия — предмет DTJ-251 (B2B-инвойс).
   4. Иначе (non-cash, заказ уже `paid_escrow`/`processing`/`picked_up` на момент доставки) —
      В ОДНОЙ транзакции: `EscrowLedger.append({ entryType: 'platform_fee_captured', direction:
      'credit', amountDiram: Σ(order_items.platform_fee_diram) })` +
      `EscrowLedger.append({ entryType: 'captured_to_pharmacy', direction: 'credit', amountDiram:
      grossAmount - commissionDiram })` + `INSERT INTO payout_schedule (order_id, pharmacy_id,
      status='pending', gross_amount_diram, commission_diram, net_amount_diram,
      hold_period_days=<снэпшот tenantSettings.holdPeriodDays НА МОМЕНТ delivered>)`
      (SRS-PAY-031 — создаётся, не только обновляется, сразу при `delivered`, статус `pending`,
      НЕ `due`).
2. `OrderDeliveredSubscriber` — регистрирует `CaptureEscrowUseCase.execute` как обработчик события
   в очереди `domain-events` (механизм подписки — BullMQ consumer/аналог, зависит от реализации
   `OutboxRelayWorker`, предположительно от общей инфраструктуры EP-01/EP-19; если отсутствует —
   временный прямой HTTP/internal endpoint-заглушка с TODO, не блокировать тикет).

## Критерии приёмки

1. **Given** `OrderDeliveredEvent` для non-cash заказа, **When** `CaptureEscrowUseCase.execute`,
   **Then** `escrow_ledger` содержит РОВНО одну пару `platform_fee_captured`+
   `captured_to_pharmacy`, `payout_schedule` содержит строку `status='pending'` с корректным
   `net_amount_diram = gross - commission`.
2. **Given** то же событие доставлено ПОВТОРНО (`event_id` тот же, at-least-once), **When**
   `CaptureEscrowUseCase.execute` вызван снова, **Then** `escrow_ledger` по-прежнему содержит
   РОВНО одну пару записей (не две), `processed_events` содержит запись после первого вызова.
3. **Given** заказ `cash_courier`, `status='delivered'`, **When** `CaptureEscrowUseCase.execute`,
   **Then** `escrow_ledger`/`payout_schedule` НЕ содержат ни одной строки для этого `order_id`.
4. **Given** `tenantSettings.holdPeriodDays` изменяется ПОСЛЕ создания `payout_schedule`, **When**
   строка уже создана, **Then** её `hold_period_days` остаётся снэпшотом на момент создания
   (не пересчитывается).

- **`OrderDeliveredEvent` публикуется модулем `delivery` (EP-13), который стартует в волне 9 —
  на 2 волны позже EP-10 (волна 7).** Реальная интеграция подписки (шаг 2 «Что сделать») может
  оказаться недостижима до готовности EP-13 — use case реализуется и тестируется полностью
  изолированно (вызов `execute()` напрямую в тестах, минуя реальную очередь событий), физическое
  подключение к очереди — при появлении публикующей стороны, координировать с тимлидом EP-13.

  `PaymentsOrdersPort.getOrderById` (расширить сигнатуру порта из DTJ-236, если текущая не
  возвращает позиции заказа целиком, не только шапку) — правка файла того же владельца/эпика.
