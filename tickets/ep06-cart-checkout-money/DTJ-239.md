## Задача

Architect Pivot §2.2 требует закладывать архитектуру целиком сразу, откладывая только то, что
физически заблокировано внешней стороной — реальный контракт банков РТ. Этот тикет доказывает, что
`PaymentProvider`-порт (DTJ-237) абстрагирует бизнес-логику от банка полностью: адаптеры
существуют, компилируются, покрыты unit-тестами на ASSUMPTION-контракте, но выключены на уровне
конфигурации до получения реального договора — переключение `PAYMENT_DRIVER=alif_mobi` в проде
физически заблокировано `tenant_settings.enabledPaymentMethods` (DTJ-229/241), не удалением кода.

## Технический контекст

Точные заголовки/поля вебхука и `createInvoice`-контракта Alif/DC — ASSUMPTION (research 03,
смоделировано по публичной документации Alifpay Узбекистан как ближайший референс, НЕ
гарантированно идентично реальному контракту Alif Bank TJ, SRS-PAY-006). `capabilities()` для
обоих: `supportsHoldCapture: false`, `supportsPartialRefund: false` (SRS-PAY-007) — ЭТО
причина, по которой раздельный биллинг (D-10, DTJ-228) не гипотетический, а единственный рабочий
путь частичного возврата в проде (владелец логики раздельного биллинга — EP-11, здесь только
подтверждение capability-флага, определяющего необходимость этой стратегии).

## Что сделать

1. `AlifMobiProvider`/`DcNextProvider` реализуют `PaymentProvider` (DTJ-237) — структура методов
   идентична `MockBankProvider` (DTJ-238), но HTTP-вызовы к реальному API банка (URL, заголовки —
   ASSUMPTION, помечены явным JSDoc-комментарием `// ASSUMPTION: контракт не подтверждён банком,
   research 03`).
2. `capabilities()`: `{ providerName: 'alif_mobi'|'dc_next', supportsHoldCapture: false,
   supportsPartialRefund: false, maxInvoiceValidityMinutes: <ASSUMPTION значение из research> }`.
3. `AlifMobiWebhookVerifierAdapter`/`DcNextWebhookVerifierAdapter` реализуют
   `BankWebhookVerifierPort` (DTJ-237) — HMAC-проверка по ASSUMPTION-схеме заголовков; ОБЯЗАТЕЛЬНО
   переиспользовать ту же внутреннюю функцию HMAC-сравнения, что `MockBankWebhookVerifierAdapter`
   (DTJ-238) — не копипастить алгоритм трижды (`02` C15).
4. Зарегистрировать обе ветки в `payments.module.ts` DI (`PAYMENT_DRIVER ∈ {'alif_mobi',
   'dc_next'}`) — переключатель НЕ влияет на `application`/`domain` код (Provider Pattern, Charter
   §3.3).
5. Unit-тесты на предполагаемом контракте: сериализация запроса `createInvoice`, парсинг ответа,
   HMAC-подпись на фикстурных данных (не реальный сетевой вызов — `nock`/аналогичный mock HTTP-
   клиента).
6. Явный комментарий в `payments.module.ts` рядом с DI-биндингом: переключение на `alif_mobi`/
   `dc_next` в проде заблокировано `tenant_settings.enabledPaymentMethods` (по умолчанию R1 —
   только `cash_courier`), НЕ этим файлом — иначе разработчик может ошибочно решить, что
   достаточно сменить `PAYMENT_DRIVER`, чтобы включить реальную оплату для пользователей.

## Критерии приёмки

1. **Given** `AlifMobiProvider`, **When** `pnpm --filter api build`, **Then** компилируется без
   ошибок, реализует ВСЕ обязательные методы `PaymentProvider`.
2. **Given** unit-тест на фикстурном ответе Alif (ASSUMPTION-формат), **When**
   `AlifMobiProvider.createInvoice()`, **Then** корректно парсит `InvoiceRef` из
   ASSUMPTION-контракта.
3. **Given** `PAYMENT_DRIVER=alif_mobi` установлен в тестовом окружении, **When**
   `tenant_settings.enabledPaymentMethods` НЕ содержит `'alif_mobi'` для тенанта, **Then**
   checkout с этим методом всё равно отклоняется `PAYMENT_METHOD_NOT_ENABLED` (DTJ-229) —
   подтверждает независимость двух уровней защиты.
4. **Given** обе HMAC-реализации (Alif, DC), **When** ревью кода, **Then** обе вызывают общую
   внутреннюю функцию сравнения подписи (не дублируют её).

## Риски и подводные камни

- **Реальный контракт банка неизвестен — это не блокирует тикет, но означает, что вся логика
  адаптеров подлежит переписыванию при получении реального договора (R3).** Не инвестировать
  сверх необходимого в детали ASSUMPTION-формата — минимально достаточная реализация,
  удовлетворяющая порту и unit-тестам, без избыточной обработки гипотетических edge-case'ов
  несуществующего контракта (`02` C15 — абстракция без второго реального потребителя).
- Явный риск, если разработчик по невнимательности решит, что раз адаптер «готов», можно включить
  `PAYMENT_DRIVER=alif_mobi` в прод-конфигурации — см. п.6 «Что сделать», обязательный комментарий-
  предупреждение прямо в коде DI-биндинга.
