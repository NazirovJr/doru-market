## Задача

`pending → due` — единственный переход в состоянии payout, управляемый временем, а не действием
пользователя (D-19, осознанное архитектурное решение, не забытый guard). Этот тикет реализует сам
переход и публичный контракт `holdPayout`, которым EP-14 (споры) заморозит выплату атомарно при
открытии спора — использование контракта принадлежит EP-14, здесь только его реализация и
гарантия изоляции джобы.

## Технический контекст

`PayoutSchedulerJob` (BullMQ repeatable, cron ASSUMPTION `'0 * * * *'` — ежечасно): `UPDATE
payout_schedule SET status='due', due_at=NOW() WHERE status='pending' AND EXISTS (SELECT 1 FROM
orders WHERE orders.id=payout_schedule.order_id AND orders.delivered_at +
(payout_schedule.hold_period_days || ' days')::interval <= NOW())` — использует СНЭПШОТ
`hold_period_days` из строки `payout_schedule` (записан при создании, DTJ-244), не текущее
значение `tenant_settings`. `PaymentsFacade` (`application/ports/payments-facade.port.ts`, часть
ПУБЛИЧНОГО фасада модуля `payments`, экспортируется через `modules/payments/index.ts`, DTJ-236) —
контракт для внешних модулей (EP-14): `holdPayout(orderId, disputeId): Promise<void>`.

## Что сделать

1. `PayoutSchedulerJob` — SQL-запрос выше, выполняется батчами (не построчно в цикле — один
   `UPDATE ... WHERE ...` покрывает весь батч атомарно на уровне БД).
2. `HoldPayoutUseCase.execute(orderId, disputeId)`: `UPDATE payout_schedule SET
   status='disputed', held_by_dispute_id=:disputeId WHERE order_id=:orderId AND status IN
   ('pending','due')` — Given строка НЕ найдена (уже `paid` — пост-payout случай) → НЕ бросает
   ошибку, возвращает `{ alreadyPaid: true }` (SRS-DOM-105/SRS-DISP-002 — вызывающий код EP-14
   решает, что делать дальше — `requires_adjustment`, поле таблицы `order_disputes`, вне
   периметра этого тикета).
3. `PaymentsFacade.holdPayout(orderId, disputeId)` — экспорт `HoldPayoutUseCase` через публичный
   фасад `modules/payments/index.ts` (расширение файла DTJ-236, тот же владелец).
4. Гарантия изоляции: `PayoutSchedulerJob`/`PayoutExecutionJob` (DTJ-250) выбирают строго `WHERE
   status='due'` — `disputed`-строки физически исключены самим значением `status`, БЕЗ
   дополнительного `WHERE status != 'disputed'` (SRS-PAY-032 — простота как гарантия, не
   отдельная проверка, которую легко забыть при рефакторинге).

## Критерии приёмки

1. **Given** `payout_schedule.status='pending'`, `hold_period_days=1`, `orders.delivered_at` —
   2 дня назад, **When** `PayoutSchedulerJob`, **Then** `status='due'`, `due_at` заполнен.
2. **Given** `payout_schedule.status='due'` для заказа, **When** `HoldPayoutUseCase.execute(orderId,
   disputeId)`, **Then** `status='disputed'`, `held_by_dispute_id` заполнен.
3. **Given** `payout_schedule.status='paid'` (пост-payout), **When**
   `HoldPayoutUseCase.execute`, **Then** возвращает `{ alreadyPaid: true }`, статус НЕ изменён,
   ошибка не брошена.
4. **Given** несколько строк `disputed`/`due`/`pending` одновременно, **When**
   `PayoutSchedulerJob` прогоняется, **Then** только `pending`-строки с истёкшим `hold_period_days`
   переходят в `due` — `disputed` не затронуты.

## Тест-план

## Риски и подводные камни

- **`PaymentsFacade.holdPayout` — публичный контракт для эпика, который ещё не начался (EP-14,
  волна 10).** Сигнатура фиксируется здесь как лучшее понимание на момент EP-10 — если EP-14
  впоследствии потребует иную форму (например, синхронный возврат текущего `payout_schedule.status`
  вместо булева `alreadyPaid`), потребуется координация и, возможно, breaking-правка публичного
  фасада — не блокирует этот тикет, но зафиксировать как известный контракт для будущей сверки.
- Батчевый `UPDATE` без построчного цикла — единственно верный подход для производительности,
  но убедиться, что индекс на `payout_schedule(status)`/`orders(delivered_at)` присутствует
  (проверить/добавить в базовой миграции DTJ-236, аналогично риску DTJ-247).
