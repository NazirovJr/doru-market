## Задача

Checkout — единственное место, где корзина клиента превращается в реальные, юридически значимые
заказы аптек. Ошибка здесь стоит дороже любой другой в эпике: пропущенная проверка активности
аптеки — заказ уходит в закрытую точку; неправильная изоляция транзакций между группами — сбой
одной аптеки откатывает уже готовый заказ другой. Этот тикет — центральная оркестрация: сплит
корзины на N групп по аптекам, атомарная обработка КАЖДОЙ группы в своей транзакции, композитный
ответ с частичным успехом, когда одни аптеки оформились, а другие — нет.

## Технический контекст

`apps/api/src/modules/orders/application/checkout/checkout.use-case.ts` — единственный публичный
use case для `POST /api/v1/orders`. Собирает воедино: `SplitCartByPharmacyUseCase` (DTJ-223),
`Order.create()` (DTJ-221), `order.confirm()` (DTJ-222, вызывается внутри `Order.create()` для
`cash_courier`), пять портов из DTJ-220 (`CatalogFacadePort`, `InventoryFacadePort`,
`PrescriptionsFacadePort`, `OnboardingFacadePort`, `TenancyFacadePort`) и НОВЫЙ порт
`PaymentInvoicePort` (уже объявлен DTJ-220) для non-cash методов.

**Архитектурное решение этого тикета (координировать с тимлидом EP-10 при расхождении):**
`21-module-orders-payments-escrow.md` §2.1 шаг «h» формулирует вызов `PaymentsFacade.
createInvoice(...)` буквально как факт, происходящий «после commit» — но `PAY-модуль (EP-10)
стартует ПОЗЖЕ EP-09` (волна 7 vs волна 6, `tickets/00-EPICS.md`). Прямой импорт `modules/payments`
здесь невозможен физически на момент разработки. Одновременно `SRS-DOM-166` требует СИНХРОННОГО
поведения (клиент получает `503 PAYMENT_PROVIDER_UNAVAILABLE` В ЭТОМ ЖЕ HTTP-ответе при таймауте
провайдера) — то есть вызов НЕ может быть полностью асинхронным событием без ответа клиенту.
Разрешение: `CheckoutUseCase` вызывает `PaymentInvoicePort.createInvoice(cmd)` (порт, DTJ-220)
СИНХРОННО, ПОСЛЕ commit транзакции создания заказа группы, В ТОЙ ЖЕ функции use case (не в outbox-
событии) — сам порт на момент EP-09 не забинжен ни к чему в проде (см. DTJ-220 «Риски»), реальную
реализацию адаптера регистрирует DTJ-242 (EP-10). Таким образом `CheckoutUseCase` компилируется и
полностью тестируется (с мок-портом) независимо от готовности EP-10, а после интеграции EP-10 в
DI-граф поведение соответствует SRS буквально.

## Что сделать

1. `CheckoutCommand` DTO: `cartItemIds[], deliveryAddressId?/inlineAddress?, deliveryLandmark?,
   paymentMethod, prescriptionIds[], expectedTotalDiram?, checkoutAttemptId` (из заголовка
   `Idempotency-Key`, SRS-DOM-166).
2. `CheckoutUseCase.execute(cmd)`:
   1. Загрузить `cart_items` по `cartItemIds`, проверить принадлежность текущему `customerId`/
      `sessionToken` — иначе `ForbiddenCartAccessError` (`403`).
   2. Для каждой затронутой аптеки — `OnboardingFacadePort.isPharmacyActive(pharmacyId)`; неактивна
      → аптека целиком исключается, `excludedItems` пополняется `PHARMACY_SUSPENDED` (покрывает
      также SRS-ORD-041 — приостановка сети из-за неоплаченного B2B-инвойса использует ТОТ ЖЕ
      флаг `isPharmacyActive`, единая точка проверки).
   3. `SplitCartByPharmacyUseCase.execute(items)` → N групп.
   4. Для КАЖДОЙ группы, В СВОЕЙ транзакции (`unitOfWork.run()` НА ГРУППУ, не на весь checkout —
      SRS-ORD-019):
      a. Rx-исключение и снэпшот каталога/резерв остатка/расчёт стоимости — делегированы DTJ-228/
         DTJ-230 (этот тикет вызывает их как под-шаги, не дублирует логику).
      b. `Order.create(cmd)` (DTJ-221/222) — конструирует заказ, для `cash_courier` синхронно
         `confirmed`.
      c. Commit транзакции группы.
      d. Given `paymentMethod ∈ {'alif_mobi','dc_next'}`: ПОСЛЕ commit — синхронный вызов
         `PaymentInvoicePort.createInvoice(...)` с таймаутом `PAYMENT_PROVIDER_TIMEOUT_MS`
         (ASSUMPTION 8000, ENV). Таймаут/ошибка → заказ ОСТАЁТСЯ созданным в `pending_payment`
         (не откатывается), группа помечается в ответе `paymentPending: true`, use case НЕ бросает
         исключение на весь запрос — если это ЕДИНСТВЕННАЯ группа, presentation-слой (DTJ-233)
         транслирует в `503 PAYMENT_PROVIDER_UNAVAILABLE`, при нескольких группах — остальные
         группы не затронуты.
   5. Собрать `{ orders: OrderResultDto[], failedGroups: FailedGroupDto[] }` + `meta.excludedItems`.
3. Given ВСЕ группы исключены/провалены (пустой `orders`), Then `422 NO_ORDERABLE_ITEMS`
   (SRS-ORD-016) — не `200` с пустым массивом.
4. `IdempotencyAttemptAdapter` — хранит `(userId, checkoutAttemptId) → сохранённый результат`
   поверх ОБЩЕГО механизма `idempotency_keys` (SRS-API-009/010, предположительно уже реализован
   EP-01 — см. «Риски»); этот адаптер — тонкая типизированная обёртка специфично для checkout, не
   переизобретение общего механизма.
5. `OrderRepository` (infrastructure): `save(order, unitOfWork)`, `findByCheckoutAttemptId(...)`.

## Критерии приёмки

1. **Given** корзина с товарами от 2 аптек, обе активны, **When**
   `POST /api/v1/orders` со всеми `cartItemIds`, **Then** ответ содержит `orders.length === 2`,
   каждый заказ — свой `pharmacyId`/`orderNumber`.
2. **Given** аптека Б имеет `stock_quantity=0` на один товар, аптека А — в наличии, **When**
   checkout на обе группы, **Then** `orders` содержит заказ А, `failedGroups` содержит запись Б с
   `INSUFFICIENT_STOCK`, заказ А НЕ откатывается.
3. **Given** корзина только из товаров неактивной аптеки, **When** checkout, **Then** `422
   NO_ORDERABLE_ITEMS`, ни один заказ не создан.
4. **Given** non-cash заказ, `PaymentInvoicePort.createInvoice` симулирует таймаут (мок), **When**
   checkout с ЕДИНСТВЕННОЙ группой, **Then** `503 PAYMENT_PROVIDER_UNAVAILABLE`, заказ существует в
   БД в статусе `pending_payment` без `paymentTransactionId`.
5. **Given** повторный `POST /api/v1/orders` с тем же `Idempotency-Key`, тем же телом, первый уже
   завершён, **Then** возвращён СОХРАНЁННЫЙ ответ, `InventoryFacadePort.reserveStock` не вызван
   повторно (проверка через мок-счётчик вызовов).

## Тест-план

- Unit (application, моки всех портов): по кейсу на каждый шаг оркестрации — happy path, частичный
  сбой одной из N групп, полный сбой всех групп, non-cash таймаут провайдера.
- Интеграционный (Testcontainers PostgreSQL + Redis): реальные транзакции — подтвердить, что
  откат группы Б не откатывает уже закоммиченную группу А (раздельные `unitOfWork`).
- Интеграционный: идемпотентность — конкурентный дубль (см. DTJ-231 для полной матрицы гонок,
  здесь только базовый повторный-после-завершения сценарий).
- Покрытие `application/` ≥ 90%.

## Риски и подводные камни

- **Архитектурное решение о синхронном вызове `PaymentInvoicePort` внутри `CheckoutUseCase` —
  решение этого тикета, не буквальная цитата ни одного SRS-документа.** Отражает компромисс между
  `SRS-ORD-018` (вызов после commit) и `SRS-DOM-166` (синхронный `503` клиенту). Явно согласовать
  с тимлидом EP-10 ДО начала DTJ-242 — если EP-10 спроектирует иначе (например, чисто событийно),
  контракт `PaymentInvoicePort` придётся пересогласовать, это МЕЖЭПИКОВЫЙ риск, эскалировать сразу
  при обнаружении расхождения.
- **`idempotency_keys` — общий механизм, предположительно от EP-01, не гарантирован.** Если
  таблица/интерсептор ещё не существуют на момент этого тикета — реализовать локальный fallback
  в `IdempotencyAttemptAdapter` поверх `orders.checkout_attempt_id` (уже в схеме, DTJ-220) как
  временное решение специфично для checkout, с TODO на миграцию к общему механизму.
- **`Money`/`GeoPoint` VO** — та же зависимость от DTJ-221 «Риски»: если ещё не определены в общем
  месте на момент этого тикета, использовать локальные копии из `orders/domain`.
