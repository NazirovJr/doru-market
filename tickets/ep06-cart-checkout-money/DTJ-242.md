## Задача

Единственный код-путь, которому разрешено перевести заказ в `paid_escrow` (кроме одного явного
административного исключения — DTJ-246). Категорический запрет (SRS-PAY-018) существует не
случайно: любой обходной путь смены статуса оплаты — прямой источник финансового расхождения
между тем, что говорит `order.status`, и тем, что реально произошло с деньгами клиента. Этот
тикет — сердце всей эскроу-механики: HMAC-проверка ДО парсинга бизнес-полей, идемпотентность ДО
бизнес-логики, `markPaidEscrow` + `EscrowLedger.recordHold` — АТОМАРНО в одной транзакции.

## Технический контекст

`POST /api/v1/payments/webhook` — единственный маршрут (не параметризован по провайдеру в пути,
SRS-API-037). Порядок обработки — строго последовательный (§5.2): (1) сырые байты тела; (2)
резолв `BankWebhookVerifierPort` по `X-Payment-Provider`; (3) `verify()`; (4) ТОЛЬКО после успеха
— `JSON.parse` + Zod-валидация. `orders-facade.adapter.ts` — реализация
`PaymentsOrdersPort` (DTJ-236) поверх реального `OrdersFacade` (DTJ-222, EP-09) — тот же паттерн
межмодульного биндинга, что DTJ-241.

**Инвариант SRS-DOM-180/SRS-ORD-027a реализуется ЗДЕСЬ буквально**: `order.markPaidEscrow(txId,
paidAt, ledgerHoldWillBeRecorded: true)` (сигнатура из DTJ-222) и `EscrowLedger.append(hold_created
entry)` (DTJ-240) — ОБЕ операции в ОДНОЙ транзакции БД (`unitOfWork.run()`), не в двух отдельных
вызовах, между которыми возможен сбой процесса.

## Что сделать

1. `PaymentsWebhookController`: `POST /api/v1/payments/webhook`, читает `rawBody` (Fastify —
   `addContentTypeParser`/`rawBody: true` конфигурация, НЕ `JSON.parse` фреймворком по умолчанию —
   подпись покрывает байты как они пришли по проводу). `X-Payment-Provider` не зарегистрирован ни
   одним адаптером → `400 WEBHOOK_PROVIDER_UNKNOWN` немедленно, тело не обрабатывается.
2. `HandlePaymentWebhookUseCase.execute(rawBody, headers, providerName)`:
   1. Резолвить `BankWebhookVerifierPort` по `providerName` (DI-биндинг по ключу — карта
      `provider → verifier`, зарегистрированная в `payments.module.ts`).
   2. `verifier.verify(rawBody, headers)` → несовпадение → `401
      INVALID_WEBHOOK_SIGNATURE`, `audit_log`-запись «подозрительное событие» (НЕ создаёт
      `support_ticket` автоматически — частота ложных срабатываний от сканеров слишком высока).
   3. `JSON.parse` + Zod-валидация `PaymentWebhookPayload` → `VerifiedWebhookPayload`.
   4. `BEGIN`: `INSERT INTO payment_operations (idempotency_key=bankEventId, ...) ON CONFLICT
      (idempotency_key) DO NOTHING RETURNING id`. Given конфликт (ничего не вставлено) → `COMMIT`,
      `200 OK` немедленно, бизнес-логика НЕ выполняется (SRS-DOM-164).
   5. Given вставлено И `type='payment_confirmed'`: `SELECT ... FOR UPDATE` на строку `orders`
      (SRS-DOM-165, построчная блокировка) → `order.markPaidEscrow(providerRef, occurredAt,
      ledgerHoldWillBeRecorded: true)` через `PaymentsOrdersPort` → `EscrowLedger.append({
      entryType: 'hold_created', direction: 'debit', amountDiram, paymentTransactionRef:
      providerRef })` (DTJ-240) → запись в `outbox` (`OrderPaidEvent`, payload из глоссария
      `10-domain-model.md`) → `COMMIT`.
   6. `200 OK` синхронно, в течение HTTP-запроса (SRS-PAY-023 — никакого исходящего сетевого
      вызова из обработчика, кроме асинхронной публикации `outbox` воркером).
3. `OrdersFacadeAdapter implements PaymentsOrdersPort` (DTJ-236) — реализация поверх реального
   `OrdersFacade.markPaidEscrow(...)` (DTJ-222).
4. Регистрация карты `providerName → BankWebhookVerifierPort` в `payments.module.ts` (расширение
   DI, включает `mock_bank` из DTJ-238, `alif_mobi`/`dc_next` из DTJ-239).

## Критерии приёмки

1. **Given** валидный вебхук `payment_confirmed` для заказа в `pending_payment`, **When**
   `POST /api/v1/payments/webhook`, **Then** заказ переходит в `paid_escrow`, `escrow_ledger`
   содержит РОВНО одну запись `hold_created`, обе мутации — в ОДНОЙ транзакции (проверка через
   искусственный сбой между шагами в тесте — обе мутации либо обе применены, либо обе откачены).
2. **Given** тот же `bankEventId` приходит повторно (сетевой ретрай банка), **When** повторный
   `POST`, **Then** `200 OK`, `escrow_ledger` содержит РОВНО ОДНУ запись `hold_created` (не две).
3. **Given** тело вебхука изменено после подписи (симуляция подделки), **When** `POST`, **Then**
   `401 INVALID_WEBHOOK_SIGNATURE`, ни одна запись БД не изменена, `audit_log` содержит событие.
4. **Given** `X-Payment-Provider: unknown_bank`, **When** `POST`, **Then** `400
   WEBHOOK_PROVIDER_UNKNOWN`, тело НЕ парсится вовсе (проверка — Zod-валидатор не вызван, счётчик
   мока).
5. **Given** два вебхука для РАЗНЫХ `orderId` приходят конкурентно, **When** оба обрабатываются,
   **Then** оба успешны независимо, без взаимной блокировки (построчная, не глобальная блокировка).

## Тест-план

- Unit (application, моки портов): полный happy path, дубликат `bankEventId`, невалидная подпись
  (порядок операций — verify ДО parse, проверяется явно: подать заведомо невалидный JSON С
  валидной подписью НЕ должен провалиться на JSON.parse раньше проверки подписи в тестовом
  сценарии наоборот).
- Интеграционный (Testcontainers PostgreSQL + Redis): TC-PAY-001/002/003/005 из
  `21-module-orders-payments-escrow.md` буквально переносятся сюда.
- Интеграционный: атомарность транзакции — искусственный сбой (например, брошенное исключение)
  между `markPaidEscrow` и `EscrowLedger.append` в тестовой обёртке → ОБЕ мутации откачены,
  `order.status` остаётся `pending_payment`.
- Нагрузочный: два конкурентных вебхука разных заказов — оба завершаются успешно без deadlock.
- Покрытие `application/` ≥ 90%.

## Риски и подводные камни

- **`rawBody` доступ во Fastify** — по умолчанию NestJS/Fastify парсит JSON до того, как
  прикладной код видит тело; нужна явная конфигурация (`rawBody: true` в `NestFactory.create`
  ИЛИ кастомный `contentTypeParser`). Если общая конфигурация Fastify (владелец — EP-01
  scaffolding) этого не предусматривает — координировать правку бутстрапа приложения, не
  обходить через `JSON.stringify(req.body)` (это НЕ те же байты, что пришли по проводу, HMAC не
  совпадёт с реальным банком).
- **`OrdersFacadeAdapter`** зависит от финальной сигнатуры `OrdersFacade.markPaidEscrow` (DTJ-222,
  EP-09) — тот же межэпиковый риск расхождения, что DTJ-241/232. Сверить перед реализацией.
- Идемпотентность вебхука (`payment_operations.idempotency_key = bankEventId`) — ДРУГОЙ механизм,
  чем `Idempotency-Key`-заголовок checkout (SRS-DOM-164 явно это подчёркивает) — не путать два
  разных стола идемпотентности в реализации.
