## Задача

D-25 — самое рискованное архитектурное решение этого эпика: наличный заказ обязан пройти
`confirmed → processing → picked_up → delivered`, НИКОГДА не касаясь `paid_escrow`, и это должно
быть структурно невозможно нарушить, а не «просто не нарушаться на практике». Этот тикет реализует
ПОЛНУЮ таблицу разрешённых переходов `Order` (обе ветви — эскроу и наличные) как явную state
machine, методы-намерения на `Order`, инвариант SRS-DOM-180/SRS-ORD-027a как programmatic
guard внутри самих методов, и публичный фасад `OrdersFacade` — единственный способ, которым EP-10
(и позже EP-11/12/13/14) будут читать/изменять заказы, не импортируя `orders/domain` напрямую.

## Технический контекст

`10-domain-model.md` §«State machines»/1 — полная таблица (обе диаграммы: основная ветка через
`pending_payment`/`paid_escrow` и параллельная ветка D-25 через `confirmed`) + список запрещённых
переходов SRS-DOM-102 (дополненный D-25: `confirmed → paid_escrow` и `paid_escrow → confirmed`
запрещены в обе стороны). `03-ARCHITECT-DECISIONS.md` §«D-25» и
`docs/spec/21-module-orders-payments-escrow.md` §2.4/§9/§10.2 — операционное обоснование каждой
ветки. Методы-намерения, ранее объявленные в `10-domain-model.md` («Методы-намерения»), дополняются
здесь методом `order.confirm()` (используется ТОЛЬКО из `Order.create()` для `cash_courier`,
SRS-ORD-027 п.1) — этот метод отсутствует в исходном перечне `10-domain-model.md`, добавление
зафиксировать как найденный пробел документа при ревью (не самовольная правка «закона» — метод
логически обязателен по D-25, физическая правка текста `10-domain-model.md` — вне периметра этого
тикета, координировать с архитектором).

`OrdersFacade` (`application/orders.facade.ts`, экспортируется через `modules/orders/index.ts` —
DI-токен `ORDERS_FACADE` уже зарезервирован в DTJ-220) — единственная точка, через которую другие
модули (`payments` — DTJ-243/245, `delivery`/`pharmacy-terminal` — будущие эпики) читают заказ и
вызывают переходы статуса. Методы фасада НЕ содержат бизнес-логику — тонкая обёртка над
`OrderRepository` + вызов метода домена + persist в той же транзакции (`unitOfWork`, передаётся
вызывающим use case, `02` §3.3 — границы транзакции задаёт use case, не репозиторий/фасад).

## Что сделать

1. `order.state-machine.ts`: таблица `ALLOWED_TRANSITIONS: Record<OrderStatus, OrderStatus[]>` —
   обе ветви (SRS-DOM-089..101, SRS-DOM-178/179), функция `isTransitionAllowed(from, to): boolean`.
   Единственный источник истины для допустимости перехода — используется КАЖДЫМ методом-намерением
   ниже, не дублируется if/else в каждом методе (`02` C15/§2.4).
2. Методы-намерения на `Order` (каждый: проверка через `isTransitionAllowed`, при нарушении —
   `InvalidOrderStatusTransitionError(from, to)`; при успехе — приватная мутация `_status`,
   аккумуляция доменного события в `order.pullDomainEvents()`):
   - `order.confirm()`: только из `pending_payment`-ЭКВИВАЛЕНТНОГО начального состояния при
     `paymentMethod==='cash_courier'` внутри `create()` (SRS-ORD-027 п.1) → `confirmed`,
     `paymentTransactionId=null`. Эмитирует внутренний факт (используется DTJ-256 для инварианта,
     НЕ `OrderPaidEvent` — наличный заказ не «оплачен» в эскроу-смысле).
   - `order.markPaidEscrow(txId, paidAt)`: только `pending_payment → paid_escrow` (SRS-DOM-089).
     Перед мутацией статуса — **инвариант SRS-DOM-180/SRS-ORD-027a**: метод принимает флаг
     `ledgerHoldWillBeRecorded: true` как обязательный параметр вызова (не булев — буквально
     заставляет вызывающий код, `HandlePaymentWebhookUseCase` DTJ-243, явно подтвердить, что
     `EscrowLedger.recordHold()` вызывается В ТОЙ ЖЕ транзакции сразу после) — отсутствие
     подтверждения = `TypeScript`-ошибка компиляции (обязательный параметр), а не рантайм-риск
     забытого вызова.
   - `order.startProcessing(pharmacistId)`: из `paid_escrow` ИЛИ `confirmed` (SRS-DOM-091/178,
     зеркальные условия) → `processing`. Бросает `ExpiredStockError`, если через
     `InventorySnapshotPort` (уже объявлен в DTJ-220 как `inventory-facade.port.ts`, добавить метод
     `hasExpiredReservedBatch(orderId)`) хотя бы одна зарезервированная партия просрочена
     (SRS-DOM-006).
   - `order.markPickedUp(handoverOtp)`: `processing → picked_up` (SRS-DOM-094).
   - `order.markDelivered(otpVerification)`: `picked_up → delivered` (SRS-DOM-095).
   - `order.cancel(reason, actor)`: из `pending_payment`/`confirmed`/`paid_escrow`/`processing` →
     `cancelled` (SRS-DOM-090/092/093/154/179). Метод НЕ решает, нужен ли рефанд — только валидирует
     переход и мутирует статус; денежное решение принимает вызывающий use case (DTJ-232/253/254) по
     `paymentMethod` (D-25: `confirmed` и `pending_payment` — без рефанда, `paid_escrow`/
     `processing` — с рефандом).
   - `order.attachReturn(returnId)` / `order.markRefunded(refundRef)` — заготовки методов для
     будущих эпиков (EP-11), реализация перехода `delivered ⇄ return_in_progress ⇄ refunded` —
     ВНЕ периметра этого тикета (владелец EP-11), здесь только сигнатуры + запись в
     `ALLOWED_TRANSITIONS`, чтобы таблица переходов была полной с первого дня (не дробить один
     источник истины между эпиками).
3. `OrderPolicy.canCancel(order, actor): boolean` (`application/policies/order.policy.ts`,
   `02` §3.4 — авторизация в application, не в guard) — `false` для `picked_up`/`delivered`/
   терминальных статусов (SRS-DOM-154), иначе проверка роли актора (`customer` — свой заказ;
   `pharmacist`/`pharmacy_admin` — своя аптека, SRS-ORD-031). Используется DTJ-232.
4. Запрещённые переходы — явный негативный список в `order.state-machine.ts` как комментарий +
   тестовые кейсы (не отдельная структура данных, `ALLOWED_TRANSITIONS` уже исчерпывающий allowlist
   — «запрещено» означает «отсутствует в списке», SRS-DOM-102).
5. `OrdersFacade`: `getOrderForCheckoutAttempt(attemptId)`, `getOrderById(orderId, unitOfWork?)`,
   `markPaidEscrow(orderId, txId, paidAt, unitOfWork)`, `startProcessing(orderId, pharmacistId,
   unitOfWork)`, `markPickedUp(...)`, `markDelivered(...)`, `cancel(orderId, reason, actor,
   unitOfWork)` — каждый метод принимает опциональный `unitOfWork` для вызова внутри чужой
   транзакции (нужно DTJ-243/245/253/254 из модуля `payments`).
6. Обновить `modules/orders/index.ts` — забиндить `ORDERS_FACADE` токен на реализацию.

## Критерии приёмки

1. **Given** заказ `cash_courier` только что сконструирован, **When** `order.confirm()`, **Then**
   статус `confirmed`, `paymentTransactionId=null`, повторный вызов `order.markPaidEscrow(...)`
   бросает `InvalidOrderStatusTransitionError` (переход `confirmed → paid_escrow` отсутствует в
   `ALLOWED_TRANSITIONS`).
2. **Given** заказ в `paid_escrow`, **When** вызывается `order.confirm()` (гипотетическая попытка
   программной ошибки), **Then** `InvalidOrderStatusTransitionError` (симметрично п.5 D-25:
   `paid_escrow → confirmed` запрещён).
3. **Given** заказ `confirmed`, **When** `order.startProcessing(pharmacistId)`, **Then** статус
   `processing`, `slaDeadlineAt` установлен (SRS-DOM-178) — идентично ветке `paid_escrow →
   processing`.
4. **Given** заказ `picked_up`, **When** `OrderPolicy.canCancel(order, customer)`, **Then**
   возвращает `false`.
5. **Given** заказ `delivered`, **When** любой метод-намерение статуса вызывается программно
   (unit-тест, симуляция ошибки вызывающего кода), **Then** `InvalidOrderStatusTransitionError` для
   ВСЕХ переходов из `delivered`, кроме зарезервированных для EP-11 (`attachReturn`).

## Риски и подводные камни

- **`order.confirm()` отсутствует в исходном перечне методов `10-domain-model.md`.** Это реальный
  пробел канонического документа, не самовольное расширение — см. «Технический контекст». Если к
  моменту реализации архитектор уже внёс правку — использовать её сигнатуру вместо предложенной
  здесь, приоритет документа выше тикета (иерархия из системного промпта тимлида).
- **`ExpiredStockError` требует метода `hasExpiredReservedBatch` на порту, который физически
  реализует модуль `inventory` (EP-05).** Если порт ещё не наполнен реальной проверкой на момент
  этого тикета — временный no-op-адаптер (`always false`) в тестовом окружении, пометить TODO со
  ссылкой на владельца EP-05, не блокировать сдачу этого тикета.
- **Обязательный параметр `ledgerHoldWillBeRecorded`** — намеренно избыточная защита (домен не
  может физически проверить, что вызывающий код действительно вызовет `EscrowLedger.recordHold()`
  следом, это лишь компиляционное напоминание). Настоящая гарантия — DTJ-243 оборачивает оба вызова
  в одну транзакцию БД; не полагаться на этот параметр как единственную линию защиты при ревью
  DTJ-243.
