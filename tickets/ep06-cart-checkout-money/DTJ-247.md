## Задача

`EscrowLedger.isBalanced()` (DTJ-240) — чистая функция, но её никто не вызывает автоматически без
этой джобы. Финансовое расхождение, обнаруженное через неделю, стоит дороже, чем обнаруженное на
следующее утро — это единственный автоматический страж целостности денежного журнала платформы,
работающий ежедневно и не пытающийся исправить расхождение сам (финансовые аномалии требуют
человеческого расследования).

## Технический контекст

`apps/worker/src/jobs/payout/escrow-reconciliation.job.ts` (BullMQ repeatable, cron
`RECONCILIATION_CRON`, ASSUMPTION `'0 3 * * *'` — 03:00 Asia/Dushanbe, после ночной 1С-синхронизации,
не одновременно с ней). Для каждого `order_id`, имеющего хотя бы одну запись `escrow_ledger` за
истекшие сутки — загружает записи через `EscrowLedgerRepository.findByOrderId` (DTJ-240), вызывает
`EscrowLedger.isBalanced(entries)`.

## Что сделать

1. `EscrowReconciliationJob` — cron-задача, запрос `SELECT DISTINCT order_id FROM escrow_ledger
   WHERE created_at >= NOW() - INTERVAL '1 day'`, для каждого — `isBalanced()`.
2. Given результат `false` (расхождение), Then:
   - Проверить, существует ли уже ОТКРЫТЫЙ `support_ticket(category='payment_issue')` для этого
     `order_id` за последние `RECONCILIATION_DEDUP_DAYS` (ASSUMPTION 7) — Given найден, Then НЕ
     создавать новый, только обновить `audit_log`-метаданные (счётчик повторных обнаружений,
     SRS-PAY-042). Given не найден, Then создать `support_tickets(channel='system_auto',
     category='payment_issue', is_escrow_blocking=false)`.
   - `audit_log(category='ledger_adjustment', metadata={orderId, discrepancyDiram})`.
   - Инкремент метрики `escrow_ledger_imbalance_count` (Prometheus-совместимый counter,
     `EscrowLedgerImbalanceMetric` — если общая инфраструктура метрик Prometheus ещё не подключена
     ни одним эпиком, реализовать минимальный in-memory counter с ENV-флагом экспорта, TODO на
     реальную интеграцию).
3. Джоба НЕ пытается исправить расхождение автоматически — только алертит (SRS-PAY-013).

## Критерии приёмки

1. **Given** `escrow_ledger`: `hold_created=10000`, `captured_to_pharmacy=9000`,
   `platform_fee_captured=800` (расхождение 200), **When** `EscrowReconciliationJob`, **Then**
   `support_tickets(category='payment_issue')` создан, `audit_log` содержит
   `discrepancyDiram=200`, `escrow_ledger_imbalance_count` инкрементирована.
2. **Given** расхождение уже зафиксировано вчера, тикет открыт, **When** джоба прогоняется снова,
   расхождение то же, **Then** новый `support_ticket` НЕ создаётся, существующий обновлён.
3. **Given** все заказы за сутки сбалансированы, **When** джоба прогоняется, **Then** ни один
   `support_ticket`/`audit_log`-запись не создаётся, метрика не инкрементируется.

## Риски и подводные камни

- **Метрика Prometheus** — вероятно требует общей инфраструктуры наблюдаемости (Charter §7),
  не гарантированной ни одним предыдущим тикетом. Деградация до in-memory counter с TODO —
  временное решение, не блокирует сдачу.
- Запрос `SELECT DISTINCT order_id ... WHERE created_at >= NOW() - INTERVAL '1 day'` на большом
  объёме данных без индекса на `escrow_ledger.created_at` может быть медленным — проверить, что
  индекс уже есть в базовой миграции DTJ-236 (`11-database-schema.md` §4 «Индексы»); если
  отсутствует — добавить в рамках этого тикета (правка того же владельца).
