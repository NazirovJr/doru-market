## Задача

Корзина не хранит снэпшот цены — это осознанное решение (снэпшот происходит только в
`order_items` на checkout, SRS-DOM-003). `GetCartUseCase` — единственное место, где эта живая
цена и живой остаток собираются в ответ, сгруппированный по аптекам, с честными предупреждениями,
если то, что лежит в корзине, больше недоступно в заявленном количестве.

## Технический контекст

`apps/api/src/modules/orders/application/cart/get-cart.use-case.ts` — оркестрирует
`CartRepository.findItemsByCartId` (DTJ-223) + `CatalogFacadePort.getMedicineSnapshot` (живая цена)
+ `AvailabilityCalculator.getAvailableQuantity` (DTJ-224, живой остаток за вычетом чужих холдов) +
`SplitCartByPharmacyUseCase` (DTJ-223, группировка). Сравнение цены «изменилась ли с последнего
просмотра» (SRS-ORD-011) выполняется ФРОНТЕНДОМ (клиент сравнивает с ранее полученным значением —
API-контракт лишь гарантирует актуальность), это НЕ ответственность backend use case.

## Что сделать

1. `GetCartUseCase.execute(cartId): CartViewDto`:
   - Загрузить строки `cart_items`.
   - Для каждой строки — живая цена/остаток через `CatalogFacadePort.getMedicineSnapshot`
     (JOIN с `pharmacy_inventory`, SRS-DOM-020 FEFO-цена — реализация снэпшота на стороне
     `catalog`-модуля, здесь только вызов порта).
   - Для каждой строки — `availableQuantity = AvailabilityCalculator.getAvailableQuantity(
     pharmacyId, medicineId, excludeCartItemId=cartItemId)`.
   - Given `cart_items.quantity > availableQuantity`, добавить в `meta.warnings:
     [{ cartItemId, type: 'insufficient_stock', availableQuantity }]` (SRS-ORD-012) — количество
     в строке НЕ обрезается автоматически.
   - Сгруппировать через `SplitCartByPharmacyUseCase` → `meta.pharmacyGroups`.
2. `CartViewDto`: `{ items: CartItemViewDto[], meta: { pharmacyGroups, warnings } }`, каждый
   `CartItemViewDto` включает `priceTjs` (текущая, не хранимая), `availableQuantity`.
3. Presentation-слой (DTJ-226) прокидывает `?extendHold=true` в `ExtendCartHoldUseCase` (DTJ-224)
   ДО вызова `GetCartUseCase` — сам `GetCartUseCase` не знает о query-параметрах HTTP.

## Критерии приёмки

1. **Given** цена товара в `pharmacy_inventory` изменилась после последнего добавления в корзину,
   **When** `GetCartUseCase`, **Then** ответ содержит АКТУАЛЬНУЮ цену, не ту, что была на момент
   `AddCartItemUseCase`.
2. **Given** `cart_items.quantity=5`, `availableQuantity=3` (после вычета чужих холдов), **When**
   `GetCartUseCase`, **Then** `meta.warnings` содержит `{ cartItemId, type: 'insufficient_stock',
   availableQuantity: 3 }`, строка в `items` по-прежнему содержит `quantity=5` (не обрезано).
3. **Given** корзина из 2 аптек, **When** `GetCartUseCase`, **Then** `meta.pharmacyGroups.length
   === 2`.
4. **Given** пустая корзина, **When** `GetCartUseCase`, **Then** `items: []`,
   `meta.pharmacyGroups: []`, `meta.warnings: []` (не `null`/`undefined`).

## Риски и подводные камни

- **Производительность при большой корзине.** `AvailabilityCalculator.getAvailableQuantity`
  вызывается на КАЖДУЮ строку — при корзине из 20+ позиций это 20 обращений к Redis
  последовательно, если не распараллелить. Обязательно `Promise.all` (C14), не `for...await`.
- Риск расхождения между `meta.pharmacyGroups[].subtotalDiram` (посчитан на момент группировки) и
  индивидуальными `items[].priceTjs`, если `SplitCartByPharmacyUseCase` и построение `items`
  используют РАЗНЫЕ вызовы `getMedicineSnapshot` (гонка чтения между двумя вызовами). Решение —
  один батч-вызов `getMedicineSnapshot` в начале `GetCartUseCase.execute()`, оба последующих шага
  переиспользуют один и тот же результат, не делают повторный запрос.
