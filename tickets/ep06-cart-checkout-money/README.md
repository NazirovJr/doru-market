## Область покрытия

**EP-09 (Корзина + Checkout)**: мультиаптечная корзина, мягкий TTL-резерв остатка, Rx-блокировка
на checkout, оркестрация оформления с частичным успехом по аптекам, отмена заказа.

**EP-10 (Оплата наличными + Escrow-ledger)**: `PaymentProvider`-порт и три реализации
(Mock/Alif/DC), эскроу-ledger двойной записи, вебхуки банка с категорическим запретом смены
статуса вне вебхука, payout-расписание с заморозкой по спору, B2B-биллинг комиссии за наличные,
таймауты неоплаченного/несобранного заказа.

**Явно ВНЕ периметра этого набора тикетов** (владеют другие тимлиды): EP-11 (возвраты, денежный и
складской аспект — `ReturnFinancialOutcomeResolver`, `order_returns`), EP-14 (споры —
`OrderDispute`, `resolve-*`-эндпоинты; здесь только контракт `PaymentsFacade.holdPayout` и
`AdjustLedgerUseCase`, которые EP-14 вызовет), EP-12 (терминал фармацевта), EP-13 (курьер,
`OrderDeliveredEvent`/`recordCash`).

## Центральное архитектурное решение эпика: D-25

`03-ARCHITECT-DECISIONS.md` §D-25 — наличный заказ (`payment_method='cash_courier'`) переходит
СИНХРОННО в статус **`confirmed`**, НЕ `paid_escrow`. `paid_escrow` достижим ИСКЛЮЧИТЕЛЬНО из
`pending_payment` по подписанному вебхуку (плюс одно явное административное исключение,
DTJ-246). Инвариант `status==='paid_escrow' ⟺ escrow_ledger непуст` (SRS-DOM-180/SRS-ORD-027a)
— обязателен к сквозному тестовому покрытию (DTJ-255). Это решение пронизывает ПОЛОВИНУ тикетов
этого набора (DTJ-221/222/230/242/243/244/245/253/254/255) — при ревью любого из них в первую
очередь проверять, не перепутаны ли ветки cash/non-cash.

## Известные внешние зависимости (не мои файлы, но блокируют часть тикетов)

1. **`0002_enums.sql` (владелец — предположительно EP-01)** должен содержать `'confirmed'` в
   `order_status` СРАЗУ при создании (канонический DDL `11-database-schema.md` уже это отражает).
   Проверить перед стартом DTJ-221/222 (см. риски DTJ-220).
2. **`tenant_settings.enabled_payment_methods` / `payment_window_minutes` / `use_split_billing`**
   (Group C, владелец — вероятно EP-01/EP-02) — вне периметра этого набора тикетов. DTJ-228/229/
   253 деградируют до жёстко закодированных R1-дефолтов, пока поля недоступны — follow-up на
   реальное подключение заводится отдельно, когда владелец Group C добавит миграцию.
3. **`Idempotency-Key`-интерсептор / таблица `idempotency_keys`** (SRS-API-009/010, общая
   конвенция, предположительно EP-01) — DTJ-227/231/233 деградируют до локального механизма
   поверх `orders.checkout_attempt_id`, если общий не готов.
4. **`OrderDeliveredEvent`** публикуется модулем `delivery` (EP-13, волна 9 — на 2 волны позже
   EP-10). DTJ-244 тестируется изолированно (прямой вызов `execute()`), физическая подписка на
   очередь — по готовности EP-13.
5. **`DomainExceptionFilter`/общий маппинг ошибок** (SRS-API-016, вероятно EP-01) — тикеты
   presentation-слоя (DTJ-226/233/248/252) деградируют до локального маппинга при отсутствии.
6. **`pharmacy_chains.is_active`-мутация из модуля `payments`** (DTJ-252) — пограничный случай
   межмодульного владения данными, рекомендуется порт `OnboardingFacadePort.suspendChain`,
   требует координации с владельцем `onboarding`-модуля.
