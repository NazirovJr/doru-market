## Задача

HTTP-граница checkout — последний рубеж перед клиентом: заголовок `Idempotency-Key`, композитный
envelope с частичным успехом, маппинг доменных ошибок в SCREAMING_SNAKE-коды. Ошибка здесь либо
пропускает двойной клик клиента напрямую в оркестрацию (нарушая SRS-API-009), либо теряет
структуру частичного успеха, превращая понятный композитный ответ в непонятный `500`.

## Технический контекст

`apps/api/src/modules/orders/presentation/checkout/**`. Конвенции — `12-api-conventions-auth-
tenancy.md` §1 (`SRS-API-001..016`): envelope `{ data, meta }`/`{ error: { code, message,
details? } }`, `Idempotency-Key` обязателен на этом эндпоинте (`400 IDEMPOTENCY_KEY_REQUIRED` при
отсутствии). Guard аутентификации (`Authorization: Bearer <JWT>`) — из общей инфраструктуры EP-01,
здесь только применение декоратора/guard'а. `SRS-ORD-020`: checkout БЕЗ аутентификации не
разрешён — гостевая корзина не может пройти оформление напрямую, только `customer`-роль.

## Что сделать

1. `POST /api/v1/orders` — роль `customer`, `Idempotency-Key` обязателен (`400
   IDEMPOTENCY_KEY_REQUIRED` при отсутствии, до вызова use case). Тело — `CreateOrderRequestDto`
   (Zod-схема, соответствует `CheckoutCommand` из DTJ-227). Вызов `CheckoutUseCase.execute(cmd)`.
   Ответ `200` (не `201` — композитный ответ может содержать 0 успешных заказов при частичном
   провале, `Charter §5`: единый конверт вместо `207 Multi-Status`):
   ```json
   { "data": { "orders": [...], "failedGroups": [...] }, "meta": { "excludedItems": [...] } }
   ```
2. `POST /api/v1/orders/:id/cancel { reason }` — роли `customer` (свой заказ)/`pharmacist`/
   `pharmacy_admin` (своя аптека, SRS-ORD-031) — вызов `CancelOrderUseCase` (DTJ-232). `200`.
3. `GET /api/v1/orders/:id/payment-status` — заглушка presentation-эндпоинта, делегирующая в
   `payments`-модуль через `PaymentInvoicePort`/будущий `PaymentsFacade` (реальная реализация —
   EP-10; здесь — контракт роута и структура ответа, `501 NOT_IMPLEMENTED` до готовности EP-10 с
   явным TODO, чтобы маршрут существовал с первого дня для фронтенда, DTJ-235).
4. Маппинг доменных/application ошибок → HTTP-коды (таблица в контроллере или общем
   `DomainExceptionFilter`, если уже существует, SRS-API-016):
   - `ControlledSubstanceNotOrderableError` → `422 CONTROLLED_SUBSTANCE_NOT_ORDERABLE`
   - `PrescriptionNotVerifiedError` (на уровне ГРУППЫ — не блокирует весь checkout, см. DTJ-230)
   - `CodForbiddenForRxError` → `422 COD_FORBIDDEN_FOR_RX`
   - `CodLimitExceededError` → `422 COD_LIMIT_EXCEEDED`
   - `PaymentMethodNotEnabledError` → `422 PAYMENT_METHOD_NOT_ENABLED`
   - `PriceOrStockChangedError` → `409 PRICE_OR_STOCK_CHANGED` (в `failedGroups`, не как HTTP-код
     всего ответа — только когда ВСЕ группы провалились этой ошибкой, тело всё равно `200`)
   - `NoOrderableItemsError` → `422 NO_ORDERABLE_ITEMS`
   - `ForbiddenCartAccessError`/`OrderPolicy.canCancel=false` → `403 FORBIDDEN`
   - Провайдерный таймаут (DTJ-227) → `503 PAYMENT_PROVIDER_UNAVAILABLE`
5. Добавить новые коды ошибок в `packages/contracts/src/errors.ts` (владелец EP-01, правило
   «Пересекающееся владение» п.3 — только добавление строк, не переписывание).

## Критерии приёмки

1. **Given** `POST /api/v1/orders` без заголовка `Idempotency-Key`, **Then** `400
   IDEMPOTENCY_KEY_REQUIRED`, `CheckoutUseCase` не вызван.
2. **Given** частичный успех (1 заказ создан, 1 группа провалена), **When** ответ собран, **Then**
   HTTP-статус `200`, тело содержит непустые `data.orders` И непустой `data.failedGroups`
   одновременно.
3. **Given** `POST /api/v1/orders/:id/cancel` от `customer`, не владеющего заказом, **Then**
   `403 FORBIDDEN`.
4. **Given** `PriceOrStockChangedError` для ВСЕХ групп запроса, **Then** HTTP-статус ответа
   ВСЁ РАВНО `200` (не `409` на уровне транспорта) — ошибка живёт внутри `failedGroups` каждой
   группы, транспортный код `409` не используется для этого сценария на уровне всего ответа.

  СЕРВЕРНУЮ половину защиты (идемпотентность), клиентская половина (кнопка → `loading`) — тикет
  DTJ-235.
