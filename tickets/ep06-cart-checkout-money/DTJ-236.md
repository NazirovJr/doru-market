## Задача

Физическое основание всего EP-10: таблицы `escrow_ledger`/`payout_schedule`/`platform_fee`/
`payment_operations` строго по DDL «Группы E», каркас модуля `payments` по Правилу Зависимостей, и
порт к модулю `orders` — единственный разрешённый способ, которым `payments` читает/меняет заказ
(вебхук переводит `order.status` в `paid_escrow`, но НЕ имеет права импортировать
`modules/orders/domain` напрямую). Без этого тикета ни один из следующих 19 тикетов EP-10 не может
начаться.

## Технический контекст

`11-database-schema.md` §«Миграции» фиксирует `0009_payments.sql` (9-й в топологическом порядке,
ПОСЛЕ `0008_orders_cart.sql` — `escrow_ledger`/`payout_schedule` ссылаются на `orders.id`
`ON DELETE CASCADE`/`RESTRICT`, физическая зависимость от существования таблицы `orders`). DDL —
«Группа E» (`11-database-schema.md` строки 812–919): `escrow_ledger`, `payout_schedule`,
`platform_fee`, `payment_operations`, все `CONSTRAINT chk_*`/`COMMENT ON`. `payout_schedule.
held_by_dispute_id` — БЕЗ `REFERENCES` на этом шаге (FK на `order_disputes` добавляется EP-11/14
своей миграцией `0010_returns_disputes.sql` через `ALTER TABLE`, см. прецедент в `tickets/
ep07-returns-disputes/DTJ-270.md`).

Модуль — стандартная структура `domain/ application/ infrastructure/ presentation/` + `index.ts`
(`02` §1.2). `tickets/00-EPICS.md` закрепляет за EP-10 `apps/api/src/modules/payments/**` целиком
и `apps/worker/src/jobs/{escrow-timeouts,payout}/**`.

## Что сделать

1. Создать `apps/api/migrations/0009_payments.sql`, воспроизводящий 1:1 DDL «Группы E»
   (`11-database-schema.md` строки 812–919). Проверить перед мержем реальный следующий свободный
   номер файла в `apps/api/migrations/` — топологический порядок (после `0008_orders_cart.sql`,
   владелец DTJ-220 EP-09) важнее буквального номера `0009`, если фактическая нумерация к моменту
   реализации сдвинулась.
2. Проверить, что `0008_orders_cart.sql` (DTJ-220) уже смержена ПЕРЕД этой миграцией — `escrow_
   ledger.order_id REFERENCES orders(id)` физически требует существования таблицы `orders`.
   Если DTJ-220 ещё не готова — это блокер, не обходить его созданием `orders`-заглушки здесь.
3. Добавить Drizzle-схему `apps/api/src/db/schema/payments.ts` (`escrowLedger`,
   `payoutSchedule`, `platformFee`, `paymentOperations`).
4. Создать `apps/api/src/modules/payments/payments.module.ts` и `.../index.ts` — публичный фасад,
   на этом шаге экспортирующий только типы и DI-токен `PAYMENTS_FACADE` (реализация — по мере
   готовности use case'ов, начиная с DTJ-243/245).
5. Объявить порты к чужим модулям:
   - `orders-facade.port.ts` — `PaymentsOrdersPort.markPaidEscrow(orderId, txId, paidAt,
     unitOfWork)`, `getOrderById(orderId)`, `cancel(orderId, reason, actor, unitOfWork)` — тонкая
     обёртка над реальным `OrdersFacade` (EP-09, DTJ-222), адаптер связывается на этапе
     DI-интеграции (см. «Риски»).
   - `tenancy-facade.port.ts` — `PaymentsTenancyPort.getTenantSettings(tenantId)` (для
     `hold_period_days`, `enabledPaymentMethods` и т.п., используется DTJ-249/253).
6. Создать `packages/contracts/src/payments.ts` (заготовки `EscrowLedgerEntryDto`,
   `PayoutScheduleDto`, `PaymentOperationDto`).
7. Добавить ОДНУ строку экспорта в `packages/contracts/src/index.ts`.
8. Зарегистрировать модуль `payments` в `apps/api/src/app.module.ts` (корневой композиционный
   модуль — правка одной строки импорта, следуя прецеденту «Пересекающееся владение» п.1
   `tickets/00-EPICS.md`: первый эпик, добравшийся до файла, владеет каркасом, остальные
   добавляют строку).
9. Прогнать `pnpm arch:check`.

## Критерии приёмки

1. **Given** применена миграция `0009_payments.sql` к БД после `0001`..`0008`, **When**
   `\d escrow_ledger`/`\d payout_schedule`/`\d platform_fee`/`\d payment_operations`, **Then**
   структура и все constraint'ы/комментарии совпадают 1:1 с `11-database-schema.md`.
2. **Given** миграция `0008_orders_cart.sql` НЕ применена, **When** пытаются применить
   `0009_payments.sql`, **Then** миграция падает на `FOREIGN KEY` (ожидаемое поведение,
   подтверждает физическую зависимость от EP-09 — не дефект, тестируется явно как негативный
   сценарий).
3. **Given** модуль `payments` подключён в `AppModule`, **When** `pnpm --filter api build`, **Then**
   сборка без циклических импортов.
4. **Given** попытка импортировать `modules/orders/domain/*` напрямую из
   `modules/payments/application/*`, **When** `pnpm arch:check`, **Then** нарушение отклонено.

## Риски и подводные камни

- **Топологическая зависимость от EP-09 (DTJ-220).** Волна 7 (EP-10) стартует ПОСЛЕ волны 6
  (EP-09, `tickets/00-EPICS.md`), поэтому на практике `orders`-миграция должна быть готова —
  фактический порядок мержа отдельных PR внутри волны не гарантирован автоматически, проверить
  перед стартом этого тикета.
- **`orders-facade.port.ts` — контракт с реализацией `OrdersFacade`, которую в итоге предоставляет
  DTJ-222 (EP-09).** Порт объявляется здесь как ИНТЕРФЕЙС payments-модуля (обёртка над реальным
  фасадом orders — не прямой импорт, а адаптер `infrastructure/adapters/orders-facade.adapter.ts`,
  который будет реализован конкретными use case-тикетами по мере надобности, начиная с DTJ-243).
  Расхождение сигнатур с фактическим `OrdersFacade` — межэпиковый риск, сверять при интеграции.
- **`app.module.ts` — общий файл, растущий с каждой волной.** Если EP-09 (DTJ-220/222) тоже успел
  зарегистрировать `OrdersModule` первым — это ожидаемо (EP-09 стартует раньше), правка здесь —
  только добавление своей строки, rebase решает конфликт при параллельном мерже.
- Файл `apps/api/src/modules/payments/payments.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/src/modules/payments/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `packages/contracts/src/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
