## Задача

Комиссия платформы — единственный источник дохода R1 (наличные заказы не проходят через эскроу,
только через эту комиссию, снэпшотированную здесь + собранную позже B2B-циклом EP-10). Ошибка
округления или неверная привязка ставки к позиции — это либо недополученный доход платформы, либо
завышенная комиссия, списанная с аптеки без основания. Этот тикет — единственное место, где
рассчитывается `total_amount_tjs` и снэпшотятся `commission_bps`/`platform_fee_diram` на каждую
позицию заказа.

## Технический контекст

`CalculateOrderCostService` вызывается из `CheckoutUseCase` (DTJ-227) шаг 4.a-e (внутри транзакции
группы, ДО `Order.create()` — результат передаётся в `cmd` конструктора, сам расчёт домену не
принадлежит, только валидация уже посчитанного, DTJ-221 п.4). Формула — `21-module-...md`
§2.2 (SRS-ORD-021/022): `items_total = Σ(unit_price × quantity)`, `platform_fee_diram` — банковское
округление НА КАЖДУЮ позицию (не на сумму), `delivery_fee_tjs` — через `DeliveryFacadePort.
calculateFee(pharmacyGeoPoint, deliveryGeoPoint)` (порт уже в DTJ-220), `total_amount_tjs =
items_total + delivery_fee_tjs`. Комиссия считается ИСКЛЮЧИТЕЛЬНО от `items_total`
(SRS-DOM-009) — сигнатура сервиса не принимает `delivery_fee` как параметр расчёта комиссии.

`billing_strategy` (`'single_invoice' | 'split_items_delivery'`, SRS-RET-009) — снэпшотится ЗДЕСЬ,
на checkout, чтобы возврат (владелец — EP-11, ВНЕ периметра этого тикета) знал, по какой стратегии
проводилась оплата, даже если тенант позже поменяет флаг. Поле `orders.billing_strategy` —
НОВОЕ, отсутствует в базовом DDL Group D (`11-database-schema.md`) — требует эволюционной миграции
(см. «Что сделать» п.1).

## Что сделать

1. Создать `apps/api/migrations/0020_orders_payments_extensions.sql` (эволюционная миграция ПОСЛЕ
   baseline, по аналогии с `0019_order_status_add_confirmed.sql` из `11-database-schema.md`
   §«Миграции»): `ALTER TABLE orders ADD COLUMN billing_strategy VARCHAR(20) NOT NULL DEFAULT
   'single_invoice'` (проверить `CHECK (billing_strategy IN ('single_invoice',
   'split_items_delivery'))`). **Это поле — ЕДИНСТВЕННОЕ из «Дополнений к схеме БД»
   `21-module-orders-payments-escrow.md`, которое трогает этот тикет** (владение Group D — моё);
   остальные поля из того же раздела документа (`payment_operations.billing_component`,
   `tenant_settings.*`) — вне периметра, см. DTJ-242/244 и «Риски». Эта миграция **требует
   подтверждения архитектора (ADR)** согласно явной пометке документа-источника перед мержем в
   основную ветку — до получения подтверждения тикет может быть реализован и покрыт тестами на
   feature-ветке, но не смержен в `main`.
2. `CalculateOrderCostService.calculate(pharmacyId, items, deliveryGeoPoint,
   tenantId): OrderCostResult` — резолвит `commission_bps` через `TenancyFacadePort.
   resolveCommissionRate(tenantId, chainId, category)` НА КАЖДУЮ позицию (категория — из
   `CatalogFacadePort.getMedicineSnapshot`, `rx|otc|parapharma`), считает `platform_fee_diram`
   банковским округлением (`Math.round` half-to-even ИЛИ явная реализация banker's rounding —
   зафиксировать конкретный алгоритм в JSDoc, не оставлять на усмотрение `Math.round` JS
   стандартного, который НЕ banker's rounding).
3. `ResolveBillingStrategyService.resolve(tenantId, paymentMethod): BillingStrategy` — Given
   `paymentMethod='cash_courier'` → всегда `'single_invoice'` (раздельный биллинг бессмыслен без
   провайдера); Given non-cash И `tenantSettings.useSplitBilling` (поле — часть отдельной,
   НЕ-моей эволюционной миграции на `tenant_settings`, см. «Риски») → `'split_items_delivery'`,
   иначе `'single_invoice'` (SRS-DOM-162, SRS-RET-006/009). Given `useSplitBilling` пока
   недоступно (миграция ещё не смержена другим владельцем) — временный жёстко закодированный
   дефолт `'single_invoice'` с TODO и явной ссылкой на блокирующую миграцию.
4. Расширить `Drizzle`-схему `apps/api/src/db/schema/orders.ts` (DTJ-220, тот же владелец) полем
   `billingStrategy`.

## Критерии приёмки

1. **Given** 3 позиции с `commission_bps=500/800/1200` соответственно, **When**
   `CalculateOrderCostService.calculate`, **Then** каждая позиция несёт СВОЙ `platform_fee_diram`,
   `Σ(platform_fee_diram)` НЕ обязана точно равняться комиссии от суммы (допустима погрешность
   ≤1 дирам на позицию, SRS-ORD-022).
2. **Given** `delivery_fee_tjs=15.00`, **When** расчёт комиссии, **Then** `delivery_fee` НЕ влияет
   ни на одно значение `platform_fee_diram` (проверка через мутацию `delivery_fee` в тесте —
   комиссия неизменна).
3. **Given** `paymentMethod='cash_courier'`, **When** `ResolveBillingStrategyService.resolve`,
   **Then** всегда `'single_invoice'`, независимо от `tenantSettings.useSplitBilling`.
4. **Given** `total_amount_tjs` пересчитан сервером, **When** сравнивается с суммой, переданной
   клиентом (если была), **Then** сервер игнорирует клиентское значение полностью — используется
   только для последующей проверки дрейфа (DTJ-231), не для самого расчёта.

## Риски и подводные камни

- **Требует ADR перед мержем миграции** — явно помечено источником (`21-module-...md`
  §«Дополнения к схеме БД»). Не блокирует РАЗРАБОТКУ и тестирование этого тикета, блокирует ТОЛЬКО
  финальный мерж в `main` без подтверждения — эскалировать архитектору заранее, не в последний
  момент перед сдачей.
- **`tenant_settings.use_split_billing` — НЕ в периметре владения этого тикета** (Group C,
  вероятный владелец — EP-01/EP-02). Пока поле недоступно — используется жёстко закодированный
  дефолт `'single_invoice'` (см. «Что сделать» п.3). Как только владелец Group C добавит поле —
  завести follow-up тикет на подключение реального чтения `tenantSettings.useSplitBilling` (вне
  диапазона DTJ-220..269, эскалировать тимлиду проекта на распределение).
- **Место резолвинга `commission_bps` (`platform_fee` таблица, специфичность
  `(tenant,chain,category) > ... > global`)** — таблица `platform_fee` уже в базовой схеме (Group
  E, владелец EP-10). Порт `TenancyFacadePort.resolveCommissionRate` — временное имя; если EP-10
  спроектирует резолвинг как часть `payments`-модуля, а не `tenancy`, порт нужно переименовать/
  перепривязать при интеграции (координация с EP-10 при пересечении с DTJ-241/245).
