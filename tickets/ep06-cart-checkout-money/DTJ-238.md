## Задача

`MockBankProvider` — не заглушка «для галочки»: это ЕДИНСТВЕННЫЙ провайдер, который реально
работает в R1-проде и через который E2E-сценарии (CUJ-2, тестовые non-cash тенанты) проходят
настоящий код-путь HMAC-подписи, идемпотентности и вебхука — Charter DoD п.7 «продукт работает без
единого внешнего API-ключа» проверяется буквально этим адаптером.

## Технический контекст

`infrastructure/adapters/mock-bank.provider.ts` реализует `PaymentProvider` (DTJ-237). Ключевое
архитектурное требование (SRS-PAY-005): HMAC-подпись мока использует ТОТ ЖЕ алгоритм/код-путь
верификации, что и реальные адаптеры (DTJ-239/244) — полиморфизм по `providerName`, НЕ отдельная
ветка `if (isMock)` в обработчике вебхука. `MOCK_BANK_AUTO_PAY_DELAY_MS` (ASSUMPTION 2000, ENV) —
BullMQ delayed job, сам отправляет HTTP на `POST /api/v1/payments/webhook` этого же инстанса API.

## Что сделать

1. `MockBankProvider.capabilities()`: `{ providerName: 'mock_bank', supportsHoldCapture: false,
   supportsPartialRefund: false, maxInvoiceValidityMinutes: 15 }` (намеренно отражает
   реалистичные ограничения Alif/DC — не оптимистичный случай).
2. `createInvoice(cmd)`: создаёт `payment_operations(operation_type='create_bill',
   status='pending', idempotency_key=cmd.idempotencyKey, provider='mock_bank')`, возвращает
   `providerRef='mock_inv_'+uuid()`, `qrPayload='mock://pay/'+providerRef`.
3. `MockBankAutoPayJob` (`apps/worker/src/jobs/escrow-timeouts/mock-bank-auto-pay.job.ts`, BullMQ
   delayed): Given `MOCK_BANK_AUTO_PAY_DELAY_MS > 0` — планируется на это время после
   `createInvoice`, отправляет `POST /api/v1/payments/webhook` с `X-Payment-Provider: mock_bank`,
   телом, подписанным ТЕМ ЖЕ HMAC-секретом (`MOCK_BANK_WEBHOOK_SECRET`, ENV, генерируется при
   первом запуске dev-окружения). Given `MOCK_BANK_AUTO_PAY_DELAY_MS=0` — джоба не планируется
   вовсе (нужно тестам, которые проверяют именно состояние `pending_payment`).
4. `POST /api/v1/dev/mock-bank/simulate-payment { providerRef, outcome: 'paid'|'failed' }` —
   доступен ТОЛЬКО если `PAYMENT_DRIVER=mock_bank` И `NODE_ENV !== 'production'` (guard на уровне
   контроллера, явная проверка ENV в каждом обработчике, не полагаться только на
   роутинг/DI-условность) — триггерит тот же вебхук вручную, для управляемых Playwright-сценариев.
5. `MockBankWebhookVerifierAdapter` реализует `BankWebhookVerifierPort` (DTJ-237) — HMAC-SHA256 по
   `rawBody` с `MOCK_BANK_WEBHOOK_SECRET`.
6. `refund()`: синхронно успешен, эмулирует `refund_confirmed`-вебхук с тем же
   `MOCK_BANK_AUTO_PAY_DELAY_MS`. `partialRefund()`: всегда `Err(NotSupportedByProviderError)`
   (`capabilities().supportsPartialRefund === false`).
7. Зарегистрировать `MockBankProvider` в `payments.module.ts` через `PAYMENT_DRIVER=mock_bank`
   ветку DI (`{ provide: PAYMENT_PROVIDER_TOKEN, useClass: MockBankProvider }`) — полное
   ветвление по `PAYMENT_DRIVER` (включая Alif/DC) завершает DTJ-239.

## Критерии приёмки

1. **Given** `createInvoice()` вызван, `MOCK_BANK_AUTO_PAY_DELAY_MS=2000`, **When** проходит
   2.5 секунды, **Then** на `POST /api/v1/payments/webhook` этого же инстанса приходит подписанный
   запрос с `type='payment_confirmed'`.
2. **Given** `MOCK_BANK_AUTO_PAY_DELAY_MS=0`, **When** `createInvoice()`, **Then** авто-вебхук НЕ
   планируется — заказ остаётся `pending_payment` до явного вызова dev-эндпоинта.
3. **Given** `NODE_ENV=production`, **When** `POST /api/v1/dev/mock-bank/simulate-payment`,
   **Then** `404`/`403` (эндпоинт недоступен — конкретный код зависит от общего роутинг-конвеншена,
   зафиксировать явным тестом).
4. **Given** `partialRefund()` вызван, **Then** `Err(NotSupportedByProviderError)`.
5. **Given** подпись HMAC для mock-вебхука верифицируется, **When** проверяется код верификатора,
   **Then** используется ТОТ ЖЕ метод/класс верификации, что зарезервирован для Alif/DC (полиморфизм
   по `providerName`, не отдельный `if`-блок — проверяется структурно на ревью).

## Тест-план

- Unit: `MockBankProvider.createInvoice/refund/partialRefund` — на моке репозитория
  `payment_operations`.
- Интеграционный (BullMQ + Testcontainers Redis): `MockBankAutoPayJob` — планирование, задержка,
  реальная отправка HTTP на локальный тестовый сервер (supertest-инстанс приложения).
- Интеграционный: dev-эндпоинт — доступен/недоступен в зависимости от `NODE_ENV`/`PAYMENT_DRIVER`.
- Покрытие `infrastructure/` ≥ 70% (не `domain`/`application`, порог 90% неприменим).

## Риски и подводные камни

- **Обработчик `POST /api/v1/payments/webhook` реализуется отдельным тикетом (DTJ-243).** Этот
  тикет создаёт КЛИЕНТА, который на него шлёт запросы (джоба + dev-эндпоинт) — до готовности
  DTJ-243 интеграционный тест п.1 использует локальный тестовый HTTP-сервер-заглушку с той же
  сигнатурой, не реальный обработчик; переключить на реальный при интеграции обоих тикетов.
- Самоссылающийся HTTP-вызов (worker → `POST` на API того же деплоя) требует, чтобы `apps/worker`
  знал базовый URL `apps/api` — использовать существующую ENV-конвенцию (`API_INTERNAL_URL` или
  аналог), если её ещё нет — завести здесь как ASSUMPTION с явной пометкой.
