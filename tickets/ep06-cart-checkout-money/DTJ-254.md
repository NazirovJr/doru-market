## Задача

Аптека не приняла заказ в сборку за `pickup_sla + buffer` (дефолт 7+5=12 минут) — товар нужно
вернуть в оборот другим покупателям. Ровно ОДИН таймер, ровно ОДНО условие, но денежный эффект
расходится по `payment_method`: non-cash — полный рефанд (деньги были собраны через эскроу),
cash — НИЧЕГО (наличные никогда не собирались курьером). Перепутать эти две ветки — либо
безосновательный вызов рефанда на пустую транзакцию (упадёт), либо украденные у клиента деньги.

## Технический контекст

Один и тот же таймер/условие (`pickup_sla + pickup_sla_buffer` истёк без принятия фармацевтом) —
ДВА исходных статуса (`paid_escrow` для non-cash, `confirmed` для cash, D-25), симметричные
переходы SRS-DOM-092/179. Использует `OrderAutoCancelledEvent` — эмитируется для ОБОИХ переходов с
полем `fromStatus`, различающим ветку (SRS-ORD-036).

## Что сделать

1. `PickupSlaTimeoutJob` (BullMQ repeatable, интервал — ASSUMPTION каждые 2 минуты, короче
   минимального `pickup_sla_minutes`): `SELECT * FROM orders WHERE status IN ('paid_escrow',
   'confirmed') AND processing_started_at IS NULL AND created_at + (tenantSettings.
   pickupSlaMinutes + tenantSettings.pickupSlaBufferMinutes || ' minutes')::interval <= NOW()`
   (оба поля `pickup_sla_minutes`/`pickup_sla_buffer_minutes` УЖЕ в базовой схеме
   `tenant_settings`, не требуют новой миграции).
2. Для каждой найденной строки:
   - `PaymentsOrdersPort.cancel(orderId, reason='pickup_sla_timeout', actor=SYSTEM)` (DTJ-236
     порт → домен DTJ-222 `order.cancel()`).
   - Given `fromStatus === 'paid_escrow'` (non-cash) → `RefundOrderUseCase.execute(orderId,
     reason='pickup_sla_timeout')` (DTJ-245) — полный рефанд.
   - Given `fromStatus === 'confirmed'` (cash, D-25) → `RefundOrderUseCase` НЕ вызывается вовсе
     (не просто «маловероятный путь» — `RefundOrderUseCase` САМ содержит NOOP-проверку на
     `cash_courier` первым шагом, DTJ-245, поэтому вызов был бы БЕЗОПАСНЫМ NOOP даже если бы этот
     тикет ошибочно его вызвал — но явно НЕ вызывать здесь для ясности кода и минимизации сетевых/
     БД-обращений, SRS-ORD-036).
   - `InventoryFacadePort.releaseStock(items)` — ВСЕГДА, обе ветки.
   - Эмитировать `OrderAutoCancelledEvent(orderId, fromStatus, reason='pickup_sla_timeout')`.

## Критерии приёмки

1. **Given** заказ `paid_escrow`, `pickup_sla+buffer` истёк, фармацевт не принял, **When**
   `PickupSlaTimeoutJob`, **Then** `status='cancelled'`, `RefundOrderUseCase` вызван ровно один
   раз, `escrow_ledger` содержит `refunded_to_customer`.
2. **Given** заказ `confirmed` (cash), тот же таймаут, **When** джоба, **Then**
   `status='cancelled'`, `cancel_reason='pickup_sla_timeout'`; `RefundOrderUseCase`/
   `PaymentProvider.refund` НЕ вызваны ни разу (счётчик мока = 0, TC-ORD-001b буквально);
   `escrow_ledger` остаётся пустым; `InventoryFacadePort.releaseStock` вызван.
3. **Given** заказ `processing` (фармацевт УЖЕ принял, независимо от способа оплаты), **When**
   джоба прогоняется, **Then** заказ НЕ затронут (`processing_started_at IS NOT NULL` исключает
   его из выборки).
4. **Given** оба типа заказов (cash и non-cash) одновременно просрочены, **When** джоба
   прогоняется, **Then** оба переходят в `cancelled`, каждый — с корректным для своей ветки
   денежным эффектом (не перепутаны).

  этот тикет полагается на неё как на вторую линию, но НЕ заменяет ею первую линию защиты
  (явное неисполнение вызова для `confirmed`-ветки, см. «Что сделать» — defense in depth,
  не единственная точка защиты).
