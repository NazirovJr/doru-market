## Задача

`PaymentProvider` — единственная точка, через которую ЛЮБОЙ код платформы разговаривает с банком
(реальным или моком) — Provider Pattern из устава, частный случай портов и адаптеров
(`02` §1.3). Ошибка в этом контракте размножается на все три адаптера (Mock, Alif, DC Next) сразу
и на все use case'ы, которые от него зависят. Этот тикет — только контракт, без единой строки
инфраструктуры.

## Технический контекст

`application/ports/payment-provider.port.ts` — интерфейс из
`21-module-orders-payments-escrow.md` §3.1 буквально. `capabilities()` — синхронный метод, не
`Promise` (значения известны на этапе конфигурации DI, не требуют сетевого вызова).
`getStatus()` — ИСКЛЮЧИТЕЛЬНО для реконсиляции/диагностики (SRS-PAY-002), категорический запрет
использовать его для смены `order.status` — зафиксировать этот запрет прямо в JSDoc интерфейса
(C11: комментарий объясняет «почему», не «что» — здесь «почему нельзя» критично важнее сигнатуры).

## Что сделать

1. Типы: `PaymentProviderCapabilities`, `CreateInvoiceCommand`, `InvoiceRef`,
   `PaymentStatusSnapshot`, `RefundRef` — 1:1 по `21-module-orders-payments-escrow.md` §3.1
   (поля, типы `bigint` для дирамов, `'TJS'` как единственная валюта MVP).
2. `PaymentProvider` interface: `capabilities()`, `createInvoice(cmd)`, `getStatus(providerRef)`,
   `refund(providerRef, idempotencyKey)`, `partialRefund(providerRef, amountDiram,
   idempotencyKey)` (опционально бросает `NotSupportedByProviderError`, если
   `!capabilities().supportsPartialRefund` — задокументировать в JSDoc, не как рантайм-логика
   этого тикета), опциональные `capturePreauth?`/`voidPreauth?`.
3. `BankWebhookVerifierPort`: `verify(rawBody: Buffer, headers: Record<string,string>):
   Result<VerifiedWebhookPayload, InvalidWebhookSignatureError>` — резолвится по
   `X-Payment-Provider` заголовку (DI-биндинг по ключу провайдера — детали в DTJ-239).
   `VerifiedWebhookPayload` — 1:1 по §5.2 (`bankEventId, providerRef, type, amountDiram,
   occurredAt`).
4. `PaymentProviderError` — базовый класс доменных ошибок провайдера (не `HttpException`,
   `02` §2.5); `NotSupportedByProviderError extends PaymentProviderError`.
5. DI-токен `PAYMENT_PROVIDER_TOKEN` (Symbol) для биндинга конкретного адаптера в
   `payments.module.ts` (биндинг — DTJ-238, здесь только объявление токена рядом с портом).

## Критерии приёмки

1. **Given** любой класс реализует `PaymentProvider`, **When** `tsc --noEmit`, **Then**
   компилятор требует реализации ВСЕХ обязательных методов (`capabilities`, `createInvoice`,
   `getStatus`, `refund`, `partialRefund`) — опциональные `capturePreauth`/`voidPreauth` можно
   опустить.
2. **Given** `amountDiram` передан как `number` в фикстуре теста типов, **When** `tsc --noEmit`,
   **Then** ошибка компиляции (поле типизировано `bigint`, не `number`, SRS-PAY-001).
3. **Given** JSDoc интерфейса `PaymentProvider.getStatus`, **When** ревью, **Then** явно
   присутствует предупреждение о категорическом запрете использовать метод для смены
   `order.status` (SRS-PAY-002).
