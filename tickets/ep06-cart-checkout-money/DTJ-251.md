## Задача

Поскольку `cash_courier` не порождает `escrow_ledger`/`payout_schedule` (D-25, DTJ-244 NOOP-ветка),
это ЕДИНСТВЕННЫЙ реальный источник дохода платформы за наличные заказы в R1-проде (Pivot §3.1
R1-8) — вся выручка от подавляющего большинства заказов R1 (банковские методы выключены для
реальных пользователей) проходит через ЭТОТ B2B-цикл, а не через ledger. Ошибка агрегации здесь —
прямая потеря дохода платформы, невидимая ни в одном другом отчёте.

## Технический контекст

`CashCommissionAggregationJob` (BullMQ repeatable, ежедневно): для каждой `pharmacy_chains`,
имеющей хотя бы один `orders(payment_method='cash_courier', status='delivered', deleted_at IS
NULL)` за истёкшие сутки, upsert строку `platform_billing_invoices(invoice_type=
'cash_courier_commission', status='draft')` за ТЕКУЩИЙ расчётный период (неделя, `period_start` =
начало текущей недели), добавляя `Σ(order_items.platform_fee_diram)` этих заказов к
`subtotal_diram`. `PlatformBillingInvoiceRepository` — тонкий Drizzle-адаптер над таблицей из
базовой схемы DTJ-236.

## Что сделать

1. `PlatformBillingInvoiceRepository`: `findDraftForPeriod(chainId, periodStart)`,
   `upsertDraft(chainId, periodStart, periodEnd, additionalSubtotalDiram)`,
   `issue(invoiceId)` (переход `draft → issued`).
2. `CashCommissionAggregationJob`:
   - `SELECT chain_id, SUM(oi.platform_fee_diram) FROM orders o JOIN order_items oi ON
     oi.order_id=o.id JOIN pharmacies p ON p.id=o.pharmacy_id WHERE o.payment_method=
     'cash_courier' AND o.status='delivered' AND o.deleted_at IS NULL AND o.delivered_at >=
     <вчера 00:00> AND o.delivered_at < <сегодня 00:00> GROUP BY p.chain_id`.
   - Для каждой строки — `upsertDraft(chainId, periodStart=<начало текущей недели, Asia/
     Dushanbe>, periodEnd=<конец недели>, additionalSubtotalDiram)`.
   - Идемпотентность на повторный прогон за ТУ ЖЕ дату — джоба обрабатывает диапазон `[вчера,
     сегодня)` детерминированно; повторный прогон в тот же день суммирует ЕЩЁ РАЗ, если не
     защититься — добавить `processed_events`-подобную защиту ключом
     `(consumer='cash-commission-aggregation', event_id=hash(chainId+date))` ИЛИ явный
     `inventory_sync_batches`-подобный журнал прогонов (выбрать более простой вариант на этапе
     реализации — минимально достаточная защита от двойного суммирования).
3. Отдельная еженедельная задача (тот же файл job'а, второй cron ИЛИ проверка условия внутри той
   же ежедневной джобы «сегодня воскресенье 23:59 Asia/Dushanbe») — переход `draft → issued`
   для ВСЕХ черновиков текущей недели: `issued_at=NOW()`, `due_at = issued_at + 7 дней`,
   `vat_diram = subtotal_diram × 0.14` (НДС 14%, REQ-MON-9, помечено ASSUMPTION до подтверждения
   налоговым консультантом — JSDoc-комментарий с этой пометкой обязателен), `total_diram =
   subtotal_diram + vat_diram`.

## Критерии приёмки

1. **Given** 5 `cash_courier`-заказов `delivered` за неделю у одной сети, **When**
   `CashCommissionAggregationJob` прогоняется ежедневно, затем наступает конец недели, **Then**
   `platform_billing_invoices(invoice_type='cash_courier_commission')` содержит `subtotal_diram =
   Σ(platform_fee_diram)` этих 5 заказов, переходит `draft → issued` в конце периода.
2. **Given** джоба прогоняется дважды за один и тот же день (ретрай/дублирующий запуск), **When**
   выполняется, **Then** `subtotal_diram` НЕ удваивается (идемпотентность подтверждена).
3. **Given** `subtotal_diram=100000`, **When** переход `draft → issued`, **Then**
   `vat_diram=14000`, `total_diram=114000`, `due_at = issued_at + 7 дней`.
4. **Given** сеть без единого `cash_courier`-заказа за сутки, **When** джоба прогоняется, **Then**
   ни одна строка `platform_billing_invoices` для этой сети не создаётся/не изменяется.

## Риски и подводные камни

- **Ставка НДС 14% помечена в источнике как требующая подтверждения налоговым консультантом** —
  реализовать как конфигурируемую константу (не хардкод буквально `0.14` в формуле без возможности
  изменить), чтобы будущее уточнение не требовало правки логики, только значения.
- **`period_start`/расчётная неделя в Asia/Dushanbe** — использовать библиотеку часовых поясов
  (уже должна быть в зависимостях проекта, `01-TECH-BASELINE.md` не называет конкретную — 
  использовать ту же, что уже применяется другими джобами с TZ-логикой, например
  `EscrowReconciliationJob` DTJ-247, для консистентности расчёта «конца дня/недели» по всему
  модулю).
