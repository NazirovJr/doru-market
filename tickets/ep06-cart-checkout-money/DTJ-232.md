## Задача

Единый вход отмены заказа для клиента и персонала аптеки. Ветвление по `payment_method` здесь —
буквально сердце D-25 после checkout: для `cash_courier` отмена НИКОГДА не вызывает рефанд (нечего
возвращать — наличные ещё не собраны курьером), для `paid_escrow`/`processing` (non-cash) —
ВСЕГДА полный рефанд. Спутать эти две ветки — либо украсть у клиента деньги, которые он не платил
(ложный вызов рефанда на нулевую транзакцию упадёт), либо не вернуть деньги, которые реально
списаны.

## Технический контекст

`apps/api/src/modules/orders/application/order-lifecycle/**` — НОВАЯ подпапка внутри `orders/
application`, вне подпапок `cart`/`checkout` (владение которыми зарезервировано DTJ-223/227 по
`tickets/00-EPICS.md`) — по прецеденту «каждый эпик добавляет свою подпапку в общий модуль»
(тот же паттерн, что EP-12 добавит `orders/presentation/pharmacy-terminal/**`). `CancelOrderUseCase`
вызывает `OrderPolicy.canCancel` (DTJ-222) и `order.cancel(reason, actor)` (DTJ-222) через
`OrdersFacade`, затем ветвится: non-cash в `paid_escrow`/`processing` → `RefundFacadePort.
refundFull(orderId)` (порт, реализация — адаптер модуля `payments`, DTJ-245 EP-10, забинживается
позже, тот же паттерн отложенного DI-биндинга, что `PaymentInvoicePort` в DTJ-220/242); cash ИЛИ
non-cash в `pending_payment` → рефанд НЕ вызывается вовсе. `InventoryFacadePort.releaseStock`
(DTJ-220) — вызывается ВСЕГДА, независимо от ветки оплаты.

## Что сделать

1. `RefundFacadePort` (`application/ports/refund-facade.port.ts`): `refundFull(orderId,
   reason): Promise<Result<void, RefundError>>` — контракт, реализация подключается DTJ-245.
2. `CancelOrderUseCase.execute(cmd: { orderId, actor, reason })`:
   - `OrderPolicy.canCancel(order, actor)` (DTJ-222) — `false` → `403 FORBIDDEN` (для
     `picked_up`/`delivered`/терминальных, SRS-DOM-154).
   - `order.cancel(reason, actor)` (домен, DTJ-222) — мутация статуса в `cancelled`.
   - Ветвление по `(order.status ДО отмены, order.paymentMethod)`:
     - `pending_payment` (non-cash) → без рефанда, только `InventoryFacadePort.releaseStock`.
     - `confirmed` (cash, D-25) → без рефанда, только `releaseStock` (SRS-ORD-029 таблица,
       строка `confirmed`; денежный эффект «НИЧЕГО», D-25 п.3).
     - `paid_escrow`/`processing` (non-cash) → `RefundFacadePort.refundFull(orderId, reason)` +
       `releaseStock`.
     - `processing` (cash, достигнут из `confirmed`) → без рефанда (та же логика, что
       `confirmed`), только `releaseStock`.
   - Записать `orders.cancel_reason` из канонического enum (SRS-ORD-030): `customer_changed_mind`,
     `found_cheaper_elsewhere`, `pharmacy_suspended`, `pickup_sla_timeout`,
     `fraud_or_safety_force_cancel`, `license_revoked_force_cancel` — Zod-схема контракта
     (`packages/contracts/src/orders.ts`, расширение файла DTJ-220), НЕ свободная строка в БД;
     произвольный текст клиента (если есть) — в `audit_log.metadata` (порт аудита — предполагается
     существующим из EP-01/общей инфраструктуры, здесь только вызов).
   - Given актор — `pharmacist`/`pharmacy_admin` своей аптеки, отменяющий `confirmed`/
     `paid_escrow`/`processing` заказ СВОЕЙ аптеки → разрешено БЕЗ согласования `super_admin`
     (SRS-ORD-031), `reason` обязателен в любом случае.
3. Эмитировать доменное событие `OrderCancelledEvent` (в outbox, та же транзакция) —
   `{ orderId, reason, cancelledBy, refundIssued: boolean }` (payload из глоссария
   `10-domain-model.md` §«События»).

## Критерии приёмки

1. **Given** заказ `confirmed` (cash_courier), **When** `customer` вызывает отмену, **Then**
   статус `cancelled`, `RefundFacadePort.refundFull` НЕ вызван ни разу (проверка счётчика вызовов
   мока), `releaseStock` вызван.
2. **Given** заказ `paid_escrow` (non-cash), **When** `pharmacist` своей аптеки вызывает отмену,
   **Then** `RefundFacadePort.refundFull` вызван РОВНО один раз, статус `cancelled`.
3. **Given** заказ `picked_up`, **When** любой актор вызывает отмену, **Then** `403 FORBIDDEN`
   (`OrderPolicy.canCancel` вернул `false`), статус не изменён.
4. **Given** `pharmacist` НЕ своей аптеки пытается отменить заказ, **Then** `403 FORBIDDEN`
   (проверка принадлежности `actor.pharmacyId === order.pharmacyId`).
5. **Given** `reason` не входит в канонический enum, **When** отмена, **Then** валидация Zod на
   уровне presentation отклоняет запрос ДО вызова use case (`400`, не доменная ошибка).
