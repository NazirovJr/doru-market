## Задача

Реализует межэпиковый контракт `RefundFacadePort`, объявленный `orders`-модулем (DTJ-232, EP-09)
для `CancelOrderUseCase`, и служит основанием, на которое позже будут опираться таймауты
(DTJ-254/255) и — за периметром этого набора тикетов — возвраты (EP-11) и споры (EP-14). Полный
рефанд — единственный сценарий этого тикета; частичный рефанд/раздельный биллинг — предмет
EP-11 (`ReturnFinancialOutcomeResolver`), не дублируется здесь.

## Технический контекст

`RefundOrderUseCase.execute(orderId, reason)` вызывает `PaymentProvider.refund(providerRef,
idempotencyKey)` (DTJ-237/238) + `EscrowLedger.append({ entryType: 'refunded_to_customer',
direction: 'credit', amountDiram: holdAmount })` (DTJ-240) — АТОМАРНО. `RefundFacadeAdapter`
реализует `RefundFacadePort` (интерфейс объявлен `orders`-модулем, DTJ-232) — тот же паттерн
межмодульного биндинга, что `PaymentInvoiceAdapter` (DTJ-241).

## Что сделать

1. `RefundOrderUseCase.execute(orderId, reason: RefundReason)`:
   - `PaymentsOrdersPort.getOrderById(orderId)` → проверить `paymentMethod` ПЕРВЫМ шагом.
   - Given `paymentMethod === 'cash_courier'` → **NOOP с логированием** (SRS-PAY-017: наличные
     заказы не порождают ledger, возвращать через `PaymentProvider` нечего — физический возврат
     наличных, если применимо, — операционный процесс вне ledger, ответственность вызывающего
     контекста, не этого use case).
   - Иначе — идемпотентность через `payment_operations` (тот же паттерн, что DTJ-241:
     `idempotency_key = derivedRefundAttemptId`, `ON CONFLICT DO NOTHING`).
   - `holdAmount = EscrowLedgerRepository.sumByType(orderId, 'hold_created')` (DTJ-240) —
     фактическая захолдированная сумма, не пересчитанная заново из `order.totalAmountDiram`
     (единственный источник истины — уже записанный `hold_created`).
   - `PaymentProvider.refund(order.paymentTransactionId, idempotencyKey)` → успех →
     `EscrowLedger.append({ entryType: 'refunded_to_customer', direction: 'credit', amountDiram:
     holdAmount })` — В ОДНОЙ транзакции с записью `payment_operations(operation_type='refund',
     status='succeeded')`.
   - Given `payout_schedule` уже существует для заказа (пост-`delivered` случай — в R1 маловероятно
     на этом пути, но защита от программной ошибки) → `payout_schedule.status = 'reversed'`.
2. `RefundFacadeAdapter implements RefundFacadePort` — обёртка над `RefundOrderUseCase.execute`.

## Критерии приёмки

1. **Given** заказ `paid_escrow`, `escrow_ledger` содержит `hold_created=10000`, **When**
   `RefundOrderUseCase.execute(orderId, reason)`, **Then** `PaymentProvider.refund` вызван один
   раз, `escrow_ledger` содержит новую запись `refunded_to_customer=10000`.
2. **Given** заказ `cash_courier`, **When** `RefundOrderUseCase.execute`, **Then**
   `PaymentProvider.refund` НЕ вызван ни разу (счётчик мока = 0), `escrow_ledger` не изменён.
3. **Given** повторный вызов с тем же `derivedRefundAttemptId` (двойной клик/ретрай), **When**
   выполняется, **Then** `PaymentProvider.refund` вызван РОВНО один раз суммарно.
4. **Given** `payout_schedule` уже существует (пост-доставочный кейс), **When** рефанд выполнен,
   **Then** `payout_schedule.status = 'reversed'`.

## Риски и подводные камни

- **`RefundFacadePort` — контракт, уже объявленный DTJ-232 (EP-09).** Сверить сигнатуру перед
  реализацией — тот же межэпиковый риск расхождения, что DTJ-241/244.
- Этот тикет намеренно НЕ реализует частичный рефанд/раздельный биллинг (D-10, SRS-RET-006..009)
  — они принадлежат EP-11 и вызывают `PaymentProvider.partialRefund()`/собственную композицию
  `refund()` двух отдельных `payment_operations`. Если EP-11 обнаружит, что текущая сигнатура
  `RefundOrderUseCase` не расширяется естественно под частичный сценарий — эскалировать как
  находку для последующего рефакторинга, не блокирует этот тикет.
