## Задача

D-25 существует, чтобы сделать одну конкретную ложь в модели данных структурно невозможной:
статус `paid_escrow`, утверждающий финансовый факт, которого нет. Каждый предыдущий тикет
(DTJ-221/222/230/242/243) реализует ЧАСТЬ этого гарантии локально, изолированно. Этот тикет —
единственный тест, который проверяет инвариант ГЛОБАЛЬНО, по ВСЕЙ таблице `orders` разом, тем
способом, каким его в итоге будет проверять `EscrowReconciliationJob` (DTJ-247) и любой будущий
финансовый аудит. Архитектор явно называет его «обязателен к покрытию тестом» дважды —
в `03-ARCHITECT-DECISIONS.md` (D-25 п.4) и в `21-module-orders-payments-escrow.md`
(SRS-ORD-027a) — это не опциональное усиление, а буквальное условие приёмки решения D-25.

## Технический контекст

`tests/invariants/escrow-invariant.spec.ts` — интеграционный тест (Testcontainers PostgreSQL),
НЕ привязанный к одному use case: проверяет эквивалентность
`order.status === 'paid_escrow' ⟺ EXISTS(SELECT 1 FROM escrow_ledger WHERE order_id = order.id)`
для КАЖДОГО заказа в тестовой БД, в ОБЕ стороны. Расположение файла — `tests/invariants/`, НЕ
внутри `apps/api/src/modules/payments/**` (по решению этого тикета: это не unit/интеграционный
тест ОДНОГО модуля, а сквозная гарантия, затрагивающая `orders` и `payments` одновременно —
логичнее держать в общей `tests/`-директории, аналогично будущему `tests/arch/` из EP-19; если к
моменту реализации в проекте уже сложилась другая конвенция для сквозных тестов — следовать ей,
не создавать третий несовместимый паттерн).

## Что сделать

1. Тестовый сценарий-фикстура (сетап через реальные use case, не прямые INSERT — тест ДОЛЖЕН
   проходить через реальный код-путь, иначе не поймает регрессию в этом коде):
   - Заказ А: `cash_courier`, доведён до `confirmed` через `Order.create()` (DTJ-221/222).
   - Заказ Б: `alif_mobi`, доведён до `paid_escrow` через `HandlePaymentWebhookUseCase` (DTJ-242,
     реальный вебхук на `MockBankProvider`, DTJ-238).
   - Заказ В: `cash_courier`, отменён по позднему платежу (`LatePaymentRefundService`, DTJ-243) —
     ГРАНИЧНЫЙ случай: `escrow_ledger` НЕПУСТ (аудиторский след `hold_created`+
     `refunded_to_customer`), но `status='cancelled'`, НЕ `paid_escrow` — инвариант формулируется
     как `paid_escrow ⟺ ledger`, а НЕ `ledger ⟹ paid_escrow`; заказ В подтверждает, что второе
     направление НЕ требуется (см. DTJ-243 «Риски», этот тест — место, где это явно
     зафиксировано, а не молчаливое допущение).
2. `EscrowInvariantSpec.checkOrder(orderId)`:
   ```
   const isPaidEscrow = order.status === 'paid_escrow';
   const hasLedgerEntries = (await escrowLedgerRepository.findByOrderId(orderId)).length > 0;
   expect(isPaidEscrow).toBe(hasLedgerEntries === isPaidEscrow ? isPaidEscrow : /* нарушение */);
   ```
   (псевдокод — реализовать как явное `expect(isPaidEscrow).toBe(hasLedgerEntriesImplyingEscrow)`
   с раздельной, читаемой проверкой обеих сторон эквивалентности, не одной свёрнутой формулой —
   C11: код, а не комментарий, должен быть понятен).
3. Для заказа А (cash/confirmed): `expect(isPaidEscrow).toBe(false)`,
   `expect(hasLedgerEntries).toBe(false)` — согласовано.
4. Для заказа Б (non-cash/paid_escrow): `expect(isPaidEscrow).toBe(true)`,
   `expect(hasLedgerEntries).toBe(true)` — согласовано.
5. Для заказа В (cash/cancelled с аудиторским следом): `expect(isPaidEscrow).toBe(false)` —
   единственная проверяемая сторона для этого случая (наличие ledger-записей НЕ проверяется как
   нарушение, т.к. инвариант не требует обратной импликации).
6. Явный НЕГАТИВНЫЙ тест (фикстура-нарушитель, по прецеденту `tests/arch/`): искусственно
   создать заказ со `status='paid_escrow'`, но БЕЗ записей `escrow_ledger` (прямой SQL `INSERT`,
   в обход домена — единственное место во всём тест-сьюте, где это оправдано, именно чтобы
   доказать, что спецификация ЛОВИТ нарушение) → тест `EscrowInvariantSpec` для этого заказа
   ДОЛЖЕН провалиться — подтверждает, что ловушка реально ловит, а не просто существует
   (`02` §6.1 «ловушка, которая перестала ловить, молчит об этом»).

## Критерии приёмки

1. **Given** заказы А (cash/confirmed) и Б (non-cash/paid_escrow) из фикстуры, **When**
   `EscrowInvariantSpec` проверяет оба, **Then** нарушений не найдено ни для одного.
2. **Given** заказ В (cash/cancelled, ledger непуст из-за поздней оплаты), **When** проверка,
   **Then** нарушений не найдено (эта сторона инварианта не применима).
3. **Given** искусственно созданный заказ-нарушитель (`paid_escrow` без ledger, обход домена),
   **When** `EscrowInvariantSpec` его проверяет, **Then** тест ПАДАЕТ с понятным сообщением,
   указывающим на нарушенный `orderId`.
4. **Given** запрещённый переход `confirmed → paid_escrow` (DTJ-222, TC-ORD-001d), **When**
   `order.markPaidEscrow(...)` вызван программно на заказе А, **Then**
   `InvalidOrderStatusTransitionError` — этот сценарий уже покрыт DTJ-222 unit-тестом, здесь
   ДОПОЛНИТЕЛЬНО переносится как явная ссылка/дубль в сьют инвариантов для полноты картины «все
   защиты D-25 в одном месте» (не заменяет unit-тест DTJ-222, дополняет).
