## Задача

Даёт клиенту физический вход в корзину по REST и решает конкретный продуктовый разрыв: гость
добавил товары в корзину ДО логина (по `session_token`), затем прошёл OTP — эти товары не должны
потеряться и не должны задублироваться, если у пользователя уже была своя корзина.

## Технический контекст

`apps/api/src/modules/orders/presentation/cart/**`. Эндпоинты — `SRS-API-001..015` конвенции
(`/api/v1` префикс, envelope `{ data, meta }`/`{ error }`, `kebab-case` под-пути). Гостевая корзина
идентифицируется `cart.session_token` (уже в схеме DTJ-220); аутентифицированная — `customer_id`.
`MergeGuestCartUseCase` вызывается модулем `auth` (EP-01) ПОСЛЕ успешного OTP-логина — точный
триггер (hook в `AuthModule`) вне периметра этого тикета, здесь только сам use case и его
регистрация в `OrdersFacade` (расширить `application/orders.facade.ts` из DTJ-222, если требуется
экспорт для вызова из `auth`).

## Что сделать

1. `GET /api/v1/cart` (роль: `customer` ИЛИ гость по `session_token`, заголовок/куки резолвинг —
   через существующий auth-guard EP-01): query `?extendHold=true` опционален — вызывает
   `ExtendCartHoldUseCase` (DTJ-224) ПЕРЕД `GetCartUseCase` (DTJ-225). Ответ —
   `{ data: CartViewDto }`.
2. `POST /api/v1/cart/items { medicineId, pharmacyId, quantity }` → `AddCartItemUseCase` (DTJ-223).
   `201`, тело — обновлённая строка + `meta.warnings` (дубликат вещества, если применимо).
3. `PATCH /api/v1/cart/items/:id { quantity }` → `UpdateCartItemQuantityUseCase` (DTJ-223). `200`.
4. `DELETE /api/v1/cart/items/:id` → `RemoveCartItemUseCase` (DTJ-223). `204`.
5. `MergeGuestCartUseCase.execute(sessionToken, customerId)`: Given гостевая корзина с этим
   `session_token` существует, Then для каждой её `cart_items` — `AddCartItemUseCase`-подобный
   upsert в корзину `customerId` (переиспользовать логику upsert из DTJ-223, не копировать),
   гостевая строка `cart` удаляется после переноса (не остаётся сиротой). Given у пользователя ещё
   нет корзины — гостевая просто перепривязывается (`UPDATE cart SET customer_id=:id,
   session_token=NULL`), без построчного переноса.
6. Ошибки домена (`ControlledSubstanceNotOrderableError` и т.д.) маппятся в HTTP через общий
   `DomainExceptionFilter` (предполагается уже существующим из EP-01 API-конвенций, SRS-API-016) —
   этот тикет добавляет только новые коды в общий реестр (не создаёт фильтр заново).

## Критерии приёмки

1. **Given** гость добавил 2 позиции в корзину по `session_token`, **When** проходит OTP-логин и
   вызывается `MergeGuestCartUseCase`, **Then** обе позиции доступны в корзине `customerId`,
   гостевая строка `cart` удалена.
2. **Given** у пользователя уже есть 1 позиция в своей корзине, гостевая корзина содержит ту же
   `(medicineId, pharmacyId)` с другим количеством, **When** merge, **Then** итоговое количество —
   СУММА обеих (не перезапись, не дублирующая строка — `UNIQUE`-констрейнт).
3. **Given** `POST /api/v1/cart/items` с товаром `psychotropic`, **Then** `422
   CONTROLLED_SUBSTANCE_NOT_ORDERABLE` (маппинг из домена).
4. **Given** `GET /api/v1/cart?extendHold=true`, **Then** холды всех позиций продлены ДО того, как
   собран ответ (порядок операций проверяется мок-шпионом в тесте).

## Тест-план

- Интеграционный (Supertest + Testcontainers): по одному кейсу на каждый эндпоинт, включая коды
  ошибок.
- Интеграционный: `MergeGuestCartUseCase` — оба сценария из критериев приёмки 1–2, плюс граничный
  случай «гостевой корзины с этим `session_token` не существует» (no-op, не ошибка).
- E2E (Playwright, часть CUJ-2'): добавление в корзину гостем → логин → корзина сохранена —
  добавляется этим тикетом как шаг существующего/будущего сценария EP-19, не отдельный E2E-раннер.

## Риски и подводные камни

- **Точка вызова `MergeGuestCartUseCase` — в модуле `auth` (EP-01), не здесь.** Этот тикет
  экспортирует use case через `OrdersFacade`, но НЕ добавляет хук в `auth`-flow — координация с
  владельцем EP-01 обязательна (иначе use case существует, но никогда не вызывается в проде).
  Зафиксировать явную договорённость в PR/канале команды перед закрытием тикета.
- **`DomainExceptionFilter` — предполагаемая, не гарантированная зависимость от EP-01.** Если на
  момент реализации общий фильтр ошибок ещё не существует, эндпоинты этого тикета временно мапят
  ошибки локально (простой `try/catch` в контроллере с explicit switch по типу ошибки) с TODO на
  миграцию к общему механизму, когда он появится — не блокировать сдачу тикета на чужой
  инфраструктуре.
