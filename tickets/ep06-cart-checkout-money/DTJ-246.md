## Задача

`AdminPaymentOverrideUseCase` — ЕДИНСТВЕННОЕ разрешённое исключение из категорического запрета
DTJ-242 (SRS-PAY-018): банк подтвердил оплату по телефону поддержки, вебхук технически не дошёл
из-за сбоя маршрутизации на стороне банка. Каждый вызов — не тихая операция, а событие,
заслуживающее алерта дежурному, несмотря на свою легитимность. `AdjustLedgerUseCase` —
единственный способ учесть спор, открытый ПОСЛЕ того, как аптеке уже выплачено (netting в
следующий период, SRS-DOM-063) — реализуется здесь как готовый к вызову use case для будущего
потребителя (EP-14), сам вызывающий код спора — вне периметра.

## Технический контекст

`AdminPaymentOverrideUseCase.execute(orderId, amountDiram, reason, actorUserId)` — вызывает ТЕ ЖЕ
доменные операции, что `HandlePaymentWebhookUseCase` (`order.markPaidEscrow` +
`EscrowLedger.recordHold`, DTJ-242), но с ролевой защитой (`super_admin` only) и обязательным
`reason` вместо банковской подписи. `AdjustLedgerUseCase.execute(orderId, amountDiram, direction,
reason, actorUserId)` — создаёт `escrow_ledger.entry_type='adjustment'` (DTJ-240 уже требует
`reason`+`actorUserId` в конструкторе VO — этот use case просто их предоставляет).

## Что сделать

1. `AdminPaymentOverrideUseCase.execute(cmd: { orderId, txId, amountDiram, paidAt, reason,
   actorUserId })`:
   - Роль-проверка `super_admin` — на уровне presentation-guard (не дублировать в application, но
     defensive-проверка `actorRole==='super_admin'` внутри use case как второй рубеж, C12).
   - `reason` — обязательное непустое поле (Zod-валидация на границе + доменная проверка).
   - В ОДНОЙ транзакции: `order.markPaidEscrow(txId, paidAt, ledgerHoldWillBeRecorded: true)` +
     `EscrowLedger.append({ entryType: 'hold_created', ... })` — ИДЕНТИЧНО DTJ-242 шаг 5, но БЕЗ
     HMAC-проверки (заменена ролью + `reason`).
   - `audit_log(category='payment_override', metadata={orderId, amountDiram, reason,
     actorUserId})` — обязательная запись.
   - Эмитировать алерт дежурному (интеграция с существующим каналом алертинга —
     предположительно от EP-16/общей инфраструктуры; если отсутствует — временный `pino.fatal`/
     `pino.error` с явным TODO на реальный алерт-канал).
2. `AdjustLedgerUseCase.execute(cmd: { orderId, amountDiram, direction, reason, actorUserId })`:
   - Только если связанный `payout_schedule.status === 'paid'` (SRS-DOM-063 — вне этого условия
     спор использует `resolveRefundFull`/`Partial`, не adjustment; проверка условия —
     ответственность ВЫЗЫВАЮЩЕГО кода EP-14, этот use case доверяет вызывающему и лишь
     ДОКУМЕНТИРУЕТ предусловие в JSDoc — доменная защита самого условия «payout уже paid» относится
     к спору, не к ledger).
   - `EscrowLedger.append({ entryType: 'adjustment', direction, amountDiram, reason,
     actorUserId })`.
3. `POST /api/v1/admin/payment-override` (роль `super_admin`, `Idempotency-Key` обязателен,
   SRS-API-009) — presentation-обёртка над `AdminPaymentOverrideUseCase`.

## Критерии приёмки

1. **Given** `super_admin` вызывает `AdminPaymentOverrideUseCase` с валидным `reason`, **When**
   выполняется, **Then** заказ переходит `pending_payment → paid_escrow`, `escrow_ledger`
   содержит `hold_created`, `audit_log(category='payment_override')` создан.
2. **Given** `reason` пустой, **When** `AdminPaymentOverrideUseCase.execute`, **Then**
   `ValidationError`, транзакция не начата.
3. **Given** актор НЕ `super_admin` (defensive-проверка на уровне application), **When**
   вызывается напрямую в обход presentation-guard (тестовый сценарий), **Then** `Forbidden`
   ошибка, не выполняет мутацию.
4. **Given** `AdjustLedgerUseCase` вызван с `direction='debit'`, **When** выполняется, **Then**
   `escrow_ledger` содержит запись `adjustment` с `direction='debit'`, `reason`/`actorUserId`
   заполнены (иначе — доменная ошибка `AdjustmentRequiresReasonError` из DTJ-240).
5. **Given** grep по кодовой базе на вызовы `order.markPaidEscrow`, **Then** ровно ДВА вызывающих
   места — `HandlePaymentWebhookUseCase` (DTJ-242) и `AdminPaymentOverrideUseCase` (этот тикет), ни
   одного третьего.

## Тест-план

- Unit: оба use case — happy path, невалидный `reason`, ролевая защита.
- Интеграционный: `AdminPaymentOverrideUseCase` — реальная транзакция, `audit_log` запись
  проверена через прямой SQL-запрос.
- Статическая проверка (ручная на ревью + при возможности — ESLint custom rule/grep-скрипт в CI):
  количество вызывающих мест `markPaidEscrow` — ровно два (критерий 5).
- Покрытие `application/` ≥ 90%.

## Риски и подводные камни

- **`AdjustLedgerUseCase` не проверяет `payout_schedule.status==='paid'` сама** — сознательное
  решение (см. «Что сделать» п.2): условие принадлежит доменной логике спора (EP-14, вне
  периметра). Если EP-14 вызовет этот use case БЕЗ проверки условия — расхождение с SRS-DOM-063
  возникнет на СТОРОНЕ вызывающего кода, не этого тикета; явно задокументировать это предусловие в
  публичной сигнатуре порта, который экспортирует этот use case другим модулям (если/когда такой
  порт понадобится EP-14).
- Канал алертинга дежурному — не гарантированная зависимость (см. DTJ-232/241 паттерн
  «предположительно от другого эпика») — не блокирует тикет, деградирует до логирования.
