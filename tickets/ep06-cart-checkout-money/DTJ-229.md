## Задача

Способ оплаты и адрес доставки — единственные два поля checkout, которые клиент вводит вручную, и
оба несут реальный риск: неверная COD-политика пропускает наличные для Rx-товара (незаконно) или
дороже лимита (риск невозврата), а незавалидированный инлайн-адрес ломает расчёт стоимости доставки
ниже по пайплайну. Этот тикет — единственная точка, где `paymentMethod` и адрес проверяются перед
тем, как попасть в `Order.create()`.

## Технический контекст

`ResolveDeliveryAddressService` вызывается из `CheckoutUseCase` (DTJ-227) до расчёта стоимости
(нужен `GeoPoint` для `DeliveryFacadePort.calculateFee`, DTJ-228). `CodPolicyService` — application-
слой политика (`02` §3.4: авторизация/бизнес-правила — в application, не в guard) поверх домена:
домен (`Order.create()`, DTJ-221) уже содержит ЖЁСТКУЮ проверку Rx/лимита как последний рубеж
(SRS-DOM-007/156) — этот сервис даёт РАННЮЮ проверку ДО вызова домена, чтобы вернуть точный код
ошибки конкретно для оплаты, не смешивая с общими доменными ошибками группы.

`enabledPaymentMethods` (SRS-ORD-025 п.2, `tenant_settings.enabled_payment_methods`) — поле,
отсутствующее в базовом DDL Group C, требует эволюционной миграции. **Владение Group C — НЕ моё**
(вероятно EP-01/EP-02) — этот тикет НЕ создаёт миграцию на `tenant_settings`, только потребляет
поле через порт с graceful-деградацией, если поле пока недоступно (см. «Риски»).

## Что сделать

1. `ResolveDeliveryAddressService.resolve(cmd): GeoPoint`:
   - Given `deliveryAddressId` передан — загрузить сохранённый `user_addresses` (порт из
     `auth`/`users`-контекста — если отдельного порта ещё нет, объявить минимальный
     `UserAddressFacadePort.getById(addressId, customerId)` в `application/ports/` этим тикетом).
   - Given вместо `deliveryAddressId` передан инлайн `{ addressText, landmarkText, latitude,
     longitude }` — валидировать через `GeoPoint.create(lat, lon)` (VO, SRS-DOM-072; предполагается
     доступным из общего домена — если ещё нет нигде, локальная копия по той же схеме, что и
     `Money`, DTJ-221 «Риски»), НЕ сохранять в `user_addresses` (разовый адрес).
   - `deliveryLandmark`, если передан отдельно от `deliveryAddressId`, ПЕРЕЗАПИСЫВАЕТ
     `landmark_text` ТОЛЬКО для этого заказа (одноразовое уточнение), не мутирует сохранённый
     адрес.
2. `CodPolicyService.isCodAllowed(items, totalAmountDiram, tenantId): PolicyResult`:
   - `false`, если ≥1 позиция `isPrescriptionRequired=true` → `CodForbiddenForRxError`
     (SRS-DOM-156а);
   - `false`, если `totalAmountDiram > tenantSettings.codLimitDiram` (поле `cod_limit_diram` УЖЕ
     в базовой схеме `tenant_settings`, DTJ-220 не требуется расширение) →
     `CodLimitExceededError`;
   - иначе `true`.
3. `PaymentMethodEnabledPolicyService.isEnabled(paymentMethod, tenantId): boolean` — читает
   `tenantSettings.enabledPaymentMethods` через `TenancyFacadePort` (расширить порт из DTJ-220
   методом `getEnabledPaymentMethods(tenantId)`). Given поле физически недоступно (миграция
   Group C ещё не смержена другим владельцем) — деградация до жёстко закодированного дефолта
   `['cash_courier']` (соответствует ASSUMPTION-дефолту документа для R1) с явным TODO. Given
   `paymentMethod` не входит в разрешённый список → `PaymentMethodNotEnabledError`
   (`422 PAYMENT_METHOD_NOT_ENABLED`).
4. Интегрировать оба сервиса в `CheckoutUseCase` (DTJ-227) ДО вызова `Order.create()` — правка
   существующего файла того же эпика, не конфликт владения.

## Критерии приёмки

1. **Given** корзина содержит Rx-позицию, **When** `paymentMethod='cash_courier'`, **Then**
   `422 COD_FORBIDDEN_FOR_RX`, заказ не создан.
2. **Given** `total_amount_diram=60000` (>50000 дефолт), non-Rx, **When**
   `paymentMethod='cash_courier'`, **Then** `422 COD_LIMIT_EXCEEDED`.
3. **Given** `tenantSettings.enabledPaymentMethods=['cash_courier']` (дефолт R1), **When**
   `paymentMethod='alif_mobi'`, **Then** `422 PAYMENT_METHOD_NOT_ENABLED`.
4. **Given** инлайн-адрес с `latitude=95` (вне диапазона), **When**
   `ResolveDeliveryAddressService.resolve`, **Then** `InvalidCoordinatesError`.
5. **Given** `deliveryLandmark` передан отдельно от `deliveryAddressId` (сохранённый адрес), **When**
   checkout завершён, **Then** заказ содержит переданный ориентир, сохранённый `user_addresses`
   НЕ изменён.

## Риски и подводные камни

- **`tenant_settings.enabled_payment_methods` — вне владения этого тикета (Group C).** Реализация
  сознательно деградирует до жёстко закодированного дефолта, если поле недоступно — это НЕ
  постоянное решение, follow-up на реальное чтение поля заводится, когда владелец Group C добавит
  миграцию (см. тот же риск в DTJ-228 — координировать одной задачей, не дублировать усилия).
- **`UserAddressFacadePort` может дублировать порт, уже созданный EP-01 для профиля
  пользователя.** Проверить перед реализацией, не существует ли уже аналогичного порта/фасада в
  `auth`/`users`-модуле — если да, переиспользовать его сигнатуру вместо изобретения нового.
