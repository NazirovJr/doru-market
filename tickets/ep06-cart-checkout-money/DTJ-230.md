## Задача

Это тикет, реализующий саму суть D-25: наличный заказ обязан появиться в статусе `confirmed`
СИНХРОННО, в той же транзакции, что и его создание, и НИКОГДА не быть наблюдаемым в `paid_escrow`
или `pending_payment`. Параллельно — Rx-позиции без покрытия рецептом молча исключаются из ПОПЫТКИ
оформления (остаются в корзине), а не блокируют весь checkout: пользователь с корзиной из 3 позиций,
где одна требует рецепта, получает 2 оформленных и честное объяснение по третьей.

## Технический контекст

`ExcludeUnverifiedRxItemsService` вызывается из `CheckoutUseCase` (DTJ-227) шаг 4.a, ДО расчёта
стоимости (DTJ-228) — исключённые позиции не участвуют в сумме. Синхронный `order.confirm()`
(метод уже реализован в DTJ-222) вызывается ВНУТРИ `Order.create()` (DTJ-221) — этот тикет не
трогает домен повторно, а описывает и тестирует ОРКЕСТРАЦИЮ вокруг него на уровне
`CheckoutUseCase`: гарантирует, что для `cash_courier` HTTP-ответ уходит клиенту ТОЛЬКО после
завершения перехода `confirm()`, и что для non-cash HTTP-ответ никогда не содержит статус
`confirmed`.

## Что сделать

1. `ExcludeUnverifiedRxItemsService.exclude(items, prescriptionIds, customerId):
   { orderable: Item[], excluded: ExcludedItem[] }`:
   - Для каждой Rx-позиции (`isPrescriptionRequired=true`) — `PrescriptionsFacadePort.
     isVerifiedFor(customerId, [medicineId])` (порт из DTJ-220).
   - Непокрытые → в `excluded` с `reason: 'PRESCRIPTION_NOT_VERIFIED'`, остаются в корзине
     (НЕ удаляются из `cart_items` — checkout только читает корзину, не мутирует её на исключение).
   - Given ВСЕ позиции группы (по аптеке) исключены → группа НЕ формирует заказ вовсе (пустая
     группа пропускается тихо на уровне этого сервиса — не ошибка ЭТОЙ группы, обрабатывается как
     «группа отсутствует» в `CheckoutUseCase`).
2. Given ПОСЛЕ исключения по ВСЕМ группам не осталось ни одной заказываемой позиции (корзина
   состояла целиком из непокрытых Rx) → `NoOrderableItemsError` (`422 NO_ORDERABLE_ITEMS`,
   SRS-ORD-016) — не создаётся пустой массив `orders`.
3. В `CheckoutUseCase` (DTJ-227, правка существующего файла того же эпика) — после успешного
   `Order.create(cmd)` для группы с `paymentMethod='cash_courier'`: убедиться, что домен УЖЕ
   вернул заказ со статусом `confirmed` (инвариант SRS-ORD-027 п.1 реализован в DTJ-221/222,
   этот тикет добавляет ЯВНУЮ assertion/тест, что use case НИКОГДА не наблюдает промежуточный
   `pending_payment` для этой ветки — если домен вернул иное, это программная ошибка,
   `InvariantViolationError`, не доменная бизнес-ошибка).
4. Для non-cash групп — симметричная assertion: заказ после `Order.create()` обязан быть
   `pending_payment`, НИКОГДА `confirmed` (SRS-ORD-028).

## Критерии приёмки

1. **Given** корзина: 1 Rx-товар без верифицированного рецепта + 1 обычный товар той же аптеки,
   **When** checkout, **Then** заказ создан ТОЛЬКО с обычным товаром, `meta.excludedItems`
   содержит Rx-строку с `PRESCRIPTION_NOT_VERIFIED`, Rx-строка остаётся в корзине.
2. **Given** корзина ТОЛЬКО из Rx-товаров без верификации, **When** checkout, **Then** `422
   NO_ORDERABLE_ITEMS`, ни один заказ не создан.
3. **Given** `paymentMethod='cash_courier'`, валидная корзина, **When** `POST /api/v1/orders`,
   **Then** ответ содержит заказ со `status='confirmed'` СРАЗУ, `payment_transaction_id=null`;
   `escrow_ledger`/`payout_schedule` — ноль строк для этого `order_id` (проверка на стороне БД в
   интеграционном тесте, таблицы существуют благодаря миграции EP-10, здесь только чтение).
4. **Given** `paymentMethod='alif_mobi'`, **When** `POST /api/v1/orders`, **Then** заказ
   создаётся со `status='pending_payment'`, НИКОГДА `confirmed`.
