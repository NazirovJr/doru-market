## Задача

Замыкает B2B-цикл: если сеть не платит комиссию за наличные заказы (единственный реальный источник
дохода платформы в R1) — она теряет право принимать НОВЫЕ заказы, но уже принятые заказы клиентов
не прерываются (нельзя наказывать клиента за неплатёж сети). Отдельно — этот тикет даёт аптеке
единственный практический в R1 способ узнать, сколько ей причитается: CSV-отчёт по payout'ам и
список выставленных счетов (до появления реального банковского перевода в R3).

## Технический контекст

`BillingInvoiceOverdueJob` — переиспользует ТУ ЖЕ ветку приостановки, что
`PharmacySuspendedEvent`/`OnboardingFacade` (REQ-ONBOARD-13, SRS-DOM-161) — единая точка проверки
`isPharmacyActive`, независимо от причины (регуляторная приостановка Onboarding-модуля ИЛИ
неоплаченный B2B-инвойс этого модуля). `GET /api/v1/pharmacy-accounts/:id/payouts`/`.../billing-
invoices` — курсорная пагинация (`SRS-API-004..007`).

## Что сделать

1. `BillingInvoiceOverdueJob` (BullMQ repeatable, ежедневно): `SELECT * FROM
   platform_billing_invoices WHERE status='issued' AND due_at + INTERVAL 'GRACE_PERIOD_DAYS days'
   < NOW()` (ASSUMPTION `GRACE_PERIOD_DAYS=3`) → для каждой найденной строки — `UPDATE
   pharmacy_chains SET is_active=false WHERE id=:chainId` (уже существующее поле схемы,
   принадлежит Group A, чужой владелец — правка данных через SQL `UPDATE`, не через прямой импорт
   `onboarding`-домена: использовать `PaymentsTenancyPort`/аналогичный порт, если требуется
   доменная мутация, ИЛИ прямой репозиторный `UPDATE`, если поле — простой флаг без доменных
   инвариантов на своей стороне; уточнить у владельца `onboarding`-модуля перед реализацией, не
   решать в одностороннем порядке).
   - Уже существующие `confirmed`/`paid_escrow`/`processing`/`picked_up` заказы этой сети НЕ
     прерываются (никакой отмены — этот тикет только меняет `is_active`, не трогает `orders`).
   - Новый checkout на эту сеть — `PHARMACY_SUSPENDED` (уже реализовано DTJ-227/229 через
     единую проверку `isPharmacyActive` — этот тикет не дублирует ту логику, только производит
     условие, которое она читает).
2. Снятие блокировки — ТОЛЬКО `super_admin`, ручное подтверждение оплаты вне системы (эндпоинт —
   вероятно принадлежит `apps/admin`/EP-15, ВНЕ периметра этого тикета; здесь только
   документируется как известная точка интеграции).
3. `GET /api/v1/pharmacy-accounts/:id/payouts` (роль `pharmacy_admin` своей сети/`pharmacist`
   read-only своей аптеки/`super_admin`) — курсорный список `payout_schedule` этой аптеки:
   `orderId, orderNumber, grossAmountDiram, commissionDiram, netAmountDiram, status, dueAt,
   paidAt`. Фильтр `filter[status][in]=due,paid`.
4. `GET /api/v1/pharmacy-accounts/:id/payouts/export?format=csv` — `Content-Type: text/csv`,
   те же данные, что список, но полным потоком (не курсорная пагинация для экспорта).
5. `GET /api/v1/pharmacy-accounts/:id/billing-invoices` — то же для
   `platform_billing_invoices` (роль `pharmacy_admin` своей сети/`super_admin`).

## Критерии приёмки

1. **Given** `platform_billing_invoices.due_at + grace_period` истёк, не оплачен, **When**
   `BillingInvoiceOverdueJob`, **Then** `pharmacy_chains.is_active=false`; уже оформленные заказы
   сети НЕ отменяются; новый checkout на эту сеть → `PHARMACY_SUSPENDED`.
2. **Given** инвойс оплачен ДО истечения grace period, **When** джоба прогоняется, **Then**
   `is_active` не изменён.
3. **Given** `pharmacy_admin` запрашивает `GET .../payouts?filter[status][in]=due,paid`, **Then**
   ответ содержит только строки с этими статусами, курсорная пагинация работает
   (`meta.pagination.hasMore`).
4. **Given** `GET .../payouts/export?format=csv`, **Then** `Content-Type: text/csv`, тело —
   валидный CSV с заголовком колонок.
5. **Given** `pharmacist` (не `pharmacy_admin`) запрашивает `.../payouts`, **Then** доступ
   разрешён ТОЛЬКО read-only для своей аптеки (не всей сети) — если запрошена чужая аптека сети →
   `403`.

## Риски и подводные камни

- **Мутация `pharmacy_chains.is_active` из модуля `payments` — пограничный случай межмодульного
  владения данными.** `pharmacy_chains` — таблица Group A (каталог/организации), не Group E.
  Формально мутировать чужую таблицу напрямую нарушает дух Правила Зависимостей (`02` §1.2) даже
  если технически возможно через Drizzle. Рекомендуемое решение — объявить порт
  `OnboardingFacadePort.suspendChain(chainId, reason='unpaid_invoice')` (аналогично портам DTJ-236)
  и договориться с владельцем `onboarding`-модуля о его реализации; если по срокам это
  недостижимо — временный прямой `UPDATE` с явным TODO и обязательной пометкой в PR как
  технического долга.
- **Снятие блокировки (эндпоинт `super_admin`)** — вне периметра, координировать с EP-15, чтобы
  функциональность не осталась «наполовину сделанной» (блокировка есть, разблокировки через UI
  нет).
