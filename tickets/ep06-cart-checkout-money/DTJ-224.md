## Задача

Когда на складе остаётся 1–2 упаковки популярного лекарства, несколько покупателей физически
целятся в одно и то же — без честного «придержано для вас N:SS» пользователь либо заказывает
товар, которого уже нет к моменту checkout, либо теряет доверие к показанному остатку. Этот тикет
— UX-смягчение гонки на уровне Redis, СОЗНАТЕЛЬНО не являющееся авторитетной резервацией (та —
`InventoryFacade.reserveStock()` внутри `Order.create()`, DTJ-227) — деградация Redis не должна
уметь заблокировать реальную покупку.

## Технический контекст

`21-module-orders-payments-escrow.md` §1.2 — расширение SRS этого документа
(SRS-ORD-005 явно помечено `[РАСШИРЕНИЕ, требует подтверждения архитектором как ADR при переносе в
тикет]`, отсутствует в `10-domain-model.md`/`11-database-schema.md`). Реализуется КАК ОПИСАНО в
документе, но перед мержем требует явного подтверждения архитектора (не блокирует написание кода
— блокирует его включение в прод-конфигурацию без ADR; см. «Риски»). Ключ Redis:
`cart:hold:{pharmacyId}:{medicineId}:{cartItemId}`, значение — зарезервированное количество,
`EXPIRE CART_HOLD_TTL_SECONDS` (ASSUMPTION `900`, ENV). Отдельно — `CART_ABANDONED_TTL_DAYS`
(ASSUMPTION `30`) для персистентной очистки самой корзины (`cart`/`cart_items` в PostgreSQL) —
ДВА независимых временных окна, не путать: 15 минут — резерв количества, 30 дней — хранение
самой корзины.

## Что сделать

1. `CartHoldStorePort` (`application/ports/cart-hold-store.port.ts`): `hold(pharmacyId,
   medicineId, cartItemId, quantity, ttlSeconds)`, `extend(pharmacyId, medicineId, cartItemId,
   ttlSeconds)`, `getActiveHolds(pharmacyId, medicineId, excludeCartItemId?): Promise<number>`
   (сумма количеств по всем активным непросроченным холдам, кроме исключённого).
2. `RedisCartHoldStoreAdapter` — реализация через `ioredis` (`SET key qty EX ttl`, `EXPIRE` заново
   при `extend`, `SCAN`/паттерн-ключ или отдельный `SET`/`ZSET`-индекс по `(pharmacyId,
   medicineId)` для быстрого `getActiveHolds` без полного `KEYS *` — `KEYS` в проде запрещён,
   `no-magic-numbers`/производительность).
3. `AvailabilityCalculator.getAvailableQuantity(pharmacyId, medicineId, excludeCartItemId?):
   Promise<number>` = `stockQuantity (через InventoryFacadePort) − getActiveHolds(...)`. Given
   Redis недоступен (таймаут/ошибка соединения), Then деградация до `stockQuantity` без вычета
   холдов (fail-open, SRS-ORD-008) — логировать `WARN`, не бросать исключение наружу.
4. Вызов `CartHoldStorePort.hold(...)` — на успешное `AddCartItemUseCase`/
   `UpdateCartItemQuantityUseCase` (DTJ-223, расширить эти use case'ы вызовом холда — правка
   существующих файлов DTJ-223, тот же эпик/автор допустим без конфликта владения).
5. `ExtendCartHoldUseCase.execute(cartId)`: продлевает холды ВСЕХ строк корзины при
   `GET /api/v1/cart?extendHold=true` (SRS-ORD-005) — вызывается presentation-слоем DTJ-226/DTJ-225,
   не автоматическим поллингом.
6. `apps/worker/src/jobs/cart-cleanup/cart-abandoned-cleanup.job.ts` (BullMQ repeatable, ежедневно):
   `DELETE FROM cart WHERE updated_at < NOW() - INTERVAL 'CART_ABANDONED_TTL_DAYS days' AND
   customer_id IS NOT NULL` (гостевые корзины без `customer_id` — отдельный, более короткий TTL,
   ASSUMPTION 7 дней, т.к. `session_token` сам по себе недолговечен) — hard delete (SRS-DB-004),
   каскадом `cart_items` (`ON DELETE CASCADE` уже в схеме).

## Критерии приёмки

1. **Given** `stockQuantity=5`, активный холд другого `cartItemId` на `3`, **When**
   `AvailabilityCalculator.getAvailableQuantity(...)` (без исключения), **Then** возвращает `2`.
2. **Given** тот же холд принадлежит ТЕКУЩЕМУ `cartItemId` пользователя, **When** вызывается с
   `excludeCartItemId` равным этому холду, **Then** возвращает `5` (свой холд не вычитается из
   собственной доступности).
3. **Given** холд истёк (TTL прошёл), **When** `getActiveHolds`, **Then** просроченный холд не
   учитывается (Redis `EXPIRE` уже удалил ключ) — доступность пересчитана без него.
4. **Given** Redis недоступен (симуляция обрыва соединения в тесте), **When**
   `getAvailableQuantity`, **Then** возвращает `stockQuantity` без вычета, не бросает исключение.
5. **Given** корзина без активности 31 день, **When** `CartAbandonedCleanupJob`, **Then** корзина и
   её позиции удалены.

## Тест-план

- Unit: `AvailabilityCalculator` — на моке `CartHoldStorePort`, включая fail-open ветку (мок
  бросает ошибку).
- Интеграционный (Testcontainers Redis): `RedisCartHoldStoreAdapter` — `hold`/`extend`/TTL
  истечение (искусственно короткий TTL в тесте, не 900 секунд)/`getActiveHolds` с несколькими
  холдами и исключением.
- Интеграционный (Testcontainers PostgreSQL): `CartAbandonedCleanupJob` — удаляет старые, не
  трогает свежие корзины.
- Покрытие `application/` ≥ 90%.

## Риски и подводные камни

- **Требует ADR-подтверждения архитектора перед прод-деплоем** — SRS-документ явно помечает
  SRS-ORD-005 как расширение, отсутствующее в `10-domain-model.md`/`11-database-schema.md`. Код
  можно и нужно писать по этому тикету (реализация нигде не меняет схему БД, только Redis + worker
  job — низкий риск отката), но перед включением в продовую конфигурацию — получить явное
  подтверждение архитектора (зафиксировать в PR-описании ссылку на ADR или на согласование).
- **Индекс `(pharmacyId, medicineId) → активные холды` в Redis** — если реализовать наивно через
  `KEYS cart:hold:{pharmacyId}:{medicineId}:*`, это O(n) блокирующая операция на проде. Обязательно
  использовать вторичную структуру (`ZSET` с score=expiry или отдельный `SET` набора активных
  `cartItemId` на паре) — заложить в дизайн адаптера с самого начала, не как оптимизацию потом.
