## Задача

Модуль `orders` — физическое основание всего эпика EP-09 и точка входа для EP-10..EP-14, которые
позже будут читать заказы через его фасад. Ни один последующий тикет (домен, use case'ы корзины/
checkout) не может начаться, пока не заведены: таблицы БД строго по DDL из `11-database-schema.md`
(«Группа D: Заказы, корзина, избранное»), каталоги модуля по Правилу Зависимостей
(`02-CLEAN-ARCHITECTURE-AND-CODE.md` §1) и порты для обращения к чужим модулям (`catalog`,
`inventory`, `prescriptions`, `onboarding`, `tenancy`, `delivery`) — заказ физически не может быть
создан без снэпшота цены/остатка/Rx-статуса/активности аптеки/комиссии/стоимости доставки из этих
пяти чужих контекстов, ни один из которых `orders` не имеет права импортировать напрямую.

## Технический контекст

`11-database-schema.md` §«Миграции» фиксирует ровно этот файл миграции — `0008_orders_cart.sql`
(строка `orders, order_items, cart, cart_items, favorites (без FK courier/prescription)`) — как
топологически 8-й в общей последовательности. FK на `couriers.id`/`prescriptions.id` НЕ создаются
здесь (эти таблицы заводят EP-13/модуль рецептов позже, отдельными `ALTER TABLE` в своих миграциях
`0011_prescriptions.sql`/`0012_delivery.sql`) — колонки `orders.courier_id`/`orders.prescription_id`
существуют как обычные `UUID` без `REFERENCES` до этого момента. DDL — «Группа D» документа
(строки 686–815): `orders`, `order_items`, `cart`, `cart_items`, `favorites`, все `CHECK`/`COMMENT
ON` дословно.

Модуль живёт по стандартной структуре `domain/ application/ infrastructure/ presentation/` +
публичный фасад `index.ts` (`02` §1.2). `tickets/00-EPICS.md` закрепляет за EP-09
`apps/api/src/modules/orders/domain/**` целиком (Cart НЕ доменный агрегат — только `Order`/
`OrderItem`) и `apps/api/src/modules/orders/application/{cart,checkout}/**`; последующие эпики
(EP-11 возвраты, EP-12 сборка аптекой, EP-13 доставка, EP-14 споры) добавят СВОИ подпапки внутри
`orders/application/**`/`orders/presentation/**` — этот тикет их не создаёт и не резервирует.

## Что сделать

1. Создать `apps/api/migrations/0008_orders_cart.sql`, воспроизводящий 1:1 DDL «Группы D»
   (`11-database-schema.md` строки 686–815): `CREATE TABLE orders/order_items/cart/cart_items/
   favorites`, все `CONSTRAINT chk_*`/`COMMENT ON`. Колонки `courier_id`, `prescription_id`,
   `handover_otp_id` — БЕЗ `REFERENCES` на этом шаге (см. «Технический контекст»); проверить перед
   мержем реальный следующий свободный номер файла в `apps/api/migrations/`.
2. Проверить (`git log`/открытые PR), не создан ли уже enum `order_status` (общий блок `0002_enums.sql`,
   владелец — EP-01) СО значением `'confirmed'` (D-25, уже отражено в каноническом DDL). Если
   `0002_enums.sql` ещё не содержит `'confirmed'` на момент этой миграции — зафиксировать это как
   блокер в комментарии к PR и скоординироваться с владельцем EP-01, а не тихо форкать enum здесь.
3. Добавить Drizzle-схему `apps/api/src/db/schema/orders.ts` (`orders`, `orderItems`, `favorites`)
   и `apps/api/src/db/schema/cart.ts` (`cart`, `cartItems`).
4. Создать `apps/api/src/modules/orders/orders.module.ts` и `apps/api/src/modules/orders/index.ts`
   — публичный фасад, на этом шаге экспортирующий только типы и DI-токен `ORDERS_FACADE`
   (реализация — тикет DTJ-222).
5. Объявить порты к чужим модулям (ТОЛЬКО интерфейсы — application-тикеты должны компилироваться
   независимо от готовности других модулей):
   - `catalog-facade.port.ts` — `CatalogFacadePort.getMedicineSnapshot(medicineIds)` (актуальные
     `unitPrice`, `isPrescriptionRequired`, `controlCategory`).
   - `inventory-facade.port.ts` — `InventoryFacadePort.reserveStock(pharmacyId, items)`,
     `releaseStock(items)`.
   - `prescriptions-facade.port.ts` — `PrescriptionsFacadePort.isVerifiedFor(customerId,
     medicineIds)`.
   - `onboarding-facade.port.ts` — `OnboardingFacadePort.isPharmacyActive(pharmacyId)`.
   - `tenancy-facade.port.ts` — `TenancyFacadePort.resolveCommissionRate(tenantId, chainId,
     category)`.
   - `delivery-facade.port.ts` — `DeliveryFacadePort.calculateFee(pharmacyGeoPoint,
     deliveryGeoPoint)`.
   - `payment-invoice.port.ts` — `PaymentInvoicePort.createInvoice(cmd): Promise<Result<InvoiceRef,
     PaymentInvoiceError>>` — порт, который позже (EP-10, DTJ-242) реализует адаптер модуля
     `payments`; здесь только контракт, чтобы `CheckoutUseCase` (DTJ-227) не зависел от
     существования модуля `payments` физически (волна 7 стартует ПОСЛЕ волны 6 — см.
     «Риски»).
6. Создать `packages/contracts/src/orders.ts` (заготовки `OrderDto`, `OrderItemDto`, `CartDto`,
   `OrderStatus` enum 1:1 с БД) — наполняется по мере готовности следующих тикетов.
7. Добавить ОДНУ строку экспорта в `packages/contracts/src/index.ts` (баррель — владелец EP-01,
   правило «Пересекающееся владение» п.3 `tickets/00-EPICS.md`).
8. Прогнать `pnpm arch:check` — модуль не должен нарушать dependency-cruiser (никаких прямых
   импортов `modules/catalog|inventory|prescriptions|onboarding|tenancy|delivery|payments/*`
   в обход портов/фасадов).

## Критерии приёмки

1. **Given** применена миграция `0008_orders_cart.sql` к чистой БД (после `0001`..`0007`), **When**
   выполняется `\d orders`/`\d order_items`/`\d cart`/`\d cart_items`/`\d favorites`, **Then**
   структура таблиц и все `CONSTRAINT`/`COMMENT` совпадают 1:1 с `11-database-schema.md`.
2. **Given** модуль `orders` подключён в `AppModule`, **When** `pnpm --filter api build`, **Then**
   сборка проходит без циклических импортов.
3. **Given** разработчик пытается импортировать `modules/catalog/domain/*` напрямую из
   `modules/orders/application/*`, **When** `pnpm arch:check`, **Then** проверка падает с
   сообщением dependency-cruiser о нарушении межмодульной границы.
4. **Given** миграция уже применена, **When** применяется повторно, **Then** ошибки не возникает.

## Риски и подводные камни

- **Зависимость от EP-01 по enum `order_status`.** Канонический DDL (`11-database-schema.md`)
  уже включает значение `'confirmed'` (D-25) в `CREATE TYPE order_status` внутри общего
  `0002_enums.sql`. Если EP-01 создаёт этот файл параллельно и НЕ синхронизирован с последней
  версией `11-database-schema.md` — enum рискует не содержать `'confirmed'`, и `0008_orders_cart.sql`
  применится, но домен (DTJ-222) не сможет протестировать переход `Order.create() → confirmed`.
  Проверить фактическое состояние `0002_enums.sql` перед началом DTJ-221/222, эскалировать
  тимлиду EP-01, если расхождение найдено — НЕ патчить чужую миграцию самостоятельно.
- **`payment-invoice.port.ts` — контракт с модулем, которого ещё нет.** EP-10 стартует в волне 7,
  на волну позже EP-09 (волна 6, `tickets/00-EPICS.md` «Волны выполнения»). Порт объявляется здесь
  умышленно (не как импорт `modules/payments/*`), чтобы `CheckoutUseCase` (DTJ-227) компилировался
  и тестировался (с мок-реализацией порта) независимо от прогресса EP-10. Конкретный адаптер и
  DI-биндинг регистрируются тикетом DTJ-242 (EP-10) — до этого момента порт в `orders.module.ts`
  НЕ забинжен ни к чему (инжектится только в тестах через мок).
- **`favorites`** не используется ни одним тикетом этого набора — таблица создаётся здесь только
  потому, что относится к той же миграционной DDL-группе; use case'ы избранного — вне периметра
  EP-09/EP-10 (см. `tickets/00-EPICS.md`, не упомянуто явно ни в одном эпике R1 — риск, что
  `favorites` не имеет владельца; зафиксировать вопрос тимлиду проекта, не блокирует этот тикет).
- Файл `apps/api/src/modules/orders/orders.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/src/modules/orders/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `packages/contracts/src/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
