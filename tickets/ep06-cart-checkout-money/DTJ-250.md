## Задача

Физическое исполнение выплаты аптеке — последний шаг денежного пути non-cash заказа. В R1-проде
эта джоба практически находит НОЛЬ строк `due` (наличные не создают `payout_schedule`, банковские
методы выключены для реальных пользователей) — это ОЖИДАЕМОЕ состояние, не ошибка. Тем не менее
весь путь обязан быть построен и протестирован через `MockBankPayoutTransferProvider`, чтобы
демо/тестовые non-cash тенанты проходили его полностью автоматически.

## Технический контекст

`BankPayoutTransferPort` — Provider Pattern, аналогичный `PaymentProvider` (DTJ-237), но для
батч-переводов на мерчант-счета аптек, а не для клиентских платежей. `PayoutExecutionJob`
(BullMQ repeatable) выбирает `WHERE status='due'` (гарантия изоляции от `disputed` — DTJ-249),
батчами вызывает `transferBatch`, переводит в `paid` ТОЛЬКО подтверждённые провайдером строки.

## Что сделать

1. `BankPayoutTransferPort` (`application/ports/bank-payout-transfer.port.ts`):
   `transferBatch(payouts: readonly { payoutScheduleId, pharmacyMerchantRef, amountDiram }[]):
   Promise<Result<{ batchRef: string }, TransferError>>` — 1:1 по §6.3.
2. `MockBankPayoutTransferProvider` — немедленно (или с задержкой `MOCK_PAYOUT_DELAY_MS`, ENV,
   ASSUMPTION 0) переводит ВСЕ переданные строки в подтверждённые, возвращает `batchRef =
   'mock_batch_' + uuid()`.
3. `PayoutExecutionJob`: `SELECT * FROM payout_schedule WHERE status='due'` (батч, ASSUMPTION
   лимит на батч — переиспользовать `PAYOUT_BATCH_SIZE`, ENV, если общий паттерн батчинга уже
   существует в кодовой базе, иначе завести локально) → `BankPayoutTransferPort.
   transferBatch(...)`. Given успех (все строки подтверждены) → `UPDATE payout_schedule SET
   status='paid', paid_at=NOW(), payout_batch_ref=:batchRef WHERE id IN (...)`. Given частичный
   сбой (адаптер различает подтверждённые/неподтверждённые строки батча — интерфейс порта
   поддерживает это через детализацию в `TransferError` ИЛИ раздельные списки в успешном
   результате, зафиксировать конкретную форму на этапе реализации) → переводятся в `paid` только
   подтверждённые, остальные остаются `due` для следующего прогона (SRS-PAY-034 — НЕ оптимистичная
   пометка всего батча).
4. Зарегистрировать `MockBankPayoutTransferProvider` в `payments.module.ts` DI (аналогичный
   `PAYMENT_DRIVER`-переключатель, но для выплат — `PAYOUT_DRIVER=mock`, реальный адаптер — R3,
   вне периметра R1).

## Критерии приёмки

1. **Given** `payout_schedule.status='due'` для 3 заказов, **When** `PayoutExecutionJob`,
   **Then** все 3 переходят в `status='paid'`, `paid_at` заполнен, `payout_batch_ref` совпадает
   у всех (один батч).
2. **Given** `MockBankPayoutTransferProvider` симулирует частичный сбой (1 из 3 строк не
   подтверждена, тестовый мок), **When** `PayoutExecutionJob`, **Then** 2 строки `paid`, 1 строка
   ОСТАЁТСЯ `due`.
3. **Given** `payout_schedule.status='disputed'` для одного из заказов, **When**
   `PayoutExecutionJob` прогоняется, **Then** эта строка НЕ включена в батч (не запрошена вовсе —
   `WHERE status='due'` уже её исключает).
4. **Given** ноль строк `due` (типичное R1-прод состояние), **When** `PayoutExecutionJob`,
   **Then** джоба завершается без ошибки, `transferBatch` НЕ вызывается на пустом массиве
   (короткое замыкание перед сетевым вызовом).

## Риски и подводные камни

- **R1-прод — это состояние «ноль строк `due`» практически всегда** (см. «Задача») — легко
  случайно недотестировать реальный код-путь, полагаясь на то, что джоба «всё равно ничего не
  делает в проде». Явно поддерживать тестовое покрытие через демо/тестовый non-cash тенант — не
  снижать усилия на этом тикете из-за низкой частоты срабатывания в реальном трафике R1.
- Реальный `BankPayoutTransferPort`-адаптер (R3) — вне периметра, физическая часть батч-перевода
  на мерчант-счета аптек не реализуется здесь.
