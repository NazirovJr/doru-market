## Задача

Замыкает контракт, объявленный `orders`-модулем (DTJ-220/227): `PaymentInvoicePort` — интерфейс,
который `CheckoutUseCase` вызывает синхронно после commit заказа для non-cash методов. Этот тикет
пишет РЕАЛЬНУЮ реализацию (адаптер на стороне `payments`) и регистрирует её в общем DI-графе, плюс
даёт клиенту способ повторить попытку оплаты, если создание счёта упало из-за сетевого сбоя
провайдера, а заказ уже существует.

## Технический контекст

`PaymentInvoiceAdapter` (`infrastructure/adapters/payment-invoice.adapter.ts`) реализует
`PaymentInvoicePort`, объявленный в `apps/api/src/modules/orders/application/ports/
payment-invoice.port.ts` (DTJ-220) — межмодульный биндинг, а НЕ прямой импорт домена `orders`
(`02` §1.2, только через фасад/порт). DI-биндинг регистрируется в композиционном корне
`apps/api/src/app.module.ts` (правка одной строки/провайдера, тот же growing-file паттерн, что
DTJ-236 п.8) — конкретно: `OrdersModule.forRoot({ paymentInvoicePort: PaymentInvoiceAdapter })`
ЛИБО эквивалентный NestJS-паттерн (`useExisting`/`useClass` на токене, объявленном в `orders`) —
выбрать конкретный механизм на этапе реализации, сверяясь с фактической структурой DI орков к
этому моменту (сверить с тимлидом EP-09, если сигнатура порта менялась после DTJ-227).

`CreatePaymentInvoiceUseCase.execute(orderId, amountDiram, idempotencyKey)`: вызывает
`PaymentProvider.createInvoice()` (DTJ-237/238) — ПЕРЕД сетевым вызовом ОБЯЗАН проверить локально
`payment_operations` по `idempotency_key` (SRS-PAY-003: «проверить локально, затем вызвать
провайдера», не наоборот).

## Что сделать

1. `CreatePaymentInvoiceUseCase.execute(cmd: { orderId, amountDiram, currency: 'TJS',
   idempotencyKey, description, customerPhone })`:
   - `INSERT INTO payment_operations (idempotency_key, operation_type='create_bill',
     status='pending', ...) ON CONFLICT (idempotency_key) DO NOTHING RETURNING id` — конфликт
     (уже существует) → вернуть СОХРАНЁННЫЙ `InvoiceRef` без повторного сетевого вызова.
   - Иначе — `PaymentProvider.createInvoice(cmd)`. Успех → `UPDATE payment_operations SET
     provider_ref=..., status='pending'`, вернуть `InvoiceRef`. Ошибка/таймаут → пробросить
     `PaymentProviderTimeoutError` вызывающему коду (не проглатывать).
2. `PaymentInvoiceAdapter implements PaymentInvoicePort` — тонкая обёртка, вызывающая
   `CreatePaymentInvoiceUseCase.execute` и маппирующая результат в формат, ожидаемый портом
   `orders`-модуля (сигнатуры должны совпадать 1:1 — сверить с DTJ-220/227 перед реализацией).
3. `POST /api/v1/orders/:id/retry-payment` (роль `customer`, владелец заказа; `Idempotency-Key`
   обязателен) — эндпоинт для SRS-PAY-041: Given заказ существует в `pending_payment` БЕЗ
   `payment_transaction_id` (предыдущая попытка `createInvoice` упала после commit заказа), Then
   повторный вызов `CreatePaymentInvoiceUseCase` для СУЩЕСТВУЮЩЕГО заказа (новый
   `idempotencyKey`, НЕ переиспользующий провалившийся — тот уже помечен `status='pending'`/
   `failed` и не должен блокировать повтор). Given заказ не в `pending_payment` (уже оплачен/
   отменён) → `409 ORDER_NOT_RETRYABLE`.
4. Расширить `packages/contracts/src/payments.ts` (DTJ-236) типом `RetryPaymentResponseDto`.

## Критерии приёмки

1. **Given** `CreatePaymentInvoiceUseCase.execute` вызван дважды с ОДНИМ `idempotencyKey`,
   **When** второй вызов, **Then** `PaymentProvider.createInvoice` вызван РОВНО один раз (счётчик
   мока), оба вызова use case возвращают ОДИН И ТОТ ЖЕ `InvoiceRef`.
2. **Given** `PaymentProvider.createInvoice` бросает исключение (симуляция сбоя адаптера, не
   таймаут сети — тот же сценарий, что SRS-PAY-041), **When** `CheckoutUseCase` (DTJ-227) вызывает
   порт ПОСЛЕ commit заказа, **Then** заказ остаётся созданным в БД, ошибка не откатывает
   транзакцию заказа (проверка на границе интеграции обоих тикетов).
3. **Given** заказ `pending_payment` без `payment_transaction_id`, **When**
   `POST /api/v1/orders/:id/retry-payment`, **Then** новый `InvoiceRef` создан, `qrPayload`
   доступен клиенту.
4. **Given** заказ уже `paid_escrow`, **When** `retry-payment`, **Then** `409
   ORDER_NOT_RETRYABLE`.

  реальное решение принимается здесь; задокументировать выбранный паттерн в PR, чтобы DTJ-232
  (`RefundFacadePort`, тот же паттерн) мог его переиспользовать без повторного изобретения.
