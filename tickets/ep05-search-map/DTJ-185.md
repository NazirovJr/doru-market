## Задача
Единственный обязательный поисковый движок R1 на объём ≥300–10k SKU (Charter ADR №1, `SRS-CAT-013`).
Это ядро CUJ-1: без него ни ранжирование (DTJ-183), ни нормализация запроса (DTJ-182) не имеют
физического пути данных к пользователю. Тикет реализует `search()`-часть интерфейса `SearchProvider`
(`suggest()` — отдельный тикет DTJ-186, т.к. использует принципиально другой SQL-путь).

## Технический контекст
Слой `infrastructure`, `modules/catalog/infrastructure/adapters/postgres-search.adapter.ts`
реализует порт `SearchProvider` (DTJ-180). Это ЕДИНСТВЕННОЕ место в кодовой базе, которому разрешено
JOIN'ить таблицы чужих bounded contexts (`pharmacy_inventory`/`inventory_batches` — `inventory`;
`pharmacies`/`pharmacy_chains` — `onboarding`) напрямую в SQL, минуя чужие фасады (`SRS-CAT-014`) —
исключение из общего правила `02-CLEAN-ARCHITECTURE-AND-CODE.md` §1.1, обязано быть
задокументировано комментарием со ссылкой на `SRS-CAT-014` прямо в файле и явным исключением в
`.dependency-cruiser.cjs` (правку конфига делает владелец EP-19 — см. риски). Опирается на индексы
`11-database-schema.md` (`ix_medicines_search_vector`, `ix_medicines_trade_name_trgm`,
`ix_pharmacy_inventory_*`, `ix_pharmacies_geo_point`) и на `pharmacy_reliability_scores`
(DTJ-181). Финальная нормализация балла — делегируется `RankingScoreMapper` (DTJ-183), НЕ
пересчитывается повторно здесь.

## Что сделать
1. `postgres-search.sql.ts` — построитель SQL по трёхуровневому CTE из `SRS-CAT-021` (`candidates`
   → `offers` → `aggregated`), параметризованный через `pg`-плейсхолдеры (никаких конкатенаций
   строк с пользовательским вводом — SQL-инъекция, обязательная проверка ревью). Учесть:
   - `WHERE m.is_published = true AND m.control_category NOT IN ('psychotropic', 'narcotic')`
     на уровне `candidates` (`SRS-CAT-055`, первый рубеж обороны);
   - три способа попадания в `candidates`: `search_vector @@ plainto_tsquery('tajik_ru', :q)`,
     `trade_name % :q`, `inn_name % :q` — объединённые ИЛИ ОБА варианта запроса (`q1`/`q2` из
     `QueryNormalizationService`, DTJ-182) через `OR`-условие на уровне SQL (`SRS-CAT-024` п.3);
   - `JOIN pharmacy_chains ... WHERE status IN ('approved','active')` — условие видимости
     (`SRS-CAT-010`/п.3, наследуется из спецификации каталога, здесь применяется буквально);
   - `LEFT JOIN pharmacy_reliability_scores` с `COALESCE(prs.score, 3.5)` (DTJ-181 обеспечивает
     таблицу, здесь — обязательный `COALESCE`, дефект без него — `NULL` в ранжировании).
2. Отдельная ветка `searchByBarcode(barcode: string)`: `WHERE m.barcode = :barcode` точное
   совпадение (`SRS-CAT-024` п.2) — вызывается адаптером, когда `QueryNormalizationService` вернул
   `mode === 'barcode'` (маршрутизация — на уровне `SearchMedicinesUseCase`, DTJ-188, но САМ
   SQL-запрос ветки — часть этого тикета); не найдено → пустой результат, БЕЗ фолбэка на текстовый
   поиск (`SRS-CAT-024` п.2, `TC-CAT-005`).
3. Явный `sort=price_asc|price_desc|distance_asc` — минует композитную формулу целиком
   (`ORDER BY min_price ASC/DESC` или `ORDER BY nearest_distance ASC`), только `sort=relevance`
   (дефолт) применяет `RankingScoreMapper` (`SRS-CAT-021`, `SRS-CAT-048`). `distance_asc` без `geo`
   — уже отклонён на уровне валидации контракта (DTJ-190), сюда не долетает.
4. Перед выполнением запроса — `SET pg_trgm.similarity_threshold = 0.20` на соединении сессии через
   `pool`-хук (`SRS-CAT-015`, порог из `SRS-DB-017`, НЕ переопределять другим значением здесь).
5. `statement_timeout` — читать `SEARCH_QUERY_TIMEOUT_MS` (ENV, default `2000`) как per-route
   `pg`-опцию; перехватить КОНКРЕТНО код ошибки `57014 query_canceled` (не generic `catch`),
   залогировать `pino.error({ query, radiusMeters, tenantId }, 'search_query_timeout')`, вернуть
   доменную ошибку `SearchTemporarilyDegradedError` (маппится в `503 SERVICE_UNAVAILABLE
   details.reason='search_temporarily_degraded'` на уровне `presentation`, DTJ-190) — `SRS-CAT-075`.
6. Маппинг строки результата → `SearchResultItem`: сырые компоненты (`text_relevance`,
   `offers_count`, `nearest_distance`, `min_price`, `cheapest_pharmacy_reliability`) передаются в
   `RankingScoreMapper.normalize()` (DTJ-183) — АДАПТЕР НЕ считает `finalScore` сам, только собирает
   вход и вызывает доменный сервис.
7. Пустой результат (ни `tsvector`, ни `trgm`, ни штрихкод не дали совпадений) → `200`-совместимая
   структура `{ items: [], nextCursor: null, hasMore: false }`, НЕ исключение (`SRS-CAT-077`).
8. Заменить в `catalog.module.ts` временный `NullSearchProvider` (DTJ-180) на реальную развилку:
   `SEARCH_DRIVER === 'postgres'` (дефолт) → `PostgresSearchProvider`; ветка `elasticsearch` пока
   резолвится в `NullSearchProvider` (ES-адаптер — DTJ-191, R2).
9. `promoted`/«не участвует в промо-подборках» (`SRS-CAT-056`, поле `isPromotable`) — вычислить как
   `controlCategory NOT IN ('potent','psychotropic','narcotic')` и вернуть в маппинге результата как
   дополнительное поле DTO (не входит в контракт `SRS-CAT-011` дословно, но нужно `presentation`-слою
   для Rx-бейджа — добавить полем `isPromotable` расширяя `SearchResultItem` ЛОКАЛЬНО в адаптере,
   зафиксировать в PR как осознанное расширение сверх минимального интерфейса порта).

## Критерии приёмки
1. Given запрос `«цытрамон»` (опечатка), медикамент «Цитрамон» с `similarity=0.62`, без
   `tsvector`-хита, 4 аптеки в радиусе на `800 м`, цена `12.00 TJS` (единственная в странице,
   `reliability=4.2/5`), When `search()`, Then `finalScore = 0.770 ± 0.001` (воспроизведение
   `TC-CAT-002`/`SRS-CAT-020` целиком через реальный SQL + `RankingScoreMapper`, не только unit
   формулы изолированно).
2. Given 13-значная строка, НЕ существующая в `medicines.barcode`, When `search()` вызван адаптером
   в режиме `barcode`, Then `data: []`, обычный текстовый фолбэк НЕ выполнен (`TC-CAT-005`).
3. Given `medicine.controlCategory = 'narcotic'` среди потенциальных кандидатов текстового поиска,
   When `search()`, Then эта запись отсутствует в результате НИ ПРИ КАКИХ условиях (негативный
   сценарий, `SRS-CAT-055`, первый рубеж — WHERE-условие в `candidates`).
4. Given принудительно медленный запрос (интеграционный тест с `pg_sleep` внутри тестового
   представления), превышающий `SEARCH_QUERY_TIMEOUT_MS`, When `search()`, Then выброшена
   `SearchTemporarilyDegradedError`, залогирован `search_query_timeout` (`TC-CAT-025`) — НЕ падение
   с generic `500`.
5. Given `pharmacy_chains.status = 'suspended'` для родительской сети единственной аптеки, несущей
   товар, When `search()`, Then товар НЕ появляется в результатах (`TC-CAT-019`) — негативный
   сценарий видимости.

## Риски и подводные камни
- `.dependency-cruiser.cjs` принадлежит EP-19 (`00-EPICS.md` «Пересекающееся владение» п.5) — этот
  тикет НЕ правит конфиг самостоятельно, а заводит согласование с владельцем EP-19 на добавление
  точечного исключения `allowed: true` для конкретного файла; до согласования `pnpm arch:check`
  будет падать на этом файле — заложить время на координацию, не блокирующий тикет сам по себе, но
  блокирующий `pnpm verify`.
- SQL-заготовка §3.3 в спецификации содержит явно помеченный «плейсхолдер для веса C» (`manufacturer
  weight`) — реализующий разработчик обязан заменить его РЕАЛЬНЫМ вычислением веса `C` через
  `ts_rank_cd`/явный `CASE` на совпадение `manufacturer_name`, не оставлять плейсхолдер как есть
  (в спецификации отмечено «см. приложение application-слоя» — уточнить с архитектором при
  неоднозначности, не изобретать вес самостоятельно без сверки с `SRS-CAT-019` п.2 `textRelevance=0.7`).
- Индекс `pg_trgm.similarity_threshold` — сессионная настройка, обязана применяться на каждое
  новое соединение из пула (`pool`-хук), не один раз глобально — иначе часть запросов в высоконагруженном
  пуле использует дефолтный порог PostgreSQL (`0.3`), а не `0.20`, что незаметно испортит `TC-CAT-001`
  под нагрузкой, но не в единичном тесте.
- Файл `apps/api/src/modules/catalog/catalog.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
