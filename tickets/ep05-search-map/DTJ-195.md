## Задача
Реализация чтения пинов карты — второе (после `postgres-search.adapter.ts`, DTJ-185) место в
кодовой базе, которому нужен прямой доступ к `pharmacies`/`pharmacy_inventory` через GiST-индекс
`bbox`, минуя ранжирование поиска (карта работает по видимой области, не по радиусу-релевантности).

## Технический контекст
Слой `infrastructure`, реализует `PharmacyMapRepository` (DTJ-194). Использует `ST_MakeEnvelope` +
оператор `&&` (GiST) — принципиально ОТДЕЛЬНЫЙ от `ST_DWithin`-пути поиска (`SRS-CAT-052`,
обоснование — `bbox` эффективнее для панорамирования карты клиентом). Индекс `ix_pharmacies_geo_point`
(GiST, уже определён `11-database-schema.md`) переиспользуется для обоих путей. Требует того же
рубежа видимости, что и поиск: `pharmacy.status = 'active'`, `pharmacy_chains.status IN
('approved','active')` — ЕСЛИ этот SQL-фрагмент уже вынесен переиспользуемым строителем в DTJ-185
(«Что сделать» п.5 того тикета) — импортировать оттуда, не дублировать текстом (C15 DRY); если к
моменту начала этого тикета DTJ-185 ещё не вынес фрагмент как переиспользуемый — написать здесь
локально и завести технический долг на объединение (не блокировать сдачу ожиданием другого тикета).

## Что сделать
1. `findPinsInBbox(query: BboxQuery): Promise<readonly PharmacyMapPin[]>`:
   ```sql
   SELECT ph.id, ph.name,
          ST_X(ph.geo_point::geometry) AS lon, ST_Y(ph.geo_point::geometry) AS lat,
          ph.is_24_7, ph.opening_time, ph.closing_time
   FROM pharmacies ph
   JOIN pharmacy_chains pc ON pc.id = ph.chain_id AND pc.status IN ('approved', 'active')
   WHERE ph.status = 'active'
     AND ph.geo_point && ST_MakeEnvelope(:lonMin, :latMin, :lonMax, :latMax, 4326)
   LIMIT 500; -- SRS-CAT-061, клиент кластеризует визуально при зуме
   ```
   `is_24_7`/`opening_time`/`closing_time` возвращаются СЫРЫМИ полями — вычисление `isOpenNow`
   происходит НЕ здесь (репозиторий — чистый I/O-адаптер, без бизнес-правила перехода через
   полночь), а в `GetPharmacyMapPinsUseCase` (DTJ-196) через `PharmacyOpeningHoursPolicy` (DTJ-184,
   переиспользуется, не дублируется).
2. Given `medicineId` передан — ДОПОЛНИТЕЛЬНЫЙ `LEFT JOIN LATERAL` на `pharmacy_inventory` для
   САМОГО дешёвого/первого активного предложения ЭТОЙ аптеки по конкретному медикаменту:
   ```sql
   LEFT JOIN LATERAL (
     SELECT pi.price_tjs, pi.stock_quantity, pi.last_synced_at
     FROM pharmacy_inventory pi
     WHERE pi.pharmacy_id = ph.id AND pi.medicine_id = :medicineId AND pi.stock_quantity > 0
     ORDER BY pi.price_tjs ASC LIMIT 1
   ) offer ON true
   ```
   `isStale` вычисляется по той же формуле, что и в поиске (`now - last_synced_at >
   INVENTORY_DELTA_SLA_MINUTES * 3`, `SRS-CAT-052`/§7.5 переиспользование правила — вынести общей
   утилитой рядом с DTJ-185, не переизобретать).
3. Given `medicineId` НЕ передан — поле `offer` в `PharmacyMapPin` — `null`, JOIN на
   `pharmacy_inventory` не выполняется вовсе (оптимизация — не тратить JOIN, если он не нужен).
4. Тот же рубеж исключения контролируемых веществ применяется КОСВЕННО: пин аптеки сам по себе не
   содержит `medicine`-данных при отсутствии `medicineId`, а при наличии — `pharmacy_inventory`
   уже не должна содержать позиции запрещённых категорий на уровне `medicines.is_published`/
   `control_category` (проверка — на стороне `medicines`, добавить `JOIN medicines m ON m.id =
   :medicineId AND m.control_category NOT IN ('psychotropic','narcotic')` В LATERAL-подзапрос как
   defensive-рубеж, даже если ожидается, что `medicineId` с фронтенда всегда легитимный —
   `SRS-CAT-055`, defense in depth).

## Критерии приёмки
1. Given 3 аптеки внутри `bbox`, 2 снаружи, When `findPinsInBbox()`, Then возвращены РОВНО 3 пина.
2. Given `medicineId` передан, у одной из аптек в bbox есть остаток `>0`, у другой — `0`, When
   запрос, Then у первой `offer !== null`, у второй `offer === null` (не показывать нулевой остаток
   как предложение).
3. Given `medicineId` НЕ передан, When запрос, Then `offer === null` для ВСЕХ пинов, ДОПОЛНИТЕЛЬНЫЙ
   JOIN на `pharmacy_inventory` не выполнен (проверяется через `EXPLAIN`, отсутствие узла плана по
   `pharmacy_inventory`).
4. Given аптека внутри bbox, но её `pharmacy_chains.status = 'suspended'`, When запрос, Then эта
   аптека ОТСУТСТВУЕТ в результате (`TC-CAT-019`-эквивалент для карты) — негативный сценарий.
5. Given `medicineId` указывает на медикамент с `control_category = 'narcotic'`, When запрос, Then
   `offer === null` для всех пинов НЕЗАВИСИМО от фактического остатка (defense in depth).

## Тест-план
Интеграционные (Testcontainers Postgres, фикстуры аптек с известными координатами): попадание/
непопадание в bbox (границы включительно — `&&`-оператор GiST, проверить угловой случай точка на
границе envelope), `medicineId` присутствует/отсутствует, `offer=null` при нулевом остатке,
исключение suspended-сети, исключение narcotic. `LIMIT 500` — тест с искусственно большим числом
фикстур (или мок-проверка наличия `LIMIT` в сгенерированном SQL). Порог покрытия `infrastructure/`
≥ 70 %.
