## Задача
Архитектурное основание порта `SearchProvider` закладывается сразу целиком (`04-SCOPE-DECISION-
PIVOT.md` §2.2) — ретрофит порта дороже проектирования с первого дня, даже если конкретный адаптер
(Elasticsearch) переносится на R2. Этот тикет — НЕ реализация полноценного ES-поиска (это отдельная
работа R2 при фактическом росте каталога за пределы комфортной зоны PostgreSQL FTS), а подтверждение,
что порт `SearchProvider` (DTJ-180) действительно компилируется со вторым адаптером без изменения
контракта, плюс механизм безопасного отказа (circuit breaker), который понадобится в R2 без
изменения `SearchMedicinesUseCase`.

## Технический контекст
Слой `infrastructure`. `SEARCH_DRIVER=elasticsearch` подключает `ElasticSearchProvider` в
`catalog.module.ts` (тот же переключатель, что DTJ-185 подготовил для `postgres`). Синхронизация
данных из PostgreSQL в Elasticsearch — ОТДЕЛЬНАЯ работа (консьюмер `outbox` на
`MedicinePublishedEvent`/`InventorySyncBatchCompletedEvent`), НЕ входит в этот тикет (`SRS-CAT-016`
явно откладывает полную реализацию на факт роста каталога).

## Что сделать
1. `ElasticSearchProvider implements SearchProvider` — минимальная реализация, посылающая запрос в
   Elasticsearch (индекс `medicines_{tenant_slug}` ИЛИ единый индекс с полем `tenant_id` — решение
   фиксируется здесь как ASSUMPTION, документируется комментарием, окончательное решение — на
   момент полной реализации R2, `SRS-CAT-016`). Для R1/этого тикета — реализовать ТОЛЬКО базовый
   `match`-запрос без полного портирования формулы ранжирования §3 (полная паритетность с Postgres —
   вне scope, `SRS-CAT-017`: интерфейс спроектирован полным именно чтобы не блокировать это сейчас).
2. `SearchProviderCircuitBreaker` (application-совместимая обёртка над `SearchProvider`,
   физически — infrastructure-декоратор, оборачивающий реальный порт): после `N=5`
   (`CIRCUIT_BREAKER_FAILURE_THRESHOLD`, именованная константа) последовательных отказов
   (`ECONNREFUSED`/таймаут) Elasticsearch — временно переключает трафик на `PostgresSearchProvider`
   как fallback (`SRS-CAT-076`), алерт в лог (`pino.error`); автоматический возврат на Elasticsearch —
   при следующем успешном `GET _cluster/health`.
3. Подключение в `catalog.module.ts`: `SEARCH_DRIVER === 'elasticsearch'` → `SearchProviderCircuitBreaker`,
   оборачивающий `ElasticSearchProvider` с fallback на `PostgresSearchProvider` (оба адаптера
   инжектируются в circuit breaker явно, не через повторный DI-lookup внутри).
4. НЕ вводить условную логику «если Elasticsearch» нигде ВНЕ `catalog.module.ts` (`SRS-CAT-017`) —
   ревью обязано проверить отсутствие `if (searchDriver === 'elasticsearch')` в
   `SearchMedicinesUseCase`/контроллере.

## Критерии приёмки
1. Given `SEARCH_DRIVER=elasticsearch`, кластер недоступен 5 попыток подряд, When 6-й запрос, Then
   автоматический фолбэк на `PostgresSearchProvider`, ответ `200` с валидными результатами (не `503`)
   (`TC-CAT-026`).
2. Given порт `SearchProvider` реализован ОБОИМИ адаптерами (`PostgresSearchProvider`,
   `ElasticSearchProvider`), When `pnpm typecheck`, Then оба класса компилируются без расширения
   интерфейса порта (проверка форвард-совместимости, `SRS-CAT-017`).
3. Given circuit breaker переключился на fallback, When следующий `GET _cluster/health` к ES
   успешен, Then трафик автоматически возвращается на `ElasticSearchProvider` — негативный сценарий:
   возврат НЕ происходит просто по истечении времени, только по факту успешного health-check.

## Тест-план
Unit: circuit breaker — счётчик отказов, порог переключения, восстановление по health-check
(мокированные вызовы `ElasticSearchProvider`/`PostgresSearchProvider`, без реального ES-кластера).
Интеграционный с реальным Elasticsearch — НЕ обязателен для R1-тикета (полная интеграция — R2), но
`ElasticSearchProvider` обязан иметь хотя бы один smoke-тест против `elasticsearch` Testcontainers,
подтверждающий, что базовый `match`-запрос действительно возвращает результат в форме
`SearchResultPage`. Порог покрытия `infrastructure/` ≥ 70 %.

## Риски и подводные камни
- Этот тикет — намеренно НЕПОЛНАЯ реализация R2-функциональности (расхождение формулы ранжирования
  между Postgres/ES не устраняется здесь) — при постановке в спринт явно предупредить, что «готово»
  здесь означает «порт и circuit breaker существуют и компилируются», не «Elasticsearch полностью
  заменяет Postgres в проде».
- Решение по схеме индекса (`per-tenant` vs `единый индекс + tenant_id`) — ASSUMPTION, требует
  утверждения архитектором до реальной эксплуатации R2 (в этом тикете достаточно зафиксировать выбор
  комментарием, не заводить отдельный ADR — само решение не блокирует R1).
- Если к моменту выполнения этого тикета реальный Elasticsearch-кластер недоступен даже для
  Testcontainers в CI-окружении, smoke-тест может быть временно помечен `skip` с тикетом-напоминанием
  для EP-19 (инфраструктура CI) — не блокировать весь тикет из-за отсутствия окружения, но не
  оставлять пропуск незадокументированным.
