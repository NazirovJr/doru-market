## Задача
Единственная точка входа, которую вызывает `presentation` (DTJ-190) для полнотекстового поиска —
собирает воедино нормализацию запроса, кэш, вызов `SearchProvider`, ranking-режимы (обычный/
browsing) и логирование для аналитики. Без этого use case все предыдущие тикеты (DTJ-182/183/184/
185/187) остаются несвязанными компонентами.

## Технический контекст
Слой `application`, один класс — один публичный метод `execute()` (`02-CLEAN-ARCHITECTURE-AND-CODE.md`
§3.1). Получает через конструктор: `SEARCH_PROVIDER` (порт, DTJ-180/185), `QueryNormalizationService`
(DTJ-182 — доменный сервис, application МОЖЕТ вызывать domain напрямую), `PharmacyOpeningHoursPolicy`
(DTJ-184), `SearchCacheService` (DTJ-187), репозиторий записи `search_query_log` (DTJ-181 — простой
insert-порт, не полноценный агрегат). НЕ импортирует `PostgresSearchProvider` напрямую — только
токен `SEARCH_PROVIDER` (`02` §1.3).

## Что сделать
1. `SearchMedicinesUseCase.execute(command: SearchMedicinesCommand): Promise<SearchResultPage>`:
   а) вычислить ключ кэша, при попадании — вернуть закэшированное значение через
      `RedisLockGuard.withLock` (stampede-защита оборачивает весь блок вычисления, не только SQL);
   б) внутри `compute()`: нормализовать `text` через `QueryNormalizationService.normalize()`
      (DTJ-182) — при `mode === 'barcode'` маршрутизировать в `searchByBarcode()` адаптера
      (`SRS-CAT-024` п.2), иначе передать `{ q1: primary, q2: alternate }` в `SearchProvider.search()`;
   в) given `filters.categoryId` задан И `text === ''` (browsing-режим) — принудительно
      `textRelevance = 1.0` для всех кандидатов через `RankingScoreMapper.forCategoryBrowsing()`
      (DTJ-183) И переключить дефолтную сортировку на `price_asc`, если клиент явно не указал `sort`
      (`SRS-CAT-023`);
   г) применить фильтры `openNowOnly`/`is24x7Only` через `PharmacyOpeningHoursPolicy` (DTJ-184) —
      ВНИМАНИЕ: эти фильтры логически применяются на уровне SQL-джойна аптек в `PostgresSearchProvider`
      (DTJ-185 берёт статические поля `is_24_7`/`opening_time`/`closing_time` из `pharmacies` и сам
      вызывает ту же формулу через переиспользуемую SQL-функцию ИЛИ этот use case передаёт вычисленное
      «сейчас» время как параметр запроса — выбрать один путь, задокументировать решение в PR: SQL
      не может вызвать TypeScript-`ClockPort`, поэтому корректный путь — use case вычисляет
      `nowInTenantTz` ОДИН РАЗ через `PharmacyOpeningHoursPolicy`/`ClockPort` и передаёт как
      параметр `SearchQuery`, адаптер использует голое время в SQL-сравнении, не переоткрывая
      бизнес-правило «переход через полночь» второй раз в SQL-синтаксисе — SQL получает уже
      вычисленный булев результат по каждой аптеке НЕВОЗМОЖНО без джойна на уровне БД, поэтому
      реальное решение — портировать `isOpenNow()`-выражение как SQL CASE WHEN внутри
      `postgres-search.sql.ts` (DTJ-185), а `PharmacyOpeningHoursPolicy` остаётся источником ПРАВДЫ
      и юнит-тестов алгоритма, SQL — его буквальный SQL-эквивалент, сверяемый интеграционным тестом
      против доменного unit-теста тем же набором кейсов, чтобы расхождение логики было невозможно
      незамеченным);
   д) вызвать `SearchProvider.search()`, замапить результат через `RankingScoreMapper` (когда
      `sort=relevance`);
   е) записать строку в `search_query_log` (`tenant_id`, `customer_id | null` для гостя,
      `query_text` — исходный `text` ДО нормализации, `results_count`) — `SRS-CAT-069`;
   ж) закэшировать результат (30 сек, `SRS-CAT-058`).
2. Given `radiusMeters` задан, но `geo` отсутствует — тихо игнорировать `radiusMeters` (не ошибка
   клиента, `SRS-CAT-044` — но эта валидация фактически уже на уровне контракта DTJ-190, здесь —
   defensive-дубль на случай прямого вызова use case в тестах).
3. Гонка «цена изменилась между поиском и открытием карточки» (`SRS-CAT-072`) — этот use case НЕ
   принимает мер (карточка всегда делает свежий запрос, ответственность EP-04) — явно НЕ
   реализовывать инвалидацию по цене здесь, только зафиксировать комментарием со ссылкой на
   `SRS-CAT-072`, почему это не баг.

## Критерии приёмки
1. Given валидный текстовый запрос с `geo`, When `execute()`, Then возвращается `SearchResultPage` с
   элементами, отсортированными по `finalScore DESC` (сквозной интеграционный сценарий, объединяющий
   DTJ-182/183/184/185/187).
2. Given `filters.categoryId=5, text=''`, When `execute()` без явного `sort`, Then результат
   отсортирован по цене возрастания, `textRelevance=1.0` у всех элементов (`TC-CAT-023`).
3. Given идентичный запрос выполнен дважды подряд в течение 30 секунд, When второй вызов, Then
   `SearchProvider.search()` НЕ вызван повторно (ответ из кэша) — проверяется через мок-счётчик
   вызовов провайдера.
4. Given `text = '4870123456789'` (валидный штрихкод, НЕ существующий в базе), When `execute()`,
   Then вызвана ветка `searchByBarcode()`, а не обычный текстовый поиск, результат — `data: []`
   (`TC-CAT-005` на уровне use case, дублирует проверку DTJ-185 на уровне оркестрации).

## Тест-план
Unit (с моками `SEARCH_PROVIDER`, `SearchCacheService`, `QueryNormalizationService`,
`PharmacyOpeningHoursPolicy`, репозитория лога): маршрутизация штрихкод/текст, browsing-режим и
переключение дефолтной сортировки, кэш-хит не вызывает провайдер повторно, запись в
`search_query_log` вызывается ровно один раз на выполнение. Интеграционный (полный стек Postgres +
Redis): сквозной happy path, TC-CAT-023. Порог покрытия `application/` ≥ 90 %.

## Риски и подводные камни
- Пункт 1г («открыто сейчас» в SQL) — самая тонкая часть тикета: бизнес-правило перехода через
  полночь обязано существовать И в domain/application (`PharmacyOpeningHoursPolicy`, DTJ-184, для
  карты и unit-тестируемости), И как SQL-эквивалент внутри composite-запроса (DTJ-185, для
  фильтрации на уровне БД, т.к. фильтровать миллион строк в памяти после выборки — неприемлемо по
  производительности). Рассинхронизация этих двух версий логики — реальный риск; смягчение — таблично
  прогнать ОДИНАКОВЫЙ набор кейсов (`TC-CAT-020` и его варианты) и через unit-тест `DTJ-184`, и через
  интеграционный SQL-тест `DTJ-185`, обе стороны должны совпадать.
- `search_query_log.customer_id` требует контекста аутентификации (гость vs залогиненный) — если
  guard/декоратор пользователя ещё не унифицирован на момент реализации (зависит от EP-01), временно
  принимать `customerId: string | null` явным параметром команды, не залезать в HTTP-контекст изнутри
  use case (нарушение правила «use case не знает про HTTP», `02` §3.2).
- Кэш-ключ включает `filters` целиком — если набор полей `SearchFilters` расширится в будущем
  (например, EP-07 добавит фильтр по аналогам), старые закэшированные ключи станут «немного другого
  формата» без коллизии (короткий TTL 30 сек делает это безопасным — устаревшие ключи просто истекут).
