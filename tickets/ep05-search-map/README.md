## Рекомендуемый порядок для параллельной команды

**Дорожка A (данные/SQL)**: `DTJ-181` → `DTJ-185` → `DTJ-186` → `DTJ-195`
**Дорожка B (домен/формулы)**: `DTJ-182`, `DTJ-183`, `DTJ-184` (параллельно, все зависят только от `DTJ-180`)
**Дорожка C (инфраструктура кэша)**: `DTJ-187` (параллельно дорожкам A/B, зависит только от `DTJ-180`/`DTJ-181`)
**Точка синхронизации 1**: `DTJ-188`/`DTJ-189` требуют завершения дорожек A+B+C для своих частей.
**Дорожка D (presentation+frontend поиска)**: `DTJ-190` → `DTJ-192` → `DTJ-193`
**Дорожка E (карта, стартует после готовности `DTJ-184`/`DTJ-185`)**: `DTJ-194` → (`DTJ-195` ∥ `DTJ-198`) → `DTJ-196` → `DTJ-197` → `DTJ-199`

`DTJ-180` и `DTJ-181` — единственные тикеты БЕЗ зависимостей, стартуют первыми и параллельно.
`DTJ-191` (R2, ElasticSearch) не блокирует и не блокируется ничем внутри R1-периметра — можно
взять в любой момент после `DTJ-180`, приоритет ниже остальных 19 тикетов.

## Известные пограничные зоны с другими эпиками (не тикеты, а риски координации)

1. **Analog Engine (EP-07)** — «лента дешевле рядом» на главном экране (`SRS-CAT-001`) требует
   расчёта экономии, который выполняет `FindAnalogsUseCase` из EP-07, не EP-06. `DTJ-192`
   реализует только позиционирование строки поиска, не сам виджет ленты — см. риски `DTJ-192`.
2. **Каталог (EP-04)** — карточка товара (`GET /medicines/:id`, §8 модульного документа) и дерево
   категорий не входят в этот диапазон, они — зона EP-04. Поиск потребляет опубликованные данные
   каталога, но не создаёт их.
3. **`packages/ui`/`packages/i18n` (EP-18)** — `MapView`-обёртка (`DTJ-198`), `Skeleton`/`Chip`/
   `EmptyState`/`OfflineBanner` (`DTJ-192`/`DTJ-193`), `useDebouncedValue`-хук — если базовые
   компоненты ещё не готовы от EP-18 на момент реализации, соответствующие тикеты создают локальную
   временную версию с обязательным тикетом-переносом в том же спринте (`SRS-UX-034`).
4. **`.dependency-cruiser.cjs` (EP-19)** — `DTJ-185`/`DTJ-195` требуют точечного исключения правила
   «нет прямого импорта чужой схемы БД» — согласование с владельцем EP-19 заложено как риск в обоих
   тикетах, не блокирует начало работы, но блокирует финальный зелёный `pnpm verify`.
5. **`RecomputePharmacyReliabilityJob`/trending-джоба (EP-17, волна 11)** — таблица
   `pharmacy_reliability_scores` и ключ `trending_searches:{tenantId}` создаются этим эпиком
   (`DTJ-181`), но ЗАПОЛНЯЮТСЯ джобами EP-17, которые появятся значительно позже по волнам. Пустое
   состояние — ожидаемое на протяжении почти всего R1, обработано дефолтами (`3.5`/пустой массив),
   не считать это дефектом при код-ревью до готовности EP-17.

Из 78 требований `SRS-CAT-001..078` документа `20-module-catalog-search.md`:

  (порт+адаптеры, DTJ-180/185/186/191), §3 (ранжирование, DTJ-183/185), §4 (обработка запроса,
  DTJ-182), §5 (автодополнение, DTJ-186/189), §7 (фильтры/гео, DTJ-184/185/193), §9 (карта, DTJ-194
  ..199), §10 (безопасность поиска — SRS-CAT-055/056/057, DTJ-185/190), §11 (кэширование поиска,
  DTJ-187), §12 (производительность — целевые p95 зашиты в критерии приёмки DTJ-185/186/190), §14.1
  /14.2/14.3 (доп. схема БД для поиска, DTJ-181).
- **Сознательно НЕ покрыты** (чужая зона EP-07/EP-04, см. «Известные пограничные зоны»): §1.1-1.3,
  1.5-1.9 (модель каталога — EP-04), §6 целиком (Analog Engine — EP-07), §8 (карточка товара —
  EP-04/EP-07), §14.4 (`i18n_overrides.review_status` для дисклеймера аналогов — EP-07), §13
  (`CatalogFacade` целиком — общий фасад модуля, владение по факту первого эпика, добравшегося до
  необходимости экспорта — вероятно EP-04, EP-06 использует, но не определяет файл `index.ts`
  модуля `catalog` целиком, только добавляет use case'ы в существующий список).
