## Задача
Формула ранжирования (§3 `20-module-catalog-search.md`) и автодополнение опираются на две таблицы
и один индекс, которых нет в базовой схеме `11-database-schema.md` — они введены этим модульным
документом как обоснованные дополнения (§14). Без них `PostgresSearchProvider` (DTJ-185/186) не
может быть реализован: SQL из §3.3 буквально джойнит `pharmacy_reliability_scores`. Тикет —
инфраструктурная подготовка, разблокирующая всю SQL-часть поиска.

## Технический контекст
Слой `infrastructure`, но по факту — чистые Drizzle-схемы + SQL-миграция, без бизнес-логики.
Таблицы READ-ONLY для поиска: `pharmacy_reliability_scores` заполняется ежесуточной джобой
`RecomputePharmacyReliabilityJob`, которая относится к контексту `analytics` (владение — EP-17,
волна 11) — эта джоба НЕ входит в данный тикет и не будет существовать до гораздо более поздней
волны. До её появления таблица пуста, и SQL-запрос ранжирования (DTJ-185) обязан работать корректно
на пустой таблице через `COALESCE(prs.score, 3.5)` (`SRS-CAT-028`, TC-CAT-028) — это уже
предусмотрено спецификацией, здесь только создаётся сама таблица со значениями по умолчанию.
`search_query_log` заполняется КАЖДЫМ вызовом `SearchMedicinesUseCase` (DTJ-188, этот же эпик).

## Что сделать
1. Создать Drizzle-схему `pharmacy-reliability-scores.schema.ts`: `pharmacy_id UUID PRIMARY KEY
   REFERENCES pharmacies(id) ON DELETE CASCADE`, `score NUMERIC(3,2) NOT NULL DEFAULT 3.50`,
   `orders_considered INT NOT NULL DEFAULT 0`, `computed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`,
   `CHECK (score BETWEEN 0 AND 5)` — дословно по DDL `SRS-CAT-066`, включая `COMMENT ON TABLE`
   (это read-модель, не доменный агрегат `PharmacyAccount`, нет UI-виджета звёзд).
2. Создать Drizzle-схему `search-query-log.schema.ts`: `id UUID PK default gen_random_uuid()`,
   `tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE`, `customer_id UUID
   REFERENCES users(id) ON DELETE SET NULL`, `query_text VARCHAR(255) NOT NULL`, `results_count INT
   NOT NULL`, `clicked_medicine_id UUID REFERENCES medicines(id) ON DELETE SET NULL`,
   `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` — по DDL `SRS-CAT-069`. Индекс
   `ix_search_query_log_trending (tenant_id, created_at DESC)`.
3. Добавить индекс `ix_medicines_trade_name_prefix ON medicines (lower(unaccent(trade_name))
   text_pattern_ops) WHERE is_published = true` (`SRS-CAT-068`) — партиальный B-tree для веток
   автодополнения `length(q) < 3` (`SRS-DB-019`).
4. Сгенерировать миграцию через `drizzle-kit generate` (следующий по порядку номер файла в
   `apps/api/migrations/`, НЕ хардкодить номер вручную, сверить с последней миграцией из EP-01/EP-04
   на момент выполнения).
5. Добавить обе схемы в баррель `apps/api/src/db/schema/index.ts` (одна строка на файл).
6. Задокументировать в комментарии над `pharmacy-reliability-scores.schema.ts`, что джоба заполнения
   принадлежит `analytics` (EP-17) и появится позже — таблица пуста в течение волн 5-10, это
   ОЖИДАЕМОЕ состояние, не баг ранжирования.
7. Настроить job очистки `search_query_log` retention (`ASSUMPTION 180 дней`, `SRS-CAT-070`) —
   для R1 достаточно ENV-константы `SEARCH_QUERY_LOG_RETENTION_DAYS=180` и BullMQ repeatable-джобы
   `PruneSearchQueryLogJob` (ежедневно 04:30 `Asia/Dushanbe`, `DELETE ... WHERE created_at <
   NOW() - INTERVAL`), реализация тривиальна — не растягивать на отдельный тикет.

## Критерии приёмки
1. Given применена миграция, When `SELECT * FROM pharmacy_reliability_scores`, Then таблица пуста,
   но `INSERT` с валидным `pharmacy_id` и `score=5.00` проходит, `score=5.01` бросает
   `CHECK constraint violation`.
2. Given применена миграция, When `EXPLAIN SELECT ... WHERE lower(unaccent(trade_name)) LIKE
   'парац%'` на опубликованном медикаменте, Then план запроса использует
   `ix_medicines_trade_name_prefix` (Index Scan, не Seq Scan) — негативный сценарий: без `WHERE
   is_published = true` в запросе индекс не применяется (партиальный индекс), это ожидаемое
   поведение, зафиксировать явно в тесте.
3. Given `PruneSearchQueryLogJob` выполнена на записи старше 180 дней, When джоба запускается, Then
   такие записи удалены, записи младше 180 дней — нет.
4. Given `pharmacy_id` не существует в `pharmacies`, When `INSERT INTO pharmacy_reliability_scores`,
   Then `FOREIGN KEY violation` (негативный сценарий, целостность).

## Тест-план
Интеграционные (Testcontainers Postgres): миграция применяется на чистой БД без ошибок; CHECK-
ограничение `score`; партиальный индекс используется в плане запроса (`EXPLAIN`); FK-ограничения
обеих таблиц; `PruneSearchQueryLogJob` unit-тест с фиксированным `Clock` (не реальным временем).
E2E не требуется. Порог покрытия для чистых Drizzle-схем формально не считается (нет исполняемой
логики), но `PruneSearchQueryLogJob` — application-код, ≥90%.

## Риски и подводные камни
- Номер файла миграции — источник конфликтов при параллельной разработке нескольких эпиков в одной
  волне (EP-04 тоже пишет миграции). Решение: генерировать номер непосредственно перед мержем, не
  резервировать заранее.
- `pharmacy_reliability_scores` пуста весь R1 до готовности EP-17 (волна 11) — если EP-17
  задержится за пределы приёмки R1, `COALESCE(..., 3.5)` в ранжировании (DTJ-185) остаётся
  постоянным дефолтом для ВСЕХ аптек — это не баг данного тикета, но важно для code review не
  спутать «функция не работает» с «данные ещё не накоплены».
- `apps/api/src/db/schema/index.ts` — общий баррель-файл, правится многими эпиками одновременно
  (аналогично `packages/contracts/index.ts`) — только добавление строк, без реорганизации.
- Файл `apps/api/src/db/schema/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
