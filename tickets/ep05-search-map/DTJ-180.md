## Задача
Поиск — вход в CUJ-1 и главный экран продукта после смены позиционирования (`04-SCOPE-DECISION-PIVOT.md`
§2.1): без стабильного архитектурного порта `SearchProvider` ни один следующий тикет модуля (нормализация
запроса, ранжирование, Postgres-адаптер, use case'ы, карта аптек) не имеет основания для параллельной
разработки. Тикет — точка синхронизации: фиксирует форму порта и публичных DTO ДО того, как несколько
разработчиков начнут писать зависимый код одновременно.

## Технический контекст
Слой `application` пакета `modules/catalog`, поддиректория `search/` (решение Tech Lead EP-06:
поиск остаётся ВНУТРИ модуля `catalog`, не выносится в отдельный `modules/search` — карта аптек §9
того же документа и Analog Engine уже физически соседствуют в `catalog`, отдельный модуль добавил бы
только лишний фасад без выигрыша в изоляции, `02-CLEAN-ARCHITECTURE-AND-CODE.md` §1.2 не требует
один bounded context = один NestJS-модуль). Порт объявляется по конвенции `02` §1.3
(`application/ports/*.port.ts`, DI-токен `Symbol`), связывание — только в `catalog.module.ts`
через `{ provide: SEARCH_PROVIDER, useClass: ... }` по ENV `SEARCH_DRIVER` (`SRS-CAT-012`).
`packages/contracts/src/search.ts` — ОТДЕЛЬНЫЙ набор типов (zod-схемы + выведенные TS-типы) для
HTTP-контракта (`presentation` ↔ `apps/web`), не совпадает 1:1 с внутренними типами порта
(порт использует доменные VO вроде `TenantId`, контракт — сериализуемые примитивы для JSON).

## Что сделать
1. Создать `search-provider.port.ts`: экспортировать `SEARCH_PROVIDER = Symbol('SEARCH_PROVIDER')`
   и интерфейсы `SearchQuery`, `SearchFilters`, `SearchResultItem`, `PharmacyOffer`,
   `SearchResultPage`, `SuggestItem`, `SearchProvider` — дословно по сигнатурам `SRS-CAT-011`
   (`20-module-catalog-search.md` §2.1). Никаких дополнительных полей сверх спецификации.
2. Добавить шапку-комментарий над файлом с обоснованием решения «поиск внутри `catalog`, не отдельный
   модуль» (см. «Технический контекст») — ссылка на этот тикет, чтобы решение не переоткрывалось молча.
3. Создать `null-search.provider.ts` — `NullSearchProvider implements SearchProvider`: `search()`
   возвращает `{ items: [], nextCursor: null, hasMore: false }`, `suggest()` возвращает `[]`.
   Нужен как временная DI-связка, чтобы приложение собиралось и поднималось ДО того как
   `PostgresSearchProvider` (DTJ-185) будет готов — без него любой параллельный тикет, поднимающий
   `apps/api` целиком (например, тесты `apps/web`), будет падать на незарезолвленном токене.
4. В `catalog.module.ts` добавить секцию провайдеров: читать `SEARCH_DRIVER` через `ConfigService`
   (дефолт `'postgres'`), сейчас ВСЕГДА резолвить в `NullSearchProvider` (реальная развилка
   `postgres | elasticsearch` подключается тикетами DTJ-185/DTJ-191 — оставить `TODO(DTJ-185)`
   рядом с местом переключения, не реализовывать заранее несуществующий класс).
5. Создать `packages/contracts/src/search.ts`: zod-схемы `SearchQuerySchema` (query-параметры HTTP:
   `text`, `lat?`, `lon?`, `radiusMeters?` — enum `[1000,3000,5000,10000,20000]`, `sort`, `cursor?`,
   `limit` 1..100 дефолт 20, объект `filters`), `SearchResultItemSchema`, `PharmacyOfferSchema`,
   `SearchResultPageSchema`, `SuggestItemSchema`. Экспортировать выведенные типы
   (`z.infer<typeof ...>`) рядом со схемами — единственный источник валидации на границе API
   (переиспользуется `presentation`-контроллером, DTJ-190, и `apps/web` для типизации fetch-хуков).
6. Добавить ОДНУ строку экспорта в барабанный `packages/contracts/src/index.ts`
   (`export * from './search';`) — не трогать остальное содержимое файла (владеет EP-01, риск
   конфликта слияния при параллельной волне 6, см. `00-EPICS.md` «Пересекающееся владение» п.3).

## Критерии приёмки
1. Given `SEARCH_DRIVER` не задан в ENV, When `apps/api` поднимается (Nest DI resolve), Then токен
   `SEARCH_PROVIDER` резолвится в `NullSearchProvider`, вызов `search()`/`suggest()` не бросает
   исключений и возвращает пустые структуры формы `SearchResultPage`/`SuggestItem[]`.
2. Given типы `SearchQuery`/`SearchResultPage`/`SuggestItem` объявлены по `SRS-CAT-011`, When
   `pnpm typecheck` (`tsc --noEmit --strict`), Then компиляция проходит без `any`/`@ts-ignore`
   (C7 `02-CLEAN-ARCHITECTURE-AND-CODE.md`).
3. Given модуль `orders` (гипотетический тестовый импорт в фикстуре) пытается импортировать
   `catalog/application/search/ports/search-provider.port.ts` НАПРЯМУЮ, минуя `catalog/index.ts`,
   When `pnpm arch:check`, Then `dependency-cruiser` отклоняет импорт (правило межмодульного
   взаимодействия, `02` §1.2) — негативный сценарий.
4. Given `SearchQuerySchema.parse({ radiusMeters: 7000 })` (значение вне разрешённого набора), When
   валидация, Then `ZodError` с указанием на `radiusMeters` (соответствует `SRS-CAT-044` на уровне
   контракта, до реализации самого use case).

## Тест-план
Unit: `null-search.provider.spec.ts` (search/suggest возвращают пустые структуры); `search.contracts.spec.ts`
(валидные/невалидные `radiusMeters`, `sort`, `limit` через zod-схему — таблица кейсов). Интеграционный
тест не требуется (нет реального I/O). Порог покрытия `application/` ≥ 90 % применяется к
`null-search.provider.ts` как к части application-слоя.
