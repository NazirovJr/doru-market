## Задача
Итоговая формула ранжирования (`finalScore = 0.40×textRelevance + 0.20×availabilityScore +
0.15×proximityScore + 0.15×priceScore + 0.10×reliabilityScore`) — прямая реализация позиционирования
«дешевле рядом», ядро CUJ-1. SQL-версия формулы (§3.3) намеренно оставлена «заготовкой» — финальная,
авторитетная нормализация (включая замену `NULL` на `1.0` для вырожденного случая одной цены на
странице и перенормировку весов без гео) обязана жить в TypeScript, покрытом unit-тестами БЕЗ БД
(`SRS-CAT-021`, примечание разработчику). Этот тикет — единственное место, где формула СЧИТАЕТСЯ
окончательно; SQL (DTJ-185) поставляет только сырые компоненты.

## Технический контекст
Слой `domain`, чистая функция без I/O — принимает на вход уже вычисленные сырые величины (текстовая
релевантность из SQL, количество офферов, дистанции, цены, reliability), возвращает `finalScore` и
использованные веса. Вызывается из `PostgresSearchProvider` (DTJ-185) как последний шаг мэппинга
строки БД → `SearchResultItem`, а также из `SearchMedicinesUseCase` (DTJ-188) при вычислении
`textRelevance = 1.0` для browsing-режима без текста (`SRS-CAT-023`). Пример расчёта §3.2
(`SRS-CAT-020`) — обязательный контрольный кейс, числа должны совпасть С ТОЧНОСТЬЮ до округления.

## Что сделать
1. `RankingScoreMapper.normalize(input: RawRankingInput): RankingResult` — реализовать пять
   компонент по формулам §3.1 (`SRS-CAT-018`, таблица):
   - `textRelevance` — принимается ГОТОВЫМ на входе (вычислен SQL по `SRS-CAT-019`, здесь только
     участвует в сумме; НЕ пересчитывать заново, но добавить defensive-проверку диапазона `[0,1]`,
     бросить `DomainInvariantViolationError` при выходе за диапазон — дефолтная защита от
     некорректных данных из SQL-слоя, `02` §2.5 «доменные ошибки — свои классы»).
   - `availabilityScore = min(offersCountInRadius / AVAILABILITY_SATURATION_OFFERS, 1.0)`,
     `AVAILABILITY_SATURATION_OFFERS = 3` (именованная константа модуля, НЕ магическое число, C6).
   - `proximityScore` — вычисляется, только если `nearestOfferDistanceMeters` передан; `null` →
     компонента отсутствует структурно (не «0», а полностью исключается из суммы весов).
   - `priceScore` — принимает `cheapestOfferPriceDiram`, `minPriceInPage`, `maxPriceInPage`; при
     `maxPriceInPage === minPriceInPage` → `1.0` для ВСЕХ элементов страницы (замена `NULL` из
     SQL-заготовки — ИМЕННО здесь происходит `COALESCE`, `SRS-CAT-021` примечание).
   - `reliabilityScore = reliabilityValue / 5.0`, `reliabilityValue` уже приходит с дефолтом `3.5`
     из SQL (`COALESCE(prs.score, 3.5)`, DTJ-181/185) — компонента НИКОГДА не исключается
     структурно (в отличие от `proximityScore`), только принимает дефолтное значение.
2. Перенормировка (`SRS-CAT-022`): если одна или несколько компонент отсутствуют СТРУКТУРНО (только
   `proximityScore` реально может отсутствовать при отсутствии `geo` — реализовать как ОБЩЕЕ
   правило `sum(weights of present components) → renormalize by dividing by (1 - sum(excluded
   weights))`, не как частный случай только для `proximityScore`, чтобы формула была расширяемой).
3. `finalScore = sum(weight_i × component_i)` по присутствующим компонентам с перенормированными
   весами; вернуть также объект `usedWeights` (для отладки/аналитики, не для UI, `SRS-CAT-011`
   `relevanceScore` комментарий).
4. Отдельный метод `RankingScoreMapper.forCategoryBrowsing(input)`: `textRelevance` принудительно
   `1.0` для всех кандидатов (`SRS-CAT-023`), остальные компоненты — как обычно; вызывающий код
   (DTJ-188) сам решает, когда вызывать этот метод (когда `filters.categoryId` задан и `text === ''`).
5. Именованные константы модуля (`AVAILABILITY_SATURATION_OFFERS = 3`,
   `RANKING_WEIGHT_TEXT = 0.40`, `RANKING_WEIGHT_AVAILABILITY = 0.20`,
   `RANKING_WEIGHT_PROXIMITY = 0.15`, `RANKING_WEIGHT_PRICE = 0.15`,
   `RANKING_WEIGHT_RELIABILITY = 0.10`) — все веса из C6-запрета на магические числа.
6. Воспроизвести пример §3.2 (`SRS-CAT-020`) как integration-style unit-тест с зафиксированными
   входными величинами, проверить финальное значение `0.770` с допуском `±0.001`.

## Критерии приёмки
1. Given входные величины из примера §3.2 (`textRelevance=0.525, offersCount=4, distance=800,
   radius=5000, price=12.00 единственная в странице, reliability=4.2/5`), When `normalize()`, Then
   `finalScore = 0.770 ± 0.001` (дословное воспроизведение `SRS-CAT-020`).
2. Given `geo` отсутствует (`nearestOfferDistanceMeters = null`), When `normalize()`, Then веса
   равны `{ text: 0.471, availability: 0.235, price: 0.176, reliability: 0.118 }` (±0.001,
   `SRS-CAT-022`), `proximityScore` отсутствует в `usedWeights`.
3. Given `maxPriceInPage === minPriceInPage` (одна уникальная цена на странице), When `normalize()`,
   Then `priceScore = 1.0` для ЭТОГО элемента (не `NaN`/`null` — проверка вырожденного случая деления
   на ноль из SQL-заготовки).
4. Given `textRelevance = 1.3` (некорректное входное значение вне `[0,1]`, симулирует баг SQL-слоя),
   When `normalize()`, Then бросается `DomainInvariantViolationError` — негативный сценарий,
   defense-in-depth против ошибки в SQL-компоненте.

## Тест-план
Unit (`ranking-score-mapper.service.spec.ts`): пример §3.2 дословно; перенормировка при отсутствии
`geo`; вырожденный случай единой цены; выход `textRelevance` за диапазон (негатив); browsing-режим

сервиса — только формула). Таблично прогнать 5-6 комбинаций весов для регрессии перенормировки.

## Риски и подводные камни
- Плавающая точка: сравнение `finalScore` с примером §3.2 обязано использовать допуск (`±0.001`),
  не строгое `===` — иначе тест станет хрупким на разных версиях V8/округления.
- Перенормировка реализована как ОБЩЕЕ правило (не частный случай `proximityScore`) по прямому
  требованию `SRS-CAT-022» — при код-ревью явно проверить, что реализация не захардкожена под один
  сценарий «нет гео», иначе будущее расширение (например, добавление шестой компоненты) снова
  потребует ручной правки формулы перенормировки.
- `RankingScoreMapper` НЕ читает `pharmacy_reliability_scores` сам — дефолт `3.5` подставляется в SQL
  (DTJ-181/185) ДО вызова этого сервиса; если DTJ-185 забудет `COALESCE`, здесь появится `null` на
  входе `reliabilityValue` — добавить defensive-проверку и на этот случай (аналогично `textRelevance`).
