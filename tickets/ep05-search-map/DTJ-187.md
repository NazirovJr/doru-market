## Задача
Целевой p95 `< 300 мс` (Charter §7) недостижим на каждый запрос через полный SQL — короткий
30-секундный кэш результатов поиска и 5-минутный кэш подсказок закрывают основную долю трафика.
Без защиты от cache stampede пиковая нагрузка (несколько пользователей ищут одно и то же слово
одновременно сразу после истечения TTL) породит N параллельных тяжёлых SQL-запросов на один и тот
же ключ — тикет закрывает оба риска одной инфраструктурной утилитой.

## Технический контекст
Слой `infrastructure`, чистая техническая утилита БЕЗ доменной логики (`02-CLEAN-ARCHITECTURE-AND-
CODE.md` §1: `RedisLockGuard` — infrastructure-утилита, не домен). Потребители —
`SearchMedicinesUseCase` (DTJ-188) и `SuggestMedicinesUseCase` (DTJ-189), оба получают
`SearchCacheService` через конструктор (DI), не создают `new RedisClient()` внутри use case.

## Что сделать
1. `SearchCacheService.getSearchResults(key: string): Promise<SearchResultPage | null>` /
   `setSearchResults(key, value, ttlSeconds=30)` — ключ `catalog:search:{tenantId}:{hash(query+
   filters+geo+radius+sort+cursor)}` (`SRS-CAT-058`, таблица). Хэш — стабильный (сортировка ключей
   объекта перед сериализацией — иначе `{a:1,b:2}` и `{b:2,a:1}` дадут разные ключи одного запроса).
2. `getSuggestions(key)`/`setSuggestions(key, value, ttlSeconds=300)` — ключ
   `catalog:suggest:{tenantId}:{normalizedQuery}`.
3. `getTrendingSearches(tenantId): Promise<string[]>` — читает `Redis:trending_searches:{tenantId}`
   (TTL управляется джобой аналитики EP-17, ЭТОТ тикет только читает, не пишет — джоба, наполняющая
   ключ, в scope EP-17/DTJ-189 использует этот метод как read-only зависимость) — given ключ
   отсутствует (джоба ещё не запускалась, ожидаемо на протяжении большей части R1-разработки), Then
   вернуть пустой массив, НЕ бросать исключение (`SRS-CAT-030`, cold-start).
4. `RedisLockGuard.withLock<T>(key: string, ttlMs: number, compute: () => Promise<T>): Promise<T>` —
   паттерн `SET key value NX PX ttl`: первый вызов, получивший лок, выполняет `compute()` и
   записывает результат в кэш; конкурентные вызовы того же ключа в узком окне ждут через короткий
   `sleep+retry` (`50мс × 3`, именованные константы `STAMPEDE_RETRY_DELAY_MS=50`,
   `STAMPEDE_RETRY_ATTEMPTS=3`), затем читают уже записанный результат из кэша, НЕ дублируют
   вычисление (`SRS-CAT-060`).
5. Инвалидация — ПАССИВНАЯ (TTL-истечение) для результатов поиска/подсказок (`SRS-CAT-058`, таблица,
   обоснование — короткий TTL важнее точности, `InventorySyncBatchCompletedEvent` НЕ используется
   здесь для точечной инвалидации, в отличие от кэша карточки медикамента — EP-04, не этот тикет).

## Критерии приёмки
1. Given ключ поиска не в кэше, When 20 параллельных идентичных запросов приходят одновременно
   (сразу после истечения TTL), Then РОВНО ОДИН вызов `compute()` выполнен (проверяется счётчиком
   вызовов мока, а не реальным `pg_stat_statements` — тот замер вынесен в нагрузочный k6-тест
   `SRS-CAT-063`, здесь достаточно unit/integration-проверки на Redis), остальные 19 обслужены
   результатом первого (`TC-CAT-027`, unit-версия).
2. Given `getTrendingSearches('tenant-A')` вызван, а ключ `trending_searches:tenant-A` отсутствует в
   Redis, When вызов, Then возвращается `[]` БЕЗ исключения (`TC-CAT-022`).
3. Given два запроса с одинаковыми `filters`, но разным порядком полей объекта JS, When ключ кэша
   вычисляется для обоих, Then оба дают ОДИНАКОВЫЙ ключ (стабильная сериализация) — негативный
   сценарий против случайного «кэш-промаха» на семантически идентичных запросах.
4. Given `compute()` внутри `withLock` бросает исключение, When лок был захвачен, Then лок
   освобождается (не остаётся «зависшим» до истечения `ttlMs`) И исключение пробрасывается вызывающему
   коду — негативный сценарий, ошибка не должна тихо проглатываться (C12, запрет пустого `catch`).

## Тест-план
Интеграционные (Testcontainers Redis, НЕ мок — реальная атомарность `SET NX PX` важна для этой
логики): stampede-сценарий (20 параллельных вызовов → 1 `compute`), TTL-истечение результатов
поиска/подсказок, cold-start trending (пустой массив), освобождение лока при исключении в
`compute()`. Unit: стабильность сериализации ключа при разном порядке полей. Порог покрытия
`infrastructure/` ≥ 70 %.

## Риски и подводные камни
- `RedisLockGuard` — общая инфраструктурная утилита, потенциально полезная другим модулям
  (например, `inventory`-синхронизации) — НЕ выносить преждевременно в `packages/shared` без второго
  реального потребителя за пределами `catalog` (C15, преждевременная абстракция); если появится
  второй потребитель позже — рефакторинг-тикет на перенос, не блокирует R1.
- Cache stampede-тест по природе таймингозависим (race condition) — избегать `sleep`-based
  синхронизации в самом тесте, использовать барьер/`Promise.all` с контролируемым стартом, иначе
  тест будет флейки в CI под нагрузкой.
- `getTrendingSearches` читает ключ, который в течение почти всего R1 (до готовности EP-17, волна
  11) заполняться не будет — это ожидаемое состояние (см. риски DTJ-181), не повод откладывать
  реализацию чтения.
