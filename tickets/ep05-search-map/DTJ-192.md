## Задача
Смена позиционирования (`04-SCOPE-DECISION-PIVOT.md` §2.1) делает строку поиска ГЛАВНЫМ элементом
первого экрана — не каталог, не баннер доставки. `SRS-CAT-001` фиксирует это как проверяемое
визуальным regression-тестом требование к порядку вёрстки. Этот тикет — точка входа пользователя в
CUJ-1: без быстрого, отзывчивого автодополнения продукт не отличается от обычной формы поиска.

## Технический контекст
`apps/web/src/features/search/**` (`00-EPICS.md`, владение EP-06). Структура по
`02-CLEAN-ARCHITECTURE-AND-CODE.md` §5: `api/` — вызовы через `shared/api` + TanStack Query,
`model/` — чистые функции/хуки состояния, `ui/` — только рендер. `SearchBar` — переиспользуемый
компонент, встраивается и на `Home` (`pages/home`), и на экране `Search` (`/search`, DTJ-193) —
сам компонент живёт в `features/search/ui`, композиция на конкретной странице — в `pages/`
(`app → pages → features → entities → shared`, зависимости строго вниз, обратные импорты запрещены).
Дизайн-референс: `docs/spec/32-design-reference.md` строки 152 (`SearchBar`, высота ~48-52px,
плейсхолдер меняется по языку), 174 (`Home`), 175 (`Search`).

## Что сделать
1. `search-bar.tsx` — поле ввода с иконкой лупы, плейсхолдер через `useT('search.placeholder')`
   (i18n-ключ, дефолт локаль `tj`, `SRS-CAT-001`) — НИКАКОГО хардкода строки плейсхолдера.
2. `use-search-suggestions.ts` — хук: debounce ввода `150–300 мс` (`useDebouncedValue` из
   `packages/ui`/`shared/hooks`, переиспользовать существующий, не писать свой — если хук ещё не
   готов от EP-18 на момент реализации, временный локальный хук в `features/search/model/` с тикетом
   на перенос, см. `00-EPICS.md` «Пересекающееся владение» п.6), отмена устаревших запросов через
   `AbortController` при новом вводе (`SRS-CAT-027`) — TanStack Query `queryKey` включает `prefix`,
   `signal` пробрасывается в `fetch`.
3. `search.api.ts` — `GET /api/v1/medicines/suggest?q=<text>&limit=10` через `shared/api`-клиент,
   типизировано контрактами `packages/contracts/src/search.ts` (DTJ-180) — НЕ голый `fetch` внутри
   компонента (`02` §5, запрещено).
4. `search-history.ts` — чтение/запись до 5 последних непустых запросов В `localStorage` (ключ,
   например, `dorutj:search-history:v1`), БЕЗ обращения к серверу (`SRS-CAT-030` п.1). Given история
   пуста — вызвать `use-search-suggestions` с `q=''`, получая серверный trending-фолбэк (DTJ-189).
5. `suggest-dropdown.tsx` — список подсказок под полем ввода; клик по подсказке с `medicineId !=
   null` → переход на `GET /search?text=<tradeName>` (полный поиск по имени, `SRS-CAT-028` —
   показываем ВСЕ варианты, не один произвольный `id`); клик по подсказке из истории/trending
   (`medicineId == null`, DTJ-189 риск) → заполняет поле и запускает тот же переход.
6. Состояния: skeleton при первой загрузке (`packages/ui` `Skeleton`, форма под строку — не общий
   спиннер, `docs/spec/32-design-reference.md` §Skeleton), офлайн — компактный `OfflineBanner`
   (единый i18n-текст `ux.error.network_offline`, НЕ разные формулировки на разных экранах —
   `32-design-reference.md` явно требует унификации текста при реализации, несмотря на разные
   форм-факторы дизайна).
7. Встроить `SearchBar` на `Home` (`pages/home`) КАК ПЕРВЫЙ элемент после шапки — визуальный
   regression-тест Playwright, подтверждающий порядок (`SRS-CAT-001`), пишется вместе с этим тикетом
   (Playwright-инфраструктура — из EP-19 baseline, здесь — конкретный сценарий/снапшот).

## Критерии приёмки
1. Given пользователь печатает `«но-ш»` с паузами `<150мс` между символами, When ввод завершён, Then
   выполнен РОВНО ОДИН сетевой запрос к `/suggest` (debounce отработал, промежуточные не отправлены).
2. Given пользователь быстро меняет запрос `«п» → «па» → «пар»`, When ответ на `«п»` приходит ПОСЛЕ
   отправки `«пар»`, Then устаревший ответ `«п»` НЕ отображается (проверка `AbortController`/
   игнорирования устаревшего промиса) — негативный сценарий гонки ответов.
3. Given `localStorage` пуст (первый визит), When поле поиска получает фокус, Then показаны
   серверные trending-подсказки (не пустой дропдаун, не ошибка).
4. Given история содержит 5 запросов, When новый непустой поиск выполнен, Then история обновляется
   (новый запрос добавлен, старейший при превышении 5 — удалён), сохраняется в `localStorage`.
5. Given загружен `Home`, When снят Playwright-скриншот/DOM-порядок, Then `SearchBar` — первый
   содержательный блок после шапки, ПЕРЕД любым баннером/картой (регресс-тест `SRS-CAT-001`).

## Тест-план
Unit (Vitest/RTL): `search-history.ts` — добавление/лимит 5/чтение при пустом хранилище (обёрнуто
`try/catch`, недоступный `localStorage` не роняет компонент); `use-search-suggestions` — debounce
таймингов через fake timers, отмена устаревшего запроса через мок `AbortController`. Компонентные:
`SearchBar`/`SuggestDropdown` — рендер состояний (loading/error/офлайн/пусто/с результатами).
Playwright: визуальный порядок блоков на `Home` (`SRS-CAT-001`), сценарий «ввод → подсказка → клик →
переход на `/search`». Порог покрытия компонентов — ≥ 70 % (`02` §6, «остальное — ≥70%»).

## Риски и подводные камни
- `useDebouncedValue`/базовые компоненты (`Input`, `Skeleton`, `OfflineBanner`) могут быть ещё не
  готовы от EP-18 на момент старта волны 5 — временная локальная реализация в `features/search/ui`
  допустима с обязательным тикетом-переносом в `packages/ui` в течение того же спринта
  (`00-EPICS.md` «Пересекающееся владение» п.6, `SRS-UX-034`), иначе White-Label-перекраска молча
  сломается на хардкоде вне общего пакета.
- Лента «дешевле рядом» на главном экране (`SRS-CAT-001`, «топ-N товаров с наибольшей относительной
  экономией») требует данных из Analog Engine (EP-07, расчёт экономии) — этот тикет реализует ТОЛЬКО
  позиционирование строки поиска и её собственное автодополнение; сам виджет ленты экономии на
  главном экране — зона EP-07/интеграционная точка на `pages/home`, НЕ входит в объём этого тикета
  (риск для отдельного согласования между EP-06 и EP-07 на границе `pages/home`, где владение
  каркасом определяется по правилу «первый добравшийся эпик» из `00-EPICS.md`).
- `localStorage` может бросать исключение (приватный режим браузера, заблокированное хранилище) —
  обязательно `try/catch` вокруг чтения/записи истории, деградация до «истории нет» без падения UI.
