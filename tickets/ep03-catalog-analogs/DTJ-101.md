## Задача

Финальная сборка блока аналогов: из кандидатов (DTJ-100) отбирает подтверждённые доменом аналоги
(DTJ-099), получает актуальные цену/остаток/дистанцию по каждому и считает `savingsDiram`
(REQ-MARKET-3 — единственное признанное защитимое отличие продукта). Это единственный use case,
которому нужны данные ДВУХ чужих контекстов (`inventory` — цена/остаток; `onboarding` — активность
аптеки/сети, гео) одновременно для КАЖДОГО кандидата — архитектурно самый сложный тикет эпика.

## Технический контекст

`SRS-CAT-014` явно ограничивает прямой межконтекстный SQL-джойн ТОЛЬКО файлом
`postgres-search.adapter.ts` (модуль EP-06) — «исключение НЕ распространяется ни на один другой файл
модуля catalog». Формально это означает, что `AnalogOfferLookupPort`, вводимый этим тикетом, обязан
получать данные `pharmacy_inventory`/`pharmacies`/`pharmacy_chains` ЧЕРЕЗ ФАСАДЫ (`InventoryFacade`,
`OnboardingFacade`), а не прямым SQL — даже несмотря на то, что задача («дай мне офферы по набору
`medicineId` в радиусе с учётом активности аптеки/сети») ПРАКТИЧЕСКИ идентична задаче, которую уже
решает `PostgresSearchProvider` (EP-06) для списка результатов поиска.

**Архитектурное решение этого тикета (задокументировать в PR по этому тикету и явно указать
ревьюеру):** реализовать `analog-offer-lookup.adapter.ts` как ЧЕТВЁРТЫЙ файл с явным исключением из
правила `dependency-cruiser` `no-cross-module-deep-import` (по образцу `postgres-search.adapter.ts`),
с ТЕМ ЖЕ обоснованием, что SRS-CAT-014 приводит для search: read-модель, агрегирующая данные
нескольких агрегатов ради одного оптимизированного запроса на ОГРАНИЧЕННОМ множестве (`≤50`
кандидатов, DTJ-100, а не весь каталог), не записывает данные и не воспроизводит бизнес-инвариант
чужого агрегата. **Это расширение правила, которого сам SRS-текст дословно не предусматривает — по
преамбуле `03-ARCHITECT-DECISIONS.md` ЛЮБОЕ такое расширение обязано пройти ADR на имя архитектора
ДО мержа этого тикета.** Если ADR не согласован к моменту реализации — fallback: `AnalogOfferLookupPort`
реализуется через последовательные вызовы `InventoryFacade`/`OnboardingFacade` (если они уже
предоставляют нужные агрегатные методы — см. «Риски», это зависит от готовности команд EP-05/EP-03)
— медленнее (до `N` фасадных вызовов на `≤50` кандидатов вместо одного SQL), но строго соответствует
букве правила без исключений.

## Что сделать

1. `application/ports/analog-offer-lookup.port.ts`:
   ```typescript
   export const ANALOG_OFFER_LOOKUP_PORT = Symbol('ANALOG_OFFER_LOOKUP_PORT');
   export interface AnalogOfferLookupPort {
     getOffersForMedicines(input: {
       medicineIds: readonly string[];
       geo?: GeoPoint;
       radiusMeters: number;
     }): Promise<Map<string, PharmacyOffer[]>>;    // ключ — medicineId, PharmacyOffer — см. SRS-CAT-011
   }
   ```
   (тип `PharmacyOffer` переиспользуется из `packages/contracts/src/catalog.ts`, если EP-06 уже
   объявил его там для `SearchProvider`, DTJ-090/096 — не дублировать тип, C15).
2. `infrastructure/adapters/analog-offer-lookup.adapter.ts` — реализация согласно решению выше (SQL
   read-модель ПОСЛЕ ADR, либо facade-оркестрация как fallback). В любом случае: фильтрует только
   `pharmacies.status='active'` И `pharmacy_chains.status IN ('approved','active')` (то же условие
   видимости, что SRS-CAT-010), сортирует офферы по `price_tjs ASC` внутри каждого `medicineId`
   (SRS-DOM-158 — список аналогов сортируется строго по цене, НЕ по формуле ранжирования §3).
3. `application/use-cases/find-analogs.use-case.ts` — `FindAnalogsUseCase.execute({ medicineId, geo,
   radiusMeters, tenantId, limit? })`:
   1. `CatalogRepository.findMedicineById(medicineId)` (DTJ-092) → `referenceMedicine`; not found/not
      visible → `MedicineNotFoundError` (та же проверка видимости, что DTJ-095 — переиспользовать
      общую функцию из DTJ-096, не дублировать).
   2. `AnalogCandidatesRepository.findCandidates(medicineId, ANALOG_CANDIDATES_LIMIT)` (DTJ-100).
   3. `CatalogRepository.findMedicinesByIds(candidateIds)` (DTJ-092) → полные агрегаты `Medicine[]`.
   4. Фильтр: `candidates.filter(c => analogEquivalenceService.isAnalog(referenceMedicine, c))`
      (DTJ-099) — АВТОРИТЕТНОЕ решение, SQL-предфильтр (шаг 2) — только оптимизация.
   5. `AnalogOfferLookupPort.getOffersForMedicines({ medicineIds: [подтверждённые аналоги], geo,
      radiusMeters })`.
   6. Оставляет только аналоги с `offers.length > 0` (`stock_quantity > 0` уже гарантирован портом),
      сортирует итоговый список по `cheapestOffer.priceDiram ASC` (SRS-DOM-158).
   7. `cheapestAnalog = items[0]` (если есть) → `savingsDiram = referenceMedicine.displayPrice -
      cheapestAnalog.displayPrice` (SRS-CAT-036/SRS-DOM-159) — `referenceMedicine.displayPrice`
      получается ТЕМ ЖЕ портом (`getOffersForMedicines([medicineId, ...candidateIds])` — референс
      включается в ОДИН батч-вызов вместе с кандидатами, не отдельным вызовом, C15/производительность).
   8. Given `savingsDiram <= 0`, Then DTO несёт `savings: null` (presentation, DTJ-102, решает не
      рендерить банner — SRS-CAT-037), список аналогов ВСЁ РАВНО возвращается непустым, если
      `items.length > 0`.
   9. `limit` (опционально, дефолт — без ограничения, но `GetMedicineDetailUseCase`, DTJ-095, вызывает
      с `limit: 1` для `hasAnalogs`) — обрезает `items` ДО применения любой дополнительной логики,
      после сортировки по цене.

## Критерии приёмки

- Given референсный товар `83.00 TJS`, самый дешёвый подтверждённый аналог в радиусе `18.00 TJS`,
  When `execute()`, Then `savingsDiram = 6500` (не округлено) — TC-CAT-013.
- Given референсный товар — сам самый дешёвый среди своих аналогов, When `execute()`, Then
  `savings: null` (или `<=0` внутренне), список аналогов всё ещё непустой — TC-CAT-014.
- Given ни один SQL-кандидат не проходит `AnalogEquivalenceService.isAnalog()` (все отсеяны доменом,
  несмотря на прохождение SQL-предфильтра), Then `items: []`, `savings: null`, метод НЕ бросает
  ошибку (пустой список аналогов — валидный ответ, не 404).
- Given вызов с `limit: 1` и ≥2 реальных аналога, When `execute()`, Then `items.length === 1`
  (используется `GetMedicineDetailUseCase.hasAnalogs`, DTJ-095).

## Тест-план

Unit (vitest, mock всех портов — `find-analogs.use-case.spec.ts`):
- Полный happy-path (кандидаты → domain-фильтр → офферы → сортировка → savings) с зафиксированными
  входными данными, сверка `savingsDiram` с точным числом (TC-CAT-013).
- `savingsDiram <= 0` → `savings: null`, список не пуст (TC-CAT-014).
- SQL-кандидаты есть, но domain отфильтровал ВСЕХ → пустой результат, без ошибки.
- `limit` обрезает после сортировки по цене, не до.
- Референс не найден/не виден → `MedicineNotFoundError`.

## Риски и подводные камни

- **Главный архитектурный риск тикета**: `AnalogOfferLookupPort`, если реализован прямым SQL, требует
  ADR-согласования с архитектором ДО мержа — без него тикет не может считаться завершённым по
  Definition of Done (`arch:check` заблокирует несогласованное исключение, если `dependency-cruiser`
  настроен строго). Разработчику — эскалировать вопрос тимлиду/архитектору В НАЧАЛЕ работы над
  тикетом, не в конце. `.dependency-cruiser.cjs` принадлежит ИСКЛЮЧИТЕЛЬНО EP-19 (`00-EPICS.md`
  «Пересекающееся владение» п.5) — этот тикет НЕ правит его напрямую; правку вносит владелец EP-19 по
  результату согласованного ADR, этот тикет только готовит код адаптера под ожидаемое исключение.
- Fallback-путь (facade-оркестрация через `InventoryFacade`/`OnboardingFacade`) предполагает, что эти
  фасады УЖЕ предоставляют нужные агрегатные методы (`getStockAndPrice`,
  `isVisibleAndActive`/аналог) — на момент написания этого тикета такие методы НЕ задокументированы
  ни в `10-domain-model.md`, ни в `22-module-inventory-sync-1c.md` явно; если их нет к моменту
  реализации, потребуется координация с владельцами EP-03/EP-05 на добавление методов в ИХ файлы
  (вне `files_owned` этого тикета) — зафиксировать как блокирующую межкомандную зависимость, не
  решаемую в одиночку.
- Бюджет `p95 < 300мс` (SRS-CAT-061) для `GET /medicines/:id/analogs` достижим комфортно только SQL-
  путём; facade-оркестрация на `≤50` кандидатов может не уложиться — при выборе fallback-пути явно
  предупредить, что производительность потребует отдельной оптимизации (батчинг фасадных вызовов,
  не N раздельных).
- Файл `apps/api/src/modules/catalog/catalog.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
