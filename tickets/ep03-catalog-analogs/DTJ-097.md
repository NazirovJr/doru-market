## Задача

Аптеки без 1С (Excel/ручной ввод) и с 1С одинаково присылают позиции свободным текстом
(`trade_name`/`dosage_form`/`manufacturer_name`), которые нужно сопоставить с уже существующей
записью каталога ИЛИ определить, что позиция новая. Прямой `WHERE barcode = ?` признан архитектором
дефектом (D-06) — этот тикет реализует catalog-часть composite-матчинга: точное совпадение по
штрихкоду + trigram-fuzzy с фильтром по эквивалентности дозировки. Оркестрация (кэш `pharmacy_sku_
mapping`, создание записей `catalog_match_queue`) остаётся за `inventory`/`moderation` (другая
команда, EP-05) — этот метод только отвечает «что нашлось», не решает, что делать с результатом.

## Технический контекст

`CatalogFacade.resolveMedicineByComposite(input: CompositeMatchInput): Promise<MedicineMatchResult>`
— 4-й метод фасада, объявленный заглушкой в DTJ-096. Порядок шагов 2 и 3 из D-06/SRS-INV-021 (кэш
`pharmacy_sku_mapping` — шаг 1, ПРИНАДЛЕЖИТ `inventory`, вызывается ДО обращения к этому методу; сюда
попадают только строки, не найденные в кэше) реализуется здесь: точный штрихкод → trigram fuzzy →
неоднозначность.

## Что сделать

1. `CompositeMatchInput` / `MedicineMatchResult` — наполнить типы в `packages/contracts/src/
   catalog.ts` (файл уже существует, DTJ-090/096):
   ```typescript
   export interface CompositeMatchInput {
     readonly rawBarcode: string | null;
     readonly rawTradeName: string;
     readonly rawDosageForm: string | null;   // свободный текст 1С/Excel, например "таблетки"
     readonly rawDosageStrength: string | null; // "500 мг"
     readonly rawManufacturerName: string | null;
   }
   export type MedicineMatchResult =
     | { readonly outcome: 'matched'; readonly medicineId: string; readonly matchedVia: 'barcode' | 'fuzzy' }
     | { readonly outcome: 'ambiguous'; readonly candidateIds: readonly string[] }
     | { readonly outcome: 'no_candidate' };
   ```
2. `application/services/dosage-form-normalizer.service.ts` — `catalogNormalizeDosageFormClass(raw:
   string | null): DosageFormClass` — чистая функция домена (без I/O), маппинг свободного текста 1С
   (`"таблетки"`, `"табл."`, `"tabs"`, …) в `DosageFormClass` enum (SRS-INV-024 — эта функция
   упоминается в спецификации inventory как «уже существующая, принадлежит catalog», реализуется
   ЗДЕСЬ впервые). Нераспознанный текст → `DosageFormClass.other`. Также экспортируется как SQL-функция
   `catalog_normalize_dosage_form_class(text)` (см. п.4) для использования ВНУТРИ SQL-запроса fuzzy-
   матчинга (SRS-INV-024 приводит её именно в `WHERE`-условии) — ЛОГИКА маппинга дублируется
   намеренно в TS (для тестируемости domain-функции) и в SQL (для производительности запроса на всей
   таблице `medicines`); TS-версия — источник истины, SQL — синхронизированная копия, тест
   `dosage-form-normalizer.parity.spec.ts` (см. тест-план) гоняет ОБА пути на одном наборе фикстур и
   сверяет результат, чтобы расхождение не прошло незамеченным.
3. `infrastructure/adapters/fuzzy-medicine-matcher.adapter.ts`:
   - Шаг 1 (штрихкод): given `input.rawBarcode` задан, `Barcode.parse(rawBarcode)` (DTJ-090) даёт
     `isValidEan13() && !isInternalPrefix()`, Then `SELECT id FROM medicines WHERE barcode =
     :rawBarcode` — точное совпадение (SRS-INV-020/021 шаг 2.2) → `{ outcome: 'matched', medicineId,
     matchedVia: 'barcode' }`, ОСТАЛЬНЫЕ шаги пропускаются.
   - Шаг 2 (fuzzy): given штрихкод не дал результата (не задан/невалиден/внутренний/не найден),
     выполняет SQL из SRS-INV-024/SRS-DB-018 запрос 4 (порог `0.35`, ВЕСА `0.7×trade_name +
     0.3×manufacturer_name`), `LIMIT 5`.
   - Постфильтр (SRS-INV-025): для каждого из топ-5 кандидатов подгружает `dosage_strength`/
     `dosage_unit`, сравнивает через `Dosage.isEquivalentTo()` (domain-kernel) с распарсенным
     `input.rawDosageStrength` (`Dosage.parse()`, DTJ-090) — несовпадение дозировки ОТБРАСЫВАЕТ
     кандидата целиком, даже при высоком `combined_score`.
   - Неоднозначность (SRS-INV-026): given после постфильтра остаётся ≥2 кандидата и разница
     `combined_score` первого/второго `< CATALOG_MATCH_AMBIGUITY_GAP` (ASSUMPTION `0.05`, ENV-
     конфигурируемая именованная константа) → `{ outcome: 'ambiguous', candidateIds: [...] }`.
   - given после постфильтра остаётся ровно 1 кандидат ИЛИ разница ≥ порога → `{ outcome: 'matched',
     medicineId: топ-1.id, matchedVia: 'fuzzy' }`.
   - given топ-5 пуст (порог `0.35` не пройден никем) → `{ outcome: 'no_candidate' }`.
4. `apps/api/src/db/migrations/sql/0007_catalog_normalize_dosage_form_class.sql` — `CREATE OR REPLACE
   FUNCTION catalog_normalize_dosage_form_class(raw text) RETURNS dosage_form_class ... LANGUAGE sql
   IMMUTABLE` — SQL-зеркало TS-функции п.2 (та же таблица маппинга, буквально синхронизированная).
5. `application/use-cases/resolve-medicine-by-composite.use-case.ts` — тонкая обёртка,
   оркеструющая шаги 1-2 через адаптер, реализует метод фасада `CatalogFacade.
   resolveMedicineByComposite` (заменяет заглушку DTJ-096).

## Критерии приёмки

- Given `rawBarcode='4870123456789'` совпадает с существующей `medicines.barcode`, When
  `resolveMedicineByComposite(input)`, Then `{ outcome: 'matched', matchedVia: 'barcode' }`, fuzzy-
  запрос НЕ выполнялся (проверяется мок/spy на репозитории — только один SQL-путь).
- Given `rawTradeName='Цитрамон П'`, ближайший кандидат `similarity=0.28` (< порога `0.35`), Then
  `{ outcome: 'no_candidate' }` — TC-INV-010.
- Given топ-1 `combined_score=0.40`, топ-2 `combined_score=0.38` (разница `0.02 < 0.05`), Then `{
  outcome: 'ambiguous', candidateIds: [id1, id2] }`, авто-выбор НЕ произошёл — TC-INV-012.
- Given топ-1 кандидат текстово похож (`combined_score=0.60`), но его `dosage_strength = '250 мг'`
  против входного `'500 мг'`, Then кандидат отброшен постфильтром — если это был единственный
  кандидат, результат `{ outcome: 'no_candidate' }`, а не ложный `matched`.

  EP-06 на момент теста, тест использует `pg_trgm`-функцию напрямую без индекса — производительность
  не важна для корректности теста, важна для прод-нагрузки, вне scope этого тикета).
- `dosage-form-normalizer.parity.spec.ts` — прогоняет фиксированный набор `rawDosageForm`-строк через
  TS-функцию И через `SELECT catalog_normalize_dosage_form_class(:raw)`, сравнивает результаты
  построчно — падение теста при расхождении TS/SQL реализаций (обязательный regression-guard,
  предотвращает «поправили TS, забыли SQL»).

## Риски и подводные камни

- SQL-зеркало функции нормализации формы выпуска (п.4) — классический источник расхождения «поправили
  одну копию, забыли другую»; parity-тест — обязательный, не опциональный пункт тест-плана именно
  по этой причине.
- Реальный вызывающий этого метода — команда EP-05 (`inventory`), которая ожидает конкретную форму
  `CompositeMatchInput`/`MedicineMatchResult` из `22-module-inventory-sync-1c.md` §4 — расхождение
  сигнатуры с их ожиданиями обнаружится только на интеграции; рекомендуется зафиксировать типы в
  `packages/contracts/src/catalog.ts` РАНО и сообщить владельцу EP-05 текущую сигнатуру до того, как
  они начнут `CompositeInventoryMatcherService`.
- Порог `CATALOG_MATCH_AMBIGUITY_GAP=0.05` — ASSUMPTION, подлежит калибровке на реальных данных после
  сбора первой партии импортов (не блокирует релиз, но стоит зафиксировать как известный tuning-риск).
- Файл `apps/api/src/modules/catalog/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
