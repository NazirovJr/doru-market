## Задача

Кто платит за брак — аптека, курьер или никто — не должно решаться разбросанными `if/else` по
коду use case'ов: это прямой канал для финансовой ошибки (клиенту не вернули деньги за то, за
что должны были, либо вернули то, чего не должны были). SRS-RET-004 требует явной таблицы
правил в отдельном классе-политике — этот тикет реализует её как чистую функцию, которую
DTJ-274 (рефанд) вызывает без доступа к БД/деньгам напрямую.

## Технический контекст

`application/policies/` модуля `returns` (`02-CLEAN-ARCHITECTURE-AND-CODE.md` §3 — политика
авторизации/бизнес-правил в application, не в domain, т.к. не является инвариантом самой
сущности `OrderReturn`, а правилом расчёта, зависящим от внешнего контекста — кто «виноват»).
Источник таблицы — `21-module-orders-payments-escrow.md` §7.2 (SRS-RET-004/005), строки
948–967.

## Что сделать

1. `return-financial-outcome.types.ts` — типы `ReturnFinancialOutcome { itemsRefund:
   'full' | 'none'; deliveryFeeRefund: 'full' | 'none'; courierReturnFeeApplies: true }`
   (`courierReturnFeeApplies` — литерал `true`, не булево поле «может быть false»: SRS-RET-005
   явно требует, чтобы курьерская компенсация начислялась ВСЕГДА независимо от исхода —
   типизация этого поля как константы `true` делает невозможным случайно закодировать
   исключение в будущем без осознанного изменения типа).
2. `return-financial-outcome.policy.ts` — `class ReturnFinancialOutcomeResolver` с единственным
   публичным методом `resolve(reason: ReturnReason, disposition: ReturnDisposition |
   'pending_inspection'): ReturnFinancialOutcome`. Таблица правил — `Record<ReturnReasonValue,
   ReturnFinancialOutcome>` (объект-константа, НЕ `switch`/`if` цепочка — C6/C15 §4
   `02-CLEAN-ARCHITECTURE-AND-CODE.md`):

   | `reason` | `itemsRefund` | `deliveryFeeRefund` |
   |---|---|---|
   | `defect` | `full` | `full` |
   | `wrong_item` | `full` | `full` |
   | `damaged_packaging` | `full` | `full` |
   | `expired_or_near_expiry` | `full` | `full` |
   | `refused_at_door` | `full` | `none` |
   | `undeliverable` | `full` | `none` |
   | `customer_dispute_post_delivery` | по итогам `disposition` (см. п.3) | как `itemsRefund` |
3. Для `reason='customer_dispute_post_delivery'` исход зависит от результата чек-листа
   фармацевта (`disposition`), а не от самой причины напрямую (SRS-RET-004, последняя строка
   таблицы): `disposition === 'restock'` → `itemsRefund='full'` (подтверждённый брак),
   `disposition === 'destroy'` без физического обоснования брака (проверяется use case'ом
   ДО вызова резолвера — см. риск ниже) → трактуется как `return_rejected` веткой use case, эта
   политика для отклонённого возврата не вызывается вовсе (нет `ReturnFinancialOutcome` для
   отказа — деньги не возвращаются, use case просто не инициирует рефанд).
4. `reason='undelivered'` НЕ входит в таблицу — метод бросает программную ошибку
   (`UnsupportedReturnReasonError`, тот же класс, что в DTJ-271, реэкспортирован) при попытке
   резолва: эта причина обрабатывается через `OrderDispute`/`SupportFacade`, не через
   `ReturnFinancialOutcomeResolver` (SRS-RET-003) — падение здесь означает баг вызывающего кода,
   не пользовательский сценарий.
5. Метод — чистая функция без побочных эффектов (C18): не читает БД, не вызывает порты, только
   маппинг вход→выход.

## Критерии приёмки

1. **Given** `reason='defect'`, **When** вызывается `resolve()`, **Then** возвращается
   `{ itemsRefund: 'full', deliveryFeeRefund: 'full', courierReturnFeeApplies: true }`
   (аналог TC-RET-002).
2. **Given** `reason='refused_at_door'`, **When** вызывается `resolve()`, **Then**
   `deliveryFeeRefund === 'none'`, `itemsRefund === 'full'` (аналог TC-RET-003).
3. **Given** `reason='undelivered'`, **When** вызывается `resolve()`, **Then** выбрасывается
   `UnsupportedReturnReasonError` — негативный сценарий, подтверждающий, что резолвер не
   пытается угадать исход для причины вне своей ответственности.

  ожидаемый `ReturnFinancialOutcome` сверяется построчно с таблицей SRS-RET-004 из
  «Технического контекста».
- Отдельный кейс: `customer_dispute_post_delivery` с `disposition='restock'` →

## Риски и подводные камни

- **Отклонённый пост-доставочный возврат не описан этой политикой намеренно.** Если
  `pharmacist` отклоняет `customer_dispute_post_delivery` через `reject()` (SRS-DOM-056, товар
  оказался не бракованным), финансового исхода нет вообще — use case (DTJ-273/274) обязан НЕ
  вызывать `resolve()` для отклонённых возвратов. Ошибка интеграции («вызвали резолвер для
  `return_rejected`») — забота вызывающего кода, эта политика не защищена от неправильного
  вызова доменной проверкой статуса (сознательно: политика не знает о `OrderReturn`, только о
  причине и диспозиции — иначе она перестаёт быть чистой функцией и приобретает зависимость от
  агрегата).
