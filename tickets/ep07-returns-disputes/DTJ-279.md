## Задача

Это единственная точка создания обращения в системе — и единственное место, где нужно жёстко
гарантировать, что R1 физически не может открыть денежно-блокирующий спор, даже если клиент в
теле запроса передаст `isEscrowBlocking: true`. SRS-ADM-053 требует, чтобы это была
архитектурная гарантия, а не проверка «на всякий случай» — эта задача реализует именно её на
уровне use case, поверх структурной гарантии домена (DTJ-278, п.4).

## Технический контекст

`application/use-cases/` модуля `support`. Источник — `27-module-admin-moderation-onboarding.md`
§9 (SRS-ADM-074), §6.1 (SRS-ADM-053, гард). Порт к заказу — `SupportOrdersFacadePort` (для
случая `orderId` присутствует — проверка владения заказом клиентом делается тут, не в
`presentation`, `02` §3.4).

## Что сделать

1. `SupportTicketsRepositoryPort` — `save(ticket: SupportTicket): Promise<void>`,
   `findById(id): Promise<SupportTicket | null>`.
2. `SupportOrdersFacadePort` — `interface { belongsToCustomer(orderId, customerId): Promise<boolean> }`
   (тонкий порт, оборачивает публичный `OrdersFacade` — правило владения `apps/api/src/modules/support/**`
   допускает обращение к другим модулям только через их фасад).
3. `CreateSupportTicketUseCase.execute({ tenantId, orderId?, channel, category, createdBy?,
   description, actorRole })`:
   - Given `orderId` присутствует И `channel !== 'system_auto'` — проверяет
     `SupportOrdersFacadePort.belongsToCustomer(orderId, createdBy)` для роли `customer`
     (RBAC уже отфильтровал на уровне presentation, здесь — доменная проверка владения, второй
     рубеж защиты, `02` §3.4).
   - Читает `tenantSettings.supportFirstResponseSlaMinutes` через `TenantSettingsPort`
     (ASSUMPTION 60 минут в рабочие часы поддержки, SRS-ADM-075 — значение конфигурируемо
     per-tenant, не константа в use case).
   - Вызывает `SupportTicket.open({ ..., firstResponseSlaMinutes })` (DTJ-278) — конструктор
     структурно не принимает `isEscrowBlocking`, поэтому **никакого дополнительного `if`,
     обнуляющего флаг, здесь не требуется** — само отсутствие параметра в сигнатуре домена и
     есть механизм SRS-ADM-053. Комментарий в коде явно ссылается на SRS-ADM-053 и
     `disputes_workflow_enabled` — чтобы будущий разработчик R2/R3, расширяющий этот use case,
     сразу увидел, ЧТО именно предстоит менять и почему сейчас этого нет.
   - Сохраняет через `SupportTicketsRepositoryPort.save()`, публикует `SupportTicketCreatedEvent`
     через `outbox` в той же транзакции.
4. `SupportTicketCreatedEvent { ticketId, tenantId, orderId?, category, channel, priority: 0 }` —
   потребители: `NotificationsFacade` (EP-16, матрица SRS-ADM-052 в этой версии НЕ содержит
   строки конкретно для `SupportTicketCreatedEvent` — уведомление `support_agent` о новом тикете
   не специфицировано явно; не добавлять его самовольно за пределами описанного контракта, это
   ответственность EP-16 решить на основании своей спеки).

## Критерии приёмки

1. **Given** `category='order_item_damaged_or_expired'` (потенциально эскроу-блокирующая по
   таблице SRS-DISP-001), **When** вызывается `CreateSupportTicketUseCase.execute()`, **Then**
   создан `support_tickets` с `is_escrow_blocking=false` в БД, `order_disputes` НЕ создан —
   негативный сценарий, аналог TC-ADM-021.
2. **Given** `channel='system_auto'`, `createdBy=undefined`, **When** use case вызывается,
   **Then** тикет создан успешно, `created_by IS NULL`.
3. **Given** `customer` пытается создать тикет для чужого `orderId`, **When** use case
   вызывается, **Then** бросается ошибка авторизации (`ForbiddenError`/аналог), тикет не создан.
4. **Given** валидный запрос, **When** use case завершается, **Then**
   `SupportTicketCreatedEvent` опубликован в `outbox` в ТОЙ ЖЕ транзакции, что `INSERT
   support_tickets` (проверка через один и тот же `unitOfWork`).

## Тест-план

- Интеграционные тесты (Vitest + Testcontainers Postgres): создание тикета по каждому каналу,
  проверка `is_escrow_blocking=false` в БД для ВСЕХ 6 категорий (не только «опасных») —
  исчерпывающий прогон, не выборочный.
- Негативный тест владения заказом — `customer` не может создать тикет для чужого `orderId`.
- Тест атомарности публикации события с `INSERT` (откат транзакции при сбое после `save()` не
  оставляет «сироту»-событие в outbox).
- Порог покрытия `application/` — 90%.

## Риски и подводные камни

- **Уведомление `support_agent` о новом тикете вне периметра.** SRS-ADM-052 (матрица
  событие×роль×канал) не содержит строки для `SupportTicketCreatedEvent` — только для
  `SlaBreachedEvent` (эскалация просрочки). Возможно, это осознанное решение источника
  (поддержка мониторит очередь сама, не по push-уведомлению на каждый новый тикет) — не
  добавлять уведомление самовольно, зафиксировать вопрос для EP-16, если потребуется.
- **`TenantSettingsPort.supportFirstResponseSlaMinutes` — новое поле `tenant_settings`,
  отсутствующее в текущей DDL.** `SUPPORT_FIRST_RESPONSE_SLA_MINUTES` в SRS-ADM-075 описано как
  ASSUMPTION-константа (60 минут), но требование гласит «не константа в коде» (Charter §3.4).
  Нужно добавить `tenant_settings.support_first_response_sla_minutes INT NOT NULL DEFAULT 60` —
  включить эту колонку в миграцию DTJ-278 (`0011_support_ticket_sla_fields.sql`), если она туда
  ещё не попала на момент реализации этого тикета — координировать между DTJ-278/279, т.к. поле
  логически часть той же миграционной группы.
