## Разрешение конфликта объёма R1 (важно прочитать перед работой над тикетами)

Источники `docs/spec/` расходятся между собой по объёму R1 для возвратов/споров:

| Источник | Возвраты (money+stock) | Полный денежный воркфлоу спора (`OrderDispute`) |
|---|---|---|
| `21-module-orders-payments-escrow.md` §7/§8, релиз-таблица | R1 полностью | R1 полностью (SRS-DISP-001..010) |
| `27-module-admin-moderation-onboarding.md` §9, релиз-таблица | — (не описывает возвраты отдельно) | **R3**, за флагом `disputes_workflow_enabled` |
| `00-SRS-MASTER.md` RELEASE 3 п.2 | **R3** (упомянут вместе со спорами) | **R3** |
| `30-ux-screens-and-flows.md` строка 51 | **R3** (экраны полной резолюции) | **R3** |
| `tickets/00-EPICS.md` (BASELINE для фазы тикетов) | **R1**, EP-11 «деньги + склад» | не входит в EP-11/EP-14 явным текстом |
| Прямое ТЗ Tech Lead на этот набор тикетов | **R1**, «order_returns, return_status, деньги и остатки» | **не входит** — явно только «support-tickets, SLA первого ответа» |

**Принятое решение для всего этого набора тикетов:**

- **EP-11 (DTJ-270..277) — возвраты реализуются ПОЛНОСТЬЮ в R1**: финансовая матрица
  «вина → исход» (SRS-RET-004/005), стратегия раздельного биллинга (SRS-RET-006..009), restock,
  все 7 REST-эндпоинтов, фронтенды клиента и аптеки. Основание: явное прямое указание объёма
  задачи + module 21 §7 (детальная, самодостаточная спецификация с тест-сценариями TC-RET-001..007)
  + `tickets/00-EPICS.md` (EP-11 без пометки «облегчённый»).
- **EP-14 (DTJ-278..284) — ТОЛЬКО облегчённая очередь `support_tickets`**: создание обращения,
  SLA первого ответа, эскалация приоритета, ответ/резолюция БЕЗ денежных последствий. Таблица
  `order_disputes`/`dispute_status_history` заводится схемой (DTJ-270, архитектурный фундамент —
  «ретрофит дороже»), но `OrderDispute`-сущность, `OpenDisputeUseCase`, `resolve-*`-эндпоинты,
  заморозка `payout_schedule` — **НЕ входят** в этот диапазон тикетов, отложены до отдельного
  R2/R3-тикета за флагом `disputes_workflow_enabled`. Основание: явное прямое указание объёма
  задачи («облегчённые») + согласованная позиция трёх источников (module 27, SRS-MASTER, 30-ux).

Если ревью укажет на расхождение с §8 `21-module-orders-payments-escrow.md` (SRS-DISP-001..010)
— это ожидаемо и осознанно, не дефект нарезки.

## Сквозные риски всего набора (см. также «Риски» в каждом тикете)

1. **Гонка миграций с EP-10** (`payout_schedule` должен существовать до `ALTER TABLE ...
   fk_payout_schedule_dispute` в DTJ-270).
2. **Несколько permission-строк и кодов ошибок — обоснованные достройки, не буквальные
   SRS-ID.** `returns:mark-in-transit`, `returns:reject` (DTJ-275), весь блок `support:*`
   (DTJ-282) — исходная RBAC-матрица `12-api-conventions-auth-tenancy.md` §4.1 не содержит этих
   строк явно. Отмечено в каждом соответствующем тикете, согласовать с архитектором при ревью
   при необходимости.
3. **`support_ticket_messages` — новая таблица сверх буквы `11-database-schema.md`**, введена
   DTJ-278 как необходимое условие физической реализуемости SRS-ADM-075 (SLA первого ответа
   требует источника «первого комментария», спецификация не описывает такую таблицу явно).
4. **`cold_chain_breach_suspected`** упомянуто как условие в SRS-DOM-053, но отсутствует в enum
   `return_reason` (`11-database-schema.md`) — трактовано в DTJ-271 как «условие всегда
   истинно», задокументировано в коде, не расширяет enum самовольно.
5. **Нет визуальных макетов** ни для одного фронтенд-экрана этого набора (`32-design-reference.md`
   «Пробелы дизайна» явно перечисляет «обращения поддержки» и не упоминает экраны возвратов
   вовсе — оба случая означают реализацию строго по письменной спецификации с обязательной
   сверкой токенов дизайн-системы).
6. **Два новых feature-slice во владении, явно не перечисленном `tickets/00-EPICS.md`**:
   `apps/pharmacy/src/features/returns/**` (DTJ-277) и `apps/web/src/features/support/**`
   (DTJ-284) — естественное расширение объёма эпиков для end-to-end покрытия, не пересекается
   с существующими владениями других эпиков.
