## Задача

Даже COD-заказы порождают жалобы («не приехал», «повреждена упаковка») — минимальная очередь
обращений нужна с первого дня продукта (`tickets/00-EPICS.md` обоснование EP-14). Это
доменное ядро: `SupportTicket` — самостоятельный агрегат (не придаток `OrderDispute`), который
должен уметь жить весь свой жизненный цикл `open → in_progress → resolved/closed` БЕЗ участия
`OrderDispute` — полный денежный воркфлоу спора (`order_disputes`, заморозка payout, частичный
рефанд) размечен `04-SCOPE-DECISION-PIVOT.md` как **R3-3**, доступен только за фиче-флагом
`disputes_workflow_enabled` (`27-module-admin-moderation-onboarding.md` §9, SRS-ADM-053/077;
граница подтверждена `30-ux-screens-and-flows.md` строка 51 и `00-SRS-MASTER.md` RELEASE 3 п.2)
и НЕ входит в этот тикет и во весь диапазон EP-14 данного набора.

## Технический контекст

`domain/` модуля `support` (`apps/api/src/modules/support/domain/`). Базовая таблица
`support_tickets` уже создана DTJ-270 по `11-database-schema.md` строки 956–975. Этот тикет
добавляет расширение схемы под SLA первого ответа и приоритет — `27-module-admin-moderation-onboarding.md`
§9/§10.1 (SRS-ADM-075/076/078), строки 986–994: `first_response_due_at`, `first_responded_at`,
`priority`. Сущность `SupportTicket` упомянута как агрегат в `10-domain-model.md` (таблица
«Сопутствующие агрегаты», модуль `disputes`) — код физически размещается в
`apps/api/src/modules/support/` согласно владению файлами `tickets/00-EPICS.md`, расхождение
в названии bounded context не меняет реализацию.

## Что сделать

1. Миграция `apps/api/migrations/0011_support_ticket_sla_fields.sql` — 1:1 по
   `27-module-admin-moderation-onboarding.md` строки 986–994:
   `ALTER TABLE support_tickets ADD COLUMN first_response_due_at TIMESTAMPTZ`,
   `ADD COLUMN first_responded_at TIMESTAMPTZ`,
   `ADD COLUMN priority SMALLINT NOT NULL DEFAULT 0`. Той же миграцией добавить
   `ALTER TABLE tenant_settings ADD COLUMN support_first_response_sla_minutes INT NOT NULL
   DEFAULT 60` — SRS-ADM-075 указывает 60 минут как ASSUMPTION-константу
   (`SUPPORT_FIRST_RESPONSE_SLA_MINUTES`), но конфигурация без деплоя (Charter §3.4) требует
   per-tenant поля, не константы в коде; используется в DTJ-279.
2. **[ДОПОЛНЕНИЕ, спецификация не описывает механизм ответа фармацевта/оператора текстом —
   см. «Риски»]** Та же миграция создаёт `support_ticket_messages(id UUID PK, ticket_id UUID
   NOT NULL REFERENCES support_tickets(id) ON DELETE CASCADE, author_user_id UUID REFERENCES
   users(id) ON DELETE SET NULL, author_role user_role NOT NULL, body TEXT NOT NULL, created_at
   TIMESTAMPTZ NOT NULL DEFAULT NOW())` — append-only история переписки по тикету, нужна, чтобы
   `first_responded_at` (SRS-ADM-075) имело физический источник «первый комментарий
   `support_agent`», а не только смену статуса.
3. `SupportTicketCategory` VO (`value-objects/support-ticket-category.vo.ts`) — обёртка над
   enum `support_ticket_category` с методом `isEscrowBlockingEligible(): boolean` — возвращает
   `true` для `'order_not_received' | 'payment_issue' | 'order_item_damaged_or_expired' |
   'order_quality_defect'` (таблица SRS-DISP-001/module 21 §8.1) — метод используется ТОЛЬКО
   для информационного отображения в UI («эта категория обычно эскроу-блокирующая»), НЕ для
   реального создания `OrderDispute` (это R3, гарантированно недостижимо, см. DTJ-279).
4. `SupportTicket` entity (`support-ticket.entity.ts`), приватный конструктор + фабрика
   `SupportTicket.open({ tenantId, orderId?, channel, category, createdBy?, description,
   firstResponseSlaMinutes })`:
   - `is_escrow_blocking` — ВСЕГДА `false` в конструкторе R1 (доменная сущность физически не
     принимает параметр `isEscrowBlocking` — не потому что «поле спрятано», а потому что
     конструктор его не объявляет вовсе; это и есть архитектурная гарантия SRS-ADM-053
     «доменный конструктор `OrderDispute` в R1 не вызывается вообще» — на уровне `SupportTicket`
     это выражается отсутствием параметра, а не условной веткой).
   - `firstResponseDueAt = openedAt + firstResponseSlaMinutes` (минуты приходят параметром — не
     `Date.now()`/захардкоженное число внутри домена, C6/§2.6).
   - `channel = 'system_auto'` допускает `createdBy = null` (SRS-ADM-074), любой другой канал —
     `createdBy` обязателен.
   - `status = 'open'`, `priority = 0` по умолчанию.
   - `ticket.transitionTo(status: 'in_progress' | 'resolved' | 'closed', actorId)` — явная
     таблица переходов (не `if/else`): `open → in_progress`, `open|in_progress → resolved`,
     `resolved → closed`, `resolved → in_progress` (переоткрытие, если решение оспорено) —
     недопустимый переход бросает `InvalidTicketStatusTransitionError`. Терминальный `closed` —
     любая мутация после него бросает `TicketAlreadyTerminalError`.
   - `ticket.recordFirstResponse(respondedAt)` — заполняет `firstRespondedAt` ТОЛЬКО если ещё
     `null` (идемпотентно — повторный вызов не перезаписывает более раннее время первого ответа).
   - `ticket.escalatePriority()` — `priority += 1`, вызывается джобой эскалации (DTJ-280), не
     пользователем напрямую.
   - `ticket.addMessage(SupportTicketMessage)` — не мутирует статус, только добавляет запись;
     ЕСЛИ `author_role === 'support_agent'` И `firstRespondedAt === null`, автоматически
     вызывает `recordFirstResponse(message.createdAt)` (SRS-ADM-075: «первый комментарий
     `support_agent` фиксирует `first_responded_at`»).
5. `SupportTicketMessage` — простая сущность (не корень агрегата, дочерняя `SupportTicket`):
   `{ id, ticketId, authorUserId, authorRole, body, createdAt }`.
6. Экспортировать всё из внутреннего барреля `apps/api/src/modules/support/domain/index.ts`.

## Критерии приёмки

1. **Given** тикет создан с `category='order_item_damaged_or_expired'`, **When** проверяется
   поле `isEscrowBlocking` результирующего объекта, **Then** значение `false`, а сам конструктор
   домена не принимает и не может принять иное значение (структурная гарантия, не рантайм-проверка).
2. **Given** тикет в статусе `resolved`, **When** первым `support_agent`-комментарием переоткрывается
   (`transitionTo('in_progress', ...)`), **Then** переход разрешён; **Given** тикет в `closed`,
   **When** вызывается `transitionTo('in_progress', ...)`, **Then** бросается
   `TicketAlreadyTerminalError` — терминальность `closed` в отличие от `resolved`.
3. **Given** `firstRespondedAt` уже заполнен, **When** повторно вызывается `recordFirstResponse()`
   с более поздним временем, **Then** значение НЕ перезаписывается (проверка идемпотентности).
4. **Given** `channel='in_app'`, `createdBy=null`, **When** вызывается `SupportTicket.open()`,
   **Then** бросается ошибка валидации — `createdBy` обязателен для не-системных каналов
   (негативный сценарий).

## Тест-план

Unit-тесты (Vitest, без БД):
- `SupportTicket.open()` — все каналы, включая граничный случай `system_auto`/`createdBy=null`
  и обратный (не-`system_auto` без `createdBy` — ошибка).
- Полная таблица переходов `transitionTo` — параметризованный прогон по всем комбинациям,
  включая заведомо недопустимые.
- `recordFirstResponse` идемпотентность.
- `addMessage` — автоматическая фиксация `first_responded_at` при первом сообщении
  `support_agent`, НЕ при сообщении от `customer`.
- `SupportTicketCategory.isEscrowBlockingEligible()` — все 6 значений enum.
Интеграционный тест — применение миграции `0011` на чистой БД (после `0010` из DTJ-270),
проверка новых колонок и таблицы `support_ticket_messages` через `information_schema`.
Порог покрытия `domain/` — 90%.

## Риски и подводные камни

- **`support_ticket_messages` — расширение сверх буквы спецификации.** SRS-ADM-075 упоминает
  «первый комментарий `support_agent`» как факт, порождающий `first_responded_at`, но НИ ОДИН
  документ `docs/spec/` не определяет таблицу для хранения самих комментариев/переписки по
  тикету. Это осознанное дополнение схемы (аналогично тому, как сами SRS-ADM-075/076 помечены
  `[ДОПОЛНЕНИЕ]` в исходнике) — необходимо для физической реализуемости требования. Если
  архитектор впоследствии решит иначе (например, переиспользовать `notifications`/`audit_log`
  вместо отдельной таблицы) — потребуется ADR и миграция удаления, это явный риск ретрофита.
- **`is_escrow_blocking` в БД остаётся `NOT NULL DEFAULT false` (DTJ-270), но домен НЕ
  управляет им активно.** Если в будущем (R2/R3) появится `OpenDisputeUseCase`, ему потребуется
  РАСШИРИТЬ (не переписать) фабрику `SupportTicket.open()` — текущая сигнатура сознательно не
  принимает этот параметр, чтобы не оставлять скрытый способ его обойти в R1.
