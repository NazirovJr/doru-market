## Задача

Возврат, доехавший обратно в аптеку, не разрешает сам себя — фармацевт физически осматривает
упаковку и принимает решение «restock или уничтожить» через чек-лист. Без этого экрана
`ConfirmReturnReceivedUseCase` (DTJ-273) и `ReturnFinancialOutcomeResolver` (DTJ-272) не имеют
входной точки в веб-кабинете аптеки — единственном интерфейсе фармацевта в R1 (Flutter-терминал
— R2, `Charter §3.6`).

## Технический контекст

`apps/pharmacy/src/features/returns/` — НОВАЯ feature-slice, отдельная от `features/inventory-manual/`
(EP-05, владелец `app/`-каркаса) и `features/order-fulfillment/` (EP-12) — правило
`tickets/00-EPICS.md` «Пересекающееся владение» п.2: общий `app/` каркас принадлежит EP-05,
этот тикет только добавляет свою запись в роутер и работает исключительно внутри
`features/returns/**`, не трогая чужие директории. Дизайн-референс не содержит макета кабинета
аптеки для возвратов (`32-design-reference.md` показывает только экран СБОРКИ заказа,
`.dc.html:120-195`) — реализация по письменной спецификации.

## Что сделать

1. `use-incoming-returns.ts` — TanStack Query список возвратов своей аптеки в статусе
   `return_in_transit` (едут) и `return_rejected` (ожидают повторной попытки/эскалации) —
   отдельная секция для каждого статуса, аналог структуры очереди заказов (`/admin/order-queue`
   паттерн, если уже реализован EP-12 к этому моменту — переиспользовать компоновку списка, не
   бизнес-логику).
2. `IncomingReturnsList.tsx` — список карточек: номер заказа, причина, ожидаемая дата прибытия
   (если есть), кнопка «Принять возврат» → открывает `ReturnChecklistForm`.
3. `ReturnChecklistForm.tsx` + `ReturnChecklistForm.model.ts` — форма чек-листа:
   - Переключатель `packagingIntact` (`Switch` из `packages/ui`, `32-design-reference.md`
     «Пробелы дизайна» отмечает этот компонент как БЕЗ визуального покрытия — временная
     локальная реализация допустима с тикетом на перенос).
   - Поле `checklistNotes` (`Textarea`).
   - **Модель (`model/`, чистая функция, юнит-тестируемая)**: given `controlCategory !== 'none'`
     товара в возврате (данные приходят в составе `GET /:id` — расширение DTO на этот случай
     координируется с DTJ-275, если поле `controlCategory` ещё не присутствует в
     `OrderReturnDto` на момент реализации — завести дополнение к контракту, не выдумывать
     собственное поле локально) — переключатель `packagingIntact` визуально ЗАБЛОКИРОВАН в
     положении «restock невозможен», с текстом-объяснением (SRS-DOM-054 — контролируемое
     вещество уничтожается независимо от состояния упаковки, UI не должен создавать иллюзию
     выбора там, где домен всё равно откажет).
   - Кнопка «Подтвердить приёмку» → `use-confirm-return.ts` (`ConfirmReturnReceivedUseCase`).
   - Кнопка «Отклонить» (отдельный CTA, не часть той же формы — reject не требует чек-листа
     упаковки, только причину отказа текстом) → `use-reject-return.ts`.
4. После успешного подтверждения — экран показывает итоговый `disposition` (`restock`/`destroy`)
   так, как его вернул сервер (НЕ пересчитывать на клиенте — сервер уже применил SRS-DOM-053/054,
   клиент только отображает результат).
5. Локализация — весь текст через `useT()`, словари `pharmacy-returns.{tj,ru,en}.json`.
6. Добавить одну строку маршрута в общий роутер `apps/pharmacy/src/app/` (созданный EP-05) —
   `/pharmacy/returns`, без правки остальной структуры каркаса.

## Критерии приёмки

1. **Given** возврат `return_in_transit` для товара с `controlCategory='none'`, **When**
   фармацевт заполняет чек-лист с `packagingIntact=true` и подтверждает, **Then** заказ уходит
   на сервер, ответ показывает `disposition='restock'`.
2. **Given** товар с `controlCategory='psychotropic'`, **When** фармацевт открывает чек-лист,
   **Then** переключатель `packagingIntact` заблокирован в положении «restock недоступен» с
   поясняющим текстом — негативный сценарий (UI не позволяет создать ложное ожидание).
3. **Given** фармацевт нажимает «Отклонить» без указания причины, **When** отправляется форма,
   **Then** отправка блокируется валидацией — причина обязательна (СХЕМА, а не серверная
   проверка постфактум — быстрая обратная связь).
4. **Given** фармацевт чужой аптеки открывает список (гипотетически, если бы UI не фильтровал) —
   этот сценарий закрывается RBAC на API-уровне (DTJ-275), UI-тест здесь ограничивается проверкой,
   что запрос списка идёт СО скоупом текущей аптеки (`pharmacyId` берётся из сессии, не из URL).

## Риски и подводные камни

- **Общий каркас `apps/pharmacy/src/app/` — чужая собственность (EP-05).** Если к моменту
  реализации этого тикета каркас ещё не готов — тикет блокирован на уровне интеграции (сама
  feature разрабатывается независимо, роутинг подключается последним шагом).
- **`controlCategory` в `OrderReturnDto`.** DTJ-275 не гарантированно включает это поле в
  исходном контракте (домен `returns` не хранит категорию контроля — она у `catalog`). Нужно
  явно согласовать расширение DTO с DTJ-275 (или с последующим PR к контракту) до начала верстки
  этой формы — иначе блокировка переключателя технически нечем обосновать на фронте.
- **Нет визуального макета** — тот же риск, что в DTJ-276, сверка токенов дизайн-системы перед
  сдачей обязательна.
