## Задача

Подтверждённый возврат (DTJ-273) по событию `ReturnConfirmedEvent` доходит до
`RefundOnReturnResolvedUseCase` через роутер domain-events (DTJ-032), но для заказов, оплаченных
онлайн (эскроу), рефанд бросает исключение: `RETURNS_PAYMENTS_PORT` связан с
`UnimplementedReturnsPaymentsAdapter`. Возврат денег за товар по R1 (D-09) фактически не работает.
Найдено при приёмке DTJ-032 (2026-09-25).

## Технический контекст

Порт уже описан в `returns/application/ports/*payments*.port.ts`: команды рефанда позиций,
доставки, полного рефанда и корректировки ledger (`amountDiram: bigint`). Модуль payments уже
умеет `RefundOrderUseCase` и `PartiallyRefundOrderUseCase` (эскроу-ledger двойной записи, D-02,
провайдер через `PaymentProviderPort`, в R1 — `MockBankProvider`). Returns обращается к payments
только через фасад `modules/payments/index.ts`.

## Что сделать

1. Если фасад payments не даёт нужных операций — добавить минимально (делегирование в
   существующие use case'ы, без новой денежной логики).
2. `PaymentsFacadeAdapter` в returns реализует `RETURNS_PAYMENTS_PORT` поверх фасада; маппинг
   команд порта → операции payments; идемпотентность по `returnId` (повтор события не делает
   второй рефанд).
3. Заменить `UnimplementedReturnsPaymentsAdapter` в `returns.module.ts` реальным адаптером,
   заглушку удалить (C8).
4. Корректировки ledger (`recordAdjustment`) — через существующий `AdjustLedgerUseCase`
   (DTJ-246), с аудитом, если он там уже пишется.

## Критерии приёмки

1. **Given** заказ `paid_escrow`, подтверждён возврат позиций на 5000 дирам, **When** событие
   обработано, **Then** в `escrow_ledger` записи рефанда на 5000 и провайдер получил рефанд.
2. **Given** то же событие доставлено повторно, **When** обработано, **Then** второго рефанда и
   второй записи ledger нет.
3. **Given** заказ с оплатой наличными курьеру, **When** возврат подтверждён, **Then** поведение
   как сейчас (ветка без движения денег), без обращения к провайдеру.
4. **Given** инвариант D-25 (`paid_escrow` ⟺ есть записи ledger), **When** после рефанда
   прогоняется `tests/invariants`, **Then** зелёный.

## Тест-план

- Интеграционный на живом Postgres: сквозной путь outbox → relay → роутер → рефанд (критерии 1–3).
- Unit адаптера: маппинг каждой команды порта.
