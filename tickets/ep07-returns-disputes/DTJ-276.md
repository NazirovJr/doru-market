## Задача

Клиент должен иметь возможность запросить возврат после вручения заказа и видеть, что с ним
происходит — иначе EP-11 остаётся бэкендом без пользователя. Дизайн-референс
(`32-design-reference.md`) НЕ содержит макета для этого экрана — раздел «Пробелы дизайна» этот
конкретный флоу явно не упоминает как готовый, значит реализация — строго по письменной
спецификации UX и токенам `packages/ui`, без визуального ориентира.

## Технический контекст

`apps/web/src/features/order-returns/` — новый feature-slice (`02-CLEAN-ARCHITECTURE-AND-CODE.md`
§5, зависимости строго вниз `app → pages → features → entities → shared`, никаких
горизонтальных импортов из `features/orders`/`features/checkout`). Точка входа —
`RequestReturnButton` встраивается в существующий экран `/orders/:id` (владелец — EP-09/EP-10,
здесь только добавляется импорт компонента ИЗ `entities`/точки расширения, не правится сама
страница напрямую, если экран уже существует — координация через `pages/order-detail` компоновку,
не прямой горизонтальный импорт `features/checkout`). Источник UX-текста — `30-ux-screens-and-flows.md`
строка 330: `/orders/:id` → `/order-returns/new` (после `delivered`, в окне) `[R1]`. API — DTJ-275.

## Что сделать

1. `use-request-return.ts` — TanStack Query мутация поверх `POST /api/v1/order-returns`,
   генерирует `Idempotency-Key` (UUID v4) один раз на попытку отправки формы (не на каждый
   ре-рендер — хранить в `useRef`, сбрасывать только при новой попытке после ошибки).
2. `use-return-details.ts` — TanStack Query запрос `GET /api/v1/order-returns/:id`, `refetchInterval`
   для отслеживания смены статуса, пока возврат не в терминальном статусе
   (`return_confirmed`/`return_rejected` — при `return_rejected` продолжать поллинг, т.к. статус
   НЕ терминален, SRS-DOM-056, возможен `admin_override` позже).
3. `return-reason-options.ts` — чистая функция, возвращающая список доступных причин для UI в
   зависимости от того, доставлен заказ или ещё нет (`picked_up` → только
   `refused_at_door`/`undeliverable`, недоступно клиенту напрямую — эта ветка инициируется
   курьером/диспетчером, не показывается в клиентском UI вовсе; `delivered` → все причины кроме
   `undelivered`, которая обрабатывается отдельной кнопкой «Не получил заказ» — редиректит на
   создание `support_tickets`, не на эту форму, SRS-RET-003).
4. `RequestReturnForm.tsx` — форма: выбор причины (`RadioGroup` из `packages/ui`, если уже готов
   к моменту реализации — иначе временный локальный компонент в `ui/` этой feature с тикетом на
   перенос, правило `tickets/00-EPICS.md` «Пересекающееся владение» п.6), комментарий (опционально,
   `Textarea`), кнопка отправки. Компонент ≤ 150 строк (`02` §5), бизнес-логика — в `model/`, не
   в компоненте.
5. `ReturnStatusTimeline.tsx` — визуальный таймлайн статусов возврата (аналог `OrderTimeline`,
   переиспользовать паттерн из `entities/`, если он там уже есть на момент реализации).
6. `RequestReturnButton.tsx` — кнопка на `/orders/:id`, видима ТОЛЬКО при: заказ `delivered` И
   `now() <= deliveredAt + disputeWindowHours` (значение окна приходит с сервера в составе заказа
   — не пересчитывается на клиенте по захардкоженному числу, C6). По истечении окна — кнопка
   скрыта, НЕ показывает disabled-состояние с объяснением (SRS-RET-012 — окно жёсткое, сервер всё
   равно отклонит, но кнопка не должна провоцировать бессмысленную попытку).
7. Локализация — все строки через `useT()` (`packages/i18n`), словари `tj`/`ru`/`en` для этой
   feature, дефолт-локаль `tj` (Charter). Ноль хардкода цвета — только CSS-переменные
   `packages/ui`.
8. Состояние сервера — TanStack Query (пп. 1-2), состояние UI (какой шаг формы активен) —
   `useState`, не смешивать (`02` §5).

## Критерии приёмки

1. **Given** заказ `delivered`, окно возврата не истекло, **When** пользователь открывает
   `/orders/:id`, **Then** видна кнопка «Запросить возврат», ведущая на форму с причинами
   (кроме `undelivered`).
2. **Given** пользователь заполнил форму и нажал «Отправить» дважды подряд (двойной клик),
   **When** оба клика долетают до сервера, **Then** отправлен ОДИН `Idempotency-Key`, создан
   ОДИН возврат (клиентская защита — кнопка блокируется после первого клика ДО ответа сервера).
3. **Given** окно возврата истекло, **When** пользователь открывает `/orders/:id`, **Then**
   кнопка «Запросить возврат» не отображается вовсе — негативный сценарий.
4. **Given** возврат в статусе `return_rejected`, **When** пользователь открывает статус
   возврата, **Then** таймлайн показывает «отклонён» БЕЗ пометки «завершено» (визуально
   отличается от терминального `return_confirmed` — статус может ещё измениться через
   `admin_override`).

## Тест-план

- Unit-тесты `model/return-reason-options.ts` — чистая функция, все комбинации входного статуса
  заказа → ожидаемый список причин.
- Component-тесты (Vitest + Testing Library) `RequestReturnForm`/`RequestReturnButton`:
  видимость кнопки по условию окна, блокировка повторной отправки, рендер всех 3 локалей без
  падения (smoke-тест на отсутствие непереведённых ключей).
- Интеграционный тест `use-request-return.ts` — мок API, проверка, что `Idempotency-Key`
  переиспользуется при ретрае того же запроса и меняется при новой явной попытке пользователя.
- E2E — не входит в этот тикет (см. риск ниже).
- Порог покрытия `frontend` — 70% (`02` §6.4).

## Риски и подводные камни

- **Нет визуального макета.** `32-design-reference.md` не содержит этого экрана — высокий риск
  разойтись стилистически с остальным приложением без явной ревью-сверки токенов (отступы,
  типографика) с разделом «Извлечённые токены» того же документа перед сдачей.
- **Точка встраивания в `/orders/:id`.** Если на момент реализации страница заказа (владелец —
  другой эпик) уже существует с иной структурой компоновки — потребуется согласовать точку
  расширения (слот/composition API), а не редактировать чужой `pages/`-файл напрямую (нарушение
  границы фичи, `02` §5).
- **`RadioGroup` из `packages/ui`** прямо назван в `32-design-reference.md` («Пробелы дизайна»,
  строка 354) как компонент БЕЗ полного визуального покрытия дизайном — есть риск, что к моменту
  реализации он ещё не готов у EP-18; временная локальная реализация — с обязательным тикетом на
  перенос (правило п.6 `tickets/00-EPICS.md`).
