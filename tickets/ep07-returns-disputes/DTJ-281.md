## Задача

Модуль `delivery` (EP-13) обнаруживает просрочку `delivery_sla` собственной джобой
(`DeliverySlaMonitorJob`) и должен уметь автоматически завести обращение — но по правилу
Зависимостей ему запрещено импортировать `modules/support/domain|application` напрямую
(`02` §1.1/§1.2). Этот тикет закрывает публичный контракт модуля `support` целиком: и точку
входа для «системного» создания тикета, и авторизационную политику для обычных пользовательских
операций (создание/чтение), которую use case'ы DTJ-279/282 переиспользуют вместо разрозненных
проверок.

## Технический контекст

`apps/api/src/modules/support/index.ts` — единственный разрешённый способ для ДРУГИХ модулей
обратиться к `support` (`02` §1.2). Источник авто-создания тикета — SRS-ADM-074
(`27-module-admin-moderation-onboarding.md` строки 805–810): `DeliverySlaMonitorJob` мониторит
`delivered_at IS NULL AND now() > sla_deadline`, создаёт тикет ВСЕГДА, независимо от R3-статуса
самой резолюции спора.

## Что сделать

1. `CreateAutoSupportTicketUseCase.execute({ tenantId, orderId, category, description })` —
   тонкая обёртка над `CreateSupportTicketUseCase` (DTJ-279) с зафиксированными
   `channel='system_auto'`, `createdBy=null` — публикуется через фасад как единственный вход для
   системных инициаторов (джоб других модулей), не как публичный REST-эндпоинт (нет
   HTTP-поверхности — вызывается исключительно server-to-server, внутри процесса `apps/api`,
   либо out-of-process воркером через тот же паттерн, что и `SupportFacade.escalateTicketPriority`
   из DTJ-280).
2. `SupportTicketsPolicy` (`application/support-tickets.policy.ts`) —
   `canRead(actor, ticket): boolean` (владелец тикета/`support_agent`/`super_admin`),
   `canRespond(actor, ticket): boolean` (`support_agent`/`super_admin`),
   `canResolve(actor, ticket): boolean` (`support_agent`/`super_admin`) — переиспользуется
   DTJ-282 (presentation), избегая дублирования правил в контроллере.
3. `modules/support/index.ts` — публичный фасад (`SupportFacade`), экспортирует:
   - `createTicket(...)` → `CreateSupportTicketUseCase` (для человеческих каналов, вызывается
     `presentation`-слоем самого модуля `support`, DTJ-282).
   - `createAutoTicket(...)` → `CreateAutoSupportTicketUseCase` (для ДРУГИХ модулей —
     `DeliveryFacade`/`ReturnsFacade`, например переадресация `reason='undelivered'` из DTJ-273
     тоже проходит через ЭТОТ метод, а не напрямую use case).
   - `escalateTicketPriority(ticketId)` → используется DTJ-280 (тот же паттерн вызова через
     фасад, не напрямую use case, даже изнутри своего же модуля — единообразие точки входа).
   - Публичные типы `SupportTicketSummary` (минимальный DTO для чужих модулей — НЕ полный
     `SupportTicketDto` из `presentation`, только то, что реально нужно потребителям: `id`,
     `status`, `category`).
   - Домен/application НЕ реэкспортируются целиком — только перечисленное выше (`02` §1.2:
     «Всё остальное внутри модуля — приватно»).

## Критерии приёмки

1. **Given** `DeliveryFacade` (гипотетический вызывающий код, здесь — тестовый двойник) вызывает
   `SupportFacade.createAutoTicket({ tenantId, orderId, category: 'order_not_received',
   description })`, **When** вызов завершается, **Then** создан `support_tickets` с
   `channel='system_auto'`, `created_by IS NULL`, `is_escrow_blocking=false`.
2. **Given** попытка импортировать `modules/support/application/use-cases/*` напрямую из другого
   модуля (например, тестовый файл, имитирующий `modules/delivery`), **When** запускается
   `pnpm arch:check`, **Then** проверка падает — только `index.ts` разрешён для межмодульного
   импорта.
3. **Given** `customer`, не являющийся автором тикета и не `support_agent`/`super_admin`,
   **When** проверяется `SupportTicketsPolicy.canRead(actor, ticket)`, **Then** возвращается
   `false`.
