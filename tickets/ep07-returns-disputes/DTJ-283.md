## Задача

`support_agent`/`super_admin` — единственные, кто закрывает обращения в R1, и делают это через
`apps/admin`, единственный человеческий UI для этих ролей (Charter §3.2). Без визуальной очереди
с явной SLA-индикацией джоба эскалации (DTJ-280) поднимает `priority` в БД, которую никто не
видит — весь смысл SLA-механизма теряется.

## Технический контекст

`apps/admin/src/features/support/**` — по правилу владения файлов `tickets/00-EPICS.md` этот
эпик владеет данной директорией целиком, но общий каркас `apps/admin/src/{app,pages}/**`
принадлежит EP-03 (первый эпик, добравшийся до `apps/admin`) — этот тикет добавляет ОДНУ запись
маршрута в существующий роутер, не переписывает каркас (правило «Пересекающееся владение» п.1).
Дизайн-референс НЕ содержит макета: `32-design-reference.md` «Пробелы дизайна» прямо перечисляет
«обращения поддержки» в списке экранов `super_admin`-раздела БЕЗ визуального покрытия — работа
строго по письменному UX (`30-ux-screens-and-flows.md` строка 378: `/admin/support-tickets` —
«список, SLA первого ответа, назначение/резолюция без финансовых последствий», `[R1]`).

## Что сделать

1. `use-support-tickets.ts` — TanStack Query список с фильтрами (`status`, `category`,
   `priority`), синхронизированными с query-параметрами URL (чтобы ссылка на отфильтрованный
   вид была шарабельной между сотрудниками поддержки).
2. `SupportTicketFilters.tsx` — панель фильтров: статус (`Select`), категория (`Select`),
   переключатель «только просроченные по SLA» (клиентский фильтр по
   `firstResponseDueAt < now() && !firstRespondedAt`, вычисляется в `model/`, не на сервере —
   сервер уже отдаёт нужные поля, доп. эндпоинт не нужен).
3. `SlaBadge.tsx` — визуальный индикатор: зелёный (в пределах SLA), жёлтый (< 15 минут до
   дедлайна), красный (просрочен, соответствует эскалированному `priority > 0` от DTJ-280).
   Цвета — ТОЛЬКО через семантические CSS-переменные `packages/ui` (`--color-status-success`/
   `--color-status-warning`/`--color-status-danger` или их эквивалент, сверить точные имена
   токенов с `32-design-reference.md` §«Извлечённые токены» перед реализацией — не изобретать
   новые имена переменных).
4. `SupportTicketQueue.tsx` — таблица/список карточек тикетов, сортировка по умолчанию:
   просроченные + высокий приоритет первыми (агент не должен листать до критичного тикета).
5. `SupportTicketDetail.tsx` — деталь тикета: метаданные (заказ-ссылка, если есть, категория,
   канал, время создания), лента сообщений (`SupportTicketMessage[]`), поле ответа
   (`use-respond-ticket.ts` → `POST /:id/messages`), кнопки смены статуса
   (`use-change-ticket-status.ts` → `POST /:id/status`) — доступны только `support_agent`/
   `super_admin` (RBAC уже на сервере, но кнопки скрываются на клиенте для чистоты UX, не как
   единственный рубеж защиты).
6. Given тикет имеет `orderId` — ссылка на деталь заказа (переиспользовать существующий роутинг
   `apps/admin`, если экран заказа уже реализован другим эпиком к этому моменту — иначе просто
   текстовый номер заказа без ссылки, без блокировки этого тикета).
7. Локализация — весь текст через `useT()`, словари `admin-support.{tj,ru,en}.json`.
8. Добавить одну строку маршрута `/admin/support-tickets` в общий роутер `apps/admin`
   (владелец каркаса — EP-03/EP-15 в зависимости от волны, см. «Риски»).

## Критерии приёмки

1. **Given** очередь содержит 3 тикета: один просрочен (`priority > 0`), два в пределах SLA,
   **When** страница загружается, **Then** просроченный тикет отображается ПЕРВЫМ, с красным
   `SlaBadge`.
2. **Given** `support_agent` открывает деталь тикета и отправляет первый ответ, **When** ответ
   отправлен успешно, **Then** UI немедленно (оптимистичное обновление TanStack Query или
   рефетч) показывает `firstRespondedAt` заполненным, `SlaBadge` переключается на нейтральное
   состояние «отвечено».
3. **Given** тикет уже `closed`, **When** агент открывает деталь, **Then** кнопки смены статуса
   скрыты — негативный сценарий (терминальное состояние визуально финально).
4. **Given** фильтр «только просроченные», **When** применяется, **Then** список показывает
   ТОЛЬКО тикеты с истёкшим `firstResponseDueAt` и незаполненным `firstRespondedAt`.

## Риски и подводные камни

- **Владелец каркаса `apps/admin/src/{app,pages}` на момент этого тикета — не факт, что EP-03.**
  Правило «Пересекающееся владение» п.1 `tickets/00-EPICS.md` отдаёт каркас «первому эпику,
  который до него добирается по волнам» — EP-03 (волна 3). К волне выполнения EP-14 (волна 10)
  каркас почти наверняка уже расширен EP-15 (тоже волна 10, но заявлен «главным автором»
  `app/pages` в этой волне). Добавлять строку роутинга нужно в АКТУАЛЬНОЕ состояние каркаса на
  момент реализации, координируя очерёдность мержа с EP-15, а не полагаться на состояние,
  описанное здесь статично.
- **Нет визуального макета** — риск разойтись с остальным `apps/admin` стилистически, сверка
  токенов обязательна перед сдачей (тот же риск, что в DTJ-276/277).
