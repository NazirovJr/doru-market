## Задача

Подтверждённый возврат обязан вернуть клиенту деньги — но КАК именно зависит от того, оформлен
ли заказ с раздельным биллингом items/delivery (D-10, т.к. `MockBankProvider` и оба реальных
адаптера R3 не поддерживают `partialRefund`). Ошибка здесь либо не вернёт клиенту деньги за
брак, либо вернёт больше денег, чем положено, без фиксации разницы для сверки с аптекой при
следующем payout. Это единственная точка, где деньги реально двигаются в модуле `returns` — всё
остальное в эпике готовит решение, это его исполняет.

## Технический контекст

`application/use-cases/` модуля `returns`, подписчик на `ReturnConfirmedEvent`/
`ReturnRejectedEvent` (публикуются DTJ-273 через `outbox`). Обращение к деньгам — ТОЛЬКО через
`ReturnsPaymentsPort` (DTJ-270), реализация которого в `infrastructure` оборачивает публичный
`PaymentsFacade` модуля `payments` (владелец EP-10) — правило владения файлов `returns`
запрещает прямой импорт `modules/payments/domain|application` (`tickets/00-EPICS.md`). Источник
— `21-module-orders-payments-escrow.md` §7.3 (SRS-RET-006..009), §7.4 (SRS-RET-010).

## Что сделать

1. `RefundOnReturnResolvedUseCase.execute({ returnId, orderId, reason, disposition })` —
   вызывается ТОЛЬКО для `ReturnConfirmedEvent` (подтверждённый возврат подразумевает деньги
   клиенту; `ReturnRejectedEvent` НЕ триггерит рефанд — деньги не возвращаются за отклонённый
   возврат, use case просто не выполняет никаких платёжных операций для этого события,
   `refund-on-return-resolved.subscriber.ts` явно разделяет подписку на оба типа событий, но
   реагирует только на `Confirmed`).
2. Вызывает `ReturnFinancialOutcomeResolver.resolve(reason, disposition)` (DTJ-272) — получает
   `{ itemsRefund, deliveryFeeRefund }`.
3. Читает `orders.billingStrategy` заказа через `ReturnsOrdersPort.getOrderForReturn(orderId)`
   (расширить порт полем `billingStrategy: 'single_invoice' | 'split_items_delivery'`,
   снэпшотится на checkout — SRS-RET-009, читается как есть, НЕ пересчитывается по текущему
   `tenant_settings.useSplitBilling`).
4. **Given** `billingStrategy === 'split_items_delivery'` (SRS-RET-007): для каждой части, где
   `*Refund === 'full'`, вызывает `ReturnsPaymentsPort.refundByComponent(orderId, component:
   'items' | 'delivery')` — это ПОЛНЫЙ `refund()` конкретной `payment_operations`-строки с
   `billing_component`, совпадающим с частью (НЕ `partialRefund()` — провайдер его не
   поддерживает, MVP-дефолт `supportsPartialRefund=false` для ВСЕХ адаптеров).
5. **Given** `billingStrategy === 'single_invoice'` (SRS-RET-008, резервная стратегия) И
   `itemsRefund === 'full'` НО `deliveryFeeRefund === 'none'` (типичный случай частичного
   возврата при выключенном split billing) — вызывает `ReturnsPaymentsPort.refundFull(orderId)`
   (ПОЛНЫЙ возврат всей суммы, включая ту часть, что «не положена» по матрице) И
   `ReturnsPaymentsPort.recordAdjustment(orderId, overpaidAmount, reason)` — аналитическая
   `escrow_ledger.entry_type='adjustment'` запись на недополученную аптекой сумму (разница НЕ
   довзыскивается с клиента, фиксируется для сверки при следующем payout — SRS-RET-008).
6. **Given** `itemsRefund === 'full' AND deliveryFeeRefund === 'full'` независимо от стратегии —
   простой случай, `refundFull(orderId)` без корректировок (обе стратегии сходятся к одному и
   тому же результату, когда возвращать нужно всё).
7. **Given** `payment_method === 'cash_courier'`: `ReturnsPaymentsPort` для такого заказа НЕ
   вызывается вовсе (SRS-RET-010, REQ-RET-10 — эскроу-леджера для наличных нет; use case
   проверяет `paymentMethod` заказа ПЕРВЫМ шагом и завершает выполнение без платёжных вызовов —
   физический возврат наличных курьером фиксируется отдельно, вне `PaymentsFacade`, best-effort
   операционная запись, не автоматизирована в R1).
8. Идемпотентность: подписчик на `outbox`-событие использует уже установленный паттерн
   at-least-once (`processed_events`, `SRS-DOM-152`-подобный) — повторная доставка
   `ReturnConfirmedEvent` для уже обработанного `return_id` не вызывает повторный рефанд.

## Критерии приёмки

1. **Given** `billingStrategy='split_items_delivery'`, возврат частичный (только `items`),
   **When** `RefundOnReturnResolvedUseCase` выполняется, **Then** `refund()` вызван ТОЛЬКО на
   `providerRef` строки `billing_component='items'`, `delivery`-транзакция не затронута
   (аналог TC-RET-004).
2. **Given** `billingStrategy='single_invoice'`, `supportsPartialRefund=false`, частичный
   возврат запрошен, **When** use case выполняется, **Then** выполняется ПОЛНЫЙ `refund()` +
   создаётся `escrow_ledger.adjustment` на недополученную разницу (аналог TC-RET-005).
3. **Given** `payment_method='cash_courier'`, возврат подтверждён, **Then**
   `PaymentProvider.refund()`/`ReturnsPaymentsPort.*` НЕ вызваны ни разу — проверка через мок
   `expect(paymentsPort.refundFull).not.toHaveBeenCalled()` (аналог TC-RET-007) — негативный
   сценарий: подтверждаем именно ОТСУТСТВИЕ вызова.
4. **Given** `ReturnConfirmedEvent` доставлен дважды (at-least-once), **When** оба вызова
   обработаны, **Then** `refund()`/`refundByComponent()` вызван РОВНО один раз суммарно, не
   дважды.

## Тест-план

Интеграционные тесты (Vitest + мок `ReturnsPaymentsPort`, без реального провайдера):
- Полный набор комбинаций `billingStrategy × itemsRefund × deliveryFeeRefund` (используя
  таблицу из DTJ-272) — проверка, какой именно метод порта вызван и с какими аргументами.
- `cash_courier` — ноль вызовов `ReturnsPaymentsPort`.
- Двойная доставка события — ровно один вызов рефанда (идемпотентность).
- `ReturnRejectedEvent` — ноль вызовов рефанда (use case не реагирует на это событие).
Покрытие `application/` — 90%.

## Риски и подводные камни

- **Сигнатуры `ReturnsPaymentsPort` — предположение о контракте `PaymentsFacade`.** Порт
  объявлен в DTJ-270 как заготовка; точные сигнатуры `refundFull`/`refundByComponent`/
  `recordAdjustment` зависят от того, что реально экспортирует публичный фасад модуля `payments`
  (владелец EP-10) на момент реализации этого тикета. Если фасад EP-10 ещё не готов —
  реализовать порт против мок-адаптера и зафиксировать несоответствие в PR как блокер для
  мержа, не для написания кода.
- **`escrow_ledger.adjustment` для `cash_courier` невозможен по определению** (ledger для
  наличных не создаётся вовсе, §4.6 module 21) — это НЕ баг данного use case: резервная
  стратегия SRS-RET-008 применяется только к non-cash заказам, `cash_courier`-ветка (п.7)
  перехватывает случай раньше, чем логика раздельного биллинга вообще рассматривается.
