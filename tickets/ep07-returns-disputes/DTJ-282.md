## Задача

Замыкает облегчённую очередь обращений человеческим доступом: клиент создаёт тикет и видит его
статус, `support_agent`/`super_admin` видят очередь, отвечают и закрывают. Без этого тикета
DTJ-283/284 (фронтенды) не имеют API, на который опираться.

## Технический контекст

`presentation/` модуля `support`. Явного эндпоинт-перечня для полного жизненного цикла тикета
(список/ответ/резолюция) в `docs/spec/` НЕТ — только создание описано явно (`SRS-ADM-074`:
`POST /api/v1/support-tickets`). Остальные эндпоинты ниже — обоснованная достройка по аналогии с
уже установленными конвенциями `12-api-conventions-auth-tenancy.md` (пагинация, формат ошибок,
permission-строки вида `<resource>:<action>[:<scope>]`, SRS-API-038), отмечено явно как
дополнение, не как SRS-ID с конкретным номером.

## Что сделать

1. `support-tickets.controller.ts`, базовый путь `/api/v1/support-tickets`:
   - `POST /` — `SupportFacade.createTicket(...)`. RBAC: `customer` (свои заказы), любой
     аутентифицированный пользователь для тикета без `orderId` (`orderId` необязателен по DDL,
     `support_tickets.order_id` nullable). Permission `support:create`.
   - `GET /` — список с фильтрами `status`, `category`, `priority`, курсорной пагинацией (уже
     установленный паттерн `CursorList`/`12-api-conventions...md`). RBAC: `customer` видит
     только свои (`support:read:own`), `support_agent`/`super_admin` — все тикеты своего тенанта
     (`support:read:any`).
   - `GET /:id` — деталь + список сообщений (`support_ticket_messages`, DTJ-278).
     `SupportTicketsPolicy.canRead`.
   - `POST /:id/messages` — добавить сообщение (`ticket.addMessage(...)`, DTJ-278). RBAC:
     владелец тикета (`customer`) ИЛИ `support_agent`/`support:respond` для сотрудника
     поддержки — оба варианта допустимы (клиент может дописать в свой тикет, агент — ответить).
   - `POST /:id/status` — `{ status: 'in_progress' | 'resolved' | 'closed' }`. RBAC:
     `support_agent`/`super_admin` — `support:resolve`. Given переход в `resolved`/`closed` —
     заголовок `Idempotency-Key` НЕ обязателен (в отличие от денежных операций эпика EP-11, здесь
     нет платёжного эффекта — двойной клик просто не меняет уже терминальный статус, домен сам
     защищён `TicketAlreadyTerminalError`).
2. DTO — Zod-схемы: `CreateSupportTicketDto { orderId?: UUID, channel, category, description }`,
   `AddMessageDto { body: string }`, `ChangeStatusDto { status: enum }`.
3. `support-ticket.mapper.ts` — `SupportTicket` (domain) → `SupportTicketDto`
   (`packages/contracts/src/support.ts`, наполняется здесь: `id`, `orderId`, `tenantId`,
   `channel`, `category`, `status`, `priority`, `firstResponseDueAt`, `firstRespondedAt`,
   `createdAt`, `messages: SupportTicketMessageDto[]`). `isEscrowBlocking` ВСЕГДА `false` в
   ответе R1 (поле присутствует в DTO для будущей совместимости с R3, но в текущей реализации не
   может быть иным — не скрывать поле, документировать константность явно в JSDoc типа).
4. Добавить в `packages/contracts/src/permissions.ts`: `support:create`, `support:read:own`,
   `support:read:any`, `support:respond`, `support:resolve`.
5. Добавить в `packages/contracts/src/errors.ts`: `TICKET_NOT_FOUND` (404),
   `INVALID_TICKET_STATUS_TRANSITION` (409), `TICKET_ALREADY_TERMINAL` (409).
6. Маппинг доменных ошибок (DTJ-278) → HTTP-коды в `DomainExceptionFilter` (уже установленный
   единый фильтр, `SRS-ADM-079`-подобный принцип «не заводить третий фильтр ошибок для этого
   модуля»).

## Критерии приёмки

1. **Given** `customer`, **When** `POST /api/v1/support-tickets` с `category='courier_conduct'`,
   **Then** `201`, тело `SupportTicketDto` с `isEscrowBlocking: false`.
2. **Given** `support_agent`, **When** `GET /api/v1/support-tickets?status=open`, **Then**
   возвращены тикеты ВСЕХ клиентов своего тенанта (не только созданные этим агентом).
3. **Given** `customer`, не являющийся владельцем тикета, **When** `GET /:id`, **Then** `403`.
4. **Given** тикет уже `closed`, **When** `support_agent` вызывает `POST /:id/status` с
   `{ status: 'in_progress' }`, **Then** `409 TICKET_ALREADY_TERMINAL` — негативный сценарий.

## Тест-план

- Интеграционные тесты (Vitest + Testcontainers + supertest): по каждому из 5 эндпоинтов —
  happy path + минимум один RBAC-негативный сценарий.
- Пагинация `GET /` — курсор корректно продвигается, фильтры комбинируются (`status` +

## Риски и подводные камни

- **Эндпоинты `GET /`, `POST /:id/messages`, `POST /:id/status` — не буквальные требования
  SRS, а обоснованная достройка.** Единственный явно специфицированный эндпоинт —
  `POST /api/v1/support-tickets` (SRS-ADM-074). Остальные необходимы для функциональной
  полноты «облегчённой очереди обращений» (иначе тикеты некому читать/резолвить), но их точная
  форма (пути, RBAC-детали) — решение этого тикета, не буквальная цитата спеки. Если ревью
  архитектора потребует иной формы — низкая цена изменения (только `presentation`-слой, домен
  и application не затронуты).
- **Новые permission-строки не входят в исходную RBAC-матрицу `12-api-conventions...md` §4.1.**
  Таблица не содержит раздела `support:*` вовсе (только `disputes:*`/`returns:*`) — та же
  ситуация, что и в DTJ-275 для `returns:mark-in-transit`. Согласовать с архитектором при ревью,
  если потребуется формальное расширение таблицы §4.1.
