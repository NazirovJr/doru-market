## Задача

Возврат — это деньги и физический товар одновременно: ошибка в state machine означает либо
двойной возврат денег клиенту, либо контролируемое вещество, отправленное обратно на полку
вместо уничтожения. D-09 (`03-ARCHITECT-DECISIONS.md`) вводит `order_returns`/`return_status`
именно потому, что в исходном ТЗ возвраты не были описаны вовсе — домен должен сам защищать
эти инварианты, а не полагаться на то, что вызывающий код «не ошибётся». Эта сущность — ядро
всего эпика: без неё ни use case'ы (DTJ-273), ни финансовая политика (DTJ-272), ни API (DTJ-275)
не имеют на что опираться.

## Технический контекст

Слой `domain` модуля `returns` (`apps/api/src/modules/returns/domain/`,
`02-CLEAN-ARCHITECTURE-AND-CODE.md` §1/§2). Ноль импортов фреймворка/Drizzle/`Date.now()` —
время приходит через порт `Clock` (уже объявлен в `packages/contracts`/EP-01, аргумент
конструктора, не глобальный вызов). Полная спецификация инвариантов — `10-domain-model.md`
строки 411–436 (SRS-DOM-052..056), use-case-уровень веток «до/после вручения» и переадресации
на спор — `21-module-orders-payments-escrow.md` §7.1 (SRS-RET-001..003).

## Что сделать

1. `ReturnReason` VO (`value-objects/return-reason.vo.ts`) — обёртка над enum `return_reason`
   (`defect`, `wrong_item`, `damaged_packaging`, `expired_or_near_expiry`, `undelivered`,
   `refused_at_door`, `undeliverable`, `customer_dispute_post_delivery`), статический `parse()`
   возвращает `Result<ReturnReason, ValidationError>`, не бросает исключение на пользовательский
   ввод (`10-domain-model.md` §«Value Objects»).
2. `ReturnDisposition` VO — обёртка над `return_disposition` (`restock`/`destroy`/
   `pending_inspection`).
3. `OrderReturn` entity (`order-return.entity.ts`), приватный конструктор + фабрики:
   - `OrderReturn.request(orderId, reason: ReturnReason, initiatorId, initiatorRole, courierId?)`
     — создаёт запись в `return_requested`; НЕ вызывается для `reason='undelivered'`
     (SRS-RET-003 — это ведёт в `SupportFacade`/будущий `OrderDispute`, не в `OrderReturn`; guard
     в самой фабрике: `reason === 'undelivered'` бросает `UnsupportedReturnReasonError` с текстом,
     объясняющим переадресацию — вызывающий use case DTJ-273 обязан проверить причину РАНЬШЕ
     вызова фабрики, эта проверка — вторая линия защиты).
   - Ветка ДО вручения (SRS-RET-001): `reason ∈ {'refused_at_door','undeliverable'}` и заказ в
     `picked_up` → сразу `return_in_transit` (курьер уже везёт товар, `courierId` обязателен и
     совпадает с курьером доставки — параметр передаёт use case, домен не резолвит доставку).
   - Ветка ПОСЛЕ вручения (SRS-RET-002): заказ в `delivered`, любая другая причина, кроме
     `undelivered` → `return_requested`, `courierId` не заполняется на этом шаге (новое
     назначение — забота use case через `DeliveryFacade`, домен об этом не знает).
   - `orderReturn.markInTransit(courierId)` — `return_requested → return_in_transit`.
   - `orderReturn.confirmReceived(pharmacistId, checklist: { packagingIntact, notes })` —
     `return_in_transit → return_confirmed` при выполнении restock-условий (см. п.5), иначе
     переход всё равно происходит, но `disposition` принудительно `destroy`
     (`RestockConditionsNotMetError` НЕ блокирует подтверждение приёмки товара, только
     запрещает restock — подтверждение возврата и решение «restock vs destroy» — разные вещи).
   - `orderReturn.reject(reason)` — `return_in_transit → return_rejected` (не терминален,
     SRS-DOM-056).
   - `orderReturn.adminOverride(actorId, reason)` — `return_rejected → return_confirmed`,
     `reason` обязателен (`admin_override_reason` в БД `NOT NULL` при этом переходе).
   - `orderReturn.retryTransit(courierId)` — `return_rejected → return_in_transit`.
   - Любой недопустимый переход — `InvalidReturnStatusTransitionError` (явная таблица
     разрешённых переходов, `02` §2.4 — НЕ `if (status === ...)` россыпью; реализовать таблицу в
     отдельном `order-return.state-machine.ts`, entity делегирует проверку ей).
4. **SRS-DOM-052**: не более одного нетерминального `OrderReturn` на `order_id` — доменный guard
   дублирует БД-индекс `ux_order_returns_one_active`; `OrderReturn.request()` принимает список
   уже существующих нетерминальных возвратов заказа (передаётся use case'ом после чтения через
   репозиторий) и бросает `DuplicateActiveReturnError`, если такой уже есть.
5. **SRS-DOM-053**: `confirmReceived()` вычисляет допустимость `restock` по ТРЁМ условиям
   одновременно: `expiryDate > today + tenantSettings.returnRestockMinRemainingDays` (значение
   передаётся параметром — домен не читает `tenant_settings` сам), `checklist.packagingIntact
   === true`, `reason !== 'cold_chain_breach_suspected'` (в текущем enum `return_reason` такого
   значения нет — трактовать как «условие всегда выполнено» и оставить TODO-комментарий со
   ссылкой на REQ-RET-3, если поле появится в будущем расширении enum). Любое нарушение —
   `disposition = 'destroy'` и исключение `RestockConditionsNotMetError` пробрасывается наружу
   ТОЛЬКО если use case явно запросил `restock` (см. DTJ-273) — сама `confirmReceived()` не
   бросает исключение за клиента, а возвращает `disposition` в результате (см. п.3).
6. **SRS-DOM-054**: товар с `controlCategory !== 'none'` (параметр, значение из каталога —
   домен `returns` не импортирует `catalog`, значение передаётся use case'ом через порт) —
   `disposition` принудительно `'destroy'`, попытка вызвать `restock()` для такой позиции —
   `ControlledSubstanceMustBeDestroyedError`.
7. **SRS-DOM-055**: `courierReturnFeeDirams` — обязательный `Money`-параметр конструктора
   `markInTransit()`, `>= 0` (VO `Money` уже существует в `packages/contracts`/EP-01), не
   зависит от причины/исхода.
8. Экспортировать `OrderReturn`, VO, все ошибки и стейт-машину из
   `apps/api/src/modules/returns/domain/index.ts` внутреннего барреля (НЕ путать с публичным
   фасадом `modules/returns/index.ts` из DTJ-270 — тот не реэкспортирует `domain` наружу модуля,
   `02` §1.2).

## Критерии приёмки

1. **Given** заказ уже имеет `OrderReturn` в статусе `return_in_transit`, **When** вызывается
   `OrderReturn.request()` повторно для того же `orderId`, **Then** бросается
   `DuplicateActiveReturnError` (аналог TC-DOM-028).
2. **Given** возврат с `packagingIntact=false`, **When** вызывается `confirmReceived()` с
   запросом `restock`, **Then** `disposition` становится `'destroy'`, метод бросает
   `RestockConditionsNotMetError` (аналог TC-DOM-030).
3. **Given** товар с `controlCategory='psychotropic'`, упаковка цела, срок годности в порядке,
   **When** вызывается `confirmReceived()` с запросом `restock`, **Then** бросается
   `ControlledSubstanceMustBeDestroyedError`, `disposition` принудительно `'destroy'`
   (аналог TC-DOM-029) — НЕГАТИВНЫЙ сценарий: `restock` невозможен даже при идеальном
   физическом состоянии упаковки.
4. **Given** возврат в терминальном статусе `return_confirmed`, **When** вызывается любой
   мутирующий метод (`markInTransit`/`reject`/`retryTransit`), **Then** бросается
   `InvalidReturnStatusTransitionError`.
5. **Given** `reason='undelivered'`, **When** вызывается `OrderReturn.request()`, **Then**
   бросается `UnsupportedReturnReasonError` (переадресация на спор — не создаётся строка
   `order_returns`).

## Тест-план

Unit-тесты (без БД, чистый домен), Vitest:
- `OrderReturn.request()` — обе ветки (до/после вручения), дубликат активного возврата,
  `reason='undelivered'` отклоняется.
- `markInTransit()` — успешный переход, `courierReturnFeeDirams < 0` отклоняется VO `Money`.
- `confirmReceived()` — все 4 комбинации restock-условий (все выполнены / упаковка вскрыта /
  просрочка / контролируемое вещество) × ожидаемый `disposition`.
- `reject()` → `retryTransit()` → `markInTransit()` — не-терминальность `return_rejected`
  (SRS-DOM-056), полный цикл повторной попытки.
- `adminOverride()` без `reason` — отклонено на уровне VO/сигнатуры (обязательный параметр,
  не опциональный — проверка типов, а не рантайм-теста).
- Таблица state machine: параметризованный тест по ВСЕМ комбинациям (статус × метод), не
  входящим в разрешённые переходы — каждая бросает `InvalidReturnStatusTransitionError`.
Порог покрытия `domain/` — 90% (`02` §6.4), для этого файла реалистичен ~100% благодаря чистоте
слоя.

## Риски и подводные камни

- **`cold_chain_breach_suspected` отсутствует в enum `return_reason`.** `11-database-schema.md`
  определяет `return_reason` без этого значения, хотя REQ-RET-3 (упомянуто в SRS-DOM-053)
  ссылается на него как на условие блокировки restock. Требование по факту НЕ покрыто текущим
  enum — трактовка «условие всегда истинно» (п.5 выше) явная, задокументированная в коде;
  расширение enum — отдельный тикет вне этого диапазона (`ALTER TYPE ... ADD VALUE`, миграция
  вне транзакции, `SRS-DB-009`), не блокирует текущую реализацию.
- **Guard на `reason='undelivered'` — двойная защита.** И домен (эта сущность), и use case
  (DTJ-273) должны проверять эту причину РАНЬШЕ создания `OrderReturn`. Если use case случайно
  пропустит проверку — домен всё равно не даст создать некорректную запись, но с менее
  дружелюбным сообщением об ошибке (это осознанный компромисс защиты инварианта, не дефект).
