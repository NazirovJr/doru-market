## Задача

Всё, что построено в DTJ-271..274, недоступно ни клиенту, ни курьеру, ни фармацевту без REST
API. Этот тикет — единственная точка входа в модуль `returns` снаружи `apps/api`, поэтому здесь
же закрывается RBAC (кто вызывает какой эндпоинт) и идемпотентность создания возврата (двойной
клик/повтор сети не должен породить два возвратных рейса).

## Технический контекст

`presentation/` модуля `returns` — контроллеры, DTO (Zod-схемы), мапперы domain↔DTO (`02` §1,
слой знает только про `application`, не про `domain` напрямую). Полный список эндпоинтов и ролей
— `21-module-orders-payments-escrow.md` §7.5 (SRS-RET-011), таблица RBAC — уже установлена в
`12-api-conventions-auth-tenancy.md` §4.1 (строки `returns:request`/`returns:confirm`/
`returns:admin-override`). Идемпотентность создания — `SRS-API-009` (таблица эндпоинтов,
требующих `Idempotency-Key`, явно включает `POST /api/v1/order-returns`).

## Что сделать

1. `order-returns.controller.ts`, базовый путь `/api/v1/order-returns`:
   - `POST /` — `RequestReturnUseCase`. RBAC: `customer` (свой заказ), `courier` (по назначению
     на доставку), `super_admin`. Заголовок `Idempotency-Key` ОБЯЗАТЕЛЕН (`SRS-API-009`) —
     отсутствие → `400 IDEMPOTENCY_KEY_REQUIRED` (код уже в `12-api-conventions...md` таблице
     ошибок, переиспользуется, не создаётся заново).
   - `POST /:id/mark-in-transit` — `MarkReturnInTransitUseCase`. RBAC: диспетчер
     (`pharmacy_admin` своей сети/`super_admin`) — permission `returns:mark-in-transit` (новая
     строка, добавляется в `packages/contracts/src/permissions.ts` — таблица §4.1
     `12-api-conventions...md` явно не перечисляет этот конкретный эндпоинт отдельной строкой,
     см. «Риски»).
   - `POST /:id/confirm` — `ConfirmReturnReceivedUseCase`. RBAC: `pharmacist` своей аптеки —
     `returns:confirm`.
   - `POST /:id/reject` — `RejectReturnUseCase`. RBAC: `pharmacist` своей аптеки — переиспользует
     `returns:confirm` (симметричное действие тому же принципалу, отдельной строки в матрице
     нет — трактовка по аналогии, не выдумывание новой роли).
   - `POST /:id/admin-override` — `AdminOverrideReturnUseCase`. RBAC: `pharmacy_admin` своей
     сети/`super_admin` — `returns:admin-override`. Заголовок `Idempotency-Key` ОБЯЗАТЕЛЕН
     (двойной клик администратора не должен переопределить дважды — тот же паттерн, что
     `disputes:resolve-*`, SRS-DISP-008, применённый здесь по аналогии для симметричного по
     значимости административного действия).
   - `POST /:id/retry-transit` — `RetryReturnTransitUseCase`. RBAC: диспетчер (как
     `mark-in-transit`).
   - `GET /:id` — чтение. RBAC: владелец заказа/`pharmacist` своей аптеки/`super_admin`
     (`ReturnsPolicy.canRead(actor, orderReturn)`).
2. `returns-policy.guard.ts` — `application`-политика авторизации (`ReturnsPolicy`, `02` §3.4):
   грубая проверка роли — на уровне `@Roles()` декоратора (guard), точная проверка владения
   («своя аптека»/«свой заказ»/«назначен на доставку») — здесь, в политике, не в guard'е.
3. DTO — Zod-схемы под каждое тело запроса, 1:1 с полями метода домена (`reason`, `checklist:
   { packagingIntact, notes }`, `reason` для reject/override). Ошибки валидации маппятся в `422`
   стандартным `ZodValidationPipe` (уже установлен фундаментом EP-01).
4. `order-return.mapper.ts` — `OrderReturn` (domain) → `OrderReturnDto` (`packages/contracts/src/returns.ts`,
   наполняется здесь конкретными полями: `id`, `orderId`, `status`, `reason`, `disposition`,
   `courierReturnFeeDiram`, `requestedAt`, `resolvedAt`). Сущность БД никогда не возвращается
   наружу контроллера напрямую (`02` §1.1 запрещённая таблица).
5. Добавить в `packages/contracts/src/errors.ts` (общий `ErrorCode` enum, владелец EP-01,
   низкий риск конфликта при рабейзе — правило `tickets/00-EPICS.md` п.3): `RETURN_WINDOW_EXPIRED`
   (422, SRS-RET-012), `RETURN_NOT_FOUND` (404), `DUPLICATE_ACTIVE_RETURN` (409),
   `INVALID_RETURN_STATUS_TRANSITION` (409).
6. Добавить в `packages/contracts/src/permissions.ts`: `returns:mark-in-transit`.
7. Обработчик доменных ошибок → HTTP: `DuplicateActiveReturnError` → `409
   DUPLICATE_ACTIVE_RETURN`, `ReturnWindowExpiredError` → `422 RETURN_WINDOW_EXPIRED`,
   `InvalidReturnStatusTransitionError` → `409 INVALID_RETURN_STATUS_TRANSITION`,
   `RestockConditionsNotMetError`/`ControlledSubstanceMustBeDestroyedError` НЕ являются
   HTTP-ошибками в контексте `confirm` (см. DTJ-271 — метод не бросает эти исключения наружу
   API, только меняет `disposition` в ответе).

## Критерии приёмки

1. **Given** валидный запрос от `customer` на свой `delivered`-заказ в пределах окна, **When**
   `POST /api/v1/order-returns` с `Idempotency-Key`, **Then** `201`, тело содержит
   `OrderReturnDto` со `status='return_requested'`.
2. **Given** `courier`, не назначенный на доставку этого заказа, **When** вызывает `POST
   /api/v1/order-returns` для чужого заказа, **Then** `403` (RBAC-политика владения).
3. **Given** запрос без заголовка `Idempotency-Key`, **When** `POST /api/v1/order-returns`,
   **Then** `400 IDEMPOTENCY_KEY_REQUIRED`, `order_returns` не создан — негативный сценарий.
4. **Given** `pharmacist` чужой аптеки, **When** `POST /:id/confirm`, **Then** `403`.

## Тест-план

Интеграционные тесты (Vitest + Testcontainers + supertest поверх Nest test app):
- По каждому из 7 эндпоинтов: happy path + минимум один RBAC-негативный сценарий (роль без
  прав/чужой ресурс).
- Идемпотентность `POST /` — повторный запрос с тем же `Idempotency-Key` возвращает сохранённый
  ответ, не создаёт вторую запись (аналог TC-API-003, применённый к этому эндпоинту).
- Маппинг доменных ошибок → HTTP-коды — по каждому классу ошибки из DTJ-271/273 отдельный кейс.
- E2E (Playwright) — НЕ входит в этот тикет; полный флоу возврата — часть CUJ, покрывается общей
  E2E-инфраструктурой EP-19, если Tech Lead решит прикрепить отдельный сценарий (вне бюджета
  этого документа).
Покрытие `presentation/` — порог 70% (`02` §6.4, не `domain`/`application`).

## Риски и подводные камни

- **`returns:mark-in-transit`/`returns:reject` — новые permission-строки, не в исходной
  RBAC-матрице.** `12-api-conventions-auth-tenancy.md` §4.1 перечисляет только
  `returns:request`/`returns:confirm`/`returns:admin-override` — эндпоинты `mark-in-transit` и
  `reject` отсутствуют как отдельные строки матрицы. Решение (переиспользование `returns:confirm`
  для `reject`, новая строка `returns:mark-in-transit` для диспетчерских действий) — трактовка
  по аналогии с уже описанным принципом «диспетчерские действия закреплены за `pharmacy_admin`
  своей сети/`super_admin`» (`12-api-conventions...md` §4.1 преамбула). Явное расхождение со
  спекой — согласовать с архитектором как ADR, если ревью потребует иного решения.
- **`Idempotency-Key` на `admin-override`** — SRS-RET-011 явно требует его (со ссылкой в
  таблице модуля 21 строка 1024), это НЕ моя трактовка, а прямое требование источника.
