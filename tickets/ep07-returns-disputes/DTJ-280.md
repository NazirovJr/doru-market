## Задача

SLA первого ответа без принуждения — это просто число в БД, на которое никто не смотрит.
`SupportSlaMonitorJob` — механизм, который реально поднимает приоритет просроченных тикетов и
будит `super_admin`/`support_agent`, аналогично уже существующему паттерну
`DeliverySlaMonitorJob` (модуль `delivery`, EP-13) — тот же принцип детекции просрочки,
переиспользованный, а не изобретённый заново.

## Технический контекст

`apps/worker/src/jobs/support-sla-monitor/` — BullMQ-джоба (периодический шедулер,
`02-CLEAN-ARCHITECTURE-AND-CODE.md` — воркер живёт в `apps/worker`, вызывает `application`
use case через тот же публичный фасад модуля `support`, не напрямую `domain`). Источник —
`27-module-admin-moderation-onboarding.md` §9 (SRS-ADM-076), матрица уведомлений §6.1
(SRS-ADM-052, строка `SlaBreachedEvent`).

## Что сделать

1. `EscalateTicketPriorityUseCase.execute({ ticketId })` (`application/use-cases/`) —
   `ticket.escalatePriority()` (DTJ-278), сохраняет через репозиторий, публикует
   `SlaBreachedEvent { entityType: 'support_ticket', entityId: ticketId, tenantId }` — тип
   события УЖЕ существует в системе (переиспользуется, не создаётся новый, SRS-ADM-076 явно
   говорит «уже существующий тип»; координировать точную сигнатуру с тем, как его определяет
   владелец `notifications`/EP-16, не изобретать параллельную структуру).
2. `support-sla-monitor.job.ts` — обработчик BullMQ job: находит тикеты, где
   `first_response_due_at < now() AND first_responded_at IS NULL AND status IN
   ('open','in_progress')`, вызывает `SupportFacade.escalateTicketPriority(ticketId)` для
   каждого (публичный фасад — не прямой вызов use case из воркера в обход `index.ts` модуля,
   `02` §1.2).
3. **Идемпотентность повторного прогона**: джоба, запущенная повторно для уже эскалированного
   (но всё ещё просроченного) тикета, увеличивает `priority` СНОВА только если прошло
   `SUPPORT_SLA_RE_ESCALATION_MINUTES` (ASSUMPTION 30 минут, конфигурируемо через аргумент джобы,
   не захардкожено) с последней эскалации — иначе `priority` растёт неограниченно на каждый тик
   шедулера, что обесценивает сам сигнал приоритета. Реализовать через поле `updated_at`
   тикета либо явный `last_escalated_at` (добавить колонку, если `updated_at` недостаточно
   специфично — координировать с DTJ-278 при необходимости миграции).
4. `support-sla-monitor.scheduler.ts` — регистрация повторяющейся BullMQ job (например, каждые
   5 минут — интервал конфигурируется через ENV, не хардкод).
5. Обработка ошибок — сбой эскалации ОДНОГО тикета не должен останавливать обработку остальных
   в том же прогоне (`Promise.allSettled`, не `Promise.all` — C14, ошибка логируется через pino,
   не проглатывается молча, C12).

## Критерии приёмки

1. **Given** тикет `open`, `first_response_due_at` в прошлом, `first_responded_at IS NULL`,
   **When** джоба выполняется, **Then** `priority` увеличен на 1, `SlaBreachedEvent` опубликован
   ровно один раз за этот прогон.
2. **Given** тикет уже получил первый ответ (`first_responded_at` заполнен) до истечения SLA,
   **When** джоба выполняется, **Then** тикет НЕ попадает в выборку — негативный сценарий,
   подтверждающий, что джоба смотрит именно на `first_responded_at IS NULL`, а не только на
   истекший дедлайн.
3. **Given** джоба выполняется дважды подряд для одного и того же просроченного тикета в
   пределах `SUPPORT_SLA_RE_ESCALATION_MINUTES`, **When** оба прогона завершаются, **Then**
   `priority` увеличен только один раз, не дважды.
4. **Given** обработка одного из N тикетов в батче падает с исключением, **When** джоба
   завершает прогон, **Then** остальные N-1 тикетов всё равно эскалированы (ошибка одного не
   блокирует остальные).

## Риски и подводные камни

- **`SlaBreachedEvent` — точная структура определяется владельцем `notifications` (EP-16).**
  Этот тикет публикует событие по описанной в SRS-ADM-052/076 семантике, но если фактическая
  Zod-схема события (владелец — фундамент EP-01/EP-16 `outbox`-инфраструктуры) на момент
  реализации отличается по именам полей — привести к фактической схеме, не изобретать свою.
- **Отсутствие явного механизма "рабочих часов поддержки".** SRS-ADM-075 упоминает «60 минут в
  рабочих часах поддержки» — но нигде в `docs/spec/` не специфицирован календарь рабочих часов
  как отдельная сущность. В этом тикете SLA считается календарно (24/7), без учёта рабочих
  часов — явное упрощение, зафиксированное как отличие от буквы требования; полноценный
  рабочий календарь — вне бюджета этого тикета, потенциальный будущий тикет.
