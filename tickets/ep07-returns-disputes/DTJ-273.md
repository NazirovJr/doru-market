## Задача

Это оркестрационный слой поверх сущности `OrderReturn` (DTJ-271): шесть сценариев, которые
реально вызывает пользователь (клиент, курьер, фармацевт, `pharmacy_admin`/`super_admin`) через
API (DTJ-275). Каждый use case — один класс, один `execute()` (`02` §3.1), не знает про HTTP.
Ключевая бизнес-развилка здесь — переадресация `reason='undelivered'` на спор вместо создания
`OrderReturn` (SRS-RET-003): именно тут проверка происходит РАНЬШЕ вызова домена.

## Технический контекст

`application/use-cases/` модуля `returns`. Обращение к заказу — через порт `ReturnsOrdersPort`
(DTJ-270), к остаткам — через `ReturnsInventoryPort`, к курьерской диспетчеризации — через
`ReturnsDeliveryPort`, к обращениям — через публичный фасад `SupportFacade` (модуль `support`,
DTJ-279) для ветки `undelivered`. Возврат денег НЕ входит в этот тикет — `confirmReceived`
использует `restock`, но рефанд запускается ОТДЕЛЬНЫМ use case'ом на событие
`ReturnConfirmedEvent`/`ReturnRejectedEvent` (DTJ-274), т.к. финансовая логика (D-10,
раздельный биллинг) достаточно объёмна для отдельного тикета и отдельного ревью. Источник —
`21-module-orders-payments-escrow.md` §7.1/§7.4 (SRS-RET-001..003, SRS-RET-010), §7.5 (перечень
методов домена, которые оборачивают эти use case'ы) и §«Пограничные случаи» (SRS-RET-012 —
возврат вне окна).

## Что сделать

1. `ReturnsRepositoryPort` (`application/ports/returns-repository.port.ts`) — `findById`,
   `findActiveByOrderId`, `save` (append новой версии сущности, не мутация строки — паттерн уже
   принят для `OrderReturn`, БД хранит текущее состояние в одной строке `order_returns`,
   история переходов — в `audit_log`, SRS-DOM-056 комментарий к таблице).
2. `RequestReturnUseCase.execute({ orderId, reason, initiatorId, initiatorRole })`:
   - Читает заказ через `ReturnsOrdersPort.getOrderForReturn(orderId)` — статус, `deliveredAt`,
     `pickedUpAt`, `pharmacyId`.
   - Given `reason === 'undelivered'` → делегирует `SupportFacade.createAutoOrManualTicket(...)`
     с `category='order_not_received'` (SRS-RET-003) и **возвращает результат создания тикета**,
     НЕ вызывает `OrderReturn.request()` вовсе.
   - Given заказ в `delivered` и `reason === 'customer_dispute_post_delivery'` — проверяет окно
     `now() <= deliveredAt + tenantSettings.disputeWindowHours` (значение читается через порт
     `TenantSettingsPort`, уже существующий из EP-01/EP-02 фундамента); нарушение окна —
     `ReturnWindowExpiredError` → маппится в `422 RETURN_WINDOW_EXPIRED` presentation-слоем
     (SRS-RET-012). Единственное исключение из этой проверки — `super_admin`, вызывающий
     `AdminOverrideReturnUseCase` напрямую (см. п.6, обходит `RequestReturnUseCase` целиком).
   - Given заказ в `picked_up` и `reason ∈ {'refused_at_door','undeliverable'}` — курьерская
     ветка (SRS-RET-001): читает уже назначенного на доставку курьера через
     `ReturnsDeliveryPort.getAssignedCourier(orderId)`, вызывает `OrderReturn.request(...)` с
     этим `courierId`, сразу переводит в `return_in_transit` (см. DTJ-271 п.3 — домен делает это
     сам внутри фабрики для этой ветки).
   - Given заказ в `delivered` и остальные причины — пост-доставочная ветка (SRS-RET-002):
     `OrderReturn.request()` без `courierId`, статус `return_requested`; асинхронно (после
     commit транзакции, не блокируя ответ) вызывает
     `ReturnsDeliveryPort.assignReturnCourier(returnId)`.
   - Публикует `ReturnRequestedEvent` через `outbox` в той же транзакции, что `INSERT
     order_returns` (паттерн `SRS-DOM-151/152`, уже установленный инфраструктурой EP-01).
3. `MarkReturnInTransitUseCase.execute({ returnId, courierId })` — `orderReturn.markInTransit(courierId,
   courierReturnFeeDirams)`, где `courierReturnFeeDirams` вычисляется через
   `ReturnsDeliveryPort.calculateReturnFee(returnId)` (SRS-RET-005 — начисляется всегда, домен
   требует значение обязательным параметром). Публикует `ReturnInTransitEvent`.
4. `ConfirmReturnReceivedUseCase.execute({ returnId, pharmacistId, checklist })` —
   `orderReturn.confirmReceived(...)` (см. DTJ-271), затем, Given `disposition === 'restock'`,
   вызывает `ReturnsInventoryPort.restock(orderId, items, disposition)` — **идемпотентно по
   `order_id`** (SRS-RET-010, повторный вызов restock для уже обработанного возврата — no-op, не
   двойное начисление остатка). Публикует `ReturnConfirmedEvent { returnId, orderId, reason,
   disposition }` — это событие потребляет DTJ-274 для рефанда, а `InventoryFacade` — для
   собственно restock (SRS-RET-010 явно разделяет: этот модуль НЕ вызывает `restock` напрямую из
   контроллера, только через порт здесь, а `InventoryFacade` подписан на само событие для СВОИХ
   внутренних целей аналитики/аудита — небольшая избыточность канала специфицирована исходником,
   не изобретена этим тикетом).
5. `RejectReturnUseCase.execute({ returnId, reason })` — `orderReturn.reject(reason)`. Публикует
   `ReturnRejectedEvent`.
6. `AdminOverrideReturnUseCase.execute({ returnId, actorId, reason })` — только роли
   `pharmacy_admin` (своя сеть)/`super_admin` (RBAC-проверка — presentation-слой, DTJ-275; здесь
   — `application`-политика `ReturnsPolicy.canOverride(actor, orderReturn)` по `02` §3.4).
   `orderReturn.adminOverride(actorId, reason)` — публикует `ReturnConfirmedEvent` (override
   всегда ведёт к `return_confirmed`, восстанавливает тот же событийный путь, что обычное
   подтверждение — рефанд запускается одинаково независимо от того, обычный это confirm или
   override).
7. `RetryReturnTransitUseCase.execute({ returnId, courierId })` — `orderReturn.retryTransit(courierId)`,
   публикует `ReturnInTransitEvent` повторно (та же логика, что и обычный `markInTransit`, но из
   статуса `return_rejected`).
8. Границы транзакций — `unitOfWork.run(...)` в каждом use case (`02` §3.3), не в репозитории.

## Критерии приёмки

1. **Given** заказ `picked_up`, клиент отказался у двери, **When** вызывается
   `RequestReturnUseCase` с `reason='refused_at_door'`, **Then** создан `OrderReturn` СРАЗУ в
   `return_in_transit`, без отдельного шага диспетчеризации (аналог TC-RET-001).
2. **Given** заказ `delivered`, окно спора истекло, **When** вызывается `RequestReturnUseCase` с
   `reason='customer_dispute_post_delivery'`, **Then** результат — ошибка, маппящаяся в `422
   RETURN_WINDOW_EXPIRED`, `order_returns` НЕ создан (аналог TC-RET-006).
3. **Given** `reason='undelivered'`, **When** вызывается `RequestReturnUseCase`, **Then**
   `order_returns` НЕ создан, вместо этого создан `support_tickets(category='order_not_received')`
   через `SupportFacade` — негативный сценарий для домена `OrderReturn`, позитивный для домена
   `SupportTicket`.
4. **Given** возврат уже `return_confirmed` с `disposition='restock'`, **When**
   `ConfirmReturnReceivedUseCase` вызывается повторно тем же `orderId` (дублирующая доставка
   события/повторный клик), **Then** `InventoryFacade.restock` вызван РОВНО один раз
   (идемпотентность по `order_id`), второй вызов — no-op, ошибка не выбрасывается.

## Тест-план

Интеграционные тесты (Vitest + Testcontainers Postgres + in-memory outbox), по каждому use case:
- `RequestReturnUseCase`: обе ветки (курьер/клиент), переадресация `undelivered`, окно
  `dispute_window_hours` истекло/не истекло, дубликат активного возврата (`DuplicateActiveReturnError`
  пробрасывается наружу как `409`).
- `MarkReturnInTransitUseCase`/`RetryReturnTransitUseCase`: `courierReturnFeeDirams` всегда `> 0`
  вне зависимости от передаваемых мок-данных `calculateReturnFee`.
- `ConfirmReturnReceivedUseCase`: restock вызывается один раз при повторном вызове (идемпотентность),
  `disposition='destroy'` НЕ вызывает `restock` вовсе.
- `RejectReturnUseCase` → `AdminOverrideReturnUseCase`: полный цикл «отклонили → администратор
  переопределил → `return_confirmed`», проверка `admin_override_reason` обязателен.
- `AdminOverrideReturnUseCase` без роли `pharmacy_admin своей сети`/`super_admin` — доступ
  запрещён на уровне `ReturnsPolicy` (unit-тест политики отдельно от use case).
Покрытие `application/` — 90%.

## Риски и подводные камни

- **`assignReturnCourier` асинхронный после commit — окно неконсистентности.** Между
  `return_requested` и фактическим назначением курьера есть небольшой временной зазор
  (SRS-RET-002 требует НОВОГО назначения, не блокирующего ответ API). Если `DeliveryFacade`
  временно недоступен — возврат остаётся в `return_requested` без курьера; нужен ретрай/алерт
  (детали — вне периметра этого документа, задача Delivery-модуля EP-13, здесь только вызов
  порта, best-effort).
- **Двойная публикация `ReturnConfirmedEvent` при override.** И обычный `confirmReceived`, и
  `adminOverride` публикуют одно и то же событие с одинаковой доменной семантикой — подписчик
  (DTJ-274) обязан быть идемпотентным по `order_id`/`return_id`, не по типу события-источника.
- **`TenantSettingsPort` — предположение о существовании.** Тикет предполагает, что порт чтения
  `tenant_settings.dispute_window_hours`/`return_restock_min_remaining_days` уже существует из
  фундамента EP-01/EP-02. Если на момент реализации такого порта ещё нет — минимальная заглушка
  (прямое чтение через уже доступный `TenancyFacade`) описывается в PR, не блокирует тикет.
