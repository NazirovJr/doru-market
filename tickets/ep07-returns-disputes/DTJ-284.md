## Задача

Клиент должен иметь способ пожаловаться, не зная о существовании Telegram-бота или телефона
поддержки — кнопка «Написать в поддержку» на экране заказа и список своих обращений. Это
последний недостающий кусок эпика: без него `support_tickets` из R1 доступен только через
Telegram/`system_auto`, а веб-канал (`in_app`, уже в enum `support_ticket_channel`) остаётся
неиспользуемым.

## Технический контекст

`apps/web/src/features/support/**` — новая feature-slice, не входит в перечень владения файлами
`tickets/00-EPICS.md` явным пунктом (таблица называет только `apps/admin/src/features/support/**`
для EP-14) — добавляется этим тикетом как естественное следствие сквозного покрытия
support-tickets end-to-end; не пересекается ни с одной существующей `apps/web`-feature.
Источник кнопки — `30-ux-screens-and-flows.md` строка 330: `/orders/:id` → «чат/тикет
поддержки (`support-tickets`)» (без явной release-метки на САМУ ссылку, но раздел в целом —
`[R1]` для `/order-returns/new` рядом; трактовка — обе ссылки одного ряда таблицы относятся к
R1-доступному экрану заказа).

## Что сделать

1. `use-create-ticket.ts` — TanStack Query мутация `POST /api/v1/support-tickets`,
   `channel='in_app'`, `orderId` — опционально (передаётся, если форма открыта с экрана
   конкретного заказа, иначе `undefined` — общий канал обращения без привязки к заказу тоже
   валиден по схеме, `support_tickets.order_id` nullable).
2. `CreateTicketForm.tsx` — форма: категория (`Select`, список — все 6 значений
   `support_ticket_category`, локализованные подписи), текст обращения (`Textarea`, обязателен).
   Компонент ≤ 150 строк, состояние формы — `useState`, отправка — через `api/`.
3. `ContactSupportButton.tsx` — кнопка на `/orders/:id`, открывает `CreateTicketForm` в модальном
   окне/на отдельном экране (решение — по существующему паттерну навигации `apps/web` на момент
   реализации, не изобретать новый механизм модалок, если он уже есть в `packages/ui`).
4. `use-my-tickets.ts` — TanStack Query список СВОИХ тикетов (`GET /api/v1/support-tickets`,
   сервер уже скоупит по `customer` из RBAC, клиент не передаёт `customerId` явно).
5. `MyTicketsList.tsx` — экран `/support`/`/profile/support` (точное расположение в навигации —
   на усмотрение реализации, ориентир — `/profile` из `32-design-reference.md` «Пробелы дизайна»
   строка 321, личный кабинет, где естественно разместить историю обращений): список карточек
   со статусом (локализованная подпись `open`/`in_progress`/`resolved`/`closed`), без деталей
   переписки в R1 (просмотр полной ленты сообщений — не входит в этот тикет, см. «Риски»).
6. Локализация — весь текст через `useT()`, словари `customer-support.{tj,ru,en}.json`, включая
   локализованные названия всех 6 категорий (`order_not_received` → «Заказ не получен» и т.д.).

## Критерии приёмки

1. **Given** клиент на `/orders/:id`, **When** нажимает «Написать в поддержку» и отправляет
   форму, **Then** создан тикет с `orderId`, равным текущему заказу, `channel='in_app'`.
2. **Given** клиент на общем экране поддержки (не привязанном к заказу), **When** отправляет
   форму, **Then** тикет создан с `orderId=null`.
3. **Given** у клиента есть 2 обращения в разных статусах, **When** открывается список своих
   обращений, **Then** отображаются оба, каждое с корректной локализованной подписью статуса.
4. **Given** форма отправлена без заполненного текста обращения, **When** пользователь нажимает
   «Отправить», **Then** отправка блокируется клиентской валидацией — негативный сценарий,
   быстрая обратная связь до похода на сервер.

## Риски и подводные камни

- **Полная лента переписки для клиента — сознательно исключена из R1-объёма этого тикета.**
  `MyTicketsList` показывает только статус, не открывает `SupportTicketMessage[]` для чтения
  ответов агента внутри `apps/web` (эта возможность технически уже есть на API-уровне,
  DTJ-282 `GET /:id` отдаёт сообщения) — сокращение объёма ради вместимости тикета в один заход
  разработчика; полноценный тред переписки для клиента — логичное следующее расширение вне
  этого диапазона, если продукт сочтёт нужным.
- **Точка размещения `/support` в навигации `apps/web` не зафиксирована ни в одном
  UX-документе явно** (только косвенно через `/profile` в «Пробелах дизайна»). Решение о точном
  URL/месте в меню — на усмотрение разработчика тикета, не блокирует реализацию.
