## Задача

Оба модуля этого эпика (`returns`, `support`) не существуют в кодовой базе. Прежде чем можно
реализовывать домен, use case'ы и API, нужен физический каркас: таблицы БД строго по DDL из
`11-database-schema.md` («Группа F: Возвраты, споры, поддержка»), директории модулей по
Правилу Зависимостей (`02-CLEAN-ARCHITECTURE-AND-CODE.md` §1), порты для обращения к чужим
модулям через фасады (а не напрямую), и файлы контрактов, которые последующие тикеты будут
наполнять типами. Без этого тикета ни один из последующих десяти тикетов эпиков EP-11/EP-14 не
может начаться параллельно — это единая точка синхронизации схемы БД для обоих эпиков сразу,
так как `order_disputes`/`dispute_status_history` (используются только в R3, но их таблицы —
часть той же миграционной группы, см. «Риски») физически заведены в одном SQL-файле с
`order_returns`/`support_tickets`.

## Технический контекст

`11-database-schema.md` группирует возвраты/споры/поддержку в одну DDL-группу «F» (строки
921–1027) и явно называет итоговый файл миграции `0010_returns_disputes.sql` (раздел
«Стратегия миграций»). Таблицы: `order_returns`, `support_tickets`, `order_disputes`,
`dispute_status_history` + `ALTER TABLE payout_schedule ADD CONSTRAINT fk_payout_schedule_dispute`
(FK на `order_disputes`, требует, чтобы `payout_schedule` — таблица модуля `payments`, EP-10 —
уже существовала на момент применения этой миграции). Enum-типы `return_status`, `return_reason`,
`return_disposition`, `dispute_status`, `support_ticket_channel`, `support_ticket_category`,
`support_ticket_status` определены в общем блоке `CREATE TYPE` (`11-database-schema.md`
строки 134–154).

Оба модуля живут по стандартной структуре `02-CLEAN-ARCHITECTURE-AND-CODE.md` §1:
`domain/ application/ infrastructure/ presentation/` + публичный фасад `index.ts`. Правило
владения файлами (`tickets/00-EPICS.md` «Порядок владения файлами») закрепляет за EP-11
`apps/api/src/modules/returns/**` (только через фасады `orders`/`payments`, без прямого импорта
чужого domain/application), за EP-14 — `apps/api/src/modules/{disputes,support}/**`. Модуль
`disputes` в R1 НЕ создаётся этим или последующими тикетами эпика — полный воркфлоу
`OrderDispute` (заморозка payout, резолюция, частичный рефанд) размечен `04-SCOPE-DECISION-PIVOT.md`
как **R3-3**, за фиче-флагом `disputes_workflow_enabled` (`27-module-admin-moderation-onboarding.md`
§9, SRS-ADM-053/077; та же граница подтверждена `30-ux-screens-and-flows.md` строка 51 и
`00-SRS-MASTER.md` RELEASE 3 п.2). См. «Риски» — таблицы `order_disputes`/`dispute_status_history`
создаются здесь ТОЛЬКО как архитектурный фундамент (правило «ретрофит дороже», SRS-ADM-001),
без домена/use case поверх них в этом наборе тикетов.

## Что сделать

1. Создать миграцию `apps/api/migrations/0010_returns_disputes_support.sql`, воспроизводящую 1:1
   DDL из `11-database-schema.md` строк 921–1027: `CREATE TABLE order_returns`, `support_tickets`,
   `order_disputes`, `dispute_status_history`, все `CONSTRAINT`/`COMMENT ON`, а также
   `ALTER TABLE payout_schedule ADD CONSTRAINT fk_payout_schedule_dispute ...`. Точный
   порядковый номер файла (`00NN_...`) свериь с реальным состоянием `apps/api/migrations/` на
   момент реализации — назначение здесь условно.
2. Проверить перед мержем через `git log`/открытые PR, не создал ли уже кто-то из
   параллельных потоков (EP-01 базовая схема, EP-10 payments) типы `return_status`,
   `return_reason`, `return_disposition`, `dispute_status`, `support_ticket_channel`,
   `support_ticket_category`, `support_ticket_status` — они должны быть созданы РОВНО один раз.
   Если ещё не созданы — включить `CREATE TYPE` в эту же миграцию.
3. Добавить Drizzle-схему `apps/api/src/db/schema/returns.ts` (`orderReturns`) и
   `apps/api/src/db/schema/support.ts` (`supportTickets`, `orderDisputes`,
   `disputeStatusHistory`) — типизированные таблицы для infrastructure-репозиториев следующих
   тикетов. Drizzle-схема НЕ импортируется в `domain`/`application` (`02` §1.1).
4. Создать `apps/api/src/modules/returns/returns.module.ts` (NestJS `@Module`) и
   `apps/api/src/modules/returns/index.ts` — публичный фасад модуля, пока экспортирующий только
   типы и DI-токен `RETURNS_FACADE` (реализация подключается тикетом DTJ-273/DTJ-275).
5. Создать `apps/api/src/modules/support/support.module.ts` и `apps/api/src/modules/support/index.ts`
   — тот же паттерн, экспорт токена `SUPPORT_FACADE`.
6. Объявить порты, через которые `returns` обращается к чужим модулям (правило «только через
   фасад», НЕ прямой импорт `domain`/`infrastructure`):
   - `application/ports/orders-facade.port.ts` — `interface ReturnsOrdersPort { getOrderForReturn(orderId): Promise<OrderReturnContext> }` (нужен статус заказа, `pharmacyId`, `paymentMethod`, `deliveredAt`).
   - `application/ports/payments-facade.port.ts` — `interface ReturnsPaymentsPort { refundItems(...); refundDelivery(...); refundFull(...); recordAdjustment(...) }` (сигнатуры уточняются в DTJ-274 по SRS-RET-006..009).
   - `application/ports/inventory-facade.port.ts` — `interface ReturnsInventoryPort { restock(orderId, items, disposition) }`.
   - `application/ports/delivery-facade.port.ts` — `interface ReturnsDeliveryPort { assignReturnCourier(returnId); calculateReturnFee(...) }`.
   Реализации адаптеров, вызывающие реальные публичные фасады `OrdersFacade`/`PaymentsFacade`/
   `InventoryFacade`/`DeliveryFacade`, добавляются инфраструктурным слоем в DTJ-273/274 —
   здесь только интерфейсы, чтобы application-тикеты могли компилироваться независимо.
7. Создать `packages/contracts/src/returns.ts` (пустые заготовки типов `OrderReturnDto`,
   `ReturnReason`, `ReturnStatus` — enum-значения 1:1 с БД) и `packages/contracts/src/support.ts`
   (`SupportTicketDto`, `SupportTicketCategory`, `SupportTicketStatus`) — наполняются по мере
   готовности следующих тикетов.
8. Добавить ОДНУ строку экспорта каждого нового файла в `packages/contracts/src/index.ts`
   (баррель уже существует, владелец — EP-01, правило «Пересекающееся владение» п.3
   `tickets/00-EPICS.md` — низкий риск конфликта, решается rebase).
9. Прогнать `pnpm arch:check` — новые модули не должны нарушать `dependency-cruiser`-правила
   (никаких импортов `modules/returns/domain` из `modules/support` и наоборот, никаких импортов
   `db/schema` в `domain`/`application`).

## Критерии приёмки

1. **Given** применена миграция `0010_returns_disputes_support.sql` к чистой БД, **When**
   выполняется `\d order_returns`/`\d support_tickets`/`\d order_disputes`/`\d dispute_status_history`,
   **Then** структура таблиц, constraint'ы (`chk_order_returns_fee_nonneg`,
   `chk_order_disputes_terminal_requires_reason`) и комментарии совпадают 1:1 с
   `11-database-schema.md`.
2. **Given** модуль `returns` подключён в `AppModule`, **When** запускается `pnpm --filter api build`,
   **Then** сборка проходит без ошибок циклических импортов (`import/no-cycle`).
3. **Given** разработчик пытается импортировать `modules/payments/domain/*` напрямую из
   `modules/returns/application/*`, **When** запускается `pnpm arch:check`, **Then** проверка
   падает с сообщением dependency-cruiser о нарушении межмодульной границы (негативный сценарий —
   ловушка действительно ловит).
4. **Given** миграция уже применена, **When** она применяется повторно (идемпотентность раннера
   миграций), **Then** ошибки не возникает (стандартный механизм `drizzle-kit`/раннера, не
   специфика этого тикета, но должен быть проверен явно).

## Риски и подводные камни

- **Гонка миграций с EP-10.** `ALTER TABLE payout_schedule ADD CONSTRAINT fk_payout_schedule_dispute`
  требует существования `payout_schedule` (модуль `payments`, владелец EP-10). Если миграция
  EP-10 ещё не смержена — эта миграция падает на `ALTER TABLE`. Синхронизировать порядок мержа с
  тимлидом EP-10 (Волна 8 по `00-EPICS.md`: EP-11/EP-12 стартуют после EP-10, так что на практике
  `payout_schedule` уже должен существовать — но порядок конкретных PR внутри волны не гарантирован
  автоматически).
- **`order_disputes`/`dispute_status_history` без домена — сознательное решение.** Это
  расхождение источников: `21-module-orders-payments-escrow.md` §8 (SRS-DISP-001..010) описывает
  ПОЛНЫЙ денежный воркфлоу спора как `[R1]`, тогда как `27-module-admin-moderation-onboarding.md`
  §9 (SRS-ADM-053/077), `00-SRS-MASTER.md` (RELEASE 3 п.2) и `30-ux-screens-and-flows.md`
  (строка 51) явно относят полную резолюцию спора к **R3** за флагом
  `disputes_workflow_enabled`, оставляя в R1 только облегчённую очередь `support_tickets`. Прямое
  указание Tech Lead для этого набора тикетов (см. `tickets/00-EPICS.md` формулировку EP-14 —
  «облегчённые») разрешает конфликт в пользу R3-версии: таблицы `order_disputes`/
  `dispute_status_history` заводятся сейчас (архитектурный фундамент, «ретрофит дороже»), но
  `OrderDispute`-сущность, `OpenDisputeUseCase` и `resolve-*`-эндпоинты — ОТДЕЛЬНЫЙ будущий тикет
  R2/R3, не входящий в этот диапазон. Если ревьюер увидит расхождение с §8 module 21 — это
  ожидаемо, не дефект данного тикета.
- **Дублирование `CREATE TYPE`.** Если параллельный поток (EP-01/EP-10) уже создал часть нужных
  enum-типов раньше этой миграции — `CREATE TYPE` упадёт на дубликате. Проверка п.2 обязательна
  перед мержем, не после.
