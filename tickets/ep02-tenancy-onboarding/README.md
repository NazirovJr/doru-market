# EP-02 + EP-03 — Мультитенантность и онбординг аптечных сетей

> Зона ответственности: **EP-02 Мультитенантность** (резолв тенанта, guard, изоляция, тест на
> утечку) и **EP-03 Онбординг аптечных сетей и аптек** (заявка, документы, верификация лицензии,
> `verification_status`). Диапазон ID: `DTJ-050`..`DTJ-089`, фактически использовано `DTJ-050`..
> `DTJ-076` (27 тикетов) — резерв `DTJ-077`..`DTJ-089` не занят, доступен на случай дробления
> будущих правок.
>
> Источники (по убыванию приоритета): `04-SCOPE-DECISION-PIVOT.md` (R1-16) →
> `03-ARCHITECT-DECISIONS.md` (D-01, D-22) → `02-CLEAN-ARCHITECTURE-AND-CODE.md` →
> `docs/spec/26-module-tenancy-whitelabel.md`, `docs/spec/27-module-admin-moderation-onboarding.md`

## Место в общем графе эпиков

```
EP-01 (Фундамент) ──▶ EP-02 (Tenancy guard, этот файл) ──▶ EP-03 (Онбординг, этот файл) ──▶ EP-05
                  └──▶ EP-04 (Каталог, параллельно EP-02/EP-03)
```

EP-02 — волна 2 (сразу после EP-01, параллельно EP-04). EP-03 — волна 3 (нуждается в `tenant_id`/
ролях из EP-02). Оба эпика — на критическом пути R1 (`EP-01 → EP-02 → EP-03 → EP-04 → EP-05 → ...`).

## Межмодульные точки координации (важно при параллельной разработке)

- **DTJ-057 (EP-02) ↔ DTJ-070 (EP-03)**: `ProvisionTenantUseCase` (тенантность) читает статус
  сети через `ChainEligibilityPort`, адаптер которого вызывает
  `OnboardingFacade.getChainEligibilityForWhitelabel(chainId)` — сигнатура зафиксирована в обоих
  тикетах одинаково; до готовности DTJ-070 использовать временную заглушку в DTJ-057 (описано в его
  разделе «Риски»).
- **DTJ-071 (EP-03) → EP-10** (не в этом файле): принудительная отмена заказов приостановленной
  аптеки объявляет `OrdersCancellationPort` с временной `NullOrdersCancellationAdapter` — реальная
  реализация подключается модулем `orders`/`payments` при достижении его волны (7–8). Проверить
  переключение перед релизом R1.
- **DTJ-062 (EP-02) → EP-16** (не в этом файле): Telegram-роутер вызывает
  `NotificationsFacade.handleTelegramUpdate` через временную заглушку до готовности `notifications`.
- **DTJ-060/075/076 (фронтенд) → EP-19**: формулировка ESLint-правила анти-хардкода бренда и текст
  e2e-сценария `BRAND_NAME` подготовлены, но их фактическое встраивание в `eslint.config.mjs`/
  `tests/e2e/**` — исключительное владение EP-19 (корневые конфиги и тестовая инфраструктура,
  `00-EPICS.md`). Передать явно при готовности EP-19 принять работу.
- **DTJ-056 (EP-02) → EP-19**: `dependency-cruiser`-правило, запрещающее прямой импорт Drizzle-
  клиента вне `infrastructure/repositories/*`, — тоже владение EP-19; тикет доставляет только
  механизм проверки (базовый класс + contract-test), не правку корневого конфига.
- **`packages/contracts/src/index.ts`**: EP-01 владеет барабаном, каждый тикет здесь (DTJ-057,
  DTJ-059, DTJ-064) добавляет РОВНО одну строку экспорта своего файла (`tenancy.ts`,
  `onboarding.ts`) — при параллельном мерже конфликт решается rebase, не перезаписью чужих строк
  (правило `00-EPICS.md` «Пересекающееся владение» п.3).
- **`apps/admin`**: DTJ-075 — первый тикет платформы, добирающийся до `apps/admin` по волнам,
  владеет общим каркасом `app/`/`pages`/роутером; последующие эпики (EP-14/EP-15/EP-17) добавляют
  гостевые правки маршрутов внутри своих `features/**`, не трогая каркас целиком.

## Известные пробелы и расхождения спецификации (зафиксировано в тикетах, требует внимания архитектора)

1. **`otp_purpose='onboarding_contact'`** (DTJ-063): `27-module-admin-moderation-onboarding.md`
   ссылается на добавление этого значения enum в «§10.1», но фактический текст того параграфа его
   не перечисляет — реализовано по духу требования (переиспользование `OtpCode` для верификации
   контакта заявки), формально это расхождение документа с самим собой.
2. **HTTP-код `PharmacySuspendedError`** (DTJ-063): `10-domain-model.md` аннотирует ошибку как
   «→ 403 PHARMACY_SUSPENDED» при родительской категории `BusinessRuleViolationError → 422`, тогда
   как `27-module-admin-moderation-onboarding.md` SRS-ADM-015 явно требует `422`. Тикеты этого
   комплекта следуют `422` (более специфичный модульный документ + согласованность с родительской
   категорией ошибок).
3. **`contact_phone_verified`** (DTJ-064): новое булево поле `pharmacy_chains`, не предусмотренное
   явно ни базовой DDL, ни §10.1 — минимальное дополнение, необходимое `VerifyChainContactPhoneUseCase`.
4. **Permission-строка «запросить реактивацию»** (DTJ-074) и точная трактовка «своя аптека» для
   `pharmacy-accounts:update-address` (DTJ-069) — матрица `12-api-conventions...md` §4.1 не даёт
   исчерпывающей формулировки для этих двух случаев, тикеты трактуют расширительно (доступ на
   уровне сети `pharmacy_admin`), с явной пометкой для ревью.
5. **Состав чек-листа верификации** (DTJ-075): не специфицирован документами конкретным перечнем
   пунктов — введён разумный набор из 4–6 пунктов, подлежащий уточнению продуктом.
6. **`whitelabel_contracts`** (модуль `26-module-tenancy-whitelabel.md` §12 п.4): таблица коммерческих
   условий White-Label, явно принадлежащая домену `billing`, не `tenancy` — НЕ реализована ни одним
   тикетом этого комплекта (вне зоны R1-16 и вне зоны EP-02/EP-03), зафиксирована здесь как
   известный пробел до появления отдельного эпика `billing`.

## Что сознательно НЕ входит в этот комплект (R2/R3, вне зоны R1-16)

- Самообслуживаемый конфигуратор брендинга в `apps/admin` (R3) — реализован только backend-движок
  и `apps/web`-применение (R1-часть, DTJ-059/060); полноценный UI редактирования палитры для
  `pharmacy_admin` — R3.
- Реальные банковские мерчант-креды (`AlifMobiProvider`/`DcNextProvider`) и второй реальный
  Telegram-бот под брендом сети — R3, заблокировано подписанным LOI (только порт + Mock/механизм —
  R1, DTJ-058/062).
- On-premise поставка (Docker-бандл, `LICENSE_KEY`) — R3, чек-лист готовится отдельно, вне этого
  комплекта.
- `pharmacy_api_keys` (D-11, доступ 1С) — не создаётся здесь несмотря на упоминание как дочерней
  сущности `PharmacyAccount` в домене; фактический потребитель — EP-05/EP-12.
