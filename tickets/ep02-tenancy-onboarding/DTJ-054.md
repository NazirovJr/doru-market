## Задача
Это ядро мультитенантности: единственное место, где по `Host`/`X-Tenant-Slug` определяется, чьи
данные видит запрос — ДО аутентификации (пользователь ищется по паре `(tenant_id, phone)`). Без
этого middleware ни один следующий эндпоинт платформы физически не может знать, какого тенанта
обслуживает.

## Технический контекст
`apps/api/src/common/context/tenant-context.ts` — общий, не модульный файл (используется ЛЮБЫМ
модулем платформы для чтения текущего тенанта), но логика РЕЗОЛВИНГА — middleware модуля `tenancy`
(владение файлом закреплено за EP-02, `00-EPICS.md`). Middleware регистрируется глобально в
`apps/api` bootstrap (EP-01 подключает `app.use(tenantResolutionMiddleware)` ДО `AuthGuard` — этот
тикет создаёт middleware и его подключение к DI, фактическую регистрацию в bootstrap-файле,
владение которым у EP-01, координирует по одной строке подключения, аналогично паттерну «гостевая
правка одной строки роутинга» из `00-EPICS.md` п.1). `AsyncLocalStorage` — request-scoped мост,
переживает весь жизненный цикл запроса без явной прокидки параметра через каждый слой NestJS.

## Что сделать
1. `common/context/tenant-context.ts`: `TenantContext` — обёртка над `AsyncLocalStorage<{ tenantId:
   string | null; slug: string; chainId: string | null; isNeutral: boolean }>`. Статические методы
   `TenantContext.run(store, callback)` (используется middleware для инициализации на запрос) и
   `TenantContext.current(): TenantContextStore | undefined` (используется репозиториями/guard'ами
   для чтения — НЕ для неявной подстановки `tenantId` в SQL, см. риск ниже и SRS-API-043).
2. `presentation/middleware/tenant-resolution.middleware.ts`: `TenantResolutionMiddleware` реализует
   алгоритм СТРОГО по приоритету (SRS-API-041):
   - Шаг 1 (Host): нормализованный `Host`-заголовок (без порта) → `tenantCachePort.getByDomain` →
     промах → `tenantRepository.findByCustomDomain`, ТОЛЬКО если найденный тенант имеет
     `customDomainStatus === 'verified'` (уточнение §12 п.3 `26-module...`, сужает условие
     резолвинга — тенант с `pending_verification` доменом НЕ резолвится по нему). Найдено → пишет в
     кэш, `X-Tenant-Slug` игнорируется, при наличии заголовка ЛОГИРУЕТСЯ `pino.warn` о расхождении
     (не блокирует запрос).
   - Шаг 2 (`X-Tenant-Slug`): если шаг 1 не дал результата И заголовок передан →
     `tenantCachePort.getBySlug` → промах → `tenantRepository.findBySlug`. Given slug не найден,
     Then middleware НЕ продолжает алгоритм (не переходит к шагу 3) — устанавливает флаг «резолвинг
     завершился ошибкой `UNKNOWN_TENANT_SLUG`» в контексте, финальный ответ `404` формирует
     `TenantResolutionGuard` (DTJ-055), middleware сам не бросает HTTP-исключение (миддлвары Fastify
     плохо совместимы с `DomainExceptionFilter`, ответственность разнесена по конвенции проекта).
   - Шаг 3 (Neutral): оба шага не дали результата → `findBySlug('neutral')` (через кэш).
3. Given ни один шаг не завершился успешно ПО ТЕХНИЧЕСКОЙ причине (БД/кэш оба недоступны даже для
   `neutral`), Then middleware помечает контекст как `unresolved: true, reason: 'technical'` —
   различие «`UNKNOWN_TENANT_SLUG`» (шаг 2 не нашёл конкретный slug) и «technical failure»
   (SRS-API-042) прокидывается ДАЛЬШЕ, в guard, двумя разными кодами (`404`/`400` соответственно).
4. Local-dev путь (SRS-TEN-007): здесь не требуется отдельный код — `X-Tenant-Slug` уже покрывает
   dev-инструменты (Postman/curl/Playwright `withTenant(slug)`-фикстура добавляется EP-19 при
   готовности e2e-инфраструктуры, не в этом тикете), `*.dorutj.local` через `Host` покрывается тем
   же шагом 1 без специального кода.
5. `common/decorators/public.decorator.ts`: `@Public()` — метаданные `IS_PUBLIC_KEY`, читаются
   `AuthGuard` (EP-01) для пропуска JWT-проверки. Уточнение SRS-TEN-008: middleware резолвит тенанта
   для КАЖДОГО запроса без исключений (даже публичных) — `@Public()` влияет только на пропуск
   аутентификации, не на пропуск резолвинга; `/health`/`/ready` исключаются из middleware отдельным
   списком префиксов в самой регистрации middleware (`excludedPaths`), т.к. это инфраструктурные, не
   продуктовые маршруты.

## Критерии приёмки
1. Given `Host: sifat.tj` совпадает с `verified` custom_domain тенанта B, When запрос (даже с
   заголовком `X-Tenant-Slug: neutral`), Then контекст резолвлен в тенанта B, `X-Tenant-Slug`
   проигнорирован, `pino.warn` о расхождении записан.
2. Given `Host` не резолвится, `X-Tenant-Slug: sifat-demo` существует в БД, When запрос, Then
   контекст резолвлен в `sifat-demo`.
3. Given `Host` не резолвится, `X-Tenant-Slug: definitely-not-real`, When запрос, Then контекст
   помечен `unresolved: true, reason: 'unknown_slug'`, шаг 3 (neutral) НЕ выполняется (негативный
   сценарий — заведомо неверный slug не должен тихо подставлять `neutral`).
4. Given `Host` не резолвится, `X-Tenant-Slug` не передан, When запрос, Then контекст резолвлен в
   `neutral`.
5. Given домен привязан к тенанту B со статусом `pending_verification` (ещё не подтверждён), When
   запрос с этим `Host`, Then шаг 1 пропускается как непройденный (домен не резолвится по
   неподтверждённому статусу), алгоритм переходит к шагу 2/3.

## Тест-план
Unit (Vitest, мокированные `TenantRepositoryPort`/`TenantCachePort`): `tenant-resolution.middleware.
spec.ts` — все 5 сценариев выше + сценарий полного технического отказа (оба порта бросают ошибку) +
сценарий `Host` с портом в значении (`sifat.tj:8443`, порт должен отбрасываться перед сравнением).
`tenant-context.spec.ts` — `AsyncLocalStorage` изолирует контекст между параллельными
`TenantContext.run()`-вызовами (тест на конкурентный доступ — два одновременных `run()` с разными
store не видят чужой контекст). Порог покрытия `presentation/` (общий порог ≥ 70%, `common/` тоже
≥ 70% как некритичная инфраструктура — не `domain`/`application`).

  в HTTP/1.1, но Fastify может отдавать его в разном регистре) — нормализовать `toLowerCase()` перед
  сравнением, добавить отдельный тест-кейс.
