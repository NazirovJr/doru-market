## Задача
Единственный способ, которым `super_admin` видит, что вообще ждёт решения. Без курсорной,
FIFO-отсортированной очереди оператор либо не видит новые заявки, либо видит их в непредсказуемом
порядке, что напрямую нарушает справедливость SLA (REQ-ONBOARD-18) — старые заявки должны
рассматриваться раньше новых.

## Технический контекст
Слой `application`. Курсорная пагинация — уже установленная конвенция `12-api-conventions...md`
§1.1 (SRS-API-004, реализована EP-01 как общий хелпер `packages/contracts/src/pagination.ts`) — этот
тикет ТОЛЬКО применяет существующий механизм к своему запросу, не изобретает пагинацию заново.

## Что сделать
1. `application/use-cases/list-pending-verifications.use-case.ts`:
   `ListPendingVerificationsUseCase.execute({ subjectType: 'chain' | 'pharmacy', cursor?, limit })` —
   читает через `PharmacyChainRepository`/`PharmacyAccountRepository` (DTJ-064/065) с фильтром
   `status = 'pending_review'`, сортировка `submittedAt: 'asc'` (FIFO), пагинация — переиспользует
   общий `CursorPaginationPort`/хелпер EP-01 (если уже существует; иначе временная локальная
   реализация курсора по `(submittedAt, id)` composite-ключу, помеченная TODO на замену общим
   хелпером при готовности).
2. Каждый элемент результата обогащается данными карточки: превью документов (`licenseScanUrl`,
   `registrationCertificateUrl` — просто прокинутые URL, без генерации превью на бэкенде, рендер
   превью — ответственность фронтенда DTJ-075) + `reviewReason` из связанной строки
   `pharmacy_verification` (JOIN по `chain_id`/`pharmacy_id`).
3. `presentation/controllers/pharmacy-verification-queue.controller.ts`: `GET
   /api/v1/pharmacy-chains?status=pending_review` и `GET
   /api/v1/pharmacy-accounts?status=pending_review` (`@Roles('super_admin')`,
   permission-строка `pharmacy-accounts:approve` — уже определена `12-api-conventions...md` §4.1,
   переиспользуется как guard-условие для ЧТЕНИЯ очереди тоже, отдельного permission на просмотр не
   заводится — кто может одобрить, тот может видеть очередь). Given `status` query-параметр передан
   со значением, отличным от `pending_review` (например, `approved`/`rejected` — просмотр истории),
   Then эндпоинт поддерживает ЛЮБОЕ значение enum статуса (не только `pending_review`) — общий
   листинг с фильтром, `pending_review` просто дефолтное/наиболее частое значение UI очереди.

## Критерии приёмки
1. Given 3 заявки сети поданы в разное время (`submitted_at` t1 < t2 < t3), все `pending_review`,
   When `GET /pharmacy-chains?status=pending_review`, Then порядок в ответе — t1, t2, t3 (FIFO, не
   `created_at`, не произвольный).
2. Given постраничный запрос с `limit=2`, When первый вызов, Then `meta.pagination.nextCursor`
   заполнен и указывает на 3-й элемент, второй вызов с этим курсором возвращает оставшийся элемент
   и `nextCursor: null`.
3. Given `pharmacy_admin` (не `super_admin`) вызывает эндпоинт, When запрос, Then `403
   INSUFFICIENT_ROLE` на уровне guard'а, до входа в use case — негативный сценарий.
4. Given заявка с `review_reason='address_change'` (появляется после DTJ-069) в очереди рядом с
   `review_reason='initial'`, When листинг, Then оба поля различимы в ответе (не потеряны при
   маппинге DTO).

## Риски и подводные камни
- Если общий курсорный пагинатор EP-01 (`packages/contracts/src/pagination.ts`, упомянут в
  `00-EPICS.md` как скелет EP-01) ещё не готов на момент реализации — временная локальная реализация
  курсора здесь допустима (не блокирует тикет), но ДОЛЖНА быть заменена на общий хелпер при его
  появлении — зафиксировать TODO с явной ссылкой, не оставлять два параллельных механизма пагинации
  в кодовой базе надолго.
- JOIN с `pharmacy_verification` в каждом элементе листинга — потенциальная точка N+1, если
  реализовано наивно; требовать от разработчика единого запроса с JOIN, не цикла отдельных запросов
  на каждую заявку (проверяется код-ревью, не автоматическим тестом в этом тикете).
