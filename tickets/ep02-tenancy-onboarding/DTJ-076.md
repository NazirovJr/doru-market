## Задача
Единственный публичный вход, через который реальная аптека/сеть попадает в платформу (раздел «Для
аптек/поставщиков», REQ-MARKET-7). Без этого экрана эндпоинты DTJ-064/065/066 существуют, но
недостижимы никем, кроме разработчика через Postman — онбординг не может стартовать в реальной
эксплуатации.

## Технический контекст
`apps/web/src/features/onboarding-application/**` — новая вертикальная фича внутри уже
существующего (к этому моменту) приложения `apps/web` (scaffolding — EP-01). Правило C16/`02` §1.2:
горизонтальные импорты между `features/*` запрещены — эта фича не импортирует ничего из
`features/auth`/`features/search`, только общие `packages/ui`/`packages/i18n`.
`32-design-reference.md` строка 323 явно относит `/pharmacy-application` к «Пробелам дизайна» —
визуального прецедента нет, форма собирается из уже описанных примитивов дизайн-системы (`Card`,
поля ввода, загрузка файла, кнопка) без нового визуального языка.

## Что сделать
1. Маршрут `/pharmacy-application` (публичный, без аутентификации — форма доступна анонимному
   посетителю) — многошаговая форма (минимум 2 логических шага: (1) данные юрлица/контакт + выбор
   «соло-аптека» / «есть сеть», (2) данные конкретной точки — адрес, лицензия, загрузка документов)
   ЛИБО одна длинная форма со скроллом, если многошаговость не даёт ощутимого UX-выигрыша при
   объёме полей — решение исполнителя, главное требование ниже.
2. Поля формы — точно по `SubmitChainApplicationRequestSchema`/`SubmitPharmacyApplicationRequestSchema`
   (`packages/contracts/src/onboarding.ts`, DTJ-064/065) — клиентская валидация ПЕРЕИСПОЛЬЗУЕТ те же
   zod-схемы (импорт из `packages/contracts`, единый источник валидации на границе API, C15 «не
   изобретать вторую валидацию»).
3. Условное отображение поля `isWhitelabelRequested` → при `true` показывает дополнительные
   обязательные поля (`legalAddress`, `registrationCertificateUrl`), согласовано с
   `.superRefine`-логикой контракта.
4. Загрузка документов (`licenseScanUrl`, `registrationCertificateUrl`) — компонент
   `<FileUploadField>`, вызывающий `POST /api/v1/onboarding-documents` (DTJ-065) ДО финальной
   отправки формы, отображает прогресс/превью загруженного файла, ошибку при превышении размера/
   неверном формате (мгновенная обратная связь, не дожидаясь финального сабмита).
5. OTP-верификация контактного телефона (DTJ-064) — встроенный шаг: после ввода телефона кнопка
   «Отправить код», поле ввода 4–6-значного кода (переиспользовать паттерн ячеек OTP-ввода, уже
   описанный `32-design-reference.md` §«Home»-подобных экранов для логина, если компонент уже есть в
   `packages/ui` к этому моменту — не дублировать компонент, ждать готовности EP-18/переиспользовать).
6. Финальный сабмит: `POST /pharmacy-chains` или `POST /pharmacy-accounts` (в зависимости от
   выбора «есть сеть»/«соло-аптека»), затем автоматически `POST .../:id/submit` (DTJ-066) — с точки
   зрения пользователя это ОДНО действие «Отправить заявку», два вызова API скрыты за одной кнопкой.
7. Экран успеха: подтверждение подачи + `id` заявки + ожидаемый SLA («рассмотрение занимает до 2
   рабочих дней») + инструкция, что делать дальше (ожидать звонка/уведомления — конкретный канал
   уточняется по готовности EP-16, на этом шаге — нейтральная формулировка через i18n-ключ, не
   привязанная к конкретному каналу).

## Критерии приёмки
1. Given посетитель заполняет форму соло-аптеки без `isWhitelabelRequested`, When отправка, Then
   создаётся заявка, статус переходит в `pending_review` (оба API-вызова выполнены последовательно),
   экран успеха показан.
2. Given `isWhitelabelRequested` включён, When попытка отправить БЕЗ `legalAddress`, Then форма
   блокирует отправку с локализованной ошибкой валидации у соответствующего поля (клиентская
   валидация СОВПАДАЕТ с серверной по составу обязательных полей).
3. Given файл лицензии 11 МБ выбран для загрузки, When попытка загрузки, Then показана ошибка
   «файл слишком большой» ДО отправки всей формы (не после финального сабмита).
4. Given телефон введён, код запрошен, When введён НЕВЕРНЫЙ код, Then показана ошибка, форма НЕ
   переходит к следующему шагу — негативный сценарий.
5. Given форма отправлена успешно, When повторная попытка сабмита той же формы (двойной клик), Then
   защита от двойной отправки (кнопка дизейблится на время запроса) — не создаёт вторую заявку.

## Риски и подводные камни
- Владение `apps/web` вне зоны EP-03 по `00-EPICS.md` («Порядок владения файлами» перечисляет
  `apps/web` только за EP-01/EP-06/EP-07/EP-08/EP-09) — этот тикет добавляет НОВУЮ, изолированную
  фичу (`features/onboarding-application/**`), не трогая существующие фичи других эпиков; решение
  включить его в EP-03 (а не оставить незакрытым пробелом) явно зафиксировано здесь как
  осознанное расширение зоны ответственности тимлида EP-02/EP-03 на этот один экран, т.к. документ
  `32-design-reference.md` относит его к «Пробелам дизайна» без явного эпика-владельца — при
  конфликте с другим тимлидом, тоже претендующим на этот маршрут, разрешение — по факту, кто первым
  смержил (стандартное правило проекта для незакреплённых зон).
- Двухшаговая структура (юрлицо → точка) технически СООТВЕТСТВУЕТ разделению `PharmacyChain`/
  `PharmacyAccount` на бэкенде, но с точки зрения пользователя это ОДНА форма (REQ-ONBOARD-2) —
  важно не дать двум API-вызовам «просочиться» в UX как два отдельных действия (например, два
  отдельных экрана успеха) — только один финальный экран подтверждения после обоих вызовов.
