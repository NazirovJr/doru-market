## Задача
Активная аптека, сменившая физический адрес, не может продолжать торговать под старой лицензионной
привязкой без повторной сверки — иначе адрес в системе разойдётся с адресом, под который выдана
лицензия. Отличие от первичной заявки — оператору не нужно проверять лицензию с нуля, только
соответствие нового адреса, что ускоряет повторную проверку и не путает её в общей очереди с новыми
заявками.

## Технический контекст
Слой `application`. Домен уже переводит `PharmacyAccount` в `pending_review` при смене адреса
активной точки (`SRS-DOM-049`, реализовано доменным методом `updateAddress` в DTJ-063) — этот тикет
добавляет ТОЛЬКО прикладную обвязку: авторизацию (`pharmacy_admin` своей же точки), создание записи
`pharmacy_verification` с `review_reason='address_change'` (отличает от `'initial'`) и появление
заявки в общей очереди DTJ-067 с этим флагом.

## Что сделать
1. `application/use-cases/update-pharmacy-address.use-case.ts`: `UpdatePharmacyAddressUseCase.
   execute({ pharmacyId, actorId, addressText, latitude, longitude })`:
   - Политика авторизации: `actor.role === 'pharmacy_admin'` И `actor.pharmacyId === pharmacyId` (или
     `actor.chainId === pharmacyAccount.chainId` — уточнить по матрице `12-api-conventions...md`
     §4.1, permission-строка `pharmacy-accounts:update-address`, доступна `pharmacy_admin` только
     «своя аптека») ЛИБО `super_admin`.
   - `pharmacyAccount.updateAddress({ addressText, latitude, longitude })` (домен, DTJ-063 —
     переводит в `pending_review`, если была `active`; НИЧЕГО не переводит, если статус уже был
     ИНОЙ, например `draft`/`pending_review` — доменный метод просто обновляет поля без побочного
     перехода статуса вне случая `active`, уточнить в реализации DTJ-063 при необходимости явного
     ветвления).
   - Given переход в `pending_review` произошёл (было `active`), Then создаёт запись
     `pharmacy_verification(pharmacy_id, verification_status='pending_review',
     review_reason='address_change', submitted_at=now(), sla_target_at=now()+2 рабочих дня)`.
   - Given статус НЕ был `active` (например, аптека ещё `draft`), Then адрес просто обновляется,
     БЕЗ создания новой verification-записи (нет смысла заново запускать проверку для заявки, уже
     находящейся в своём обычном цикле подачи).
   - Сохраняет обе сущности в одной транзакции, публикует событие (переиспользует форму, схожую с
     `PharmacyAccountActivated`, но со своим типом `PharmacyAccountAddressChangedEvent` — новый DTO
     этого тикета, для будущих подписчиков карты/каталога, не реализуется здесь дальше публикации).
2. Добавить маршрут `PATCH /api/v1/pharmacy-accounts/:id` в контроллер DTJ-065 (тело `{ addressText,
   latitude, longitude }`).

## Критерии приёмки
1. Given активная аптека (`status='active'`), When `PATCH /pharmacy-accounts/:id { addressText:
   'новый адрес', latitude, longitude }` от её `pharmacy_admin`, Then `status='pending_review'`,
   создана `pharmacy_verification` с `review_reason='address_change'`.
2. Given та же операция, When очередь верификации запрошена (`GET /pharmacy-accounts?
   status=pending_review`, DTJ-067), Then новая карточка присутствует с флагом
   `reviewReason='address_change'`, отличимым от `'initial'`.
3. Given аптека в статусе `draft` (ещё не одобрена впервые), When `PATCH .../address`, Then адрес
   обновлён, статус остаётся `draft`, НЕ создана лишняя verification-запись.
4. Given `pharmacy_admin` ЧУЖОЙ аптеки пытается сменить адрес, When запрос, Then `403` — негативный
   сценарий (политика владения, не guard — проверяется на уровне application).

## Риски и подводные камни
- Точная permission-модель («своя аптека» для `pharmacy_admin`, который управляет СЕТЬЮ, а не одной
  точкой) — матрица `12-api-conventions...md` §4.1 формулирует `pharmacy-accounts:update-address`
  как «✅ своя аптека» без уточнения, относится ли это к КОНКРЕТНОМУ `pharmacy_admin`-аккаунту
  привязанному к одной точке, или к любому `pharmacy_admin` СВОЕЙ сети (управляющему несколькими
  точками) — реализация по умолчанию трактует как «любая точка своей сети» (согласуется с ролью
  `pharmacy_admin`, управляющей сетью, а не персоналом одной аптеки — тот отдельная роль
  `pharmacist`), уточнить при код-ревью, если найдётся более точная формулировка в UX-документах.
