## Задача
Telegram — единственный протокол платформы, который НЕ передаёт кастомные заголовки в
webhook-запросе, поэтому тенант не может резолвиться обычным алгоритмом `Host`/`X-Tenant-Slug`
(DTJ-054) — единственное задокументированное исключение из общего резолвинга, обоснованное
физическим ограничением Telegram Bot API. Без этого роутера ни один Telegram-бот (нейтральный или
White-Label) не может физически принимать апдейты — это блокирует канал уведомлений EP-16.

## Технический контекст
Слой `presentation`/`infrastructure` модуля `tenancy` — маршрут несёт `tenantSlug` явно в пути
(`POST /api/v1/webhooks/telegram/:tenantSlug`), поэтому НЕ проходит через
`TenantResolutionMiddleware` (DTJ-054) в обычном порядке — этот контроллер сам резолвит тенанта из
параметра пути, устанавливает `TenantContext` вручную перед передачей апдейта дальше. Фактическая
бизнес-логика обработки Telegram-апдейта (`TelegramUpdateHandler`) — вне зоны этого тикета,
принадлежит `modules/notifications` (EP-16, «работает ОДИНАКОВО для всех тенантов», SRS-TEN-027) —
этот тикет ТОЛЬКО резолвит тенанта и передаёт управление через узкий порт.

## Что сделать
1. `application/ports/telegram-token-resolver.port.ts`: `TelegramTokenResolverPort` —
   `resolveByTenantSlug(slug: string): Promise<{ tenantId: string; secretToken: string } | null>`.
2. `infrastructure/adapters/telegram-token-resolver.adapter.ts`: реализация — `tenantRepository.
   findBySlug(slug)` → given не найден или `telegramBotTokenRef` не заполнен, `null`; иначе
   `secretsVaultPort.resolve(telegramBotTokenRef)` (DTJ-058) → `{ tenantId, secretToken: token }`
   (значение `secret_token`, заданное при регистрации вебхука через `setWebhook`, ХРАНИТСЯ рядом с
   самим токеном бота в том же секрете — формат значения секрета согласовать так, чтобы
   `resolve()` возвращал ОБА поля, `{ token, secretToken }`, адаптер использует `secretToken` для
   сравнения, `token` передаётся дальше в `notifications` для исходящих сообщений).
3. `presentation/controllers/telegram-webhook.controller.ts`: `TelegramWebhookController` —
   `@Public()` (без JWT — Telegram не аутентифицируется как пользователь платформы), маршрут ВНЕ
   обычного `TenantResolutionMiddleware` (регистрируется с явным исключением пути в middleware
   DTJ-054, ОДНА строка в списке `excludedPaths` того тикета — координация, не полное
   переопределение).
   - `resolveByTenantSlug(tenantSlug)` → given `null`, `404 UNKNOWN_TENANT_SLUG`.
   - Сравнивает заголовок `secret_token` (Telegram Bot API, `X-Telegram-Bot-Api-Secret-Token`) с
     разрешённым `secretToken` — НЕсовпадение → `401`, апдейт НЕ передаётся дальше, никакая
     сущность не создаётся (SRS-TEN-027).
   - Совпадение → устанавливает `TenantContext` (DTJ-054) вручную для длительности запроса, вызывает
     `NotificationsFacade.handleTelegramUpdate(tenantId, updatePayload)` (импорт ТОЛЬКО из
     `@/modules/notifications` — публичный барабан; метод обязан существовать к моменту интеграции,
     реализуется EP-16 — временная заглушка `NullNotificationsFacade.handleTelegramUpdate` до
     готовности, аналогично паттерну DTJ-057/070) → `200` с пустым `{ data: { success: true } }`
     (Telegram Bot API ожидает `200` быстро, тело не имеет значения для Telegram).
4. Given тенант резолвлен, но `telegramBotTokenRef` не заполнен (SRS-TEN-029, из другого маршрута —
   исходящие уведомления, а не входящий webhook) — этот тикет НЕ обрабатывает исходящий фоллбэк
   (это `notifications`, EP-16), только фиксирует, что для ВХОДЯЩЕГО webhook отсутствие токена
   эквивалентно `404` на этапе `resolveByTenantSlug` (бот этого тенанта физически не может получать
   апдейты, если у него нет зарегистрированного токена).

## Критерии приёмки
1. Given webhook на путь тенанта A с `secret_token` тенанта B (несовпадение), When `POST
   /webhooks/telegram/tenant-a-slug`, Then `401`, апдейт не обработан, `NotificationsFacade` не
   вызван (проверяется через spy).
2. Given webhook на путь несуществующего slug, When запрос, Then `404 UNKNOWN_TENANT_SLUG`.
3. Given корректный `secret_token`, When запрос, Then `TenantContext` установлен в `tenantId` этого
   тенанта ДО вызова `NotificationsFacade.handleTelegramUpdate`, ответ `200`.
4. Given тенант без `telegramBotTokenRef` (White-Label клиент не прошёл чек-лист, либо `neutral` до
   первого ENV-деплоя бота), When webhook на его путь, Then `404` (не `500`) — негативный сценарий,
   не путать с несовпадением токена (тоже отклонение, но другая причина/код).

## Риски и подводные камни
- Прямая зависимость `tenancy → notifications` (EP-16, волна 10) при том, что `tenancy` — волна 2:
  реализация ИСПОЛЬЗУЕТ `NullNotificationsFacade`-заглушку (метод логирует и возвращает успех) до
  готовности реального `NotificationsFacade` — аналог решения DTJ-057 для `onboarding`. Переключение
  на реальную реализацию — ответственность EP-16 при достижении своей волны, не блокирует закрытие
  этого тикета.
- Формат хранения `{ token, secretToken }` в одном секрете Vault — решение этого тикета, требующее
  согласования с DTJ-058 (описавшим формат `resolve()` как произвольный `Record<string, string>` —
  совместимо без изменения порта, только соглашение по именам ключей внутри конкретного секрета).
