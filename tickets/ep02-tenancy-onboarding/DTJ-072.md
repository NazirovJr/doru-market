## Задача
Отзыв верификации — признание, что ПРЕДЫДУЩЕЕ решение `approve` было ошибочным (например, лицензия
впоследствии оказалась поддельной, обнаружено уже после активации). Это принципиально отличается от
`reject` (применим только к ещё не одобренной заявке) и требует каскадного эффекта — если поддельна
лицензия сети, ВСЕ её дочерние точки должны быть немедленно закрыты для заказов, не только
формально помечена сама заявка.

## Технический контекст
Слой `application`. Работает на уровне `pharmacy_verification` (не напрямую `pharmacy_chains`/
`pharmacies` — отзыв верификации логически отдельная сущность от статуса онбординга, хотя и
вызывает изменение последнего). Каскад реализуется через `PharmacyAccountRepository` (уже
существующий, DTJ-065) — читает все дочерние точки субъекта проверки.

## Что сделать
1. `application/use-cases/revoke-verification.use-case.ts`: `RevokeVerificationUseCase.execute({
   verificationId, actorId, reason })`:
   - Читает `pharmacy_verification` по `id`. Given `verification_status ∉ {'verified'}` (используется
     как прокси для «уже активный/одобренный субъект» — уточнить у домена DTJ-063 точное соответствие
     `verification_status='verified'` ↔ статус сущности `'active'`/`'approved'`; если между ними
     обнаружится рассинхронизация в ходе реализации DTJ-068, это отдельный баг тех тикетов, не этого),
     Then `409 CONFLICT` (`AlreadyReviewedError`/новая `NotYetVerifiedError` — на усмотрение, главное
     — `revoke` НЕДОСТУПЕН для `not_started`/`pending_review` субъекта, SRS-ADM-017).
   - `pharmacy_verification.verification_status → 'revoked'`, `revoked_at=now()`,
     `revoked_reason=reason`, `revoked_by=actorId` (колонки из DTJ-063 миграции).
   - Given `verification.chainId` заполнен (отзыв на уровне СЕТИ), Then читает ВСЕ дочерние
     `PharmacyAccount` этой сети через репозиторий, для каждой активной точки вызывает
     `pharmacyAccount.suspend('license_revoked', actor)` и сохраняет.
   - Given `verification.pharmacyId` заполнен (отзыв на уровне ОТДЕЛЬНОЙ аптеки), Then вызывает
     `suspend('license_revoked', actor)` только для этой точки.
   - Журналирует `onboarding_review_log(action='revoke_verification', reason, actorUserId)` — ОДНУ
     запись на операцию (не по одной на каждую каскадно приостановленную точку — верхнеуровневое
     решение фиксируется единожды, отдельные `suspend`-эффекты не дублируют журнал повторно; если
     ревью архитектора потребует отдельную запись на каждую точку — пересмотреть, не критично для
     функциональности).
   - Всё — в одной транзакции.
2. `presentation/controllers/pharmacy-verification-revocation.controller.ts`: `POST
   /api/v1/pharmacy-verifications/:id/revoke { reason: string }` (`@Roles('super_admin')`).

## Критерии приёмки
1. Given сеть с 3 активными точками, `pharmacy_verification` (уровень сети) `verification_status
   ='verified'`, When `POST /pharmacy-verifications/:id/revoke { reason: 'поддельная лицензия' }`,
   Then `verification_status='revoked'`, все 3 точки переведены в `status='suspended',
   suspension_reason='license_revoked'`.
2. Given verification на уровне ОДНОЙ аптеки, When `revoke`, Then приостановлена ТОЛЬКО эта аптека,
   остальные точки сети (если есть) не затронуты.
3. Given `verification_status='pending_review'` (заявка ещё не одобрена), When `revoke`, Then
   `409` — негативный сценарий (отзыв неприменим к ещё не верифицированному субъекту).
4. Given verification уже `'revoked'`, When повторный `revoke`, Then `409` (идемпотентность решения,
   не двойной каскад).

## Тест-план
Unit (`application`): `revoke-verification.use-case.spec.ts` — все 4 сценария, включая проверку
точного количества затронутых `PharmacyAccount` в каскадном сценарии 1 (не больше, не меньше 3).

## Риски и подводные камни
- Точное соответствие `pharmacy_verification.verification_status` статусу самой сущности
  (`pharmacy_chains.status`/`pharmacies.status`) — документ не даёт явной формулы синхронизации
  между двумя разными таблицами состояния (verification — отдельное «состояние проверки», onboarding
  status — отдельное «состояние жизненного цикла»); реализация этого тикета читает ОБЕ (verification
  для проверки применимости `revoke`, onboarding-статус сущности — для каскадного `suspend`) —
  задокументировать явно в коде use case, почему читаются оба источника, чтобы не выглядело
  избыточным при ревью.
- Если у сети НЕТ ни одной активной точки на момент отзыва (все уже `suspended`/`terminated` по
  другой причине), каскад не находит кого приостанавливать — не ошибка, просто пустой список
  затронутых точек, отзыв всё равно фиксируется на уровне verification.
