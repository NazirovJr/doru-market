## Задача
Мост между доменной моделью (DTJ-050) и физической схемой (DTJ-051). Без этого репозитория
резолвинг (DTJ-054) не может найти тенант по `Host`/slug, а use case провизионинга (DTJ-057) не
может создать новую строку. Таблица `tenants` НЕ тенант-скоупная сама по себе (это таблица
определения тенантов, не данные одного тенанта) — репозиторий НЕ наследует `TenantScopedRepository`
(DTJ-056), это единственное намеренное исключение в модуле `tenancy`, зафиксированное явным
комментарием в коде, чтобы не выглядело забытым при код-ревью.

## Технический контекст
Слой `infrastructure`, порты объявлены в `application/ports/*.port.ts` по конвенции `02` §1.3
(interface + `Symbol`-токен), связывание — в `tenancy.module.ts` (`{ provide: TENANT_REPOSITORY,
useClass: DrizzleTenantRepository }`). Маппер переводит Drizzle row → доменный `Tenant`/
`TenantSettings` и обратно — `application`/`domain` никогда не видят Drizzle-тип напрямую (C1 `02`).

## Что сделать
1. `application/ports/tenant-repository.port.ts`: интерфейс `TenantRepositoryPort` — `findById(id:
   TenantId): Promise<Tenant | null>`, `findBySlug(slug: string): Promise<Tenant | null>`,
   `findByCustomDomain(domain: string): Promise<Tenant | null>`, `findByChainId(chainId: TenantId):
   Promise<Tenant | null>`, `save(tenant: Tenant): Promise<void>` (upsert по `id`).
2. `application/ports/tenant-settings-repository.port.ts`: `TenantSettingsRepositoryPort` —
   `findByTenantId`, `save`.
3. `infrastructure/mappers/tenant.mapper.ts`: `toDomain(row): Tenant`, `toPersistence(tenant):
   InsertTenantRow` — двунаправленное преобразование, включая enum `customDomainStatus` (строка БД
   ↔ TS-литерал).
4. `infrastructure/repositories/tenant.repository.ts`: `DrizzleTenantRepository implements
   TenantRepositoryPort` — каждый метод использует `db.select().from(tenants).where(...)` через
   единый Drizzle-клиент модуля (инжектируется через DI-токен из общей инфраструктуры БД,
   уже определённой EP-01). `findBySlug`/`findByCustomDomain` — точечные `WHERE`-запросы без
   дополнительной логики (кэширование — ответственность DTJ-053, репозиторий не знает о Redis).
5. `infrastructure/repositories/tenant-settings.repository.ts`: аналогично для `tenant_settings`.
6. Явный комментарий в обоих классах репозитория: «НЕ наследует `TenantScopedRepository` — `tenants`/
   `tenant_settings` определяют сами тенанты, тенант-скоуп неприменим по определению (см. DTJ-056)».

## Критерии приёмки
1. Given в БД есть тенант со `slug='sifat-demo'`, When `tenantRepository.findBySlug('sifat-demo')`,
   Then возвращается доменный `Tenant` с корректно замапленными полями (включая `TenantSlug`/
   `TenantId` VO, не сырые строки).
2. Given slug не существует, When `findBySlug('does-not-exist')`, Then возвращается `null` (не
   исключение — вызывающий код, например `TenantResolutionMiddleware`, сам решает, что делать
   дальше по алгоритму §5).
3. Given новый `Tenant`, созданный доменной фабрикой, When `tenantRepository.save(tenant)` затем
   `findById(tenant.id)`, Then возвращённый объект равен исходному по всем полям (round-trip тест).
4. Given попытка сохранить тенант с уже занятым `customDomain` (нарушение `UNIQUE`), When
   `save()`, Then репозиторий перехватывает код ошибки PostgreSQL `23505` и пробрасывает
   `DuplicateCustomDomainError` (не сырое исключение драйвера) — негативный сценарий.

## Тест-план
Интеграционные тесты (Vitest + тестовый Postgres): `tenant.repository.integration.spec.ts` (все 4
сценария выше + `findByChainId`), `tenant-settings.repository.integration.spec.ts` (сохранение и
чтение `brandPalette` JSONB, дефолтные SLA-поля). Unit-тест на маппер: `tenant.mapper.spec.ts`
(двунаправленное преобразование не теряет и не искажает поля, включая граничный случай
`customDomain = null`). Порог покрытия `infrastructure/` ≥ 70%.

## Риски и подводные камни
- Общий Drizzle-клиент/пул соединений — инфраструктура EP-01 (`apps/api` bootstrap); этот тикет
  ПОТРЕБЛЯЕТ существующий DI-токен клиента БД, не создаёт новый пул — если на момент реализации
  общий провайдер клиента ещё не готов, координация с владельцем EP-01, не дублировать подключение.
- `save()` как upsert (не раздельные `create`/`update`) — сознательное упрощение для агрегата с
  единственным владельцем записи (провизионирование происходит один раз, DTJ-057); если позже
  понадобится различать «уже существует» как ошибку (например, повторный вызов
  `ProvisionTenantUseCase`), это проверяется НА УРОВНЕ use case (проверка `findByChainId` ПЕРЕД
  `save`), не в репозитории.
