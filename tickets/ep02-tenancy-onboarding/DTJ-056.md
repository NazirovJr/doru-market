## Задача
Charter §3.4 требует «обязателен тест на утечку данных между тенантами» как часть `pnpm verify` для
КАЖДОГО тенант-скоупного репозитория в системе — не только в модуле `tenancy`. `dependency-cruiser`
не может статически проверить содержимое SQL-запроса (есть ли `WHERE tenant_id=`), поэтому эта
гарантия ЦЕЛИКОМ держится на дисциплине типов (обязательный параметр) + переиспользуемом
поведенческом тесте. Этот тикет — единственное место, где пишется САМ механизм проверки; каждый
последующий модуль (`orders`, `prescriptions`, `cart`, ...) параметризует его своим репозиторием
(инструкция для этого — в DoD любого будущего тикета репозитория, уже установлено `26-module-
tenancy-whitelabel.md` SRS-TEN-011, эта же формулировка перенесена в чеклист ревью `02` §7).

## Технический контекст
`infrastructure/base/tenant-scoped-repository.ts` — переиспользуемый базовый класс/примесь,
которую наследуют репозитории тенант-скоупных таблиц ДРУГИХ модулей (`users`, `orders`, `cart`,
`prescriptions`, `notifications`, `i18n_overrides` — прямой tenant-скоуп по `11-database-schema.md`
§«Изоляция тенантов»). Класс живёт в модуле `tenancy`, но экспортируется через `index.ts` — это
ЕДИНСТВЕННЫЙ элемент инфраструктуры, разрешённый к прямому импорту другими модулями (публичный
контракт Facade-паттерна, не нарушение границ модуля, т.к. `02` §1.2 разрешает публичные типы через
`index.ts`). `dependency-cruiser`-правило, блокирующее прямой импорт `drizzle-orm`-клиента вне
`infrastructure/repositories/*`, — уже действующее архитектурное правило проекта; если конкретная
запись для tenant-scope ещё не добавлена в `.dependency-cruiser.cjs` на момент реализации, этот
тикет НЕ правит корневой конфиг сам (владение — исключительно EP-19, `00-EPICS.md` п.5) — вместо
этого заводится согласованный запрос владельцу EP-19 с точной формулировкой правила (см. «Риски»).

## Что сделать
1. `tenant-scoped-repository.ts`: абстрактный класс `TenantScopedRepository<TEntity>` — ЛЮБОЙ метод
   чтения/записи в наследнике обязан принимать `tenantId: TenantId` ПЕРВЫМ явным параметром (сам
   базовый класс не содержит query-логики — это контракт по сигнатуре, конкретные `findById`/
   `save`/`delete` определяет каждый конкретный репозиторий-наследник, базовый класс задаёт только
   защищённый хелпер `protected assertTenantId(tenantId: TenantId): void` — рантайм-проверка на
   `undefined`/`null` для мест, где TypeScript обошли через `any`, второй рубеж после типов).
2. `testing/tenant-isolation.contract-test.ts`: экспортирует функцию `describeTenantIsolationContract
   <TRepo extends TenantScopedRepository<unknown>>(options: { repositoryFactory: () => TRepo;
   seedEntity: (tenantId: TenantId) => Promise<{ entityId: string }>; findById: (repo: TRepo,
   tenantId: TenantId, entityId: string) => Promise<unknown | null> })` — использует `describe.each`
   (Vitest) для параметризации: (а) создаёт сущность в тенанте A, (б) пытается прочитать её через
   `findById(repo, tenantIdB, entityId)` (чужой тенант), (в) ассертирует `null`/`NotFoundError`.
   Функция экспортируется из `testing/`, импортируется тестовыми файлами других модулей
   (`apps/api/src/modules/orders/infrastructure/repositories/orders.repository.contract-test.spec.ts`
   и т.д., по мере готовности — не создаются этим тикетом, только сам механизм).
3. `testing/fixtures/violator-repository.fixture.ts`: `ViolatorRepository extends
   TenantScopedRepository<unknown>` — намеренно НЕПРАВИЛЬНАЯ реализация (метод `findById` игнорирует
   переданный `tenantId`, фильтрует только по `id`) — используется в тесте САМОГО контракт-теста
   («ловушка, которая перестала ловить, молчит об этом», `02` §6.1 — доказывает, что
   `describeTenantIsolationContract` действительно фейлится на нарушителе, не просто всегда зелёный).
4. Тест на саму ловушку: `tenant-isolation-contract-test-self-check.spec.ts` — запускает
   `describeTenantIsolationContract` с `ViolatorRepository` внутри `expect(() =>
   ...).rejects`/аналог (framework-специфичный способ проверить, что параметризованный набор
   тестов ПАДАЕТ на нарушителе) — этот файл живёт РЯДОМ с фикстурой, не смешивается с обычным
   `pnpm test` прогоном модулей (маркируется отдельным Vitest-тегом/`describe.skip` в обычном
   прогоне и явно запускается в CI-джобе, аналогичной `tests/arch` EP-19, либо интегрируется в
   `tests/arch` при готовности инфраструктуры EP-19 — координация, не блокирует этот тикет).

## Критерии приёмки
1. Given корректный репозиторий (мок, честно фильтрующий по `tenantId`), When
   `describeTenantIsolationContract(...)` прогоняется против него, Then все тесты набора зелёные.
2. Given `ViolatorRepository` (фикстура), When тот же набор прогоняется против неё, Then минимум
   один тест набора падает (доказательство, что механизм действительно ловит нарушение).
3. Given класс-наследник `TenantScopedRepository`, When вызывается его публичный метод БЕЗ
   аргумента `tenantId`, Then `tsc --noEmit --strict` не компилируется (метод объявлен с
   обязательным, не опциональным параметром) — статическая, не рантайм проверка.
4. Given `assertTenantId(undefined as unknown as TenantId)` (обход типов через `any`/`unknown`,
   негативный сценарий защиты в глубину), When вызов, Then бросается ошибка (не тихий проход) —
   рантайм-рубеж для случаев, когда TypeScript обойдён намеренно/по ошибке.

## Тест-план
Unit (Vitest): `tenant-scoped-repository.spec.ts` (сценарий 4), `tenant-isolation-contract-test-
self-check.spec.ts` (сценарии 1–2, через фикстуру-нарушителя и через корректный мок). Отдельный
интеграционный тест не требуется в ЭТОМ тикете (механизм тестируется на моках/фикстурах; реальное
интеграционное применение — обязанность каждого будущего репозитория, использующего этот
контракт-тест против настоящей БД). Порог покрытия `infrastructure/`/`testing/` ≥ 70%.

## Риски и подводные камни
- `dependency-cruiser`-правило «запрет прямого импорта Drizzle-клиента вне
  `infrastructure/repositories/*`» — НЕ реализуется этим тикетом (владение конфигом — только
  EP-19). Формулировка запроса владельцу EP-19: «добавить правило, запрещающее импорт
  `drizzle-orm` типа `NodePgDatabase`/аналога напрямую в `application/**`/`domain/**` любого
  модуля — уже неявно подразумевается C1 `02-CLEAN-ARCHITECTURE-AND-CODE.md`, здесь фиксируется
  явной статической проверкой». Пока правило не добавлено, единственная защита — типы +
  контракт-тест из этого тикета (частичное, не полное покрытие риска — открытый риск до
  координации с EP-19).
- Модули с ТРАНЗИТИВНЫМ tenant-скоупом (`pharmacies`, `pharmacy_inventory` — через `chain_id`, не
  прямую колонку `tenant_id`) НЕ используют `TenantScopedRepository` в буквальном виде (нет прямого
  `tenant_id` для передачи первым параметром) — для них контракт-тест неприменим дословно; явно
  зафиксировано как ограничение механизма, изоляция транзитивных таблиц проверяется другим способом
  (JOIN-цепочкой, ответственность конкретного модуля, например EP-05 для `pharmacy_inventory`).
