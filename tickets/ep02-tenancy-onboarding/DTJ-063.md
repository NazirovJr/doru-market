## Задача
Первый тикет эпика EP-03 (открывает волну 3, требует готовых `tenant_id`/ролей из EP-02). Без
доменной модели `PharmacyChain`/`PharmacyAccount` онбординг не имеет легитимного, промодерированного
источника аптек, а каталог (EP-04/EP-06) не сможет честно исключать неактивные точки — это прямая
архитектурная предпосылка `04-SCOPE-DECISION-PIVOT.md` R1-2/R1-5/R1-9, закрывающая решение
архитектора D-22.

## Технический контекст
Слой `domain` модуля `apps/api/src/modules/onboarding`. Базовые таблицы `pharmacy_chains`/
`pharmacies` (Группа A `11-database-schema.md`) — ФУНДАМЕНТ, создаётся EP-01 (базовая DDL для всех
последующих модулей, включая catalog/inventory) — этот тикет их НЕ создаёт, только строит
доменную модель поверх уже существующих колонок. Таблицы `pharmacy_verification`/
`onboarding_review_log` (Группа I «Онбординг, верификация») — специфичны для этого модуля,
создаются ЗДЕСЬ целиком (базовые поля из `11-database-schema.md` §«Полный DDL» Группа I + сразу
дополнения `27-module-admin-moderation-onboarding.md` §10.1, т.к. таблица новая — та же логика, что
DTJ-051 для `tenants`). Доменные ошибки — подклассы каталога `10-domain-model.md` §«Доменные
ошибки» (`ParentChainNotActiveError extends BusinessRuleViolationError`,
`AutomaticReactivationForbiddenError extends ForbiddenTransitionError`).

## Что сделать
1. `db/schema/pharmacy-verification.ts` + миграция: таблица `pharmacy_verification` — базовые поля
   (`id`, `pharmacy_id` nullable, `chain_id` nullable, `verification_status`, `checklist_snapshot`
   jsonb, `submitted_at`, `reviewed_by`, `reviewed_at`, `sla_target_at`) + CHECK
   `chk_pharmacy_verification_one_subject` + дополнения §10.1: `review_reason VARCHAR(30) NOT NULL
   DEFAULT 'initial'`, `revoked_at`, `revoked_reason`, `revoked_by`.
2. `db/schema/onboarding-review-log.ts` + та же миграция: таблица `onboarding_review_log`
   (append-only) — `id`, `pharmacy_id`/`chain_id` (ровно одно заполнено, CHECK), `action`
   (varchar(30)), `actor_user_id` (`ON DELETE RESTRICT`), `reason`, `checklist_snapshot`,
   `created_at`. Индексы `ix_onboarding_review_log_pharmacy`/`_chain` (частичные, per
   `11-database-schema.md` §«Индексы»).
3. Отдельная миграция (`-- disable-transaction`, SRS-ADM-078/SRS-DB-009): `ALTER TYPE
   verification_status ADD VALUE 'revoked'`.
4. Отдельная миграция (`-- disable-transaction`): `ALTER TYPE otp_purpose ADD VALUE
   'onboarding_contact'` — расширение перечисления, определённого модулем `auth` (EP-01);
   координация: значение введено ПОВЕРХ существующего `otp_purpose` (`'login'`,
   `'delivery_handover'`), запрос-уведомление владельцу EP-01 о добавлении этого значения (см.
   «Риски»), сама миграция физически применяется этим тикетом, т.к. её потребитель (OTP-верификация
   контактного телефона заявки, DTJ-064) — часть onboarding.
5. `domain/value-objects/onboarding-status.vo.ts`: тип `OnboardingStatus` (объединение значений
   `chain_onboarding_status`/`pharmacy_onboarding_status` — они идентичны по набору значений,
   переиспользуется один TS-тип) + чистая функция `isTransitionAllowed(from, to): boolean`,
   кодирующая граф переходов `draft → pending_review → (changes_requested ↔ pending_review) →
   approved → active → (suspended → pending_review [reactivation] → ...) `, `* → terminated`
   (терминально, без пути назад) — используется ОБОИМИ сущностями ниже.
6. `domain/pharmacy-chain.entity.ts`: `PharmacyChain` — поля из `pharmacy_chains` (не дублировать
   схему БД дословно — только поля, нужные домену: `id`, `legalEntityName`, `tinInn`, `status`,
   `isWhitelabelRequested`, `tenantId?`). Методы: `PharmacyChain.submit(application)`,
   `chain.approve(actor, checklist)`, `chain.requestChanges(actor, reason)`, `chain.reject(actor,
   reason)`, `chain.terminate(actor, reason)` — каждый вызывает `isTransitionAllowed`, бросает
   `InvalidOnboardingTransitionError` (уже в каталоге `10-domain-model.md`) при недопустимом
   переходе.
7. `domain/pharmacy-account.entity.ts`: `PharmacyAccount` — поля из `pharmacies` + инварианты:
   - SRS-DOM-047: `chainId` обязателен всегда (конструктор требует непустое значение — application
     создаёт `PharmacyChain` заранее для соло-заявки, домен просто не допускает `null`).
   - SRS-DOM-048: `pharmacyAccount.activate()` принимает `parentChainStatus: OnboardingStatus`
     параметром (не читает сам — порт `PharmacyChainStatusPort`, реализуемый application-слоем
     ЭТОГО ЖЕ модуля, простая внутримодульная зависимость, не межмодульная) — given
     `parentChainStatus ∉ {'approved', 'active'}`, бросает `ParentChainNotActiveError`.
   - SRS-DOM-049: `pharmacyAccount.updateAddress(newAddress)` на `status === 'active'` переводит
     объект в `'pending_review'` (не тихий апдейт полей).
   - SRS-DOM-050: `pharmacyAccount.suspend(reason, actor)` — устанавливает `status = 'suspended'`,
     `suspensionReason = reason`; `pharmacyAccount.requestReactivation()` разрешён ТОЛЬКО из
     `'suspended'`, переводит в `'pending_review'` с намерением «reactivation» (флаг возвращается в
     application, где формируется `review_reason`, домен сам не знает о колонке БД); отдельный
     метод `activateProgrammatically()` НЕ существует — попытка вызвать `activate()` напрямую из
     `'suspended'` без прохождения `'pending_review'` бросает `AutomaticReactivationForbiddenError`.
   - SRS-DOM-051: НЕ реализуется в этом тикете (`pharmacy_api_keys` — дочерняя сущность вне зоны
     онбординга, зафиксировано как явный пробел зоны ответственности в «Рисках»).
8. Доменные ошибки: `ParentChainNotActiveError` (`code = 'PARENT_CHAIN_NOT_ACTIVE'`),
   `AutomaticReactivationForbiddenError` (`code = 'INVALID_STATE_TRANSITION'`),
   `ChainApplicationAlreadyExistsError` (`code = 'CHAIN_APPLICATION_ALREADY_EXISTS'`, используется
   DTJ-064), `AlreadyReviewedError` (`code = 'ALREADY_REVIEWED'`, используется DTJ-068) — оба новых
   кода добавляются в `packages/contracts/src/errors.ts` каталог (одна строка на код, файл владения
   EP-01/общий — координация по аналогии с правилом «одна строка экспорта», не переписывание
   каталога целиком).
9. `onboarding.module.ts` + `index.ts` — пустой скелет модуля, публичный экспорт ТОЛЬКО типов и
   ошибок на этом шаге (Facade `OnboardingFacade` — DTJ-070).

## Критерии приёмки
1. Given `PharmacyAccount` с `status = 'pending_review'`, When `activate(parentChainStatus:
   'pending_review')`, Then `ParentChainNotActiveError`, статус объекта не изменился.
2. Given активная аптека (`status = 'active'`), When `updateAddress(newAddress)`, Then `status`
   переходит в `'pending_review'`, не остаётся `'active'`.
3. Given аптека в `'suspended'` (`reason = 'license_expired'`), When прямой вызов `activate()` (не
   через `requestReactivation()` → одобрение), Then `AutomaticReactivationForbiddenError`.
4. Given `PharmacyChain.status = 'terminated'`, When любой вызов перехода (`approve`/
   `requestChanges`/`reject`), Then `InvalidOnboardingTransitionError` (терминальное состояние без
   пути назад) — негативный сценарий.
5. Given чистая БД, When применение всех миграций этого тикета, Then `information_schema` содержит
   обе новые таблицы со всеми колонками §10.1, а `pg_enum` содержит значения `'revoked'`
   (`verification_status`) и `'onboarding_contact'` (`otp_purpose`).

## Риски и подводные камни
- `otp_purpose` — enum, введённый и логически принадлежащий модулю `auth` (EP-01); добавление
  значения `ALTER TYPE ... ADD VALUE` здесь — ДОПОЛНЕНИЕ существующего типа, не создание нового,
  формально не требует владения файлом (это не редактирование `db/schema` EP-01, а отдельный SQL-
  файл миграции нового значения), но по духу правила «Пересекающееся владение» `00-EPICS.md`
  требует уведомления владельца EP-01 перед мержем — сделать явно, не молча.
- `27-module-admin-moderation-onboarding.md` §2.1 ссылается на «§10.1» как источник дополнения
  `otp_purpose='onboarding_contact'`, но фактический текст §10.1 документа этот `ALTER TYPE` НЕ
  перечисляет явно (только `notification_channel`, `audit_action_category` добавления) — это
  ПРОБЕЛ/несогласованность самой спецификации, обнаруженная при подготовке тикетов; реализация
  здесь следует духу требования (переиспользование `OtpCode` для верификации контактного телефона
  заявки нужно логически), но формулировка enum-добавления — решение Tech Lead этого эпика при
  отсутствии точной директивы документа, зафиксировать как расхождение для ревью архитектора.
- `pharmacy_api_keys` (Группа I, D-11) сознательно НЕ создаётся здесь — SRS-DOM-051 упоминает её
  как дочернюю `PharmacyAccount`, но фактическое использование (1С-доступ) — зона EP-05/EP-12, не
  онбординга; таблица заводится тем эпиком, который первым в ней нуждается.
- Несогласованность HTTP-кода `PharmacySuspendedError` между `10-domain-model.md` (аннотация «→ 403
  PHARMACY_SUSPENDED» при родительской категории `BusinessRuleViolationError → 422») и
  `27-module-admin-moderation-onboarding.md` SRS-ADM-015 (явно требует `422 PHARMACY_SUSPENDED`) —
  этот тикет не реализует сам код (появится в DTJ-070/чекауте EP-09), но фиксирует расхождение
  здесь, у источника доменной ошибки, чтобы DTJ-070 не изобретал решение заново: используется `422`
  (следует родительской категории `BusinessRuleViolationError` и явной формулировке SRS-ADM-015,
  более специфичного модульного документа), несоответствие — вопрос к архитектору на ревью.
- Файл `apps/api/src/modules/onboarding/onboarding.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
