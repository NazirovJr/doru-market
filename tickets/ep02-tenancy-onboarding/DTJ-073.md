## Задача
Единственный автоматический (без участия человека) переход статуса во всём модуле онбординга —
истечение лицензии обязано приостанавливать аптеку системно, т.к. дистанционная продажа лекарств по
просроченной лицензии — не операционная небрежность, а нарушение закона РТ. Проактивный список
«истекающие лицензии» даёт оператору шанс предупредить до авто-приостановки.

## Технический контекст
Слой `infrastructure` (BullMQ repeatable job, `apps/worker`) + `application` (use case списка для
`apps/admin`). Job — единственный потребитель `SuspendPharmacyUseCase` (DTJ-071) с `actor = SYSTEM`
(служебный `user_id`, определённый ЕДИНООБРАЗНО для всей платформы — если общий «системный
пользователь» ещё не заведён EP-01/инфраструктурой на момент реализации, этот тикет заводит
временную seed-запись `users(id=<фиксированный UUID>, role=?, ...)`-константу
`SYSTEM_ACTOR_USER_ID`, координируя с EP-01 при обнаружении дублирования).

## Что сделать
1. `apps/worker/src/jobs/license-expiry-check/license-expiry-check.job.ts`:
   `LicenseExpiryCheckJob` (BullMQ repeatable, cron `0 6 * * *` таймзона Asia/Dushanbe,
   `01-TECH-BASELINE.md`/`@nestjs/schedule` или чистый BullMQ repeatable — на усмотрение, следуя
   существующей конвенции `apps/worker`, если она уже установлена другим модулем к этому моменту):
   - Сканирует `pharmacies.license_expiry_date` WHERE `status = 'active'` (переиспользует индекс
     `ix_pharmacies_license_expiry`, уже определённый `11-database-schema.md` §«Индексы»).
   - Для каждой записи вычисляет `daysRemaining = licenseExpiryDate - today`.
   - `daysRemaining ∈ {30, 14, 3}`: публикует `LicenseExpiringSoonEvent` — ИДЕМПОТЕНТНО, РОВНО один
     раз на пару `(pharmacyId, daysRemaining)` (защита от повторной публикации при повторных
     запусках job в один день — таблица дедупликации/уникальный индекс на
     `(pharmacy_id, days_remaining, date_trunc('day', occurred_at))`, простейшая реализация — проверка
     существования аналогичной записи в `outbox`/отдельной небольшой таблице `license_expiry_notice_
     log(pharmacy_id, days_remaining, notified_on DATE, UNIQUE(pharmacy_id, days_remaining,
     notified_on))` — **[ДОПОЛНЕНИЕ]** новая маленькая таблица, добавляется миграцией этого тикета).
   - `daysRemaining <= 0` (истекла): вызывает `SuspendPharmacyUseCase.execute({ pharmacyId, actorId:
     SYSTEM_ACTOR_USER_ID, reason: 'license_expired' })` — БЕЗ участия человека, публикует
     `LicenseExpiredAutoSuspendEvent`.
   - Обработка одной аптеки не должна прерывать обработку остальных при ошибке (try/catch на
     каждую итерацию, суммарный отчёт об ошибках в лог job'ы — паттерн, аналогичный «одна плохая
     строка не роняет весь батч», REQ-SYNC-9, применённый здесь по аналогии).
2. `application/use-cases/list-expiring-licenses.use-case.ts`:
   `ListExpiringLicensesUseCase.execute({ withinDays: number, cursor?, limit })` — `GET`-style запрос,
   `WHERE license_expiry_date <= today + withinDays AND status = 'active'`, отсортировано
   `licenseExpiryDate: asc`.
3. `presentation/controllers/pharmacy-accounts-admin.controller.ts`: `GET
   /api/v1/pharmacy-accounts?filter[licenseExpiryDate][lte]=<+30d>` (`@Roles('super_admin')`) —
   параметр фильтра по конвенции §1.2 `12-api-conventions...md` (уточнить точный формат
   query-параметра по общей конвенции фильтрации, если она уже установлена EP-01 к моменту
   реализации — не изобретать отдельный формат для этого эндпоинта).

## Критерии приёмки
1. Given аптека с `license_expiry_date = today + 30`, `status='active'`, When job выполняется, Then
   `LicenseExpiringSoonEvent` опубликовано РОВНО один раз для пары `(pharmacyId, 30)`.
2. Given job выполняется ПОВТОРНО в тот же день (например, ручной перезапуск), When та же аптека
   сканируется снова, Then событие НЕ публикуется повторно (дедупликация сработала).
3. Given `license_expiry_date = today - 1` (истекла вчера), When job выполняется, Then
   `SuspendPharmacyUseCase` вызван с `reason='license_expired'`, `actorId=SYSTEM_ACTOR_USER_ID`,
   аптека переходит в `status='suspended'`.
4. Given одна из 10 обрабатываемых аптек вызывает ошибку (например, поле повреждено/репозиторий
   бросает исключение), When job выполняется, Then остальные 9 аптек обработаны штатно, ошибка по
   одной записи залогирована, job не падает целиком — негативный сценарий отказоустойчивости.
5. Given `GET /pharmacy-accounts?filter[licenseExpiryDate][lte]=<+30d>`, When запрос от
   `super_admin`, Then возвращены только аптеки с `license_expiry_date` в пределах 30 дней,
   отсортированные по возрастанию даты.

## Риски и подводные камни
- `license_expiry_notice_log` — таблица, введённая ЭТИМ тикетом как минимальный механизм
  дедупликации; документ `27-module-admin-moderation-onboarding.md` формулирует требование
  идемпотентности («ровно один раз на пару») но НЕ даёт готовой DDL для неё — решение Tech Lead
  здесь; альтернатива (проверка существования соответствующего `outbox`-события за сегодня) тоже
  возможна, если общий `outbox`-механизм EP-01 к моменту реализации предоставляет удобный запрос по
  типу+payload — выбор конкретной реализации не блокирует тикет, главное — гарантия сценария 2.
- Единый `SYSTEM_ACTOR_USER_ID` — если аналогичная потребность («системный актор» для
  автоматических действий) уже возникла в ДРУГОМ модуле раньше (например, `inventory`/1С-приём,
  EP-05), переиспользовать существующую константу вместо создания второй параллельной — проверить
  перед реализацией.
- Таймзона `Asia/Dushanbe` для cron-расписания — координация с общей конфигурацией
  `@nestjs/schedule`/BullMQ repeatable в `apps/worker` (владение — вероятно EP-01/общая
  инфраструктура очередей), не хардкодить таймзону локально в этом файле без проверки, что остальные
  job'ы платформы используют ту же конвенцию.
