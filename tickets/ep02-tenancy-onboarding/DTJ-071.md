## Задача
Приостановка аптеки — единственное операционное действие, которое напрямую затрагивает уже
существующие заказы клиентов (SRS-DOM-161: судьба `pending_payment`/`confirmed`-заказов зависит от
причины приостановки). Без явного механизма принудительной отмены незавершённые заказы
мошеннической/утратившей лицензию аптеки зависли бы неопределённо, деньги клиента остались бы
удержаны без исхода.

## Технический контекст
Слой `application`. `orders`/`payments` (EP-09/EP-10) ещё не существуют на волне 3 (этот эпик) — по
той же схеме, что DTJ-057/DTJ-062 в EP-02, здесь объявляется УЗКИЙ порт
`OrdersCancellationPort` (application/ports ЭТОГО модуля) с ВРЕМЕННОЙ null-реализацией
(`NullOrdersCancellationAdapter`, возвращает пустой список отменённых заказов и не бросает
исключение — приложение собирается и работает ДО готовности EP-10, аналог `NullSearchProvider` из
DTJ-180 EP-06) — реальная реализация подключается EP-10 при достижении своей волны, ЭТОТ тикет
только фиксирует контракт и DI-переключатель.

## Что сделать
1. `application/ports/orders-cancellation.port.ts`: `OrdersCancellationPort` — `forceCancelIncomplete
   (pharmacyId: string, reason: string): Promise<{ cancelledOrderIds: string[] }>` (доменная
   логика «какие статусы считаются незавершёнными», рефанд через `PaymentProvider` — целиком
   ответственность `orders`/`payments`, этот порт лишь ОРКЕСТРИРУЕТ вызов извне).
2. `infrastructure/adapters/null-orders-cancellation.adapter.ts`: `NullOrdersCancellationAdapter
   implements OrdersCancellationPort` — возвращает `{ cancelledOrderIds: [] }`, логирует
   `pino.warn('orders_cancellation_not_wired')` — временная связка, переключаемая на реальный
   адаптер модулем `orders` при готовности (`TODO(EP-10)` в коде DI-провайдера).
3. `application/use-cases/suspend-pharmacy.use-case.ts`: `SuspendPharmacyUseCase.execute({
   pharmacyId, actorId, reason: PharmacySuspensionReason, notes? })` (`@Roles('super_admin')` на
   уровне контроллера, use case сам роль не проверяет):
   - `pharmacyAccount.suspend(reason, actor)` (домен DTJ-063).
   - Given `reason ∈ {'fraud_or_safety', 'license_revoked'}`, Then результат use case включает
     `requiresForceCancelAction: true` (флаг, читаемый контроллером/фронтендом — САМ вызов
     `forceCancelIncomplete` НЕ выполняется автоматически внутри `suspend()`, это ОТДЕЛЬНОЕ явное
     действие оператора, SRS-ADM-016).
   - Журналирует в `onboarding_review_log` (`action='suspend'`) — переиспользует репозиторий
     DTJ-068.
4. `application/use-cases/force-cancel-incomplete-orders.use-case.ts`:
   `ForceCancelIncompleteOrdersUseCase.execute({ pharmacyId, actorId, reason })`:
   - Given `pharmacyAccount.status !== 'suspended'`, Then отклонено (нельзя force-cancel для аптеки,
     которая не приостановлена — доменная защита, использует существующую доменную ошибку
     `BusinessRuleViolationError`-семейства).
   - `ordersCancellationPort.forceCancelIncomplete(pharmacyId, reason)` — идемпотентно (заголовок
     `Idempotency-Key` ОБЯЗАТЕЛЕН на уровне контроллера, SRS-ADM-016 явно требует — повторный вызов
     не должен рефандить дважды; сама идемпотентность реализуется общим механизмом EP-01, use case
     лишь помечен `@RequireIdempotencyKey()`).
   - Журналирует результат (`action` — новое значение, например `'force_cancel_orders'`, в
     `onboarding_review_log`, включая список `cancelledOrderIds` в `reason`/отдельное поле метаданных
     — уточнить формат при реализации, `onboarding_review_log.reason` — `TEXT`, можно сериализовать
     список компактно).
5. `presentation/controllers/pharmacy-suspension.controller.ts`: `POST
   /api/v1/pharmacy-accounts/:id/suspend` (`@Roles('super_admin')`, permission
   `pharmacy-accounts:suspend`) и `POST /api/v1/pharmacy-accounts/:id/force-cancel-incomplete-orders`
   (`@RequireIdempotencyKey()`).

## Критерии приёмки
1. Given активная аптека, When `POST /pharmacy-accounts/:id/suspend { reason: 'voluntary_pause' }`,
   Then `status='suspended'`, ответ НЕ содержит `requiresForceCancelAction: true` (не входит в
   список причин, требующих принудительной отмены).
2. Given та же операция с `reason: 'fraud_or_safety'`, When вызов, Then ответ содержит
   `requiresForceCancelAction: true`.
3. Given аптека приостановлена с `reason='fraud_or_safety'`, When `POST .../force-cancel-incomplete-
   orders { reason: '...' }` с `Idempotency-Key`, Then `ordersCancellationPort.forceCancelIncomplete`
   вызван РОВНО один раз, журнал содержит запись.
4. Given аптека НЕ приостановлена (`status='active'`), When `POST .../force-cancel-incomplete-
   orders`, Then отклонено доменной ошибкой — негативный сценарий.
5. Given запрос без `Idempotency-Key`, When `POST .../force-cancel-incomplete-orders`, Then `400
   IDEMPOTENCY_KEY_REQUIRED`.

  релизом R1, что `NullOrdersCancellationAdapter` заменена на реальную (часть Definition of Done
  СБОРКИ релиза, не этого тикета — фиксируется здесь как явный сигнал для интеграционного ревью).
- Формат хранения `cancelledOrderIds` в `onboarding_review_log.reason` (TEXT) — временное упрощение;
  если позже понадобится структурированный запрос по списку отменённых заказов, потребуется отдельное
  поле/таблица — не блокирует этот тикет, отмечено для будущего рефакторинга.
