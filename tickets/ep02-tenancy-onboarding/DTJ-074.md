## Задача
Единственный легитимный путь для приостановленной аптеки вернуться к работе — через полноценный
повторный чек-лист `super_admin`, НИКОГДА автоматически, независимо от причины приостановки. Без
этого use case аптека, приостановленная за `voluntary_pause` (добровольная пауза, не нарушение),
не имеет способа вернуться, кроме ручного вмешательства в БД — недопустимо для продакшена.

## Технический контекст
Слой `application`. Домен уже гарантирует терминальную защиту (`AutomaticReactivationForbiddenError`
при прямом `activate()` из `suspended`, DTJ-063) — этот use case реализует ЕДИНСТВЕННЫЙ разрешённый
путь: перевод в `pending_review` с `review_reason='reactivation'`, после чего заявка проходит ТОТ ЖЕ
конвейер `approve`/`reject` (DTJ-068), что и первичная заявка.

## Что сделать
1. `application/use-cases/request-reactivation.use-case.ts`: `RequestReactivationUseCase.execute({
   pharmacyId, actorId })`:
   - Политика авторизации: `actor.role === 'pharmacy_admin'` своей аптеки (permission — по аналогии
     с DTJ-069, `pharmacy-accounts:update-address`-подобная, если отдельная строка
     `pharmacy-accounts:request-reactivation` не заведена матрицей — уточнить на ревью; в отсутствие
     явной записи в `12-api-conventions...md` §4.1 для этого конкретного действия, разрешить его
     той же ролью, что доступ к своей аптеке в целом, задокументировав как явное дополнение матрицы).
   - Given `pharmacyAccount.status !== 'suspended'`, Then отклонено (доменная ошибка перехода —
     нельзя запросить реактивацию активной/ещё не одобренной точки).
   - `pharmacyAccount.requestReactivation()` (домен DTJ-063, переводит в `'pending_review'`).
   - Создаёт запись `pharmacy_verification(pharmacy_id, verification_status='pending_review',
     review_reason='reactivation', submitted_at=now(), sla_target_at=now()+2 рабочих дня)` —
     переиспользует расчёт `addBusinessDays` из DTJ-066 (импорт общей утилиты этого же модуля, не
     дублирование).
   - Сохраняет, публикует событие (переиспользует форму `PharmacyAccountAddressChangedEvent`-подобную
     или новую `PharmacyReactivationRequestedEvent` — небольшое расхождение семантики, лучше
     отдельный DTO, не переиспользовать чужое имя события ради экономии файла).

## Критерии приёмки
1. Given аптека `status='suspended'`, `suspension_reason='voluntary_pause'`, When
   `RequestReactivationUseCase.execute({ pharmacyId, actorId })` от её `pharmacy_admin`, Then
   `status='pending_review'`, создана `pharmacy_verification` с `review_reason='reactivation'`.
2. Given та же заявка теперь в очереди верификации (DTJ-067), When `super_admin` вызывает `approve`
   (DTJ-068), Then заявка проходит ТОТ ЖЕ путь, что первичная — `pending_review → approved → active`
   (переиспользование существующего конвейера подтверждено, не отдельная ветка кода).
3. Given аптека `status='active'` (не приостановлена), When вызов `RequestReactivationUseCase`, Then
   отклонено доменной ошибкой — негативный сценарий (реактивация неприменима к уже активной точке).
4. Given попытка программно вызвать `pharmacyAccount.activate()` напрямую из `suspended` В ОБХОД
   этого use case (гипотетический тест на архитектурную гарантию, не через HTTP), When вызов, Then
   `AutomaticReactivationForbiddenError` — подтверждение, что домен (DTJ-063) действительно
   исключает прямой путь, даже если БЫ этот use case содержал баг.

## Риски и подводные камни
- Отсутствие явной permission-строки для «запросить реактивацию» в прочитанной версии матрицы
  `12-api-conventions...md` §4.1 — трактуется расширительно (доступ на уровне «своя аптека», как
  `update-address`), зафиксировано как отклонение/дополнение матрицы для последующего ревью
  архитектора, не блокирует реализацию.
- Этот тикет НЕ создаёт отдельный файл контроллера намеренно (см. DoD) — решение, куда именно
  добавить маршрут, оставлено на усмотрение исполнителя по факту существующей структуры файлов на
  момент реализации (после мержа DTJ-065/068/071).
