## Задача
Charter §5 и D-01 требуют, чтобы нейтральный тенант DoruTJ проходил через ТОТ ЖЕ движок брендинга,
что и White-Label клиент — иначе e2e-тест смены `BRAND_NAME` (критерий приёмки R1 №6) невозможен, а
White-Label-архитектура осталась бы теоретической. Этот тикет — серверная часть движка: без него
`GET /tenant/branding` (обязательный по SRS-API-059) не существует, и фронтенд (DTJ-060) не может
применить брендинг в рантайме.

## Технический контекст
`packages/contracts/src/tenancy.ts` уже частично начат в DTJ-057 (`ProvisionTenantRequestSchema`,
`NEUTRAL_FALLBACK_PALETTE`) — этот тикет ДОПОЛНЯЕТ тот же файл (не создаёт заново, файл уже
существует к этому моменту по порядку волны, `depends_on` гарантирует последовательность). Слой
`application` — два use case, `presentation` — контроллер с двумя маршрутами
(`PUT /api/v1/admin/tenants/:id/branding`, `GET /api/v1/tenant/branding`). `GET` — публичный
(`@Public()`, DTJ-054), но тенант всё равно резолвлен обычным алгоритмом (SRS-TEN-008) — отвечает
брендингом РЕЗОЛВЛЕННОГО тенанта запроса, `:id` в пути не требуется для `GET`.

## Что сделать
1. `packages/contracts/src/tenancy.ts`: добавить `BrandPaletteSchema` (zod) — allowlist ПО
   КАЖДОМУ известному CSS-токену (SRS-TEN-013): `--brand-primary`, `--brand-primary-hover`,
   `--brand-secondary`, `--brand-accent`, `--brand-bg`, `--brand-surface`, `--brand-text`,
   `--brand-text-muted`, `--brand-border`, `--brand-success`, `--brand-danger`, `--brand-warning` —
   каждый `z.string().regex(/^#[0-9a-fA-F]{6}$/)`; `--brand-radius` — `z.string().regex(/^\d{1,2}px$/)`;
   `--brand-font-family` — `z.enum([...])` из фиксированного списка ≤10 Google Fonts стеков +
   `'system-ui, sans-serif'` (список согласовать с EP-18 при готовности `packages/ui`, на этом шаге —
   минимум `['system-ui, sans-serif']` с TODO на расширение списка). Схема — `z.object({...}).strict()`
   (лишние ключи отклоняются, не игнорируются молча).
2. `UpdateBrandingRequestSchema`: `{ brandName: z.string().min(1).max(255), brandPalette:
   BrandPaletteSchema.partial(), logoUrl: z.string().url().optional() }`.
3. `application/use-cases/update-branding.use-case.ts`: `UpdateBrandingUseCase.execute({ tenantId,
   brandName, brandPalette, logoUrl })` — читает `TenantSettings` через репозиторий (DTJ-052),
   вызывает `tenant.updateBranding(palette, logoRef)` (доменный метод из DTJ-050 — валидация формата
   УЖЕ прошла на границе контракта, домен принимает провалидированные значения), сохраняет,
   публикует `TenantBrandingUpdatedEvent` (форма события из DTJ-053) — обработчик инвалидации кэша
   подписан отдельно (DTJ-053), этот use case только публикует.
4. `application/use-cases/get-branding.use-case.ts`: `GetBrandingUseCase.execute({ tenantId })` —
   читает `TenantSettings`; given `brandPalette` пустой объект (`{}`, только что провизионированный
   тенант, SRS-TEN-038), Then возвращает `NEUTRAL_FALLBACK_PALETTE` (из DTJ-057) вместо пустого
   объекта — НЕ палитру нейтрального тенанта DoruTJ по умолчанию (чужой бренд не должен
   «просвечивать»), а именно нейтрально-серую заглушку.
5. `presentation/controllers/tenancy-branding.controller.ts`:
   - `PUT /api/v1/admin/tenants/:id/branding` — `@Roles('pharmacy_admin', 'super_admin')` +
     application-политика (`02` §3.4: `pharmacy_admin` разрешён ТОЛЬКО для тенанта своей же сети,
     `super_admin` — для любого; вызывающая проверка — `BrandingAuthorizationPolicy.canManage(actor,
     tenantId)`, не guard). Невалидное значение → `400 VALIDATION_ERROR`, `details.field` — конкретный
     CSS-токен (из ошибки Zod, замаппленной контроллером).
   - `GET /api/v1/tenant/branding` — `@Public()`, `Cache-Control: public, max-age=300`, `ETag`
     формируется как хэш (`sha256`) от сериализованного ответа (SRS-API-059) — поддержка
     `If-None-Match` → `304` без тела при совпадении.
6. Гонка двух одновременных `PUT /branding` (SRS-TEN-040) — НЕ обрабатывается optimistic
   concurrency намеренно (последний committed `UPDATE` побеждает) — явный комментарий в use case,
   почему это осознанное решение (брендинг не финансовая операция).

## Критерии приёмки
1. Given `PUT /admin/tenants/:id/branding` с `--brand-primary: "url(javascript:alert(1))"`, When
   запрос, Then `400 VALIDATION_ERROR`, `details.field='--brand-primary'`, значение НЕ сохранено в БД.
2. Given `--brand-font-family: "MyCustomHackerFont, sans-serif"` (вне allowlist), When запрос, Then
   `400 VALIDATION_ERROR`.
3. Given только что провизионированный тенант (`brand_palette = {}`), When `GET /tenant/branding`,
   Then возвращается `NEUTRAL_FALLBACK_PALETTE`, не пустой объект и не палитра другого тенанта.
4. Given `pharmacy_admin` тенанта B пытается `PUT /admin/tenants/{A}/branding` (чужой тенант), When
   запрос, Then отклонено политикой авторизации (`403`) — негативный сценарий, независимый от
   `TenantScopeGuard` (это тот же тенант с точки зрения резолвинга запроса, но чужой `:id` в пути —
   политика уровня `application`, не guard).
5. Given `TenantBrandingUpdatedEvent` опубликовано для тенанта X, When повторный `GET
   /tenant/branding` с устаревшим `If-None-Match`, Then возвращён `200` с новым `ETag`, не `304`.

## Риски и подводные камни
- `BrandingAuthorizationPolicy` — новый класс, которого не было в предыдущих тикетах эпика; следует
  паттерну `application/policies/*.policy.ts` (SRS-API-036) — если к моменту реализации в проекте уже
  сложилась общая база `Policy`-классов (EP-01), наследовать её, иначе — самостоятельный класс с тем
  же контрактом, унификация — отдельный рефакторинг-тикет при необходимости, не блокирует этот.
- Список из ≤10 Google Fonts стеков — ASSUMPTION, требующий согласования с EP-18/дизайном; временный
  минимальный список (`system-ui, sans-serif`) не блокирует прод-функциональность (шрифт всегда есть
  фолбэк), но требует последующего тикета на расширение — зафиксировать как открытый пункт, не
  заводить отдельный тикет сейчас (вне диапазона DTJ-050..089, зона EP-02/EP-03).
- D-27: `packages/contracts/src/tenancy.ts` делится с `DTJ-057` в одной подволне — `DTJ-057`
  правит файл первым, этот тикет получил `depends_on: [..., DTJ-057]`, начинать правку файла
  только после его завершения (перечитать перед правкой).
