## Задача
Модуль `onboarding` — единственный источник истины по статусу аптек/сетей, но по правилу проекта
(`02` §1.2) никакой другой модуль не может импортировать его `domain`/`application` напрямую.
Этот тикет — публичный контракт, через который EP-04/EP-06 (видимость в поиске уже реализуют
условие через прямой JOIN, SRS-CAT-010, не через этот фасад — см. «Технический контекст»), EP-09
(чекаут — 422 PHARMACY_SUSPENDED), EP-02 (провизионинг тенанта, DTJ-057) получают статус БЕЗ
нарушения границ модуля.

## Технический контекст
`OnboardingFacade` — публичный сервис, экспортируемый `modules/onboarding/index.ts` (Facade-паттерн,
`02` §1.2). Важное уточнение из `20-module-catalog-search.md` SRS-CAT-010: видимость медикамента в
ПОИСКЕ реализована ПРЯМЫМ JOIN на `pharmacy_chains` внутри `PostgresSearchProvider`, НЕ вызовом этого
фасада (осознанное решение модуля `catalog` — избежать N+1 вызовов фасада на каждый результат
поиска) — этот тикет НЕ противоречит тому решению, а покрывает ДРУГИЕ два потребителя: (1)
чекаут/orders (единичная проверка на заказ, не массовая — фасад уместен), (2) внутримодульный
`PharmacyChainStatusPort`, используемый ДОМЕНОМ этого же модуля в `PharmacyAccount.activate()`
(SRS-DOM-048) — это НЕ межмодульная зависимость, а внутримодульный порт, реализация которого просто
читает `PharmacyChainRepository` этого же модуля напрямую (без фасада, т.к. оба — часть одного
bounded context).

## Что сделать
1. `application/ports/pharmacy-chain-status.port.ts`: `PharmacyChainStatusPort` — `getStatus(chainId):
   Promise<OnboardingStatus | null>` — используется ВНУТРИ модуля доменом (`PharmacyAccount.
   activate()` принимает результат этого порта как параметр, см. DTJ-063 п.7).
2. `infrastructure/adapters/pharmacy-chain-status.adapter.ts`: `PharmacyChainStatusAdapter
   implements PharmacyChainStatusPort` — тонкая обёртка над `PharmacyChainRepository.findById(chainId)
   .then(chain => chain?.status ?? null)`.
3. `onboarding.facade.ts`: `OnboardingFacade` — публичный класс с методами:
   - `isPharmacyActive(pharmacyId: string): Promise<boolean>` — given `PharmacyAccount.status ===
     'active'` И `parentChain.status ∈ {'approved','active'}` (условие СИММЕТРИЧНО SRS-CAT-010, но
     переиспользуется здесь для checkout-проверки, не поиска), Then `true`.
   - `getPharmacySuspensionReason(pharmacyId): Promise<PharmacySuspensionReason | null>` — для
     формирования подробного сообщения об ошибке потребителем (например, `orders` может отличить
     «ещё не одобрена» от «приостановлена за мошенничество» в логах/аудите, хотя клиенту всегда
     возвращается один и тот же код `PHARMACY_SUSPENDED`, SRS-ADM-015).
   - `getChainEligibilityForWhitelabel(chainId): Promise<{ status: OnboardingStatus;
     isWhitelabelRequested: boolean } | null>` — СИГНАТУРА ТОЧНО СООТВЕТСТВУЕТ ожиданию EP-02
     DTJ-057 (см. тот тикет, «Технический контекст») — потребляется через
     `ChainEligibilityPort`-адаптер модуля `tenancy`.
4. `index.ts`: экспортирует `OnboardingFacade` (класс/интерфейс), `PharmacySuspensionReason`-тип,
   доменные ошибки из DTJ-063 (`ParentChainNotActiveError` и др., если их код используется вызывающей
   стороной для маппинга), НЕ экспортирует ничего из `domain/`/`infrastructure/` напрямую.
5. Given `pharmacyId`/`chainId` не найден, Then `isPharmacyActive` возвращает `false` (не бросает
   исключение — «не существует» и «не активна» эквивалентны с точки зрения потребителя-чекаута,
   SRS-ADM-015 требует `422` в обоих случаях одинаково).

## Критерии приёмки
1. Given `pharmacies.status='active'`, `pharmacy_chains.status='active'`, When
   `OnboardingFacade.isPharmacyActive(id)`, Then `true`.
2. Given `pharmacies.status='approved'` (сама точка одобрена, но сеть ещё `pending_review` — не
   входит в допустимый набор родителя), When `isPharmacyActive(id)`, Then `false` — прямое следствие
   SRS-ADM-013 (аптека `approved` не видна и не заказываема, пока полностью не `active`).
3. Given `pharmacies.status='suspended'`, `suspension_reason='fraud_or_safety'`, When
   `getPharmacySuspensionReason(id)`, Then возвращается `'fraud_or_safety'`.
4. Given несуществующий `pharmacyId`, When `isPharmacyActive(id)`, Then `false` (не исключение) —
   негативный сценарий.
5. Given сеть `status='active'`, `is_whitelabel_requested=true`, When
   `getChainEligibilityForWhitelabel(chainId)`, Then возвращается `{ status: 'active',
   isWhitelabelRequested: true }` — контракт, потребляемый DTJ-057.

## Риски и подводные камни
- Это тикет с САМОЙ высокой межмодульной видимостью в эпике — любое изменение сигнатуры
  `OnboardingFacade` после мержа DTJ-057/будущих потребителей (EP-09 чекаут) требует координации с
  этими модулями; рекомендация — не менять публичные сигнатуры без явного обсуждения, даже в рамках
  той же кодовой базы одного тимлида (будущие волны EP-09/EP-10 будут писаться другими
  разработчиками, читающими только этот файл).
- `isPharmacyActive`/`getPharmacySuspensionReason` дублируют по смыслу условие SRS-CAT-010, уже
  реализованное ПРЯМЫМ JOIN в `catalog` (EP-06) — намеренное дублирование логики между двумя
  местами (SQL JOIN vs фасад) явно обосновано в «Техническом контексте»; если оба места разойдутся
  при будущих изменениях доменной модели (например, появится новый онбординг-статус), рассинхрон
  — известный риск, смягчается тем, что оба места ссылаются на один и тот же исходный SRS
  (SRS-ADM-013/SRS-CAT-010 дословно зеркалируют друг друга по требованию документа).
- Файл `apps/api/src/modules/onboarding/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
