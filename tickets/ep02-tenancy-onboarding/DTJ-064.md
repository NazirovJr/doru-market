## Задача
Первая точка входа онбординга — публичная форма заявки сети (REQ-ONBOARD-3/4), без JWT. Это
единственный способ, которым аптечная сеть попадает в систему; без него весь дальнейший конвейер
(верификация, провизионинг White-Label тенанта DTJ-057) не имеет источника данных.

## Технический контекст
Слой `application` модуля `onboarding`. Публичный контроллер — `@Public()` (декоратор из DTJ-054,
EP-02, публичный экспорт `@/modules/tenancy`). `OtpCode` (VO, `purpose` параметризован) — уже
существующая инфраструктура EP-01 (`modules/auth`); этот тикет ПЕРЕИСПОЛЬЗУЕТ существующий
`OtpGeneratorPort`/`OtpRepository` через их публичный барабанный экспорт `@/modules/auth`, не
дублирует OTP-механику — только новое значение `purpose = 'onboarding_contact'` (введено миграцией
DTJ-063).

## Что сделать
1. `packages/contracts/src/onboarding.ts`: `SubmitChainApplicationRequestSchema` (zod) —
   `legalEntityName`, `tinInn` (формат ИНН РТ — уточнить паттерн у `10-domain-model.md`/существующего

   ТРЕБУЕТ (через `.superRefine`) `legalAddress` и (после загрузки, DTJ-065)
   `registrationCertificateUrl` непустыми — на уровне контракта, не только БД.
2. `infrastructure/repositories/pharmacy-chain.repository.ts`: `PharmacyChainRepository` — методы
   `findByTinInn(tinInn)`, `save(chain)` — базовая инфраструктура для домена DTJ-063 (таблица
   `pharmacy_chains` уже существует из фундамента EP-01, репозиторий здесь пишется впервые, т.к.
   первый потребитель — этот use case).
3. `application/use-cases/submit-chain-application.use-case.ts`:
   `SubmitChainApplicationUseCase.execute(dto)`:
   - `pharmacyChainRepository.findByTinInn(dto.tinInn)`.
   - Given не найдено, Then `PharmacyChain.submit(dto)` (доменная фабрика, `status='draft'`),
     сохранить, вернуть `{ id, status: 'draft' }`.
   - Given найдено со `status='rejected'`, Then ПЕРЕИСПОЛЬЗОВАТЬ существующую запись: обновить поля
     заявки, сбросить `submitted_at = NULL`, вернуть её `status='draft'` (SRS-ADM-007) — НЕ создавать
     вторую строку.
   - Given найдено в ЛЮБОМ другом статусе, Then `ChainApplicationAlreadyExistsError` (DTJ-063) →
     `409`.
4. `application/use-cases/verify-chain-contact-phone.use-case.ts`:
   `VerifyChainContactPhoneUseCase.execute({ chainId, code })` — резолвит `subjectRef` заявки
   (например, `contactPhone` + `chainId` как составной ключ, согласовать с существующим форматом
   `subject_ref` в `otp_codes`), вызывает `otpVerificationPort.verify(subjectRef, code, purpose:
   'onboarding_contact')` (порт из `@/modules/auth`) — при успехе помечает
   `pharmacy_chains.contact_phone_verified = true` (новое булево поле — **[ДОПОЛНЕНИЕ]**, добавить
   в ту же зону схемы, что и остальные поля этого модуля, миграцией внутри этого тикета, т.к. не
   было предусмотрено ни базовой DDL, ни §10.1 module-27 явно — минимальная точечная `ALTER TABLE
   pharmacy_chains ADD COLUMN contact_phone_verified BOOLEAN NOT NULL DEFAULT false`).
5. `presentation/controllers/pharmacy-chains-public.controller.ts`:
   - `POST /api/v1/pharmacy-chains` (`@Public()`) → `SubmitChainApplicationUseCase` → `201` с `{ id,
     status }`.
   - `POST /api/v1/pharmacy-chains/:id/verify-contact-phone` (`@Public()`, тело `{ code: string }`)
     → `VerifyChainContactPhoneUseCase` → `200 { data: { verified: true } }`.
   - Отдельный `POST /api/v1/pharmacy-chains/:id/request-contact-phone-otp` — тонкая обёртка над
     существующим `OtpGeneratorPort`/rate-limit из EP-01 (`purpose='onboarding_contact'`), не
     переизобретает лимиты §1.6/§3.1 `12-api-conventions...md`.

## Критерии приёмки
1. Given валидное тело заявки без `isWhitelabelRequested`, When `POST /pharmacy-chains`, Then `201`,
   `status='draft'`, запись в БД.
2. Given `isWhitelabelRequested=true`, `legalAddress` пустой, When `POST /pharmacy-chains`, Then
   `400 VALIDATION_ERROR` до попадания в use case (граница контракта).
3. Given заявка с `tinInn=X` существует со `status='rejected'`, When повторная подача с тем же
   `tinInn`, Then существующая запись переведена `status='draft'`, `submitted_at=NULL`, НЕ создана
   вторая строка (`SELECT count(*) WHERE tin_inn=X` возвращает `1`).
4. Given заявка с `tinInn=X` существует со `status='pending_review'`, When повторная подача, Then
   `409 CHAIN_APPLICATION_ALREADY_EXISTS` — негативный сценарий (в отличие от `rejected`).
5. Given верный OTP-код для заявки, When `POST /:id/verify-contact-phone`, Then
   `contact_phone_verified=true`; given неверный код, Then ошибка OTP-каталога (`OtpError`-семейство,
   уже определён EP-01), поле не изменяется.

## Риски и подводные камни
- Формат ИНН РТ (`tinInn`) — точный regex не найден ни в одном прочитанном спек-файле как готовый
  VO; временная граница `min(9).max(20)` — ASSUMPTION, подлежит уточнению доменным VO при появлении
  (возможно, зона EP-01 или отдельный будущий тикет вне диапазона EP-02/EP-03) — зафиксировать как
  открытый пробел.
- `contact_phone_verified` — поле, не предусмотренное явно ни базовой DDL, ни §10.1
  `27-module-admin-moderation-onboarding.md` (тот параграф покрывает другие таблицы) — минимальное
  дополнение, необходимое, чтобы `VerifyChainContactPhoneUseCase` вообще имело куда записать
  результат; при ревью архитектора решение может быть скорректировано (например, вынесено в
  `pharmacy_verification.checklist_snapshot` вместо отдельной колонки) — не блокирует реализацию.
- `OtpGeneratorPort`/`OtpVerificationPort` — публичные порты EP-01 модуля `auth`; если на момент
  реализации этого тикета их публичный барабанный экспорт ещё не готов, координация с EP-01,
  временная локальная заглушка НЕ создаётся (в отличие от кросс-эпик `Facade`-заглушек в EP-02) —
  OTP-верификация контакта не является критичным путём для параллельной разработки других тикетов
  этого файла, можно ждать готовности EP-01 без блокировки всей волны.
