## Задача
Центральный тикет эпика — единственное место, где заявка получает юридически значимое решение
человека. Каждое решение обязано быть безвозвратно зафиксировано в append-only журнале
(REQ-ONBOARD-7) — это комплаенс-требование, не техническая деталь: без журнала невозможно доказать,
кто и когда одобрил конкретную лицензию.

## Технический контекст
Слой `application`. Ровно 4 действия — `approve`, `request-changes`, `reject`, `terminate` — каждое
отдельный эндпоинт с собственной обязательной валидацией (`approve` требует `checklist`,
остальные три требуют `reason`), НЕ общий `PATCH status` (SRS-ADM-011). `PharmacyChainActivatedEvent`
запускает ОТЛОЖЕННЫЙ авто-переход `approved → active` при появлении первой `active` дочерней точки
— это доменный инвариант, реализованный в самой `PharmacyChain`/`PharmacyAccount` (DTJ-063,
`isTransitionAllowed`/будущий метод `chain.activateIfFirstPharmacyActive()`), здесь только
публикация события-триггера.

## Что сделать
1. `infrastructure/repositories/onboarding-review-log.repository.ts`:
   `OnboardingReviewLogRepository.append(entry)` — append-only, метода `update`/`delete` НЕТ на
   уровне репозитория (архитектурная гарантия неизменяемости, дублирует `REVOKE UPDATE, DELETE`
   на уровне роли БД, которую вводит `27-module...` §10.1 для `audit_log` — здесь аналогичный
   принцип для `onboarding_review_log`, хотя явный `REVOKE` для этой конкретной таблицы документом
   не прописан; см. «Риски»).
2. `application/use-cases/review-chain-application.use-case.ts` — четыре публичных метода на одном
   use case-классе (согласовано с C15/C17 `02`: один файл, т.к. это один связный сценарий с общей
   инфраструктурой журналирования, не 4 отдельных класса ради формальности) либо 4 отдельных класса,
   если код-ревью посчитает файл превышающим порог `02` §C2 — оставить на усмотрение исполнителя,
   главное требование ниже:
   - `approve({ chainId, actorId, checklist, notes? })`: `chain.approve(actor, checklist)` (домен),
     `onboardingReviewLogRepository.append({ chainId, action: 'approve', actorUserId: actorId, reason:
     notes, checklistSnapshot: checklist })`, `pharmacyVerificationRepository` обновляет
     `verification_status='verified', reviewed_by=actorId, reviewed_at=now()`, публикует
     `PharmacyChainActivatedEvent` (для будущего авто-перехода в `active`, слушатель — тот же модуль
     или `orders`/каталог по мере готовности, не в зоне этого тикета) — всё внутри одной транзакции.
   - `requestChanges({ chainId, actorId, reason })`: `chain.requestChanges(actor, reason)`,
     журналирование (`action='changes_requested'`) — `submitted_at` НЕ сбрасывается (время в
     `changes_requested` не засчитывается в SLA — расчёт `resolved_at - submitted_at -
     Σ(время в changes_requested)` фиксируется как формула для БУДУЩЕЙ SLA-отчётности EP-15/EP-17,
     не реализуется полностью в этом тикете — здесь только гарантируется, что `submitted_at`
     сохраняется неизменным при этом переходе, точный расчёт задержки — вне зоны R1-16/онбординга
     тимлида).
   - `reject({ chainId, actorId, reason })`: `chain.reject(actor, reason)`, журналирование
     (`action='reject'`) — терминально ДО повторной подачи (§2.1, DTJ-064 п.3 уже обрабатывает
     повторную подачу после `rejected`).
   - `terminate({ chainId, actorId, reason })`: `chain.terminate(actor, reason)`, журналирование
     (`action='terminate'`) — терминально НАВСЕГДА, без пути назад (уже гарантировано доменом
     DTJ-063).
3. `application/use-cases/review-pharmacy-application.use-case.ts` — зеркальная реализация для
   `PharmacyAccount`/`pharmacy_id`.
4. `application/events/pharmacy-chain-activated.event.ts` / `pharmacy-account-activated.event.ts` —
   простые DTO-события, публикуются в `outbox`.
5. `presentation/controllers/pharmacy-verification-decisions.controller.ts`:
   `@Roles('super_admin')`, permission `pharmacy-accounts:approve` — 8 маршрутов (4 действия × 2
   типа сущности): `POST /pharmacy-chains/:id/approve`, `/request-changes`, `/reject`, `/terminate`
   и зеркально для `/pharmacy-accounts/:id/...`. Тело: `approve` — `{ checklist: Record<string,
   boolean>, notes?: string }`; остальные три — `{ reason: string }` (обязательное поле, `min(1)`
   в zod-схеме).

## Критерии приёмки
1. Given заявка сети `pending_review`, When `POST /pharmacy-chains/:id/approve { checklist: {...},
   notes: 'ok' }` от `super_admin`, Then `status='approved'`, `onboarding_review_log` содержит новую
   строку с `action='approve'`, `checklist_snapshot` совпадает с переданным.
2. Given та же заявка уже `approved`, When повторный `POST .../approve`, Then `409`, доменная ошибка
   перехода (`AlreadyReviewedError` или `InvalidOnboardingTransitionError`, на усмотрение
   реализации — оба уже определены DTJ-063/каталогом) — негативный сценарий, повторное
   рассмотрение отклонено.
3. Given заявка `pending_review`, When `POST .../reject` БЕЗ поля `reason` в теле, Then `400
   VALIDATION_ERROR` до входа в use case.
4. Given заявка `pending_review`, When `POST .../request-changes { reason: '...' }`, Then
   `status='changes_requested'`, `submitted_at` в БД остаётся РАВНЫМ значению до этого вызова
   (не обновляется, не обнуляется).
5. Given заявка `active` (терминальный вне зоны обычного пересмотра, но `terminate` разрешён из
   ЛЮБОГО статуса), When `POST .../terminate { reason: 'доказанное мошенничество' }`, Then
   `status='terminated'`, дальнейшие вызовы `approve`/`reject`/`request-changes` на этой заявке
   отклоняются (терминальность подтверждена).

## Риски и подводные камни
- `REVOKE UPDATE, DELETE ON onboarding_review_log FROM app_role` — явно НЕ прописан
  `27-module-admin-moderation-onboarding.md` §10.1 (только `audit_log` там упомянут для `REVOKE`),
  хотя логика «append-only» идентична; рекомендация — завести такой же `REVOKE` для симметрии
  комплаенс-гарантии, но это требует координации с владением ролей БД (вероятно EP-01/инфраструктура)
  — не блокирует этот тикет (репозиторий и так не предоставляет методов мутации на уровне
  приложения, `REVOKE` — второй, БД-уровневый рубеж защиты в глубину, как и везде в проекте).
- Точный расчёт «эффективного» времени в SLA с вычетом периодов `changes_requested` — формула
  указана SRS-ADM-011, но полная реализация (агрегирующий запрос/отчёт) — вне зоны этого тикета
  (относится к EP-15 «истекающие лицензии»/отчётность или EP-17 аналитика) — здесь гарантируется
  только корректность исходных данных (`submitted_at` не искажается), сам расчёт откладывается.
- Восемь маршрутов на одном контроллере — если превышает читаемость/порог строк файла (`02` §C2),
  разделить на `pharmacy-chains-decisions.controller.ts` и `pharmacy-accounts-decisions.controller.ts`
  — решение по факту объёма кода, не блокирует написание тикета.
