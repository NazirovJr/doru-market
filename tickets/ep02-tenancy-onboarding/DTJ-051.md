## Задача
Даёт физическое хранилище доменной модели из DTJ-050 и единственную гарантированную строку
`is_neutral=true`, без которой резолвинг тенанта (DTJ-054) не может фолбэкнуться на публичный
DoruTJ. Файл `apps/api/src/db/schema/tenants.ts` явно закреплён за EP-02 в `00-EPICS.md`
(«Порядок владения файлами») отдельно от общего `db/schema/**` EP-01 — этот тикет реализует именно
эту границу.

## Технический контекст
Полная DDL — `11-database-schema.md` Группа C (`tenants`, `tenant_settings`) плюс дополнения
`26-module-tenancy-whitelabel.md` §12 п.1–3 (уникальность тенанта на сеть, поля брендинга/контактов,
статус верификации домена) — поскольку таблица создаётся ЗАНОВО в этом тикете, дополнения
включаются сразу в одну DDL, отдельная ALTER-миграция не нужна. `pharmacy_chains.tenant_id` —
отложенный внешний ключ (SRS-DB-010): базовая таблица `pharmacy_chains` создаётся раньше по волнам
(EP-01/EP-03-scaffolding), FK на `tenants` добавляется ЗДЕСЬ вторым файлом миграции, т.к. `tenants`
появляется только сейчас (волна 2). Drizzle-схема — `drizzle-orm` ^0.45 (`01-TECH-BASELINE.md`),
миграции — `drizzle-kit generate` + ручная проверка сгенерированного SQL на соответствие DDL
документа (расхождение — блокирующее замечание ревью).

## Что сделать
1. `db/schema/tenants.ts` (Drizzle): таблица `tenants` — `id` (uuid, pk, `gen_random_uuid()`),
   `slug` (varchar(32), not null, unique), `chainId` (uuid, nullable, `ON DELETE RESTRICT`),
   `customDomain` (varchar(255), unique, nullable), `isNeutral` (boolean, default false),
   `courierSourcingMode` (enum `courier_sourcing_mode`, default `platform_pool`), `customDomainStatus`
   (новый enum `custom_domain_status`: `none`|`pending_verification`|`verified`, default `none`),
   `domainVerificationToken` (varchar(64), nullable), `createdAt`. CHECK-constraints:
   `chk_tenants_neutral_has_no_chain` (`is_neutral = false OR chain_id IS NULL`),
   `chk_tenants_domain_status` (домен и статус согласованы, §12 п.3).
2. Та же таблица `tenant_settings`: `tenantId` (pk, fk `ON DELETE CASCADE`), `brandName` (varchar,
   not null), `brandLogoUrl`, `brandLogoSquareUrl`, `brandFaviconUrl` (text, nullable — §12 п.2),
   `brandPalette` (jsonb, default `{}`), `telegramBotUsername`, `telegramBotTokenRef`,
   `merchantCredentialsRef`, `merchantCredentialsStatus` (varchar(20), default
   `not_configured`), `supportPhone`, `supportEmail`, `codLimitDiram` (bigint, default 50000),
   `holdPeriodDays` (int, default 1), `pickupSlaMinutes` (default 7), `pickupSlaBufferMinutes`
   (default 5), `deliverySlaCityMinutes` (default 240), `deliverySlaRemoteMinutes` (default 1440).
3. Индексы: `CREATE UNIQUE INDEX ux_tenants_single_neutral ON tenants ((true)) WHERE is_neutral =
   true`; `CREATE UNIQUE INDEX ux_tenants_single_chain ON tenants (chain_id) WHERE chain_id IS NOT
   NULL` (§12 п.1).
4. Enum `custom_domain_status` — создать `CREATE TYPE` в этой же миграции (новый тип, транзакция не
   нарушается, т.к. это не `ADD VALUE` к существующему типу).
5. Вторая миграция (`_pharmacy_chains_tenant_fk.sql`, только если `pharmacy_chains` уже существует к
   моменту разработки — проверить фактическое состояние схемы перед написанием; если таблицы ещё
   нет, добавить FK в отдельную миграцию с явным `-- depends-on: pharmacy_chains` комментарием,
   применяемую CI после миграции, создающей `pharmacy_chains`): `ALTER TABLE pharmacy_chains ADD
   CONSTRAINT fk_pharmacy_chains_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE SET
   NULL`.
6. `db/seed/tenants/neutral.seed.ts`: `INSERT INTO tenants (slug, is_neutral, ...) VALUES ('neutral',
   true, ...)` (idempotent upsert по `slug`) + соответствующая строка `tenant_settings` с
   `brand_name = 'DoruTJ'` — ЕДИНСТВЕННОЕ место в кодовой базе, где буква «DoruTJ» разрешена как
   литерал (seed-данные, не исполняемый UI-код — не нарушает SRS-TEN-017/DTJ-060, т.к. лог-правило
   явно исключает тестовые фикстуры/seed). `courierSourcingMode = 'platform_pool'`,
   `customDomain = 'sifat.dorutj.local'` — НЕТ, неверно: `sifat.dorutj.local` относится к демо-сети
   (не нейтральному тенанту) — оставить `customDomain = NULL` для нейтрального; демо White-Label
   тенант с этим доменом заводится отдельно EP-03/сид-скриптом сети после провизионинга (DTJ-057),
   не в этом seed-файле.
7. Подключить `db:seed`-скрипт к общему `pnpm db:seed` раннеру (уже существующему из EP-01
   scaffolding — если раннера ещё нет на момент реализации, завести минимальный вызов по конвенции
   `01-TECH-BASELINE.md`, не изобретать новый механизм).

## Критерии приёмки
1. Given чистая БД, When `pnpm db:migrate && pnpm db:seed`, Then `SELECT count(*) FROM tenants WHERE
   is_neutral = true` возвращает `1`.
2. Given нейтральный тенант уже есть, When повторный `INSERT tenants(is_neutral=true, slug=<любой
   другой>)`, Then `23505 unique_violation` на `ux_tenants_single_neutral`.
3. Given тенант с `chain_id = X` уже существует, When `INSERT tenants(chain_id=X, ...)` второй раз,
   Then `23505 unique_violation` на `ux_tenants_single_chain`.
4. Given `custom_domain IS NULL`, When `INSERT tenants(custom_domain_status='verified', ...)`, Then
   `23514 check_violation` на `chk_tenants_domain_status` (негативный сценарий — статус без домена
   запрещён).

## Тест-план
Интеграционный (Vitest + тестовый Postgres-контейнер, тот же паттерн, что использует остальная
кодовая база проекта): `tenants-migration.integration.spec.ts` — применяет миграции на чистую БД,
проверяет наличие всех колонок/индексов/constraint'ов через `information_schema`, проверяет seed
(п.1 выше), проверяет оба уникальных индекса (п.2, п.3) и check-constraint (п.4) прямыми SQL-вызовами
через тестовый пул соединений. Unit-тесты не нужны (чистая инфраструктура, нет бизнес-логики).
Порог покрытия ≥ 70% (не `domain`/`application`) — миграционный код тестируется интеграционно, не
через покрытие строк.

## Риски и подводные камни
- Порядок миграций между EP-01 (или EP-03, если Group A создаётся там), создающей `pharmacy_chains`,
  и этой (создающей `tenants` + FK) — реальная межкомандная зависимость: если на момент реализации
  `pharmacy_chains` ещё не существует физически в `main`, шаг 5 откладывается до её появления
  (миграция FK готовится, но не мержится раньше базовой таблицы) — не блокирует остальные пункты
  тикета (`tenants`/`tenant_settings` не зависят от `pharmacy_chains` для CREATE, только для ALTER).
- `custom_domain_status`/`domain_verification_token` вводятся здесь СРАЗУ (не отдельной ALTER-
  миграцией DTJ-061), т.к. таблица ещё не существует нигде — дешевле включить в первую DDL, чем
  добавлять `ALTER TYPE`/`ALTER TABLE` следующим тикетом.
- Формулировка demo custom_domain (`sifat.dorutj.local`) из `26-module-tenancy-whitelabel.md`
  SRS-TEN-007 относится к демонстрационному White-Label тенанту, а не к нейтральному — явно
  зафиксировано в п.6, чтобы не перепутать при реализации.
