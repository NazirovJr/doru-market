## Задача
Кастомный домен — единственный шаг чек-листа запуска White-Label тенанта (§6
`26-module-tenancy-whitelabel.md`), требующий внешней зависимости (DNS клиента), и единственный
шаг, растягивающий «48 часов» запуска. Механизм обязан работать в R1 (реальная привязка домена сети
— R3, но сам механизм проверки — нет), иначе ни demo-домен (`sifat.dorutj.local`, SRS-TEN-007), ни
будущая продажа White-Label не имеют технической основы.

## Технический контекст
Слой `application` модуля `tenancy`. `custom_domain_status`/`domain_verification_token` уже в схеме
(DTJ-051). DNS-проверка — Provider Pattern (порт + адаптер), т.к. это внешняя I/O-зависимость
(Charter §3.3). Фоновая проверка — BullMQ repeatable job (`apps/worker`, `01-TECH-BASELINE.md`),
повтор каждые 15 минут до 48 часов (SRS-TEN-018 шаг 5).

## Что сделать
1. `application/ports/dns-verification.port.ts`: `DnsVerificationPort` — `verifyTxtRecord(domain:
   string, expectedToken: string): Promise<boolean>`.
2. `infrastructure/adapters/dns-txt-verification.adapter.ts`: `NodeDnsTxtVerificationAdapter
   implements DnsVerificationPort` — использует встроенный Node.js `dns.promises.resolveTxt(domain)`,
   ищет запись вида `dorutj-verify=<token>` среди всех TXT-записей домена, сравнивает с ожидаемым
   токеном. Сетевая ошибка (`NXDOMAIN`, таймаут) → возвращает `false` (не бросает исключение — «TXT
   не найдена» и «домен не резолвится» с точки зрения бизнес-логики эквивалентны: не верифицировано
   в этой попытке, будет ретрай следующим циклом job).
3. `application/use-cases/attach-custom-domain.use-case.ts`: `AttachCustomDomainUseCase.execute({
   tenantId, domain })`:
   - Given домен уже привязан (`verified` ИЛИ `pending_verification`) к ДРУГОМУ тенанту (проверка
     через `tenantRepository`, доп. метод `findByCustomDomain` из DTJ-052), Then `409 DOMAIN_TAKEN`
     (`DuplicateCustomDomainError`, DTJ-050) — проверка ЗАРАНЕЕ на уровне application, БД-`UNIQUE` —
     последний рубеж, не единственный (SRS-TEN-039).
   - Генерирует `domainVerificationToken` (криптографически случайная строка, 32+ символа), вызывает
     `tenant.attachCustomDomain(domain)` (DTJ-050, переводит статус в `pending_verification`),
     сохраняет.
   - Возвращает клиенту `{ domain, verificationToken, txtRecordInstructions: 'TXT dorutj-verify=<token>' }`
     — инструкция для добавления TXT-записи в DNS-зоне клиента.
4. `apps/worker/src/jobs/tenant-domain-verification/tenant-domain-verification.job.ts`:
   `TenantDomainVerificationJob` (BullMQ repeatable, cron `*/15 * * * *`) — выбирает ВСЕ тенанты с
   `custom_domain_status = 'pending_verification'`, для каждого вызывает
   `dnsVerificationPort.verifyTxtRecord(domain, token)`; при `true` — переводит статус в `verified`,
   публикует `TenantDomainAttachedEvent` (форма из DTJ-053, инвалидирует кэш); given попытка длится
   дольше 48 часов от момента инициации (`SRS-TEN-018`/`SRS-TEN-019` — верхняя граница ожидания, не
   технический лимит DoruTJ) — job НЕ переводит статус в ошибочный автоматически (клиент может
   исправить DNS-запись позже, попытки продолжаются бессрочно, "48 часов" — управление ожиданиями
   продажи, не таймаут кода) — явный комментарий в коде job'ы, почему нет авто-отмены.
5. `presentation/controllers/tenancy-domain.controller.ts`: `POST /api/v1/admin/tenants/:id/custom-
   domain` (инициация, `@Roles('super_admin', 'pharmacy_admin')` + политика владения тенантом, как в
   DTJ-059) и `POST /api/v1/admin/tenants/:id/custom-domain/verify` (ручной триггер проверки вне
   расписания — вызывает тот же use case логики верификации синхронно, полезно для демонстрации/
   тестирования без ожидания 15-минутного цикла).
6. Орфанный домен (SRS-TEN-035): отдельного кода не требует в ЭТОМ тикете — уже покрыто
   резолвингом DTJ-054 (шаг 1 не находит совпадения, если `custom_domain = NULL`, фолбэк на шаг
   2/3 — поведение автоматическое, только подтверждается тестом здесь).

## Критерии приёмки
1. Given домен `pharmacy.example.tj` уже `verified` у тенанта A, When `AttachCustomDomainUseCase`
   для тенанта B с тем же доменом, Then `409 DOMAIN_TAKEN`.
2. Given `custom_domain='sifat.tj'`, `custom_domain_status='pending_verification'` (DNS TXT ещё не
   проверен), When запрос с `Host: sifat.tj`, Then тенант НЕ резолвится по этому домену (шаг 1
   резолвинга пропущен, статус не `verified`), фолбэк на `X-Tenant-Slug`/`neutral` — сквозной тест,
   опирающийся на DTJ-054, подтверждающий интеграцию с этим тикетом.
3. Given TXT-запись с верным токеном добавлена в DNS клиента, When `TenantDomainVerificationJob`
   выполняет цикл (или ручной `POST .../verify`), Then `custom_domain_status` переходит в
   `verified`, кэш инвалидирован.
4. Given `tenants.custom_domain=NULL` (тенант отвязан вручную), внешний DNS клиента ещё указывает на
   инфраструктуру DoruTJ, When запрос с этим устаревшим `Host`, Then показан нейтральный публичный
   DoruTJ, НЕ ошибка, `pino.warn(domain_resolution_fallback)` записан — негативный сценарий
   («осиротевший» домен не должен приводить к 5xx).

## Риски и подводные камни
- Реальная DNS-проверка зависит от исходящего сетевого доступа `apps/worker`-контейнера — в
  `OFFLINE_MODE=true` (on-premise профиль, R3) эта job должна быть отключена целиком; в R1
  (облачное окружение) сетевой доступ предполагается доступным по умолчанию, отдельный флаг для
  отключения НЕ вводится этим тикетом (вне зоны R1-16), фиксируется как известное ограничение,
  переносимое на R3-тикет on-premise поставки (вне диапазона EP-02/EP-03).
- `apps/worker` bootstrap-регистрация job — общий файл, владение которым, вероятно, у EP-01/общей
  инфраструктуры очередей; при отсутствии готового раннера на момент реализации — координация,
  временная точка входа может быть отдельным `main.ts` внутри `apps/worker/src/jobs/tenant-domain-
  verification/`, переносимая позже без изменения бизнес-логики job.
