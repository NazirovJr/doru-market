## Задача
Charter §3.4 требует «guard, запрещающий запрос без резолва тенанта» — это последний рубеж защиты
ПЕРЕД контроллером, отдельный от middleware (которое только резолвит, но не блокирует). Этот guard
превращает результат резолвинга DTJ-054 в конкретные HTTP-ответы и реализует единственную защиту
от кросс-тенантного доступа по украденному/скопированному JWT, обязательную по Charter §3.4.

## Технический контекст
`apps/api/src/common/guards/tenant-scope.guard.ts` — файл, явно закреплённый за EP-02 в
«Порядке владения файлами» `00-EPICS.md` отдельно от общего `common/`. Guard работает ПОСЛЕ
`AuthGuard` (порядок: `TenantResolutionMiddleware` → `AuthGuard` → `TenantResolutionGuard` →
`RolesGuard` → контроллер — уточнение относительно SRS-API-041, которое требует резолвинга ДО
`AuthGuard`; сам блокирующий guard логично идёт после, т.к. для проверки `token.tenantId !==
resolvedTenantId` нужен уже распарсенный JWT). Условная авторизация «это его ресурс» — НЕ здесь
(это `application`-политики, SRS-API-036), guard проверяет только совпадение тенанта.

## Что сделать
1. `TenantScopeGuard implements CanActivate`: читает `TenantContext.current()` (DTJ-054) и
   `request.user` (заполнен `AuthGuard`, EP-01).
2. Given `TenantContext.current().unresolved === true, reason: 'technical'` (SRS-API-042), Then
   `400 TENANT_NOT_RESOLVED` — ни один запрос к репозиторию не выполняется дальше.
3. Given `unresolved === true, reason: 'unknown_slug'`, Then `404 UNKNOWN_TENANT_SLUG`.
4. Given эндпоинт помечен `@Public()` (DTJ-054) — тенант всё равно резолвлен (это НЕ то же самое,
   что «нетенантный», SRS-TEN-008), но guard пропускает проверку совпадения `token.tenantId` (нет
   JWT вовсе на публичном эндпоинте) — только шаги 2/3 (проверка технической ошибки/неизвестного
   slug) применяются одинаково для публичных и защищённых маршрутов.
5. Given `token.role === 'super_admin'` (`token.tenantId === null`, SRS-API-017 из EP-01), Then
   проверка совпадения тенанта ПРОПУСКАЕТСЯ безусловно (SRS-API-044) — `super_admin` может явно
   запросить любой `tenantId` через `X-Tenant-Slug`. Given резолвленный `tenantId` запроса ≠
   `null` (т.е. `super_admin` явно указал конкретного тенанта, не работает в «платформенном»
   контексте без тенанта), Then guard публикует в `outbox` (или напрямую пишет в `audit_log`, если
   `outbox`-обёртка для аудита ещё не готова на момент реализации — координация с EP-16) запись с
   `crossTenantOverride: true, actorUserId, targetTenantId` — это ОБЯЗАТЕЛЬНОЕ логирование, не
   опциональное.
6. Given роль НЕ `super_admin` И `token.tenantId !== resolvedTenantId`, Then немедленно `403
   CROSS_TENANT_ACCESS_DENIED`, контроллер не вызывается (SRS-API-045) — публикует также
   `CrossTenantAccessAttemptedEvent` в `outbox` (SRS-TEN-037, отдельно от `audit_log` — это ПОПЫТКА
   нарушения, не легитимное действие, не должна засорять пользовательский аудит-лог).
7. Given роль НЕ `super_admin` И `token.tenantId === resolvedTenantId` (штатный случай), Then guard
   пропускает запрос без дополнительных действий.

## Критерии приёмки
1. Given резолвинг не удался по технической причине, When любой защищённый эндпоинт, Then `400
   TENANT_NOT_RESOLVED`, ни один вызов репозитория/use case не зафиксирован (мок use case не вызван —
   проверяется через spy).
2. Given `X-Tenant-Slug: definitely-not-a-real-slug`, When запрос, Then `404 UNKNOWN_TENANT_SLUG`.
3. Given JWT `tenantId=A`, роль `customer`, запрос резолвлен в тенанта B (через домен/slug B), When
   любой защищённый эндпоинт, Then `403 CROSS_TENANT_ACCESS_DENIED` до входа в контроллер + событие
   `CrossTenantAccessAttemptedEvent` в `outbox`.
4. Given JWT `super_admin`, `tenantId=null`, `X-Tenant-Slug` указывает на тенант B, When запрос к
   ресурсу тенанта B, Then доступ разрешён, запись с `crossTenantOverride=true` создана.
5. Given обычный `customer` тенанта A обращается через домен/slug ИМЕННО тенанта A (совпадение), When
   запрос, Then guard пропускает без побочных эффектов (негативный по отношению к «всегда логировать»
   — штатный путь НЕ создаёт лишних записей аудита).

сценариев выше плюс комбинация `@Public()` + `unresolved: unknown_slug` (публичный эндпоинт всё
равно получает `404`, если slug в заголовке заведомо неверный — резолвинг обязателен независимо от

guard'а как часть код-ревью, даже если формальный порог ниже).

## Риски и подводные камни
- Публикация в `audit_log`/`outbox` из guard'а — guard'ы традиционно не должны знать о персистентности
  (нарушение единственной ответственности), но Charter требует обязательного аудита именно на этом
  рубеже (до контроллера); смягчение — guard вызывает узкий порт `SecurityAuditPort.record(...)`
  (application-порт этого же модуля, а не прямой репозиторий) — реализация адаптера координируется с
  EP-16 (`audit_log`), временная реализация может писать напрямую через тонкий адаптер до готовности
  общего аудит-фасада, без блокировки этого тикета.
- Если `outbox`-инфраструктура EP-01/EP-16 не готова к моменту реализации, `CrossTenantAccessAttemptedEvent`
  можно временно только логировать через `pino.warn` с полным контекстом (не терять сигнал), с
  TODO на переключение на `outbox`, когда он появится — согласовать с EP-16 при пересечении волн.
