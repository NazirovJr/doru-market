## Задача
На каждый HTTP-запрос система резолвит тенанта (DTJ-054) — без кэша это лишний `SELECT` на КАЖДЫЙ
запрос платформы, включая анонимный трафик каталога (самый частый путь). Redis-кэш с graceful
degradation даёт производительность резолвинга без риска отказа системы при недоступности Redis
(Charter §7 «падение внешнего провайдера не роняет систему»).

## Технический контекст
Слой `infrastructure` модуля `tenancy`, порт `TenantCachePort` в `application/ports` (используется
`TenantResolutionMiddleware`, DTJ-054, через DI, middleware не знает о Redis напрямую). Redis-клиент
— `ioredis` ^5 (`01-TECH-BASELINE.md`), общий пул соединений — инфраструктура EP-01, этот адаптер
только потребляет DI-токен клиента. Инвалидация — по доменному событию, не по TTL (TTL 60с —
подстраховка на пропущенную инвалидацию, не основной механизм, SRS-TEN-005).

## Что сделать
1. `application/ports/tenant-cache.port.ts`: `TenantCachePort` — `getByDomain(host: string):
   Promise<TenantId | null>`, `getBySlug(slug: string): Promise<TenantId | null>`,
   `setByDomain(host, tenantId)`, `setBySlug(slug, tenantId)`, `invalidateDomain(host)`,
   `invalidateSlug(slug)`.
2. `infrastructure/adapters/tenant-cache.adapter.ts`: `RedisTenantCacheAdapter implements
   TenantCachePort` — ключи `tenant:by-domain:{host}`/`tenant:by-slug:{slug}`, значение — сырой
   `tenantId` (UUID-строка), `EX TENANT_DOMAIN_CACHE_TTL_SECONDS` (ENV, дефолт 60 — ASSUMPTION
   SRS-TEN-005, задокументировать в `.env.example`).
3. Graceful degradation (SRS-TEN-006): каждый метод чтения оборачивает вызов Redis в try/catch —
   при ЛЮБОЙ ошибке подключения (не найденный ключ — это НЕ ошибка, а штатный промах кэша,
   возвращает `null` без исключения) логирует `pino.warn({ err }, 'tenant_cache_unavailable')` и
   возвращает `null`, имитируя промах кэша — вызывающий код (middleware) единообразно идёт в
   `TenantRepository` независимо от причины промаха (нет разницы «не найдено» vs «Redis недоступен»
   с точки зрения потребителя, только с точки зрения лога).
4. Методы записи (`set*`) при ошибке Redis — тоже не бросают исключение (кэш — оптимизация, не
   источник истины), только `pino.warn`.
5. `application/events/tenant-branding-updated.event.ts` и `tenant-domain-attached.event.ts` —
   простые доменные события-DTO (`{ tenantId, occurredAt }` / `{ tenantId, oldDomain?, newDomain,
   occurredAt }`), публикуются use case'ами DTJ-059/DTJ-061 в `outbox` (механизм `outbox` — общая
   инфраструктура EP-01/EP-16, этот тикет только определяет форму события).
6. Обработчик события (тот же процесс, синхронно после commit транзакции, SRS-TEN-005) —
   `TenantCacheInvalidationHandler` в `infrastructure` — на `TenantBrandingUpdatedEvent`/
   `TenantDomainAttachedEvent` вызывает `invalidateDomain`/`invalidateSlug` для затронутого тенанта.

## Критерии приёмки
1. Given `tenantId` записан в кэш по домену, When `getByDomain(host)` в пределах TTL, Then
   возвращается тот же `tenantId` без обращения к БД (проверяется мок-репозиторием с счётчиком
   вызовов, равным 0).
2. Given Redis-соединение симулированно разорвано (тестовый mock клиента бросает
   `ECONNREFUSED`), When `getByDomain(host)`, Then метод возвращает `null` (не пробрасывает
   исключение), в логе присутствует запись уровня `warn`, не `error`.
3. Given событие `TenantBrandingUpdatedEvent` для тенанта X, When обработчик срабатывает, Then ключи
   `tenant:by-domain:{host тенанта X}`/`tenant:by-slug:{slug тенанта X}` удалены из Redis.
4. Given ключ отсутствует в кэше (штатный промах, НЕ ошибка соединения), When `getByDomain`, Then
   возвращается `null` БЕЗ записи в лог (отличие от сценария 2 — не путать промах с деградацией) —
   негативный сценарий проверки отсутствия лишнего шума в логах.

## Риски и подводные камни
- Обработчик инвалидации подписывается на события ПОСЛЕ commit транзакции — если инфраструктура
  `outbox`/событийной шины EP-01 на момент реализации ещё не даёт синхронного in-process хука
  «после commit», временное решение — прямой вызов `cachePort.invalidate*()` из самого use case
  (DTJ-059/061) сразу после успешного `save()`, БЕЗ ожидания outbox-релея (расхождение с буквальной
  формулировкой SRS-TEN-005 «через событие» — задокументировать как временное упрощение до
  готовности общего событийного моста, не блокирует этот тикет).
- Ошибка записи в кэш (`set*`) при живом Redis, но, например, `OOM`/`maxmemory-policy` — тоже
  перехватывается тем же try/catch, что и обрыв соединения; не разбито на отдельные случаи, т.к. с
  точки зрения потребителя любой сбой записи в кэш — не блокирующая деградация.
