## Задача
Это ПЕРВЫЙ экран приложения `apps/admin` (`00-EPICS.md` «Обязательные сквозные тикеты»: «Scaffolding
`apps/admin` — первый экран — верификация лицензии аптеки», владение общим каркасом `app/`/`pages`
закрепляется за этим тикетом как первым, добирающимся до `apps/admin` по волнам — EP-14/EP-15/EP-17
позже добавляют СВОИ разделы гостевыми правками маршрутов, не трогая этот каркас целиком). Без
рабочего UI очереди верификации `super_admin` физически не может одобрить ни одну аптеку иначе как
через Postman — блокирует весь дальнейший продуктовый цикл.

## Технический контекст
`apps/admin/**` — новое React-приложение (`01-TECH-BASELINE.md` стек — тот же, что `apps/web`: Vite
7, React, `packages/ui`/`packages/i18n` для дизайн-токенов и словарей). `32-design-reference.md`
строка 335 явно перечисляет «очередь онбординга сетей/аптек» в разделе «Пробелы дизайна» — визуального
прецедента НЕТ, реализация строго по письменной спецификации SRS-ADM-009/010/011 и общим паттернам
дизайн-системы (карточка, кнопка, форма — уже описаны `32-design-reference.md` §«Компоненты» для
`apps/web`, переиспользовать те же токены/компоненты `packages/ui`, не изобретать параллельный
визуальный язык для `apps/admin`).

## Что сделать
1. Scaffolding приложения: `apps/admin/vite.config.ts`, `apps/admin/src/app/` (роутер, точка входа,
   RBAC-гейт по `01-TECH-BASELINE.md`/`30-ux-screens-and-flows.md` §«пятиролевой RBAC-роутинг» —
   доступ к `apps/admin` только ролям `super_admin`/`pharmacy_admin`/`support_agent`, редирект прочих),
   `apps/admin/index.html` (нейтральные `:root { --brand-* }` дефолты — ТОЧНАЯ копия значений из
   `apps/web/index.html`, DTJ-060, единственный источник — держать в синхроне тем же способом, что и
   там, отдельный тест синхронизации НЕ дублируется здесь — переиспользовать логику/подход из
   DTJ-060, применённую ко второму файлу).
2. `apps/admin/src/features/onboarding-verification/`: экран `/admin/onboarding-queue` — список
   заявок (`GET /pharmacy-chains?status=...` и `/pharmacy-accounts?status=...`, DTJ-067) с
   переключателем «Сети / Аптеки», FIFO-порядок, индикатор просроченности (`sla_target_at` vs
   текущее время — визуальная пометка, не блокирующая логика), пагинация (курсорная, «Показать ещё»
   или infinite scroll — на усмотрение, следуя общему паттерну `apps/web` при его наличии).
3. Экран детали заявки `/admin/onboarding-queue/:type/:id` — все поля формы заявки (из
   `packages/contracts/src/onboarding.ts`, DTJ-064/065), превью документов (`licenseScanUrl`,
   `registrationCertificateUrl` — `<img>`/`<iframe>` в зависимости от MIME, PDF — встроенный
   просмотрщик браузера через `<embed>`/`<iframe>`, без сторонних PDF-библиотек), чек-лист
   (динамический список чекбоксов — состав чек-листа не специфицирован документами КОНКРЕТНЫМ
   перечнем пунктов, реализовать как редактируемый набор `{ [key: string]: boolean }` с 4–6
   разумными пунктами по смыслу проверки, например «ИНН совпадает с документом», «Лицензия
   действительна», «Адрес соответствует лицензии», «Контактный телефон подтверждён» — финальный
   состав уточняется продуктом/дизайном, не блокирует техническую реализацию формы).
4. Кнопки действий на карточке — «Одобрить» (модалка подтверждения чек-листа →
   `POST .../approve`), «Запросить изменения» (текстовое поле причины → `POST .../request-changes`),
   «Отклонить» (`POST .../reject`), «Прекратить» (`POST .../terminate`, с усиленным подтверждением —
   двойной клик/чекбокс «я понимаю необратимость», т.к. действие терминально навсегда).
5. i18n: ВСЕ строки интерфейса — через `useT()`/`packages/i18n` (нет хардкода, C6
   `02-CLEAN-ARCHITECTURE-AND-CODE.md`), ключи локали `tj`/`ru`/`en` — минимум `ru` заполнен
   реальным текстом на этом шаге, `tj`/`en` — заглушки/машинный перевод с TODO, если полный словарь
   `packages/i18n` ещё не готов к моменту реализации (координация с EP-18, не блокирует сам экран).

## Критерии приёмки
1. Given `super_admin` авторизован, When открывает `/admin/onboarding-queue`, Then видит список
   заявок в статусе `pending_review`, отсортированный по времени подачи (старые сверху).
2. Given заявка выбрана, When открыт `/admin/onboarding-queue/chain/:id`, Then видны все поля формы
   + превью загруженных документов + чек-лист.
3. Given чек-лист заполнен, When нажатие «Одобрить», Then вызывается `POST
   /pharmacy-chains/:id/approve` с телом `{ checklist, notes }`, после успеха карточка исчезает из
   очереди `pending_review` (реального времени/WS-обновление — НЕ обязательно в этом тикете, ручное
   обновление списка после успешного действия допустимо для R1).
4. Given `pharmacy_admin` (не `super_admin`) пытается открыть `apps/admin`, When навигация, Then
   редирект/экран отказа в доступе — негативный сценарий (RBAC-гейт на уровне роутера, не только
   бэкенд-guard).
5. Given попытка нажать «Прекратить» без второго подтверждения, When клик, Then действие НЕ
   отправляется — защита от случайного необратимого действия.

## Риски и подводные камни
- Состав чек-листа НЕ специфицирован документами конкретным перечнем пунктов — реализация вводит
  разумный набор (п.3 «Что сделать»), подлежащий уточнению продуктом на следующей итерации; не
  является блокером технической готовности экрана.
- Реального времени (WS-уведомление о новой заявке в очереди) НЕТ в этом тикете — SRS-API-047..054
  (реалтайм-канал) специфицирован в `12-api-conventions...md`, но подключение конкретно этого экрана
  к WS — отдельное усиление, не обязательное для R1 функциональной полноты (ручное обновление
  списка достаточно для запуска).
- `apps/admin` как общий каркас — этот тикет владеет `app/`/`pages`/роутером ПЕРВЫМ по правилу
  `00-EPICS.md` «Пересекающееся владение» п.1; последующие эпики (EP-14/EP-15/EP-17) добавляют
  гостевые правки маршрутов — не блокирует этот тикет, но реализующий разработчик должен оставить
  роутер легко расширяемым (не монолитный switch без точки для добавления новых веток).
