## Задача
Создание White-Label тенанта — единственная платформенная операция, включающая механизм
мультитенантности «для второго тенанта» (реально активируется в R3, но use case и эндпоинт обязаны
существовать и работать в R1 — SRS-TEN-000: без флага «отключить», без заглушек). Также этим
use case создаётся демо-тенант для локальной разработки/e2e (SRS-TEN-007) — без него невозможно
продемонстрировать резолвинг по нескольким тенантам.

## Технический контекст
Слой `application` модуля `tenancy`. Предусловие «сеть одобрена и запросила White-Label»
проверяется по данным `pharmacy_chains`, которым владеет модуль `onboarding` (EP-03) — по правилу
межмодульного взаимодействия (`02` §1.2) `tenancy` объявляет СОБСТВЕННЫЙ узкий порт
`ChainEligibilityPort` (application/ports этого модуля, не заимствует чужой), реализация которого
(`infrastructure/adapters`) вызывает `OnboardingFacade.getChainEligibilityForWhitelabel(chainId)` —
метод, который обязан экспортировать `modules/onboarding/index.ts` (заведён тикетом DTJ-070 того же
эпика; т.к. оба модуля разрабатываются одним тимлидом в одном комплекте тикетов, здесь фиксируется
точная сигнатура, которую DTJ-070 обязан реализовать без переговоров). Идемпотентность —
общий механизм `Idempotency-Key` из `12-api-conventions...md` §1.4 (инфраструктура EP-01,
интерцептор/декоратор `@RequireIdempotencyKey()` — этот тикет ТОЛЬКО применяет декоратор к
эндпоинту, не реализует сам механизм).

## Что сделать
1. `application/ports/chain-eligibility.port.ts`: `ChainEligibilityPort` — метод
   `getEligibility(chainId: string): Promise<{ status: 'draft'|'pending_review'|'changes_requested'|
   'approved'|'active'|'rejected'|'suspended'|'terminated'; isWhitelabelRequested: boolean } | null>`.
2. `infrastructure/adapters/onboarding-chain-eligibility.adapter.ts`: реализация вызывает
   `OnboardingFacade.getChainEligibilityForWhitelabel(chainId)` (импорт ТОЛЬКО из
   `@/modules/onboarding` — публичный барабанный экспорт, не внутренние файлы модуля).
3. `application/use-cases/provision-tenant.use-case.ts`: `ProvisionTenantUseCase.execute({ chainId,
   slug, initialBrandName }: ProvisionTenantCommand)`:
   - `TenantSlug.parse(slug)` — форматная валидация + проверка на `RESERVED_SLUGS` (DTJ-050) →
     `ReservedTenantSlugError` при совпадении.
   - `chainEligibilityPort.getEligibility(chainId)` — `null` или `status` вне `{'approved',
     'active'}` → доменная ошибка (переиспользуется `ParentChainNotActiveError` по аналогии с
     существующим каталогом ошибок домена — она же используется `PharmacyAccount.activate()`,
     семантически подходит: «родительская сущность ещё не в подходящем статусе»). `
     isWhitelabelRequested !== true` → отдельная ошибка `ChainNotWhitelabelRequestedError` (новый
     класс, `domain/errors` этого модуля, `409 CONFLICT`-семейство).
   - `tenantRepository.findByChainId(chainId)` уже существует → `409`, доменная ошибка «тенант уже
     существует для сети» (новый класс `TenantAlreadyProvisionedError`).
   - Внутри единицы работы (`unitOfWork.run()` — общий механизм транзакций EP-01/`infrastructure`):
     `Tenant.create(slug, { chainId, isNeutral: false })`, затем `TenantSettings` с ДЕФОЛТНОЙ
     нейтрально-серой палитрой (та же, что build-time fallback фронта, DTJ-060 — константа
     `NEUTRAL_FALLBACK_PALETTE`, определяемая в `packages/contracts/src/tenancy.ts`, единственный
     источник, переиспользуется и бэкендом здесь, и фронтендом там) и `initialBrandName`
     (обязателен, не пустая строка — SRS-TEN-038), `courierSourcingMode = 'platform_pool'`.
   - `tenantRepository.save(tenant)` + `tenantSettingsRepository.save(settings)` в одной транзакции.
   - Публикует `TenantProvisionedEvent` в `outbox` (для будущего аудита/аналитики, SRS-TEN-020).
4. `packages/contracts/src/tenancy.ts`: zod-схема `ProvisionTenantRequestSchema` (`chainId: uuid,
   slug: string, initialBrandName: string`), `NEUTRAL_FALLBACK_PALETTE` константа (объект CSS custom
   properties, серая палитра — точные HEX-значения согласовать с `packages/ui`/EP-18 при появлении
   design-токенов; на этом шаге — заглушечные, но валидные по формату HEX значения, не блокирующие
   тикет). Добавить ОДНУ строку экспорта в `packages/contracts/src/index.ts`.
5. `presentation/controllers/tenancy-admin.controller.ts`: `POST /api/v1/admin/tenants`
   (`@Roles('super_admin')`, `@RequireIdempotencyKey()`) — маппинг DTO → `ProvisionTenantCommand`
   → use case → `201` с созданным тенантом.

## Критерии приёмки
1. Given `pharmacy_chains.status = 'approved'`, `is_whitelabel_requested = true`, тенанта для этой
   сети ещё нет, When `POST /admin/tenants { chainId, slug: 'sifat-pharma', initialBrandName: 'Sifat
   Pharma' }` от `super_admin` с `Idempotency-Key`, Then `201`, тенант создан, `tenant_settings`
   содержит нейтрально-серую дефолтную палитру и переданное имя бренда.
2. Given `pharmacy_chains.status = 'pending_review'` (ещё не одобрена), When тот же вызов, Then
   отклонено доменной ошибкой (аналог `ParentChainNotActiveError`), тенант не создан.
3. Given `slug = 'admin'` (зарезервированное значение), When вызов, Then `ReservedTenantSlugError` →
   `400`.
4. Given запрос без заголовка `Idempotency-Key`, When `POST /admin/tenants`, Then `400
   IDEMPOTENCY_KEY_REQUIRED` — негативный сценарий (эндпоинт создания тенанта в списке обязательных
   по аналогии с уже перечисленными в `12-api-conventions...md` §1.4, расширяет список этим
   эндпоинтом по прямому указанию SRS-TEN-021).
5. Given тенант для `chainId` уже существует, When повторный вызов с тем же `chainId`, Then `409`,
   `TenantAlreadyProvisionedError`.

## Риски и подводные камни
- Прямая межмодульная зависимость `tenancy → onboarding` СОЗДАЁТ порядок разработки: адаптер этого
  тикета не скомпилируется, пока `modules/onboarding/index.ts` не экспортирует нужный метод
  (DTJ-070). В рамках эпика это не блокер (оба тикета в одном комплекте одного тимлида), но при
  параллельной разработке разными разработчиками — координация обязательна, `depends_on` в
  метаданных тикета намеренно НЕ включает DTJ-070 (чтобы не заблокировать волну 2 EP-02 ожиданием
  волны 3 EP-03) — вместо этого адаптер на первом шаге можно временно реализовать как
  `StubChainEligibilityAdapter`, возвращающий фиксированный ответ, с явным `TODO(DTJ-070)`,
  переключение — отдельным маленьким PR при готовности DTJ-070.
- `NEUTRAL_FALLBACK_PALETTE` дублируется по смыслу с bootstrap-фронтендом (DTJ-060) — единственный
  источник констант в `packages/contracts`, оба места ИМПОРТИРУЮТ, не переопределяют локально.
- D-27: `packages/contracts/src/tenancy.ts` делится с `DTJ-059` в одной подволне — этот тикет
  правит файл первым (создаёт), `DTJ-059` получил `depends_on: [..., DTJ-057]`, чтобы не
  редактировать файл параллельно.
