## Задача
Заявка отдельной аптечной точки — второй, обязательный шаг конвейера онбординга. Специфика этого
use case — прозрачное создание `PharmacyChain` «на лету» для соло-аптеки без сети (REQ-ONBOARD-2):
заявитель заполняет ОДНУ форму, разделение на два агрегата невидимо пользователю — без этого
единый UX-пайплайн (обязательное требование) невозможен.

## Технический контекст
Слой `application`. `POST /api/v1/onboarding-documents` — отдельный эндпоинт загрузки файлов ДО
финальной отправки формы (тот же паттерн, что `prescription_image_url`, Charter §3.6.3), возвращает
`{ url }`, подставляемый клиентом в поле формы. `ObjectStoragePort` — если общий порт уже определён
в другом модуле (например, `prescriptions`/EP-01 инфраструктура MinIO), этот тикет ПЕРЕИСПОЛЬЗУЕТ
его через существующий публичный интерфейс, а не создаёт параллельный; порт в
`files_owned` объявлен НА СЛУЧАЙ, если к моменту реализации общего порта ещё нет — тогда этот тикет
временно вводит его здесь с намерением поднять в общий `packages/contracts`/shared-слой позже
отдельным рефакторинг-тикетом (правило EP-18 п.6 `00-EPICS.md`, применённое по аналогии).

## Что сделать
1. `application/ports/object-storage.port.ts` (только если общий порт ещё не существует —
   ПРОВЕРИТЬ перед созданием): `ObjectStoragePort` — `upload(file: { buffer: Buffer; mimeType:
   string; sizeBytes: number }, options: { bucket: string; allowedMimeTypes: string[]; maxSizeBytes:
   number }): Promise<{ url: string }>` — бросает `UnsupportedMediaTypeError`/`PayloadTooLargeError`
   при нарушении ограничений (`image/*`, `application/pdf`, ≤10 МБ, bucket `onboarding-docs`).
2. `presentation/controllers/onboarding-documents.controller.ts`: `POST /api/v1/onboarding-documents`
   (`@Public()`, `multipart/form-data`, `@fastify/multipart`) — валидирует MIME/размер ДО передачи в
   порт (fail-fast), возвращает `201 { data: { url } }`.
3. `infrastructure/repositories/pharmacy-account.repository.ts`: `PharmacyAccountRepository` —
   `findById`, `save` (аналогично DTJ-064 для `PharmacyChain`).
4. `application/use-cases/submit-pharmacy-application.use-case.ts`:
   `SubmitPharmacyApplicationUseCase.execute(dto: { chainId?: string; name; addressText; landmarkTj?;
   latitude; longitude; phone; isOpen247; openingTime?; closingTime?; licenseNumber;
   licenseIssuingAuthority; licenseIssueDate; licenseExpiryDate; licenseScanUrl;
   pharmacistInChargeName })`:
   - Given `chainId` не передан (соло-аптека), Then СНАЧАЛА вызывает
     `SubmitChainApplicationUseCase.execute({ legalEntityName: dto.name, tinInn: <отдельное
     обязательное поле формы соло-заявки, добавляется в контракт>, legalAddress: dto.addressText,
     directorFullName: dto.pharmacistInChargeName, contactPhone: dto.phone })` (внутримодульный вызов
     use case, не HTTP) — получает `chainId` созданной сети с ОДНОЙ дочерней точкой.
   - `PharmacyAccount.submit(dto)` (доменная фабрика DTJ-063, `status='draft'`, `chainId` теперь
     всегда заполнен — либо переданный, либо только что созданный).
   - Сохраняет, возвращает `{ id, chainId, status: 'draft' }`.
5. `packages/contracts/src/onboarding.ts` (файл уже существует после DTJ-064, дополняется):
   `SubmitPharmacyApplicationRequestSchema` — все поля из п.4 + `tinInn` опционально (обязателен
   ТОЛЬКО когда `chainId` отсутствует — через `.superRefine`).
6. `presentation/controllers/pharmacy-accounts-public.controller.ts`: `POST
   /api/v1/pharmacy-accounts` (`@Public()`) → use case → `201`.

## Критерии приёмки
1. Given `chainId` передан (аптека существующей сети), When `POST /pharmacy-accounts`, Then создаётся
   ТОЛЬКО `PharmacyAccount`, `pharmacy_chains` не затронута.
2. Given `chainId` НЕ передан, When `POST /pharmacy-accounts` с полным набором полей соло-заявки,
   Then создаются ОБЕ сущности: новая `PharmacyChain` (с одной дочерней точкой) и `PharmacyAccount`,
   `pharmacyAccount.chainId` указывает на только что созданную сеть.
3. Given `POST /onboarding-documents` с файлом 11 МБ, When запрос, Then `413 PAYLOAD_TOO_LARGE` до
   полного разбора тела.
4. Given `POST /onboarding-documents` с `Content-Type: application/zip`, When запрос, Then `415
   UNSUPPORTED_MEDIA_TYPE`.
5. Given успешная загрузка PDF-скана лицензии, When `POST /onboarding-documents`, Then возвращён `{
   url }`, который клиент подставляет в `licenseScanUrl` следующего вызова `POST /pharmacy-accounts`
   — сквозной интеграционный сценарий (загрузка → подача формы с этим URL → успешное создание).

## Риски и подводные камни
- Основной риск тикета — дублирование `ObjectStoragePort`, если модуль `prescriptions` (или другой,
  первым нуждающийся в загрузке файлов) уже определил эквивалентный порт к моменту реализации;
  явно предписано проверить перед созданием (см. DoD) — при обнаружении дубликата использовать
  существующий порт через его публичный экспорт, файл `object-storage.port.ts` из `files_owned`
  тогда не создаётся, а заменяется прямым импортом (отклонение от заявленного `files_owned`
  документируется в PR).
- Соло-заявка создаёт `PharmacyChain` СИНХРОННО внутри одной транзакции с созданием
  `PharmacyAccount` (обе доменные операции — часть одного `unitOfWork.run()`) — если по факту
  `SubmitChainApplicationUseCase` (DTJ-064) реализован с собственной внутренней транзакцией, здесь
  требуется рефакторинг на переиспользуемый доменный метод БЕЗ транзакции (`application`-orchestration
  оборачивает обе операции ОДНОЙ внешней транзакцией) — уточнить при интеграции, не блокирует
  написание тикета, но важно для реализующего разработчика.
