## Задача
Клиентские UX-события (`search_performed`, `analog_shown`, `analog_clicked`, `added_to_cart`) не
известны серверу иначе — это события интерфейса, а не результат серверного use case. Приём ОБЯЗАН
быть мгновенным (`202 Accepted` немедленно) и батчируемым, чтобы аналитика НИКОГДА не замедляла
пользовательский путь (`SRS-ADM-067`).

## Технический контекст
Единственный ПУБЛИЧНЫЙ (без строгой ролевой проверки — доступен `customer` и гостю без JWT, т.к.
`search_performed` может происходить ДО логина) эндпоинт этого эпика. Использует
`AnalyticsFacade.recordEvent` (`DTJ-378`), добавляет батчевую обёртку. `savingsDiramAtAdd` для
`added_to_cart` — снэпшот экономии НА МОМЕНТ добавления (цена аптеки может измениться до заказа,
`SRS-ADM-068`) — клиент обязан передать уже вычисленное значение, сервер НЕ пересчитывает его
(сервер в этот момент не обязан знать текущую цену — расчёт был на клиенте в момент рендера
карточки, пересчёт на сервере создал бы гонку с реальным изменением цены).

## Что сделать
1. `packages/contracts/src/analytics.ts` — Zod-схема `ProductEventInputSchema` (`eventType` —
   union 5 обязательных значений (+расширяемо), `sessionId` обязателен, `medicineId?`,
   `pharmacyId?`, `savingsDiram?`, `metadata?` — свободный JSON, ограниченный разумным размером
   (`.refine` на `JSON.stringify(metadata).length < 4096` — защита от неограниченно большого
   payload через это поле)), `ProductEventsBatchSchema = z.array(ProductEventInputSchema).max(50)`
   (ограничение размера батча — защита от избыточной нагрузки одним запросом) + строка экспорта в
   корневой `packages/contracts/src/index.ts`.
2. `RecordProductEventsBatchUseCase.execute({ events, actor?, tenantId, sessionId }): Promise<void>`
   — резолвит `userId = actor?.userId ?? null` (гость допустим, `SRS-ADM-067`), делегирует
   `AnalyticsFacade.recordEvent` для КАЖДОГО элемента батча. Given один элемент батча содержит
   невалидный `eventType` (прошёл мимо Zod из-за версионного рассинхрона клиент/сервер — защитный
   сценарий) → этот ОДИН элемент пропускается с логированием предупреждения (pino `warn`, не
   `error` — не критично для бизнес-процесса), ОСТАЛЬНЫЕ элементы батча обрабатываются (частичный
   успех — телеметрия не блокирует друг друга).
3. `AnalyticsEventsController`: `POST /api/v1/analytics/events` — БЕЗ `@Roles(...)` (доступен без
   JWT — `catalog:search`-подобная публичность, `12-api-conventions...md` §4.1 паттерн), но ЕСЛИ
   JWT передан — `actor` резолвится обычным guard'ом аутентификации (опциональная, не обязательная
   проверка токена). Ответ — ВСЕГДА `202 Accepted` НЕМЕДЛЕННО (обработка батча — синхронная внутри
   запроса в R1, т.к. `INSERT` в `product_events` быстр и не требует отдельной очереди; `fire-and-
   forget` — по семантике ответа клиенту, не по факту асинхронного выполнения на сервере —
   уточнение спецификации: обработка сервером синхронна и быстра, но КЛИЕНТ не ждёт и не проверяет
   результат, что и создаёт субъективный эффект «fire-and-forget» для UX).
4. Rate-limiting: применяется существующий глобальный `@fastify/rate-limit` (`EP-01`), без
   специальной настройки для этого эндпоинта в R1 (не блокирующий фактор для реализации — только
   не отключать общий rate-limit для этого пути явным исключением без причины).

## Критерии приёмки
1. Given батч из 10 валидных событий, When `POST /analytics/events`, Then `202 Accepted`
   НЕМЕДЛЕННО (без ожидания завершения всех 10 вставок клиентом — тест измеряет, что ответ уходит
   ДО или сразу после начала обработки, не после гарантированного завершения всех side-эффектов,
   если архитектура выбрала async-диспетчеризацию; при синхронной реализации — просто быстрый ответ).
2. Given батч из 51 события, When Zod валидирует, Then `400 VALIDATION_ERROR` (превышен лимит
   размера батча — `.max(50)`).
3. Given один элемент батча из 5 содержит `eventType='unknown_future_event'`, When батч
   обрабатывается, Then ОСТАЛЬНЫЕ 4 события успешно записаны в `product_events`, невалидный элемент
   пропущен с предупреждением в логе (частичный успех, не полный отказ батча).
4. Given запрос БЕЗ заголовка `Authorization` (гость), When `POST /analytics/events` с
   `eventType='search_performed'`, Then `202 Accepted` — эндпоинт не требует аутентификации.

## Риски и подводные камни
- `savingsDiramAtAdd`/`savingsDiram` — клиент передаёт значение, вычисленное НА КЛИЕНТЕ в момент
  показа/добавления — сервер НЕ проверяет его математическую корректность против текущей цены (это
  сознательно: цель поля — зафиксировать, ЧТО пользователь ВИДЕЛ в момент действия, включая
  устаревшие данные, а не пересчитанную постфактум «правильную» цифру) — не «исправлять» это поле
  при реализации, считая его багом.
- Публичный эндпоинт без ролевой проверки — потенциальная цель для спама/накрутки метрик воронки
  (никто не мешает боту слать поддельные `order_placed` без реального заказа). `SRS-ADM-069`
  считает РЕАЛИЗОВАННУЮ экономию ТОЛЬКО по факту `order_placed` СО ССЫЛКОЙ `orderId` — сервер
  проверяет существование `orderId` при построении воронки (`DTJ-381`), не здесь — но для событий
  БЕЗ `orderId` (`search_performed`/`analog_shown`/`analog_clicked`/`added_to_cart`) накрутка
  технически возможна и не блокируется этим тикетом (rate-limiting — единственная защита в R1,
  усиление — вне скоупа, отдельный ADR при доказанной проблеме).
