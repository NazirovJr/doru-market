## Задача
`pharmacy_admin` следит за заказами своей сети НА УРОВНЕ МОНИТОРИНГА (сколько заказов, есть ли
просрочка SLA сборки), не на уровне интерактивной сборки конкретного заказа (та — экран роли
`pharmacist`, вне этого эпика, модуль Orders/Fulfillment). Без обзорного списка владелец сети не
видит операционную картину без опроса каждой точки вручную.

## Технический контекст
Реализует `orders:read:pharmacy` (`12-api-conventions-auth-tenancy.md` §4.1) — использует
`OrdersFacadePort`, расширенный `DTJ-355` (`findOrdersAny` переиспользуется с принудительным
`pharmacyId ∈ actor.ownPharmacyIds` — тот же паттерн ограничения scope, что `DTJ-362`). Вычисляемое
поле `slaBreached` (`now() > sla_deadline_at AND status='processing'`) — вычисляется НА СТОРОНЕ
`OrdersFacade` (домен `orders`, `EP-09`/`EP-10`), этот тикет только передаёт фильтр и отображает
готовый признак, не пересчитывает SLA самостоятельно (единственный источник истины).

## Что сделать
1. Расширить `OrdersFacadePort.findOrdersAny` (или добавить отдельный метод
   `findOrdersByPharmacyIds`, если сигнатуры разойдутся по фильтрам — решение на месте по факту
   реализации `DTJ-355`) поддержкой фильтра `filter[slaBreached]=true`.
2. `ListOrdersOwnUseCase.execute({ filter, pagination, actor })` — резолвит
   `pharmacyId ∈ actor.ownPharmacyIds` СЕРВЕРОМ (не из query), делегирует
   `OrdersFacadePort`, добавляет фильтр по статусу и `slaBreached`.
3. Добавить в существующий `orders-admin.controller.ts` (`DTJ-355`) метод `GET
   /api/v1/orders?scope=own` — `@Roles('pharmacy_admin', 'super_admin')` (для `super_admin` с
   `scope=own` — семантически бессмысленно, т.к. у него нет `ownPharmacyIds`; use case возвращает
   пустой список для этой комбинации, не ошибку — задокументировать поведение явно, не оставлять
   неопределённым).
4. Frontend: `own-orders-page.tsx` — таблица заказов сети (номер, аптека точки, статус — Badge,
   признак просрочки SLA — Badge `danger` при `slaBreached=true`), фильтры (статус, просрочка SLA).
   Это ОБЗОРНЫЙ список — клик на заказ ведёт на READ-ONLY карточку (переиспользует
   `order-detail-page.tsx` из `DTJ-355` в режиме без кнопок `payment-override`/`force-cancel` —
   те видны ТОЛЬКО `super_admin`, компонент уже получает роль актора и скрывает секцию действий).

## Критерии приёмки
1. Given `pharmacy_admin` сети `A` (2 точки), When `GET /orders?scope=own`, Then видит заказы ТОЛЬКО
   этих 2 точек, никаких заказов других сетей.
2. Given заказ в `processing` с `now() > sla_deadline_at`, When список рендерится с фильтром
   `filter[slaBreached]=true`, Then заказ включён; заказ `delivered` с истёкшим по времени, но уже
   завершённый SLA-окном, НЕ включён (признак не путает «был просрочен когда-то» и «просрочен
   сейчас» — определение `slaBreached` требует `status='processing'` одновременно с условием
   времени).
3. Given `customer` вызывает `GET /orders?scope=own`, When guard проверяет `@Roles`, Then `403
   INSUFFICIENT_ROLE` (эндпоинт для этого `scope` недоступен клиентской роли — у клиента свой
   `orders:read:own` эндпоинт, вне этого эпика).

## Риски и подводные камни
- Прямая зависимость от `DTJ-355` (общий контроллер и общий компонент карточки заказа) —
  координация порядка аналогична риску `DTJ-353`/`DTJ-362`.
- Вычисление `slaBreached` — полностью на стороне `OrdersFacade` (`EP-09`/`EP-10`), этот тикет не
  реализует собственную формулу `now() > sla_deadline_at` — если фасад ещё не поддерживает такой
  фильтр на момент разработки, гостевая правка одной строки в чужом facade (см. риски `DTJ-350`).
