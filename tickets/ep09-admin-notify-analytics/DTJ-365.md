## Задача
Единственный способ подключить 1С-модуль аптеки к платформе (D-11) — API-ключ + HMAC-секрет.
Экран технически прост по CRUD, но КРИТИЧЕН по безопасности: секрет показывается ОДИН РАЗ, никогда
больше не восстанавливается, полностью маскируется в логах. Ошибка здесь — прямая утечка
production-доступа к остаткам/ценам аптеки.

## Технический контекст
`pharmacy_api_keys` — таблица УЖЕ существует в исходной схеме (`03-ARCHITECT-DECISIONS.md` Часть C
п.8: `argon2`-хеш, `require_mtls`, ротация). Владеет модуль `inventory`/`onboarding` (точное
размещение — решение `EP-05`/`EP-03`, здесь используется через новый узкий
`PharmacyApiKeysFacadePort`, создаваемый этим тикетом). `crypto.randomBytes(32)` — генерация СЛУЧАЙНО,
не производные от предсказуемых данных (`SRS-ADM-043`). Маскирование в логах — через общий список
чувствительных полей (`packages/contracts/src/sensitive-fields.ts`), вводимый `DTJ-375` — этот
тикет добавляет `apiKey`/`hmacSecret` в тот список СВОЕЙ строкой (координация, не блокирующая
зависимость: до готовности `DTJ-375` — локальный pino-редактор полей на уровне этого модуля,
заменяемый на общий по готовности).

## Что сделать
1. `PharmacyApiKeysFacadePort`: `create(pharmacyId, actor): Promise<{ id, apiKey, hmacSecret,
   keyPrefix }>` (генерирует ОДИН РАЗ), `list(pharmacyId): Promise<PharmacyApiKeySummaryDto[]>`
   (БЕЗ полных значений — только `{ id, keyPrefix, isActive, requireMtls, createdAt, lastUsedAt,
   revokedAt }`), `rotate(keyId, actor): Promise<{ id, apiKey, hmacSecret, keyPrefix }>`,
   `revoke(keyId, reason, actor)`, `setRequireMtls(keyId, requireMtls, actor)`.
2. `CreatePharmacyApiKeyUseCase`/`RotatePharmacyApiKeyUseCase` — использует `crypto.randomBytes(32)`
   ВНУТРИ порта (генерация — infrastructure-ответственность, не application; use case вызывает
   порт, не генерирует секрет сам, `02` §1.3). `RotatePharmacyApiKeyUseCase` — `Idempotency-Key`
   ОБЯЗАТЕЛЕН (`12-api-conventions...md` §1.4, повторный вызов с тем же ключом идемпотентности НЕ
   создаёт вторую пару).
3. `RevokeExpiredRotatedKeysJob` (`apps/worker`, BullMQ) — по истечении
   `API_KEY_ROTATION_GRACE_PERIOD_HOURS` (ASSUMPTION 24) физически деактивирует старый ключ после
   ротации (оба ключа валидны параллельно В ТЕЧЕНИЕ окна, `SRS-ADM-045`).
4. `PharmacyApiKeysController`: `POST /api/v1/pharmacy-accounts/:id/api-keys`, `GET
   /api/v1/pharmacy-accounts/:id/api-keys`, `POST .../:keyId/rotate`, `POST .../:keyId/revoke
   { reason }`, `PATCH .../:keyId { requireMtls }` — `@Roles('pharmacy_admin', 'super_admin')`,
   policy `pharmacyId ∈ actor.ownPharmacyIds` для `pharmacy_admin` (`super_admin` — любая аптека).
5. Логгер: зарегистрировать `apiKey`/`hmacSecret` в редакторе полей pino (или временный локальный
   редактор до `DTJ-375`, см. «Технический контекст») — сериализатор ответа `create`/`rotate`
   ЯВНО помечен «не логировать целиком» комментарием в коде рядом с местом формирования ответа.
6. Frontend: `api-keys-page.tsx` — таблица (`keyPrefix`, статус, mTLS-флаг, `lastUsedAt`), кнопки
   «Создать»/«Ротировать»/«Отозвать» (последняя — с полем причины). `api-key-created-modal.tsx` —
   ЕДИНСТВЕННОЕ место, где показываются `apiKey`/`hmacSecret` целиком, с явным предупреждением
   «Секрет показан один раз, скопируйте сейчас» и кнопкой копирования — модалка закрывается ТОЛЬКО
   явным действием пользователя (не автозакрытие таймером, в отличие от Toast).

## Критерии приёмки
1. Given `POST /pharmacy-accounts/:id/api-keys` выполнен успешно, When ЛЮБОЙ последующий запрос
   (включая тот же `GET .../api-keys`), Then полный `apiKey`/`hmacSecret` НИГДЕ не встречается в
   ответе — только `keyPrefix` (`TC-ADM-017`).
2. Given ротация ключа выполнена, When запрос со СТАРЫМ ключом отправляется В ТЕЧЕНИЕ
   `API_KEY_ROTATION_GRACE_PERIOD_HOURS`, Then он валиден (`TC-ADM-018`); Given то же время истекло
   и `RevokeExpiredRotatedKeysJob` отработала, Then запрос со старым ключом → `401
   PHARMACY_API_KEY_INVALID` (`TC-ADM-019`).
3. Given `POST .../rotate` вызван ДВАЖДЫ с ОДНИМ `Idempotency-Key`, When второй запрос обрабатывается,
   Then возвращается ТОТ ЖЕ результат первого вызова (`SRS-API-010`), НЕ создаётся третья пара
   ключей.
4. Given `pharmacy_admin` сети `A` вызывает `POST /pharmacy-accounts/:id/api-keys` для аптеки сети
   `B`, When policy проверяется, Then `403 CROSS_TENANT_ACCESS_DENIED`.

## Риски и подводные камни
- `pharmacy_api_keys` — таблица существует в схеме, но её РЕАЛЬНОЕ применение (проверка подписи
  HMAC при входящем `X-Pharmacy-API-Key`) — ответственность `EP-05`/`EP-01` (принципал
  `pharmacy_system`, вне JWT-модели). Этот тикет управляет ЖИЗНЕННЫМ ЦИКЛОМ ключа (CRUD), не
  реализует middleware проверки подписи входящих 1С-запросов.
- `API_KEY_ROTATION_GRACE_PERIOD_HOURS` — `ASSUMPTION` (24 часа), конфигурируемое значение
  (`ConfigService`), не константа в коде (C6) — учесть при написании теста джобы (использовать
  тестовое переопределённое короткое значение, не ждать реальные 24 часа в тесте).
- Если `DTJ-375` (общий список чувствительных полей) сдаётся позже этого тикета — временный
  локальный редактор здесь ОБЯЗАН быть заменён на общий при готовности `DTJ-375`, не оставлен как
  параллельная реализация той же функции (риск расхождения списков, C15).
