## Задача
Общая инфраструктура экспорта, переиспользуемая ЛЮБЫМ отчётным экраном платформы (продажи/выплаты
аптеки — `DTJ-366`, платформенные метрики — `EP-17`): для периодов ≤31 дня — синхронный поток
файла, для более длинных — асинхронная джоба с сохранением в MinIO и polling-статусом. Без общей
реализации каждый отчётный экран изобретал бы собственный механизм экспорта — прямое нарушение
DRY (C15) и источник расхождений в поведении (разный TTL файла, разный формат имени).

## Технический контекст
Абстрактный `ReportExportPort` — интерфейс `render(reportType, params, format): Promise<Buffer |
{ exportJobId: string }>`, конкретная логика ПОСТРОЕНИЯ данных отчёта (SQL/агрегация) остаётся у
модуля-потребителя (`DTJ-366`/`EP-17`) — этот тикет знает ТОЛЬКО про формат (CSV/XLSX), хранение
(MinIO, `ObjectStorageProvider` — уже существующий порт `EP-01`/Charter §3.3) и оркестрацию
sync/async ветки, не про конкретные колонки конкретного отчёта (Interface Segregation: конкретный
рендер-датасет передаётся потребителем как уже готовый массив строк + заголовков).

## Что сделать
1. `ReportExportPort` (application): `renderSync(rows: Record<string, unknown>[], columns:
   ColumnDef[], format: 'csv'|'xlsx'): Buffer`; отдельно — `enqueueAsyncExport(reportType, params,
   format): Promise<{ exportJobId: string }>`.
2. `csv-renderer.ts`/`xlsx-renderer.ts` (infrastructure) — чистые функции сериализации массива строк
   в `Buffer` (CSV — простой `String.join`, без внешних тяжёлых зависимостей; XLSX — библиотека,
   уже согласованная `01-TECH-BASELINE.md`, если таковая зафиксирована; если нет — выбор Tech Lead
   на старте реализации, задокументировать в коде).
3. `RequestReportExportUseCase.execute({ reportType, params, format, periodDays, actor })`: Given
   `periodDays <= 31` → синхронный путь (вызывающий контроллер сам стримит `Buffer` с
   `Content-Disposition: attachment`); Given `periodDays > 31` → создаёт запись `export_jobs`
   (**[ДОПОЛНЕНИЕ]**, таблица ОТСУТСТВУЕТ в исходной схеме — минимальная миграция этим тикетом:
   `id, report_type, params jsonb, format, status, download_url, requested_by, created_at,
   completed_at`), публикует BullMQ job `GenerateReportExportJob`, возвращает `202 { exportJobId }`.
4. `GenerateReportExportJob` (`apps/worker`) — исполняет отчёт (вызывает обратно use case построения
   данных через передаваемый `reportType`-диспетчер, реализация конкретных типов — у потребителя),
   загружает в MinIO по ДЕТЕРМИНИРОВАННОМУ ключу `report-exports/{exportJobId}.{format}`
   (`SRS-ADM-085` — повторный запуск при ретрае BullMQ идемпотентно перезаписывает тот же объект, не
   плодит версии), помечает `export_jobs.status='ready'`, `download_url` — подписанный URL с TTL 1
   час (объект в MinIO — TTL bucket-политики 7 дней, отдельная настройка `report-exports` bucket).
5. `GetExportJobStatusUseCase`/`ReportExportController`: `GET
   /api/v1/reports/export-jobs/:exportJobId` — `{ status: 'processing'|'ready'|'failed',
   downloadUrl? }`.
6. Frontend: `report-export-button.tsx` — переиспользуемый компонент `packages/ui`-уровня внутри
   `apps/admin/shared` (кнопка «Скачать CSV/XLSX», при `periodDays > 31` автоматически переключается
   на polling-режим с индикатором прогресса вместо мгновенного скачивания — единый UX для ВСЕХ
   потребителей, не переизобретается каждым отчётным экраном).

## Критерии приёмки
1. Given период отчёта 20 дней, When `POST /reports/:reportType/export?format=csv`, Then ответ —
   синхронный `200` с `Content-Disposition: attachment`, файл содержит корректные данные, БЕЗ записи
   в `export_jobs`.
2. Given период отчёта 45 дней, When тот же запрос, Then `202 { exportJobId }`, запись в
   `export_jobs.status='processing'` создана НЕМЕДЛЕННО (не после завершения джобы).
3. Given `GenerateReportExportJob` успешно загрузила файл в MinIO, но упала ДО `UPDATE
   export_jobs SET status='ready'`, When BullMQ ретраит джобу, Then повторный запуск перезаписывает
   ТОТ ЖЕ объект MinIO (детерминированный ключ), финальный `status='ready'` устанавливается без
   дублирования файла (`TC-ADM-085`-подобный сценарий).
4. Given `GET /export-jobs/:id` для НЕСУЩЕСТВУЮЩЕГО `exportJobId`, When запрос, Then `404
   NOT_FOUND`.

## Риски и подводные камни
- **Пробел в спецификации**: таблица `export_jobs` НЕ описана ни в `11-database-schema.md`, ни в
  `27-module-admin-moderation-onboarding.md` §10.1, хотя `SRS-ADM-073` явно ссылается на
  `GET /reports/export-jobs/:exportJobId`. Это архитектурный пробел документа, закрываемый Tech
  Lead минимальной схемой (см. п.3 «Что сделать») — подлежит утверждению архитектором при следующей
  сверке (ADR), не самовольное расширение бизнес-логики.
- WS-событие `report.export_ready` (упомянуто `SRS-ADM-073` как альтернатива polling) — НЕ
  реализуется этим тикетом (явно вынесено спецификацией: «отдельная строка добавляется туда при
  следующей редакции документа», т.е. ещё не специфицирован формат комнаты) — только HTTP polling.
  Если WS понадобится, отдельный тикет после уточнения контракта.
- Выбор конкретной XLSX-библиотеки — если `01-TECH-BASELINE.md` не фиксирует её явно, решение
  принимается на старте реализации и документируется комментарием в коде со ссылкой на этот тикет.
