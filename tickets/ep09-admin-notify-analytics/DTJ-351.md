## Задача
`super_admin` — единственная роль, видящая ВСЕ тенанты платформы (нейтральный + White-Label сети).
Без этого экрана оператор не может проверить/поправить брендинг, ставку COD-лимита, срок холда
выплаты или другие per-tenant параметры без прямого доступа к БД — что нарушает принцип «White-Label
конфигурация без деплоя» (D-01, R3-2 фундамент). В R1 — программная форма без визуального
конструктора (полноценный конфигуратор — R3, `SRS-ADM-038`, не в этом тикете).

## Технический контекст
`application` этого тикета обращается к `Tenant`/`TenantSettings` ТОЛЬКО через `TenancyFacade`
(контекст `tenancy`, `10-domain-model.md` §«Ограниченные контексты», модуль владеет `EP-02`) — в
`modules/admin` создаётся узкий порт `TenancyFacadePort` (по аналогии с портами `DTJ-350`, добавляется
этим тикетом в `admin.module.ts`, не переопределяет существующие 4 порта). Тенант СОЗДАЁТСЯ только
побочным эффектом одобрения заявки сети с `is_whitelabel_requested=true` (владеет `EP-03`,
`SRS-ADM-027`) — `POST /api/v1/tenants` в этом тикете НЕ реализуется, только `GET`/`PATCH`.

## Что сделать
1. `TenancyFacadePort`: методы `listTenants(pagination)`, `getTenantById(id)`,
   `updateTenantSettings(tenantId, patch, actor)` — интерфейс, реализация делегируется реальному
   `TenancyFacade` в `admin.module.ts` через `useExisting`.
2. `ListTenantsUseCase`/`GetTenantUseCase` — курсорная пагинация по `SRS-API-004`, сортировка по
   умолчанию `createdAt:desc`.
3. `UpdateTenantSettingsUseCase.execute({ tenantId, patch, actor })` — валидирует `patch` Zod-схемой
   `TenantSettingsPatchSchema` (поля §«Группа C» `tenant_settings`: `brandName, brandLogoUrl,
   brandPalette (HEX-объект), codLimitDiram, holdPeriodDays, ...`), вызывает
   `TenancyFacadePort.updateTenantSettings`. Ответ — обновлённый `TenantSettingsDto`.
4. `TenantsController`: `GET /api/v1/tenants` (`@Roles('super_admin')`), `GET /api/v1/tenants/:id`,
   `PATCH /api/v1/tenant-settings/:tenantId` — маппинг доменных/`TenancyFacade`-ошибок в HTTP через
   существующий `DomainExceptionFilter` (не собственный `try/catch`, C12).
5. `packages/contracts/src/admin/tenants.ts` — Zod-схемы `TenantSummarySchema`,
   `TenantSettingsPatchSchema` (только текстовые поля и HEX-строки для палитры, БЕЗ файлового
   аплоада логотипа — R1 принимает готовый URL, загрузка файла вне скоупа тикета) + строка экспорта
   в `admin/index.ts` (`DTJ-350`).
6. Frontend: `tenants-list-page.tsx` — таблица (`CursorTable` из `packages/ui`) со столбцами
   `brandName`, `slug`/`domain`, `createdAt`, клик — переход на форму настроек.
   `tenant-settings-form.tsx` — форма с текстовыми полями + HEX-инпутами для
   `brandPalette.primary/secondary/accent` (raw color input, БЕЗ визуального пикера/превью — по
   `SRS-ADM-027` явно «без визуального редактора» в R1), кнопка «Сохранить» вызывает `PATCH`,
   успех — toast `ux.success.saved` (существующий ключ), ошибка — маппинг `error.code` → текст поля.

## Критерии приёмки
1. Given `super_admin` открывает `/admin/tenants`, When список загружен, Then видит ВСЕ тенанты
   (нейтральный + White-Label), без фильтра по своему тенанту (в отличие от `pharmacy_admin`-разделов).
2. Given `PATCH /tenant-settings/:tenantId` с `codLimitDiram = -100` (невалидное значение), When
   запрос обрабатывается, Then `400 VALIDATION_ERROR` с `details.field = 'codLimitDiram'`, БД не
   изменена.
3. Given валидный `PATCH` с изменённым `brandName`, When запрос успешен, Then `GET
   /tenants/:id` немедленно отражает новое значение (без кеша, синхронная запись).
4. Given роль `pharmacy_admin` вызывает `GET /api/v1/tenants`, When guard проверяет `@Roles`, Then
   `403 INSUFFICIENT_ROLE` до входа в use case (негативный сценарий, `SRS-API-036`).

## Тест-план
Unit: `update-tenant-settings.use-case.spec.ts` (валидный патч → вызов фасада с точным payload;

невалидном вводе); `list-tenants.use-case.spec.ts` (пагинация, дефолтная сортировка). Интеграционный:
`tenants.controller.e2e.spec.ts` (401/403/200 по ролям, `PATCH` end-to-end на тестовой БД).
