## Задача
`audit_log` — единственный неизменяемый журнал для комплаенс-выгрузки по деньгам, рецептам и
платформенным ролям (Часть C п.13 решений архитектора). Это ФУНДАМЕНТ, от которого зависят
`DTJ-354` (grant-platform-role), `DTJ-356` (payment-override/force-cancel), `DTJ-359` (billing
lift-block) — без готового порта эти три тикета EP-15 не могут быть безопасно сданы (чувствительные
финансовые/ролевые действия без аудита — блокирующее архитектурное нарушение, не техдолг).

## Технический контекст
`audit_log` — таблица УЖЕ существует в исходной схеме (`11-database-schema.md` §40, дословно
приведена в контексте задачи). Владелец по `00-EPICS.md` — `apps/api/src/common/audit/**`, т.е.
СКВОЗНОЙ инфраструктурный сервис (не bounded context со своим `application`/`presentation`,
`SRS-ADM-001`: «владелец — `identity`/инфраструктурный сквозной сервис, пишется из ЛЮБОГО модуля
через общий порт `AuditLogPort`, не собственный bounded context»). Неизменяемость — на ДВУХ
уровнях ОДНОВРЕМЕННО (`SRS-ADM-064`): архитектурный (репозиторий физически не экспонирует
`update()`/`delete()`) и эксплуатационный (`REVOKE UPDATE, DELETE ON audit_log FROM app_role`) —
оба обязательны, не один вместо другого.

## Что сделать
1. Миграция `00XX_audit_log_revoke_update_delete.sql`: `REVOKE UPDATE, DELETE ON audit_log FROM
   app_role;` — дословно по `SRS-ADM-064`/§10.1 документа 27. Обычная транзакционная миграция
   (не `ALTER TYPE`, `SRS-DB-009` неприменим).
2. `AuditEntry` (domain, минимальный value object): `create({ category, entityType, entityId,
   actorUserId, action, reason?, metadata, requestId, tenantId })` — приватный конструктор,
   валидирует `metadata` НЕ содержит запрещённых полей (см. п.4 ниже) как ИНВАРИАНТ конструктора
   (не полагаться на вызывающий код — если `metadata` содержит `apiKey`, конструктор бросает
   ошибку, а не молча пропускает).
3. `AuditLogPort` (application, объявляется в `common/audit`, реэкспортируется для использования
   ЛЮБЫМ модулем): `write(entry: AuditEntryInput): Promise<void>` — ЕДИНСТВЕННЫЙ метод порта. НЕТ
   `update`/`delete`/`patch` ни в интерфейсе, ни в реализации (`SRS-ADM-064` п.1, архитектурный
   уровень защиты — сам TypeScript-интерфейс не предлагает мутирующих методов).
4. `AuditLogRepository implements AuditLogPort` (infrastructure, Drizzle) — `write()` выполняет
   ТОЛЬКО `INSERT`. Формат `metadata` — единая форма для ВСЕХ категорий: `{ before?, after?,
   requestId, extra? }` (`SRS-ADM-063`) — `before`/`after` содержат ТОЛЬКО изменившиеся поля, не
   полный снепшот. Перед `INSERT` — вызов маскирующей функции по списку чувствительных полей
   (временно — локальный список в этом файле; после `DTJ-375` — заменяется на общий
   `packages/contracts/src/sensitive-fields.ts`, см. риски).
5. `AuditLogModule` — `@Global()` NestJS-модуль (доступен ЛЮБОМУ другому модулю без явного импорта
   в каждый `<context>.module.ts` — обоснование: журнал аудита используется настолько широко
   (`DTJ-354`, `DTJ-356`, `DTJ-359`, `DTJ-376`, будущие модули `EP-10`/`EP-14`), что явный импорт в
   каждом потребителе создавал бы избыточный шум; это ЕДИНСТВЕННОЕ исключение из правила «явный
   импорт модуля» в проекте — задокументировать обоснование комментарием в самом модуле).

## Критерии приёмки
1. Given роль приложения (`app_role`), When выполняется прямой SQL `UPDATE audit_log SET reason=...`
   ЛЮБЫМ клиентом БД, Then запрос отклоняется правами БД (`REVOKE UPDATE`), НЕЗАВИСИМО от уровня
   приложения (`TC-ADM-027`) — тест подключается к БД НАПРЯМУЮ (не через ORM-репозиторий), чтобы
   исключить «репозиторий просто не предлагает метод» как единственную защиту.
2. Given `AuditLogPort` интерфейс, When статический анализ/тест интерфейса выполняется, Then он НЕ
   содержит методов `update`/`delete`/`patch` — только `write` (архитектурный уровень защиты,
   проверяемый компиляцией, не рантаймом).
3. Given `AuditEntry.create()` вызывается с `metadata.extra = { apiKey: '...' }`, When конструктор
   выполняется, Then доменная ошибка (секрет НИКОГДА не попадает в запись, даже по ошибке
   вызывающего кода — `SRS-ADM-063`).
4. Given `AuditLogPort.write()` вызывается из ДВУХ разных модулей (`DTJ-354` и гипотетический
   тестовый модуль) без явного импорта `AuditLogModule` в их `<context>.module.ts`, When приложение
   поднимается, Then DI резолвит порт успешно (подтверждение `@Global()`-регистрации).

## Тест-план
Unit: `audit-entry.spec.ts` (валидация `metadata` против списка запрещённых полей — таблица
кейсов). Интеграционный: `audit-log-revoke.e2e.spec.ts` (прямой SQL `UPDATE`/`DELETE` от имени
`app_role` — ожидаемая ошибка прав PostgreSQL, не ошибка приложения); `audit-log-repository.e2e.
spec.ts` (`write()` создаёт корректную строку, `before`/`after` содержат только изменившиеся
поля — переданный тестом полный снепшот НЕ проходит валидацию домена, если содержит неизменившиеся
поля — фиксирует дисциплину вызывающего кода на уровне контракта). Порог `domain/`+
`infrastructure/` ≥ 90 %/70 % соответственно.

- `@Global()` — единственное сознательное исключение из общего правила явных импортов модулей
  проекта; ревьюер обязан НЕ распространять этот паттерн на другие модули по аналогии без такого же
  явного архитектурного обоснования (широчайшая межмодульная используемость).
- `entity_type`/`action` в `audit_log` — свободные `VARCHAR`, не enum (уже так в исходной схеме) —
  этот тикет не вводит валидацию допустимых значений (это ответственность вызывающего кода на
  местах вызова `write()`, не самого порта — порт должен оставаться максимально общим для любых
  будущих категорий действий).
- Файл `apps/api/src/common/audit/audit-log.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
