## Задача
`order_placed` — единственное событие воронки, которое НЕ может прийти от клиента (клиент не
имеет доступа к финальному, серверу известному состоянию заказа сразу после его создания, и доверие
клиентскому сообщению об оформлении заказа было бы легко подделать). Без этого события воронка
обрывается на шаге `added_to_cart` — конверсия в заказ (ключевая метрика kill-критерия №1)
физически не может быть посчитана.

## Технический контекст
`CheckoutUseCase` — файл модуля `orders`, владение `EP-09` (внешний эпик, вне диапазона тикетов
этого документа). Правка этого тикета — ГОСТЕВАЯ, ОДНА вставка вызова
`AnalyticsFacade.recordEvent({ eventType: 'order_placed', orderId, ... })` В КОНЦЕ метода
`execute()`, ПОСЛЕ успешного коммита транзакции создания заказа (не внутри той же транзакции —
аналитика НЕ должна откатывать коммерческую операцию при её собственном сбое, `SRS-ADM-067`:
«аналитика НЕ должна замедлять пользовательский путь» распространяется и на надёжность — сбой
записи телеметрии не есть сбой заказа). Реализованная экономия
(`SRS-ADM-069`: `Σ savingsDiram по order_items, где medicine соответствует ранее показанному
дешёвому аналогу`) — ОТДЕЛЬНЫЙ расчётный сервис в `analytics`, не логика `orders`.

## Что сделать
1. `RealizedSavingsCalculator` (application service модуля `analytics`) —
   `calculate(orderId, orderItems, tenantId, sessionId): Promise<bigint>` — для каждой позиции
   заказа ищет предшествующее событие `analog_shown`/`added_to_cart` этой же `sessionId` с тем же
   `medicineId`, суммирует `savingsDiram` совпавших позиций (запрос к `ProductEventsRepositoryPort`,
   `DTJ-378`, метод `findMatchingSavingsEvents` — добавляется этим тикетом в порт).
2. `AnalyticsFacade.recordEvent` (уже существует, `DTJ-378`) — вызывается с
   `eventType: 'order_placed', orderId, savingsDiram: <результат калькулятора>` — калькулятор
   вызывается ВНУТРИ `RecordProductEventUseCase` для этого конкретного `eventType` (ветвление по
   типу события внутри use case `DTJ-378`, правка того файла — ОДНА добавленная ветка `if
   (eventType === 'order_placed')`, не переписывание всего use case).
3. Гостевая правка `apps/api/src/modules/orders/application/use-cases/checkout.use-case.ts`:
   ПОСЛЕ строки, коммитящей транзакцию создания заказа (`unitOfWork.run(...)` завершён успешно), —
   ОДИН вызов `this.analyticsFacade.recordEvent({ eventType: 'order_placed', orderId: order.id,
   tenantId, sessionId, orderItems: order.items })`. Given этот вызов бросает исключение (сбой БД
   аналитики) → ОБЯЗАТЕЛЬНО перехватывается `try/catch` ИМЕННО вокруг этого вызова (не общий
   catch всего метода) и ЛОГИРУЕТСЯ как `warn`, НЕ ре-бросается — заказ считается успешно
   оформленным независимо от судьбы аналитики (это ЕДИНСТВЕННОЕ разрешённое исключение из правила
   C12 «запрещён пустой `catch {}`» — здесь `catch` НЕ пустой, обогащает контекстом через
   pino-лог, что соответствует C12, просто НЕ ре-бросает специально по бизнес-причине).
4. `CheckoutUseCase` получает `AnalyticsFacade` через конструктор (DI, `orders.module.ts` — правка
   ОДНОЙ строки провайдера, гостевая, не переписывание файла).

## Критерии приёмки
1. Given клиент видел `analog_shown` для препарата `X` с `savingsDiram=5000` в текущей сессии,
   добавил его в корзину и оформил заказ, When `CheckoutUseCase` завершается, Then `product_events`
   содержит запись `order_placed` с `savingsDiram=5000` (реализованная экономия совпадает с
   показанной).
2. Given клиент оформил заказ БЕЗ предшествующего `analog_shown` для купленных позиций (обычная
   покупка без сравнения аналогов), When `order_placed` записывается, Then `savingsDiram=0`/`NULL`
   (не ошибка — просто нет реализованной экономии для этого заказа).
3. Given `AnalyticsFacade.recordEvent` бросает исключение (симулированный сбой БД аналитики в
   тесте), When `CheckoutUseCase.execute()` выполняется, Then заказ ВСЁ РАВНО считается успешно
   созданным (метод возвращает успех клиенту), ошибка аналитики залогирована, но НЕ пробрасывается
   наружу — негативный сценарий надёжности.
4. Given ДВА разных `sessionId` (гость сменил сессию между просмотром аналога и заказом — например,
   очистил cookies), When расчёт реализованной экономии выполняется, Then `savingsDiram=0` для
   этого заказа (совпадение ищется СТРОГО в пределах одной сессии — намеренное консервативное
   ограничение, не пытается связывать события через `userId` как запасной путь в R1).

## Тест-план
Unit: `realized-savings-calculator.spec.ts` (совпадение по `sessionId`+`medicineId` → сумма;
отсутствие совпадения → 0; разные сессии → не совпадают). `checkout.use-case.spec.ts` (расширение
существующего набора тестов `EP-09`, ЭТОТ тикет ДОБАВЛЯЕТ кейс: сбой `AnalyticsFacade` не влияет
на результат заказа — координировать с владельцем файла, чтобы не сломать существующие тесты).
Интеграционный: `checkout-analytics-integration.e2e.spec.ts` (сквозной сценарий: показ аналога →
корзина → заказ → проверка записи `order_placed` с корректной экономией). Порог `application/` ≥
90 % для `RealizedSavingsCalculator`.

## Риски и подводные камни
- **Межэпиковая координация ОБЯЗАТЕЛЬНА**: этот тикет физически правит файл, которым владеет
  `EP-09` (`00-EPICS.md`: `apps/api/src/modules/orders/domain,application/{cart,checkout}/**`).
  Перед реализацией согласовать точное место вставки вызова с командой `EP-09` (после какой именно
  строки — до или после публикации `OrderPaidEvent`-подобных событий этого же метода, если
  таковые там есть) — избегать слепого патча без синхронизации с актуальным состоянием файла на
  момент разработки (файл мог существенно измениться с момента написания этого тикета).
- **Архитектурная развилка** — та же, что зафиксирована в «Риски» `DTJ-378`: синхронный вызов
  `AnalyticsFacade` ИЗ `CheckoutUseCase` — это [F]-вызов ИЗ `orders` В `analytics`, не
  предусмотренный явно интеграционной матрицей `10-domain-model.md` (та описывает только
  `analytics ← [E]` через `outbox`). Реализация следует букве `SRS-ADM-067`/`068`, расхождение —
  предмет ADR архитектора, не самостоятельного решения на этом или последующих code review.
- `findMatchingSavingsEvents` — запрос по `(sessionId, medicineId)` в append-only таблице,
  растущей КАЖДЫМ поисковым запросом платформы (`search_performed` пишется на каждый ввод в
  поиске) — оценить необходимость индекса `idx_product_events_session` (уже в DDL `DTJ-378`)
  достаточен для приемлемой производительности при ожидаемых объёмах R1; если нет — оптимизация
  отдельным тикетом по факту профилирования.
