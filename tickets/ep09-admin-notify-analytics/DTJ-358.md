## Задача
Комиссия платформы (D-03, дефолт Rx 5% / ОТС 8% / парафармация-БАД 12%) — калиброванная гипотеза,
подлежащая коммерческому утверждению заказчиком (`03-ARCHITECT-DECISIONS.md` Часть D). Экран нужен,
чтобы менять ставки БЕЗ деплоя по мере согласования реальных цифр с заказчиком, с учётом
специфичности (тенант/сеть/категория) и периодов действия — без ретроактивного пересчёта уже
оформленных заказов.

## Технический контекст
`platform_fee` — таблица `payments`/`billing`-контекста (владеет `EP-10`), резолвинг ставки по
специфичности уже полностью специфицирован доменом (`SRS-DOM-160`) и ГАРАНТИРОВАННО снэпшотится в
`order_items.platform_fee_diram` в момент оформления (`SRS-DOM-008`) — этот тикет НЕ трогает домен
резолвинга, только CRUD-обёртку через `PaymentsFacadePort` (расширяется методами
`listCommissionRates`/`upsertCommissionRate`). UI обязан явно предупреждать о нератроактивности
(`SRS-ADM-035`) — не полагаться на то, что оператор помнит документацию.

## Что сделать
1. Расширить `PaymentsFacadePort`: `listCommissionRates(filter: { tenantId?, chainId?, category?
   }, pagination)`, `upsertCommissionRate({ tenantId?, chainId?, category, rateBps,
   effectiveFrom, effectiveTo?, actor })`.
2. `UpsertCommissionRateUseCase` — Zod-валидация: `rateBps` 0..10000 (0–100.00%), `effectiveFrom <
   effectiveTo` если оба заданы, `category ∈ {'rx','otc','parapharmacy'}` (те же 3 категории, что
   дефолты D-03). НЕ проверяет пересечение периодов действия для одной специфичности — эта
   валидация уже существует в домене `SRS-DOM-160` (единственный источник, не дублировать здесь).
3. `CommissionRatesController`: `GET/POST/PATCH /api/v1/finance/commission-rates` —
   `@Roles('super_admin')` (`tenancy:manage-commission-rates`, `12-api-conventions...md` §4.1).
4. Frontend: `commission-rates-page.tsx` — таблица текущих и будущих ставок (тенант/сеть/категория,
   ставка %, период действия), форма добавления/редактирования с ПОСТОЯННО видимым баннером-
   предупреждением (не модалка-подтверждение, а статичный текст на форме) — ключ `admin.finance.
   commission_rate_not_retroactive_warning`: «Изменение не повлияет на уже оформленные заказы».

## Критерии приёмки
1. Given форма редактирования ставки открыта, When рендерится, Then предупреждение о
   нератроактивности видно БЕЗ дополнительного действия пользователя (не за раскрывающимся
   тултипом).
2. Given `POST /finance/commission-rates` с `rateBps = 15000` (150%, вне диапазона), When Zod
   валидирует, Then `400 VALIDATION_ERROR`.
3. Given ставка успешно создана с `effectiveFrom = <будущая дата>`, When существующий заказ
   оформляется СЕГОДНЯ, Then комиссия заказа снэпшотится по ставке, действующей НА МОМЕНТ
   оформления (проверяется косвенно — этот тикет не переоткрывает `SRS-DOM-160`, но негативный
   тест на use case подтверждает, что `upsert` не переписывает существующие `order_items`).
4. Given `pharmacy_admin` вызывает `GET /finance/commission-rates`, When guard проверяет `@Roles`,
   Then `403 INSUFFICIENT_ROLE` (доступ строго `super_admin`, `12-api-conventions...md` §4.1 —
   `pharmacy_admin` не имеет `tenancy:manage-commission-rates` даже для своей сети).

## Тест-план
Unit: `upsert-commission-rate.use-case.spec.ts` (валидация диапазона `rateBps`, `effectiveFrom <
effectiveTo`, некорректная `category` → `ZodError`). Интеграционный:

меняется после `PATCH` ставки). Порог `application/` ≥ 90 %.

## Риски и подводные камни
- Резолвинг ставки по специфичности (`SRS-DOM-160`) и снэпшотирование (`SRS-DOM-008`) — целиком
  ответственность `EP-10`, этот тикет полагается на их корректность, не проверяет её повторно
  (проверка домена — тесты `EP-10`, не дублируются здесь избыточно).
- Дефолтные ставки D-03 явно помечены `ASSUMPTION` до утверждения заказчиком — сид-данные для
  локальной разработки допустимы, но НЕ описываются в этом тикете как «финальные значения продукта».
