## Задача
Все 17 следующих тикетов этого эпика (тенанты, фиче-флаги, заказы, финансы, кабинет
`pharmacy_admin`) физически не могут стартовать параллельно без общего каркаса: единого
backend-модуля `admin` с точкой подключения фасадов чужих контекстов и единого фронтового роутера
`apps/admin`, различающего разделы `super_admin`/`pharmacy_admin` по роли из JWT. Без этого тикета
каждый следующий разработчик заново решает «как модуль admin достаёт данные онбординга/заказов/
платежей» — и решает по-разному, что ломает Правило Зависимостей (`02-CLEAN-ARCHITECTURE-AND-CODE.md`
§1). Это тикет-синхронизация волны 10, аналогичный по роли `DTJ-180` в EP-06.

## Технический контекст
`apps/admin` уже существует как приложение — каркас (`app/`, `pages/`, роутер) создан `EP-03`
(волна 3, экран верификации лицензии) согласно `00-EPICS.md` «Пересекающееся владение» п.1.
`EP-15` в волне 10 становится ГЛАВНЫМ владельцем `app/`/`pages`-роутера (добавляет разделы
`super_admin` целиком: тенанты/фиче-флаги/аптеки/пользователи/заказы/финансы/настройки — и разделы
`pharmacy_admin`: свои точки/заказы/сотрудники/ключи/отчёты/расписание) — правки вносятся ТОЛЬКО в
файлы, перечисленные в `files_owned`, существующие экраны онбординга (`EP-03`) не трогаются.

Backend-модуль `apps/api/src/modules/admin` — presentation+application слой, БЕЗ собственного домена
(`SRS-ADM-002`): use cases этого модуля обращаются к `PharmacyChain`/`PharmacyAccount` ТОЛЬКО через
`OnboardingFacade`, к `Order` — через `OrdersFacade`, к `EscrowLedger`/`PayoutSchedule` — через
`PaymentsFacade`, к остаткам — через `InventoryFacade` (все четыре фасада уже существуют как публичные
контракты соответствующих модулей, `10-domain-model.md` §«Ограниченные контексты» — этот тикет НЕ
создаёт их реализацию, только объявляет узкие подпорты application-слоя `admin`, которые в
`admin.module.ts` связываются с реальными фасадами через DI). Прямой импорт
`modules/onboarding/domain/*` или `modules/orders/infrastructure/*` из `modules/admin` — блокирующее
нарушение `02` §1.1/§1.2, ловится `pnpm arch:check`.

Guard-слой переиспользуется из `EP-01`: `@Roles('super_admin')` / `@Roles('super_admin',
'pharmacy_admin')` на контроллерах (грубая проверка роли, `SRS-API-036`), условная авторизация
(«это своя сеть», `scope=own`) — в `application/policies/*.policy.ts` этого модуля, не в guard'е.

## Что сделать
1. Создать `apps/api/src/modules/admin/admin.module.ts` — пустой NestJS-модуль с секциями
   `controllers: []`, `providers: []`, готовыми к пополнению следующими тикетами (каждый следующий
   тикет добавляет РОВНО свой контроллер/юзкейс/провайдер в существующие массивы, не переписывает
   файл целиком — см. правило C2, файл не должен превышать 300 строк по мере роста; если превысит —
   разбить на суб-модули `TenantsAdminModule`/`FinanceAdminModule`/… отдельным рефакторинг-тикетом).
2. Создать `admin/index.ts` — публичный фасад модуля `AdminFacade` (на старте — пустой интерфейс,
   заполняется по мере необходимости другими модулями, вероятно останется пустым в R1: `admin`
   типично ПОТРЕБИТЕЛЬ чужих фасадов, а не их поставщик).
3. Объявить 4 узких application-порта (`OnboardingFacadePort`, `OrdersFacadePort`,
   `PaymentsFacadePort`, `InventoryFacadePort`) — интерфейсы, содержащие ТОЛЬКО методы, которые
   реально понадобятся use case'ам admin (не копировать весь чужой фасад целиком — Interface
   Segregation). Пример метода: `OnboardingFacadePort.findPharmacyAccounts(filter): Promise<Page
   <PharmacyAccountSummaryDto>>`. Конкретные методы добавляются point-in-time каждым следующим
   тикетом (в этом тикете — только сами файлы портов с комментарием `// заполняется тикетами
   DTJ-351..367`).
4. В `admin.module.ts` связать порты с реальными фасадами через `{ provide: ONBOARDING_FACADE_PORT,
   useExisting: OnboardingFacade }` (паттерн `02` §1.3) — фасады импортируются из барабанных
   `index.ts` соответствующих модулей (`@/modules/onboarding`, НЕ `@/modules/onboarding/domain/...`).
5. Frontend: `apps/admin/src/app/router.tsx` — добавить ветку `/admin/*`, читающую роль из JWT
   (уже декодируется существующим `AuthProvider` `EP-01`/`EP-03`) и рендерящую ЛИБО набор пунктов
   меню `super_admin` (Тенанты/Фиче-флаги/Аптеки/Пользователи/Заказы/Финансы/Настройки), ЛИБО
   `pharmacy_admin` (Мои точки/Заказы/Сотрудники/Ключи 1С/Отчёты/Расписание) — единая сборка
   фронтенда, разделение только клиентским роутингом (`SRS-ADM-003`).
6. `apps/admin/src/app/role-routes.ts` — декларативная карта `role → RouteConfig[]` (путь, компонент
   лениво импортируется `React.lazy`, пункт меню, иконка) — каждый следующий тикет ДОБАВЛЯЕТ один
   элемент массива своей роли, не переписывает файл.
7. `apps/admin/src/shared/api/admin-client.ts` — тонкая обёртка над общим `packages/contracts`
   HTTP-клиентом (уже существует из `EP-01`/`EP-03` scaffolding) с базовым путём `/api/v1`, единым
   обработчиком `{ error: { code, message } }` → toast (переиспользует существующий паттерн
   `ux.error.*`, не создаёт новый).
8. `packages/contracts/src/admin/index.ts` — пустой барабанный файл-заглушка для подпапки `admin/`
   (каждый следующий тикет создаёт `packages/contracts/src/admin/<feature>.ts` и добавляет ОДНУ
   строку экспорта сюда — тот же паттерн, что `00-EPICS.md` «Пересекающееся владение» п.3 для
   корневого `index.ts`; здесь заводится подпапка, чтобы не разрастать общий баррель `EP-01`).

## Критерии приёмки
1. Given `apps/api` поднимается локально (`pnpm --filter api start:dev`), When DI резолвит
   `AdminModule`, Then приложение стартует без ошибок резолвинга портов (даже с пустыми
   контроллерами) — здоровье проверяется существующим `/health` (`@nestjs/terminus`, EP-01).
2. Given модуль `payments` (гипотетический тестовый импорт в фикстуре) пытается импортировать
   `modules/admin/application/*` напрямую в обход `modules/admin/index.ts`, When `pnpm arch:check`,
   Then `dependency-cruiser` отклоняет импорт — негативный сценарий, симметричный правилу §1.2.
3. Given пользователь с ролью `pharmacy_admin` открывает `apps/admin` (`GET /admin`), When
   `role-routes.ts` резолвит пункты меню, Then в UI отсутствуют пункты `super_admin`-раздела
   (Тенанты/Фиче-флаги/Финансы) — не просто скрыты CSS, а не смонтированы (защита от прямого
   перехода по URL — маршрут `pharmacy_admin` не существует в дереве роутера для чужой роли,
   попытка прямого URL даёт `403`-страницу, не пустой экран).
4. Given `pnpm typecheck`, Then компиляция всех новых файлов проходит без `any`/`@ts-ignore` (C7).

## Тест-план
Unit: `admin.module.spec.ts` (DI резолвит все 4 порта без ошибок при поднятии тестового модуля с
моками фасадов); `role-routes.spec.ts` (для каждой из 6 ролей `user_role` — корректный список
маршрутов, `customer`/`pharmacist`/`courier`/`support_agent` получают ПУСТОЙ список для `/admin/*`).
Интеграционный тест: `admin-module-bootstrap.e2e.spec.ts` — `apps/api` поднимается целиком с реальным
DI-графом (частично относится к `EP-19`, но контракт «модуль стартует» проверяется здесь как gate).
Порог покрытия `application/` (порты — тонкие интерфейсы, не логика) — неприменим впрямую, но файлы
включаются в общий отчёт.
