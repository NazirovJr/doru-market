## Как читать этот документ

- Тикеты пронумерованы `DTJ-350`..`DTJ-384`, сгруппированы по трём эпикам ниже.
- **Порядок выполнения** внутри каждого эпика — по номеру волны/уровню зависимости, не по номеру
  ID (номер ID отражает порядок создания тикета Tech Lead'ом, не порядок разработки).
- `depends_on`/`blocks` внутри каждого файла тикета — единственный источник истины по
  зависимостям; таблицы ниже — читаемая проекция того же графа для планирования спринта.
- Тикеты, помеченные **[координация]**, физически правят файл, которым владеет ДРУГОЙ эпик Tech
  Lead'а (`EP-03`, `EP-05`, `EP-09`, `EP-10`, `EP-13` и т.д.) — гостевая правка одной
  строки/метода, требует синхронизации с соответствующей командой ПЕРЕД реализацией, не блокирует
  сдачу этого набора тикетов формально, но риск конфликта слияния выше обычного.

## EP-15 — Админ-панель super_admin и кабинет pharmacy_admin (DTJ-350..367, 18 тикетов)

Единый backend-модуль `apps/api/src/modules/admin` (агрегирующие фасады поверх `onboarding`/
`orders`/`payments`/`inventory`) + единый фронтенд `apps/admin` (роутинг по роли из JWT, разделы
`super_admin` и `pharmacy_admin` в одной сборке).

(Auth/RBAC) и `EP-03` (scaffolding `apps/admin`). **Шаг 2** — 11 тикетов независимы друг от друга,
разрабатываются параллельно любым числом пар разработчиков. **Шаг 3** — пять тикетов, каждый либо
достраивает файл шага 2 (`DTJ-362`→`DTJ-353`, `DTJ-363`→`DTJ-355`, `DTJ-356`→`DTJ-355`), либо
зависит от `audit_log` (`EP-16`, `DTJ-374`) — **межэпиковая зависимость**, `EP-16`/`DTJ-374`
должен быть готов ДО начала `DTJ-354`/`DTJ-356`/`DTJ-359`, координировать очерёдность на уровне
спринта. **Шаг 4** — `DTJ-366` замыкает эпик, требует готовой инфраструктуры экспорта (`DTJ-361`).

## EP-17 — Продуктовая аналитика воронки R1-15 (DTJ-378..384, 7 тикетов)

Замыкающий продуктовый эпик — стартует только после готовности `DTJ-350` (`EP-15`, для размещения
экранов в `apps/admin`) и по мере готовности `EP-06`/`EP-07`/`EP-09` (источники клиентских событий
воронки, вне диапазона этого документа).

### Порядок выполнения

| Шаг | Тикет | Название | Зависит от |
|---|---|---|---|
| 1 | `DTJ-378` | Скелет модуля `analytics` + `AnalyticsFacade.recordEvent` + `product_events` | — |
| 2 | `DTJ-379` | `POST /analytics/events` — приём клиентской телеметрии | `DTJ-378` |
| 2 | `DTJ-380` | Событие `order_placed` из `CheckoutUseCase` [координация с `EP-09`] | `DTJ-378` |
| 2 | `DTJ-382` | `GET /analytics/platform-metrics` + дашборд | `DTJ-378` |
| 2 | `DTJ-384` | `GET /analytics/onboarding-funnel` + экран [координация с `EP-03`] | `DTJ-378` |

приоритетны внутри эпика относительно `DTJ-383`/`DTJ-384` (вспомогательные отчёты).

### [координация] с другими эпиками Tech Lead'ов — требует ОСОБОГО внимания

- `DTJ-380` физически правит `apps/api/src/modules/orders/application/use-cases/checkout.use-
  case.ts` (владелец файла — `EP-09`) — согласовать точное место вставки вызова ДО начала
  реализации, файл может измениться относительно состояния на момент написания этого тикета.
- `DTJ-384` читает `onboarding_review_log` через новый узкий `OnboardingFacadePort` модуля
  `analytics` — метод `getReviewDurationStats` реализуется `EP-03`, если отсутствует — гостевая
  правка одной строки в `onboarding/index.ts`.
- Вызовы `AnalyticsFacade.recordEvent` для `search_performed`/`analog_shown`/`analog_clicked` из
  модулей `catalog`/`search` (`EP-06`) и `analogs` (`EP-07`) — **НЕ входят** ни в один тикет этого
  документа (только `order_placed`, `DTJ-380`, покрыт явно). Синхронизировать с владельцами `EP-06`/
  `EP-07` отдельно — без этих вызовов воронка `DTJ-381` будет показывать нули на первых трёх шагах.

### Архитектурная развилка, вынесенная как риск в `DTJ-378`/`DTJ-380`

`10-domain-model.md` описывает контекст `analytics` как ИСКЛЮЧИТЕЛЬНО subscriber-side через
`outbox`; `27-module-admin-moderation-onboarding.md` (`SRS-ADM-067`) вводит для таблицы
`product_events` ВТОРОЙ, синхронный путь записи через факад. Реализация этого набора тикетов следует
`SRS-ADM-067` дословно (документ, детально специфицирующий именно эту таблицу); расхождение
подлежит подтверждению архитектором отдельным ADR, не переинтерпретации на code review.
