## Задача
Пять метрик платформенного здоровья, из которых ОДНА — `activePharmaciesSendingDataRate` —
ПРЯМОЙ вход для kill-критерия №2 пивота: «менее 3 из 5–10 пилотных аптек готовы присылать данные»
(`04-SCOPE-DECISION-PIVOT.md` §7). Без этого дашборда решение о продолжении/остановке пилота
принимается на глазок, а не на данных — прямое противоречие цели самого пивота (данные вместо
предположений).

## Технический контекст
Продолжает `AnalyticsDashboardController` (создан `DTJ-381`, этот тикет добавляет ВТОРОЙ метод в
ТОТ ЖЕ файл, не создаёт новый контроллер). Источники метрик — РАЗНЫЕ порты, не `product_events`:
`gmvDiram`/`averageCheckDiram` — `OrdersFacade` (через НОВЫЙ `OrdersFacadePort` в модуле
`analytics`, отдельный от одноимённого порта в `modules/admin`, т.к. это ДРУГОЙ модуль — НЕ
переиспользовать порт `EP-15` напрямую, каждый модуль объявляет свои узкие порты независимо, `02`
§1.2/1.3); `pickupSlaComplianceRate`/`deliverySlaComplianceRate`/`cancellationRate` — тот же порт;
`activePharmaciesSendingDataRate` — `InventoryFacadePort` (аналогично, свой узкий порт модуля
`analytics`).

## Что сделать
1. `OrdersFacadePort` (НОВЫЙ, в `modules/analytics`, НЕ путать с одноимённым портом `modules/
   admin`): `getGmvAndAverageCheck(tenantId, period): Promise<{ gmvDiram, orderCount,
   averageCheckDiram }>` (GMV — по заказам `status='delivered'` за период, консервативная
   методология «по факту доставки», `SRS-ADM-070`), `getSlaComplianceRates(tenantId, period):
   Promise<{ pickupSlaComplianceRate, deliverySlaComplianceRate }>`,
   `getCancellationRate(tenantId, period): Promise<number>`.
2. `InventoryFacadePort` (НОВЫЙ, в `modules/analytics`): `getActivePharmaciesSendingDataRate(
   tenantId): Promise<number>` — доля аптек со `status='active'`, у которых
   `inventory_sync_batches` за последние 7 дней содержит хотя бы одну запись ЛЮБОГО канала.
3. `GetPlatformMetricsUseCase.execute({ tenantId, period, actor })` — агрегирует все 5 метрик из
   двух портов параллельно (`Promise.all`, не последовательные `await` в цикле, C14).
4. Добавить в `AnalyticsDashboardController` метод `GET /api/v1/analytics/platform-
   metrics?period=...` — `@Roles('super_admin')`.
5. Frontend: `platform-metrics-page.tsx` — БЕЗ дизайн-референса (`32-design-reference.md`
   §«Пробелы дизайна»: «Остальные экраны `apps/admin` (платформенная аналитика GMV/SLA...) не
   нарисованы» — реализовывать строго по письменной спецификации). 5 карточек-метрик
   (`packages/ui` `StatCard`-подобный компонент, если существует в инвентаре компонентов —
   иначе простая карточка с числом+подписью), `activePharmaciesSendingDataRate` — визуально
   ВЫДЕЛЕННАЯ карточка (Badge `danger` при значении ниже порога 60% — `3 из 5` из формулировки
   kill-критерия, `ASSUMPTION`, задокументировать как таковой) — единственная метрика этого экрана
   с прямой привязкой к решению «продолжать/останавливать пилот».

## Критерии приёмки
1. Given 3 из 8 активных пилотных аптек прислали данные за последние 7 дней, When `GET
   /platform-metrics`, Then `activePharmaciesSendingDataRate ≈ 0.375` (`TC-ADM-030`).
2. Given заказы со статусами `delivered`/`cancelled`/`processing` смешаны за период, When
   `gmvDiram` вычисляется, Then учитываются ТОЛЬКО `delivered` (не `processing`, не `cancelled`,
   не `confirmed`/`paid_escrow` — GMV признаётся по факту доставки, не по факту заказа).
3. Given `pickupSlaComplianceRate` вычисляется для периода БЕЗ ни одного заказа со статусом,
   позволяющим измерить SLA (например, все ещё `processing`), When метрика рассчитывается, Then
   `0`/`null` (задокументировать выбранное поведение явно), НЕ исключение и НЕ `NaN`.
4. Given `pharmacy_admin` вызывает `GET /platform-metrics`, When guard проверяет `@Roles`, Then
   `403 INSUFFICIENT_ROLE`.

## Риски и подводные камни
- Порог `60%`/`3 из 5` для визуального выделения `activePharmaciesSendingDataRate` — вычислен Tech
  Lead ИЗ формулировки kill-критерия №2 пивота (`04-SCOPE-DECISION-PIVOT.md` §7: «менее 3 из
  5–10»), но точное число НЕ зафиксировано документом как жёсткий порог интерфейса (документ
  описывает критерий решения о судьбе продукта, не порог цвета Badge) — пометить `ASSUMPTION` в
  коде, подлежит подтверждению продуктовой командой при первой реальной сверке с пилотными данными.
- Два узких порта `OrdersFacadePort`/`InventoryFacadePort`, объявленных В МОДУЛЕ `analytics` —
  сознательно ОТДЕЛЬНЫЕ TypeScript-интерфейсы от одноимённых портов в `modules/admin` (`EP-15`),
  даже если оба в итоге связываются DI с ОДНИМ И ТЕМ ЖЕ реальным `OrdersFacade`/`InventoryFacade`
  — каждый модуль решает Interface Segregation независимо (не создавать общий «супер-порт» между
  `admin` и `analytics` ради экономии файла — это была бы связанность двух МОИХ модулей напрямую,
  что тоже запрещено правилом `02` §1.2, только не с чужим модулем, а между двумя своими).
