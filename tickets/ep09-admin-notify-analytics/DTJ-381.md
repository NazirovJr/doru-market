## Задача
ПРЯМОЙ вход для kill-критерия №1 пивота: «доля кликнувших на аналог и дошедших до заказа близка к
нулю» (`04-SCOPE-DECISION-PIVOT.md` §7). Это ключевой экран продукта — единственное место, где
команда видит, работает ли центральное УТП платформы (экономия в сомони) на реальных пользователях,
а не в гипотезе. Экран ЕСТЬ в дизайн-референсе (`32-design-reference.md` §«Аналитика») — единственный
экран этого эпика с готовым визуальным ориентиром.

## Технический контекст
`GetFunnelUseCase` агрегирует `product_events` (`DTJ-378`) по `event_type` за период, вычисляет
`conversionRates` — использует `ProductEventsRepositoryPort.countByEventType(tenantId, period,
eventTypes)`. Реализованная/показанная экономия — `SUM(savings_diram)` по соответствующим типам
события (`analog_shown` — показанная, `order_placed` — реализованная, уже посчитанная `DTJ-380`).
Дизайн-референс специфицирует: переключатель периода «Неделя/Месяц», две hero-карточки, воронка 4
шагов с шириной полосы и % конверсии от предыдущего шага, тренд реализованной экономии (7 столбцов
бар-чарта) — соответствовать буквально, включая реальные подписи оси (дизайн использует «Н1…Н7» как
упрощение демо-данных, `32-design-reference.md` §«Аналитика»: «при реализации использовать реальные
подписи оси»).

## Что сделать
1. Расширить `ProductEventsRepositoryPort`: `countByEventType(tenantId, period, eventTypes:
   string[]): Promise<Record<string, number>>`, `sumSavingsByEventType(tenantId, period,
   eventType): Promise<bigint>`, `getWeeklyRealizedSavingsTrend(tenantId, period):
   Promise<{ weekLabel: string; realizedSavingsDiram: bigint }[]>` (последние 7 периодов
   относительно выбранного окна).
2. `GetFunnelUseCase.execute({ tenantId, period, actor })` — собирает: `searchPerformed,
   analogShown, analogClicked, addedToCart, orderPlaced` (счётчики), `conversionRates: {
   shownToClicked, clickedToCart, cartToOrder, overallShownToOrder }` (деление счётчиков, защита от
   деления на 0 — `0` при пустом знаменателе, не `NaN`/`Infinity`), `totalSavingsShownDiram`
   (`sumSavingsByEventType('analog_shown')`), `totalSavingsRealizedDiram`
   (`sumSavingsByEventType('order_placed')`), `weeklyTrend`.
3. `AnalyticsDashboardController`: `GET /api/v1/analytics/funnel?period=2026-08&tenantId=...` —
   `@Roles('super_admin')` (`period` — формат `YYYY-MM` для месяца ИЛИ `YYYY-Www` для недели,
   согласовано с переключателем «Неделя/Месяц» дизайна).
4. Frontend: `funnel-page.tsx` — ТОЧНО по дизайн-референсу (`.dc.html:197-250`): переключатель
   периода (`Tabs`-компонент, `packages/ui`), две hero-карточки («Показано экономии всего» /
   «Реализовано экономии» с % от показанного), воронка 4 шагов (ширина полосы пропорциональна
   значению, % конверсии от предыдущего шага подписан на каждом сегменте), бар-чарт тренда 7
   столбцов с РЕАЛЬНЫМИ подписями оси (даты/номера недель из ответа API, не статичные «Н1…Н7»).

## Критерии приёмки
1. Given `analog_shown=100, analog_clicked=20, added_to_cart=15, order_placed=10` за период, When
   `GET /analytics/funnel`, Then `conversionRates.overallShownToOrder = 0.10` (`TC-ADM-029`).
2. Given `analog_shown=0` за период (нет данных), When расчёт `shownToClicked`, Then результат `0`,
   НЕ `NaN`/деление на ноль/исключение (защитный сценарий пустых данных — актуален на самых первых
   пилотных неделях продукта).
3. Given hero-карточка «Реализовано экономии», When рендерится, Then показывает И абсолютное
   значение (TJS), И процент от «Показано экономии» — оба числа одновременно, не одно из двух.
4. Given `pharmacy_admin` вызывает `GET /analytics/funnel`, When guard проверяет `@Roles`, Then
   `403 INSUFFICIENT_ROLE` (экран — исключительно платформенный, не доступен ни одной аптечной
   роли, даже для своей сети — воронка считается по ВСЕЙ платформе/тенанту, не по конкретной сети).

## Риски и подводные камни
- Экран — единственный в эпике с прямым дизайн-референсом; тем не менее «упрощение демо-данных»
  дизайна (подписи «Н1…Н7» для ЛЮБОГО периода, включая месячный) ЯВНО помечено в самом документе
  32 как то, что НЕ переносится буквально — не копировать этот аспект дизайна дословно.
- На первых неделях пилота (малые пилотные аптеки, kill-критерий №2) абсолютные числа воронки
  будут МАЛЫ (единицы-десятки событий) — конверсии на таких объёмах статистически шумны; экран не
  обязан ничего с этим делать специально (не требуется доверительный интервал/предупреждение о
  малой выборке в R1 — не специфицировано документом), но разработчику стоит иметь это в виду при
  тестировании на реалистично малых наборах данных, а не только на крупных синтетических.
