## Задача
Ядро `NotificationService`: единственная точка, где событие `outbox` превращается в реальную
попытку доставки конкретному пользователю конкретным каналом, с гарантией «пользователь получит
уведомление ХОТЬ КАКИМ-ТО каналом» даже при отказе внешних провайдеров (`SRS-ADM-084`) и без риска
задвоения сообщения при at-least-once доставке `outbox` (`SRS-DOM-152`, `SRS-ADM-057`). Это самый
технически рискованный тикет эпика — без него матрица `SRS-ADM-052` (14 событий) остаётся
декларацией без исполнения.

## Технический контекст
`OutboxToNotificationsConsumer` — подписчик `outbox` (паттерн `[E]` асинхронное доменное событие,
`10-domain-model.md` §«Матрица взаимодействий», строки `payments → notifications`,
`delivery → notifications`, `disputes → notifications`, `onboarding → notifications`,
`prescriptions → notifications`) — идемпотентен по `event_id` через `processed_events`
(`consumer_name='notifications.dispatch'`, механизм УЖЕ существует, `SRS-DOM-152`). Дедупликация НА
УРОВНЕ УВЕДОМЛЕНИЯ (не события) — ОТДЕЛЬНЫЙ механизм: `notifications.source_event_id` +
`UNIQUE(user_id, channel, source_event_id)` (`SRS-ADM-057`) — эти два уровня дедупликации решают
РАЗНЫЕ проблемы (consumer processed once vs один user+channel не получает дубль даже если consumer
почему-то вызван дважды для одной комбинации) и оба нужны одновременно.

## Что сделать
1. Миграция `00XX_notifications_source_event_id.sql`: `ALTER TABLE notifications ADD COLUMN
   source_event_id UUID; ALTER TABLE notifications ADD CONSTRAINT uq_notifications_dedup UNIQUE
   (user_id, channel, source_event_id);` + отдельная миграция `-- disable-transaction` для `ALTER
   TYPE notification_channel ADD VALUE 'in_app'` (`SRS-DB-009`, `SRS-ADM-078`) — ДВА разных файла
   миграции, не один (enum-расширение и обычный `ALTER TABLE` не смешиваются в одной транзакции).
2. `notification-event-matrix.ts` — константа: `Record<EventType, { recipientRoles: UserRole[];
   channels: NotificationChannel[] }>` — дословная копия таблицы `SRS-ADM-052` (14 строк), СО
   ССЫЛКОЙ в комментарии на источник (та же константа, что читает CI-тест `DTJ-369` — РЕАЛЬНОЕ
   переиспользование одного файла между `application` и `tests/arch`, устраняющее риск
   рассинхронизации, отмеченный в `DTJ-369` «Риски»).
3. `OutboxToNotificationsConsumer` — подписывается на ВСЕ `event_type` из матрицы, для каждого:
   (а) `processed_events` insert-guard (идемпотентность consumer'а); (б) резолвит получателя(ей) по
   `recipientRoles` события (например, `CourierAssignedEvent` → и `customer`, и `courier` —
   ДВЕ отдельные записи `notifications`, не одна); (в) для каждого получателя × каждого канала из
   `channels` события — вызывает `DispatchNotificationUseCase`.
4. `DispatchNotificationUseCase.execute({ userId, eventType, sourceEventId, channels, payload })`:
   ГАРАНТИРОВАННЫЙ `in_app` — СИНХРОННО (внутри этого же вызова, не через очередь) создаёт запись
   `channel='in_app'` ПЕРВОЙ, до постановки внешних каналов в очередь (`SRS-ADM-084`) — `UNIQUE`-
   конфликт `(user_id, 'in_app', sourceEventId)` перехватывается как идемпотентный no-op
   (`SRS-ADM-057`), не бросает исключение наружу. Затем — для каждого ВНЕШНЕГО канала матрицы (в
   порядке приоритета фолбэка) ставит BullMQ job в очередь `notification-dispatch`.
5. `notification-dispatch.processor.ts` — обрабатывает job одного канала: рендерит шаблон
   (`NotificationTemplatesRepositoryPort`, локаль — из `user.locale`), вызывает
   `NotifyProviderPort.send()` соответствующего канала. Retry policy BullMQ: 3 попытки,
   экспоненциальный backoff 2с/8с/32с (`SRS-ADM-060`). Given ВСЕ 3 попытки провалились → `status=
   'failed'`, `failed_reason` заполнено, И процессор САМ ставит job СЛЕДУЮЩЕГО канала по приоритету
   матрицы (не просто завершается) — если следующего канала нет (последний в списке), запись
   помечается для панели недоставленных (`DTJ-373`), но НЕ блокирует бизнес-процесс.
6. Троттлинг Telegram: `throttle_key = 'telegram:' + chatId` передаётся в BullMQ rate-limiter
   САМОЙ очереди (≤1/сек, `SRS-ADM-061`, `REQ-TG-5`) — при превышении job ОТКЛАДЫВАЕТСЯ (BullMQ
   `rateLimiter` опция), `notifications.status` остаётся `'queued'` (НЕ `'suppressed_rate_limit'` —
   этот статус зарезервирован исключительно для дедупликации, не для временной задержки лимитом).

## Критерии приёмки
1. Given `OrderPaidEvent` публикуется дважды (at-least-once доставка `outbox`, `SRS-DOM-152`), When
   `OutboxToNotificationsConsumer` обрабатывает оба, Then `processed_events`-guard блокирует вторую
   обработку — пользователь получает уведомление РОВНО один раз (`TC-ADM-022`).
2. Given `SmsProvider` возвращает 5xx во всех 3 попытках, а `web_push`/`in_app` доступны, When
   диспетчеризация `OrderPaidEvent` для `customer` завершается, Then `notifications(channel='sms')
   .status='failed'`, НО `web_push`/`in_app` доставлены успешно (`TC-ADM-025`).
3. Given ВСЕ 4 канала недоступны одновременно (маловероятный сбой инфраструктуры), When
   `DispatchNotificationUseCase` выполняется, Then `in_app`-запись ВСЁ РАВНО создана (она пишется
   СИНХРОННО до постановки внешних каналов в очередь, не зависит от их здоровья, `SRS-ADM-084`).
4. Given `telegram_chat_id` пользователя отправляет >1 сообщения/сек (несколько событий подряд),
   When очередь обрабатывает job'ы, Then фактическая отправка Telegram не превышает 1/сек, лишние
   job'ы ОТКЛАДЫВАЮТСЯ (не отбрасываются, не переходят в `failed`).
5. Given `CourierAssignedEvent` публикуется, When консьюмер резолвит получателей, Then СОЗДАЮТСЯ
   ДВЕ независимые цепочки диспетчеризации — для `customer` и для назначенного `courier` (разные
   `userId`, потенциально разные каналы согласно матрице).

## Тест-план
Unit: `dispatch-notification.use-case.spec.ts` (синхронный `in_app` создаётся ВСЕГДА первым,
включая ветку «все внешние каналы недоступны»; `UNIQUE`-конфликт `in_app` — идемпотентный no-op, не

из логики даже если не перечислен явно в списке канала события). Интеграционный:
`outbox-to-notifications-consumer.e2e.spec.ts` (повторная публикация одного `event_id` → одна
попытка обработки), `notification-dispatch.processor.e2e.spec.ts` (реальная BullMQ-очередь на
test-container Redis, 3 ретрая с реальным backoff — таймауты теста сокращены через
переопределённую конфигурацию задержек). Порог `application/` ≥ 90 %.

## Риски и подводные камни
- Это САМЫЙ технически рискованный тикет эпика (BullMQ retry+rate-limiter+фолбэк одновременно) —
  закладывать буфер времени на интеграционное тестирование с реальным Redis test-container, не
  полагаться только на unit-тесты с моками для retry-логики (моки легко скрывают ошибки в реальной
  конфигурации BullMQ).
- `notification-event-matrix.ts` дублирует по СОДЕРЖАНИЮ таблицу `SRS-ADM-052` — при изменении
  документа архитектором ОБА места (этот файл и ссылающийся на него `DTJ-369` CI-тест) требуют
  синхронной правки; поскольку файл теперь ОДИН (не два, как было бы при независимой реализации),
  риск рассинхронизации из `DTJ-369` снят этим тикетом.
- `user.locale` — источник для выбора шаблона на нужном языке — предполагается существующим полем
  `identity` (`EP-01`). Если поле называется иначе на момент реализации, использовать реальное имя,
  не переизобретать локаль пользователя в этом модуле.
