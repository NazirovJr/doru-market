## Задача
Секрет, случайно попавший в лог ИЛИ в `audit_log`, — компрометация, которую нельзя отменить постфактум
(лог/аудит уже мог быть прочитан/выгружен). Два независимых механизма маскирования (pino-логгер,
`DTJ-368`/`DTJ-365` API-ключи; `audit_log`, `DTJ-374`) ОБЯЗАНЫ читать ОДИН список полей — иначе
неизбежно расхождение: разработчик добавит новое чувствительное поле в один список и забудет про
второй (`SRS-ADM-063`: «сериализатор записи в `audit_log` использует ТОТ ЖЕ список маскируемых
полей, что логгер»).

## Технический контекст
`packages/contracts/src/sensitive-fields.ts` — единственный источник, экспортирует константу
`SENSITIVE_FIELD_NAMES: readonly string[]` (например, `['apiKey', 'hmacSecret', 'codeHash',
'password', 'refreshToken', 'accessToken']`) и функцию `maskSensitiveFields(obj: Record<string,
unknown>): Record<string, unknown>` (рекурсивная, глубокая — маскирует по ИМЕНИ поля на ЛЮБОЙ
глубине вложенности объекта, не только на верхнем уровне, `SRS-ADM-044`: «не полагаясь на то, что
разработчик не забудет залогировать»). `pino` — редактор полей (`redact`-опция) конфигурируется ИЗ
этой же константы, не отдельным списком путей.

## Что сделать
1. `packages/contracts/src/sensitive-fields.ts` — константа `SENSITIVE_FIELD_NAMES` (объединяет
   минимальный список `DTJ-374` + `apiKey`/`hmacSecret` из `DTJ-365`) и чистая функция
   `maskSensitiveFields()` (глубокая рекурсия по объекту/массиву, заменяет значение на строку-
   маркер `'[REDACTED]'`, НЕ удаляет ключ — сохраняет форму объекта для отладки структуры).
2. `pino-redaction.config.ts` (`apps/api/src/common/logging`) — генерирует `pino` `redact.paths`
   ИЗ `SENSITIVE_FIELD_NAMES` через wildcard-паттерн `*.{field}`/`{field}` (синтаксис `redact`-опции
   `pino` — конкретный формат paths уточняется по факту версии `pino` из `01-TECH-BASELINE.md`),
   подключается в существующей конфигурации логгера (`EP-01`, гостевая правка секции `redact`, не
   переписывание всей конфигурации).
3. Обновить `apps/api/src/common/audit/infrastructure/audit-log.repository.ts` (`DTJ-374`) —
   заменить временный локальный список на импорт `maskSensitiveFields` из
   `packages/contracts/src/sensitive-fields.ts` (убрать `TODO(DTJ-375)`, оставленный `DTJ-374`).
4. Добавить строку экспорта в `packages/contracts/src/index.ts` (гостевая правка, `00-EPICS.md`
   «Пересекающееся владение» п.3).

## Критерии приёмки
1. Given объект `{ user: { apiKey: 'sec_live_123' } }` (поле на второй глубине вложенности), When
   `maskSensitiveFields()` вызывается, Then `apiKey` заменён на `'[REDACTED]'` НА ЛЮБОЙ глубине, не
   только на верхнем уровне объекта.
2. Given `pino`-логгер вызывается с объектом, содержащим `hmacSecret`, When лог сериализуется в
   тестовом выводе, Then строка `hmacSecret`-значения НИГДЕ не встречается в итоговом JSON лога
   (негативный тест на весь вывод, аналогичный `TC-ADM-017`).
3. Given `AuditLogPort.write()` вызывается с `metadata.extra` содержащим `password`, When запись
   создаётся, Then сохранённая в БД строка содержит `'[REDACTED]'` вместо значения (проверяется
   прямым чтением из БД в тесте, не только через доменную ошибку `DTJ-374` — этот тикет проверяет
   ФАКТИЧЕСКОЕ маскирование результата, `DTJ-374` проверял ОТКАЗ конструктора при явно запрещённом
   поле; после этого тикета поведение — маскирование вместо отказа, уточнить в реализации, какое из
   двух ожидается финально, см. риски).

## Риски и подводные камни
- **Решение о поведении**: `DTJ-374` специфицировал ОТКАЗ конструктора `AuditEntry.create()` при
  обнаружении запрещённого поля (fail-fast — вызывающий код обязан сам не передавать секрет). Этот
  тикет вводит МАСКИРОВАНИЕ (замену значения) как альтернативную стратегию для pino. Для
  `audit_log` — сохранить поведение `DTJ-374` (отказ, не маскирование) — журнал аудита не должен
  тихо принимать «почти секрет», лучше явная ошибка разработчика на code review. Для pino —
  маскирование (лог не может «отказаться писаться», приложение не должно падать из-за случайного
  секрета в объекте лога). Это осознанное АСИММЕТРИЧНОЕ решение Tech Lead, зафиксировать
  комментарием в обоих местах, чтобы будущий разработчик не «исправил» одно под другое по аналогии.
- Формат `redact.paths` у `pino` зависит от точной мажорной версии библиотеки — сверить синтаксис
  wildcard на старте реализации, не полагаться на память о более старой версии API.
