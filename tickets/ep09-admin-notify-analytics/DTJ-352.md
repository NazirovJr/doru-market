## Задача
Фиче-флаги — единственный способ включать R2/R3-функциональность (например,
`prescription_ocr_pipeline_enabled` для OCR, `disputes_workflow_enabled` для полного workflow споров)
БЕЗ деплоя, начиная с первого дня R1 (`04-SCOPE-DECISION-PIVOT.md` §4: «включается фиче-флагом»).
Без этого экрана `super_admin` не может ни включить готовую, но выключенную функциональность, ни
безопасно погасить сломанную в проде — прямой доступ к БД для такой операции недопустим.

## Технический контекст
Единственная таблица этого модуля с СОБСТВЕННЫМ (тривиальным) доменом внутри `modules/admin`
(`FeatureFlag` — value object уровня «resolve по специфичности», без сложных инвариантов состояния,
`02` §2 применяется частично: приватный конструктор + фабрика, но без state machine). Резолвинг
специфичности («per-tenant запись переопределяет global той же `flag_key`») — доменная логика метода
`FeatureFlag.resolve(candidates: FeatureFlag[]): boolean`, НЕ разбросана по SQL/use case (правило C18
— функция `resolve` не имеет побочных эффектов, чистая). Схема — `11-database-schema.md`
СУЩЕСТВУЮЩИХ таблиц не содержит `feature_flags` — DDL полностью взят из
`27-module-admin-moderation-onboarding.md` §10.1 SRS-ADM-028 дословно.

## Что сделать
1. Миграция `00XX_feature_flags.sql` — DDL таблицы `feature_flags` дословно по §10.1
   `27-module-admin-moderation-onboarding.md` (поля `flag_key`, `scope`, `tenant_id`, `is_enabled`,
   `rollout_percentage`, `description`, `updated_by`, `updated_at`, оба `CHECK`, `UNIQUE(flag_key,
   scope, tenant_id)`). Сид (`pnpm db:seed` дополнение, НЕ отдельная миграция с данными) —
   `prescription_ocr_pipeline_enabled` (`scope='global', is_enabled=false`) и
   `disputes_workflow_enabled` (`scope='global', is_enabled=false`) — обязательные R1-флаги.
2. `apps/api/src/db/schema/feature-flags.ts` — Drizzle-схема таблицы (infrastructure-слой, НЕ
   импортируется в `domain`/`application`, `02` §1.1).
3. `FeatureFlag` (domain): `create({ flagKey, scope, tenantId, isEnabled, rolloutPercentage,
   description })` с валидацией инварианта (`scope='tenant'` требует `tenantId`), метод
   `static resolve(candidates: FeatureFlag[]): boolean` — per-tenant запись побеждает global той же
   `flagKey`, отсутствие обеих → `false` (безопасный дефолт, неизвестный флаг не считается включённым).
4. `FeatureFlagsRepositoryPort` (application) + `FeatureFlagsRepository` (infrastructure, Drizzle) —
   `findByKey(flagKey, tenantId?)`, `list(pagination)`, `upsert(entity)`.
5. `ListFeatureFlagsUseCase`, `UpsertFeatureFlagUseCase` (валидирует `reason`-НЕ требуется явно по
   спецификации, но пишет `updated_by=actor.userId`).
6. `FeatureFlagsController`: `GET /api/v1/feature-flags`, `POST /api/v1/feature-flags`, `PATCH
   /api/v1/feature-flags/:id` (`@Roles('super_admin')`).
7. Frontend: `feature-flags-page.tsx` — таблица (флаг, скоуп, тенант если есть, `isEnabled`
   Switch-переключатель из `packages/ui`, `rolloutPercentage` числовой инпут 0–100) + кнопка
   «Добавить флаг» (форма: `flagKey`, скоуп, опционально тенант — Select из списка тенантов `DTJ-351`).

## Критерии приёмки
1. Given `feature_flags` содержит `(flagKey='prescription_ocr_pipeline_enabled', scope='global',
   isEnabled=false)` и `(scope='tenant', tenantId=X, isEnabled=true)` для того же `flagKey`, When
   `FeatureFlag.resolve()` вызывается для тенанта `X`, Then результат `true` (per-tenant побеждает).
2. Given тот же `flagKey`, тенант `Y` (без собственной per-tenant записи), When `resolve()` для `Y`,
   Then результат `false` (используется global).
3. Given `POST /feature-flags` с `scope='tenant'` без `tenantId`, When запрос обрабатывается, Then
   `400 VALIDATION_ERROR` — `CHECK`-инвариант БД дублируется на уровне Zod ДО INSERT (не полагаться
   только на ошибку БД, которая менее информативна для клиента).
4. Given `rolloutPercentage = 150` (вне диапазона), When `PATCH`, Then `400 VALIDATION_ERROR`.

## Тест-план
Unit: `feature-flag.entity.spec.ts` (`resolve()` — таблица кейсов: только global; только tenant;
оба, tenant побеждает; ни одного → `false`; невалидный `scope='tenant'` без `tenantId` в фабрике
→ ошибка домена); `upsert-feature-flag.use-case.spec.ts`. Интеграционный:
`feature-flags.controller.e2e.spec.ts` (реальная БД, `UNIQUE`-конфликт при дублирующей паре
`(flag_key, scope, tenant_id)`). Порог `domain/`+`application/` ≥ 90 %.

## Риски и подводные камни
- Другие модули (например, `prescriptions` в R2) будут ЧИТАТЬ этот флаг через
  `FeatureFlagsFacade.isEnabled(flagKey, tenantId?)` — этот тикет создаёт таблицу/CRUD, но публичный
  метод чтения для ДРУГИХ модулей (не через `apps/admin` UI, а программно) в этом тикете НЕ
  добавляется в барабанный `admin/index.ts` — заводится отдельным тикетом в момент, когда первый
  потребитель (R2 OCR) реально появится, чтобы не создавать «абстракцию без второго потребителя»
  (C15). До этого момента `prescription_ocr_pipeline_enabled` существует в схеме, но физически
  никем не читается — соответствует `04-SCOPE-DECISION-PIVOT.md` (архитектурное основание в R1,
  включение функции — в R2).
- `rollout_percentage` в этом тикете хранится, но НЕ используется ни одним потребителем (нет
  постепенного роллаута ни для одного R1-флага) — поле для будущего использования, заведено схемой
  архитектора заранее, не расширять логику домена сверх хранения значения.
