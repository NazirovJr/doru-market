## Задача
Три READ-ONLY экрана для расследований и финансовой сверки: движения по эскроу конкретного заказа,
очередь предстоящих выплат аптекам и — самое критичное — список рассинхронизаций, которые
`EscrowReconciliationJob` (`EP-10`) обнаружила автоматически, но исправить которые обязан ЧЕЛОВЕК
(«автоматическое исправление денежного расхождения запрещено архитектурой», `SRS-ADM-034`). Без
этого экрана рассинхронизация видна только в логах worker'а — операционно нежизнеспособно.

## Технический контекст
Все три источника данных — `PaymentsFacadePort` (расширяется этим тикетом). `escrow_ledger` —
append-only таблица (`SRS-DB-024`) — эндпоинт этого тикета ТОЛЬКО читает, никогда не создаёт
контроллер `POST`/`PATCH` поверх неё (архитектурный инвариант «никогда не `POST`/`PATCH` на саму
таблицу», `SRS-ADM-034`, дублируется здесь как явное ограничение реализации, не только БД-грант).

## Что сделать
1. Расширить `PaymentsFacadePort`: `findEscrowLedgerEntries(filter: { orderId? }, pagination)`,
   `findPayoutSchedule(filter: { status?, pharmacyId? }, pagination)`,
   `findReconciliationAlerts(pagination)` (возвращает заказы, где
   `hold_created != Σ(остальные записи)`, готовое расхождение — вычисляется `EscrowReconciliationJob`
   `EP-10`, здесь только чтение результата, не пересчёт).
2. `ListEscrowLedgerUseCase`/`ListPayoutScheduleUseCase`/`ListReconciliationAlertsUseCase` —
   курсорная пагинация (`SRS-API-004`), без мутирующих методов вообще (даже на уровне сигнатуры
   use case — только `execute(query): Promise<Page<T>>`).
3. `FinanceLedgerController`: `GET /api/v1/finance/escrow-ledger?filter[orderId]=...`, `GET
   /api/v1/finance/payout-schedule?filter[status]=due&filter[pharmacyId]=...`, `GET
   /api/v1/finance/reconciliation-alerts` — все `@Roles('super_admin')`, все — ТОЛЬКО `GET`
   (контроллер физически не объявляет других HTTP-методов, arch-тест `DTJ-19x` может проверить
   отсутствие `@Post`/`@Patch`/`@Delete` в этом файле).
4. Frontend: `escrow-ledger-page.tsx` — таблица движений (тип операции, сумма в дирамах →
   форматирование в TJS на границе UI, дата, ссылка на заказ). `payout-schedule-page.tsx` — таблица
   с фильтром по статусу (`due`/`paid`/...) и аптеке. `reconciliation-alerts-page.tsx` — таблица с
   визуальным акцентом (Badge `danger`) — единственный экран платформы, помеченный как «требует
   немедленного расследования» в самом UI (текст через `useT()`, новый ключ `admin.finance.
   reconciliation_alert_warning`).

## Критерии приёмки
1. Given `escrow_ledger` содержит записи для заказа `X`, When `GET /finance/escrow-
   ledger?filter[orderId]=X`, Then возвращаются ВСЕ записи в хронологическом порядке
   (`createdAt:asc` — порядок операций важен для чтения человеком, не `desc` по умолчанию, как в
   остальных списках).
2. Given `EscrowReconciliationJob` (внешний, `EP-10`) записала алерт для заказа `Y`, When `GET
   /finance/reconciliation-alerts`, Then заказ `Y` появляется в списке с суммой расхождения.
3. Given `super_admin` пытается вызвать НЕСУЩЕСТВУЮЩИЙ `POST /finance/escrow-ledger`, When
   маршрутизация, Then `404 NOT_FOUND` (метод физически не объявлен в контроллере, не `405` —
   Fastify по умолчанию для незарегистрированного пути, зафиксировать в тесте как документирующий
   инвариант «append-only на уровне presentation тоже», не только БД).

## Риски и подводные камни
- `EscrowReconciliationJob` — ответственность `EP-10` (внешний эпик, worker `apps/worker`). Этот
  тикет предполагает, что джоба УЖЕ пишет алерты в структуру, которую можно прочитать — если формат
  хранения алертов ещё не согласован на момент разработки, зафиксировать ожидаемый контракт
  `ReconciliationAlertDto` в `PaymentsFacadePort` как явную спецификацию (contract-first), не
  дожидаться реализации `EP-10` пассивно.
- Три READ-ONLY экрана логически могли бы быть одним контроллером с тремя методами — сделаны так
  намеренно (один файл, три `@Get`), не разбиты на три контроллера, чтобы не плодить файлы ради
  формальности (C2 — файл контроллера с тремя тонкими методами останется далеко ниже 300 строк).
