## Задача

Главная метрика продукта — экономия пользователя в сомони (Pivot §2.1, kill-критерии §7). Сейчас
`savingsDiram` в клиентских событиях `analog_shown`/`added_to_cart` (DTJ-379) приходит от браузера и
сервером не проверяется, а реализованная экономия заказа (DTJ-380) суммирует именно эти значения.
Одним запросом можно записать любую «экономию». Найдено при приёмке DTJ-380 (2026-09-25), решение
владельца — сервер считает экономию сам.

## Технический контекст

Экономию уже считает движок аналогов: `FindAnalogsUseCase` (`catalog`, DTJ-102..104) отдаёт
`savingsDiram = цена референса − цена аналога` в целых дирамах по офферам тенанта. Аналитика
обращается к нему только через фасад `modules/catalog/index.ts` (межмодульно — только фасад).

## Что сделать

1. Контракт клиентского события: для `analog_shown`/`added_to_cart` клиент передаёт
   `referenceMedicineId` (препарат, к которому показан аналог) и `medicineId` (аналог);
   `savingsDiram` из тела клиента больше не принимается как источник истины (поле допускается
   для совместимости, но игнорируется и не пишется).
2. Порт `AnalogSavingsPort.compute({ tenantId, referenceMedicineId, analogMedicineId, pharmacyId? })
   → Promise<bigint | null>` + адаптер поверх фасада каталога (новый метод фасада, если готового
   нет — минимально, переиспользуя расчёт `FindAnalogsUseCase`, без копии формулы).
3. Батч-приём (DTJ-379): для этих двух типов `savingsDiram` пишется из порта; `null` (аналог не
   дешевле, нет офферов, неизвестный препарат) → событие пишется с `savingsDiram = null`.
   Расчёт — батчем, без N+1 запросов на событие.
4. Реализованная экономия DTJ-380 не меняется: она суммирует уже серверные значения.

## Критерии приёмки

1. **Given** клиент прислал `analog_shown` с `savingsDiram = 100000000`, а по офферам экономия
   5000, **When** событие записано, **Then** в `product_events.savings_diram` — 5000.
2. **Given** аналог не дешевле референса, **When** `analog_shown`, **Then** `savings_diram = null`.
3. **Given** батч из 50 событий, **When** приём, **Then** к каталогу уходит не больше одного
   запроса на уникальную пару (референс, аналог), а не 50.
4. **Given** `analog_shown` → заказ этого аналога в той же сессии, **When** `order_placed`,
   **Then** реализованная экономия равна серверному значению, а не клиентскому.

## Тест-план

- Unit: адаптер (null-ветки), батч-use case (игнор клиентского значения, дедупликация пар).
- Интеграционный на живом Postgres: критерии 1, 2, 4.
