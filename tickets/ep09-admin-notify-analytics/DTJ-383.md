## Задача
Прямая проверка гипотезы REQ-MARKET-3/пивота на РЕАЛЬНЫХ данных, а не предположении: КАКИЕ именно
препараты чаще всего показываются как более дешёвый аналог, и КАК ЧАСТО это приводит к заказу.
Продуктовая команда без этого отчёта не может расставить приоритеты — например, решить, для каких
МНН в первую очередь расширять покрытие каталога/остатков.

## Технический контекст
Агрегирует `product_events` по `medicine_id` для событий `analog_shown` — группировка,
недоступная через простой `countByEventType` (`DTJ-381`), требует `GROUP BY medicine_id` — новый
метод порта. `conversionToOrder` для конкретного медикамента — доля `analog_shown` этого
`medicine_id`, за которыми в ТОЙ ЖЕ сессии последовал `order_placed` с этим же `medicine_id`
(переиспользует ЛОГИКУ, близкую к `RealizedSavingsCalculator`, `DTJ-380`, но на уровне АГРЕГАТА по
всем сессиям, не одного заказа — не переиспользует тот класс напрямую, т.к. решает другую задачу
(отчёт vs расчёт для одного заказа), но использует тот же принцип сопоставления по `sessionId`).

## Что сделать
1. Расширить `ProductEventsRepositoryPort` (`DTJ-378`): `getTopAnalogsBySavings(tenantId, period,
   limit): Promise<{ medicineId, avgSavingsDiram, timesShown, conversionToOrder }[]>` — SQL
   агрегация: `GROUP BY medicine_id` по `event_type='analog_shown'` для `avgSavingsDiram`
   (`AVG(savings_diram)`) и `timesShown` (`COUNT(*)`); `conversionToOrder` — подзапрос/JOIN с
   событиями `order_placed` той же `(session_id, medicine_id)` пары, делённый на `timesShown`.
2. `GetTopAnalogsReportUseCase.execute({ tenantId, period, limit = 10, actor })` — делегирует порту,
   возвращает медикамент-DTO, обогащённый названием (через `CatalogFacade.getMedicineSnapshot`,
   `10-domain-model.md` — уже существующий метод чужого фасада, гостевой вызов, не создание нового).
3. Добавить в `AnalyticsReportsController` (НОВЫЙ файл этого тикета, отдельный от `analytics-
   dashboard.controller.ts` `DTJ-381`/`DTJ-382` — оправдание разделения: dashboard-эндпоинты
   агрегируют платформенные числа, report-эндпоинты — построчные таблицы, разная природа ответа)
   метод `GET /api/v1/analytics/top-analogs?period=...&limit=10` — `@Roles('super_admin')`.
4. Frontend: `top-analogs-page.tsx` — БЕЗ дизайн-референса (та же оговорка, что `DTJ-382`).
   Таблица (название медикамента, средняя показанная экономия TJS, число показов, % конверсии в
   заказ — Badge цветом от величины конверсии), сортировка по умолчанию `timesShown:desc`.

## Критерии приёмки
1. Given препарат `X` был показан как аналог 50 раз с `savingsDiram` от 1000 до 3000, из них 5 раз
   привёл к заказу, When отчёт запрашивается, Then `timesShown=50`, `avgSavingsDiram` —
   среднее в диапазоне, `conversionToOrder=0.10`.
2. Given `limit=10` не передан явно, When запрос, Then применяется дефолт `10` (не возвращает ВСЕ
   препараты без ограничения — защита от неограниченного ответа).
3. Given период БЕЗ единого `analog_shown`-события, When отчёт запрашивается, Then пустой массив
   `[]` (не ошибка).

## Риски и подводные камни
- SQL-агрегация с `GROUP BY` + подзапрос конверсии на растущей append-only таблице `product_events`
  — потенциально дорогой запрос при больших объёмах; для ожидаемых объёмов пилота R1 (сотни-тысячи
  событий) не требует специальной оптимизации, но если производительность станет проблемой —
  материализованное представление/периодический пересчёт — отдельный тикет по факту профилирования,
  не преждевременная оптимизация сейчас (C15).
- `conversionToOrder` использует ТОТ ЖЕ принцип сопоставления по `sessionId`, что
  `RealizedSavingsCalculator` (`DTJ-380`) — если тот класс окажется переиспользуемым буквально
  (не только «тот же принцип», а идентичный код), рассмотреть вынесение общей утилиты ПОСЛЕ того,
  как оба тикета сданы и видно реальное дублирование (C15 — на третьем повторе, не заранее).
