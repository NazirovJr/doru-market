## Задача
Given ВСЕ каналы события отказали для конкретного пользователя (`failed` на последнем канале
фолбэк-цепочки, `DTJ-370`), диспетчер НЕ блокирует бизнес-процесс — заказ продолжает обрабатываться
независимо от того, узнал ли клиент об этом мгновенно (`SRS-ADM-060`). Но кто-то должен УВИДЕТЬ
накопление таких отказов (массовый сбой Telegram Bot API, невалидный номер телефона у клиента) —
иначе проблема остаётся невидимой до жалобы пользователя «мне ничего не пришло».

## Технический контекст
READ-ONLY диагностический экран для `super_admin` поверх `NotificationsRepositoryPort` (реализован
`DTJ-370`) — новый метод `findUndeliveredAcrossAllChannels(pagination)` (заказ, у которого
ПОСЛЕДНИЙ канал фолбэк-цепочки также `failed`, не просто «один канал failed, но следующий ещё не
попробован»). `apps/admin/src/features/notifications/**` — НОВАЯ папка фичи, не пересекается ни с
одной из уже перечисленных владений `EP-15` (`00-EPICS.md` строка EP-15: `tenants`,
`pharmacies-crud`, `users`, `orders`, `finance`) — правка `role-routes.ts` (владение `DTJ-350`,
`EP-15`) ограничивается ОДНОЙ строкой добавления пункта меню (гостевая правка, аналогичная
описанным в `00-EPICS.md` «Пересекающееся владение»).

## Что сделать
1. Расширить `NotificationsRepositoryPort` (`DTJ-370`): `findUndeliveredAcrossAllChannels(
   pagination): Promise<Page<UndeliveredNotificationDto>>` — записи, где ВСЕ каналы, назначенные
   событию по матрице (`notification-event-matrix.ts`, `DTJ-370`), имеют `status='failed'` для
   данного `(userId, sourceEventId)` (агрегирующий запрос по группе строк одного события+
   получателя, не по одной строке).
2. `ListUndeliveredNotificationsUseCase` — курсорная пагинация, сортировка `createdAt:desc`.
3. `NotificationsDiagnosticsController`: `GET /api/v1/notifications/undelivered` —
   `@Roles('super_admin')`.
4. Гостевая правка `apps/admin/src/app/role-routes.ts` (`DTJ-350`): добавить ОДИН пункт меню
   раздела `super_admin` — «Недоставленные уведомления».
5. Frontend: `undelivered-notifications-page.tsx` — таблица (получатель, событие, все
   опробованные каналы со статусами, время последней попытки), БЕЗ действий (чисто диагностический
   READ-ONLY экран — повторная отправка вручную НЕ специфицирована документом, не реализуется этим
   тикетом).

## Критерии приёмки
1. Given событие `OrderPaidEvent` для пользователя `X` — `telegram` и `sms` оба `failed`, `web_push`
   и `in_app` доставлены успешно, When экран диагностики запрашивается, Then пользователь `X` для
   ЭТОГО события НЕ появляется в списке (гарантированный `in_app` доставлен — цепочка не полностью
   провалена, `SRS-ADM-084` сработала).
2. Given у пользователя `Y` НЕТ `telegramChatId` (не открывал TWA) И `sms`/`web_push` также
   недоступны, но `in_app` ВСЕГДА создаётся синхронно (`DTJ-370`), When экран диагностики
   запрашивается, Then `Y` тоже НЕ появляется (in_app физически не может провалиться — синхронная
   запись в БД, не сетевой вызов) — это подтверждает архитектурный инвариант «список недоставленных
   всегда пуст в отношении in_app», зафиксировать как явный тест, не как случайное наблюдение.
3. Given `pharmacy_admin` вызывает `GET /notifications/undelivered`, When guard проверяет `@Roles`,
   Then `403 INSUFFICIENT_ROLE`.

## Риски и подводные камни
- Определение «полностью недоставлено» зависит от точного состава каналов конкретного события из
  `notification-event-matrix.ts` (`DTJ-370`) — если матрица изменится (архитектор добавит канал
  событию), агрегирующий запрос ОБЯЗАН читать актуальный список каналов из той же константы, не
  хардкодить предположение «4 канала для всех событий» (у части событий каналов меньше, например
  `OrderProcessingStartedEvent` — только `telegram → web_push`, без `sms`).
- Повторная ручная отправка недоставленного уведомления — явно НЕ специфицирована документом 27,
  не додумывается этим тикетом; если появится реальная операционная потребность — отдельный ADR/
  тикет с чётким use case (например, `POST /notifications/:id/retry`).
