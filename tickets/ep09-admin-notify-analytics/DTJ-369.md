## Задача
14 событий матрицы `SRS-ADM-052` × до 4 каналов × 3 языка (tj/ru/en) — потенциально более 100
комбинаций текста. Без централизованной таблицы шаблонов и автоматической проверки полноты
ЛЮБОЙ пропуск (например, забыли добавить `en`-версию нового события) обнаруживается только в
продакшене при реальной отправке — прямое нарушение D-01 (бренд/строки — не хардкод) и общего
принципа «ловушка проверяется CI, не глазами ревьюера» (`02` §6.1).

## Технический контекст
`notification_templates` — **[ДОПОЛНЕНИЕ]** таблица, ОТСУТСТВУЕТ в `11-database-schema.md`, вводится
`27-module-admin-moderation-onboarding.md` §10.1 (`SRS-ADM-054`) дословно. Движок подстановки —
простой `String.replace` по плейсхолдерам `{{var}}`, НЕ Handlebars/шаблонизатор общего назначения
(`SRS-ADM-054` — минимизация поверхности инъекций в исходящий текст, эта же логика — часть
`NotificationTemplate.render()` домена, не application). `brandName` — ВСЕГДА плейсхолдер
`{{brandName}}`, заполняется из `tenant.settings.brandName` в момент рендера (D-01, `SRS-ADM-056`) —
шаблон НИКОГДА не хранит финальную строку бренда.

## Что сделать
1. Миграция `00XX_notification_templates.sql` — DDL дословно по `SRS-ADM-054` (`event_type,
   channel, locale, subject?, body, variables_schema JSONB`, `UNIQUE(event_type, channel, locale)`).
2. `NotificationTemplate` (domain, минимальный): `render(variables: Record<string, string>):
   { subject?: string; body: string }` — чистая функция, проверяет `variables` против
   `variablesSchema` (Zod-подобная JSON-схема, п.4 ниже) ДО подстановки, бросает доменную ошибку
   `MissingTemplateVariableError` при недостающем поле (не молчаливая пустая подстановка).
3. `subject` заполняется ТОЛЬКО для `channel ∈ {'email','web_push'}` (`SRS-ADM-055`) — доменная
   фабрика `NotificationTemplate.create()` бросает ошибку валидации при попытке задать `subject`
   для `telegram`/`sms`/`in_app`.
4. `NotificationTemplatesRepositoryPort`/`NotificationTemplatesRepository` — `findByEventChannel
   Locale(eventType, channel, locale)`.
5. Сид `db/seed/notification-templates/`: JSON/TS-файлы по одному на `event_type` из матрицы
   `SRS-ADM-052` (14 событий), КАЖДЫЙ — с телом на `tj`/`ru`/`en` для КАЖДОГО назначенного канала
   этого события (например, `order.paid` → `telegram`+`sms`+`web_push`+`in_app` × 3 языка = 12
   строк). Тексты — по смыслу события, с плейсхолдерами `{{brandName}}`, `{{orderNumber}}`,
   `{{savingsDiram}}` и т.п. согласно `variables_schema` каждого шаблона. `pnpm db:seed` загружает
   их идемпотентно (`ON CONFLICT (event_type, channel, locale) DO UPDATE`).
6. `tests/arch/notification-templates-completeness.spec.ts` — CI-тест: для КАЖДОЙ пары
   `(event_type, channel)` из таблицы `SRS-ADM-052` (константа-копия матрицы в самом тесте, со
   ссылкой на источник в комментарии) проверяет наличие строки в `notification_templates` на ВСЕХ
   трёх `locale` — тест ПАДАЕТ, если хотя бы одна комбинация отсутствует (`SRS-ADM-054`: «CI-тест
   полноты матрицы... падает ДО деплоя, не в рантайме», `TC-ADM-026`).

## Критерии приёмки
1. Given сид выполнен, When `tests/arch/notification-templates-completeness.spec.ts` запускается,
   Then тест ПРОХОДИТ для полного набора 14×N×3 комбинаций (`N` — число каналов конкретного события
   из матрицы).
2. Given один шаблон УДАЛЁН из сида искусственно (тестовая фикстура), When тот же CI-тест
   запускается, Then тест ПАДАЕТ с точным указанием отсутствующей комбинации
   `(event_type, channel, locale)` — не просто «тест упал», а читаемое сообщение (`TC-ADM-026`).
3. Given шаблон `channel='telegram'` создаётся с непустым `subject`, When
   `NotificationTemplate.create()` вызывается, Then доменная ошибка валидации (негативный сценарий
   `SRS-ADM-055`).
4. Given `render({ orderNumber: 'X' })` вызывается для шаблона, `variablesSchema` которого требует
   ЕЩЁ И `savingsDiram`, When рендер выполняется, Then `MissingTemplateVariableError` — рендер НЕ
   возвращает текст с буквальным `{{savingsDiram}}` внутри (частичный рендер запрещён — либо полный
   успех, либо явная ошибка ДО отправки).

## Тест-план
Unit: `notification-template.entity.spec.ts` (рендер с полным набором переменных; недостающая
переменная → ошибка; `subject` для `telegram` → ошибка валидации фабрики). CI/arch:
`notification-templates-completeness.spec.ts` (описан выше, обязателен — тест самого теста:
искусственно убрать одну строку сида в фикстуре, убедиться, что тест это ловит, `02` §6.1 принцип
«ловушка, которая перестала ловить, молчит об этом»). Порог `domain/` ≥ 90 %.

## Риски и подводные камни
- Переводы `tj` — как и везде в проекте, предварительные (машинно-выверенные), подлежат вычитке
  носителем перед продакшен-релизом (та же оговорка, что `12-api-conventions...md` для кодов
  ошибок) — не блокирует сдачу тикета, но фиксируется как известное ограничение.
- Движок подстановки `String.replace` — ПРОСТОЙ, без условной логики (`{{#if}}` и т.п.) — если
  какому-то шаблону реально нужна условность (например, разный текст для Rx/не-Rx позиции в одном
  событии), это решается ДВУМЯ разными `event_type`, не усложнением движка (сохраняет минимальную
  поверхность инъекций, обоснование `SRS-ADM-054`).
- Список 14 событий матрицы скопирован в тест КАК КОНСТАНТА — если архитектор добавит 15-е событие
  в будущей редакции документа 27, этот тест НЕ поймает автоматически (нет единого источника
  события↔тест) — риск рассинхронизации, зафиксировать в комментарии теста ссылку на `SRS-ADM-052`
  для ручной сверки при каждой правке документа.
