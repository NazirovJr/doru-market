## Задача
`NotificationService` — application-уровня контекст без богатого домена (`10-domain-model.md`:
`NotificationJob`), но с ЧЕТЫРЬМЯ каналами доставки (D-23): Telegram (основной), SMS (fallback),
web push (дополнительный), in-app (гарантированный минимум). Без единого модуля и Provider Pattern
каждый следующий тикет (шаблоны, матрица диспетчеризации, тихие часы) не имеет основания —
аналогично роли `DTJ-350`/`DTJ-180` для своих эпиков.

## Технический контекст
`SmsProvider` (`SmsGatewayProvider`/`MockSmsProvider`) и `PushProvider` (`WebPushProvider`/
`MockPushProvider`) УЖЕ существуют как инфраструктура контекста `identity`/Charter §3.3
(`EP-01`) — этот модуль их ПЕРЕИСПОЛЬЗУЕТ через DI-инъекцию существующих токенов, не создаёт
вторую реализацию. Новые — `TelegramNotifyProvider` (единственная реализация, без Mock — тестовое
окружение использует тестовый Bot API токен, `SRS-ADM-051`) и `InAppNotifyProvider` (тривиальный —
запись в `notifications` с `channel='in_app'`). `users.telegram_chat_id` (захватывается при `/start`
TWA, `11-database-schema.md`) — читается через `IdentityFacadePort`, НЕ напрямую из чужой схемы
(правило `02` §1.1: Drizzle-схема чужого модуля не импортируется).

## Что сделать
1. `NotifyProviderPort` (application) — единый интерфейс `send(userId, channel, renderedMessage:
   { subject?, body }): Promise<{ success: boolean; providerMessageId?: string }>` для ВСЕХ 4
   каналов (единая сигнатура, полиморфизм через DI-токен по каналу — `NOTIFY_PROVIDER_TELEGRAM`,
   `NOTIFY_PROVIDER_SMS` и т.д., связывание в `notifications.module.ts`).
2. `TelegramNotifyProvider implements NotifyProviderPort` — Telegram Bot API (`node-telegram-bot-
   api`/аналог, версия — по `01-TECH-BASELINE.md` если зафиксирована), читает `telegramChatId`
   получателя через `IdentityFacadePort.getTelegramChatId(userId)` (новый метод порта, добавляется
   этим тикетом в `IdentityFacadePort` как гостевая правка, см. риски `DTJ-350`). Given
   `telegramChatId IS NULL` (пользователь не открывал TWA) → `send()` возвращает `{ success: false
   }` немедленно, БЕЗ обращения к внешнему API (не тратить retry-бюджет на заведомо невозможную
   доставку).
3. `InAppNotifyProvider implements NotifyProviderPort` — синхронная запись строки в `notifications`
   (через `NotificationsRepositoryPort`, порт создаётся ЭТИМ тикетом, реализация — `DTJ-369`/`DTJ-
   370`, здесь только интерфейс) с `channel='in_app'`, `status='sent'` немедленно (in-app не имеет
   понятия «доставка» отдельно от записи — как только строка создана, считается доставленной).
4. `notifications.module.ts` — DI-связывание всех 4 токенов, реэкспорт существующих `SmsProvider`/
   `PushProvider` из модуля `identity` (импорт МОДУЛЯ, не файла реализации напрямую).
5. `notification-dispatch.processor.ts` (`apps/worker`) — ПУСТОЙ BullMQ processor-скелет для
   очереди `notification-dispatch` (регистрация очереди, обработчик логики — `DTJ-370`, здесь
   только `@Processor('notification-dispatch')` класс с `TODO(DTJ-370)`).

## Критерии приёмки
1. Given `apps/api` поднимается локально, When DI резолвит `NotificationsModule`, Then все 4 токена
   `NotifyProviderPort` резолвятся без ошибок (для Telegram/In-App — реальные реализации; для
   SMS/Push — существующие из `identity`, не заглушки).
2. Given пользователь БЕЗ `telegramChatId`, When `TelegramNotifyProvider.send()` вызывается, Then
   возвращается `{ success: false }` СИНХРОННО, без сетевого запроса к Telegram Bot API (проверяется
   через мок HTTP-клиента — 0 вызовов).
3. Given `InAppNotifyProvider.send()` вызван, When запись создана, Then `notifications.status`
   немедленно `'sent'` (не `'queued'`, в отличие от внешних каналов — in-app не проходит через
   BullMQ-очередь для самой доставки, только для остальной оркестрации диспетчера, `DTJ-370`).

## Тест-план
Unit: `telegram-notify.provider.spec.ts` (отсутствие `chatId` → без сетевого вызова; наличие →
вызов Bot API с корректным `chatId`+текстом); `in-app-notify.provider.spec.ts` (синхронная запись,
`status='sent'`). Интеграционный тест не требуется для скелета (реальная отправка/rate-limiting —
`DTJ-370`). Порог `infrastructure/` ≥ 70 %.
