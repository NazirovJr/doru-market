## Задача
Единственная точка чтения `audit_log` — журнал существует ДЛЯ НАДЗОРА над платформой, а не как
пользовательский лог активности (`SRS-ADM-065`): ни `pharmacy_admin`, ни `support_agent` не видят
даже записи о СОБСТВЕННЫХ действиях. Без экрана чтения неизменяемый журнал был бы неизменяемым, но
бесполезным — комплаенс-выгрузка требует человеко-читаемого интерфейса, не только SQL-доступа
администратора БД.

## Технический контекст
`AuditLogController` — часть `apps/api/src/common/audit/**` (тот же владелец, что `DTJ-374`/`DTJ-
375`, продолжает файлы того тикета, не создаёт отдельный модуль). Использует `AuditLogRepository`
(`DTJ-374`) в РЕЖИМЕ ЧТЕНИЯ — репозиторий уже реализован, этот тикет добавляет READ-метод
`findByFilters` в тот же класс (репозиторий изначально был write-only по методам порта, но САМ
класс репозитория — единственная точка доступа к таблице и МОЖЕТ содержать доп. read-методы, не
экспонируемые через `AuditLogPort`, а через отдельный `AuditLogQueryPort` — read/write разделение
интерфейсов, CQRS-подобное, чтобы `AuditLogPort` (пишущий, доступный всем модулям) НЕ приобрёл
случайно метод чтения, который открыл бы дверь для проверок «уже залогировано ли» — античтение
самими use case).

## Что сделать
1. `AuditLogQueryPort` (НОВЫЙ, отдельный от `AuditLogPort` — read-only интерфейс):
   `findByFilters(filter: { category?, entityType?, entityId?, actorUserId?, tenantId?, createdAtFrom?,
   createdAtTo? }, pagination): Promise<Page<AuditLogEntryDto>>`.
2. Реализовать метод в `AuditLogRepository` (`DTJ-374`, тот же класс, ДВА интерфейса —
   `AuditLogPort` и `AuditLogQueryPort` — implements оба, физически один класс с write- и
   read-методами, но потребители видят только нужный им интерфейс через DI-токены — большинство
   модулей инжектируют `AUDIT_LOG_PORT` (write-only), только этот тикет инжектирует
   `AUDIT_LOG_QUERY_PORT`).
3. `ListAuditLogUseCase` — курсорная пагинация (`SRS-API-004`), сортировка `createdAt:desc`.
4. `AuditLogController`: `GET /api/v1/audit-log` — `@Roles('super_admin')` СТРОГО (`audit-
   log:read`, `12-api-conventions...md` §4.1) — ни одна другая роль не значится в декораторе вовсе
   (не условно запрещено — маршрут физически недоступен, `403` на уровне guard'а до входа в use
   case, симметрично `SRS-API-039`).
5. Frontend: `audit-log-page.tsx` — таблица (дата, категория — Badge, тип/id сущности, актор,
   действие, причина если есть), фильтры (категория — Select из `audit_action_category`, диапазон
   дат, поиск по `entityId`). Каждая строка `metadata` раскрывается по клику (JSON-просмотр
   `before`/`after`, УЖЕ замаскированный на уровне записи `DTJ-374`/`DTJ-375` — экран НЕ выполняет
   дополнительное маскирование, доверяет данным из БД).

## Критерии приёмки
1. Given `pharmacy_admin` вызывает `GET /audit-log`, When guard проверяет `@Roles`, Then `403
   INSUFFICIENT_ROLE` на уровне guard'а, ДО входа в use case (`TC-ADM-028`) — не `403` внутри
   application-policy (эта роль вообще не значится в `@Roles(...)` декоратора).
2. Given `pharmacy_admin` пытается получить доступ к записи о СОБСТВЕННОМ действии (например,
   гипотетическая будущая ссылка на конкретную запись по id), When любой путь чтения проверяется,
   Then недоступно НИ ОДНОЙ ролью, кроме `super_admin` — нет специального «своя запись» исключения.
3. Given `filter[category]=payment_override&filter[createdAtFrom]=2026-08-01`, When запрос, Then
   возвращаются только записи этой категории за период (комбинация фильтров работает одновременно,
   не только по одному).

## Риски и подводные камни
- Разделение `AuditLogPort` (write, `@Global`, все модули)/`AuditLogQueryPort` (read, только этот
  модуль) — сознательное архитектурное решение Tech Lead, не предусмотренное явно документом 27
  (документ говорит просто «`GET /api/v1/audit-log` — ТОЛЬКО `super_admin`», не специфицирует
  внутреннее разделение интерфейсов). Обоснование — Interface Segregation (`02` — общий принцип
  чистой архитектуры проекта) — зафиксировать комментарием в коде, чтобы решение не выглядело
  случайным усложнением при код-ревью.
- Полнотекстовый поиск по `metadata` (JSONB) — НЕ specified/не реализуется этим тикетом (только
  структурные фильтры по колонкам) — если понадобится поиск внутри `metadata.extra`, отдельный
  тикет с оценкой производительности `JSONB`-индексов на растущей append-only таблице.
