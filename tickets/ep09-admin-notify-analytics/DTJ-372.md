## Задача
`in_app` — гарантированный минимум доставки (`SRS-ADM-051`, `SRS-ADM-084`): пользователь ДОЛЖЕН
иметь возможность прочитать уведомления при следующем открытии приложения, даже если все внешние
каналы были недоступны в момент события. Без READ-эндпоинта записи `channel='in_app'` существуют
только в БД, недостижимы клиентом — гарантия «пользователь как минимум увидит уведомление» остаётся
неисполненной со стороны API.

## Технический контекст
Единственный эндпоинт этого тикета, доступный ВСЕМ аутентифицированным ролям (не только
`super_admin`/`pharmacy_admin`, как остальные тикеты эпика) — каждая роль читает СВОИ уведомления
(`scope=own` неявно, `userId` из JWT). Использует `NotificationsRepositoryPort`, реализованный
`DTJ-370`. Frontend-потребление (`apps/web`, Telegram Mini App, `apps/pharmacy`, `apps/courier`) —
ВНЕ файлов этого тикета (эти приложения не входят в владение моих эпиков) — тикет сдаёт только
backend API и типизированный контракт.

## Что сделать
1. `ListOwnNotificationsUseCase.execute({ actor, filter: { status?[] }, pagination })` — курсорная
   пагинация (`SRS-API-004`), `userId` резолвится ИЗ JWT (не query-параметр — недопустимо читать
   чужие уведомления через подмену `userId`), сортировка `createdAt:desc` (новые сверху,
   единственное отличие от стандартного дефолта других списков платформы — обоснование: лента
   уведомлений читается «сверху вниз от новых», не архивный список).
2. `NotificationsFeedController`: `GET /api/v1/notifications?filter[status]=queued,sent` —
   `@Roles('customer', 'pharmacist', 'courier', 'pharmacy_admin', 'super_admin', 'support_agent')`
   (буквально ВСЕ роли платформы — этот эндпоинт не ролевой, а универсальный).
3. `packages/contracts/src/notifications.ts` — Zod-схема `NotificationSummarySchema` (`id`,
   `eventType`, `channel`, `status`, `payload` — уже отрендеренный текст на языке пользователя, НЕ
   сырые плейсхолдеры, `createdAt`, `sentAt?`) + строка экспорта в корневой `index.ts` (владение
   `EP-01`, гостевая правка одной строки, `00-EPICS.md` «Пересекающееся владение» п.3).

## Критерии приёмки
1. Given пользователь `A` имеет 5 уведомлений, пользователь `B` — 3, When `A` вызывает `GET
   /notifications`, Then видит РОВНО свои 5, ни одной записи `B` (без параметра `userId` в query
   вообще — эндпоинт физически не принимает такой параметр).
2. Given `filter[status]=queued,sent` передан, When запрос обрабатывается, Then `failed`-записи
   исключены из ленты обычного пользователя (диагностика `failed` — отдельный экран `DTJ-373`,
   только для `super_admin`).
3. Given курьер (`courier`) вызывает эндпоинт, When guard проверяет `@Roles`, Then `200` (не
   `403`) — подтверждение, что эндпоинт универсален для всех ролей, не ограничен `super_admin`/
   `pharmacy_admin`, в отличие от большинства остальных эндпоинтов этого эпика.

## Риски и подводные камни
- Frontend-потребление этой ленты (виджет колокольчика/список во всех клиентских приложениях) — НЕ
  реализуется этим тикетом. Явно зафиксировать в спринт-планировании, к какому эпику/владельцу
  `apps/web`/`apps/pharmacy`/`apps/courier` относится потребляющий UI, чтобы backend не остался
  невостребованным до следующего релиза.
- `payload` в ответе — уже ОТРЕНДЕРЕННЫЙ текст (после подстановки плейсхолдеров, `DTJ-369`/`DTJ-
  370`), не сырые данные события `outbox` — это НЕ то же самое поле, что `payload` в `notifications`
  из исходной DDL (`11-database-schema.md` §44 описывает `payload JSONB` как исходные данные для
  рендера) — контракт `NotificationSummarySchema` явно отделяет «что хранится» от «что отдаётся
  клиенту», маппинг — ответственность presentation-слоя этого тикета.
