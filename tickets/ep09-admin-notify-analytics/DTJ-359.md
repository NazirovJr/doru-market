## Задача
R1 — наличные (`cash_courier`) единственный способ оплаты COD-заказов, и единственный способ,
которым платформа собирает комиссию с этих заказов — через B2B-биллинг сети, НЕ через
`escrow_ledger` (D-25 п.7). Без этого экрана и джобы просрочки сети физически не платят комиссию за
COD-объём, что напрямую бьёт по выручке платформы уже в R1 (`REQ-MON-6/7`).

## Технический контекст
`platform_billing_invoices` — таблица контекста `billing` (владеет `EP-10`/финансовый под-модуль,
`BillingFacade`, `10-domain-model.md`). Этот тикет — CRUD/операционная обёртка `admin` поверх
`BillingFacadePort` (новый порт, создаётся этим тикетом по образцу `DTJ-350`) + worker-джоба
просрочки. `lift-block` требует `audit_log` (через `AuditLogPort`, `DTJ-374`) — снятие блокировки
сети это финансово чувствительное действие, симметричное `payment-override` (`DTJ-356`).

## Что сделать
1. `BillingFacadePort`: `listInvoices(filter: { chainId?, type?, status? }, pagination)`,
   `markInvoicePaid(invoiceId, actor)`, `liftInvoiceBlock(invoiceId, reason, actor)`.
2. `ListBillingInvoicesUseCase` — курсорная пагинация, `filter[chainId]`,
   `filter[type]=cash_courier_commission` (по умолчанию UI фильтрует именно этот тип — White-Label
   роялти/лицензия, `whitelabel_license`/`whitelabel_royalty`, вне скоупа R1, `SRS-ADM-036`
   таблица релизов).
3. `MarkInvoicePaidUseCase.execute({ invoiceId, actor })` — use case
   `MarkInvoicePaidUseCase` уже поименован спецификацией (`SRS-ADM-036`), ручная фиксация оплаты по
   банковской выписке (нет автосверщика поступлений в R1) — пишет `audit_log(category=
   'onboarding_decision'`... НЕТ: категория для этого действия НЕ перечислена явно в таблице
   `SRS-ADM-062` — использовать ближайшую подходящую существующую категорию неверно (создание новой
   категории enum — решение архитектора, не Tech Lead). Зафиксировать как явный пробел (см. «Риски»).
4. `LiftInvoiceBlockUseCase.execute({ invoiceId, reason, actor })` — `reason` ОБЯЗАТЕЛЕН (Zod
   `.min(10)`, паттерн `SRS-ADM-032`), атомарно снимает `pharmacy_chains.is_active=false` +
   пишет аудит (та же категория, что п.3 — тот же нерешённый вопрос категории).
5. `InvoiceOverdueCheckJob` (`apps/worker`, BullMQ repeatable, ежедневно) — сканирует
   `platform_billing_invoices` где `due_at + grace_period < now() AND status != 'paid'`, вызывает
   `BillingFacadePort`-эквивалент внутри `billing`-модуля (домен уже владеет переходом
   `pharmacy_chains.is_active=false`, worker только триггерит проверку — сама блокировка не
   реализуется в `admin`, только читается на экране).
6. `BillingInvoicesController`: `GET /api/v1/finance/billing-invoices`, `POST
   /api/v1/finance/billing-invoices/:id/mark-paid`, `POST
   /api/v1/finance/billing-invoices/:id/lift-block` — `@Roles('super_admin')`.
7. Frontend: `billing-invoices-page.tsx` — таблица инвойсов (сеть, период, сумма, статус — Badge,
   срок `dueAt`), действия «Отметить оплаченным» (confirm-модалка) и «Снять блокировку» (форма с
   обязательной причиной, видна ТОЛЬКО когда `pharmacy_chains.is_active=false` по этому инвойсу).

## Критерии приёмки
1. Given инвойс `due_at + grace_period` уже в прошлом и `status != 'paid'`, When
   `InvoiceOverdueCheckJob` выполняется, Then `pharmacy_chains.is_active` становится `false` для
   этой сети (проверяется через `BillingFacadePort`, домен которой это гарантирует, здесь —
   контракт-тест на вызов).
2. Given сеть заблокирована просрочкой, When `super_admin` вызывает `lift-block` без `reason`,
   Then `400 VALIDATION_ERROR`.
3. Given валидный `lift-block`, When выполняется, Then `pharmacy_chains.is_active → true` И запись
   аудита создана в той же транзакции (атомарность, симметрично `DTJ-356`).
4. Given `mark-paid` вызван ПОВТОРНО для уже `status='paid'` инвойса, When запрос обрабатывается,
   Then `409 CONFLICT` (идемпотентность на уровне домена — заказчик решает точный код, здесь
   зафиксировано ожидание «не тихий no-op, не повторное начисление»).

## Риски и подводные камни
- **Пробел в спецификации**: `SRS-ADM-062` (таблица обязательных категорий `audit_log`) НЕ содержит
  строки для `mark-invoice-paid`/`lift-invoice-block` — только `payment_override`,
  `return_override`, `dispute_resolution`, `prescription_access`, `control_category_change`,
  `onboarding_decision`, `force_cancel_order`, `ledger_adjustment`, `role_grant`. Ни одна из этих
  категорий по смыслу точно не описывает биллинг-инвойс. Решение Tech Lead на время реализации:
  переиспользовать `ledger_adjustment` для ОБОИХ действий (ближайшая по смыслу — тоже про
  финансовую корректировку записи), с явным `entityType='billing_invoice'` в самой записи для
  отличимости от истинных `ledger_adjustment` (`EP-10`, R3). Это ОТКЛОНЕНИЕ от буквального текста
  документа 27, подлежит подтверждению архитектором отдельным ADR — если не подтверждено к моменту
  code review, ревьюер обязан эскалировать, не одобрять молча.
- `BillingFacade`/`platform_billing_invoices` — ответственность `EP-10`, включая саму реализацию
  снятия/наложения блокировки сети — этот тикет не дублирует эту логику.
