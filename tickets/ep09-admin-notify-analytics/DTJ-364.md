## Задача
`pharmacy_admin` — единственная роль, создающая учётные записи `pharmacist`/`courier` для своей
сети. Без этого экрана единственный способ добавить сотрудника — прямая вставка в БД, что означает
отсутствие OTP-логина «из коробки» (учётная запись создаётся БЕЗ пароля, Charter §5) и отсутствие
контроля владельцем сети над собственным штатом.

## Технический контекст
`User`/`Courier` — агрегаты контекстов `identity` (`EP-01`) и `delivery` (`EP-13`). Guard: `role=
'pharmacist'` требует `pharmacyId ∈ actor.ownPharmacyIds`; `role='courier'` создаёт
`Courier(chainId=actor.chainId)` — собственный флот сети, `pharmacy_admin` НЕ может создать курьера
платформенного пула (`chainId=NULL`, только `super_admin` через `POST /users/:id/grant-platform-
role`-подобный отдельный путь, вне скоупа этого тикета, `SRS-ADM-041`). Использует
`IdentityFacadePort` (расширяется здесь) + новый `DeliveryFacadePort` (создаётся здесь по образцу
`DTJ-350`, только для метода `createCourier`).

## Что сделать
1. Расширить `IdentityFacadePort`: `createStaffUser({ phoneNumber, fullName, role: 'pharmacist',
   pharmacyId, actor }): Promise<UserDto>`, `listStaffAccounts(filter: { scope: 'own' },
   pagination)`, `deactivateStaffAccount(userId, actor)`.
2. Создать `DeliveryFacadePort.createCourier({ phoneNumber, fullName, chainId, actor }):
   Promise<CourierDto>`.
3. `CreateStaffAccountUseCase.execute({ phoneNumber, fullName, role, pharmacyId, actor })`: Zod —
   `role ∈ {'pharmacist','courier'}` СТРОГО (иные значения — `400`, платформенные роли и `customer`
   недостижимы этим эндпоинтом); ветвление — `role='pharmacist'` → policy `pharmacyId ∈
   actor.ownPharmacyIds` (иначе `403`), вызов `IdentityFacadePort.createStaffUser`; `role='courier'`
   → игнорирует `pharmacyId` (курьер привязан к сети, не к точке), вызов
   `DeliveryFacadePort.createCourier(chainId=actor.chainId)`. Ответ ВСЕГДА включает
   `temporaryOtpHint: false` (учётная запись без пароля, первый вход — обычный OTP, `SRS-ADM-041`).
4. `ListStaffAccountsUseCase` — `scope=own` резолвится сервером из `actor.chainId` (тот же паттерн
   ограничения, что `DTJ-362`/`DTJ-363`).
5. `DeactivateStaffAccountUseCase.execute({ userId, actor })` — `PATCH { isActive: false }`, policy
   `userId` принадлежит сети `actor.chainId` (иначе `403`). Явно НЕ удаляет исторические
   `order_items`/`delivery_assignments`, где сотрудник фигурирует как актор — гарантия уже на
   уровне схемы (`ON DELETE SET NULL`/`RESTRICT`), этот use case только ставит флаг.
6. `StaffAccountsController`: `POST /api/v1/staff-accounts`, `GET
   /api/v1/staff-accounts?scope=own`, `PATCH /api/v1/staff-accounts/:id` — `@Roles('pharmacy_admin',
   'super_admin')`.
7. Frontend: `staff-accounts-page.tsx` — таблица сотрудников (имя, телефон, роль, аптека/точка если
   `pharmacist`, статус активности), форма добавления (телефон с маской `+992`, имя, роль-Select,
   поле «Аптека» появляется ТОЛЬКО при выборе `pharmacist`), действие «Деактивировать» (confirm-
   модалка).

## Критерии приёмки
1. Given `pharmacy_admin` вызывает `POST /staff-accounts { role: 'pharmacist', pharmacyId: X }`,
   где `X` НЕ принадлежит его сети, When policy проверяется, Then `403
   CROSS_TENANT_ACCESS_DENIED`, учётная запись НЕ создана.
2. Given `POST /staff-accounts { role: 'courier', pharmacyId: X }` (передан лишний `pharmacyId`),
   When use case обрабатывается, Then `pharmacyId` ИГНОРИРУЕТСЯ (курьер создаётся с
   `chainId=actor.chainId`, без привязки к точке) — ответ НЕ содержит ошибки из-за лишнего поля
   (Zod-схема допускает `pharmacyId` как опциональный, но применяет его условно).
3. Given `POST /staff-accounts { role: 'super_admin' }`, When Zod валидирует, Then `400
   VALIDATION_ERROR` — платформенная роль физически недостижима этим эндпоинтом (симметрично
   `DTJ-354` для `change-staff-role`).
4. Given успешное создание, When ответ формируется, Then `temporaryOtpHint: false` присутствует
   всегда, независимо от роли — учётная запись НИКОГДА не получает пароль этим путём.

## Риски и подводные камни
- `DeliveryFacade.createCourier` — ответственность `EP-13` (внешний эпик, курьерский модуль). Если
  метод отсутствует на момент разработки — гостевая правка одной строки в чужом `index.ts`, логика
  создания курьера НЕ реализуется внутри `admin`.
- Различие «курьер собственного флота сети» vs «курьер платформенного пула» (`chainId=NULL`) —
  архитектурно важное разграничение (`SRS-ADM-041`, `12-api-conventions...md` §4.1 матрица) — при
  реализации не смешивать пути создания, платформенный пул НЕ создаётся этим тикетом вообще (его
  создаёт `super_admin` отдельным эндпоинтом `staff-accounts:create` с иной семантикой, не
  специфицированным детально в доступных документах — если такой эндпоинт понадобится, отдельный
  тикет по факту потребности).
