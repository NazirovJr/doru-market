## Задача
Единственная легитимная лазейка изменить `orders.status` в обход банковского вебхука
(`REQ-PAY-1`) и единственный способ отменить заказ в ЛЮБОМ нетерминальном статусе при инциденте
(поддельный рецепт, обнаруженный постфактум, `SRS-DOM-171`). Оба действия финансово/юридически
чувствительны — платформа обязана иметь неопровержимый след «кто, когда и почему обошёл обычный
процесс», иначе расследование спорной транзакции невозможно.

## Технический контекст
`Order.markPaidEscrowManually(reason, actor)` и `AdminForceCancelOrderUseCase`-подобная точка входа
— доменные методы-намерения, УЖЕ специфицированные `10-domain-model.md` (`SRS-DOM-171`) и
`21-module-orders-payments-escrow.md` (владеет `EP-10`) — этот тикет НЕ реализует доменную логику
перехода, только presentation/application-обёртку модуля `admin`, вызывающую `OrdersFacadePort`
(расширяется здесь методами `adminPaymentOverride`/`adminForceCancelOrder`). Обязательная запись в
`audit_log` — через `AuditLogPort` (`DTJ-374`), в ОДНОЙ транзакции с доменным вызовом (не два
отдельных запроса — при падении между ними нельзя получить смену статуса без следа).

## Что сделать
1. Расширить `OrdersFacadePort`: `adminPaymentOverride(orderId, targetStatus, reason, actor):
   Promise<OrderDto>` (делегирует `Order.markPaidEscrowManually`), `adminForceCancelOrder(orderId,
   reason, actor): Promise<OrderDto>` (делегирует `AdminForceCancelOrderUseCase` домена заказов —
   ИМЯ метода фасада НЕ совпадает с именем доменного use case намеренно, чтобы не создавать
   иллюзию, что логика живёт в `admin`).
2. `AdminPaymentOverrideUseCase.execute({ orderId, targetStatus, reason, actor })`: (а) Zod
   `.min(10)` на `reason` (`SRS-ADM-032` п.1); (б) `unitOfWork.run` — вызов
   `OrdersFacadePort.adminPaymentOverride` + `AuditLogPort.write({ category: 'payment_override',
   entityType: 'order', entityId: orderId, reason, actorUserId: actor.userId, metadata: {
   statusFrom, statusTo, orderTotalDiram } })` атомарно.
3. `AdminForceCancelOrderUseCase.execute({ orderId, reason, actor })`: аналогичная атомарная пара
   (`category: 'force_cancel_order'`), делегирует домену полный `PaymentProvider.refund()` если
   заказ был оплачен (логика рефанда — целиком в домене `orders`/`payments`, здесь только
   оркестрация вызова + аудит).
4. `OrdersAdminActionsController`: `POST /api/v1/orders/:id/payment-override`, `POST
   /api/v1/orders/:id/admin-force-cancel` — `@Roles('super_admin')`.
5. Frontend: `payment-override-modal.tsx`/`force-cancel-modal.tsx` — модалки на экране детали заказа
   (`DTJ-355`, `order-detail-page.tsx`), поле «Причина» ОБЯЗАТЕЛЬНО (client-side валидация ≥10
   символов, дублирует Zod для мгновенной обратной связи, не заменяет серверную), кнопки — вариант
   `danger` из `packages/ui` (единственный экран R1, где этот вариант применяется системно, не
   ситуативно, `32-design-reference.md` §«Инвентарь компонентов»).

## Критерии приёмки
1. Given `POST /orders/:id/payment-override` с `reason` короче 10 символов, When Zod валидирует,
   Then `400 VALIDATION_ERROR`, `orders.status` НЕ изменён, `audit_log` НЕ содержит новой строки
   (`TC-ADM-015`-подобный сценарий).
2. Given валидный `payment-override`, When транзакция коммитится, Then `audit_log(category=
   'payment_override', metadata.statusFrom, metadata.statusTo, metadata.orderTotalDiram)` создана
   В ТОЙ ЖЕ транзакции, что смена статуса (`TC-ADM-016`).
3. Given заказ в статусе `delivered` (терминальный для `force-cancel` по смыслу — уже вручён), When
   `POST /admin-force-cancel` вызывается, Then домен возвращает ошибку недопустимого перехода
   (`422 BUSINESS_RULE_VIOLATION`), use case НЕ пишет `audit_log` для неудачной попытки (аудит
   фиксирует только СОВЕРШЁННОЕ действие, не попытки).
4. Given `AuditLogPort.write` бросает исключение (сбой БД) ПОСЛЕ успешного вызова
   `OrdersFacadePort.adminPaymentOverride` внутри `unitOfWork.run`, When транзакция обрабатывается,
   Then ВЕСЬ `unitOfWork` откатывается — смена статуса заказа НЕ применяется без аудита (негативный
   сценарий атомарности, не «частичный успех»).

## Тест-план
Unit: `admin-payment-override.use-case.spec.ts` (успех → 2 side-effect'а в одном `unitOfWork`;
короткий `reason` → 0 side-effect'ов; исключение `AuditLogPort` → откат обоих);
`admin-force-cancel-order.use-case.spec.ts` (аналогично + ветка «заказ уже оплачен → вызывается
`refund`» через мок `OrdersFacadePort`, не реальный `PaymentProvider`). Интеграционный:
`orders-admin-actions.controller.e2e.spec.ts` (реальная БД, проверка атомарности через
принудительный сбой в middleware теста). Порог `application/` ≥ 90 %.

## Риски и подводные камни
- Доменная state machine и `PaymentProvider.refund()` — ответственность `EP-10` (внешний эпик).
  Этот тикет НЕ добавляет новых доменных переходов, только оркестрирует уже существующие через
  фасад — если на момент разработки конкретный метод домена ещё не готов, блокирующая зависимость,
  не обходится заглушкой (в отличие от `DTJ-350`, здесь заглушка дала бы ложное чувство готовности
  финансово-чувствительной функции).
- `AdminForceCancelOrderUseCase` в этом модуле — presentation/application ОБЁРТКА, не путать
  одноимённым доменным use case `orders`/`payments` (`SRS-DOM-171`) — рекомендуется явный
  комментарий-разграничение в коде, чтобы будущий разработчик не решил «логика уже здесь, допишу
  прямо в admin».
