## Задача
`audit_log` растёт БЕЗ ограничения — append-only, ничего не удаляется приложением обычным путём.
Юридический срок хранения финансовых/операционных записей — `AUDIT_LOG_RETENTION_YEARS`
(ASSUMPTION 5 лет), НО записи категории `prescription_access` (доступ к медданным) НЕ удаляются
НИКОГДА (REQ-REG-10/11 трактуется как требование к неограниченному хранению именно этой категории —
более строгий режим комплаенса, чем финансовый аудит, `SRS-ADM-066`). Без джобы таблица растёт
неограниченно, что рано или поздно деградирует производительность и нарушает право на «забвение»
для категорий, где оно применимо.

## Технический контекст
Единственная джоба этого эпика, которая УДАЛЯЕТ строки из append-only таблицы — легитимно, т.к.
`REVOKE UPDATE, DELETE ON audit_log FROM app_role` (`DTJ-374`) отзывает права у `app_role`
(runtime-роль приложения), а джоба ретеншена выполняется под ОТДЕЛЬНОЙ ролью БД с правом `DELETE`
(миграционная/административная роль, НЕ `app_role`) — это НЕ нарушение неизменяемости, а
единственный санкционированный канал удаления, работающий В ОБХОД обычного пути приложения
намеренно (задокументировать явно, чтобы не выглядело противоречием `DTJ-374`).

## Что сделать
1. `audit-retention.config.ts` — читает `AUDIT_LOG_RETENTION_YEARS` из `ConfigService` (дефолт 5,
   `ASSUMPTION`, конфигурируемо — НЕ константа в коде джобы, C6).
2. `AuditLogRetentionJob` (`apps/worker`, BullMQ repeatable, cron раз в квартал — например,
   `0 3 1 */3 *` Asia/Dushanbe) — удаляет записи `audit_log` где `category != 'prescription_access'
   AND created_at < now() - AUDIT_LOG_RETENTION_YEARS лет`, БАТЧАМИ (например, `DELETE ... WHERE id
   IN (SELECT id ... LIMIT 1000)`, цикл до исчерпания — не блокирующий `DELETE` по всей таблице
   разом, `SRS-ADM-066`).
3. Джоба подключается к БД под ролью с правом `DELETE` на `audit_log` — ЯВНО отличной от `app_role`
   основного приложения (используется отдельный connection string/роль БД, конфигурация — по
   соглашению `EP-19`/DevOps, если такая роль ещё не существует — завести её миграцией этого
   тикета: `CREATE ROLE audit_retention_role; GRANT DELETE, SELECT ON audit_log TO
   audit_retention_role;`).
4. Логирование результата каждого запуска (сколько строк удалено, сколько батчей) — через
   стандартный pino-логгер worker'а, НЕ `console.log` (C9).

## Критерии приёмки
1. Given записи категории `payment_override` старше `AUDIT_LOG_RETENTION_YEARS`, When джоба
   выполняется, Then они удалены.
2. Given записи категории `prescription_access`, ЛЮБОГО возраста (включая старше срока хранения),
   When джоба выполняется, Then они НЕ удалены НИКОГДА — негативный тест с искусственно старой
   датой (например, 10 лет назад) подтверждает, что даже явно просроченная по обычному сроку запись
   этой категории остаётся нетронутой.
3. Given таблица содержит >100 000 строк, подлежащих удалению, When джоба выполняется, Then
   удаление происходит батчами (проверяется через подсчёт числа отдельных `DELETE`-запросов в
   тестовом моке — не один гигантский запрос).
4. Given джоба выполняется под ролью `app_role` по ошибке конфигурации (гипотетический тест), When
   `DELETE` выполняется, Then запрос отклоняется правами БД (подтверждение, что `REVOKE` из
   `DTJ-374` действительно защищает от НЕПРАВИЛЬНО сконфигурированного запуска джобы, не только от
   произвольного стороннего SQL).

## Тест-план
Unit: `audit-log-retention.job.spec.ts` (фильтрация по категории и возрасту — `prescription_access`
исключена безусловно; батчинг — мок репозитория вызывается N раз для N батчей, не 1 раз для всей
таблицы). Интеграционный: `audit-log-retention.e2e.spec.ts` (реальная БД, смешанные по возрасту и
категории записи — удалены только подходящие под условие; попытка запуска под `app_role` —
`403`-подобная ошибка прав PostgreSQL). Порог `infrastructure/` ≥ 70 %.

## Риски и подводные камни
- Заведение отдельной роли БД с правом `DELETE` — операционный вопрос, пересекающийся с
  ответственностью `EP-19` (инфраструктура/DevOps, управление ролями БД и секретами подключения).
  Координировать точный механизм (отдельная строка подключения worker'а vs `SET ROLE` внутри
  транзакции) с владельцем `EP-19` — не решать в одиночку без сверки, т.к. это влияет на общую
  модель доступа к БД проекта.
- Квартальная периодичность — ASSUMPTION, не специфицирована документом дословно (документ говорит
  «раз в квартал, батчами», без точного cron-выражения) — конкретное время суток/день квартала
  выбирается Tech Lead с минимальным пересечением с другими ночными джобами (`LicenseExpiryCheckJob`
  `06:00`, `InvoiceOverdueCheckJob` — время не специфицировано, свериться при реализации).
