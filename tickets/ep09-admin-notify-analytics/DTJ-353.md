## Задача
Служба поддержки и расследования инцидентов (жалоба на конкретную аптеку, проверка её текущего
статуса, поиск по названию) требуют единой точки входа поверх ВСЕХ аптек платформы, вне зависимости
от статуса онбординга — очередь верификации `EP-03` (§2.2 модуля 27) намеренно ограничена
`status=pending_review` и не годится для этой цели. Без этого экрана `super_admin` не может быстро
найти конкретную аптеку по имени/сети/статусу без прямого SQL.

## Технический контекст
Дублирует по данным очередь онбординга `EP-03`, но с другим фильтром и назначением
(`SRS-ADM-029`) — use case этого тикета обращается к `PharmacyAccount` ТОЛЬКО через
`OnboardingFacadePort` (порт создан `DTJ-350`), добавляя в него метод `findPharmacyAccountsAny
(filter, pagination)`, не дублирует репозиторий. `orders:read:any`-подобный охват — единственная
роль, для которой видимость распространяется на аптеки ЛЮБОГО статуса и ЛЮБОЙ сети (в отличие от
`pharmacy_admin`, `DTJ-362`, который видит только `scope=own`).

## Что сделать
1. Расширить `OnboardingFacadePort` (`DTJ-350`) методом `findPharmacyAccountsAny(filter: {
   status?, chainId?, nameLike? }, pagination): Promise<Page<PharmacyAccountAdminSummaryDto>>`.
2. `ListPharmacyAccountsAnyUseCase` — курсорная пагинация (`SRS-API-004`), полнотекстовый
   `filter[name][like]` (регистронезависимый `ILIKE`/`pg_trgm`, без ранжирования — простой фильтр,
   не полноценный поиск как `EP-06`), `filter[status]`, `filter[chainId]`.
3. `PharmacyAccountsAdminController`: `GET /api/v1/pharmacy-accounts` БЕЗ query-параметра `scope`
   (или `scope` отсутствует/не равен `own`) — `@Roles('super_admin')`. Эндпоинт СОВМЕСТНО
   используется этим тикетом (кросс-тенантный, `super_admin`) и `DTJ-362` (`scope=own`,
   `pharmacy_admin`) — единый контроллер, различие по `actor.role`+`query.scope` внутри одного
   метода (см. риски).
4. Frontend: `pharmacy-accounts-page.tsx` — таблица с фильтрами (статус — Select, сеть — Select,
   поиск по имени — SearchBar), столбцы: название, сеть, статус (Badge с цветом по статусу —
   `packages/ui` семантические токены, не хардкод HEX), срок лицензии, клик — переход на карточку
   (карточка детали/действия suspend/revoke — уже покрыты онбордингом `EP-03`, здесь только readonly
   обзор + ссылка).

## Критерии приёмки
1. Given аптеки в статусах `draft`, `pending_review`, `active`, `suspended`, `terminated` существуют
   одновременно, When `super_admin` вызывает `GET /pharmacy-accounts` без фильтра, Then видны ВСЕ,
   включая `terminated` (в отличие от очереди онбординга `EP-03`, где видна только `pending_review`).
2. Given `filter[name][like]=Салом` (частичное совпадение, кириллица), When запрос, Then возвращаются
   все аптеки, чьё название содержит подстроку, регистронезависимо.
3. Given роль `pharmacy_admin` без `scope=own` вызывает тот же эндпоинт, When guard/policy
   проверяет, Then `403 CROSS_TENANT_ACCESS_DENIED` (не `pharmacy-accounts:approve`-подобная
   `403`, а именно кросс-тенантный запрет — `pharmacy_admin` обязан явно передать `scope=own`,
   негативный сценарий, зеркальный `DTJ-362`).

## Риски и подводные камни
- Один и тот же путь `GET /api/v1/pharmacy-accounts` обслуживает ДВА разных сценария (`scope=any`
  для `super_admin` этим тикетом, `scope=own` для `pharmacy_admin` тикетом `DTJ-362`) — оба тикета
  правят ОДИН файл `pharmacy-accounts-admin.controller.ts`. Договорённость: этот тикет (`DTJ-353`,
  реализуется раньше по номеру) создаёт файл и метод с веткой `if (query.scope !== 'own')`; `DTJ-362`
  добавляет ветку `else` в ТОТ ЖЕ метод, не создаёт второй контроллер. Порядок реализации в спринте
  — по здравому смыслу команды, не обязан совпадать с порядком номеров тикетов.
- Полнотекстовый поиск по имени — простой `ILIKE`, не `pg_trgm`-ранжирование (это не поисковый экран
  `EP-06`) — если объём аптек вырастет на порядки, потребуется индекс `pg_trgm` отдельным тикетом
  оптимизации (не блокирует R1 при ожидаемых объёмах — сотни, не десятки тысяч аптек).
