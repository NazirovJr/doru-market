## Задача
`product_events` — единственный источник воронки «показ экономии → клик → корзина → заказ»,
проверяющей kill-критерии №1/№2 пивота (`04-SCOPE-DECISION-PIVOT.md` §7). Без этой таблицы и
единой точки записи (`AnalyticsFacade.recordEvent`) следующие тикеты (приём клиентской телеметрии,
интеграция `order_placed`, экраны воронки) не имеют основания. Это тикет-синхронизация волны 11,
аналогичный по роли `DTJ-350`/`DTJ-368`/`DTJ-180` для своих эпиков.

## Технический контекст
`analytics` — контекст `10-domain-model.md` §«Ограниченные контексты»: «Read-модели/дашборды
(только на чтение, доменных инвариантов не содержит)... `AnalyticsFacade`». Общая интеграционная
матрица того же документа описывает `analytics ← (все контексты) [E]` как ПОДПИСЧИК на `outbox`
(субъект чтения, никогда не пишет обратно). `product_events` — СОЗНАТЕЛЬНОЕ исключение из этого
общего правила: `27-module-admin-moderation-onboarding.md` (`SRS-ADM-067`) явно специфицирует, что
эта таблица пишется НАПРЯМУЮ из `presentation` (клиентская телеметрия) И из application других
модулей («из backend use case напрямую там, где событие уже известно серверу»), НЕ через `outbox` —
обоснование: `product_events` включает чисто UX-телеметрию (`search_performed`, `analog_shown`),
не имеющую доменного смысла и не порождающую доменных последствий, для которой заводить `outbox`-
событие было бы искусственным (событие без агрегата, без домена, без инварианта). Это ОТКЛОНЕНИЕ
от буквы `10-domain-model.md` подлежит подтверждению архитектором отдельным ADR при следующей
сверке документов (см. «Риски») — до подтверждения реализуется буквально по `SRS-ADM-067`, как
документу, детально специфицирующему именно эту таблицу.

## Что сделать
1. Миграция `00XX_product_events.sql` — DDL дословно по §10.1 `27-module-admin-moderation-
   onboarding.md` (`tenant_id, user_id?, session_id, event_type, medicine_id?, pharmacy_id?,
   order_id?, savings_diram?, metadata JSONB, occurred_at`), включая оба индекса
   (`idx_product_events_tenant_type_time`, `idx_product_events_session`).
2. `ProductEvent` (domain, минимальный): фабрика `create({ tenantId, userId?, sessionId,
   eventType, medicineId?, pharmacyId?, orderId?, savingsDiram?, metadata })` — валидирует
   `eventType ∈ EVENT_TYPES` (константа — 5 обязательных из `SRS-ADM-068`:
   `search_performed`, `analog_shown`, `analog_clicked`, `added_to_cart`, `order_placed`, плюс
   расширяемый список для будущих UX-событий, C6 — не магическая строка).
3. `ProductEventsRepositoryPort`/`ProductEventsRepository` — `insert(event): Promise<void>`,
   `insertBatch(events: ProductEvent[]): Promise<void>` (для батчевого приёма клиентской
   телеметрии, `DTJ-379`).
4. `RecordProductEventUseCase.execute(command): Promise<void>` — тонкая оркестрация: валидация →
   `ProductEvent.create()` → `repository.insert()`. Это ЕДИНСТВЕННЫЙ use case, вызываемый ЛИБО из
   `presentation` этого модуля (`DTJ-379`), ЛИБО из ДРУГИХ модулей через `AnalyticsFacade` (см. п.5).
5. `analytics/index.ts` — публичный фасад `AnalyticsFacade.recordEvent(command):
   Promise<void>` — делегирует `RecordProductEventUseCase`. Это ЕДИНСТВЕННЫЙ публичный метод
   фасада в этом тикете (остальные методы — `getFunnel`/`getPlatformMetrics` и т.д. — добавляются
   тикетами `DTJ-381`/`DTJ-382`/... по мере готовности, не создаются здесь заранее — C15).
6. `analytics.module.ts` — DI-связывание порта и репозитория.

## Критерии приёмки
1. Given `AnalyticsFacade.recordEvent({ eventType: 'search_performed', ... })` вызывается ЛЮБЫМ
   другим модулем (гипотетический тестовый вызов), When выполняется, Then строка вставлена в
   `product_events` с корректным `occurred_at` (через порт `Clock`, не `Date.now()` внутри домена,
   `02` §2.6).
2. Given `eventType` НЕ входит в список известных типов события, When
   `ProductEvent.create()` вызывается, Then доменная ошибка валидации — таблица НЕ принимает
   произвольные строки без контроля (защита от опечатки в клиентском коде, которая иначе тихо
   создавала бы «мёртвый» тип события, невидимый воронке).
3. Given модуль `orders` (гипотетический импорт в фикстуре) пытается импортировать
   `modules/analytics/domain/product-event.entity` напрямую, When `pnpm arch:check`, Then
   `dependency-cruiser` отклоняет импорт (межмодульное взаимодействие — только через
   `AnalyticsFacade`, симметрично `SRS-ADM-002`).

## Риски и подводные камни
- **Архитектурная развилка, требующая ADR**: `10-domain-model.md` (документ ВЫШЕ по приоритету
  внутри `docs/spec/`, помечен «ЗАКОН» для сущностей/контекстов) описывает `analytics` как
  ИСКЛЮЧИТЕЛЬНО subscriber-side через `outbox`. `27-module-admin-moderation-onboarding.md`
  (`SRS-ADM-067`) явно вводит ВТОРОЙ, синхронный путь записи через факад для отдельной таблицы
  `product_events`. Оба документа формально одного уровня иерархии (`docs/spec/*.md`), но заголовок
  документа 27 обязывает НЕ переопределять `10-domain-model.md`, только расширять. Позиция Tech
  Lead: `product_events` — НОВАЯ таблица вне описанных в `10-domain-model.md` агрегатов, поэтому
  правило «analytics — subscriber-only» (написанное про READ-МОДЕЛИ поверх доменных событий других
  контекстов) не покрывает этот случай буквально — телеметрия без домена не может быть выражена
  доменным событием. Реализация следует `SRS-ADM-067` дословно; при расхождении мнений на code
  review — эскалация архитектору за ADR, не самостоятельная переинтерпретация в ту или иную сторону.
- `AnalyticsFacade.recordEvent` будет ВЫЗЫВАТЬСЯ из `CheckoutUseCase` (модуль `orders`, эпик
  `EP-09`) и, вероятно, из `catalog`/`search` (`EP-06`) для `search_performed`/`analog_shown`/
  `analog_clicked` — эти вызовы НЕ входят в этот тикет (см. `DTJ-380` для `order_placed`; вызовы из
  `catalog`/`search` — вне диапазона тикетов Tech Lead этого документа, координация с `EP-06`
  отдельно, вне созданного здесь набора).
- Файл `apps/api/src/modules/analytics/analytics.module.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
- Файл `apps/api/src/modules/analytics/index.ts` — barrel (D-27): правится ТОЛЬКО добавлением строки, перечитывать перед правкой, слияние конфликтов — за архитектором.
