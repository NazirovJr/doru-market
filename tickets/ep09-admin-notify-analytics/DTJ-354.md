## Задача
`super_admin` — единственная роль с кросс-тенантным доступом к пользователям (`SRS-ADM-030`).
Экран нужен для поддержки (найти пользователя по телефону при жалобе), деактивации при увольнении/
злоупотреблении и — что наиболее чувствительно — выдачи платформенных ролей (`super_admin`,
`support_agent`) новому сотруднику. Последнее действие обязано быть отделено от бытовой смены роли
сотрудника аптеки (`pharmacist`↔`courier`) и оставлять неизменяемый след в `audit_log`, поскольку
платформенная роль даёт доступ ко ВСЕМ тенантам.

## Технический контекст
`User` — агрегат контекста `identity` (`EP-01`), доступ ТОЛЬКО через `IdentityFacadePort` (создаётся
этим тикетом по аналогии с портами `DTJ-350`). `grant-platform-role` пишет в `audit_log` с НОВОЙ
категорией `'role_grant'` — эта категория ОТСУТСТВУЕТ в `11-database-schema.md`, вводится
`27-module-admin-moderation-onboarding.md` §10.1 (`SRS-ADM-030`/`SRS-ADM-062`) как
`ALTER TYPE audit_action_category ADD VALUE 'role_grant'`. Запись аудита выполняется через
`AuditLogPort`, объявленный тикетом `DTJ-374` (жёсткая зависимость — без него это действие не может
быть безопасно реализовано, `SRS-ADM-030` требует запись в `audit_log` как обязательное условие
действия, не опциональное дополнение).

## Что сделать
1. Миграция `00XX_audit_action_category_add_role_grant.sql` — `ALTER TYPE audit_action_category ADD
   VALUE 'role_grant';` ОТДЕЛЬНЫМ файлом с пометкой `-- disable-transaction` (`SRS-DB-009`,
   `SRS-ADM-078` — новое значение enum нельзя использовать в той же транзакции, где добавлено).
   Обновить `apps/api/src/db/schema/enums/audit-action-category.ts` (Drizzle enum-список) синхронно.
2. `IdentityFacadePort`: `listUsers(filter: { role?, phoneLike?, tenantId? }, pagination)`,
   `deactivateUser(userId, actor)`, `changeStaffRole(userId, newRole, actor)`,
   `grantPlatformRole(userId, role, reason, actor)`.
3. `ListUsersUseCase` — курсорная пагинация, фильтры `filter[role]`, `filter[phoneNumber][like]`,
   `filter[tenantId]` (`SRS-ADM-030`).
4. `DeactivateUserUseCase.execute({ userId, actor })` → `PATCH { isActive: false }` — НЕ физическое
   удаление, `deleted_at` зарезервирован под отдельную процедуру запроса на удаление ПДн (вне
   скоупа тикета, только не путать эти два действия в реализации).
5. `ChangeStaffRoleUseCase.execute({ userId, newRole, actor })` — Zod-схема ограничивает `newRole`
   ТОЛЬКО значениями `'pharmacist'|'courier'|'pharmacy_admin'` (400 при попытке передать
   `'super_admin'`/`'support_agent'` — эти два ТОЛЬКО через отдельный use case ниже). Домен
   `IdentityFacade` дополнительно проверяет «в рамках одной точки/сети» — эта проверка НЕ
   дублируется здесь (правило единственного источника инварианта).
6. `GrantPlatformRoleUseCase.execute({ userId, role: 'super_admin'|'support_agent', reason, actor })`
   — `reason` ОБЯЗАТЕЛЕН (Zod `.min(10)`, тот же паттерн, что `SRS-ADM-032`). Атомарно (одна
   транзакция через `unitOfWork`): (1) `IdentityFacadePort.grantPlatformRole(...)`; (2)
   `AuditLogPort.write({ category: 'role_grant', entityType: 'user', entityId: userId, actorUserId:
   actor.userId, reason, metadata: { before: { role: oldRole }, after: { role } } })`.
7. `UsersAdminController`: `GET /api/v1/users`, `PATCH /api/v1/users/:id`, `PATCH
   /api/v1/users/:id/role`, `POST /api/v1/users/:id/grant-platform-role` — все `@Roles('super_admin')`.
8. Frontend: `users-page.tsx` — таблица с фильтрами (роль, телефон, тенант), действия в контекстном
   меню строки: «Деактивировать» (confirm-модалка), «Сменить роль» (Select с 3 бытовыми ролями),
   «Выдать платформенную роль» (ОТДЕЛЬНАЯ форма с обязательным полем «Причина», явное предупреждение
   в UI о чувствительности действия).

## Критерии приёмки
1. Given `pharmacy_admin` вызывает `PATCH /users/:id/role { newRole: 'super_admin' }`, When Zod
   валидирует тело, Then `400 VALIDATION_ERROR` — платформенная роль физически недостижима через
   этот эндпоинт независимо от роли вызывающего (`ChangeStaffRoleUseCase` не принимает такое
   значение на уровне схемы, а не только на уровне guard'а).
2. Given `POST /users/:id/grant-platform-role` без `reason`, When запрос, Then `400
   VALIDATION_ERROR` — действие не выполнено, `audit_log` не создан.
3. Given успешный `grant-platform-role`, When транзакция коммитится, Then строка `audit_log
   (category='role_grant')` существует В ТОЙ ЖЕ транзакции, что смена роли (симметрично
   `SRS-ADM-032`/`TC-ADM-016`) — при откате транзакции роль НЕ меняется и аудит НЕ пишется (атомарность,
   не два отдельных запроса).
4. Given `PATCH /users/:id { isActive: false }` для пользователя, фигурирующего как актор в
   исторических `order_items`, When деактивация выполняется, Then исторические записи НЕ теряют
   ссылку (проверяется на уровне `IdentityFacade`, здесь — негативный тест «деактивация не удаляет
   пользователя физически»).

## Тест-план
Unit: `grant-platform-role.use-case.spec.ts` (успех → атомарная запись роли+аудита в одном
`unitOfWork.run`; отсутствие `reason` → `ZodError` до вызова фасада; откат `unitOfWork` при ошибке
`AuditLogPort.write` → роль НЕ применена — тест на согласованность двух побочных эффектов);
`change-staff-role.use-case.spec.ts` (Zod отклоняет `super_admin`/`support_agent`).

запись в `audit_log`, `SELECT audit_log WHERE category='role_grant'` после вызова). Порог
`application/` ≥ 90 %.

## Риски и подводные камни
- Жёсткая зависимость от `DTJ-374` (`AuditLogPort`) — если порядок разработки в спринте нарушен
  (эта задача взята раньше), временная заглушка `AuditLogPort` (`NullAuditLogPort`, аналогично
  `NullSearchProvider` из `DTJ-180`) допустима ТОЛЬКО как промежуточный шаг, финальная сдача тикета
  требует реального порта.
- `newRole` в `ChangeStaffRoleUseCase` намеренно НЕ включает `'customer'` — понижение сотрудника до
  клиента не специфицировано документом 27 и не реализуется этим тикетом (риск: если появится
  реальная потребность — отдельный ADR, не молчаливое расширение enum значений use case).
