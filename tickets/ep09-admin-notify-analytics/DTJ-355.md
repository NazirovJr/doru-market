## Задача
Реализует `orders:read:any` (единственная роль с безусловным кросс-тенантным доступом к заказам,
`12-api-conventions-auth-tenancy.md` §4.1) — необходимо для расследования инцидентов, ответа на
жалобы клиентов и подготовки к ручному вмешательству (`DTJ-356`). Без полной временной шкалы
оператор не может понять, на каком шаге застрял конкретный заказ, не читая логи вручную.

## Технический контекст
Доступ к `Order` — ТОЛЬКО через `OrdersFacadePort` (расширяется этим тикетом, порт создан
`DTJ-350`). Связанные сущности из ДРУГИХ модулей — `escrow_ledger` (`PaymentsFacadePort`),
`prescription` метаданные (порт `PrescriptionsFacadePort`, добавляется этим тикетом — четвёртый
внешний факт, которого не было в исходном наборе `DTJ-350`, добавляется по мере необходимости, как
и предполагалось). Доступ к самому изображению рецепта — НЕ этот тикет (`SRS-DOM-155в`, отдельный
клик с аудитом — покрывается интеграцией с `DTJ-374`/`DTJ-376`, здесь только `prescriptionId` +
статус метаданных).

## Что сделать
1. Расширить `OrdersFacadePort`: `findOrdersAny(filter: { orderNumberLike?, status?, tenantId?,
   pharmacyId?, customerId?, createdAtFrom?, createdAtTo? }, pagination)`,
   `getOrderTimeline(orderId)` (возвращает временные метки всех переходов
   `processing_started_at/picked_up_at/delivered_at/...`).
2. Создать `PaymentsFacadePort.findEscrowLedgerByOrder(orderId)`,
   `PaymentsFacadePort.findPayoutScheduleByOrder(orderId)` — добавить в существующий порт
   `DTJ-350` (не создавать второй файл порта для того же фасада).
3. Создать `PrescriptionsFacadePort.getPrescriptionMetaByOrder(orderId)` — возвращает ТОЛЬКО
   `{ prescriptionId, status }`, без URL изображения (`SRS-ADM-031`: «только метаданные статуса...
   доступ к самому изображению требует отдельного клика с явной причиной»).
4. `ListOrdersAnyUseCase` — курсорная пагинация, полнотекстовый `filter[orderNumber]`, фильтры
   `status`/`tenantId`/`pharmacyId`/`customerId`, диапазон `createdAt`.
5. `GetOrderDetailAdminUseCase.execute({ orderId })` — агрегирует: детали заказа
   (`OrdersFacadePort`), таймлайн, `payoutSchedule`/`escrowLedger` записи ЕСЛИ
   `paymentMethod != 'cash_courier'` (`REQ-PAY-14`, для `cash_courier` секция явно помечена в UI
   «эскроу не применяется — оплата наличными», не пустая таблица без объяснения), `prescriptionMeta`
   если есть.
6. `OrdersAdminController`: `GET /api/v1/orders` (без `scope=own`/`scope=pharmacy` — реализует
   `orders:read:any`), `GET /api/v1/orders/:id` — `@Roles('super_admin')`.
7. Frontend: `orders-list-page.tsx` — таблица с фильтрами (номер, статус — Badge, тенант, аптека,
   диапазон дат). `order-detail-page.tsx` — компонент `OrderTimeline` (`packages/ui`, уже
   специфицирован `30-ux`), блок эскроу-записей (READ-ONLY таблица), блок рецепта (статус-бейдж +
   кнопка «Показать изображение» — обработчик кнопки реализуется тикетом `DTJ-376`, здесь только
   заглушка с `TODO(DTJ-376)`, кнопка неактивна до готовности того тикета).

## Критерии приёмки
1. Given заказ `payment_method='cash_courier'`, When открывается деталь заказа, Then блок
   эскроу-записей показывает явное сообщение «Эскроу не применяется — оплата наличными», НЕ пустую
   таблицу без объяснения (`REQ-PAY-14`, инвариант `paid_escrow ⟺ существуют записи escrow_ledger`
   из D-25 согласуется визуально).
2. Given `super_admin` открывает `GET /orders/:id` для ЛЮБОГО тенанта, When запрос обрабатывается,
   Then `200` без проверки `tenant_id`-принадлежности (в отличие от ВСЕХ остальных ролей).
3. Given `filter[orderNumber]=ORD-2026-000042` (точный номер), When поиск, Then возвращается
   ровно один заказ (или пусто, если не существует — `data: []`, не `404` для спискового
   эндпоинта, `SRS-API-014`).
4. Given `pharmacist` вызывает `GET /api/v1/orders` без `scope`, When guard проверяет `@Roles`,
   Then `403 INSUFFICIENT_ROLE` (эндпоинт `orders:read:any` физически недоступен этой роли,
   негативный сценарий).
