## Что работает руками

- **API физически не запускается штатной командой.** `apps/api/tsconfig.json` (на него
  указывает `nest-cli.json`) содержит `"noEmit": true` → и `nest build`, и
  `pnpm --filter @dorutj/api dev` компилируются с «0 errors», но не создают `dist/` →
  процесс падает на старте: `Cannot find module dist/main`, до открытия порта. Это происходит
  **до** попытки подключения к БД/Redis — `curl /health` и `/ready` физически невозможны в
  текущем состоянии дерева. Прямой обход через `tsx` (не штатный способ) вскрывает ещё и
  DI-проблему `UndefinedDependencyException` на `IdempotencyInterceptor` (вероятно, артефакт
  отсутствия `emitDecoratorMetadata` у esbuild/tsx, не проверено при штатной сборке).
- **apps/web** — собирается (`vite build`), 199 модулей, `dist/` создаётся, ~313KB основной
  чанк. Но 2 из 37 тестов красные: авто-refresh JWT-токена на 401 `TOKEN_EXPIRED` не вызывает
  refresh вообще (`expected 1 call, got 0`) — сессионный flow сломан даже в юнит-тесте.
- **apps/admin** — собирается (`vite build`), 87 модулей, `dist/` создаётся. Возвращён в
  `arch:check`, 0 собственных нарушений — этот пункт критерия завершения волны 3.5 выполнен.
- **Каталог не грузится в БД.** Seed-данные реальны и превышают порог (317 medicines /
  87 substances / 18 categories, JSON), но `pnpm db:seed` завершается `exit 2` осознанно —
  `DrizzleSeedCatalogPort` не реализован. Ни одна из 317 позиций физически не попадает в БД.
  `pnpm db:migrate` — не заглушка, реально пытается `CREATE SCHEMA` через `drizzle-orm/pg`,
  падает `ECONNREFUSED` (в песочнице нет живого Postgres — ограничение среды, не находка по коду).
- **docker compose config валиден** (`docker compose config` рендерит полный merged-конфиг:
  postgres/redis/api/worker/migrate/seed/minio), но реальный запуск контейнеров не проверен
  (Docker Desktop не поднялся в песочнице за ~10 минут) — не находка по коду, ограничение среды.
- **Ни docker-compose.yml/Dockerfile в реальном прогоне, ни .github/workflows нигде не
  проверены живьём** — CI/деплой-пайплайна физически нет в репозитории.
- **19 HTTP-маршрутов существуют статически** (health/ready/docs, auth: otp/refresh/logout/
  sessions/telegram/me, staff-accounts, catalog: categories/medicines, inventory: batch-update,
  onboarding-documents, pharmacy-accounts/chains/verifications, admin verifications) — но ни
  один не проверен живым curl из-за пункта выше.
- **typecheck 14/14 пакетов зелёные** (форс-прогон без кэша) — фундамент типов исправен.
- **`pnpm test`/`turbo run test` не зелёный нигде за пределами domain-kernel/contracts/worker
  тест-кейсов**: сами ассерты в этих трёх пакетах проходят (29+1skip / 158 / 32), но команда
  падает `exit 1` на coverage-порогах (worker statements/branches ~28-43% при пороге 70%;
  contracts branches 46% при 70%; domain-kernel lines/branches ниже 90%). Итого ВСЕ 6 пакетов
  с тестами дают ненулевой код возврата в `pnpm verify`, не только apps/api и apps/web.

**Итог по этому разделу: продукт нельзя потрогать руками ни через один реальный HTTP-запрос.**
Единственный вход (apps/api) не запускается из-за конфигурационного дефекта сборки, не из-за
отсутствия инфраструктуры.

## Готовность к волне 4

**Ответ: НЕ НАЧИНАТЬ волну 4 в буквальном виде — ни как EP-05 «Приём остатков» (канонически
верно), ни тем более как эпик поиска (что бриф ошибочно называет «EP-05»). Допустимо частичное
исключение: 2 стартовых тикета эпика поиска без зависимостей можно вести в отдельной ветке
параллельно с закрытием долга — не сливать в `main`, пока не закрыты блокеры ниже.**

Обоснование по графу зависимостей (`tickets/00-EPICS.md`): волна 4 = EP-05 (Приём остатков),
зависит от EP-03 (онбординг) и EP-04 (каталог). Волна 5 = EP-06 (умный поиск), зависит от
EP-04 **и** EP-05. Ни то, ни другое условие не выполнено:

- EP-04 не закрыт: read-репозитории in-memory, `db:seed` не работает (`exit 2`), фасад
  composite-матчинга — заглушка, 2 красных теста.
- EP-05 сам ещё дальше от готовности (5/31), чем EP-04 — а именно EP-05 физически и есть
  волна 4. Начинать волну 4 «начинать волну 4» бессмысленно — это уже идущий, наполовину
  сделанный минимально эпик, а не новый старт.
- Формальное закрытие волны 3.5 (собственные критерии STATE-документа §11.5: `pnpm verify`
  зелёный целиком, ноль красных тестов, `pnpm db:seed` работает, приложение поднимается и
  отвечает на curl) не достигнуто ни по одному пункту, кроме «apps/admin вернулся в arch:check».

**Если вопрос буквально про 20 тикетов эпика поиска (DTJ-180..199, канонически EP-06,
ошибочно названных «EP-05» в задании) — детализация:**
