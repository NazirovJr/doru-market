# tests/arch/ — ловушка для ловушки

> DTJ-415. Источник требования: `docs/02-CLEAN-ARCHITECTURE-AND-CODE.md` §6.1.
> «Ловушка, которая перестала ловить, молчит об этом: ловушку нужно проверять ловушкой.»

## Что это и что это НЕ

Эта папка — **не пример для копирования** и не место для настоящего бизнес-кода. Каждый файл
под `tests/arch/fixtures/**` — минимальный синтетический TypeScript-файл, который НАМЕРЕННО
нарушает ровно одно архитектурное правило из `.dependency-cruiser.cjs`/`eslint.config.mjs`.

`tests/arch/run-fixture-check.spec.ts` (Vitest) программно запускает ESLint и/или
dependency-cruiser против каждой фикстуры и проверяет, что инструмент её отвергает: код
возврата ≠ 0 и вывод содержит ожидаемый фрагмент сообщения из таблицы §6.1 документа.

## ЭТИ ФАЙЛЫ ДОЛЖНЫ ПАДАТЬ

Если `run-fixture-check.spec.ts` вдруг позеленел на какой-то фикстуре — это значит, что
`.dependency-cruiser.cjs` или `eslint.config.mjs` молча ослабли (например, при обновлении
версии ESLint/dependency-cruiser или при рефакторинге конфига), и граница архитектуры больше
не охраняется.

**В этом случае: НЕ удаляйте фикстуру и не подгоняйте тест под новое (зелёное) поведение.**
Почините конфигурацию так, чтобы правило снова ловило нарушение. Фикстура — контрольная точка,
а не помеха.

## Изоляция от продуктовой сборки

- `tests/arch/fixtures/**` НЕ входит ни в один продуктовый `tsconfig.json` (`apps/*/tsconfig.json`,
  `packages/*/tsconfig.json`) — `pnpm --filter <app> build`/`typecheck` их не видит.
- `pnpm arch:check` = `depcruise --config .dependency-cruiser.cjs apps packages` — таргет не
  включает `tests/`, поэтому фикстуры физически не участвуют в обычной проверке.
- `eslint.config.mjs` → `ignores` содержит `'tests/arch/fixtures/**'` — обычный `pnpm lint`/
  `pnpm verify` их пропускает молча (иначе намеренно нарушающие правила файлы вечно ронял бы
  весь репозиторий). `run-fixture-check.spec.ts` обходит это исключение явно флагом
  `eslint --no-ignore` — то есть правило проверяется, а не обходится стороной.
- У каждой фикстуры — свой локальный `tsconfig.json` внутри её собственной папки. Он нужен
  ТОЛЬКО чтобы `parserOptions.projectService: true` в ESLint мог распарсить файл (без
  включения в какой-либо tsconfig ESLint выдаёт `Parsing error`, см. §6.1 документа) — это НЕ
  делает фикстуру частью продуктовой сборки.
- `tests/arch/tsconfig.json` — отдельный tsconfig ТОЛЬКО для `run-fixture-check.spec.ts`
  (`include` явно перечисляет один файл, `fixtures/**` в него не входит).

## Почему у некоторых фикстур файлы вложены глубже, чем кажется нужным

Правила `no-cross-module-deep-import` и `fe-features-are-isolated` в `.dependency-cruiser.cjs`
заякорены на `^apps/(api|worker)/src/modules/...` / `^apps/[^/]+/src/features/...` — то есть
требуют, чтобы путь модуля (относительно cwd запуска dependency-cruiser) буквально начинался с
`apps/...`. Поэтому `cross-module-deep-import/` и `frontend-horizontal-feature-import/`
физически содержат вложенную структуру `apps/api/src/modules/...` /
`apps/web/src/features/...` внутри СВОЕЙ собственной папки фикстуры, а
`run-fixture-check.spec.ts` запускает dependency-cruiser с `cwd`, указанным на саму папку
фикстуры (а не на корень репозитория) — тогда относительный путь совпадает с якорем правила.
Остальные правила (`domain/`, `application/`, `infrastructure/` — без `^`) не заякорены и не
требуют этой техники.

## Как добавить новую фикстуру под новое архитектурное правило

1. Найди правило в `.dependency-cruiser.cjs` или `eslint.config.mjs`, для которого нет фикстуры.
2. Создай `tests/arch/fixtures/<kebab-case-имя-нарушения>/` с МИНИМАЛЬНЫМ `.ts`/`.tsx`-файлом,
   нарушающим ровно это правило и ничего больше.
3. Если правило проверяется ESLint с `projectService: true` — добавь в папку фикстуры
   локальный `tsconfig.json` (скопируй с соседней фикстуры, `include: ["**/*.ts", "**/*.tsx"]`).
4. Если правило dependency-cruiser заякорено на `^apps/...` — вложи путь `apps/...` внутрь
   папки фикстуры и запускай depcruise с `cwd` на саму папку фикстуры (см. раздел выше).
5. Добавь `it(...)` в `run-fixture-check.spec.ts`: точный инструмент (ESLint и/или
   dependency-cruiser — не «один из двух», а явно какой), точный ожидаемый фрагмент сообщения
   из правила/документа, `expect(exitCode).not.toBe(0)`.
6. Прогони `pnpm test:arch` — новый кейс обязан упасть, если временно закомментировать
   проверяемое правило в конфиге (ручная проверка при код-ревью, см. DTJ-415 АС3), и обязан
   пройти в норме.
